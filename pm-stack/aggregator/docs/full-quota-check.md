# Full-quota utilization plan and the 4–6h check

Drew's standing rule (#2173, 2026-10-29): **if a plan is not on track to be
used in full by its reset, queue more useful work.** Leftover quota is
waste; useful work done sooner is not a bad thing.

This directory holds the plan that rule needs and the records of every
check that keeps it current:

| File | What it is |
| --- | --- |
| `full-utilization-plan.md` | The standing plan, one row per pool's largest window. Regenerated by every check; do not hand-edit the tables. |
| `full-utilization-plan.json` | The same plan in machine form — the baseline the next check diffs against. |
| `quota-checks/<instant>.json` | One add-only record per check run: verdict, per-pool escalations, verdict changes, landing drift, and the dated audibles that were due. |

The code is `pm-stack/aggregator/scripts/quota-full-utilization-plan.ts`
(CLI) over `pm-stack/aggregator/src/quota-plan.ts` (pure model), tested by
`pm-stack/aggregator/test/quota-plan.test.ts`.

## Where the numbers come from

Nothing in the projection is assumed. Both the fresh reading and the burn
history come from the quota ledger the gatherer already writes every 15
minutes: Turso `fleet-platform.agent_quota_records`, source
`opencode-quota` (the single producer, `opencode quota --json`). The
newest row is the fresh reading; the series around it is the history.

- **Largest window per pool** by duration (`monthly` > `weekly`/`7d` >
  `5h`; per-model Antigravity windows resolve by their suffix). Only
  windows that carry a percentage are candidates.
- **Burn rate** is measured, not assumed: the net change across the
  current window segment, over the time between the ends. A reset inside
  the series is segmented out (a material drop restarts the measurement),
  and each end is the mean of up to three samples with the single most
  extreme value dropped, so one bad tick cannot move the projection. The
  measurement is capped at 168h of history so month-old data cannot
  dominate a monthly window. The trailing 24h rate is computed the same
  way as an acceleration signal (reported in the row's notes when it
  differs by more than 50%).
- **Projection** is `current + rate × hours-to-reset`, plus the same rate
  applied to a whole period for the **reset after next**. A plan that
  lands this period but strands the next is not a plan, so the next
  period's landing is in the table and called out in the row notes.
- **Required burn** is `(100 − current) / hours-to-reset`: the rate that
  lands the pool at ~100% exactly at its reset.
- **Cascade** is the routing fallback map (`CASCADE_GROUPS` in
  `src/quota-plan.ts`): the pool's position in its capability group, its
  successor when it walls, and the spill (in percentage points of its own
  window) the successor absorbs. Percent-only readings have no absolute
  denominator, so spill is flow-sized, the same convention the quota
  registry uses. Changing routes or weights remains Drew's call — this map
  only models the consequence.

Multi-credential pools write several rows per tick under one pool id with
no credential label in the payload (`openai.main` does this for two weekly
credentials). The plan collapses each tick to the **binding** read — the
credential closest to walling, never the comfortable one — and says so in
the row's notes.

## Verdicts and what each one does

| Verdict | Meaning | Audible |
| --- | --- | --- |
| `under_pace` | Projects below 90% at reset (or no burn measured with time left) | `queue-catch-up`: dated next check, names the shortfall, the required pts/day, the provider/model class and the queue to put the work in; carries the last useful action date |
| `over_pace` | Projects above 105% at reset while still burning | `flag-drew`: dated now — slow down, or keep progressing (default bias: keep useful work); names the cascade successor |
| `exhausted` | Already at ~100% for this period | `confirm`: fully used; work routes to the cascade successor until the reset |
| `on_track` | Projects inside the ±5/10-point band | `confirm` at the next check, or `plan-next-period` when the following period would strand quota |
| `stale` | Newest reading older than 6h | `repair-reading` |
| `no_reset` | Reading carries no reset instant (e.g. `_commandcode` monthly) | `repair-reading` |

## The check

```
bun run scripts/quota-full-utilization-plan.ts --check
```

A run:

1. applies the **4–6h due guard** against the newest record in
   `quota-checks/` (default interval 6h; `--force` runs anyway);
2. reads the ledger and rebuilds the plan;
3. **diffs** it against `full-utilization-plan.json` — verdict changes,
   landing drift ≥ 5 points, newly actionable pools, cleared pools;
4. rewrites the standing plan and writes one add-only check record;
5. prints the verdict, the escalations, and every audible that is due.

Exit status is 0 unless `--fail-on-escalate` is passed (a cron must not
be retried for an escalation; the steward reads the output).

`--replay --replay-hours 48 --step-hours 6` runs the same check at
successive past instants over the recorded series and writes one record
per step. Replay is how the cadence was backfilled when the check was
introduced; the records are marked `"mode": "replay"` so nobody mistakes
them for live runs. `--from-file <jsonl>` reads decoded ledger rows
instead of Turso (offline runs and tests).

## Integration: the steward runs the check

The check is **not a new job**. `pool-quota-steward` (hourly) already
carries the balance pass, and its step 2 asks for "any pool whose window
will expire unspent (burn-by-expiry — prefer feeding it real queued work
via a note to the dispatcher log)". The full-quota check is the measured
form of that question: same job, same slot, deterministic numbers, and a
record of every verdict. It self-throttles to 4–6h on its own record log,
so the job's cadence does not change (cadence changes are Drew's call;
#2173 carries his 4–6h direction for this check).

Two job surfaces use it, and neither is a duplicate:

- **`pool-quota-steward`** (`interval@1h`,
  `/home/hatch/workspace/goals/keep-the-four-repos-healthy/crons/hourly/pool-quota-steward__interval@1h.md`,
  delegating to `hidden_files/pool-quota-steward-instruction.md`) — the
  hourly balance pass gains this step 2a. The check's due guard keeps it
  to 4–6h:

  ```
  2a. Full-quota plan + 4–6h check (#2173). Run
      `bun run scripts/quota-full-utilization-plan.ts --check` from
      pm-stack/aggregator in the code checkout. It self-throttles to
      its 4–6h cadence, so an hourly run is correct. Use the verdicts in
      this step: `under_pace` → queue the work the row's
      `queue-catch-up` audible names (shortfall, required pts/day,
      destination queue, provider model class) and record it in the
      ledger; `over_pace` → post the `flag-drew` audible as a comment on
      #2173, deduped per this job's 24h rule, default bias
      keep-progressing; `repair` → name the unjudgeable pools in the
      report. `--check` rewrites docs/full-utilization-plan.{md,json}
      and appends docs/quota-checks/<instant>.json — commit both in the
      same pass (the schedule registry's same-pass rule).
  ```

- **`go-plan-expiry-watch`** (the live 6h "Full-quota check" job) — it
  already performs this check in prose (plan v47 at
  `~/workspace/research_notes/quota-burn-plan-20261029/plan-current.md`).
  Its projection step should call the same engine instead of re-deriving
  rates by hand, and archive the plan to `plan-history/` before
  overwriting. The command is the same `--check`; point `--plan-dir` at
  the goal workspace and let the job copy the previous plan into
  `plan-history/` first.

The live job definitions change only through the host's `cron.update` /
instruction edit on the Muse sandbox — editing the mirror copy on the
laptop changes nothing. The insertion above is the whole change; the
registry row records it in the same pass.

## Limits

- Percent-only readings give flow-sized cascade spill, not absolute
  tokens; the quota registry has the same constraint.
- Step meters (providers that refresh a percentage every few minutes to
  an hour) make short-period rates provisional; those rows say so.
- A brand-new period starts with no burn, so a pool judged in its first
  hour is on track by construction rather than by evidence.
- Multi-credential pools are planned at their binding credential, as
  described above.
