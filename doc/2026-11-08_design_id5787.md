# Design: Spill v2 — native spill pools, lease failover, and multi-holder fencing

- Date: 2026-11-08
- Status: **decision-ready proposal** — design only; no protocol code is implemented here.
- Issue: [#5787](https://github.com/developing-today/code/issues/5787), parent epic [#2056](https://github.com/developing-today/code/issues/2056).
- Extends: [#2819](https://github.com/developing-today/code/issues/2819) (v1 single-holder spill lease; design doc `doc/2026-11-01_design_id2819.md`; phases [#3803](https://github.com/developing-today/code/issues/3803) closed, [#3804](https://github.com/developing-today/code/issues/3804) / [#3805](https://github.com/developing-today/code/issues/3805) open).
- Related: [#2818](https://github.com/developing-today/code/issues/2818) (region-seam handoff, closed — journaled export/import), [#2059](https://github.com/developing-today/code/issues/2059) (hot-world investigation, closed), [#5685](https://github.com/developing-today/code/issues/5685) (fairness-attack cases the multi-world section composes with), and the deterministic-testing design (failover interleavings are one of its named oracle cases).
- V1 invariants are inherited, not restated for amendment: one authoritative journal and one append gate per world, the Durable Object (DO) as sole lease grantor and append authority, epoch fencing at the append linearization point, no local commits by a native node, fail-closed recovery. Everything below is an extension of v1's protocol, never a second authority.

## Decision to make

When a spilled world needs more than the one native holder v1 designs for — the holder dies mid-term, a second native node is available, read load grows, or one host spills many worlds — what does the lease protocol do, and what does it honestly refuse to do?

## Recommendation

**Honest v2 is failover + read replicas + a pool of eligible holders. It is not write scaling.** At every instant a world still has exactly one holder and one epoch chain, exactly as in v1. The pool changes *who can become* the holder and how fast a replacement is granted; it never lets two holders commit in parallel. The three open questions are answered in §Answers; the load argument for refusing concurrent writers is:

1. **The append gate is the write bottleneck by design.** Every accepted mutation is serialized, epoch-checked, and fsynced by the DO's single append gate (v1). Adding holders cannot raise that ceiling; it can only add contenders to it. Write throughput of a single world is bounded by journal append latency, not by executor count.
2. **Executor parallelism does not exist inside one world to scale.** The world actor runs turns serially (v1 context: `actor.rs` handles commands serially, and program state is a single in-memory image restored from the journal prefix). Two executors for one world would need partitioned world state — that is sharding, a different design (see §Region interplay: that need is served by *moving* or *splitting*, not by spilling wider).
3. **What a hot world actually runs out of first is (a) survival — its one holder dies and the world waits out a term with no failover path — and (b) read capacity.** Both are real, both are designed below, and neither needs a second writer.

So v2 adds: automatic holder failover (§1), a spill pool with reader-then-holder admission (§2), fenced read replicas with explicit staleness (§3), multi-world composition and fairness on one host (§4), and a spill-vs-move rule (§5). Concurrent multi-writer spill is **rejected** (§Viable options), and the trigger that would reopen it is named in §Load triggers.

## Viable options

| Option | Trade-offs | Decision |
| --- | --- | --- |
| **Pool of eligible single holders + automatic failover + read replicas (this design)** | Keeps v1's split-brain proof untouched (one holder, one epoch chain, one gate); solves holder death, read load, and drain overlap. Does not raise single-world write throughput. | **Recommend.** It is what the load evidence supports (§Answers Q1). |
| Concurrent multi-holder writes with partitioned epochs | Would need a merge/conflict rule for one journal and partitioned program state; breaks v1 invariant 1–3 (one append order, monotonic single epoch chain) and reopens the catastrophic split-brain case #2819 was designed to exclude. | Reject. If write scaling is ever proven necessary, it arrives as world *splitting* under the region/shard designs, not as parallel holders of one journal. |
| Failover only, no pool (operator picks the next holder by hand) | Smallest delta from v1; but failover waits on a human, and an unprepared replacement pays full replay before it can hold, stretching the outage the failover exists to shorten. | Reject as the end state; it is phase 1 of the recommended option with the pool roster set to one standby. |
| Stretch v1 by hand (operator revokes and re-grants ad hoc) | Available today on paper, but the in-flight command posture, candidate readiness, and flap protections are exactly what improvisation gets wrong under incident pressure. | Reject. This is the failure mode #5787 was filed to pre-empt. |

## Answers to the issue's open questions

### Q1 — Is write scaling ever actually needed?

**Decision: no, not on any evidence available, and v2 does not build it.** Per the load argument above, a single world's durable write rate is capped by the serialized append gate, and its execution is serial by construction. The plausible hot-world pressures are holder loss, read volume, and *many* hot worlds — addressed by failover, replicas, and multi-world spill respectively. Write scaling for one world would be a claim that append-gate serialization itself is the measured bottleneck *and* that the world's program state is partitionable; the first has no measurement behind it and the second contradicts the single-actor world model. **Deciding evidence to reopen:** production spill telemetry showing the append gate (not the executor) saturated for a single world across a sustained window, with replay/benchmark reproduction — owner: whoever operates the first production spills; the reopening proposal must come as a world-splitting design, not a lease amendment (§Load triggers, trigger T4).

### Q2 — Lease term / renewal defaults under failover (v1: 30 s term, 10 s renewal)

**Decision: keep 30 s / 10 s unchanged for v2.** Failover's worst-case detection-plus-revoke latency is one term (30 s) because the DO may not grant to a successor until the old epoch is fenced by expiry or by a journaled revoke (§1) — shortening the term is the *only* lever that shortens that bound, and it is a bad trade on current evidence:

- Renewal cost is one journaled control append per renewal per spilled world. At 10 s that is 0.1 appends/s — noise next to any mutation traffic worth spilling. Even a 10 s / ~3 s term would only triple a negligible number, so **journal traffic is not the constraint either way**; the real cost of short terms is false expiry: a holder paused by GC, scheduling, or a transient network stall longer than the term loses its epoch and pays discard-and-replay, and frequent false failovers flap the world between holders.
- The recovery-time side is dominated not by the term but by **successor replay**: a cold successor must replay to the grant position before accepting work (v1 replay barrier). Pool read-replicas (§2) attack that term directly — a caught-up replica fails over in grant-plus-one-append time — which buys back most of the recovery a short term promises, without the flap risk.

**Deferred tuning, with the deciding evidence and owner named:** term/renewal values are revisited only when both exist: (a) failover measurements from the #3805 failure-walkthrough tests extended with the §7 failover interleavings (measured detection, grant, and replay-to-ready times), and (b) at least one real or game-day holder-death failover with its timeline. Until then 30 s / 10 s stands. Owner: the v2 failover implementation follow-on (§Implementation follow-ons, F1). No product decision is needed from Drew.

### Q3 — Does journal-position-as-truth survive holder changes across nodes with skewed clocks?

**Decision: yes, unchanged — because neither the epoch nor expiry is ever read from a holder's clock.** V1 already assigns the epoch at the DO's serialized append gate, in journal order, and checks expiry against the DO clock only. V2 keeps both rules and makes the clock contract explicit:

- The **epoch** is a logical counter advanced only by DO-appended grant/revoke/handoff records. It is a position in the journal, not a timestamp; clock skew between native nodes cannot create, skip, or reuse one.
- **Expiry** is decided only at the append gate, against the DO clock, at the linearization point (v1). A holder's local clock is used for exactly one thing: a conservative dead-man switch — the holder stops submitting when *its own* clock says the term has lapsed without a renewal receipt — and skew there fails safe in both directions (a fast holder clock stops it early; a slow holder clock keeps it submitting, and the gate rejects its fenced appends, which are audited, never applied).
- **Renewal receipts carry journal positions, not times the holder must trust.** A holder knows its lease is live because it holds a durable renewal receipt at a journal position, under its epoch — the same position-as-truth rule v1 uses for handoff barriers, extended to failover grants (§1).

## 1. Holder failover

V1 designs polite handoff and expiry recovery (revoke, then grant, DO resumes). V2 automates recovery *to a pool successor* and names the postures v1 leaves implicit.

### Detection

The DO is the only detector that matters, because it is the only grantor:

- **Missed renewal preconditions.** The DO renews a healthy, caught-up holder every 10 s (v1). A holder that is unreachable, or that stops acknowledging renewal receipts, or whose submissions stop arriving, is *suspect* at the first missed renewal cycle and *expired* only when the term lapses on the DO clock. Suspicion starts successor preparation (§2 catch-up check); it grants nothing.
- **No holder-side self-promotion.** A partitioned or restarted node never declares itself, or anyone else, holder. There is no election in the pool; there is only the DO's next grant record.

### Failover sequence (normative)

1. **Fence.** The old epoch ends in exactly one of v1's two ways: term expiry on the DO clock, or a journaled `LeaseRevoked` (operator-requested, or DO-issued after expiry as in v1 recovery). An operator revoke *before* expiry is safe for the same reason handoff is: the epoch advances at one journal position, and the old epoch fails the gate from that position on. Its risk is availability flapping, not correctness — so pre-expiry revoke is operator-only, never automatic.
2. **Select.** The DO picks the successor by the §2 selection policy among pool members that are caught up to the current journal tip (or can be brought to it within the catch-up bound). If none qualifies, the DO grants to *itself* (v1 recovery) rather than to a lagging node.
3. **Grant.** The DO appends `LeaseGranted { holder: successor, epoch: old_epoch + 1 }` (via the revoke-then-grant pair when a revoke is needed, exactly as v1). The grant record's journal position is the failover barrier.
4. **Replay barrier.** The successor replays through the grant position before accepting or submitting anything — the same barrier as a v1 handoff. A caught-up read replica (§2) satisfies this at grant time; a cold node pays replay here, and that cost is measured, not hidden (§Answers Q2).
5. **Resume.** The successor executes under the new epoch; the append gate fences the old epoch's submissions as in v1, including the rejection-audit rule.

A crash between revoke and grant leaves the world **unavailable, not split-brained** (v1's rule, unchanged).

### In-flight command posture

V1's posture — a command durably appended before the boundary stands; an unappended command gets a retryable `not-holder` and the client retries with the same `operation_id` to the command-level dedupe — extends with one new retryable result and no new semantics:

- Commands in flight at failover resolve exactly as at handoff: appended-before-barrier ⇒ committed, receipt returned on retry via dedupe (even though the retry reaches a *different holder* — dedupe is keyed by the client's original request identity, v1); not appended ⇒ retryable.
- The retryable result during the fence-to-grant window is `holder-lost` (distinct from `not-holder`, which means "you reached a node that is not the holder in steady state"). `holder-lost` tells the client the world is mid-failover and to retry with backoff against any pool member / the DO; it is never a terminal error and never carries speculative results.
- The dead holder's speculative in-memory work is discarded exactly as after a rejected append in v1: nothing it did not get through the gate exists.
- A *second* spill requested while the first is still draining (v1 handback in progress) does not create a second lease chain: the request is recorded as a pending intent by the DO and either coalesces into the post-handback grant decision or is cancelled by the handback completing. Pending intent is grantor-side state, not a journal lease record — it can never fence or grant anything.

## 2. Spill pool

### Membership and eligibility

- The pool is a **grantor-side eligibility roster**: the set of native nodes the DO may grant this world's lease to. Roster changes are operator/configuration actions on the DO side; they are not journal lease records and cannot affect a live epoch. A node not on the roster can never receive a grant, whatever it claims.
- A roster member is **eligible** for a specific grant only when: its identity authenticates as in v1 (authenticated writer identity bound to the node's signing identity), it is reachable, and it is **caught up**: it has replayed through the journal tip the grant will name, or within a bounded lag it can close before the grant barrier (the grant waits for the barrier, §1 step 4 — eligibility is about *bounded* catch-up, not zero lag).
- Roster size is expected to be small (2–4). The pool is a standby set, not a fleet: nothing in this design load-balances one world's writes across it (§Recommendation).

### Selection policy

Deterministic, in this order, evaluated by the DO at grant time:

1. **Caught-up first** — a member already at the tip (in practice, a read replica, §3) beats a member that must replay.
2. **Healthy and least-loaded** — by the host's own reported load and its current holder count (§4 admission state).
3. **Stickiness** — the previous holder, if eligible and the failure was not its death (e.g. after a handback or an operator revoke), wins ties: gratuitous holder changes cost replay and cache warmth and buy nothing.
4. **Deterministic tie-break** — by node identity order, so two grant decisions from the same inputs agree and the choice is auditable from the grant record.

**Flap protection:** a minimum tenure applies to automatic grants — after an automatic failover grant, no further *automatic* failover is granted for the same world until the new holder has served at least one full term, unless the new holder itself expires. Failover storms degrade to v1 expiry recovery, never to grant churn.

### Reader-then-holder join

A node joins a world's pool in two steps, never directly as holder:

1. **Reader join.** The node subscribes as a read replica (§3), replays from a checkpoint plus journal tail, and begins serving fenced reads with its position watermark. This proves reachability, identity, and replay throughput on live traffic with zero write risk.
2. **Holder eligibility.** After the replica has stayed within the catch-up bound across a continuous observation window (default: ten consecutive renewal cycles at the tip), the DO marks it eligible for grants. Eligibility lapses if the replica falls beyond the catch-up bound; regaining it requires a fresh window. There is no path from "just booted" to "holder" that skips the reader stage.

### Epochs stay per-world global

Epochs are **never partitioned** across the pool. There is one epoch counter per world journal, advanced only by the DO's lease records in journal order (v1 invariant 3, restated for the pool). Partitioned epoch spaces (per-node ranges, vector epochs) would require a merge rule at the gate and would break the proof that at any journal position exactly one epoch is current. Pool members hold no epoch state of their own between grants: a node's authority is entirely "the current grant record names me, at this epoch, and my last durable renewal receipt is at this position."

## 3. Read-your-spill (read replicas)

### What a replica is

A pool member replaying the world's journal from the DO's authoritative stream (v1's read mirror, given a contract). A replica has no append path, no lease, and no authority to acknowledge mutations — v1 invariant 4 applies verbatim.

### Staleness contract

Every replica serves reads **at a named journal position** (its replay watermark) and says so:

- A read response carries the position it was served at. "Stale" is therefore a measurable value (tip − served position), not a vibe.
- **Bounded service:** a replica serves a read only while its lag is within a configured bound (positions and/or wall time on the DO-stamped stream). Beyond the bound it refuses with a retryable `replica-behind` rather than serving silently old state — the read-side analogue of v1's `journal-behind`.
- **Read-your-writes:** a client presenting its last acknowledged position (from any prior mutation receipt) is served only when the replica's watermark is ≥ that position; otherwise the replica waits for replay to reach it (bounded wait) or redirects the client to the holder/DO. Read-your-writes is a property of the *position check*, available on any replica, not a reason to route all reads to the holder.
- Monotonic reads within a session follow from the same mechanism: the session's floor position never decreases, and a replica below the floor does not serve that session.

### Presence and session traffic

- **Presence (ephemeral, TTL'd, loss-tolerant) may be served by replicas** — and may be *originated* at a replica only as explicitly ephemeral data that is never journaled as a world mutation, is labelled with its origin and expiry, and whose loss or duplication is harmless by construction. If presence ever needs durability, it stops being presence and goes through the gate as a mutation.
- **Session traffic that reads** follows the staleness contract above. **Session traffic that mutates** — including anything that changes membership, capabilities, or world state — goes to the holder and the append gate, always. A replica never proxies a mutation in a way that lets it acknowledge before the gate's durable receipt returns (v1: no acknowledgment before durable append).

## 4. Multi-world spill (one host, many worlds)

### Composition

Leases compose by **independence**: each world has its own journal, epoch chain, holder term, and failover (§1) on the host. There is no host-wide lease and no cross-world transaction added by this design. A host failure is N independent per-world failovers, each following §1; a host's return rejoins each world through reader-then-holder (§2) independently.

### Resource fairness (composes with #5685)

The risk v2 adds is a *noisy neighbour with a lease*: a spilled world is by definition hot, and one host spilling many worlds must not let the hottest starve the others — #5685's fairness-attack cases apply to the spill host as a surface. Rules:

- **Per-world budgets on the host:** turn CPU time, concurrent in-flight turns, append submission rate, and replay bandwidth are budgeted per held world. A world exceeding its budget is throttled at its own executor; its lease is not revoked for heat alone (revocation is §1's tool, for failure and operators).
- **Control traffic outranks mutation traffic:** renewal submissions and replay catch-up for *other* worlds are scheduled ahead of a hot world's mutation submissions, so one world's flood cannot cause another world's holder to miss renewals and false-expire — the multi-world version of Q2's false-expiry concern.
- **Admission control at grant time:** the DO's selection policy (§2) sees host load: a host at its holder budget is ineligible for new grants even if roster-listed, and a spill request that cannot be placed without breaching budgets waits (pending intent, §1) rather than over-committing the host. Fairness is enforced where the grant is made, not by after-the-fact eviction.
- **Fairness evidence:** the #5685 adversarial cases for concurrent-world load are the acceptance oracle here — a host under a fairness attack from one spilled world must keep every other held world's renewal and append latency inside the bounds those cases name (§7 oracle cases).

## 5. Region interplay — spill or move?

#2818 (closed) designs the region-seam handoff: a world *moves* by journaled export from region A and import to region B — the journal's home changes, the entity is visibly in transit mid-handoff, and there is no cross-region atomicity. Spill and move are different tools, and choosing wrong is expensive in both directions (a move for a transient spike pays export/import for nothing; a spill as a permanent home pays append-gate latency forever).

| Signal | Spill (§2819 + this design) | Move (#2818) |
| --- | --- | --- |
| Expected duration | Transient — the #2059 warning band, expected to clear (v1 de-escalation ≈ one hour clear) | Durable — the heat or the audience has relocated |
| What moves | Execution only; journal and identity stay home | The journal's home region itself, via export/import |
| Commit latency during the state | Every append still crosses to the home DO's gate — spill target must be network-near the DO | After the move, appends are local to the new home |
| Recurrence | First / rare spill of this world | Repeated spills of the same world (default signal: spilled again within its de-escalation window, or spill tenure dominating its timeline) |
| Failure shape | Holder failover (§1), journal home untouched | In-transit states and import failure recovery (#2818's design) |

Rules:

- **Spill near, move far.** A spill target must be close enough to the DO that append round-trips stay inside the world's latency budget — in practice the same or an adjacent region. A hot world whose *audience* is in a distant region is a move candidate, not a cross-region spill: spilling it across regions would tax every single append with the distance the move pays once.
- **No spill during a move, no move during a spill, without handback first.** A world in #2818 transit has no stable journal home to fence a lease against; a spilled world must complete handback to its DO (v1) before export begins, so the export is taken from the home executor's state, not from a native holder's.
- **Recurrence promotes spill to move.** The DO-side spill bookkeeping (grant/handoff records are already journaled) makes recurrence observable from the journal itself: when the recurrence signal above fires, the follow-up is a move evaluation under #2818, filed as its own issue — v2 does not automate the move.

## 7. Failure walkthroughs and oracle cases

V1's walkthrough table is inherited (native crash, partition, mid-turn expiry, mirror lag, handoff race, lost reply). V2 adds — these are also the deterministic-testing design's failover interleavings, stated here as the oracle cases an implementation must reproduce deterministically, not just encounter:

| Failure | Required result |
| --- | --- |
| **Holder dies mid-term, caught-up replica in pool** | No grant before fence (expiry/revoke). Successor granted at epoch+1, already at the barrier; world resumes with only term-plus-grant downtime. In-flight commands resolve by dedupe / `holder-lost` retry; none is applied twice, none of the dead holder's unappended work exists. |
| **Holder dies, no eligible successor** | DO grants to itself (v1 recovery) rather than to a lagging replica. Availability follows v1; a replica beyond the catch-up bound is never granted "to save time." |
| **Partitioned old holder reconnects after failover** | Its submissions carry the old epoch and are rejected and audited at the gate (v1). It rejoins, if at all, as a reader (§2), never by resuming its old epoch. |
| **Failover races a polite handback** | The append gate serializes fence, grant, and handoff records in journal order; whichever boundary linearizes first wins, the other resolves against the new state. Exactly one epoch is current at every position. |
| **Replica serves during failover** | Reads continue at the replica's watermark under §3's contract (the journal stream is unaffected by holder change); mutation attempts receive `holder-lost` until the grant lands. No read is served from beyond the watermark, and no presence data is promoted to durable state by the failover. |
| **Two worlds on one host, one floods** | The flooding world is throttled at its own budget; the other world's renewals and appends stay in bound (§4). The flood cannot false-expire its neighbour. |
| **Spill requested for a world in region transit** | Refused / deferred until the move completes or aborts (§5); no lease is granted against a journal whose home is in transit. |
| **Grant storm (repeated holder deaths)** | Minimum-tenure flap protection (§2) degrades recovery to v1 expiry pacing; the journal shows every transition, and no two grants overlap an epoch. |

**Invariants added by v2** (v1's seven stand):

8. Pool membership confers eligibility, never authority; authority exists only as the current grant record naming the holder at the current epoch.
9. A successor is granted only after the predecessor's epoch is fenced and only at a replay barrier it has demonstrably reached.
10. A replica's served position never exceeds its replayed prefix, and a read's position is always knowable from its response.
11. No world's lease, budget, or failover can consume another world's renewal path on a shared host.
12. Spill never changes a world's journal home; move never borrows spill's lease. The two mechanisms compose only in sequence, never concurrently, for one world.
