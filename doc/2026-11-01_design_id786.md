# Design: F13.4 presentation capability tiers with in-band terminal detection

- Date: 2026-11-01
- Status: **decision-ready design** — implementation has not started; prerequisites and open owner questions are recorded below.
- Issue: [#786](https://github.com/developing-today/code/issues/786), Phase 13 F13.4.
- Design tracker: #535, D1-052. Related follow-up: #787, F13.5 (Kitty keyboard protocol).

## The decision

Choose where terminal capability detection runs, how its result selects one of three presentation tiers, and how to keep terminal probe replies out of world input. The design must give the same result over SSH and iroh, preserve the existing shell/journal contract, use a safe fallback when a terminal does not answer, and make each tier benefit from batching and rendering deltas.

**Recommendation:** probe at the TTY-owning presentation adapter, using one shared, bounded in-band detector. Keep the resulting profile local to that adapter; do not add capability negotiation to shell-contract v1. Derive a rich, cell-grid, or line-mode presenter from positive probe results, and fall back to line mode on no TTY, timeout, malformed, or conflicting replies.

## Context and current evidence

Issue #786 specifies three targets: enhanced terminals (Ghostty/Kitty/WezTerm), xterm-class cell-grid terminals, and line mode. It names `XTGETTCAP`, `CSI ? u`, and DECRQM for in-band detection, and requires one harness to cover all three tiers, batching/diff benefit for every tier, and identical detection over SSH and iroh. The issue is still open and its latest triage says it is not started.

The current checkout has a portable cell grid, not a rich-media or tier model: `WorldSurface` has only `Screen`, and `ScreenSurface` carries version, dimensions, and cells (`pkgs/id/src/world_presentation.rs:23-43`). Each cell contains a safe glyph, xterm-256 foreground/background, bold, and width (`pkgs/id/src/world_presentation.rs:218-232`). `ScreenPatch::diff/apply` already provides transport-neutral cell deltas and parity tests (`pkgs/id/src/world_presentation.rs:112-216`, `:537-571`), but `render_ansi` still emits home + clear and the complete grid (`pkgs/id/src/world_presentation.rs:423-495`). The SSH presenter calls that renderer for each view (`pkgs/id/src/world_ssh.rs:904-925`).

The SSH PTY request records dimensions but deliberately ignores the terminal name (`_term`), so this design should not turn `$TERM` into an authority for capability claims (`pkgs/id/src/world_ssh.rs:412-425`). Raw SSH bytes currently become `input` frames (`pkgs/id/src/world_ssh.rs:577-591`); `input` is an event delivered to the world (`pkgs/id/src/world_session/mod.rs:2212-2214`, `pkgs/id/contract/shell-contract.v1.json:235-239`). A probe reply must therefore be recognized before `raw_frame`, or the guest may receive and journal terminal-control replies as keystrokes. Resize, by contrast, is explicitly ephemeral (`shell-contract.v1.json:245-251`).

The direct iroh join pump currently prints each server frame as JSON and reads stdin by line (`pkgs/id/src/commands/world.rs:1754-1805`). F13.4 therefore needs a TTY presentation path for iroh as well as the existing SSH presenter; non-TTY/script use should keep the JSON-lines behavior.

There is an important version boundary. Shell-contract v1 is revision 3; its description says a new frame kind waits for F11.12, and it explicitly reserves `presentation_tiers` for F13.4 rather than defining a capability frame (`pkgs/id/contract/shell-contract.v1.json:1-5`, `:382-389`). The Phase 13 plan describes capability negotiation in F13.1, but the committed contract does not yet contain it. The recommended local profile avoids creating a second, conflicting wire contract: only rendering changes, and no terminal identity or probe state enters the journal.

Readiness is gated, not assumed: #545 (alternate screen) and #564 (Phase 13 plan) are closed. #561 (server-side batching) remains open; its latest note reports an uncommitted 5 ms implementation attempt whose test had not finished. #562 (incremental ANSI rendering) remains open with PR #3773 unmerged. F13.4 rendering integration should wait for both prerequisites to land and be verified. The still-open remainder of #785 is the iroh-over-SSH fallback; it is not a gate for proving parity over the existing iroh and SSH frame paths.

## Options and trade-offs

### 1. Infer tiers from terminal names or `$TERM`

Map known names to a tier and use a generic fallback for everything else.

- **Advantages:** little probe machinery; easy to log and test.
- **Disadvantages:** contradicts F13.4's in-band requirement; the name is not proof of the features exposed by a particular version, multiplexer, or tunnel; unknown names are common. It also cannot prove that synchronized output or graphics commands are safe to send.
- **Decision:** reject as the selector. A terminal name may be diagnostic context, never positive capability evidence.

### 2. Probe locally at the TTY adapter and keep the profile local — recommended

Use the same detector at the SSH PTY and iroh client's TTY boundary. It sends the prescribed in-band queries, demultiplexes replies from user input, and returns a typed local profile. The adapter selects a presenter; the transport carries the existing world frames unchanged.

- **Advantages:** identical detector and tier rules over both transports; no new shell-contract frame or journal change; terminal-specific details stay with the component that can actually query the terminal.
- **Disadvantages:** both TTY adapters need the shared I/O seam; bounded timeouts and interleaved input need careful tests. A server-side policy cannot inspect the local profile without a later protocol decision.
- **Decision:** recommend. It fits the current contract and F13.4's presentation-only boundary.

### 3. Negotiate a capability frame between shell and host

Probe locally, then send the profile in a new `ClientFrame` so the host can choose content or rendering policy.

- **Advantages:** central policy and one explicit profile representation for clients.
- **Disadvantages:** adds a wire kind that v1 currently reserves pending F11.12; sends terminal facts beyond the TTY adapter; couples presentation to server behavior even though the existing view is already portable. It would require a contract/revision decision and transport compatibility tests.
- **Decision:** do not use for F13.4 unless a concrete host-side consumer is identified. If needed later, update the versioned contract first; do not smuggle the profile into `input`, `resize`, or a guest event.

## Recommendation

### Local detector and safe fallback

Implement one `TerminalNegotiator`-style helper behind a small terminal-I/O interface shared by the SSH and iroh TTY presenters. Run it only when the process owns an interactive TTY; preserve the existing JSON-lines pump for non-TTY iroh use. Probe in-band with the protocol families named by #786 (`XTGETTCAP`, `CSI ? u`, DECRQM). Before implementation, verify the exact query/reply table for each advertised capability against its protocol specification and capture those transcripts in tests; the issue names the mechanisms but not a complete per-feature transcript.

Use one bounded startup deadline (recommended default: 250 ms total, with probes sent without serial per-query waits). During the probe, retain bytes that do not match an outstanding query and replay them, in order, to the normal key/input path. Consume only complete, matching replies. On timeout, malformed response, conflicting response, or no TTY, choose Tier 3. Never emit a graphics or synchronized-output control sequence unless that specific feature was affirmatively detected. Keep query replies, the profile, and presenter state out of world input and the journal.

| Tier | Selection evidence | Presentation behavior |
| --- | --- | --- |
| **1 — enhanced** | Positive in-band evidence for Kitty graphics **or** Sixel, plus positive DECRQM evidence for synchronized output. Treat Kitty keyboard support as a separate profile bit pending Drew's ruling below. | High-throughput screen updates, synchronized output when confirmed, and a graphics-capable presenter. Use a 60 Hz scheduling ceiling as the initial default; coalesce to the newest view rather than queue stale frames. |
| **2 — ANSI cell grid** | Positive evidence for the minimum ANSI/terminfo features required by the cell presenter, but not the Tier 1 visual requirements. | Cell-grid rendering with the incremental ANSI path. Resize, attach, or invalidated state forces a full repaint. |
| **3 — line mode** | No TTY, no conclusive response before the deadline, or responses insufficient for Tier 2. | Plain text/transcript output, no full-screen control sequences. Emit only changed text for coalesced views, not repeated complete transcripts. |

The classification is by confirmed features, not product name. Keep independent bits in the profile even if the current renderer derives one tier from them. In particular, the F13.5 keyboard feature must not silently change input parsing in F13.4: the example parser still treats a lone ESC as Escape and unrecognized CSI sequences as `Unknown` (`pkgs/id/examples/roc-world/Key.roc:22-32`, `:54-80`).

### Graphics scope

The current `ScreenSurface` has no image or sprite payload (`world_presentation.rs:23-43`); it is a cell DTO. Do not let a guest supply Kitty/Sixel escape bytes. F13.4 should own detection and presenter-side graphics encoding, and its harness can exercise that encoder with a bounded, test-owned image fixture. Keep the guest view format unchanged in this issue; a guest-authored image/asset surface would alter the content contract and needs its own size, format, and validation decision. This is a recommended scope boundary, not a claim that current game views contain images.

For batching and diffs, interpret “every tier benefits” as: server-side event coalescing applies to every tier; Tier 1 and 2 use cell diffs when rendering a screen; Tier 3 applies a logical text diff to the latest coalesced view. The #786 acceptance harness must measure each presenter's output against a full-render control, in addition to the existing F11.9 comparison. A line-mode presenter should not fake cell addressing merely to satisfy the word “diff.”

## Invariants

1. The terminal adapter is the only component that sends terminal queries or terminal-control output; guests never supply raw terminal escapes.
2. A query reply is consumed by the detector and never delivered to the guest as `input`; unrelated bytes are replayed without loss or reordering.
3. Capability claims require positive, feature-specific evidence. Unknown or late responses cannot enable a richer tier mid-frame; a later re-probe may only change tiers after a clean presenter reset.
4. No-TTY and inconclusive-probe behavior is Tier 3. It does not wait indefinitely or emit cursor, graphics, or synchronized-output sequences.
5. Tier selection affects rendering only. It does not change journal contents, world authority, guest ABI, or the server projection (`phase-13-client-shells.md:59-62`).
6. Batching is shared across all tiers. A changed viewport, attach, or invalidated diff state triggers a full repaint; incremental state is committed only after a successful output write.
7. If synchronized output is entered, it is left on every normal, error, and disconnect path, just as the existing alternate-screen mode is restored (`world_ssh.rs:739-768`).

## Acceptance criteria for implementation

- A transcript-driven terminal harness covers positive Tier 1, Tier 2, Tier 3, no-reply, malformed, partial, late, and interleaved-user-input cases. It asserts the selected profile and the emitted output, not only the classifier result.
- The same harness drives the shared detector through both the SSH PTY and interactive iroh TTY adapters. Equivalent terminal transcripts select the same tier and produce the same logical view; transport envelopes do not change probe parsing.
- Query replies never appear in world input or the journal; unmatched keystrokes survive a probe byte-for-byte and in order.
- Tier 1 sends graphics/synchronized-output sequences only after positive detection and restores terminal modes on every exit. Tier 2 uses cell diffs and repaints fully on resize/attach/invalidation. Tier 3 emits no full-screen escapes and outputs only changed text after batching.
- Every tier consumes the F11.9-baselined server batching; cell tiers verify diff parity, and line mode verifies text-delta parity. The harness reports frame counts and emitted bytes for each tier against a full-render control and the recorded baseline.
- Non-TTY `id world join` retains its current JSON-lines behavior; ordinary raw SSH input and command mode remain unchanged outside the probe demultiplexer.
- No capability frame is added to shell-contract v1. If implementation discovers a host-side need for the profile, stop that slice and design a versioned contract change rather than adding an undocumented frame.

## Phased implementation plan

Each step can merge independently while preserving the previous behavior; richer behavior stays disabled until its probe and renderer tests pass.

0. **Prerequisite gate — batching and ANSI diff.** Land and verify #561 and #562 first. Do not re-implement them in F13.4. As of this note, #561 is open with an uncommitted attempt and #562 is open with PR #3773; F13.4 may develop its harness/profile scaffolding while these are pending, but must not claim the rendering acceptance is met.
1. **Profile and terminal transcript harness.** Define the local typed capability profile, tier classifier, injectable terminal I/O, and fixtures for the supported query/reply transcript. Establish full-render and presenter-byte counters. No runtime behavior changes in this slice.
2. **Bounded in-band detector.** Add shared query/reply parsing and input demultiplexing to the SSH PTY and iroh TTY adapters. Enable only the Tier 3 safe fallback first. Prove no-TTY, timeout, malformed, late, and interleaved-key behavior; retain the profile locally rather than adding a shell-contract frame.
3. **Tier 2 and Tier 3 presenters.** Add an interactive iroh TTY path while leaving non-TTY JSON-lines unchanged. Route confirmed Tier 2 through the cell renderer and incremental ANSI diffs; render Tier 3 as coalesced text deltas. Gate this slice on #561/#562 landing.
4. **Tier 1 presenter.** Add synchronized-output bracketing and the Kitty/Sixel output adapter behind positive capability bits. Restore modes on every exit and test with a test-owned bounded image fixture. Do not add a guest image field or activate Kitty keyboard parsing in this slice.
5. **Cross-transport acceptance and baseline report.** Run the same transcript matrix over SSH and iroh; compare logical outputs, diff application, frame counts, bytes, and effective frame rate. Verify all three tiers benefit from shared batching and that every richer terminal output has a tested fallback.

## Questions for Drew

These do not block the recommended implementation path; record the answers before finalizing the Tier 1 and rich-content acceptance wording.

1. **Does Kitty keyboard support gate Tier 1?** Option A: require it as the F13.4 tier-1 definition currently reads, which couples presentation classification to F13.5 and delays Tier 1 until the raw-input parser lands. Option B: detect it as an independent capability bit and let F13.5 consume it; Tier 1 is selected by visual graphics plus synchronized output. **Recommendation: B**, because F13.5 separately owns Kitty input negotiation and visual rendering does not depend on Escape-vs-Alt parsing.
2. **Should F13.4 add guest-authored image content?** Option A: extend the typed surface now with bounded image assets, expanding this issue into a guest-content/schema and validation change. Option B: keep F13.4 presentation-only, exercise Kitty/Sixel output with a test-owned image fixture, and leave guest image content for a separately scoped design. **Recommendation: B**, matching the current cell-only surface and the Phase 13 rule that presentation changes alter rendering, not recorded content.
