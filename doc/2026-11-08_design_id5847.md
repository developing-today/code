# Design: importer design — Logseq into the #2048 object model

- Date: 2026-11-08
- Status: **decision-ready proposal** — design only; no importer code is implemented here.
- Issue: [#5847](https://github.com/developing-today/code/issues/5847), parent programme [#5678](https://github.com/developing-today/code/issues/5678), programme epic [#2056](https://github.com/developing-today/code/issues/2056).
- Object model: [#2048](https://github.com/developing-today/code/issues/2048) as landed in `doc/2026-11-01_design_id2048.md` (PR #3885, closed 2026-11-07): stable logical notes (`note.create` = stable note ID), signed immutable revisions (`note.revise` naming parents and a content blob), structured typed references (target note ID, sigil/type, authored surface, optional pinned revision), tags as signed observed-remove claims, names/aliases as claims, tombstone removal, group `Read`/`Write` as the authority model. This design **consumes** those decisions; it does not re-decide them. The one place it touches a parent decision is flagged explicitly in §7.
- Sibling importer design: [#5848](https://github.com/developing-today/code/issues/5848) (Joplin), record at `doc/2026-11-08_design_id5848.md`. This design follows its shape deliberately — same manifest contract, same invariant set, same corpus discipline — so the importer family stays one design with per-source deltas, not N unrelated designs. Where Logseq forces a different answer, the difference is stated as a delta against that record (§0).

## Decision to make

How does a Logseq graph — an **outliner** of nested blocks, a **daily-journal** page stream, `[[page]]` and `((block-uuid))` references, page properties, and a `logseq/` directory of Markdown (or org) files — enter the #2048 object model such that (a) the imported graph uses the model's stable identity, typed references and claims rather than a file dump beside it, and (b) a later export back to Logseq keeps block structure, block references, page links, properties and journal dates intact?

## Recommendation

**Import is a mapping into the object model, recorded in a persisted import manifest, and it is one-shot plus idempotent re-import — never a sync emulation.** The shape is the Joplin record's; the Logseq deltas are these:

1. **Pages → logical notes; blocks are content, not notes.** Each Logseq page becomes one logical note (`note.create`, initial revision blob = the page's Markdown/org body after reference rewriting, §3). A **block is not a note**: blocks are the outline structure _inside_ a note's revision content, carried as an explicit block tree with stable block identities in the manifest (§2.1). Minting a note per block would flood the graph with thousands of one-line notes, break the page-level read unit, and make a page's revision history meaningless.
2. **Block references are references to blocks, and blocks therefore need stable identity.** `((uuid))` names a block, not a page. The model's typed reference targets a _note_; a block reference is carried as a typed reference to the owning note **plus** a block selector recorded in the manifest's reference metadata — never in the revision-pin slot, which names revisions only (§3) — and the manifest maps Logseq block UUID ↔ (note ID, block identity) (§2.2, §3). This is the one place Logseq's shape is harder than Joplin's, and it is the reason §7 touches a parent decision.
3. **The manifest is a first-class artifact.** It records page name/source-page-UUID ↔ note ID, block UUID ↔ (note ID, block identity), asset filename ↔ blob reference, and source-graph identity plus import time. An import without a manifest is a failed import — same contract as #5848.
4. **Journals are notes with a date claim, not a second type.** A `journals/2026-11-08` page is a logical note carrying a journal-date claim; the journal stream is a query over that claim, not a stored ordering fact (§2.3).
5. **Pages → notes; `[[page]]` → typed note references; tags → tag claims; assets → blobs.** The Joplin record's mappings apply unchanged except that a Logseq "page" is the note unit (§2).
6. **Outliner structure survives because it is content.** Nested blocks, bullets, and block-level properties are preserved verbatim in the revision blob, with the block tree recorded alongside so export can rebuild the outline exactly (§5).

## §0 Deltas against the Joplin importer design (#5848)

| Concern                  | Joplin (#5848)                         | Logseq (this design)                                                                | Why                                                                                  |
| ------------------------ | -------------------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Primary content unit     | Note = the body                        | Page = the note; **blocks** are structure inside it                                 | Logseq is an outliner; a page is the reading unit and the revision unit              |
| Identity beyond the note | Joplin note ID                         | Page name **and** per-block UUID                                                    | `((block-ref))` targets a block; the UUID must survive round trip                    |
| Reference target         | `:/<note-id>` → note                   | `[[page]]` → note; `((uuid))` → note + block selector (manifest reference metadata) | Two reference kinds with different granularity                                       |
| Time model               | Created/updated claims                 | **Journal date** claim on daily pages                                               | The daily journal is a first-class Logseq concept                                    |
| Source shapes            | JEX, Markdown dir, (ENEX out of scope) | Graph directory (Markdown or org), EDN export as metadata-rich source               | Logseq's native on-disk form _is_ the graph directory                                |
| Properties               | To-do claims                           | **Page and block properties** (arbitrary key/value) as claims                       | Logseq properties are user-defined and pervasive (`tags::`, `alias::`, `template::`) |
| Lossy list               | Revision history, plugin markup, E2EE  | Query blocks, templates as macros, whiteboards, plugin/extension data               | Logseq has features with no note-model counterpart                                   |

Everything else — manifest contract, idempotency, no-silent-drops accounting, no key handling, corpus discipline — is inherited from #5848 unchanged.

## §1 Source shape (what Logseq actually gives an importer)

Stated against Logseq's export shapes, in preference order:

- **Graph directory (Markdown or org mode)** is the canonical import source: `pages/*.md`, `journals/YYYY_MM_DD.md`, `assets/*`, plus `logseq/config.edn` and `logseq/metadata.edn`. It is what Logseq itself stores on disk and what "export graph" produces, so it carries pages, journals, block structure, properties and assets together.
- **EDN export** (`logseq/metadata.edn`, and the `db/` graph when the graph is in DB mode) is accepted as a **metadata-rich supplement**: it carries explicit block UUIDs and page identities that the Markdown files only carry implicitly (a block UUID appears in a body only when something references it). Where both are present, the EDN metadata wins for identity and the Markdown wins for content.
- **Markdown-only export without `logseq/` metadata** is a degraded source: block UUIDs are absent except for referenced blocks, so the manifest is built from page names plus content hashes and block identities are minted deterministically (§2.2). The import report must name the degradation.

Relevant Logseq facts the mapping relies on: a page is identified by its name (case-insensitive, with `namespace/` hierarchy); a daily page is a page whose name is a date; blocks nest arbitrarily deep and are bullet items; a block may be referenced by `((uuid))` from anywhere in the graph; pages are referenced by `[[name]]`; `#tag` is page-reference sugar for `[[tag]]`; properties are `key:: value` lines on a page or block; assets are files under `assets/` referenced by relative path or by `![alt](../assets/name.ext)`; org-mode graphs use `*` headings and `:PROPERTIES:` drawers instead of Markdown bullets and `key:: value`.

## §2 Entity mapping

### §2.1 Pages and blocks

| Logseq item                               | #2048 mapping                                                                      | Notes                                                                                                                                                                                                      |
| ----------------------------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Page                                      | Logical note (`note.create` + initial revision)                                    | Body blob = page content after §3/§4 rewriting. Page name → alias/filename claim (names are claims, never identity, per #2048).                                                                            |
| Daily-journal page                        | Logical note + journal-date claim                                                  | §2.3.                                                                                                                                                                                                      |
| Namespaced page (`a/b/c`)                 | Logical note + namespace claim                                                     | The `namespace/` hierarchy is an alias-claim structure, not collection nesting — Logseq namespaces are naming, not containment, and treating them as collections would invent a tree Logseq does not have. |
| Block                                     | Block identity **inside** the note's content, recorded in the manifest             | Not a note (§Recommendation 1). The block tree is stored with the revision so export can rebuild it.                                                                                                       |
| Block property (`key:: value` on a block) | Claim on the block identity                                                        | Block-level claims live in the manifest's block record, not as separate events.                                                                                                                            |
| Page property (`key:: value` on a page)   | Claim on the note                                                                  | `alias::`, `tags::`, `title::` map to the model's alias and tag claims; other keys are recorded verbatim as provenance claims.                                                                             |
| Asset (file under `assets/`)              | Content blob + resource record                                                     | §4.                                                                                                                                                                                                        |
| `[[page]]` link                           | Typed reference to the target note                                                 | §3.                                                                                                                                                                                                        |
| `((uuid))` block reference                | Typed reference to the owning note + block selector in manifest reference metadata | §3.                                                                                                                                                                                                        |
| `#tag`                                    | Tag claim (observed-remove)                                                        | Sugar for a page reference; imported as a tag claim _and_ as a typed reference to the tag page when that page exists.                                                                                      |
| Whiteboard / plugin data                  | Out of scope, reported                                                             | §5 lossy list.                                                                                                                                                                                             |

### §2.2 Block identity

A block identity is stable first, derived second — re-import must resolve references, never silently retarget them:

- **An explicit source UUID wins wherever one is present.** With EDN metadata, the identity is the Logseq block UUID, recorded in the manifest against (note ID, position path). In a Markdown-only export, a block whose UUID appears in a `((uuid))` elsewhere in the graph is still known — that UUID is its identity. Only blocks with no known UUID get a derived identity.
- **Derived identity (no known UUID):** a hash of (note ID, parent block identity, ordinal among siblings, normalized block text). The same block re-imported from the same export therefore gets the same identity; an edited block gets a new one, which is correct — it is a different block content and its old references should surface as dangling rather than silently retarget.
- A `((uuid))` whose block is absent from the export is preserved with its authored surface and marked unresolved, per #2048's degradation rule.

### §2.3 Journals

A daily page becomes a logical note carrying a journal-date claim (`journal_date: YYYY-MM-DD`, taken from the page name, not from file mtime). The journal stream is a query over that claim. Consequence worth stating: importing a graph into a world that already has notes on the same days produces two notes with the same journal-date claim — the model has no uniqueness on claims, so this is allowed and the import report names it; merging journals is a user act, not an importer act. Export of duplicate journal dates is disambiguated losslessly per §5 item 6.

## §3 References

- During import, every `[[page]]` occurrence is rewritten to a structured typed reference: target = the manifest's note ID for that page name, sigil/type = note reference, authored surface = the original link text.
- Every `((uuid))` occurrence is rewritten to a typed reference whose target is the **owning note** of that block, with the reference's revision pin left **unset**: a block identity is not a revision, and placing one in the pin slot trips `PinNotOfTarget` in `project_links` (`pkgs/id/src/note_links.rs:322–329`), which requires the pin to name a revision of the target note. The block identity travels as a **block selector in the manifest's reference metadata**, keyed by the reference record; export reconstructs `((uuid))` from the manifest. This is the round-trip requirement that makes block identity non-negotiable.
- A `[[page]]` naming a page absent from the graph is preserved with its authored surface and marked unresolved — Logseq itself allows links to non-existent pages (they are how pages get created), so a dangling link is normal source data, not corruption. The import report counts them.
- A reference inside a **code block or inline code** is not a reference and is not rewritten. Logseq does not linkify inside code; the importer must match that, and the corpus includes the case (§8).
- Reference rewriting never changes the rendered text of a page: only the link target representation changes.

## §4 Assets

Inherited from #5848 §4 with one Logseq-specific rule: Logseq references assets by **relative path** (`../assets/name.ext`), and the same file may be referenced from several pages. The manifest records asset filename ↔ blob reference; every referencing page's body is rewritten to a blob reference; the resource record carries filename and MIME type. Byte identity is the acceptance bar (§8 oracle). An asset present in `assets/` but referenced by no page is imported and reported as an orphan, never dropped.

## §5 Round-trip export expectations

Export from ID back to a Logseq graph directory is part of this design's contract, stated as testable equalities over canonical sets:

1. **Pages:** the set of exported pages corresponds 1:1 (via the manifest) to the imported set, plus notes created natively in ID since import, which export with freshly minted page names recorded back into the manifest.
2. **Block structure:** the block tree of every page is equal — same nesting, same order, same text — for pages that were not edited in ID.
3. **Block references:** every reference to an imported block exports as a `((uuid))` resolving to the same block; unresolved references export with their authored surface intact.
4. **Page links:** every typed note reference exports as `[[page-name]]`; tag claims export as `#tag` (or `[[tag]]` where the source used the long form — the manifest records which).
5. **Properties:** page and block properties export to the corresponding `key:: value` lines (or org `:PROPERTIES:` drawers for org graphs).
6. **Journals:** journal-date claims export to `journals/YYYY_MM_DD` pages. **Duplicate journal dates:** when two notes carry the same journal-date claim, the note the manifest records as that journal page's import keeps the canonical destination; each additional note exports to `journals/YYYY_MM_DD__<short-note-id>` (suffix = first 8 hex characters of the note ID) and the export report names the collision. The writer never merges, overwrites, or drops — merging journals stays a user act (§2.3).
7. **Assets:** bytes hash-equal; filenames preserved; relative paths rewritten correctly for the export root.

**Stated lossy list** (the round trip does _not_ promise these, and the export report must say so): **query blocks** (`{{query ...}}`) export as literal text — they are live database queries in Logseq and have no note-model counterpart; **templates and macros** (`{{template ...}}`, `{{embed ...}}`) export as literal text; **whiteboards**; **plugin/extension data** and `logseq/config.edn` settings; **built-in dynamic variables** (`<% today %>`) export as their literal source; **ID-side structure with no Logseq counterpart** — a note with unmerged concurrent heads exports the Joplin-lineage rule of #5848 §7 (the head descended from the last import, others named in the report); and **block-level revision history**, since the model versions notes, not blocks.

## §6 Invariants implementation must hold

1. **Stable identity is ID's.** Imported pages get ID note IDs; page names live as alias claims and in the manifest. Renames (either side) never change a note ID — source-side renames resolve through invariant 3's dedupe, and the name-only delete-plus-create case is a new note, not a renamed one. Block identities are manifest-scoped and stable across re-import (§2.2).
2. **Append-only import.** Import writes signed `note.create`/`note.revise` events under the importing identity; it never edits or deletes existing world content. Re-import of a changed page creates a new revision under the _same_ logical note (found via the manifest), joining heads explicitly if ID-side edits created a divergent head — never last-writer-wins, per #2048.
3. **Idempotency and rename-stable dedupe.** Re-importing the same export into the same world creates no duplicate notes, blocks or blobs: the page dedupe key is (source-graph identity, source page identity) — the source page UUID where the source provides stable page identity (EDN export), falling back to (source-graph identity, page name) for name-only sources — and the block dedupe key is (source-graph identity, block identity) via the manifest; content blobs dedupe by hash. A source-side rename therefore re-resolves to the same note when stable page identity is available; for name-only sources a rename is treated as delete-plus-create and the import report names it, since there is no page identity to join on.
4. **No silent drops.** Every page, block, property, reference and asset in the source export is accounted for in the import report: imported, deduplicated, degraded (Markdown-only case), dangling, or refused with a reason. A count mismatch fails the import.
5. **References are never invented or dropped.** A dangling `[[page]]` or `((uuid))` keeps its authored surface and is counted; a reference inside code is never rewritten.
6. **No key handling.** The importer never handles encryption keys or encrypted payloads; encrypted items are refused and reported.
7. **Parent decisions stand.** Anything not settled here or in #2048 — cluster features, other importers, the graph view — is out of scope; where an implementation choice would change a #2048/#5678 decision, it is recorded on the parent, not forked here (§7 is the worked example).

## §7 The one explicit parent-decision touch

#2048's typed reference targets a **note** and optionally pins a **revision**. Logseq's `((uuid))` targets a **block**. This design carries block references as note-targeted references with a block selector recorded in the manifest's reference metadata (the revision pin is left unset — it names revisions only), which means:

- the model gains no new reference kind, and backlinks at the note level work exactly as #2048 specifies;
- but a block reference is **not** a first-class graph edge in the substrate — resolving "what links to this block" requires the manifest, and a block reference whose owning note is deleted surfaces as a dangling note reference, not a dangling block reference.

**The alternative — promote blocks to first-class reference targets in #2048** — would make block backlinks native and export exact, at the cost of a new reference target kind and a block-level identity/versioning story in the event model, which #2048 deliberately does not have (it versions notes, not blocks). This design declines to re-decide that on an importer ticket. If Drew wants native block backlinks, that is a #2048 amendment, and this paragraph is the decision to amend — on #5678/#2048, not in importer code.

## Viable options

| Option                                                         | Trade-offs                                                                                                                                                                                                                                                                 | Decision                                                                                                                                                                                                         |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Manifest-recorded model mapping (this design)**              | Import lands in the object model with stable identity, typed references and claims; round-trip and idempotent re-import are possible _because_ the manifest persists page/block/asset mappings. Costs an importer that understands both models and a manifest to maintain. | **Recommend.** It is the only option that satisfies the issue's round-trip expectation while keeping blocks out of the note graph.                                                                               |
| **One note per block**                                         | Every block gets a stable ID for free and block backlinks become native note backlinks.                                                                                                                                                                                    | Reject: floods the graph (a 10k-block graph becomes 10k notes), destroys page-level reading and revision history, and inverts Logseq's own model where the page is the file.                                     |
| **One `document.put` per page (files with frontmatter)**       | Minimal new machinery; mirrors the on-disk graph.                                                                                                                                                                                                                          | Reject: #2048 already rejected per-put identity — event IDs change per save, so links/backlinks cannot survive edits, and there is nowhere for the manifest or typed references to live.                         |
| **Markdown-only import, no manifest**                          | Simplest possible importer; fine for a one-way migration.                                                                                                                                                                                                                  | Reject: without the manifest, block references cannot round-trip at all, re-import duplicates everything, and §5's equalities are untestable.                                                                    |
| **Logseq sync-target emulation (ID as a Logseq sync backend)** | Continuous two-way sync instead of import/re-import.                                                                                                                                                                                                                       | Reject for v1: couples ID to Logseq's sync protocol and conflict semantics, which fight #2048's multi-head model. The manifest design keeps the option open without paying for it now (cf. #5848's #7676 split). |

## §8 Test corpus plan

The corpus is the oracle for §5 and §6; the oracle is **canonical set equality**: pages, block trees, per-page tag sets, typed-reference targets (including block identities), journal dates, properties, and asset byte hashes, compared modulo the §5 lossy list.

- **Synthetic corpus (generated fixtures, committed with the importer):** nested blocks ≥4 levels including an empty block; a page with duplicate titles differing only by namespace; a reference graph including a cycle, a self-reference, a dangling `[[page]]`, a dangling `((uuid))`, and a block reference to a block in another page; `[[link]]` and `((uuid))` appearing inside fenced code and inline code (must not be rewritten); `#tag` and `[[tag]]` forms of the same tag; namespaced pages; daily pages across a month boundary including a leap day and a day with no page; page and block properties including `alias::`, `tags::`, and a user-defined key; assets of each common class (PNG, PDF, audio, unknown binary) including one asset referenced by two pages and one orphan; Unicode/emoji and very long blocks; an org-mode graph variant of a representative subset; a page renamed between two imports (EDN-identified rename resolves to the same note; name-only rename reports delete-plus-create); two notes sharing a journal date (export disambiguation per §5 item 6); a `((uuid))`-referenced block in a Markdown-only export keeping its UUID identity across re-import.
- **Round-trip property:** for every corpus graph — import → export → import into a _fresh_ Logseq graph → canonical comparison against the original export. Generators vary graph shape (page count, block depth, link density, journal span) property-style.
- **Idempotency property:** importing the same graph twice yields a world whose canonical projection is unchanged by the second import (invariant 3), and importing a one-page-changed graph produces exactly one new revision (invariant 2).
- **Reference-fidelity property:** for every block reference in the source, the exported graph contains a `((uuid))` resolving to the same block identity — the check that makes §2.2 and §3 testable.
- **Real-graph sample:** one anonymised real-world Logseq graph run through the same properties, to catch shapes generators do not imagine. Named as a corpus _requirement_, not a fixture this design provides.

## Implementation slicing (follow-on issues, not this design)

1. **Graph reader + manifest:** parse the graph directory (Markdown and org) plus `logseq/metadata.edn`, build/persist the manifest and import report, no content written yet — report-only mode.
2. **Pages, journals, tags, properties:** `note.create` mapping per §2 with idempotency (invariant 3).
3. **Blocks and references:** block identity derivation (§2.2), `[[page]]` and `((uuid))` rewriting (§3), dangling accounting.
4. **Assets:** §4 blob storage and relative-path rewriting.
5. **Re-import:** changed-page revision path and head-joining (invariant 2).
6. **Export:** graph-directory writer satisfying §5, with the lossy-list report.
7. **Corpus:** §8 fixtures + round-trip/idempotency/reference-fidelity properties wired into the importer's test suite.

No splits are filed by this design beyond the slicing above; if a slice grows a piece, it files then, per the parent programme's rule.
