# Design: conversion & RateAuthorisation across the #5676 currency stages

- Date: 2026-11-05
- Status: **decision record** — docs only, no implementation code.
- Issue: [#5828](https://github.com/developing-today/code/issues/5828), follow-on
  of [#5676](https://github.com/developing-today/code/issues/5676) (currency
  scaling: Redis → multi-Turso → TigerBeetle), programme epic #2056.
- Canonical contracts reused, not re-decided:
  [#2063](https://github.com/developing-today/code/issues/2063) conversion
  engine (`doc/2026-11-01_design_id2063.md`) and
  [#2290](https://github.com/developing-today/code/issues/2290)
  `currency.rate_authorisation`
  (`doc/2026-11-01_design_id2290.md`), as synthesised by
  [#2043](https://github.com/developing-today/code/issues/2043)
  (`doc/2026-11-01_design_id2043.md`). Both contracts are merged: PR #3831
  (#2290) and PR #3844 (#2063) merged 2026-11-02.

## The decision

1. **One conversion contract, three stage adapters.** The #2063 contract —
   signed `currency.rate_authorisation` (#2290), event-pinned 60-second quote,
   durable intent as the admission point, cap reservation in the admission
   transaction, persisted client idempotency key, leg IDs chosen once and
   never regenerated, monotonic intent states, correction only by a new
   compensating conversion — is stage-independent. What changes per stage is
   only how the adapter makes the legs atomic (or honestly doesn't, §3), and
   that difference is confined behind the #5676 backend port: the gateway
   calls one operation, `postConversion(intent)`, and the stage adapter
   returns one of the #2063 outcomes (`POSTED`, `FAILED_ATOMIC`, or the
   Stage B saga outcomes in §3.2). No stage gets its own authorization,
   quote, rounding, or receipt semantics.
2. **Authorization is verified once, at admission, identically at every
   stage.** The gateway checks in §2.2 of the #2063 record (signed request,
   taker eligibility, offer signature/`issuer_id`, latest unrevoked version
   at the offerer's chain frontier, caps, expiry) happen before the durable
   intent is written. Expiry or revocation after admission does not
   invalidate an admitted intent; it blocks new intents. The adapter never
   re-interprets the offer.
3. **Stage A (Redis + regular store) is atomic inside Redis and durable
   through the regular store** (§3.1). **Stage B (multi-Turso) makes no
   cross-database atomicity claim**: it is a saga with a durable coordinator
   intent, pending holds, and compensating legs, and its weaker guarantee
   and user-visible pending state are explicit (§3.2). **Stage C
   (TigerBeetle) is the #2063 linked batch unchanged** (§3.3).
4. **Graph-native exchange stays outside v1.** Conversions exist only for
   ledger-anchored currencies, exactly as #2043 decided; nothing in the
   staged path adds offline/graph-native conversion.

## 1. The adapter boundary

Settled as follows; this is the boundary every stage design ticket in
#5676's decomposition (items 2, 4, 5) must build against:

- **Above the port (shared):** quote issuance and binding (#2290), admission
  checks, durable intent + cap reservation, receipt construction, the
  conversion state machine, and reconciliation reporting. Written once.
- **Behind the port (per stage):** leg posting, the stage's atomicity
  mechanism, leg-ID allocation within the intent's pre-assigned ID set,
  and recovery probing ("given these leg IDs, what actually posted?").
- **The intent is the contract between the two.** It carries everything
  #2063 §2.4 requires (conversion_id, all leg IDs, amounts, accounts,
  ledgers/shards, offer ID/version/frontier, quote, cap reservation,
  caller) plus the stage's routing data (Redis key namespace, or the
  currency→DB directory resolution, or TigerBeetle ledger IDs). An adapter
  that needs a field the intent does not carry is a port change, reviewed
  as a change to this record — not a per-stage improvisation.

Explicitly deferred (does not block any stage): the coordinator-migration
procedure when a Stage B currency is rebalanced to another DB while sagas
are in flight. Owner: the Stage B design ticket (#5676 decomposition
item 4). Until it settles, rebalancing a currency with in-flight
conversions is not permitted — the directory freezes that currency's
conversions (new intents rejected with a typed maintenance error) until
in-flight sagas drain, which is always bounded by the saga timeout in
§3.2.

## 2. Shared contract (all stages)

Everything in #2063 §2 and §3 applies verbatim, including: exact rational
rates with the floor formula and LP-kept remainder; fee as a separate
visible source-currency leg; `conversion_id` as the 128-bit correlation ID
on every leg; no floating point anywhere; inventory protected by
store-level constraints, never read-then-write; posted conversions are
immutable and corrected only by a new conversion referencing the original.

Per-stage additions to the invariant set:

- **Intent before legs, everywhere.** No adapter posts a leg for an intent
  that is not durably recorded in that stage's system of record.
- **Recovery is by leg ID, everywhere.** After any crash or lost response,
  recovery probes the exact stored leg IDs. All present and matching →
  `POSTED`; none present → retry the identical legs/IDs; partial or
  mismatched → quarantine and alert as an invariant violation (Stage B:
  partial is an expected saga state, handled by §3.2, not quarantine —
  quarantine is for legs that match no saga state).
- **Receipts are stage-blind.** A receipt names legs, amounts, offer
  version, and outcome; a reader cannot tell which stage posted it except
  from the recorded adapter name, which is audit metadata, not semantics.

## 3. Per-stage atomicity, failure, and recovery

### 3.1 Stage A — Redis hot store + regular store

- **System of record:** the regular store (per #5676 Stage A). Redis is
  the hot/operational layer only; it is the system of record for nothing.
- **Posting:** admission writes the durable intent to the regular store
  first. Leg posting is a single Lua-scripted Redis operation keyed by
  `conversion_id`: it checks the idempotency marker, applies all legs
  (source principal, optional fee, destination credit) with the
  per-account debit constraints, and sets the marker — all legs or none.
  The gateway then marks the intent `POSTED` in the regular store and
  write-through-updates the durable balance records.
- **Atomicity guarantee (stated precisely):** atomic with respect to
  Redis (one script, no interleaving), and durable with respect to the
  regular store intent + posting record. The window between Redis posting
  and the `POSTED` mark is closed by recovery, below — it is never closed
  by pretending the two writes are one transaction.
- **Posting happens in admission order, and credits are not spendable
  until durable.** Admission assigns each intent a monotonic sequence
  number inside the regular-store admission transaction. Live posting is
  executed by the single logical writer (#2062 §4.5, already mandatory
  in the #2063 contract) **strictly in admission-sequence order**: the
  writer keeps a durable next-posting-sequence watermark in the regular
  store, the Lua script is invoked with the intent's sequence, and it
  refuses to post any sequence other than the watermark's — so the
  order legs hit Redis is the admission order by construction, not by
  timing luck with concurrent admissions. The watermark advances only
  when that sequence reaches a terminal posting outcome (`POSTED` mark
  written, or atomic failure recorded), which is also recorded before
  the next sequence posts. A conversion's destination credit is visible
  in Redis immediately but is *pending* — not spendable, and not usable
  as another conversion's source — until the intent's `POSTED` mark is
  durable in the regular store. Together these make recovery order-safe
  in both directions: replay in admission order reproduces a history
  that actually happened, and a later conversion can never durably
  depend on an earlier credit whose own posting is not yet durable.
- **Failure/recovery:** crash before the script → no legs, intent stays
  `PREPARED`, retry identical. Crash after the script, before the mark →
  recovery finds the `conversion_id` marker in Redis and marks `POSTED`.
  Redis loss → rebuild hot state by replaying the regular store's posted
  records **in admission-sequence order**; a conversion whose intent is
  `SUBMITTED` with no Redis marker after rebuild is resolved in that
  same order — re-posted with the identical legs/IDs (the idempotency
  marker makes re-posting safe) or failed atomically — before any
  intent with a higher sequence number is resolved, and admissions stay
  closed until the replay finishes. The continuous reconciliation job
  (hot store vs regular store, per #5676) treats any divergence older
  than one reconciliation pass as an alert, not a rounding error.

### 3.2 Stage B — multi-Turso (sharded regular store)

- **No cross-database atomicity is claimed.** Turso DBs are separate
  stores; there is no XA/two-phase-commit coordinator across them in
  this design, and this record does not invent one (see Alternatives).
  A conversion whose legs live in one DB is locally atomic and behaves
  exactly like Stage A with that DB as the store. The rest of this
  section is only for cross-DB conversions.
- **Mechanism — saga with durable coordinator intent:**
  1. The **coordinator** is the source currency's DB, as resolved by the
     currency→DB directory at admission. Admission writes the intent
     there, in the same local transaction that places a **pending hold**
     on the source account (principal + fee) — the source funds are
     reserved, not yet moved.
  2. The destination DB posts the destination leg (LP → caller) marked
     with the `conversion_id` and a `pending` state, crediting a
     non-spendable pending balance.
  3. **Commit is a durable decision, written once.** The coordinator
     records `COMMIT` in its intent row in the same local transaction
     that converts the source hold into the posted source legs
     (caller → LP principal, caller → fee account). After that
     transaction, the saga has exactly one direction: **forward**. The
     destination leg is confirmed spendable; intent → `POSTED`.
  4. **Compensation exists only before the commit decision.** A step
     failing or timing out (saga timeout: 5 minutes, an operator
     parameter) before `COMMIT` is recorded triggers compensation: the
     destination pending leg is voided (it was never spendable, so
     voiding moves no value), the source hold is released, and the
     intent ends `FAILED_COMPENSATED`. Once `COMMIT` is recorded,
     compensation in this sense no longer exists — the hold is already
     consumed by posted legs, and there is nothing left to "release".
     Recovery after a post-commit crash or a failed destination
     confirmation **finishes forward**: it re-drives the destination
     confirmation until it lands. If forward completion proves
     permanently impossible (e.g. the destination DB is being retired),
     the only permitted exit is an explicit **refund conversion** — a
     new compensating conversion that restores the caller's posted
     source principal and fee in full and reverses the LP's destination
     position — and the intent ends `FAILED_COMPENSATED` only after
     that refund has posted. A caller is never left charged without
     either the destination funds or a posted refund.
     Both compensation and forward recovery are idempotent and driven
     by the coordinator intent, so a crashed coordinator recovers by
     resuming the saga from its recorded step and its recorded
     commit/no-commit state.
- **The weaker guarantee, stated plainly:** between steps 2 and 3 a
  cross-DB conversion is *visibly unsettled*. There is no moment at
  which the money has vanished — source funds are held, destination
  funds are pending — but finality is eventual (bounded by the saga
  timeout), not atomic. If compensation itself cannot complete, the
  intent sits in `COMPENSATING` and alerts; funds stay held/pending,
  never half-spendable.
- **User-visible behavior:** the conversion shows `pending settlement`
  from admission until `POSTED`/`FAILED_COMPENSATED`; the source balance
  shows the held amount as unavailable; the destination pending amount
  is shown as pending and is not spendable, not counted in the
  spendable balance, and not usable as conversion input. Receipts are
  issued only at a terminal saga state. This is the honest Stage B
  behavior; a UI that hides the pending state would be claiming
  atomicity the backend does not have.
- **Ordering:** sagas for the same source account execute their hold
  step under that DB's local ordering; there is no global cross-DB
  ordering guarantee, and none is needed — caps and balances are
  per-DB facts enforced at the hold step.

### 3.3 Stage C — TigerBeetle

The #2063 contract as written: all legs in one linked TigerBeetle batch
per ledger pair, `FAILED_ATOMIC` semantics, cluster-side account flags
as the inventory guard, recovery by exact leg IDs (§2.4 table of the
#2063 record). Nothing in Stages A or B may assume a TigerBeetle-only
behavior (linked batches, cluster flags) — that is what keeps the B→C
migration a deployment exercise per #5676 principle 4.

## 4. Invariant and test strategy

Oracle doctrine (testing doctrine, 2026-11-04): every automated check
below names its oracle.

- **One invariant suite, every adapter** (per #5676): balanced postings,
  no negative balances, idempotent retries, cap enforcement under
  concurrency, crash-injection at every state transition. Oracle: a
  simple in-memory reference ledger (model-based testing) driven by the
  same generated operation sequences (property-based testing over random
  transfer/conversion sequences, including failures injected between
  saga steps in Stage B).
- **Stage A additions:** Lua atomicity under concurrent scripts;
  out-of-sequence posting attempts are rejected by the watermark check;
  Redis-loss rebuild equivalence. Oracle: regular-store replay result.
- **Stage B additions:** saga compensation completeness — after any
  injected failure, terminal state is `POSTED` with both legs, or
  `FAILED_COMPENSATED` with (pre-commit) hold released and no spendable
  destination credit, or (post-commit) a posted refund restoring the
  caller's principal and fee. A crash injected between the commit
  transaction and destination confirmation must finish forward. Oracle:
  per-DB leg census by `conversion_id`. A test that finds a fourth
  terminal shape fails the adapter.
- **Stage C additions:** the #2063 §3 acceptance list as written.

## 5. Sequencing and dependencies

1. **#3801** (gateway verification flow + revocation-set check, Phase 2
   of #2290) lands first: admission at every stage depends on its
   verification and revocation semantics. No stage adapter enables
   conversions before it.
2. **#3802** (quote issuance + binding, Phase 3 of #2290) lands second:
   adapters consume issued quotes; they do not issue their own.
3. **#2290 Q1** (may the platform emergency-revoke another LP's
   authorisation?) **does not block this design or any stage.** The
   assumed contract is the recommended Option A from both the #2290 and
   #2063 records: issuer-only graph revocation; platform response is a
   local, logged gateway suspension. If Drew rules Option B, only
   #3801's revocation-set check gains a second event type — the intent,
   saga, and adapter contracts in this record are unchanged, because
   admission already consumes "the current revocation set" as an input
   rather than encoding who may revoke.
4. Stage order follows #5676 (A, then B, then C); conversion enablement
   per stage waits for that stage's invariant suite (§4) passing against
   its adapter.

## Alternatives considered

- **Claim two-phase commit for Stage B.** Rejected: no concrete
  cross-Turso coordinator mechanism exists in the current store stack;
  acceptance for this record forbids claiming cross-Turso atomicity
  without one. The saga's guarantee is weaker and is stated as such.
- **Single coordinator DB holding all conversion legs.** Rejected: it
  re-centralises exactly the hot path Stage B shards, and breaks when
  the coordinator DB is itself the bottleneck. (The coordinator
  *intent* lives in the source DB; the legs still live in their own
  DBs.)
- **Per-stage conversion semantics** (e.g. Redis conversions without
  quotes, TigerBeetle conversions with extra rules). Rejected: breaks
  #5676 principles 3–4 (backend-independent invariants; swap, don't
  rewrite) and triples the audit surface.
- **Synchronous dual-write in Stage A** (Redis and regular store in
  one gateway operation treated as atomic). Rejected: two systems, no
  shared transaction — a crash between them is ambiguous by
  construction. Intent-first + idempotent posting + recovery probing
  gives the same user guarantee honestly.
- **Defer all conversion until Stage C.** Rejected: #5676's whole point
  is a usable Stage A; the #2063 contract was written stage-neutrally
  precisely so conversion does not wait for TigerBeetle.

## Non-goals

- No runtime code, schema, or adapter implementation (design only).
- No change to the merged #2063/#2290 contracts, and no second signed
  rate-authorisation format.
- No graph-native (offline) conversion — outside v1, per §0 decision 4.
- No rate discovery, routing, or AMM behavior (already #2063 non-goals).
