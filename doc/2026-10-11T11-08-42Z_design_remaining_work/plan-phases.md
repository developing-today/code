## 1. How to read the plan

- **Steps** have an ID (P0.1, P1.3, ...). A step is done when its tests exist and pass, its review is recorded, and its commits are marked in the phase document.
- **Blocker** means a true dependency: the step cannot merge until the named step has merged. Everything not blocked runs in parallel.
- **Track** is a stream of work that one subagent, or the lead, owns from start to finish, in its own worktree.
- **Owner-blocked** means the step needs something only the owner can provide. It never blocks other steps.
- **(decided)** marks a decision recorded in the index. **(owner question)** marks something waiting for an answer, listed in section 4.

## 2. Execution rules (apply to every phase)

These rules govern how each phase runs. They are repeated in every phase document.

1. **Start of a phase.** Merge `main` into the phase base branch and run the baseline tests. Record the start commit as `Phase N start: <sha>`. Create the phase document in `doc/<datetime>_phase_<n>_<name>/` with the step list. Link it from the plan.
2. **Tracks run in worktrees.** Each track works in its own `git worktree`, on its own branch, created from the phase start commit: `phase-N/<track>`. Worktrees live in `/home/user/work/wt/`. Each worktree builds into its own target directory, outside the repository. Tracks that touch the same files run one after another, and the plan marks them.
3. **Subagents run targeted tests.** A subagent runs the tests for what it changed, plus its new tests. It runs the full suite or a full build only when its change touches shared code, and then only once. The lead runs the full suite at merge points.
4. **Commits carry the step ID**, for example `feat(id): ChainExt validation [P1.2]`. Commits follow Conventional Commits. The subagent reports its commit SHAs.
5. **The lead merges in dependency order**, one track at a time, not all at once. After each merge the lead pulls `main` if it moved, reviews the merged diff, adds tests the review found missing, reruns the targeted tests, and records the commit-to-step mapping.
6. **End of a phase.** Review the whole diff from the phase start commit to the phase end commit, not just the merges. Run the full test run (section 13). Fix problems and add tests. Record the end commit as `Phase N end: <sha>`. Record every step as done, deferred, answered, or cancelled, with the reason.
7. **Every bug gets a regression test that would have caught it.** The test covers the whole class of error, not only the one instance. Use many cases against the same property.
8. **Fuzzing feeds a checked-in list.** A fuzz or property failure is minimized and added to `pkgs/id/tests/regressions/<area>.txt`. The normal test run replays that list every time, so a fixed bug cannot return unnoticed.
9. **Test layers** follow the repo's testing reference, `doc/2026-03-29T00-00-00Z_reference_testing_architecture/`. Rust unit tests live in `#[cfg(test)] mod tests`, with `#[allow(clippy::unwrap_used, clippy::expect_used)]` in test modules, as `pkgs/id/AGENTS.md` requires. Rust integration tests live in `tests/`. New layers for this work are property tests, the crash gate, the regression replay, and fuzz smoke runs (section 13).
10. **Dependencies.** Adding or updating a dependency is allowed, and each one is reported to the owner in the final report, with its name, version, why, and the feature it enables (`pkgs/id/AGENTS.md`). Dev-only tools go in `nix-common.nix`, never in `shell.nix` or `flake.nix`.
11. **Justfile and Nix stay in step.** A new `just` recipe gets a matching `nix run .#<command>` app in `flake.nix`, and a check where CI can verify it.
12. **Never discard unstaged work.** No `git restore`, no `git checkout -- <file>`, and no command that overwrites uncommitted changes. This applies to subagents as well. Worktrees are created from commits, so uncommitted design files are not visible in them until committed.
13. **Nothing is pushed to `main` by a track.** The lead merges to the feature branch. The owner signals the merge to `main`.
14. **Concurrency limit.** At most four cargo builds of `pkgs/id` run at once on this 16-CPU host. Builds that share dependencies are serialized.

## 4. Owner questions to answer before Phase 0 starts

These do not block the first steps, but each answer changes a step. The preferred answer is in brackets.

1. **Ed25519.** Stay on 3.0.0 with a conversion shim, and switch the five plain `verify` calls to `verify_strict` [preferred]. Moving to 2.x is not possible while iroh 1.3.0 is pinned. Confirm, or name the alternative.
2. **Scheme v1 as the first release.** The serde_bytes encoding becomes the first released scheme, since nothing has shipped [preferred]. It needs a fork change of two lines, which you accepted as a fork we own.
3. **Ticket route when the invite event is unreadable.** Proceed unverified and label it clearly [preferred], or refuse. This arises when pull is authorized and the joiner is not yet a member.
4. **Welcome frame cap.** One identity frame cap for welcomes and chunk above it [preferred], or the 1 MiB cap the world session uses. The number decides when `full` history needs chunking.
5. **`recent:N` presets.** 32 for quiet worlds and 128 for churn-heavy ones [preferred], and `full` remains the default for every world.
6. **Clippy 1.99 lints.** Keep them as a TODO and allow the two lint names for now [preferred], or fix the about 50 sites in Phase 0. The owner's lints review is later either way.
7. **Where documents go.** The design and phase documents in `doc/` at the repo root [preferred, as the root CLAUDE.md says], with plans also in `.opencode/plans/` [preferred, as `pkgs/id/AGENTS.md` says]. `pkgs/id/AGENTS.md` names `docs/` instead of `doc/`. Confirm.
8. **Real-network tests.** These need two separate networks. You said you would set up VPS later. Is that the time to run them, or should they wait [preferred: wait]?

## 13. Testing

**Layers.** These follow the repo's six layers, and add the layers this work needs.

| Layer                          | What                                                   | When it runs                          | Used by                                            |
| ------------------------------ | ------------------------------------------------------ | ------------------------------------- | -------------------------------------------------- |
| 1. Rust unit                   | `#[cfg(test)] mod tests`                               | every run                             | every step                                         |
| 2. Rust integration            | `tests/`, several nodes in one process over loopback   | every run                             | sync, groups, invites, pull                        |
| 3. Property                    | proptest, many cases, fixed seeds in CI                | every run                             | ChainExt, tuple, tags, membership, sync sets, caps |
| 4. Crash gate                  | in-process fault model for redb, release mode          | every run (about 40 s)                | storage, identity store                            |
| 5. Regression replay           | `tests/regressions/*.txt`, every entry replayed        | every run                             | every area                                         |
| 6. Fuzz smoke                  | a bounded run of each fuzz target; long runs on demand | every run; long runs on demand        | decoders, tuple, tickets                           |
| 7. End-to-end, CLI             | the binaries as separate processes, with timeouts      | every run                             | CLI, `serve`, invites                              |
| 8. NixOS VM                    | two or more VMs on the network                         | the nix check                         | relays, the systemd unit, real-looking topologies  |
| 9. Playwright E2E              | the web UI                                             | `just test-e2e` when web code changes | web                                                |
| 10. Live network               | n0, real networks                                      | on demand, marked ignored             | connectivity                                       |
| 11. Mutation checks            | planted bugs must fail                                 | on demand at phase end                | membership, tags                                   |
| 12. Interop and golden vectors | CBOR, Seitan, scheme versions                          | every run                             | encodings                                          |

**The full test run** is one script, with these parts: `just check` (the primary check in `AGENTS.md`), `just test` (fast Rust and TypeScript), the crate's full test set with the three known failures handled (P0.1), the regression replay, the property tests with the CI seed set, the crash gate, the fuzz smoke runs, and `doc` tests. At phase end, add `just test-nix` (27 checks, heavy) and `just test-e2e` when web code changed. The script reports what it skipped and why.
