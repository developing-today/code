# Exact arithmetic in the currency supply audit

**Design proposal dated November 23, 2026.** The motivating observations use the pinned sources below.

**Proposed correction to the existing reconciliation job.** Owner to establish against the currency repository issues before filing. At the reviewed revision, posted fields are unsigned 128-bit counters, and the audit converts each to a signed integer with saturation before taking a difference. Holder aggregation also takes place in signed width. This record changes the accounting/reporting boundary only. [Reconciliation implementation](https://github.com/developing-today/code/blob/7310a95730791e66da98f7b0e13865930058a516/pkgs/id/src/currency/reconcile.rs#L186) · [Existing reconciliation PR](https://github.com/developing-today/code/pull/13139)

**Invariant.** Compare exact mathematical debits and credits across the complete account set in a single ledger view. Reading a backend error must produce an incomplete audit. A missing lazily created fee/burn account can follow the existing zero policy. Preserve the distinction among balanced, divergent and indeterminate in both the typed API and serialized report. A counter that exceeds a preferred output representation can still be a valid ledger value. Never turn overflow into a clean result.

**Implementation choice.** First inspect the supported ledger snapshot semantics and all public report consumers. Keep an explicit error/refusal for an unrepresentable intermediate as the small compatible fallback. For a full-range exact result, use checked wider accumulation with a proven bound for the number of accounts, or arbitrary-precision arithmetic in the audit boundary. A fixed 256-bit accumulator needs a stated account-count/counter bound and checked additions. JSON-facing large magnitudes need an agreed lossless representation with compatible readers. The authorization and posting paths require no change for this invariant.

**Independent oracle.** Set M to 2^127−1. Issuer posted debits M+2, one holder's posted credits M+1, other counters zero. The mathematical shortfall is one. The current conversion maps both to M. Repeat with equal M+2 on both sides, split the holder credits between accounts and cover both above and below the signed limit. Under an explicit limited-range implementation, the allowed result for an unrepresentable total is an indeterminate audit. It must carry the reason rather than report clean. Confirm that summing accounts in a different order gives the same audit outcome. This is a fixture for the auditor reading a deliberately divergent ledger view. Reachability through normal currency posting has not been established.

**Rollout.** Check whether the product already constrains posted totals elsewhere. If so, enforce that bound in the auditor too and document how historical data outside it is reported. Use the existing reconciliation tests and portable Fleet verification route. No production scan is required to decide the mathematical question.
