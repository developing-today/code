# Design: UDP-denied SSH fallback for `id`

- Date: 2026-11-01
- Status: **design — recommendation recorded; Drew's scope decision is open**
- Issue: [#785](https://github.com/developing-today/code/issues/785), Phase 13 F13.3
- Scope: the remaining UDP-denied fallback only. SSH-over-iroh reachability and
  normal SSH authentication have already landed in [PR #842](https://github.com/developing-today/code/pull/842).

## Decision to make

Should the UDP-denied route implement a literal **Iroh-over-SSH transport**,
reuse the existing **SSH frame transport** as a session-level fallback, or drop
the fallback requirement and leave SSH as an explicit route?

**Recommendation: reuse F13.2's SSH exec frame transport as an opt-in,
session-level fallback from Iroh.** Do not carry Iroh/QUIC inside SSH. This
achieves the issue's world-join outcome over an available port-22 path using
the existing frame protocol, while being explicit that it is not an Iroh
transport. It requires clarifying acceptance criterion 2; see Q1 in §8.

## 1. Context and current state

Issue #785 asks for an unmodified SSH client to reach a NAT'd host through
Iroh, a fallback when UDP is denied but port 22 is open, and preservation of
normal host-key and peer-ID trust. The latest issue triage records acceptance
criteria 1 and 3 as met by #842 and criterion 2 as still open. The latest
comment on transport tracker #536 likewise says D1-051's SSH-over-Iroh portion
is superseded by Phase 13; it does not close the fallback remainder.

The two routes in the current implementation are different transport
envelopes for the same world-session protocol:

- **Iroh route:** `WorldClient` connects using the world ALPN and opens an Iroh
  bidirectional stream (`pkgs/id/src/world_net.rs:173-199`). The host registers
  that ALPN and accepts bidirectional streams (`pkgs/id/src/world_net.rs:30-32,
  57-95`; `pkgs/id/src/commands/serve.rs:986-1005`). The connectivity helper
  uses the Iroh endpoint connect path, with a deadline; its relay policy is
  still Iroh connectivity, not an SSH/port-22 route
  (`pkgs/id/src/connectivity.rs:16-20, 37-47, 69-85`).
- **F13.2 SSH route:** the CLI already offers `--via ssh`; `--addr` and
  `--no-relay` are Iroh-specific (`pkgs/id/src/commands/world.rs:720-757`).
  SSH exec accepts only the `id-world/1` request and runs the normal session
  over `SshFrameIo` (`pkgs/id/src/world_ssh.rs:151-158, 359-391`). The client
  checks a known-hosts entry or explicit fingerprint before starting that
  request (`pkgs/id/src/world_ssh.rs:1110-1171`). The join pump is generic over
  async byte streams and uses the same frame envelope
  (`pkgs/id/src/commands/world.rs:1754-1775`). Existing tests compare the Iroh
  and SSH frame bodies (`pkgs/id/src/world_ssh.rs:2559-2647`), but do not test
  automatic fallback with UDP denied.
- **SSH-over-Iroh (already delivered):** `SshTunnelProtocol` forwards each Iroh
  stream's bytes to the host's loopback SSH listener
  (`pkgs/id/src/world_ssh.rs:83-147`). The SSH listener remains opt-in through
  `--world-ssh-port` (`pkgs/id/src/commands/serve.rs:1150-1169`). This direction
  solves third-party OpenSSH reachability; it is not the reverse fallback.

The Phase 13 plan separates the transport envelope from the
`ClientFrame`/`ServerFrame` session protocol and describes F13.3's UDP-denied
case as Iroh-over-SSH (`.opencode/plans/phase-13-client-shells.md:31-37,
78-80`). The shell-contract reference records that this literal fallback
requires a non-QUIC Iroh transport or SSH-carried datagram channel, neither of
which exists; it also says F13.2 covers the join use-case in the meantime
(`doc/2026-10-25T05-54-40Z_reference_shell_contract/2026-10-25T05-54-40Z_reference_shell_contract.md:148-174`).

## 2. Viable options

| Option | What it means | Benefits | Costs / risks |
| --- | --- | --- | --- |
| **A. Literal Iroh-over-SSH** | Carry Iroh's transport through an SSH-carried datagram channel or add a non-QUIC Iroh transport. | Preserves the Phase 13 wording and could make Iroh protocols available over the SSH route. | Requires a new transport or bridge, not a small change to the current QUIC connector. It duplicates/overlaps F13.2 for world joins and adds transport, lifecycle, and failure modes. The existing SSH exec byte stream is not an Iroh transport. |
| **B. Session-level SSH fallback (recommended)** | Attempt Iroh first; if Iroh cannot be reached for a classified network-connectivity reason, use the existing SSH exec frame route, provided the caller supplied an SSH target and trusted host key. | Reuses F13.2, preserves identical session frames, and gives world joins a port-22 path without nesting QUIC in SSH. A UDP-denied test can exercise real fallback selection. | It is not literally “Iroh-over-SSH”; the issue and Phase 13 acceptance wording must say “Iroh-to-SSH frame-transport fallback.” It is scoped to world sessions, not arbitrary Iroh ALPNs. Requires both an Iroh destination and a distinct SSH destination because a peer ID is not an SSH host name or host-key pin. |
| **C. Keep SSH explicit; remove fallback** | Leave `--via ssh` as the operator-selected constrained-network route and drop criterion 2. | No new transport selection logic; F13.2 already provides the join path over SSH. | No automatic fallback and no evidence that a single command negotiates around UDP denial. This weakens the issue's explicit fallback requirement. |

## 3. Recommended behavior

Implement option B as an **opt-in route policy**, not a change to existing
defaults:

1. The caller supplies the ordinary Iroh destination and a separate SSH
   destination plus host-key trust material. Never infer an SSH hostname or
   host key from an Iroh peer ID.
2. The client attempts Iroh first. It may fall back to SSH exec only when
   Iroh connection establishment fails with a classified reachability error
   (for example, timeout or unreachable network).
3. Do not fall back after an Iroh peer-identity rejection, a world/session
   authorization rejection, a protocol/version error, or an SSH host-key or
   authentication failure. These are trust or application failures, not
   evidence that UDP is unavailable.
4. The SSH leg runs the existing `id-world/1` exec session and carries the
   same framed session protocol. It does not create an Iroh connection or
   provide non-world Iroh protocols.
5. Existing explicit `--via iroh` and `--via ssh` behavior remains unchanged.
   No SSH server is enabled automatically; the host's SSH server stays
   opt-in.

This is a deepening at the **session transport-selection seam**: one policy
selects between existing adapters, while Iroh connectivity, SSH host-key
verification, and the session protocol remain owned by their current modules.
Changing only `connectivity::connect` is insufficient for this option: the
current `WorldClient` owns an Iroh connection and QUIC streams
(`pkgs/id/src/world_net.rs:173-199`), whereas SSH exec already supplies the
byte-stream path at the join pump (`pkgs/id/src/commands/world.rs:1754-1775`).

## 4. Invariants

1. **Transport choice does not change the world-session protocol.** Both legs
   deliver the same `ClientFrame`/`ServerFrame` stream; the fallback does not
   alter journal semantics or add frame kinds.
2. **The two trust decisions stay distinct.** Iroh peer identity authenticates
   the Iroh route; the SSH route verifies its SSH host key and SSH
   authentication. Neither identity substitutes for the other's, and SSH
   login alone grants no world capability
   (`pkgs/id/src/world_ssh.rs:20-26, 1110-1171`).
3. **No fallback masks a trust or application rejection.** Only a classified
   Iroh reachability failure can select SSH; a bad peer ID, SSH host key,
   credential, session authorization, or protocol version remains a visible
   error.
4. **No ambient SSH exposure.** Fallback does not enable or bind the host SSH
   listener; `--world-ssh-port` remains an explicit server option
   (`pkgs/id/src/commands/serve.rs:1150-1169`).
5. **No silent route change for current callers.** Existing explicit Iroh and
   SSH selection remains stable; automatic fallback is used only when opted
   into and when both destinations are configured.
6. **The existing OpenSSH tunnel remains byte-forwarding only.** Reaching the
   SSH server over Iroh still requires normal SSH authentication
   (`pkgs/id/src/world_ssh.rs:83-147`).

## 5. Implementation acceptance criteria

These criteria implement the recommendation in §3. They intentionally replace
the ambiguous phrase “iroh-over-SSH fallback” with the accurate
“Iroh-to-SSH frame-transport fallback” if Drew accepts Q1.

- [ ] Existing acceptance 1 remains covered: an unmodified OpenSSH client
      reaches the NAT'd host through the Iroh tunnel (already verified by
      #842; retain as regression coverage).
- [ ] An opt-in automatic route requires both an Iroh destination and an SSH
      destination with host-key trust configured; existing explicit route
      selection is unchanged.
- [ ] A test with UDP/Iroh connectivity denied and SSH reachable proves the
      Iroh attempt fails for reachability, the client selects SSH exec, and
      the world session succeeds over the same frame protocol.
- [ ] A parity test proves the fallback and direct Iroh paths produce the
      same session frames and world/journal outcome.
- [ ] Tests prove that peer-identity, host-key, SSH-authentication,
      world-authorization, and protocol errors do not trigger fallback or
      become success.
- [ ] The host SSH listener remains opt-in, and an Iroh peer ID alone cannot
      authorize SSH or world access (existing acceptance 3 remains covered).
- [ ] User-facing help/docs describe this as an SSH frame-transport fallback,
      not as Iroh carried over SSH.

## 6. Phased implementation plan

Each step has a reviewable deliverable and can land as a separate PR after the
scope question in §8 is answered “B”. Steps 2–4 depend on step 1.

1. **Route contract and policy.** Add the opt-in dual-destination route shape
   and a small transport-selection policy. Preserve the existing explicit
   `--via` modes. Unit-test required inputs, route order, and the reachability
   error classification. **Done when:** policy tests prove the default is
   unchanged and SSH can only be selected with an explicit trusted SSH
   target.
2. **Iroh-first SSH-exec fallback.** Wire the policy into world join; on an
   eligible Iroh connection failure, run the existing SSH exec session.
   Keep auth, identity, and protocol failures terminal. **Done when:** a
   focused client/server test exercises a successful fallback and checks
   failure classification without changing the frame protocol.
3. **UDP-denied and trust regression tests.** Add an integration test with
   Iroh/UDP blocked and SSH available, plus negative cases for bad peer
   identity, SSH host key, SSH authentication, and world authorization.
   Compare the session frames and durable world outcome against direct Iroh.
   **Done when:** the positive UDP-denied case falls back and every negative
   trust/application case fails closed.
4. **Reconcile docs and issue acceptance.** Update the Phase 13 plan, shell
   contract reference, CLI help, and #785 acceptance wording to call this
   “Iroh-to-SSH frame-transport fallback”; keep the distinct literal Iroh
   carrier out of this implementation. **Done when:** docs match the shipped
   route and #785's three acceptance criteria distinguish the already-landed
   SSH-over-Iroh path from the new fallback.

If Q1 selects literal Iroh-over-SSH instead, do not implement steps 1–3 as a
proxy for it. File a separate transport design for a non-QUIC Iroh path or an
SSH-carried datagram channel first; that is a different, broader seam.

## 7. Non-goals

- Do not tunnel QUIC packets or arbitrary Iroh ALPNs through the SSH exec
  channel.
- Do not make SSH-over-Iroh a prerequisite for SSH frame transport, or vice
  versa; they solve opposite directions.
- Do not change SSH host-key policy, Iroh peer identity, world authorization,
  journal format, shell contract frames, or the server's opt-in SSH setting.
- Do not close #785 as part of this design. The fallback remains unimplemented
  until its selected behavior is built and tested.

## 8. Question for Drew

**Q1 — What does the UDP-denied acceptance criterion require?** This changes
the published F13.3 transport requirement, so implementation should wait for
this scope ruling; the design and recommended implementation path are complete.

- **A. Literal Iroh-over-SSH** — preserve the current phrase and build a
  non-QUIC Iroh transport or SSH-carried datagram channel. **Not recommended:**
  larger new transport work, and it duplicates F13.2 for the stated world-join
  use-case.
- **B. Session-level fallback to SSH exec** — Iroh first, then the existing
  SSH frame transport when Iroh cannot be reached and a separately trusted SSH
  destination is configured. **Recommended:** meets the port-22 world-join
  outcome by reusing F13.2; update criterion 2 to name the actual transport.
- **C. Explicit SSH route only** — count `id world join --via ssh` as sufficient
  and remove automatic fallback from F13.3. **Not recommended:** smallest
  scope, but does not meet a negotiated/fallback acceptance test.
