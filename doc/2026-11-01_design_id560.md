## Decision to make

How should F12.18 finish when its literal acceptance asks every denial to
assert an F11.13 code, but several protected boundaries use different error
contracts—and the journal has no byte-limit refusal to test at all?

**Recommendation:** keep this a verification-only change. Assert each bound's
existing, documented outcome; assert F11.13 `CapError` codes only for
capability refusals; and remove journal size from this suite unless Drew
separately chooses to design a hard journal limit. Do not unify unrelated
errors or add a journal cap in a test PR.

## Options and trade-offs

### A. Assert each bound's own refusal contract; keep journal out of scope — recommended

Extend the probe-driven suite for fuel, memory/output, frame size, session and
open-world ceilings, and schedule count/horizon. Assert the trap/poison,
framing error, `ResolveError` variant, or schedule reason that the code actually
returns. Assert an F11.13 code only where the refusal is a `CapError`. Do not
claim that journal size is bounded; defer that requirement for Drew's ruling.

**Why:** every test describes behavior the program implements today, preserves
the stable capability-code contract, and stays inside Phase 14's verification
plane. It avoids changing errors that clients may already distinguish and
doesn't invent a journal budget inside a test task.

### B. Normalize all denials onto F11.13 codes and add a journal cap

Change framing, hub, and schedule failures to capability-code errors and add a
hard `FileJournal` byte limit with a selected refusal action.

**Trade-off:** it would make the original wording literal, but it changes
runtime and possibly wire-visible behavior. A journal cap also needs decisions
about whether append is refused, compaction is forced, or the world is closed.
This is a separate production design, not a test-only extension of F14.17.

### C. Keep the literal acceptance without changing behavior

Only assert F11.13 codes for capability cases and leave the other mapped
bounds out of the harness.

**Trade-off:** this neither meets the issue's all-bounds acceptance nor the
F14.17 plan, which specifically calls for folding the mapped bounds into the
suite (`phase-14-close-out.md:142`). It is not recommended.

## Recommended decision and invariants

Adopt option A. The implementation should use the narrowest existing test seam
for each boundary and share a probe/liveness helper where that can be done
without widening production APIs. The probe demonstrates node/service
responsiveness; it must not require a target world to survive a failure whose
documented behavior poisons that world.

Invariants:

1. No production behavior, public API, wire format, or error mapping changes
   are included. If a test exposes a missing or incorrect limit, file a
   separate production issue rather than expanding this test change.
2. Capability denials continue to assert their stable F11.13 code. Other
   boundaries assert their own concrete error or failure condition; tests must
   not manufacture `CapError` expectations for `anyhow` framing errors,
   `ResolveError`, sandbox traps, or schedule validation.
3. A probe operation succeeds before/after each applicable hostile case. For a
   deliberately poisoned target world, the probe is against a separate
   healthy service/world, so the assertion is node liveness rather than false
   recovery of the poisoned instance.
4. The `world_dos` integration target remains in the existing PR-gate shard
   set. Do not add a duplicate serial CI job or a separate workflow solely to
   run it.
5. Journal-size refusal is not claimed or tested until a byte cap and its
   refusal semantics have a separate product decision.

## Implementation acceptance criteria

- The probe-driven `world_dos` target covers the existing provider, wants/args,
  and schedule-ID cases plus fuel, guest-memory/output, frame-size,
  session-ceiling, open-world-ceiling, and schedule-count/horizon bounds.
- Every case asserts the code's actual refusal outcome: F11.13 string codes
  only for `CapError`; the subsystem-specific trap, framing error, hub variant,
  or schedule reason everywhere else.
- Probe liveness is verified without asserting that an intentionally poisoned
  world recovers.
- The module header inventory matches what is directly exercised by the
  consolidated target and what remains covered only by dedicated tests.
- The existing CI shard discovery includes `world_dos`; verify with the
  targeted test and the relevant shard/check. No production source changes are
  required for acceptance.
- Journal size is explicitly excluded pending the Drew decision below.

## Phased implementation plan

Each phase is an additive, separately mergeable test-only increment; after
each, `world_dos` should compile and pass. A later phase can be skipped without
leaving an earlier phase broken.

1. **Probe harness and sandbox limits** (`pkgs/id/tests/world_dos.rs`). Factor
   the current probe assertion into reusable test support, then add fuel,
   memory-growth, and guest-output cases with their current
   trap/poison/error assertions. Keep probe checks isolated from the target
   instance when that instance is poisoned. Done check: the focused target
   passes with the existing hostile-provider assertions unchanged.
2. **Transport and hub ceilings** (`pkgs/id/tests/world_dos.rs`). Add the
   frame-size case (asserting the current framing error), session-ceiling case
   (`Busy`), and open-world ceiling case (`TooManyWorlds`) through their
   existing public/test seams. Demonstrate that the healthy probe path still
   answers while these bounded denials are exercised. Done check: each case
   asserts its actual refusal and the focused target passes.
3. **Schedule limits, inventory, and CI exit**
   (`pkgs/id/tests/world_dos.rs`). Add schedule count/horizon cases with the
   reason currently returned; retain the existing schedule-ID case. Update
   the module header map to distinguish direct suite coverage from remaining
   dedicated tests. Done check: run the focused target and verify its
   automatically assigned `test-shard-*` CI partition. If any bound has no
   current refusal or exposes a defect, route the runtime decision separately
   rather than changing production code in this suite.

## Question for Drew

**Should journal size remain an F12.18 acceptance item when there is no
`FileJournal` byte limit today?**

1. **Remove journal size from this test suite (recommended).** Keep F14.17
   test-only and accept that the journal has no absolute byte ceiling; any
   existing checkpoint compaction is not itself a hard byte limit. This avoids
   inventing a product budget and refusal semantic here.
2. **Design a separate production issue for a journal byte cap.** Choose a
   limit and define whether reaching it refuses append, triggers compaction, or
   closes the world; then test that contract in its own change.
3. **Add the cap to F14.17 (not recommended).** This mixes new runtime behavior
   into a verification-only task and leaves the refusal semantics unresolved.

Recommendation: option 1 for #560/F14.17; if an absolute journal budget is a
product requirement, choose option 2 and settle its semantics separately.
This answer does not block the already-scoped test-only packet #3840; it only
decides whether the original journal-size bullet is removed or routed as
separate production design. No other Drew-only decision blocks implementation.
