# R2 — the shipped middle between Rummager and Cobweb (Sneakerweb, Earthstar, Weird/Leaf, SSB tangles + post-mortem)

## 1. Sneakerweb — the static whole-site middle

Model. Sneakerweb is a peer-to-peer protocol for publishing static websites, built on the Willow'25 parameterisation of Willow (https://sneakerweb.org/spec). Each site is a set of Willow Entries in one communal namespace (fixed namespace id given in the spec), with a strict one-to-one mapping between subspaces and websites ("domains"): all assets of one site share one subspace id, and that subspace id (an Ed25519 public key) IS the domain, served as `<pubkey>.localhost` (https://sneakerweb.org/spec). Paths inside the subspace map to URL paths, with `index.html` fallback conventions spelled out in the spec (https://sneakerweb.org/spec). The CLI offers `domain`, `publish`, `export`, `import`, `block`, and `serve` subcommands (https://sneakerweb.org/).

Composition unit. The unit is the whole static site (one subspace = one domain = one site). Cross-site composition is by ordinary hyperlinks between key-addressed sites; the project presents this as sites forming an interlinked web by links rather than by shared data (https://sneakerweb.org/). There is no multi-app shared document layer: each site is authored by whoever holds the subspace key.

Cross-reference story. References live in the content layer (plain HTML links between `<pubkey>` domains), not in a naming layer or a data model. The spec defines an optional `sneakerweb.html` preview entry per subspace (https://sneakerweb.org/spec). What breaks when the target changes or is deleted: nothing structural — a link to a key-addressed site either resolves (peer has the entries) or it does not; there is no referential integrity, no backlink index, no tombstone propagation at the web layer. Blocking is a local client behavior (`sneakerweb block`), not a protocol deletion.

Onboarding / first-sync cost. There is no live sync at all: distribution is by `.snk` drop files (Willow Drop Format) carried on physical media or LAN, explicitly recommended as the ONLY sharing channel (https://sneakerweb.org/spec). First sync cost = obtaining the `.snk` (in person, "sneakmeets"/on foot per the Lobsters thread with gwil: https://lobste.rs/s/vwni9c/sneakerweb) and importing it. There is no pub/invite bootstrap to pay for, but also no way to catch up incrementally over the internet — cost is social/logistical rather than bandwidth.

Link/reply as data. Links are NOT data in Sneakerweb: they are HTML strings inside payloads. No reply/mention object exists at the protocol level. That bought simplicity (any static site generator works; serving is a localhost web server) at the cost of no live interaction, no comments, no cross-site queries — the "gives up live sync and URIs" point in the issue brief is confirmed by the spec.

Deletion / pruning story. Willow underneath gives Sneakerweb true deletion via prefix pruning (newer entries overwrite; deleting a prefix removes the subtree — see Willow comparison page https://willowprotocol.org/more/willow_compared and Meadowcap moderation example https://willowprotocol.org/specs/meadowcap/index.html). At the Sneakerweb layer, deletion = publishing tombstoning entries and re-exporting the `.snk`; already-distributed copies only disappear when holders import the newer drop. No evidence in the spec of per-page retraction across all holders; the offline-drop model makes deletion eventual and cooperative.

What it proves. Authoring/reading a whole site on Willow works with zero servers and zero DNS; key = domain is legible and censor-resistant. But composition stops at the hyperlink: no shared mutable state, no cross-app data reuse.

## 2. Earthstar — the flagship predecessor and app-facing model

Model. Earthstar is a spec plus JS library for offline-first multiwriter apps: data lives in shares (small-group universes, `+name.pubkey`), written as documents at paths by identities (`@shortname.pubkey`, Ed25519), synced peer-to-peer with replica servers as dumb always-on stashes (https://earthstar-project.org/docs/how-it-works). The es.5 data format spec defines documents, signatures, ingestion, ephemeral documents, and attachments (https://earthstar-project.org/specs/data-spec-es5). The current line is superseded by an Earthstar-v6/Willow-based spec, with v11 in beta (https://earthstar-project.org/specs/data-spec-es5, banner).

Composition unit. The share is the composition unit: a bounded multiwriter dataset that many apps can read/write simultaneously. Cross-app sharing works by path-prefix convention: first path segment names the data type or app (e.g. `/wiki/`, `/chat/`), and community application formats (e.g. `/about/1.0/displayName`) let many apps reuse profile/avatar data (https://earthstar-project.org/community/application-formats). Versioned format namespaces (`{MAJOR}.{MINOR}`) with upgrade rules are mandatory in the application-formats process (https://earthstar-project.org/community/application-formats). Failure mode: collisions when two apps pick the same prefix, and no enforcement — conventions only; apps MUST assume arbitrary subsets of docs may be missing (https://earthstar-project.org/specs/data-spec-es5).

Cross-reference story. References live in the data (paths and text content), resolved by convention, not by the protocol. Identity profiles live under `/about/` paths keyed by identity address (https://earthstar-project.org/specs/data-spec-es5). When a target changes: paths are mutable slots, so a newer document from an authorized writer silently replaces the old one (last-writer-per-author-per-path, newest timestamp wins; https://earthstar-project.org/specs/data-spec-es5). When a target is deleted: wipe = overwrite with empty text, but metadata (author, path, timestamp, signatures) remains (https://earthstar-project.org/docs/how-it-works); peers that never sync the wipe keep the old doc. No backlinks, no cascade.

Onboarding / first-sync cost. Shares are undiscoverable by design (zero-knowledge-style sync handshake hides share membership; users exchange share addresses out of band) (https://earthstar-project.org/docs/how-it-works). First sync = learn the share address (+ secret for write), find a peer/server holding a replica, then full-share sync (es.5 syncs everything in the share; partial sync was future work) (https://earthstar-project.org/docs/future). Pub/servers reduce the simultaneity burden but full-feed-per-follow cost remains within a share. Share-secret leak is unrecoverable: no member removal; the documented remedy is a new share and migrate (https://earthstar-project.org/docs/how-it-works).

Link/reply as data. Application formats DO model social content as data (chat messages, wiki pages, about/profile docs), but reply/thread structure is app-level path convention, not a protocol tangle: documents are independent (explicitly "don't form a chain or feed or refer to each other (e.g. no Merkle backlinks)") (https://earthstar-project.org/specs/data-spec-es5). That bought app authors a simple key-value mental model ("data as files in a folder" per the making-an-app tutorial) at the cost of every app re-solving threading, moderation, and conflict display itself.

Deletion / pruning story. Two generations: es.5 = overwrite-with-empty plus ephemeral `deleteAfter` docs that replicas must actually delete (hourly sweep, no tombstone left) (https://earthstar-project.org/specs/data-spec-es5); the roadmap promised true prefix deletion (write at a prefix to delete the whole subtree, leaving one doc) carried forward into Willow (https://earthstar-project.org/docs/future). Known hard lesson, stated in the future doc: leaked share keys permanently compromise a share; and wipe-leaves-metadata was deemed privacy-insufficient, motivating prefix deletion (https://earthstar-project.org/docs/future).

What Willow kept vs dropped. Kept: subspaces≈shares-as-personal-universes, paths, multiwriter, offline-first, replica servers, app-format-by-convention. Dropped/changed: Earthstar's share-secret = write-access model became Meadowcap capabilities (delegable, restrictable by area/time; https://willowprotocol.org/specs/meadowcap/index.html); full-share sync became partial/area sync with resource budgets; wipe-leaves-metadata became prefix pruning with traceless removal (https://willowprotocol.org/more/willow_compared).

## 3. Weird / Leaf — the live third-party-app shape on Willow-family data

Model. Leaf is an experimental peer-to-peer federation protocol on Willow, built to back Weird (a local-first personal-web CMS: "WordPress + Notion editing + Linktree simplicity" per https://github.com/muni-town/weird). All user data lives in personal subspaces (like files with hierarchical paths; entities carry schema-typed components, Entity-Component-System style, with immutable content-hashed schema IDs) (https://blog.muni.town/leaf-atproto-activitypub). Weird usernames are domains resolving via DNS to (subspace ID, data nodes); subspaces hold a handle-validation record cross-checking DNS ↔ subspace (https://blog.muni.town/capabilities-and-identity-with-leaf).

Composition unit. The personal subspace is the composition unit (analogous to an ATProto PDS), with Leaf-level replication so the whole dataset can live on the user's own devices and sync offline-first (https://blog.muni.town/leaf-atproto-activitypub). Cross-app composition is via shared schemas and permissions: subspaces expose inboxes (world-writable paths that don't allow overwriting others' messages) enabling ActivityPub-like patterns without tying data to an instance (https://blog.muni.town/leaf-atproto-activitypub). Federation can grow relays/app-views ATProto-style or instance-hosts ActivityPub-style on top (https://blog.muni.town/leaf-atproto-activitypub). Mostly design + early implementation as of the write-ups (Nov 2024).

Cross-reference story. References span three layers: DNS handle → subspace (discovery/root of trust), contact-book entries caching handle/subspace/display-name/avatar per peer, and content links between subspaces (https://blog.muni.town/capabilities-and-identity-with-leaf). Breakage is handled socially/technically: handle change = update DNS + validation record, contacts re-verify automatically; key loss = recovery via server-held copy, new subspace, contacts choose trust-domain vs trust-subspace out-of-band; domain loss = warning until handle re-validated; key theft = new subspace + per-contact "distrust old key after date" cutoff (four scenarios worked through in https://blog.muni.town/capabilities-and-identity-with-leaf). This is the most explicit broken-reference playbook of the four systems — and it pushes the decision to the user contact book, not the protocol.

Onboarding / first-sync cost. New-device onboarding is "replicate my subspace" (full personal dataset, realtime when online). New-contact onboarding is DNS resolve + fetch subspace from listed data nodes (https://blog.muni.town/capabilities-and-identity-with-leaf); pkarr/Mainline-DHT resolution is the sketched DNS-free path, trading away human-readable global handles (https://blog.muni.town/capabilities-and-identity-with-leaf). Optional FROST 2-of-3 threshold keys (server + laptop + phone) for recovery/2FA, with the caveat that initial server-generated keys require trusting the server to delete the master (https://blog.muni.town/capabilities-and-identity-with-leaf).

Link/reply as data. Entities with schema components make posts, follows, and mentions first-class typed data (ECS middle ground between RDF and ATProto Lexicons) (https://blog.muni.town/leaf-atproto-activitypub). Capabilities (Meadowcap + FROST co-signing server for revocable online-only caps vs expiring local-first caps) gate who may write where, including inbox paths (https://blog.muni.town/capabilities-and-identity-with-leaf). Bought: fine-grained sharing/private subspaces with E2E-capable channels; Cost: revocation needs online co-signer (called out as unsolved p2p-wide in the post).

Deletion / pruning story. Inherits Willow deletion (overwrite + prefix pruning). Distinct contribution: per-contact trust cutoffs ("don't trust old key after date X") as a social deletion/retraction tool after key theft (https://blog.muni.town/capabilities-and-identity-with-leaf). Rest-revocation gap acknowledged: base Meadowcap caps are non-revocable, expiry-only; FROST co-signing closes it only while online (https://blog.muni.town/capabilities-and-identity-with-leaf). E2E at-rest encryption still open work at time of writing (https://blog.muni.town/capabilities-and-identity-with-leaf).

What it proves. A third-party app model on Willow-family data is expressible (personal subspace + schemas + inboxes + contact books), and identity/key/handle rotation can be designed for — but every hard problem (revocation, discovery without DNS, E2E) is pushed to servers, contact-book UX, or future work. Production-shape, not production-hardened.

## 4. SSB tangles + post-mortem — what one-graph-many-apps proved

Model. SSB: per-identity append-only signed feeds (sigchains) gossiped peer-to-peer; identity = Ed25519 key, feed = its log; replication = follow (fetch all messages newer than known) plus pubs/rooms and EBT vector clocks (https://ssbc.github.io/scuttlebutt-protocol-guide). Threading (tangles): reply messages embed `root` + `previous` references forming a cross-feed DAG layered over the per-feed chains — proposed natively in ssb2 discussion (tangle keyed by root, previous-arrays per tip; verification = every hash in previous must be locally known) (https://github.com/ssbc/ssb2-discussion-forum/issues/20) and shipped in metafeed announcements as `tangles: { name: { root, previous } }` conforming to the tangles spec (https://ssbc.github.io/scuttlebutt-protocol-guide). The ICN'19 analysis formalized these as "tangles" built by explicitly referencing others' messages (https://conferences.sigcomm.org/acm-icn/2019/proceedings/icn19-19.pdf).

Composition unit. Two units, mismatched: the feed (single-writer log = unit of replication/identity) and the tangle/thread (multi-writer DAG = unit of conversation). Every app (Patchwork, Manyverse, Oasis) read the SAME global feed-graph, filtering by message `type` — one-graph-many-apps for real (https://ssbc.github.io/scuttlebutt-protocol-guide, message `type` field + app filtering). Sharing across the unit worked socially (follow = replicate whole feed) but failed granularly: you could not follow a thread without replicating whole feeds, and could not partially replicate a feed (partial replication only arrived with metafeeds/bendy-butt, https://ssbc.github.io/scuttlebutt-protocol-guide).

Cross-reference story. References are content hashes in message bodies (`%...sha256` for messages, `@...` for feeds, `&...` for blobs) (https://www.miguelmota.com/blog/getting-started-with-secure-scuttlebutt-ssb? via https://medium.com/@miguelmota/getting-started-with-secure-scuttlebutt-ssb-6d80e5be5db4 — canonical symbol table; also https://ssbc.github.io/scuttlebutt-protocol-guide). Threads ARE data (root/previous links inside signed content), so the reply graph survives independent of any server. What breaks: nothing at the link level (hashes are immutable), but EVERYTHING at the liveness level — unfollowed, pruned, or never-replicated messages leave dangling references; tombstoning a feed for partial replication was a metafeed-era retrofit (https://ssbc.github.io/scuttlebutt-protocol-guide). Deleting or editing history forks the chain and stalls sync (next section).

Onboarding / first-sync cost. Brutal and well documented: new users needed an invite/pub to find anyone (out-of-band invite codes redeemable for a follow-back) (https://ssbc.github.io/scuttlebutt-protocol-guide); then two-hop "replicate everything from everyone you follow" pulled entire feed histories including blobs — gigabytes on mobile, hours on first sync. Manyverse's whole arc (Bluetooth replication, room servers, a from-scratch 5x-faster DB) was paying down this cost (https://www.manyver.se/blog/2024-04-05). Single-device identity compounded it: lose `~/.ssb/secret`, lose your feed; new key = new person, re-follow everyone (https://ssbc.github.io/scuttlebutt-protocol-guide: "If a user loses their secret key... they will need to generate a new identity").

Link/reply as data. YES — the strongest case of the four: root/previous references are signed content, so threads, likes, about-messages, and follows are all queryable data any app can render. Bought: genuine multi-app interop on one graph (all clients read the same types), offline-first threads, content-addressed permanence. Cost: the reply graph is append-only forever — no edit, no delete, no moderation primitive; blocking is local "free listening," not removal (https://srcco.de/posts/secure-scuttlebutt-ssb.html).

Deletion / pruning story. The hard lesson, stated bluntly by primary-adjacent critics and conceded by the ecosystem: append-only = cannot delete or modify history without forking your chain and breaking convergence (protocol guide: "append-only means you cannot delete an existing message, or change your history... enforced by a per-feed blockchain... entire network converges on the same state," https://ssbc.github.io/ssb-db; ctrl.blog: any modification creates a new chain, old stays equally valid → conflicts and stalemate, https://www.ctrl.blog/entry/append-only-social). Social graphs are mutable (relationships end, regretted posts, storage limits) but the log is not — the prescribed escape is minting a new identity (https://www.ctrl.blog/entry/append-only-social). Willow's designers cite exactly this as motivation: hash-chain verification precludes multi-device concurrency and makes edit/delete punishing; Willow drops completeness proofs to allow traceless removal (https://willowprotocol.org/more/willow_compared).

Post-mortem ledger (decline). No single canonical post-mortem exists; the closest primary materials are Staltz's farewell (mission drift, not a technical post-mortem: social graphs as attention-routers lost interest for him; handoff to Jacob/Mix; https://www.manyver.se/blog/2024-04-05) and the structural critiques above. Attributable decline factors from primary sources: (a) all-or-nothing follows → storage/bandwidth blowup on mobile; (b) single-device keys → no recovery story; (c) append-only → no deletion/moderation primitive, chilling mainstream adoption; (d) invite/pub bootstrap → capacity-limited onboarding. PPPPP (Staltz's successor effort, tangle-goals/conductor/hub repos) implicitly concedes the feed-unit by moving to goal-directed tangles — but PPPPP material is prototype-grade, so I mark protocol-lesson claims from it unanswerable-from-sources.

## What this proves or disproves for the ID graph layer

1. Whole-site-as-unit (Sneakerweb) proves key-addressed publishing needs no servers or DNS — but disproves that hyperlinks alone compose apps: no shared state, no queries, no live interaction (https://sneakerweb.org/spec).
2. Share-as-unit with path-prefix app formats (Earthstar) proves small-group multi-app data reuse works with nothing but naming conventions — but disproves convention-only scaling: collisions, missing-subset assumptions, and unscoped full-share sync are inherent (https://earthstar-project.org/community/application-formats, https://earthstar-project.org/docs/future).
3. Personal-subspace-as-unit with schemas + inboxes (Leaf/Weird) proves the ATProto/ActivityPub patterns re-emerge on Willow data with stronger local-first properties — but disproves free revocation and DNS-free discovery: both need online co-signers or out-of-band trust (https://blog.muni.town/capabilities-and-identity-with-leaf).
4. Feed-as-unit with tangle-as-thread (SSB) proves one-graph-many-apps interop is real when replies/links are signed data — but disproves append-only-forever as a social substrate: no delete, all-or-nothing replication, and single-device identity sank mainstream onboarding (https://www.ctrl.blog/entry/append-only-social, https://ssbc.github.io/ssb-db, https://www.manyver.se/blog/2024-04-05).
5. For D3's verb-object model: the systems that made links/replies DATA (SSB tangles, Leaf entities, Earthstar app-format docs) all got multi-app rendering for free; the system that left links as content strings (Sneakerweb HTML) got zero cross-app behavior — citable direction: model verbs/edges as typed data, not markup (https://github.com/ssbc/ssb2-discussion-forum/issues/20, https://blog.muni.town/leaf-atproto-activitypub, https://earthstar-project.org/community/application-formats).
6. Deletion must be a first-class layer primitive (prefix pruning / trust cutoffs), not a client convention: every system that left it to clients (SSB forks, Earthstar wipe-leaves-metadata, Sneakerweb re-export) produced either stalemates or residue (https://willowprotocol.org/more/willow_compared, https://earthstar-project.org/docs/future).
7. Onboarding cost dominates adoption more than cryptography: invites+pubs (SSB), share-address exchange (Earthstar), physical media (Sneakerweb), DNS+contact-book verification (Leaf) are all out-of-band bottlenecks no sync protocol removes — budget D3 design effort for first-sync UX, not just sync math (sources per system above).
8. Possible tension with #13779 (flagged, not posted): if #13779 positions content-addressed links as sufficient for cross-app composition, SSB supports it but Earthstar's "independent documents, no backlinks" + Sneakerweb's string-links show addressing alone does not yield shared semantics — conventions/schemas/tangles did that work. Confirm against #13779 ground before citing.

## Open questions / unanswerable from sources

- Sneakerweb live-sync cost curve: no published measurements of .snk sizes, import times, or multi-site collection scaling. Gap: no benchmarks found in primary sources.
- Sneakerweb deletion propagation: spec silent on whether import merges or replaces; cooperative-deletion claim above is inference from drop-format + Willow pruning, not a tested behavior.
- Earthstar partial sync + prefix deletion shipped status: roadmap promised them via Willow (future doc, ~2023 vintage); v11-beta/Willow-Earthstar spec not surveyed — do not cite as shipped.
- Weird/Leaf production status: write-ups label design work-in-progress/non-functional (identity, E2E, co-signing protocol unstandardized). Treat all Leaf composition claims as design evidence, not deployment evidence.
- SSB canonical decline post-mortem: none found; Staltz farewell is personal/mission framing, ctrl.blog is external critique, Willow-comparison is a competitor's framing. Two-hop-replicate-everything and brutal-first-sync are well attested technically but I found no primary SSB-authored "we declined because X" document.
- FROST/Meadowcap revocation semantics for shared inboxes under partition: unanswerable — no spec text found.
