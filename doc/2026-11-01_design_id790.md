# Design: F13.8 multi-server and multi-client topology

- Date: 2026-11-01
- Status: **decision-ready**; one journal-scope question for Drew is called out in §7, with a safe default recommendation.
- Issue: [#790 — F13.8 multi-server, multi-client topology; client-only mode always supported](https://github.com/developing-today/code/issues/790).
- Baseline: `origin/main` at `33aefa7f7` after fast-forwarding this design branch; this record changes no implementation code.

## 1. Decision

Add an explicit client-side session coordinator that lets one `id` process hold live sessions to multiple worlds and multiple server endpoints at once. Keep `WorldClient` as the transport/session primitive: a coordinator reuses a connection for worlds at one endpoint and owns a separate connection for each other endpoint. Give every opened session an independent handle and route its requests, capabilities, replies, and shutdown to that handle—not to a process-global “current world.”

Keep the client-only path as the default and only behavior of client commands. A client operation must never start a world host; hosting remains an explicit `id serve` action, with SSH world serving opt-in. Preserve existing sequential APIs and one-shot CLI joins. Joining itself does not issue a committed user event; a first/last `players` presence transition can separately issue a system event, addressed explicitly in §7 rather than silently removed.

## 2. Context and current state

Issue #790 asks for clients to connect to several worlds and servers, to coexist with other clients, and for a client-only mode to remain available. Its exit criteria are two live world sessions from one client, a documented/tested client-only boundary that adds no authority, and an unchanged world journal when a second client joins. The issue names the Phase 13 shell contract as its prerequisite; the Phase 13 plan gives the same F13.8 exit criteria and keeps SSH servers rare and opt-in (`#790`; `.opencode/plans/phase-13-client-shells.md:95-105`).

**The client-only boundary is already implemented on this baseline.** The CLI documents that `serve` is the only command that hosts a world and that world serving over SSH is opt-in (`pkgs/id/src/cli.rs:211-220`). The `world` command documentation states that client commands do not host or grant authority; it also documents the local-listener exceptions (`ssh-tunnel` and `mirror`) and says neither grants world authority (`pkgs/id/src/cli.rs:1096-1115`). The README makes the same distinction (`pkgs/id/README.md:110-127`). A parser regression test pins that world-client arguments do not dispatch `serve`, that explicit `id serve` does, and that there is deliberately no `--client-only` flag (`pkgs/id/src/cli.rs:4251-4286`). This satisfies the client-only criterion without inventing a redundant mode flag.

**The server already serves many worlds, but this is not a multi-server client coordinator.** `WorldHub` is a registry that leases named worlds to sessions (`pkgs/id/src/world_hub.rs:211-239,464-483`); its default limits are 256 open worlds and 1,024 sessions (`pkgs/id/src/world_hub.rs:82-102`). The protocol caps one transport connection at 16 sessions (`pkgs/id/src/world_net.rs:47-48,73-95`). These are server-side bounds, not a reason for a client to treat one connection as spanning different endpoints.

`WorldClient::connect` dials one endpoint and opens a stream; `open_session` opens another stream on that same connection and binds the returned handle to the requested world (`pkgs/id/src/world_net.rs:183-216`). The test `one_connection_reaches_many_worlds_and_many_clients_share_a_host` visits `alpha`, `beta`, and `gamma` in sequence; it does not keep two world sessions live together (`pkgs/id/src/world_net.rs:1782-1833`). The current `id world join` path connects, pumps one stream, then closes that connection (`pkgs/id/src/commands/world.rs:720-749`). Thus the requested concurrent coordinator and multi-endpoint routing are not demonstrated by these paths.

**Session identity must be resolved here, not shared implicitly.** F13.7 explicitly deferred multi-session identity to F13.8 and recommended that client-provider requests continue to go only to the session that opened them until F13.8 defines the rule (`doc/2026-10-25T05-37-57Z_design_client_capability_providers/2026-10-25T05-37-57Z_design_client_capability_providers.md:455-458`). This design settles it as per-session routing: an opaque session handle owns its endpoint, stream, world, and capability context. A session on another shell or to another world must not receive a request merely because it belongs to the same process or participant.

**Journal acceptance has a real edge case.** A successful join reads the participant and snapshot, sends the view, and then registers session presence (`pkgs/id/src/world_session/mod.rs:1846-1928`). Presence is refcounted per participant; only a first/last transition emits a `players` event, and only when that capability is granted and subscribed (`pkgs/id/src/world/actor.rs:804-854`). Host-originated events are persisted as `JournalEntry::System` (`pkgs/id/src/world/actor.rs:401-439`); participant input is persisted as `JournalEntry::Committed` (`pkgs/id/src/world/actor.rs:1132-1155`). Therefore, a second session for an already-present participant is journal-neutral, while a distinct participant can intentionally cause a durable presence event. The existing contract test already distinguishes ephemeral/query/control frames from journaled events, but does not resolve this join/presence acceptance case (`pkgs/id/src/world_session/contract_tests.rs:212-247`).

## 3. Viable options

| Option | Trade-offs | Decision |
| --- | --- | --- |
| Keep only one-shot joins. | Lowest complexity and preserves the existing safe CLI path, but cannot meet the two-simultaneous-session exit criterion. | Reject as the complete F13.8 solution; retain one-shot joins for compatibility. |
| Open an unrelated client connection for every world session. | Makes distinct endpoints possible with existing primitives, but duplicates connections for worlds on one server and leaves session ownership/routing implicit at call sites. | Reject as the coordinator design. |
| Add an endpoint-keyed client session coordinator over `WorldClient`. | Explicitly owns connections per server and live stream handles per session; reuses one connection for worlds at one endpoint; preserves the existing capability-bearing join path. | **Recommend.** It meets the topology requirement with the smallest change to transport, journal, and guest ABI. |
| Start a local server automatically when a client opens another world. | Could make local worlds appear reachable, but silently adds hosting/resource authority and contradicts the client-only contract. | Reject. Only explicit `id serve` may host a world. |

## 4. Recommendation and invariants

1. **Endpoint-scoped connections; session-scoped streams.** Keep one `WorldClient` connection per explicit server endpoint. A session handle includes enough identity to distinguish endpoint, world, and multiple sessions to the same world; do not key live state by world name alone. Different endpoints always use different connections.
2. **Origin-session routing.** Every operation and client-provider request/reply stays on the session handle that originated it. Do not add a global active-session fallback. The server still checks the existing per-world capability (`pkgs/id/src/world_session/mod.rs:1857-1863`); node connectivity or endpoint membership is never authority.
3. **No ambient hosting.** Opening, retaining, or closing client sessions cannot start a server or grant authority. Preserve the documented local-listener exceptions: `world ssh-tunnel` and `world mirror` do not host a world or grant its authority (`pkgs/id/src/cli.rs:1103-1115`).
4. **Journal semantics stay explicit.** Session setup and ephemeral frames do not create committed user events. Preserve existing `players` system-event semantics unless Drew chooses the stricter behavior in §7; do not describe all distinct-participant joins as journal-neutral while that event is enabled.
5. **Compatibility and bounds.** Keep current sequential `open_session` and one-shot CLI behavior. The coordinator surfaces existing host/connection refusal and cleanup; it must not bypass the 16-stream connection bound or the `WorldHub` limits (`pkgs/id/src/world_net.rs:47-95`; `pkgs/id/src/world_hub.rs:82-102`).

## 5. Implementation acceptance criteria

- One process holds two world sessions open simultaneously against one server; operations on each continue to reach the correct world after both are opened.
- One process holds sessions open simultaneously against two distinct server endpoints; each endpoint has an independent transport connection, and same-named worlds on different endpoints cannot collide.
- A request/reply or provider request associated with one session is never delivered through another session, even for the same participant. A capability from one world/session is not accepted as authority for another.
- Joining does not append a `Committed` user event. Add journal-before/after assertions for the scenarios agreed in §7, and separately pin intentional `players` system-event behavior when enabled.
- The client-only help/README/parser regression remains green: client operations do not dispatch server startup, and only explicit `id serve` hosts worlds. Do not add `--client-only` unless a future command actually has a hosting mode to disable.
- Existing sequential `open_session` and one-shot `id world join` behavior remains supported. Session closure releases its stream/lease and does not leave the coordinator's endpoint or session registry stale.
- Resource limits and errors remain visible: a full connection or hub refuses a session rather than causing implicit redial/hosting or cross-endpoint fallback.

## 6. Phased implementation plan

Each step is scoped so it can be reviewed and merged separately; steps 2 and 3 are ordered extensions, not parallel changes to one public interface.

0. **Client-only boundary — complete.** The independent documentation and parse-level regression slice landed in PR [#3862](https://github.com/developing-today/code/pull/3862) for issue #3846. Treat it as a guardrail; do not redo it or introduce a mode flag.
1. **Journal characterization — independently mergeable test slice.** Before changing coordinator behavior, add a black-box journal comparison for a second session with no `players` presence transition, plus a focused test that records the existing first/last `players` system event when that capability is active. Resolve §7's interpretation before calling the broad issue criterion complete.
2. **Concurrent worlds on one endpoint — independently mergeable feature slice.** Add the client coordinator and opaque session handles over one endpoint's `WorldClient`; prove two sessions remain live together, route to their own worlds/capabilities, and close cleanly. Keep the current one-shot CLI unchanged.
3. **Concurrent endpoints — independently mergeable extension.** Extend the coordinator to own one connection per explicit endpoint and route sessions by handle. Add an integration test with two server endpoints live at once, including same-named worlds and a negative cross-endpoint/capability-routing assertion. Re-run the connection and hub bound tests.

The current F13.8 implementation packet is issue [#3845](https://github.com/developing-today/code/issues/3845), with draft PR [#3896](https://github.com/developing-today/code/pull/3896); the already-merged #3846/#3862 work covers step 0. This record clarifies the acceptance boundary and can be used to split the implementation if the current packet grows beyond its coordinator scope.

## 7. One question for Drew

**Does “a world's journal is unchanged by a second client joining it” include an intentional `players` presence event for a newly present participant?**

- **Option A — strict neutrality:** no second-client join may add any journal entry, including `JournalEntry::System` presence events. This honors the literal acceptance criterion but requires changing or relocating the existing durable presence behavior.
- **Option B — session-join neutrality (recommended):** joining itself adds no journal entry; keep the current `players` event when a new participant's first/last presence transition is subscribed and granted. Test neutrality with a second session for an already-present participant or with no active `players` subscription, and test the presence event separately. This preserves existing journal/replay behavior while making the test's setup precise.

**Recommendation: Option B.** It preserves existing event semantics and separates an intentional participant-state event from transport/session setup. If Drew selects A, treat that as an explicit scope expansion before implementation; do not silently make F13.8 appear complete by choosing a narrower test setup.

No Drew decision is needed on the client-only flag: the current CLI and README explicitly document that no client command has a hosting mode, and #3862 pins that boundary in a regression test (`pkgs/id/src/cli.rs:1103-1115,4251-4286`; `pkgs/id/README.md:110-127`).

## Non-goals

- No automatic local world server, new world authority, journal format change, or guest ABI change.
- No redesign of the current `id world join` one-shot command or addition of a new multi-session CLI surface unless a consumer requires one.
- No relaxation of per-world capability checks, connection/session limits, or SSH opt-in behavior.
