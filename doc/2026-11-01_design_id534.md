# Design: Run Phase 12 deliverables through the research workflow

- Date: 2026-11-01
- Status: **recommended** — workflow and tracker policy; no implementation changes
- Issue: [#534](https://github.com/developing-today/code/issues/534)

## Decision

How should the 11 design items tracked by #534 be taken through research and
design without duplicating implementation issues, blocking already-ready work,
or treating code progress as a substitute for the committed design evidence the
issue requires?

**Recommendation:** keep #534 as the umbrella ledger and run one shared Phase 12
research package with one concept per listed D1 item. Keep each concept's
research/design record and implementation handoff independently reviewable and
mergeable. Reconcile each concept against the current code and the newest issue
comments before dispatch; reuse the existing F12 implementation issues instead
of filing duplicates. Design work may proceed ahead of its implementation, but
the stated prerequisite remains a gate to implementation. Tick a D1 checkbox
only after its committed design (or research package for D1-026) and linked
implementation issue are both present. Do not close #534 as part of this work.

## Options and trade-offs

### A. One umbrella design document for all Phase 12 items

This minimizes workflow overhead and gives a single overview. It also mixes
items with different evidence, prerequisites, security properties, and size
(M through XL in the issue). The resulting document would be hard to review or
implement incrementally, and a single completion signal would conceal which
designs are ready. It conflicts with #534's per-item acceptance tracking.

### B. An independent research package for every D1 item

This maximizes isolation and lets each item choose its own research scope. It
duplicates the common Phase 12 context, makes cross-item dependencies harder to
keep consistent, and multiplies package-level setup and tracking for work that
the workflow already supports as separate concepts.

### C. One Phase 12 package, one concept and independently mergeable design per D1 item — recommended

This preserves shared context and gives each D1 item its own research questions,
evidence, decisions, design record, and implementation handoff. The workflow
already supports one agent per concept and separate design records, so a
package-wide stage does not require one monolithic design PR. Dependencies
control implementation order, not whether independent research can start.
The cost is package coordination and careful ownership of the package's shared
index files; the workflow's one-writer-per-wide-file rule addresses that cost.

## Recommendation and rationale

Use option C, with two adjustments for the issue's evolved state:

1. Start with an evidence reconciliation against the current `pkgs/id` sources
   and the dated comments, not the issue body's old “not started” status text.
   F12.1's manifest parser, planner and apply/diff path exist, but roles and
   invites are absent from its manifest model and apply steps; the separate
   apply calls can partially succeed before an error. F12.3 has role bits and
   journal records, but the wire install path still requires the admin token.
   Preserve that work and design the remaining delta. Code alone does not
   satisfy the committed-artifact acceptance criterion.
2. Reuse the existing F12 implementation issues listed above. Their existence
   satisfies the “linked issue” part only after each concept's design is
   committed and the link is verified; do not create duplicate implementation
   issues.
3. Follow the newest queue decision: prerequisite path first, Phase 12 second;
   within the Phase 12 work, maintain the plan's high-return emphasis on F12.1,
   F12.4, and F12.7 and honor each recorded gate. Since F12.1 has progressed,
   advance the F12.1/F12.3 delta records and F12.4/F12.7 foundations; F12.6 can
   be designed in parallel even while its F11.7 prerequisite is being resolved.
   Do not implement F12.5 until the D1-023/D1-024 order question is answered.
4. Let each concept's design PR merge independently. Keep #534 open until each
   listed D1 item has both its committed artifact and an implementation issue;
   update only the corresponding tracker checkboxes when that evidence exists.

This recommendation uses the research workflow for decomposition and
traceability without making the completion of all 11 designs a gate for an
already-ready concept or implementation. It also respects the explicit Phase 12
authority rule: no new guest access to files, network, or processes except via a
named, ceilinged provider, with audit and refusal coverage for the new providers.

## Invariants and acceptance criteria

### Invariants

- #534 remains the umbrella tracker; this design neither closes it nor changes
  implementation code.
- The D1 inventory is exactly the 11 items in the issue body. Other F12 work
  stays with its existing issues unless a later recorded decision changes the
  scope.
- A D1 checkbox means both **committed design/research artifact** and **linked
  implementation issue**. Plan references, code already landed, or an open PR
  alone do not satisfy it.
- Every concept cites current `pkgs/id` evidence and distinguishes observed
  behavior from proposed behavior. When tracker prose conflicts with later
  comments or current code, record the discrepancy and prefer the newer
  decision; never silently erase earlier context.
- Design can run ahead of implementation, but implementation must honor the
  item prerequisites and Phase 11 gates recorded by #534 and the Phase 12 plan.
- Dispatch only concepts ready under their hard `requires` edges and within the
  research workflow's configured writer cap; keep soft ordering suggestions
  distinct from blockers.
- New guest capabilities remain named, bounded, ceilinged, auditable, and
  explicitly refused outside their grants. Existing provenance is not a trust
  attestation. Existing journal compatibility rules remain in force.
- Each concept's record and handoff is reviewable and mergeable without waiting
  for unrelated concepts; shared package indexes have a single writer.
