## 1. The question

When the serverless edition's store is Turso/libSQL, the journal
appears to have two replication systems available: libSQL's own
(embedded replicas syncing from a primary; primary replication
between `sqld` instances) and #806's signed stream (single writer,
ordered signed batches of exact journal-entry bytes, replicas
verify-then-persist and serve spectators offline). Two systems
moving the same data is the hazard the parent named. This record
settles which layer owns what, and what implementation must never
do.

Not this record's question: D1 vs Turso vs both (#5681, decided
with roles); the #5863 contract surface; backend choice and
migration mechanics (#5867). Also not this seam: the read-only
foreign-data adapter `pkgs/id/src/foreign_libsql.rs` **[landed]**
(#7577, decision #5806) speaks the libSQL HTTP pipeline to
*foreign* stores under grant filtering. It is evidence the HTTP
pipeline is the house way to reach libSQL from `id`, but the
journal store is native data under the journal's own trust rules,
not foreign data — the two must not be merged.

## 2. Decision: one replication of record, one materialisation accelerator

1. **The signed stream is the only journal replication.** Every
   movement of journal data across a trust boundary — another
   node, another deployment, another backend, a spectator replica
   that may outlive the writer — is #806 replication: exact
   `JournalEntry` bytes, cursor `(entry ordinal, rolling digest)`,
   signature verification before anything becomes visible.
2. **libSQL replication is a materialisation accelerator inside
   one deployment.** Within a single Turso-backed deployment,
   libSQL may replicate the *materialised tables* (the journal
   table of §4 and its projections) from the deployment's primary
   to embedded replicas on that deployment's own endpoints, to
   make local reads fast and offline-tolerant. It moves rows
   inside one trust domain; it confers no journal authority.
3. **An embedded replica is a cache with a freshness bound, not a
   journal replica.** What it may serve is bounded by its last
   completed sync, and that bound must be expressible as a journal
   cursor (§5.3) before any of its content is presented as world
   state. Anything it holds past the last *verified* cursor is
   unverified materialisation, treated exactly like a #806 replica
   that has received bytes it has not verified yet: present on
   disk, invisible to readers.
4. **Writes go to the primary only, and the writer is the journal
   writer.** The single writer of #806 appends through the
   deployment primary (§4). Embedded replicas never accept a
   journal write locally, and libSQL write-forwarding from a
   replica is not used for journal appends — an append is only
   durable when the writer's own append path (§4.2) has the
   primary's acknowledgement and the entry's digest is chained.

## 3. Why the layers must not be swapped

- **Verification does not ride libSQL replication [documented].**
  Frame sync replicates whatever the primary holds; it carries no
  signatures, no cursor chain, no tamper evidence. A replica that
  trusted frame sync as journal replication would accept a
  tampered or forked primary's rows silently — #806 acceptance
  ("a tampered stream is refused") would fail by construction.
- **Fork behaviour differs.** If a primary is restored from backup
  or a failover promotes a stale node, libSQL replication
  converges replicas to the primary's current state, including
  *backwards*. The journal chain is append-only and digest-linked:
  convergence backwards is a fork the journal layer must detect
  (head digest mismatch at a known ordinal), never follow.
  Detection lives at the journal layer (§5.4); libSQL cannot see
  it.
- **Ordering guarantees differ.** The journal's order is the
  ordinal chain the writer assigned. libSQL frame order is an
  internal physical order; using it as journal order would couple
  the journal's meaning to one store's internals and break the
  #5869 exit story (export = journal + snapshot, replayable into
  any backend).
- **Offline behaviour is the one place they agree — use it.**
  #806 replicas serve spectators while the writer is offline
  **[landed design]**; embedded replicas serve local reads while
  disconnected **[documented]**. The composition keeps both: the
  endpoint serves from its materialisation, stamped with the last
  verified cursor and sync time (#806's staleness metadata), and
  grants nothing beyond spectator scope while disconnected
  (#806's offline-admission rule is unchanged).

## 4. The journal in libSQL: mapping

### 4.1 Tables (spike-verified shape, §6.1)

```sql
CREATE TABLE journal_entry (
  world_id       TEXT    NOT NULL,
  ordinal        INTEGER NOT NULL,
  rolling_digest BLOB    NOT NULL,
  header_version INTEGER NOT NULL,
  entry_bytes    BLOB    NOT NULL,
  PRIMARY KEY (world_id, ordinal)
);
CREATE TABLE journal_head (
  world_id       TEXT PRIMARY KEY,
  head_ordinal   INTEGER NOT NULL,
  head_digest    BLOB    NOT NULL,
  header_version INTEGER NOT NULL
);
```

`entry_bytes` is the exact serialized `JournalEntry` (JSONL line
bytes, boundaries preserved) — the #806 payload rule applied to
storage: never a lossy projection. The `(world_id, ordinal)`
primary key makes a conflicting repeat at a known ordinal a
storage-level refusal, backing the journal layer's own check.

### 4.2 Append path

The writer appends one batch per transaction: insert the batch's
entries at their ordinals, then advance `journal_head` to the
batch's final `(ordinal, rolling_digest)` in the same transaction.
A reader that sees a head therefore sees every entry up to it —
the store-level mirror of #806's "a tail is visible only after its
complete signed batch verifies". Publication to the signed stream
still happens from the writer's journal, after the append is
durable, exactly as #806 orders it; the table is the serverless
edition's durable journal form (the JSONL `FileJournal` remains
the local edition's).

### 4.3 Snapshots, compaction, header bumps

#806: compaction or a header-version bump changes the chain base;
a replica off-chain receives a full signed reset snapshot. In the
table: a reset is a transaction that replaces the world's rows
with the snapshot's entries at their ordinals under the new
`header_version` and resets `journal_head`. Rows from two chain
bases never coexist for one world — `header_version` is part of
every read's predicate until the reset transaction commits.

### 4.4 Access path

`id` reaches Turso over the libSQL HTTP pipeline, as the foreign
adapter already does **[landed precedent]**, not via the native
libsql crate in the shipped graph: the `store_traits` guard that
keeps a SQLite-family dependency (and any log-sync wiring) out of
the native graph stays intact, and Workers has no native crate
option anyway. Embedded replicas are therefore a property of the
*deployment's* libSQL client tier (endpoint tooling, CLI,
spectator clients), not of the `id` binary's dependency graph —
one more reason their contents are a materialisation detail, not
journal truth.

## 5. Invariants implementation must hold

1. **One writer.** Only the journal writer appends; the primary
   is a store, not a writer. No code path appends from an embedded
   replica, a promoted replica, or a second primary.
2. **Verify before visible, at both layers.** Signed-stream
   batches follow #806 verification. Materialised rows are visible
   to world-state readers only up to a verified cursor (§2.3).
3. **Cursor honesty.** Every read surface that presents world
   state can report the verified `(ordinal, digest)` it reflects
   and when it was verified; an embedded replica's sync watermark
   is never presented as a verified cursor unless the rows up to
   it passed journal verification.
4. **Fork refusal.** If the primary's `journal_head` at a known
   ordinal carries a different digest than the verified chain —
   after a restore, failover, or tamper — the deployment refuses
   to serve or extend the journal and raises the #806 fork path;
   it never converges silently (§3).
5. **Byte fidelity.** `entry_bytes` round-trips exactly; restore
   from the table alone reproduces the writer's records through
   the existing replay path (the #806 replica acceptance, restated
   for the table form).
6. **Reset atomicity.** Snapshot/reset replacement is one
   transaction per world (§4.3); a crash mid-reset leaves either
   the old chain base or the new one, never a mixture.
7. **Exit stays open.** Export reads the journal from the table
   in ordinal order and emits the #5869 bundle; nothing in the
   libSQL mapping may exist only in libSQL-specific form (no
   triggers, no generated columns, no frame-level state in the
   journal's meaning).

## 6. Spike

### 6.1 Executed: the mapping against the engine [spike]

Executed 2026-11-10 on the fleet laptop against the SQLite
engine libSQL forks (the `turso` CLI's local shell is a
CGO-disabled stub and no `sqld` is installed — see §6.2; the
schema, constraints, and byte behaviour spiked here are the
shared SQLite core, and are claimed as exactly that, no more):

- The §4.1 schema creates and accepts the journal shape.
- Entries insert and read back in ordinal order; `entry_bytes`
  round-trips byte-exactly, including JSON entry bytes.
- A duplicate insert at an existing `(world_id, ordinal)` is
  refused by the primary key (`UNIQUE constraint failed`) — the
  conflicting-repeat refusal holds at the storage layer.
- The head-consistency check (`journal_head.head_ordinal` equals
  `MAX(ordinal)`) evaluates as a single query — the §5.4 fork
  check's cheap half.

### 6.2 Owed: embedded-replica sync behaviour [spike-owed]

Not executable in this environment: no `sqld` on the fleet
laptop, `turso dev` refuses to start without it, and the `turso`
shell binary is compiled `CGO_ENABLED=0` (its local shell is a
stub). Filed as follow-on spike
  [#8346](https://github.com/developing-today/code/issues/8346);
  its acceptance:

- Stand up `sqld` (or a Turso database) as primary; create the
  §4.1 tables; append a journal batch through the primary.
- Open an embedded replica from the libsql client; measure sync
  latency distribution for the batch to become readable, at rest
  and under append load.
- Disconnect the replica; confirm reads serve the last synced
  state and writes are not accepted locally; reconnect and
  confirm convergence to the primary's head.
- Restore the primary from an older backup (head moves
  backwards); record what the replica does on next sync — the
  §5.4 fork-refusal trigger must fire at the journal layer before
  any converged state is served.
- Record results on the follow-on issue and link them here; if
  measured sync behaviour contradicts §2.3's freshness model,
  this record is amended, not silently outlived.

## 7. Alternatives rejected

- **libSQL replication *as* the journal replication.** Rejected
  in §3: no signatures, no cursor chain, backwards convergence.
  This was the parent's named hazard; the answer is not "careful
  use", it is layer separation.
- **Embedded replica as writer failover.** Promoting a replica to
  writer on primary loss would create a second journal writer
  whose chain base the first writer never signed. Writer failover
  is a journal-layer decision (new chain base, signed reset,
  #806 lifecycle), after which libSQL re-materialises — never the
  reverse.
- **Native libsql crate for the journal store.** Rejected in
  §4.4: it fights the landed `store_traits` dependency guard and
  is unavailable on Workers; the HTTP pipeline is the established
  house path.
- **Journal as JSONL files inside the Turso deployment.**
  Keeping the file journal and treating Turso as a generic table
  store for projections only was considered; rejected because the
  serverless edition has no durable local file to fsync — the
  table *is* the durable form there (§4.2), while the file journal
  remains the local edition's form behind the same chain rules.
