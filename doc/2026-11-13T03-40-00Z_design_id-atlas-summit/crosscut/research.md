# Cross-cutting primitives and configuration research

Scope: #9110 (S0, S1.114–S1.120), #9111 (S7), and sequencing input for #9112. This is a focused evidence/options note, not a replacement for the ID store, hosted-edition, tenancy, content-plane, or Atlas designs. No external benchmark was run; performance claims below are hypotheses to measure, not results.

## Evidence and current boundary

- The proto assigns extensibility/conformance to #9110, modes/configuration to #9111, and refinement to #9112; it explicitly makes the signed-and-validated acceptance invariant non-configurable (proto note.md §§1, 3–5).
- #9082 specifies redb as existing native storage, Turso/libSQL as the hosted addition, and IndexedDB as evaluate-only; it leaves transaction/consistency semantics, authority, migration, and WASM open. Its amendment clarifies architecture extensibility is broad while implementation remains focused on these backends (issue snapshots in `../inventory-live/live-issues.json`).
- #9078 requires both Rust binaries and Cloudflare/Turso hosted services to be fully featured tier-1 systems, with deliberate divergence rather than a reduced port. The successor program additionally requires adapters for RustFS/NATS/tiered storage and says the first-party server is a peer, not a protocol exception (same issue snapshot).
- Existing code evidence is bounded: ID has an Iroh blob-store seam with persistent redb-backed and memory modes; event/world stores are separate seams. Iroh sync, payload signatures, tuple codecs, and Atlas backends are domain-specific, not proof of a universal store/transport/config contract (`baseline/v1-audit.md`; `baseline/seam-map.md`).
- The updated baseline resolves identity details: Iroh blob hashes are unkeyed BLAKE3 over exact bytes; event commitments are p2panda BLAKE3; signed artifacts use SHA-256 over `serde_json::to_vec(SignedBody)` and Ed25519 over those bytes, while code and function documentation disagree on the preimage recipe. World module IDs use Iroh BLAKE3. These typed profiles are not interchangeable. Atlas has `content_hash` schema/consumers but no checked-in production producer, so the specific producer contract is missing rather than a generally unknown hash algorithm (`baseline/v1-audit.md` §§1, 3).
- Cross-part binding: signed acceptance is not a single signature check—transport authentication, signature verification, semantic validation, signer authority, tenant/scope authorization, and replay handling are distinct applicable checks. A local producer signs before the same gate. Acknowledgment contradiction evidence is meaningful only for comparable signed statements about scope, time, authorization, and applicable retention/completeness obligations (`main.md` §§2, 4).

## Stable primitive surface: options

| Option                                   | Shape                                                                                                                                                                    | Benefits                                                                                                         | Costs / limits                                                                                                                                                  | Recommendation                               |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| A. One universal backend interface       | A single trait/API promises CRUD, transactions, watches, blob streams, and remote transport.                                                                             | Superficially simple consumer story.                                                                             | Lowest-common-denominator semantics; HTTP/IndexedDB cannot honestly promise native transaction/watch behavior; forces unrelated resources into one abstraction. | Reject.                                      |
| B. Capability-oriented resource ports    | Separate store, object/bucket, stream/log, and transport ports. Each declares a versioned capability set and semantic guarantees; callers request required capabilities. | Stable mechanism seams; backend limitations remain explicit; adding Postgres/NATS/custom connectors is additive. | More types and explicit negotiation; optional capability combinations need testing.                                                                             | Adopt.                                       |
| C. Backend-specific APIs behind a facade | Consumers use a facade but it exposes backend-specific escape hatches.                                                                                                   | Fast initial adoption; easy to use optimizations.                                                                | Leaks backend semantics into core and makes portability/conformance unverifiable.                                                                               | Keep only in adapters, never core contracts. |

**Port families (not one mega-trait):** `RecordStore` for key/value and bounded scans; `BlobStore` for immutable byte streams and content verification; `EventLog` for append/range/receipt semantics; `WorldStore` for world-specific state; `ObjectBucket` for opaque object put/get/list/delete and metadata; `MessageStream` for publish/subscribe/ack; `RequestTransport` for request/response and streaming RPC. The names are candidate stable conceptual seams; map each to existing ID subcrate ownership before implementation. A port declares `PortContractVersion`, required/optional capabilities, consistency/ordering, durability, transaction scope, idempotency token behavior, limits, and error taxonomy. Capability mismatch fails before side effects (`UnsupportedCapability`), never through silent weakening.

**Capability examples:** atomic batch within a declared scope; compare-and-swap; ordered append; range scan; snapshot/read timestamp; watch/change feed; durable acknowledgement; resumable byte stream; conditional object write; per-operation connection selection; idempotent request; cancellation. A backend reports `supported`, `unsupported`, or `conditional` with condition/limit. Do not equate “supported” with the same performance or transaction horizon.

“Tier-1” is product support and feature intent, not a false promise of identical backend internals. Both Rust-native and Cloudflare/Turso must implement the required product operations and validate the same semantic fixtures; when atomicity, durability, offline behavior, or limits differ, expose the difference and use protocols that preserve correctness (for example outbox/inbox plus idempotency), rather than hiding it as a degraded edition. Exactly-once across independent stores/transports is not promised.

## Hooks and callback system: options and contract

| Option                                                                         | Pros                                                           | Risks                                                                                      | Recommendation                            |
| ------------------------------------------------------------------------------ | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | ----------------------------------------- |
| Unordered mutable callbacks                                                    | Easy plugin registration.                                      | Nondeterministic order, hidden mutation, recursion, bypasses and partial commit ambiguity. | Reject.                                   |
| Ordered synchronous interceptors on every operation                            | Easy to reason about on one path.                              | I/O hooks block critical path and cannot model after-commit/outbox recovery.               | Use for pure validation/observation only. |
| Typed lifecycle hooks with immutable context, explicit phases and event outbox | Covers normal paths and recovery; deterministic and auditable. | More explicit API; delivery is at-least-once and consumers need idempotency.               | Adopt.                                    |

**Mandatory order:** fixed trusted normalization/signing (local producer only; pure deterministic code, no extension callback) → immutable envelope binding → signature/semantic/replay/authorization/tenant gate → `prepare` hooks → reauthorize against current policy revision at commit boundary → durable operation/outbox commit → `after_commit` delivery/retry. Every prepare hook sees validated immutable input and the validation result; it cannot mutate signed bytes, decision, authority, or tenant scope. It may emit a namespaced annotation for the current operation, not accepted persistent data. If enrichment must persist, construct a distinct derived object, sign it under its own authorized signer, and submit it through a new complete admission operation; a hook cannot make arbitrary bytes trusted. If policy is revoked while a hook runs, commit-time reauthorization rejects. If commit outcome is unknown, do not blindly replay: resolve by stable operation ID, reauthorize before any retry/new admission, and preserve unknown status until readback resolves it. Reentrant mutation into the same operation is rejected or queued as a new operation with a new idempotency key. Errors distinguish pre-commit veto, store failure/unknown outcome, and post-commit pending delivery.

This pipeline applies to accepted data/assertions (including local writes and federation payloads). A read request is not accepted data: local reads require authenticated caller and tenant/scope authorization; state-changing requests also require replay/idempotency handling. Federated query envelopes follow their protocol's signature/validation requirements. No unsigned input becomes accepted retained data merely because it came from a hook or local call.

## Mechanism vs behavior; configuration choices

Mechanism belongs in versioned primitives: signature verification and signer binding; validation and authorization gate stages; request/replay identity; transaction/outbox mechanics; ordering/ack protocol; bounded recursion/budget enforcement; capability negotiation. Behavior belongs in validated config: peer class, sync scope, mode, allowed links, prioritization weights, retention, tier placement, retry budgets within hard ceilings, and optional feature enablement. A config may tighten a mechanism's accepted set but never disable signature validation, tenant scope, replay checks, or acceptance-state rules. Local producers sign before admission and then traverse the same validation gate.

Configuration is versioned, schema-validated, canonicalized, and resolved with precedence: immutable primitive invariants + hard protocol/resource ceilings → deployment behavioral defaults → named mode behavioral defaults → tenant/peer/link/storage behavioral overrides → permitted operation-scoped behavioral overrides. **Authority ceilings** (permitted tenant/peer scope) and **resource ceilings** (maximum hops, bytes, time, fan-out) can only narrow at lower scopes and can never be enlarged. **Behavioral defaults** can be replaced in either direction by a later authorized scope, but the result must remain within every applicable authority/resource ceiling and preserve primitive invariants. Example: deployment default `sync_scope=metadata`, mode sets `full`; tenant authority permits only `metadata`, so resolved scope is `metadata`. A deployment may default `tier=cold`, a mode may choose `hot`, and a tenant can choose `warm` if all are allowed. A mode can set `max_hops=3` under hard ceiling 5, while a per-peer binding can use 1 but cannot choose 6. Reject unknown required fields, invalid enum values, capability conflicts, unbounded limits, and attempts to weaken gates. Produce a deterministic resolved-config digest and provenance.

Separate planes: (1) peer relationship/class and permitted actions; (2) link/transport kind and per-operation connection selection; (3) storage resource kind/capabilities/durability/retention; (4) data tier and placement; (5) namespace registry/resolution behavior. Modes are named bundles across these planes, not a conflation of peer trust with storage tier. Tiering is native in the record model: a signed record carries versioned `data_tier` and/or `storage_tier` references (and classification scope/provenance); policy separately maps those references to placement/retention. Reclassification or copy to a different tier creates a new signed version/derived record and does not mutate the signed historical value. A peer class does not imply a transport, and storage tier does not imply trust or authorization. First-party/hosted deployments are ordinary config instances.

## Operational and protocol cases to resolve before implementation

- Restart recovery uses durable operation/outbox identifiers, monotonic per-resource sequence where promised, replay-safe redelivery, and explicit dead-letter/quarantine policy; callbacks themselves may repeat.
- Rollback restores prior config snapshot and mode, but cannot roll back acknowledged external effects. Configuration rollout is staged and reports per-adapter capability validation before activation.
- Schema/config evolution uses explicit major/minor contract versions and migrations; readers reject unsupported mandatory versions. Protocol negotiation chooses the highest mutually supported version within an allowlist; signed negotiation binds identities and transcript. Downgrade is rejected if it removes a required security/correctness capability; no silent fallback to unsigned/unvalidated or weaker tenancy behavior.
- No exactly-once guarantee across store + stream + transport. Use transactional outbox only within one store's documented atomic scope, at-least-once delivery, stable event IDs and idempotent consumers; document reconciliation for split-brain/unknown outcomes.

## Test approach and oracles

1. Shared conformance suite runs against redb, Turso/libSQL, and any adopted IndexedDB adapter; optional backends have an explicit subset report. Oracle: abstract reference state machine plus observed adapter state. Test read-after-write, scan boundaries, idempotent retry, declared transaction scope, capability-negotiation rejection before writes, restart/reopen, and fault injection at every uncertainty boundary.
2. Property tests for codec/config canonicalization, stable IDs, capability negotiation symmetry, no weakening of invariants, and hook ordering. Oracle: invariants and canonical reference encoder/resolver; generate versioned schemas/configs and operation traces.
3. Model-based hook/outbox tests compare actual traces to a small state machine (trusted normalize/sign → gate → immutable-input prepare → commit-time reauthorization → commit → outbox → delivery), injecting crashes, policy revocation, unknown outcomes and timeouts at each edge; assert hooks see validated immutable inputs, no unauthorized commit/retry, and no report of rollback after committed state.
4. Cross-runtime Rust and TypeScript golden vectors/fixtures establish tier-1 semantic parity. Oracle: checked-in protocol vectors plus independent verifier; run adapter matrix with deliberate capability differences.
5. Transport/stream conformance checks delivery/ack/replay/ordering scope and bounded resources separately from stores; model at-least-once outcomes. No test asserts global exactly-once.
