## Other primary prior art and lessons

* **Conflict detection / transparency:** Willow Confidential Sync gives a range-reconciliation design, but its own page warns it is a paused/outdated proposal. RFC 9162 (2021-12), [Certificate Transparency v2](https://www.rfc-editor.org/rfc/rfc9162.html), defines signed tree heads, inclusion proofs and consistency proofs. These prove log inclusion/append-only consistency, not truth of an entry or a specific conflict-report workflow. Therefore Part B specifies that local comparison emits a durable report before any merge; Merkle/range techniques are replaceable anti-entropy adapters.
* **Replay, rotation and revocation:** RFC 9420 (2023-07), [MLS](https://www.rfc-editor.org/rfc/rfc9420.html), has epochs and key updates/removal. RFC 9750 (April 2025), [MLS Architecture §8.6](https://www.rfc-editor.org/rfc/rfc9750.html#section-8.6), specifically warns that MLS gives no protection against replay by **insiders**; it does not establish a general within-epoch replay limitation. Binding a stable event ID/counter is this design's recommendation, not an RFC prescription. RFC 9162 contributes signed history proofs. No cited standard defines this system's envelope or historical-key policy. New signed records bind issuer/key-id, object, sequence/parent, unique event ID, payload digest and domain; rotation is append-only authorization, revocation has explicit effective-time semantics.
* **Bounded propagation / duplicate state / scoring:** libp2p [Gossipsub v1.0](https://github.com/libp2p/specs/blob/master/pubsub/gossipsub/gossipsub-v1.0.md) uses bounded mesh degrees, seen-ID cache and fanout TTL; [v1.1](https://github.com/libp2p/specs/blob/master/pubsub/gossipsub/gossipsub-v1.1.md) adds local peer scoring and thresholds. This is useful machinery precedent, not proof that gossip priorities are globally fair or secure. A routing profile must bound breadth, depth, work, bytes and time independently.
* **Acknowledgments / claims:** RFC 9162's signed log commitments and RFC 9942 (2026-06), [COSE Receipts](https://www.rfc-editor.org/rfc/rfc9942.html), support signed proof of a VDS property true at receipt issuance (the concrete profile covers Merkle inclusion/consistency). A signature authenticates a key; attributing it to a named party separately requires signer-key identity binding. A receipt proves neither perpetual retention, availability, query eligibility, nor broader truth. Public claims remain claims; right of reply and rate limits are required. Ratings are portable attestations at most, weighted locally.

## Component research and options

### #9141 — peer classes, signatures, lifecycle and replay
**Options:** (A) three coarse directional classes with policy hooks; (B) capability references as the primary access model. Recommend A as the stable core classification. A future application-level capability wrapper may be evaluated for narrower relay grants; this is not claimed as OCapN attenuation. It maps directly to fully-trusted / send-only / accept-signed-from; class is policy, not a signature bypass or relay grant. Unknown peer = reject acceptance. Signed+validated ingest applies equally to loopback, internal, remote and hosted. Signature input must be canonical and domain-separated, while legacy SignedBody JSON preimage bytes remain unchanged and get compatibility vectors. Event ID/sequence/parent handle replay, while same content with a new event ID is not silently confused with duplicate delivery. Keep key lineage and signed rotations; revocation marks affected ranges and triggers revalidation/quarantine, not retroactive deletion of historical signature bytes. Algorithm agility is a suite registry plus versioned envelope.

### #9142 — sync, scope and conflict reports
**Options:** (A) inventory/hash anti-entropy then selective fetch; (B) stream all records and compare. A is default: bounded, restartable and permits selective scope. Internal peers have implicit-trust sync posture, with target “1:1 sameness within reason” (S1.27): explicitly scoped by authorization, capacity, retention, tenant/trust boundaries, deletion and privacy. Divergence is detectable, not assumed away. It must emit durable conflict records (both version IDs, origins, signatures, policy/scope, detection time) before any resolution. Unrelated records continue. Never equate no local copy with global absence.

### #9143 — CRDT exploration
The four-project comparison above is the common matrix. **Options:** adopt a CRDT immediately vs isolate a merge adapter after V2 reports. Choose deferred adapter: V2 preserves signed immutable operations and reports, so a later CRDT can consume a report without erasing provenance. Prior-art findings are research seeds: benchmark Automerge for structured metadata; Diamond Types for text-only workloads; Willow range reconciliation for large scoped sets; OCapN for explicit authority transport. None alone solves signatures, deletion/privacy, reputation or federation-wide trust.

### #9144 — fan-out and acknowledgment
**Options:** (A) bounded sequential prioritized fanout; (B) parallel bounded batches. A is default for predictable cost/privacy; later configurable batches may improve latency. Immutable origin query has nonce-derived request ID, origin signature, scope, deadline and independent budgets; mutable per-hop path and child budgets are in chained relay grants, never edited inside origin signature. Each honest relay partitions its durable local budget ledger; per-request, authenticated-client/peer, tenant and node limits apply. Own store first. Preserve original responder signature/proof end-to-end. B19 supplies the shared V2 receipt schema in an independent interface PR, not a V3 dependency; it states what was accepted/retained/verified at a time under policy, never perpetual retention or query eligibility.

### #9145 — duplicate, replay, cycle
**Options:** (A) bounded in-memory cache; (B) durable request ledger. Use memory cache for in-flight work plus bounded durable outcome cache where idempotency survives restart. Distinguish: replay = invalid/reused signed event identity under freshness rules; duplicate = same valid request ID delivered again; cycle = duplicate with evidence the local node already occurs in signed relay path. Surface duplicate/loop status to requester, short-circuit cached work, merge results by stable result identity. Cache retention is finite and declared; after expiry, work may execute again under remaining budget, but cycle suspicion must not be asserted without retained path proof.

### #9146 — routing state
**Options:** (A) signed gossip of observed reachability/coverage; (B) direct probes of configured peers. Use both as evidence sources, neither authoritative. Shape is partial and time-bounded; observations include observer, timestamp, expiry, scope and proof. Periodic validation updates stale/vanished/appeared edges. Poisoned claims are constrained by local policy and direct evidence; never infer complete topology.

### #9147 — reputation, claims and abuse
**Options:** (A) global scalar score; (B) signed evidence claims with local weighted policy. Choose B. Claims/disputes are append-only, attributed statements, not verdicts; accused has equal-authentication right of reply. An invalid signature does not authenticate its purported signer; rating penalty requires evidence tying the exact bytes to an authenticated supplying peer. Otherwise retain unattributed rejection evidence only. Limit claim rate/bytes, require signatures and evidence references, allow moderation/quarantine, and expose corrections as new entries. Resist self-rating, Sybil, retaliation, collusion and whitewashing with local weighting, identity continuity evidence, caps and human/admin review; no mechanism eliminates collusion. No first-party privilege. Reputation never overrides signature validation.

### #9148 — takeover and inconsistency
**Options:** (A) revoke peer and quarantine all history; (B) scoped incident ranges and policy review. Choose B with emergency peer disable: preserve signed evidence, identify events by key and acceptance interval, revalidate/quarantine in affected scope, allow restore after review. Contradiction is evidentiary only when both claims match object/content digest, scope, time interval, retention/query policy, authorization and completeness semantics. A signed recipient receipt proves receipt at that time, not continued retention or eligibility. Missing data alone cannot prove omission. Acknowledgment-chain collusion remains a residual risk; log evidence and local reputation consequences, not automatic universal guilt.

### #9111 — modes/configuration inputs (not final configuration)
Proposed inputs for its separate owner: modes bundle peer class defaults, sync scope, link kinds (sync/query/send-only), storage retention/durability, relay permission, budget ceilings and scoring weights. Every field is overridable per peer where safe. Hard invariants (signature validation, envelope parsing, finite bounds, provenance) cannot be disabled. Internal/hosted peers receive no protocol exception. These are inputs, not a replacement final config design.

4. Model-check fan-out budgets, duplicate cache expiry, cycles, retries and signed original-responder preservation.
