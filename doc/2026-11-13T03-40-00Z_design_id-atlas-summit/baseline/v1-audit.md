## Section 4 correction: do not flatten existing ID into “no namespaces / no federation”

The proto's V1 shorthand “no namespaces as a designed system, no federation” is directionally useful for the *new general-purpose contract*, but over-compresses implemented mechanisms. ID already has Iroh document namespace/registry mechanisms and replicated/synchronized event/world data; group/world authorization, writer sets, delegation, signed chains, relay operations, peer discovery, and query-local/remote behavior exist in bounded product domains. These are not the proposed general namespace and peer-class model, nor unrestricted global federation. State the distinction explicitly: **domain-specific namespace/sync/authorization mechanisms exist; a uniform cross-domain namespace registry and generic federation protocol do not have evidence here.**

Also correct the storage shorthand: `id-store` documents Iroh's redb-backed persistent blob storage, while the event store is explicitly a one-file redb DB and durable worlds are `journal.jsonl` + content-addressed modules. These are distinct stores with different responsibilities. V1 is not one storage engine. Atlas's Python/Rust/Turso/shard paths likewise form separate pipeline/search surfaces rather than one uniform store.

## V2–V4 boundary advice (design guidance only)

1. **V2 establish contracts, not breadth:** document ID content-hash profile and bytes-to-hash oracle; define storage and namespace seams; define signed object envelope + validation hook and list each ingress path. Do not claim a universal signature gate until all ingress paths are enumerated and tested, including local writes and hosted edges.
2. **Keep acceptance layers distinct:** transport peer authentication, payload signature verification, signer authorization/peer class, object semantic validation, tenant/scope authorization, and replay/idempotency are separate decisions. A valid signature proves key possession over bytes—not truth, authority, freshness, or permission.
3. **V3 federation after V2 seams:** add fan-out, bounded recursion, duplicate/loop semantics and response provenance only after request identity, validation, budgets, and tenancy scope are stable. Existing Iroh sync is not itself the desired query federation.
4. **V4 extensions remain adapters:** CRDTs, graph query, stream lifecycles, recommendation indexing and additional stores must consume stable primitives. Conformance should be per primitive capability, with explicitly unavailable capabilities, rather than assuming every backend supports all features.
5. Preserve ID's existing world/event/group contracts and Atlas's existing content/provenance/search designs as sibling owners; do not redefine them under “namespace” or “triples” without a compatibility mapping.
