**As of:** 2026-11-12. **Scope:** #9133–#9140, S2.1–S2.19 and S6.1–S6.17. This is evidence and alternatives, not a report of production measurements. ## Evidence and alternatives

### #9133 — benchmark harness and economics (S2.1–S2.3, S2.16)

Compare Cloudflare D1, R2 object operations, laptop redb and laptop Turso as non-equivalent workloads; keep native semantics and billing counters distinct. D1 paid DBs cap at 10 GB; R2 meters storage and Class A/B operations. The local fixture validates only mapping/correctness. #9133 reports storage metrics only and makes no search/shard recommendation. Search quality/shard decisions, including fixed recall@10 #8627, belong solely to #9092; #9133 may optionally validate/link its owner-produced artifact by schema and corpus/eval digests.

Alternatives: per-engine hand-coded benchmarks drift; a shared logical workload spec with native adapters improves parity but may hide engine-specific features. Keep native operations visible and versioned. Matrix: storage shard counts 1/4/16/64; DB sizes 10 MB/1 GB/8 GB; R2 objects 1k/100k/1M at 4 KiB/1 MiB/64 MiB/1 GiB; concurrency 1/8/64; warm/cold; read, write, read-after-write, scan, ingest, recovery, GC. Record p50/p95/p99, errors, durability/replica, billed units and dated price. `benchmark-plan.json` maps each logical op to D1 SQL, R2 API, redb transaction and Turso SQL/sync. It contains no timings. Separate laptop redb/Turso and cloud D1/R2 follow-ups capture their own runner/environment/result schema. #9092 owns search shards/recall; no storage-derived shard winner.

### #9134 — D1 tenant hot cache (S2.4–S2.6, S2.17)

Alternatives: (A) bounded D1 hot rows/results; (B) Workers Cache API; (C) no extra cache, rely on replica/local reads. **V1 evidence:** `cache_do.ts` retains results indefinitely and `key.ts` keys normalized query/config; #9092 confirms no TTL/eviction/invalidation, monolith default, hidden shards and dead flags. Design must migrate this behavior. Avoid Turso hop per hot hit with pushed corpus watermark/policy epoch; no source lookup per hot hit. Admit by configured tenant tier and compute usage, enforce per-tenant/global byte caps and deterministic LRU/age eviction. Serve only within watermark lag bound and current policy epoch; event gap/expired lease fails closed. Realtime/cache-disable bypasses cache. Revocation is immediate; stale/unknown policy never serves. Key includes tenant/auth scope/policy epoch/query/schema/search space. Signature and authorization gates precede release.

### #9135 — tenant store placement and SQLite-file sync (S2.7–S2.9)

Alternatives: (A) D1 per tenant/shard; (B) SQLite + Litestream; (C) Turso Sync; (D) redb local. redb 4.3 docs state embedded portable ACID KV, MVCC concurrent readers/writer and crash-safe transactions—not replication. Litestream v0.5 docs describe asynchronous WAL-page replication to one replica, LTX compaction and restore boundaries—not multi-writer sync. Turso Sync docs specify local-first explicit push/pull of logical statements and last-push-wins conflict handling—not backup replication. D1 size/metering requires shard topology. Evaluate RPO/RTO, write authority, checkpoint/recovery, conflicts, restore drills and operator cost. No copied SQLite multi-writer over object storage. Do not prescribe one backend migration.

### #9136 — shared buckets and trust modes (S2.10–S2.13, S2.18)

Alternatives: (A) shared bucket with opaque tenant-scoped locator + broker; (B) separate buckets; (C) shared bucket with client-side envelope encryption; (D) server-side encryption alone. Keep canonical plaintext CAS identity (existing global ID/hash) separate from physical ciphertext locator; do not silently replace the global ID with keyed hashes. In untrusted mode, co-tenants see ciphertext payloads only; brokered opaque mapping hides plaintext ID/path/metadata by policy. A visible plaintext CAS key leaks equality/presence even if bytes are encrypted. Broker authorization and encryption are distinct. Threats include list/head/timing, confused deputy, key compromise, replay, metadata leakage and noisy neighbor. #9083/#9084 own interfaces.

### #9137 — GC for large files (S2.14–S2.15, S2.19)

Alternatives: mark/sweep, reference counts, epoch/lease tracing. A fresh recheck alone has TOCTOU and is insufficient. Required but unresolved #9084 authority contract: transactional reference/tombstone generation state. Writers conditionally commit reference intents only while generation `Live(g)`; GC atomically fences `Live(g)→Tombstoned(g)` only when no references/intents/leases; no late refs to g. Each physical generation has an immutable generation-qualified key that is never reused. Resurrection g+1 receives a distinct key; canonical ContentId/PayloadId stays stable. After fence and grace, GC may plain-delete only the captured old key for g. R2 conditional operations document conditionally supports writes (Put/Multipart/Copy), not delete; do not claim conditional DeleteObject. Without proof of both #9084 fence and key non-reuse, physical deletion is unsupported/disabled. A delayed delete of g cannot alias g+1. Cross-store publication may leave orphans but never exposes a reference before authority accepts it. Prioritize largest reclaimable files; chunks are independent and do not rewrite whole-file identity. Do not settle reference-v-copy.

### #9138 — ID search and vectorization (S6.1–S6.3, S6.13–S6.14)

Current selected MODEL: **Snowflake arctic-embed-m-v2.0** (#9092; not a Cortex vendor choice). Second embedder is **undecided by owner**, with candidates BGE-M3, Voyage, OpenAI text-embedding-3 and Workers AI evaluated on #8627 quality, cost, self-hostability and mixed-embedder support. Alternatives have distinct tradeoffs: BAAI model card describes self-hostable BGE-M3 as 1024-D, 8192-token with dense/sparse/ColBERT-style outputs (more control/multi-signal potential, more local compute/index complexity); Workers AI hosts `@cf/baai/bge-m3` with documented token-unit pricing (managed serving, but hosted data/runtime boundary); Voyage documents hosted general/code/multilingual choices and token prices (context/model flexibility, vendor dependency); OpenAI documents `text-embedding-3` API and dimension shortening (hosted, pinned model/dimension required); lexical-only is the no-embedding fallback. Snowflake Cortex docs describe separate product functions/models, not the selected vendor. No candidate quality winner is claimed without fixed #8627 evaluation. Platform behavior is ingest→async autoqueue for configured much/all accepted content, idempotent embedding and backfill; ingest never waits, and tenant-authorized built-in ID search is first-class. Persist exact model/revision/preprocess/dimensions with content identity/version; keep vector spaces separate. Signed validated acceptance and tenant auth precede indexing and result release. Search/shard recommendation belongs to #9092.

### #9139 — recommendation fan-out and Durable Object accumulator (S6.4–S6.7, S6.15)

Alternatives: (A) one logical fan-out worker plus per-user Durable Object (DO) accumulator; (B) queue workers write ordered pages into a durable SQL/object store and clients cursor there; (C) fully materialized recommendation snapshots. A single DO serializes per-key state and offers durable storage, but is not unbounded: SQLite-backed DO limits are 10 GB/object, alarms have a 15-minute wall-time limit, and throughput is bounded. Alarms can retry; checkpoint idempotently. At pinned cutoff, materialize order score DESC then immutable recommendation ID ASC. Parent SnapshotId hashes a signed parent envelope describing inputs/ranking/cutoff only, excluding pages. Page body binds parent SnapshotId+position; each page has its own signed envelope and EnvelopeId. Cursor binds parent SnapshotId+position, so restart returns the same page; wrong-parent cursor rejects. Any final page manifest is a separate later envelope to avoid a hash cycle. Durable queue/table is an alternative if DO bounds are exceeded; delivery remains at-least-once, not exactly-once.

### #9140 — recommendation objects and retention (S6.8–S6.12, S6.16–S6.17)

Alternatives: (A) immutable content-addressed recommendation snapshot objects plus mutable pointer/index; (B) append-only event log from which snapshots can be reconstructed; (C) ephemeral ranked feed only. Snapshots support before/after admin comparison and audit but cost storage and can preserve sensitive input; event logs replay but require deterministic versioned ranking and bounded compaction; ephemeral feed is cheap but cannot meet history requirement. Store recommendation snapshot as its own versioned object with owner/tenant, input snapshot, algorithm/model versions, creation time and provenance; keep query/search history as separately authorized input objects, not conflated with generated recommendation object. Per-class TTL covers `whats-hot` intermediate data vs durable snapshots/history; explicit deletion/legal hold overrides retention policy. Before/after comparison pins snapshot IDs and algorithm version. #9084 owns object lifecycle and reference predicate.

## Shared summit identity constraint

Part C follows the cross-part contract from the summit owner: `ContentId` hashes exact profile bytes; `PayloadId` hashes raw payload; `EnvelopeId`/`AssertionId`/`SnapshotId` hash complete canonical signed envelope including signature and never self-occur in signed preimage; `LogicalGraphId` remains separate. New records use deterministic CBOR and domain-prefixed detached signatures over canonical Body committing payload ID, length, domain/context. Legacy artifact JSON/signature bytes remain a compatibility profile because baseline audit found documentation/code Ed25519 preimage mismatch. Do not re-sign/rehash during cache, vector, bucket or GC migration. Rebuildable derived records project validated signed authority; independently retained/transported recommendation/search-derived objects need signed service envelopes. Atlas observed data uses SHA256 of exact UTF-8 chunk text, but its producer is not located in inspected source; ID/Iroh BLAKE3 identity is separate.
