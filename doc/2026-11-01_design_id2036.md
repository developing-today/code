# Design: ID messaging and relay protocol v1

- Date: 2026-11-01
- Status: **decision-ready design**; implementation is tracked in #3794–#3797.
- Issue: #2036 (parent epic #2056); synthesis of investigations #2034 and #2035.
- Scope: application messaging semantics and relay behavior. No implementation changes are included here.

## The decision

Specify how ID carries low-latency data without a central application server while keeping durable facts independently verifiable: choose the data classes, delivery and retention rules, relay authorization and hop semantics, and the point where live activity becomes a dispute-grade attestation.

**Recommendation:** keep durable facts in the existing origin-signed event graph; carry high-rate live input in a session-scoped MAC-authenticated stream and sign periodic segment checkpoints into that graph. Use one logical membership and relay policy, but distinct delivery modes: gossip-style fan-out for chained facts, ordered QUIC streams for live frames. A member may bridge traffic when direct reachability fails. The transport or a relay never becomes the source of truth. See [§4](#4-recommended-protocol-v1).

This follows the latest #2036 triage comment (2026-11-01): two data classes, signed session headers and checkpoints, the proposed 256-event/2-second checkpoint defaults, origin-signature validity, hop records for audit/loop control, four implementation phases, and one non-blocking channel-default question. It also resolves a material constraint recorded in the merged #2035 investigation: stock iroh-gossip eagerly forwards before ID's receive handler can approve a message. Therefore, **unvalidated stock-gossip forwarding is not an acceptable implementation**; phase 3 must provide a pre-forward validation gate or use ID-controlled forwarding. [#2036 body and 2026-11-01 triage comment; #2035 investigation, §2.2, lines 146–184]

## 1. Context at this checkout

- ID already has a durable signed graph. `ChainExt` puts kind, optional group, and causal frontier in the signed header; `chain::sign` commits to the body hash and computes the event ID over the signed bytes, while `decode` verifies canonical encoding and signature (`pkgs/id/src/chain.rs:4-16, 93-118, 271-342`). The event store retains accepted events, fork proofs, and waiting dependencies (`pkgs/id/src/event_store/mod.rs:1-23`); receive-side ingest verifies before applying (`pkgs/id/src/event_store/ingest.rs:1-27, 226-269`).
- The existing group-operation body encodes create/join/remove/promote/demote and access levels, but not friendship or group policy (`pkgs/id/src/membership/body.rs:1-28`). A separate local `GroupLog` is explicitly unsigned and is not a substitute for the event store (`pkgs/id/src/groups/log.rs:1-10`).
- Iroh relay policy today is transport/NAT traversal (N0 relays by default or direct-only), not application-message authority (`pkgs/id/src/connectivity.rs:16-46`). `id serve` registers iroh-gossip and range sync; its discovered-peer loop offers range-sync sessions (`pkgs/id/src/commands/serve.rs:973-1019`). Current gossip use is peer discovery (`pkgs/id/src/commands/peers.rs:1-4, 16-21, 48-52`), not validated group-message relay.
- Existing collaboration already distinguishes transient frames from saved facts: its live protocol has steps, updates, acknowledgements, and cursors (`pkgs/id/src/web/collab.rs:6-17`); a saved web revision enters the shared signed event store and next range-sync session (`pkgs/id/src/event_sync.rs:14-20`). The world transport likewise says that an Iroh node identity is not authority; the join capability is (`pkgs/id/src/world_net.rs:8-10`).
- Range sync already reconciles stored graph events and fork-proof headers (`pkgs/id/src/event_store/sync.rs:333-353, 356-373`). It provides eventual catch-up for durable facts, not delivery for live frames.
- The match-attestation module is explicitly a PoC, not a production feature; its witness slot is unused and it has no witness flow (`pkgs/id/src/attestation.rs:1-24, 53-68`). Messaging must hand dispute-grade outcomes to mutual, per-match attestation rather than treating a live-stream checkpoint as a verdict.

These distinctions matter: the design adds application-level semantics above existing transports and storage; it does not equate an Iroh relay, a gossip topic, a local group log, or a live session with authorization or durable truth.

## 2. Options and trade-offs

### Data lifecycle

| Option | Benefits | Costs / failure mode | Decision |
| --- | --- | --- | --- |
| Sign and retain every live frame as a graph event | Per-frame attribution and straightforward replay | High-rate cursor/keystroke/input traffic becomes permanent signed storage and puts per-event signing on the latency path | Reject for transient live input; retain for durable facts and dispute-grade records |
| Keep all live traffic ephemeral, with no signed checkpoint | Lowest storage and signing cost | A reconnecting peer has no durable state boundary; a relay can truncate or equivocate between participants without a signed segment boundary | Reject |
| Split durable facts from session traffic; sign ordered segment checkpoints | Low-cost live frames, reconstructable state boundaries, and durable origin-signed facts | Checkpoints do not prove exact per-frame timing or what every peer saw between checkpoints | **Choose**, with explicit limits and attestation hand-off |

### Fan-out and relay

| Option | Benefits | Costs / failure mode | Decision |
| --- | --- | --- | --- |
| Direct connections only | Simple paths and no intermediate application relay | Cannot reach members behind incompatible NATs or network restrictions | Keep as first choice, not the only path |
| Central application broker | Simple rendezvous, ordering, and policy enforcement | Central availability and trust become part of message validity; conflicts with the issue's no-central-server goal | Reject as the default |
| iroh-gossip with ID semantics and hop records | Reuses the selected broadcast-tree, duplicate-suppression, and repair substrate | Stock iroh-gossip forwards before the application can validate membership, so post-receive validation alone is too late | Choose only with a validation-before-forward hook; otherwise use ID-controlled forwarding |

### Live-stream transport

| Option | Benefits | Costs / failure mode | Decision |
| --- | --- | --- | --- |
| Send ordered live frames through the same gossip delivery path as durable events | One apparent transport | Gossip delivery is eventual and unordered; it cannot be the ordered low-latency session stream | Reject for live frames |
| Use per-session ordered QUIC streams, direct where possible and member-forwarded only while connected | Preserves sender order and low latency; no central application server or offline queue | A bridge can observe timing and withhold traffic; disconnected live frames are lost by design | **Choose** |

The “one fan-out” in the latest #2036 triage is therefore one **logical** membership/routing policy, not one wire transport: chained traffic can use gossip fan-out; ordered live traffic uses per-session QUIC. The #2035 investigation specifically warns that eventual, unordered gossip is wrong for live streams requiring sender order (`doc/2026-10-29T11-05-00Z_investigation_multi_hop_relay_and_p2p_media/2026-10-29T11-05-00Z_investigation_multi_hop_relay_and_p2p_media.md:161-184, 246-261`).

## 3. Protocol classes

| Class | Examples | Authenticity and ordering | Delivery / retention | Recovery |
| --- | --- | --- | --- | --- |
| **Chained / durable** | Identity, membership, documents, money, durable chat, match results, session checkpoints | Origin signs each fact; event sequence/backlink and causal frontier provide graph order. Receivers verify the signed envelope and group membership at send time. | Retained as ordinary event-graph entries; durable facts are never moved to checkpoint-only signing. | Any peer can catch up from another member by range sync. Arrival may be out of order; graph dependencies determine application. |
| **Ephemeral / live** | Keystrokes, cursors, presence, live input, live-session chat | One signed session header binds session ID, purpose, participants and key commitment; frames carry per-session sequence numbers and MACs; signed segment checkpoints bind ordered deltas to state roots. | Live frames stay out of the durable graph and are not queued for offline members. A checkpoint is a normal signed graph event. Initial default: checkpoint every 256 events or 2 seconds, whichever comes first, and at explicit commit/blur/end; make limits configurable in the `WorldLimits` style. | Rebuild from the latest checkpoint plus the live frames since it. A disconnected live stream may lose its uncheckpointed tail; this is acceptable only for non-dispute-grade state. |

The checkpoint commits to the session, monotonic segment number, immediate previous checkpoint, ordered segment root, event count and time bounds. Frames must bind their session ID, sequence and payload under the session MAC. The 256-event/2-second values are defaults from the latest issue triage, not magic protocol constants. The existing `WorldLimits` pattern supports bounded runtime-configurable limits (`pkgs/id/src/world/mod.rs:57-100`). The investigation's threat analysis makes the guarantee explicit: a checkpoint attests to a signer-committed segment; it does not prove the exact time of each frame or that every recipient saw the same intermediate stream (`doc/2026-10-29T10-45-00Z_investigation_ephemeral_live_data_retention/2026-10-29T10-45-00Z_investigation_ephemeral_live_data_retention.md:84-99, 110-118`).

For chat, the channel policy is explicit: `durable` means each message is a signed retained fact; `live` means session frames plus checkpoints and a bounded audit-retention window (90 days is the proposed starting value). New-channel default is the one policy question for Drew in §7. Do not silently infer retention from message type or transport.

## 4. Recommended protocol v1

### 4.1 Immutable origin envelope and relay record

For a chained message, the origin-signed envelope contains the origin ID, group ID, origin sequence, predecessor references, class, and either bounded inline content or a content hash/blob reference. Its stable message ID is the BLAKE3 hash of the complete canonical signed envelope, excluding only the mutable hop chain. The origin never changes that envelope when relaying.

Each member relay may append a self-signed hop record `(relay_id, previous_hop_id, received_at)`. The hop chain is **audit and loop-control metadata only**: it cannot make an invalid origin message valid, and its absence or alteration does not change the origin signature's validity. A member does not forward a message twice, does not forward when its own ID is already in the hop chain, and stops forwarding at the four-hop default cap. These envelope, dedupe and hop rules follow the merged #2035 investigation (§2.3, lines 186–231); the signed event ID's full-byte hashing has a direct analogue in `pkgs/id/src/chain.rs:263-269, 302-308, 337-341`.

### 4.2 Authorization before forwarding

The relay must validate the origin signature, canonical envelope, message ID, class and local group authorization **before it forwards**. A gossip topic ID is not a group credential. Current group-operation encoding provides a base for group membership/access facts but does not encode friendship or policy (`pkgs/id/src/membership/body.rs:13-28`); the v1 message policy must name the authoritative membership state and the point in the signed graph against which write access is evaluated.

**Required implementation choice:** first verify that the selected iroh-gossip version can gate eager forwarding on ID's accept decision. If it cannot, keep gossip for swarm discovery/repair only and make forwarding ID-controlled over Iroh connections. Do not ship stock eager-forwarding plus post-hoc ingest checks: the #2035 investigation records that this would propagate unsigned or unauthorized traffic before validation (`doc/2026-10-29T11-05-00Z_investigation_multi_hop_relay_and_p2p_media/2026-10-29T11-05-00Z_investigation_multi_hop_relay_and_p2p_media.md:161-184`). This is a technical acceptance gate, not a question for Drew.

An authorized relay may still delay or withhold a message. That is an availability fault, not a validity change: chained messages remain recoverable through range sync; ephemeral frames are not recoverable after their live session. Application relays are members, not a central authority. Iroh's transport relay may still be used for NAT traversal; it is distinct from an application broker (`pkgs/id/src/connectivity.rs:16-46`, `pkgs/id/src/envelope_net.rs:1-7`).

### 4.3 Live session and checkpoint boundary

The session header is signed once and binds a fresh session ID, purpose, participant set, start/nonce and a commitment to the MAC key. Each authenticated participant's live frame has a per-sender monotonic sequence and MAC over the session ID, sequence and payload. Reject wrong-session, invalid-MAC, replayed or duplicate sequence numbers; do not put the raw frames in the event store.

At a segment boundary (256 frames, 2 seconds, or explicit commit/blur/end), the session owner signs a checkpoint event in the existing graph. Each checkpoint names its immediate predecessor and a root over the ordered segment. A gap is detectable; a missing live tail is not proof of a completed action. Key derivation, key rotation and participant-specific MAC scope must be made explicit in phase 1; never publish the MAC secret in the checkpoint. This preserves the latest issue's signed-header/MAC/checkpoint decision while making the unresolved key-handling contract an implementation acceptance item.

### 4.4 Attestation hand-off

Live frames and segment checkpoints are evidence of a session, not the verdict for a two-party dispute. Match results, transfers and contract-like chat remain individually signed durable facts and require the relevant mutual/per-transaction attestation. For matches, the hand-off is the signed `attestation.genesis` agreement before play and the players' `attestation.claim` records at completion; the live stream can supply evidence but a checkpoint alone cannot settle disagreement. The current attestation code establishes only a mutual-concession PoC and explicitly has no production witness flow (`pkgs/id/src/attestation.rs:1-24, 53-68`). This design does not expand or replace the attestation protocol.

### 4.5 Media, framing and privacy

Media is outside the gossip tree. Prefer direct QUIC mesh for small groups (the current recommendation is around six participants); if reachability requires it, one member selectively forwards already-encrypted media packets. A central hairpin is opt-in privacy-relay mode only. That mode must disable direct transport/address-candidate exchange or use proxy connections: routing through a relay alone does not hide peer addresses (`doc/2026-10-29T11-05-00Z_investigation_multi_hop_relay_and_p2p_media/2026-10-29T11-05-00Z_investigation_multi_hop_relay_and_p2p_media.md:300-337`).

Do not add a new wire-level chunking protocol. QUIC streams carry the existing length-prefixed application frames; the shared frame cap is 1 MiB (`pkgs/id/src/frames.rs:1-20`). For a larger framed object, reuse the checked-chunk/reassembly pattern already used by welcomes (`pkgs/id/src/encryption/welcome.rs:1-19, 31-48`); large media uses content-addressed blob references as described in the #2036 triage and #2035 investigation.

### 4.6 Retention and compaction

The event store currently retains accepted event bytes, fork proofs, and waiting dependencies (`pkgs/id/src/event_store/mod.rs:4-23`); the #2034 investigation records no event-store TTL/compaction path today (§2, lines 31-41). Phase 4 adds reclamation only for expired ephemeral/audit material according to the channel/session policy. It must preserve every durable fact and checkpoint, every fork-proof header, and any event/dependency needed to resolve a waiting `after` reference. Checkpoint graph events themselves are not deleted by live-data compaction. Treat an unavailable expired audit blob as a declared retention outcome, not as permission to alter the signed checkpoint.

## 5. Invariants and acceptance criteria

1. **Origin truth is path-independent.** The same signed envelope verifies to the same message ID over a direct path or any number of relay paths; hop records never affect validity. Different signed envelopes/forks do not collapse under dedupe.
2. **No unauthorized onward propagation.** A non-member, invalid signature, malformed envelope, replay, or message lacking write authorization at the defined membership frontier is refused before the node forwards it. A topic ID alone never authorizes a sender.
3. **Bounded, auditable relaying.** Each relay appends its own signed hop record; a node forwards at most once per message, refuses its own prior hop, and enforces the four-hop cap. Tests cover loops, duplicate paths, stripped/malformed hop chains, and over-cap paths.
4. **Durable catch-up is eventual.** Reordering does not change graph application; missing predecessors remain pending/refused under the existing event-store rules and are retried through range sync. A relay outage may delay a durable fact but cannot rewrite it.
5. **Live traffic is session-bound and bounded.** Frames with invalid MACs, the wrong session, duplicate/replayed sequence, or expired session are rejected. At the 256-frame/2-second threshold and explicit commit, the checkpoint verifies against its predecessor and ordered root. Raw live frames are not added to the durable graph; disconnected peers are not sent a backlog.
6. **Checkpoint claims are honest.** Checkpoints prove only the signer's ordered segment commitment and endpoint state. No consumer treats them as per-frame non-repudiation, exact timing proof, or evidence that every peer observed the segment.
7. **Dispute-grade outcomes stay durable.** A match result or other two-party obligation cannot be accepted solely from an ephemeral frame or one-sided segment checkpoint; the class-specific mutual attestation is required.
8. **Compaction preserves graph validity.** Tests reopening/syncing a compacted store retain all durable events, checkpoint events, fork proofs and required dependency resolution; only eligible bounded audit data may expire.
9. **Transport is not authority.** Direct connections, N0 relay, gossip transport and a member bridge all lead to the same ID validation. Privacy-relay mode is opt-in and passes an address-isolation test.
10. **No new chunking wire format.** Frames respect the 1 MiB limit; checked reassembly refuses oversized, reordered, altered or digest-mismatched chunks; large payloads are references, not unbounded gossip frames.

## 6. Phased implementation plan

Each phase is a separately reviewable and mergeable change. Phase 1 freezes the shared event/session schema; phases 2 and 3 may then proceed independently if their interfaces are held to that schema. Phase 4 follows the checkpoint and retention contracts. The issue's existing packets are referenced; this note does not create or modify them.

| Phase | Packet | Scope and dependencies | Merge acceptance |
| --- | --- | --- | --- |
| **1 — session header and `session.checkpoint` event** | #3794 | Add the signed session-header/checkpoint schema, validation rules, event kind and configurable defaults. No live relay behavior yet. Resolve MAC-key derivation/rotation and define exactly which identities can authenticate frames. | Canonical encode/decode and signature tests; monotonic segment/predecessor validation; replay/session-binding vectors; 256-event/2-second defaults are configurable; old event kinds remain compatible. |
| **2 — intermittent-signature live-stream PoC** | #3795 | Apply the session/MAC/checkpoint contract to collaborative live data. Use ordered per-session transport, direct first and active member forwarding only where needed; no offline queue. | End-to-end test with two direct peers and one bridge; reject bad MAC/replay/wrong session; checkpoint at limits and commit; verify raw frames never enter the event store and loss of the uncheckpointed tail is explicit. |
| **3 — chained-message relay envelope and hop records** | #3796 | Add origin envelope, stable message ID, membership-aware acceptance, hop record, loop detection and four-hop cap. Prove a validate-before-forward seam before relying on iroh-gossip. If stock gossip cannot gate eager forwarding, use ID-controlled forwarding rather than weaken authorization. | Multi-hop topology test proves unauthorized traffic is not forwarded; valid origin bytes remain identical; alternate paths dedupe; forks stay distinguishable; outage catch-up uses range sync; loop/cap tests pass. |
| **4 — event-store retention/compaction** | #3797 | Reclaim only eligible expired live/audit material; retain graph checkpoints and durable facts and preserve the store's proof/dependency invariants. Depends on phase 1's checkpoint format and phase 2/3's declared retention metadata. | Crash/reopen and sync tests prove checkpoints, durable records, fork proofs and waiting dependencies remain valid; expired audit data follows the declared retention policy; compaction is atomic or leaves the old valid store. |

This order matches the existing #2036 triage packets. The bridge PoC #2249 may proceed only against phase 3's reviewed envelope and must not become production code before review, as the issue requires.

## 7. Question for Drew

**New chat-channel default (non-blocking; phases proceed either way):**

- **Option A — durable by default; live/90-day-bounded is opt-in per channel. Recommended.** Missing history is visible and difficult to recover retroactively; channels can relax retention later.
- **Option B — live/90-day-bounded by default for high-chatter rooms.** Reduces retained history, but a channel may silently lose context unless users opt into durability.

Recommendation: **A**. Implement the per-channel policy object regardless; store the chosen default as configuration so Drew's answer changes policy, not the wire format. This is the only decision in this design that genuinely needs Drew; the relay validation gate, key handling and compaction safety are implementation requirements with defaults/acceptance criteria above.

## Non-goals

- No central application broker or server-assigned message validity.
- No per-frame durable event for cursor, keystroke, presence or live input.
- No trust in hop records, transport identity, gossip topic secrecy or a member relay's claims.
- No media forwarding through the gossip tree; no default central media hairpin.
- No new chunking wire protocol.
- No redesign of the attestation protocol, world journal or event-store identity format; this document defines their messaging hand-offs only.
