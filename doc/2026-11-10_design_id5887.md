# Design: user-held keys — key custody variant (b) for `id`

- Date: 2026-11-10
- Status: **decision-ready proposal** — design only; no custody code is implemented here.
- Issue: [#5887](https://github.com/developing-today/code/issues/5887), parent design [#5684](https://github.com/developing-today/code/issues/5684), programme epic [#2056](https://github.com/developing-today/code/issues/2056).
- Parent decisions consumed, not re-decided: identity is a keypair (iroh-style; the public key is the identifier, no central registry mints or revokes it); simplicity-first is a hard requirement and login UX must be indistinguishable from ordinary logins; custody honesty (for every variant, state who can sign as the user, who can lock them out, who can recover them); the signed-hash setup artefact is the acceptance root (later acceptance verifies a signature against the established public key / signed artefact, never a party's custody of the private key); issuer rotation and compromise recovery mechanics belong to [#2804](https://github.com/developing-today/code/issues/2804) and are inputs here. The one place this design touches a parent question is flagged in §8 (it answers the parent's variant-(b) open question; it does not change any parent decision).
- Splits: none filed from this design. The two implementation follow-ons are named in §10 as queue-ready scopes; filing them is the parent's decomposition bookkeeping, and this issue's acceptance is the recorded decision, not new tickets.

## Decision to make

In custody variant (b), where does the user's real key live, how does the user unlock it on a device, and what happens on a new device or when part of the setup is lost — given that the login service / authorizer **only authenticates the person and never possesses the key**, and that a non-technical user must be able to walk every flow?

## Recommendation

**The key lives as an encrypted blob in storage the user already has; the client — never a server — decrypts it; the authorizer authenticates the person and issues challenges, and holds only public artefacts.** Concretely:

1. **The blob is the only key home.** At setup the client generates the identity keypair locally and exports exactly one artefact: an encrypted key blob — the private key wrapped with a key-encryption key derived from the user's **key passphrase** via Argon2id (parameters in §2). The raw private key is never written to disk, never uploaded, and never shown to the user as text.
2. **Default home: the user's own cloud drive, advanced home: a file.** The blob is stored by default in the app-data folder of the user's Google Drive (the same account they sign in with), and the setup flow always offers a downloaded copy of the same blob as a file backup. Drive is a *storage* choice, not a trust choice: what Drive holds is ciphertext (§6). A user may keep the blob only as a file; the flows are identical.
3. **Unlock is client-side, after ordinary login.** Everyday login is: sign in with Google (or username/password) exactly as usual → the client fetches the blob → the user enters their key passphrase → the client unwraps in memory, signs the authorizer's challenge, and immediately issues the device a scoped pseudo-login delegation (variant (d) of #5684) so the real key is used once per device, not per action. The passphrase never leaves the device; the authorizer cannot verify it, reset it, or bypass it.
4. **Recovery is copies + codes, or it is honestly nothing.** Losing one copy of the blob is recoverable from the other copy. A forgotten passphrase is recoverable only if the user also set up variant (c) security codes, which wrap a second copy of the key (§5). If every blob copy is gone, or the passphrase is forgotten with no codes set up, **the identity is unrecoverable — nobody can unlock it, not support, not the service, not the developers** — and setup says so in plain language before the user commits (§5).
5. **The authorizer's compromise is a denial-of-service event, not an identity compromise.** A malicious or compromised authorizer can refuse logins and can phish at the *login* surface, but it cannot sign as the user, cannot decrypt the blob (it never holds a copy it can usefully attack beyond offline guessing against a stolen blob, §6), and cannot mint a new device delegation without a signature from the unlocked real key or a live pseudo-login.

## §1 Roles and artefacts

| Party | Holds | Never holds |
| --- | --- | --- |
| User's client (app / browser) | The private key, in memory only, between unlock and lock | — (it is the only place the key exists in plaintext) |
| User's storage (Drive app-data folder and/or a file the user keeps) | The encrypted key blob (§2) | The passphrase; the plaintext key |
| Authorizer / login service | The public key, the signed-hash setup artefact (§3), challenge nonces, the pseudo-login delegation records, optionally a mirror of the *encrypted* blob for fetch convenience | The private key in any form it can decrypt; the passphrase |
| Relying parties / worlds | The public key and delegation artefacts they verify against | Any key material |

Two consequences are load-bearing and must survive implementation unchanged:

- **Authentication ≠ custody.** The authorizer's "this is the right person" answer (OIDC / password) gates *fetching the blob and being issued a challenge*. It never gates the key itself: an attacker who fully defeats the login still faces the passphrase-wrapped blob; a user who loses login access but keeps blob + passphrase has lost convenience, not identity (§5, Drive-access-lost row — re-binding a new login to the same public key is an authorizer-side record change authorised by a signature from the unlocked key).
- **Fetch is not unlock.** Any number of failed passphrase attempts happen locally and are unobservable to the authorizer; there is no server-side lockout counter to abuse for lockout attacks, and no server-side reset to abuse for takeover.

## §2 The encrypted key blob

One canonical blob format, versioned, identical in Drive, in the file backup, and in the optional authorizer mirror:

- **Contents:** format version; identity public key; Argon2id salt and parameters; AEAD nonce; ciphertext of the private key (plus the setup-artefact hash, §3, as associated data so a blob cannot be silently paired with a different identity's artefacts).
- **Wrap:** KEK = Argon2id(passphrase, salt) with memory-hard parameters chosen for a ~1s unlock on a mid-range phone (record the parameters in the blob; they are not secret). AEAD (XChaCha20-Poly1305 or AES-256-GCM — one, chosen at implementation, named in the format version) over the private key.
- **Passphrase rules:** a *key passphrase*, distinct from the login password, minimum strength enforced by an estimator at setup (not a character-class rule), with the honest one-line explanation: "This is the one secret that protects your identity itself. Your sign-in gets you the locked box; this opens it."
- **Passphrase change = re-wrap, not rotation.** Changing the passphrase re-wraps the same key under a new salt/KEK and replaces every blob copy the client can reach; the identity does not change. Key *rotation* (a new keypair succeeding the old) is #2804 mechanics, signed by the old key, and is a different operation the UX must never conflate with a passphrase change.
- **No plaintext fallback.** There is no "export raw key" affordance in the default UX. Support and debugging flows must be designed so nobody ever asks a user to paste a private key anywhere.

## §3 The signed-hash setup artefact in variant (b)

Per the parent's required construction, specialised to this variant:

- **At setup**, once the keypair exists, the client signs a setup statement: a hash over (public key ‖ blob hash ‖ wrap parameters ‖ creation time ‖ "id setup v1" domain separator). That signature plus the statement is the **setup artefact**, stored by the authorizer and by the client inside the blob's associated data.
- **At login**, acceptance is: the authorizer issues a fresh challenge (random nonce, expiry ≤ 5 minutes, bound to the authorizer's identity and the requested delegation scope); the unlocked client signs it; the authorizer verifies against the public key established by the setup artefact. No step requires any party to hold the private key between unlocks.
- **At new-device enrolment**, the challenge the new device signs additionally names the requested pseudo-login scope, so the first delegation is itself part of the signed record (§4).
- **Limits, stated plainly:** the artefact proves continuity from setup; it cannot recover a key that no longer exists anywhere, and it cannot distinguish "the user unlocked" from "someone who obtained blob + passphrase unlocked" — that is the variant's stated trust shape (§6), not a defect to be papered over.

## §4 Flows

### 4.1 First-time setup (Google sign-in)

1. User chooses "Sign in with Google" and authenticates — ordinary OIDC, nothing key-shaped is shown.
2. Client generates the keypair locally, asks for a key passphrase (with the §2 explanation and the §5 unrecoverability wording shown *before* generation is finalised), builds the blob, signs the setup artefact.
3. Client stores the blob in the Drive app-data folder, offers the file backup download (recommended in one sentence, skippable), and offers variant (c) code setup as the next step (recommended, skippable, with the consequence of skipping stated in the same sentence).
4. Client registers (public key, setup artefact) with the authorizer and signs the first device delegation. Total user-visible novelty: one new passphrase and two one-sentence choices.

Username/password sign-up is identical from step 2 on; the login password and the key passphrase are separate secrets and the UX must say which is which at the moment each is created (conflating them is the known failure mode of this variant).

### 4.2 Everyday login (same device)

The device's live pseudo-login delegation (variant (d)) does the day-to-day work; the real key is not needed. The user sees an ordinary signed-in session. Unlocking the real key is demanded only for sensitive operations: enrolling a new device, changing the passphrase, rotating the key, widening a delegation, or recovering.

### 4.3 New device

1. User signs in on the new device (Google / password) — the authorizer authenticates the person.
2. Client fetches the blob (from Drive, or the user picks the file backup).
3. User enters the key passphrase; client unwraps, signs the enrolment challenge naming the new device's requested delegation scope.
4. Authorizer verifies against the setup artefact and records the new pseudo-login. The user sees the new device appear in their device list (variant (d) management view) and can revoke it there; revoking a device never touches the real key or other devices.

If step 3 fails because the user does not remember the passphrase, the flow ends in §5 — the already-enrolled devices keep working; a forgotten passphrase does not lock the user out of live sessions, only out of new enrolments and sensitive operations.

### 4.4 Passphrase change

Unlock → re-wrap per §2 → replace blob copies (Drive, authorizer mirror; the file backup is re-downloaded and the user is told the old file copy still opens with the *old* passphrase and should be replaced or destroyed — stated honestly: the client cannot reach into the user's drawer).

## §5 Failure and recovery matrix

| Failure | Recoverable? | Path |
| --- | --- | --- |
| Blob copy in Drive deleted / corrupted | Yes | File backup copy (identical blob); client re-uploads on next unlock. |
| File backup lost | Yes | Drive copy; re-download a fresh backup. |
| Google / Drive access lost (account closed, locked) | Yes, if any blob copy survives | File backup + passphrase unlock; sign a re-binding that attaches a new login identity to the same public key. If *no* blob copy survives, see the last row. |
| Passphrase forgotten, variant (c) codes set up | Yes | A security code authorises unwrapping the **code-wrapped second blob** created at code setup (same key, wrapped under a code-derived key per the variant (c) design), then the user sets a new passphrase and re-wraps. Codes are doing recovery *of the wrap*, never of a key that has no surviving copy. |
| Passphrase forgotten, no codes | **No** | Live device sessions continue until they expire or are revoked, but no new device, passphrase change, or rotation is possible. The honest end-state: the identity is frozen, then lost as sessions lapse. Setup and the forgot-passphrase screen both say this before it happens, not as a surprise. |
| Every blob copy lost (Drive gone *and* file gone) | **No** | The key exists nowhere; no artefact, code, or support action recreates it. The identity is unrecoverable; the user's path is a new identity. This is the variant-(c) all-codes-lost statement generalised: **if the key is gone, nobody can unlock the account — not support, not the service, not the developers.** |
| Device with a live delegation is lost / stolen | Yes | Revoke that pseudo-login from any other device or via the authorizer after login authentication + a real-key unlock for the revocation of record. Actions already taken under the delegation stand (provenance, variant (d)). |
| Authorizer account (login) compromised, blob + passphrase safe | Yes | Attacker can fetch ciphertext and fail against it locally; user re-binds login credentials; delegations issued by the attacker are impossible without a key signature, and any session-only artefacts are revocable server-side. |

Setup must surface the two **No** rows as an informed choice, in plain words, at the moment of setup — with the codes offer attached to exactly those rows ("Codes are how you avoid this"). Burying them in terms text fails the parent's honesty requirement and fails this design.

## §6 Threat model

**A compromised or malicious authorizer can:** deny login / enrolment (availability only); observe metadata (when logins happen, device enrolments, public keys); serve a stale or withheld blob mirror (availability / rollback to an older passphrase wrap — mitigated by the blob's signed associated data and monotonic wrap version the client checks against the setup artefact chain); attempt to phish the *login* credential on a lookalike surface (ordinary web risk, unchanged by this design).

**It cannot:** sign as the user; issue itself a valid delegation (delegations require a signature verifiable against the setup artefact); decrypt the blob with anything it holds — it holds at most ciphertext, and turning a stolen blob into the key requires offline passphrase guessing, whose cost is set by Argon2id parameters and passphrase strength (§2). That residual is stated, not hidden: **blob + weak passphrase = eventually guessed.** The mitigations are the strength estimator at setup, the memory-hard KDF, and codes-wrapped copies never being mirrored server-side.

**A compromised Drive / file store can:** delete or withhold the blob (availability; §5 copies answer it); read ciphertext (same offline-guessing residual as above); roll back to an older blob version (same mitigation as above).

**A compromised unlocked device can:** use the key while it is unlocked and the live delegation thereafter. Variant (b) does not solve endpoint compromise; it bounds it via memory-only key residency, lock-on-idle, and per-device revocable delegations so the real key is exposed as rarely as the design can arrange.

**Out of scope by parent ruling:** social / guardian recovery, hardware keys / passkeys as a primary topic (either can later become an additional wrap factor for the blob without changing this design's shape).

## §7 Alternatives considered and rejected

1. **Raw key file the user carries (no wrap).** Rejected: a plaintext key file will be emailed, screenshotted, and pasted into support chats; one disclosure is total and irrevocable. The wrapped blob degrades a disclosure to an offline guessing problem.
2. **Identity key derived from the login password.** Rejected as the identity mechanism: password entropy makes the public identity itself dictionary-attackable in structure and couples identity survival to a credential the user reuses and resets. Password-derived wrapping of an independent random key (this design, where the passphrase is passphrase-strength rather than password-strength) keeps the usable part and drops the coupling.
3. **Authorizer holds the key "temporarily" during login (upload-to-sign).** Rejected: that is variant (a) with extra steps — the service possesses the key in usable form and the honesty statement becomes variant (a)'s. Variant (b) exists precisely for users who choose otherwise.
4. **Device-local storage only (no blob portability).** Rejected: first lost phone is total identity loss for exactly the non-technical users the parent centres; portability of ciphertext is what makes (b) survivable.
5. **Drive-only, no file backup.** Rejected: it makes a third party's account-standing decision (Google closing an account) a single point of identity death, contradicting §5's "login loss is not identity loss" property.

## §8 The parent's variant-(b) open question, answered

*"Is Google Drive an acceptable key home for non-technical users, or does file-based custody fail the simplicity requirement?"* — **Drive as the default home passes, file-only custody would fail.** The distinction this design draws is *storage vs handling*: the user never handles a file, a key, or an export in the default flow — they sign in with the Google account they already have and type one passphrase; the blob's Drive residence is invisible plumbing over ciphertext. The file copy is a backup affordance, explained in one sentence, never a step the user must understand to proceed. What would fail simplicity is making the user the transport (carrying files between devices as the normal path); §4.3 makes the file a fallback, not the path. This answers the question at the design level; the implementation follow-on (§10) should still put the setup flow in front of non-technical testers, because the remaining risk is wording, not architecture.

## §9 Invariants implementation must hold

1. The private key exists in plaintext only in client memory, only between unlock and lock; it is never persisted, logged, transmitted, or rendered.
2. Every server-side store holds at most: public keys, setup artefacts, delegation records, and blob ciphertext. Any design or code change that would put a decryptable key or a passphrase on a server is a variant change, not an implementation detail, and goes back to design.
3. Delegations are issued only against a signature verified against the setup artefact; there is no admin or support path that mints one.
4. Blob format, KDF parameters, and wrap versions are explicit in the blob; clients refuse blobs whose parameters fall below the floor in force, and refuse wrap-version rollback.
5. The two unrecoverable states in §5 are reachable only through user-visible setup choices whose consequences were stated at choice time; no silent path leads there.
6. Passphrase change, key rotation (#2804), and login-password reset are three distinct operations in code and in copy, and none is ever labelled as another.

## §10 Follow-ons (named, not filed here)

- **Blob format + client unlock implementation:** the §2 format as code in `pkgs/id`, KDF parameter selection measured on target devices, lock-on-idle and memory hygiene, with property tests naming their oracle (wrap/unwrap round-trip; tampered-ciphertext refusal; parameter-floor refusal).
- **Setup / new-device UX implementation:** §4 flows against the §8 wording risk, including the §5 informed-choice screens, validated with non-technical testers before the flow ships.

Both are implementation of this decision, sequenced after the parent #5684 design set (variants (a), (c), (d) and the management UX) is complete, since §4.3 and §5 deliberately lean on (c) and (d).
