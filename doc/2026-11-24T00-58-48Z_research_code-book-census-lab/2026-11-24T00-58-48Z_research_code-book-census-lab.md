### 2.2 The TALM per-node disk answer — the one fully proven piece (PROVEN as design + local flow)

Drew's open design question — _how do you declaratively configure, in Talos/TALM, a bunch of hard drives that are all different per machine?_ — is **answered and closed**: [#1812](https://github.com/developing-today/code/issues/1812), landed as `infra/cluster/README.md` (+ worked examples `infra/cluster/examples/node-file.yaml`, `user-volume.yaml`) via PR #5052. The answer, in brief:

- One TALM node file per node in git (`infra/cluster/<cluster>/nodes/<hostname>.yaml`); `talm template -i` against a node booted in Talos maintenance mode harvests its real hardware into that file as comments; anything below the file's modeline is a strategic merge patch over the shared cluster template at `talm apply` time. A non-empty body pins the file to exactly one node — a disk patch can never leak onto the wrong machine.
- Match disks by **identity, not description**: boot disk via `machine.install.diskSelector` on `serial`/`wwid` (never size/model alone — a replacement drive must fail loudly, not silently match a sibling); data volumes via Talos ≥v1.10 `UserVolumeConfig` CEL selectors with the load-bearing `!system_disk` guard. `machine.disks[]` is deprecated in v1.10 — do not build on it.
- Runbook included: adding a node, replacing a disk (a boot-disk swap is a rebuild of that node from config, by design), and wiping/rebuilding a node from config only ("the node rejoins the cluster from git alone").
- **Local container-flow proof recorded:** `talm template -i` harvest, hand-edit of disk fields only, `talm apply --dry-run` showing the resolved install disk, `talm apply` — observed in Drew's local container runs and verified in triage task 7746 on #1812 (2026-11-03). What it does **not** prove: real drive-swap behaviour or the rebuild drill on physical nodes — gated on [#1810](https://github.com/developing-today/code/issues/1810).

### 6.2 The ESP32 platform design (#5783) — designed, decision-ready

`doc/2026-11-09_design_id5783.md` — "Design: ESP32 hardware platform line — boards, provisioning, firmware lifecycle, OTA, power". Status in the record: **decision-ready proposal — design only; no firmware is implemented here.** Issue [#5783](https://github.com/developing-today/code/issues/5783) open, under ID epic [#2056](https://github.com/developing-today/code/issues/2056). Its decisions:

- **Board:** one reference board (ESP32-S3 devkit-class) + a written compatibility envelope (Wi-Fi, ≥16 MB flash, PSRAM, hardware RNG, USB flashing without an external UART bridge) — **no supported family in v1**. Rejected as reference: ESP32 classic (no native USB, thinnest RAM margin; eligible later in a WROVER/PSRAM variant), ESP32-C3/C6 (RAM too tight for the TLS + frame budget; named revisit), ESP32-S2 (single core, no BLE).
- **Identity (the long-term ID tie-in, §6.5):** device-owned keypair generated on-device at first boot; enrolment binds it through the [#5884](https://github.com/developing-today/code/issues/5884) setup ceremony; factory reset **destroys** the key and re-enrols as a _new_ device; a stolen device yields only its own key, expiry-bounded cached grants and its journal — never user keys.
- **Lifecycle:** Nix-flake reproducible builds in CI, offline-signed images, A/B partitions with automatic rollback to last-good, OTA fetched over **HTTPS** (never inside MQTT frames), checksummed journal ring across reconnects.
- **Firmware language:** Rust on esp-idf, sharing the workspace's wire-bounds constants and manifest schema types with the bridge so the 64 KiB / 8 KiB limits are one definition. C/Arduino and bare-metal esp-hal + embassy-net both rejected for v1 (embassy-net with a named revisit).
- **Power:** v1 reference build is mains-powered ("Drew's bench"); battery is a budgeted envelope, **not a tested claim** — invariant I-10 forbids shipping a battery-life number without a measured profile on the reference board. Wake-storm avoidance is a fleet property (jittered, per-device-seeded backoff on the bridge's 1 Hz `time.tick` floor).
- **Field posture:** fail-closed, distrust power/network/broker/time in that order; the device is never a time authority (bridge assigns ingest time); bounded store-and-forward with explicit gap signalling; never clicks through captive portals.

| Radio coprocessor      | ESP32-C6 module (WiFi 6, BLE 5.3, IEEE 802.15.4) over ESP-Hosted (SDIO)                                  |
| Management coprocessor | WCH CH32V203 (keyboard matrix + power management, I2C peripheral to the P4)                              |
| Display                | 3.97″ 800×480 MIPI-DSI (ST7701S)                                                                         |
| Input                  | 69-key QWERTY keyboard (no touchscreen)                                                                  |
| Extras                 | LoRa module (Ai-Thinker Ra-01S/SH, 433 or 868/915 MHz) on the C6 side; microSD slot                      |
| Licensing              | Software MIT; hardware CERN-OHL-P-2.0                                                                    |

The app system the tier adopts from it: the **tanmatsu-launcher** + **AppFS** (badge.team) — an app is a standard, unmodified ESP-IDF binary with slug/title/version metadata in an 8 MB AppFS partition; apps arrive via the on-device Hatchery store, BadgeLink over USB (also the provisioning route), host-side image tools (apps embedded in the firmware image at build time), or as the main firmware itself (kiosk boot). Adopted shapes: presenter-as-an-app, slug-keyed data, BSP-shaped hardware access, a host management protocol. **One honest gap recorded in the research:** stock AppFS bootloader support covers ESP32, ESP32-C6 and ESP32-P4 — **not yet the ESP32-S3**, this tier's first target; adopting AppFS literally on the S3 presenter waits on an upstream bootloader port, while on P4-class hardware it works today. A hardware-doc device family for Nicolai Electronics exists (`doc/hardware/devices/nicolai-electronics/`).
