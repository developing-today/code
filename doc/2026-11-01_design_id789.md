# Design: Phase 13 F13.7 client-side capability providers

- Date: 2026-11-01
- Status: **decision-ready design** — implementation remains gated on the
  provider registry, structured audit, client-session attribution, and restart
  semantics below. Nothing in this note implements a provider.
- Issue: [#789](https://github.com/developing-today/code/issues/789), F13.7.
- Code baseline: this checkout after merging `origin/main` at `a9e976ac2`.
- This is a current refinement of the design-only record in
  `doc/2026-10-25T05-37-57Z_design_client_capability_providers/`. It preserves
  its brokered protocol and bounded `client.file.read` first slice, and makes
  explicit the newer registry, audit, session-attribution, restart, and
  capability-taxonomy decisions.

## 1. Decision to make

F13.7 must let a world program request a resource held by a client without
giving the guest a new authority path or letting a host reach a user's device
without that user's consent. The decisions are:

1. Where client providers are declared, authorized, executed, and audited.
2. What the world administrator controls versus what the local client user
   controls.
3. How requests are tied to the session that caused them and remain bounded,
   auditable, and deterministic across timeout, disconnect, and world reopen.

**Recommendation:** declare a provider in the F12.4 registry as `side: client`;
keep authorization, ceiling checks, routing, correlation, and host audit in a
host-owned broker; execute only in the shell adapter that holds the resource.
The world grant and ceiling are a server policy gate on what a guest may ask
for. The client user is the sole authority that opts the shell into accessing
its local resource. Both checks must pass, and either side can stop future
access. The guest keeps the existing `wants`/result protocol and receives no
Wasm import.

The first provider is read-only `client.file.read`, disabled by default,
restricted to a user-selected root, and bounded by the manifest, world policy,
and local client policy. GPU buffers and native notifications are deferred.

## 2. Context and evidence

### Issue requirements

The issue requests local-resource providers under the Phase 12 named-provider
and ceiling rule. The guest requests through the existing capability protocol;
the result is a bounded capability reply, not a new host-authority path. Its
acceptance criteria require a provider that does not edit the host `CATALOG`,
works under a ceiling and is refused outside it, leaves an audit entry, adds no
Wasm import, and answers who grants it (issue #789 body).

The issue's older “not started” status and its initial prerequisite reference
to umbrella #534 have been refined by later records. The latest Nov 1 triages
keep F12.4 registry issue #1061 open and gated by the default-ceiling fix #838;
F12.6 audit issue #1063 is also open. Phase 14 sequences registry before audit
and audit before #789 (`.opencode/plans/phase-14-close-out.md:94-96,148-170`).
The F11.7 foundation #553 is now closed (latest #1063 triage), not an additional
open F12.6 blocker.

### Current code facts

- `pkgs/id/src/world_caps.rs:1-24,69-90` defines the guest's `wants`/result
  capability protocol and the static host `CATALOG`. The issue's request to add
  a provider without changing this list depends on F12.4's registry seam.
- `pkgs/id/src/world/actor.rs:618-661` asks the host ledger for a decision and
  then executes providers through a string `match`. The actor currently owns
  provider execution; there is no client-side dispatch path.
- `pkgs/id/src/world_caps.rs:507-569` says every catalog name is allowed until
  a ceiling narrows it, then checks the ceiling, actor scope, and grant. A
  registry addition must not inherit that broad default. Issue #838 and the
  latest #1061 triage make per-provider `default_ceiling: excluded` a hard
  prerequisite, not an optional F13.7 preference.
- `pkgs/id/src/sandbox.rs:1-11` defines the guest ABI and states that the guest
  receives no imports, including no filesystem, sockets, clock, or random
  source. F13.7 must preserve that property.
- `pkgs/id/src/world_session/types.rs:78-266,272-386` contains the current
  `ClientFrame` and `ServerFrame` types; there is no provider offer/request/
  reply negotiation today. The shell contract v1 reserves client providers.
- `pkgs/id/src/world/actor.rs:100-104` shows `WorldCommand::Input` carries a
  capability token and bytes but no session identity. The actor therefore
  cannot route a provider request to the originating connection. Issue #840
  remains open for this ephemeral session ID and a two-connection test.
- `pkgs/id/src/world/actor.rs:442-497` keeps `handled_requests` in actor memory
  and executes newly observed requests from `wants`. Issue #839 remains open
  because a reopen can re-run a request without its original actor/session.
- `pkgs/id/src/world_caps.rs:310-329,343-375` already defines a stable
  `result_too_large` code and a final serialized-event size guard; it landed in
  #837 / PR #3786. F13.7 should reuse it as a last guard, while rejecting
  provider replies that exceed their own bounds before delivery.
- `pkgs/id/src/world/actor.rs:425-437` journals a result only after the guest
  accepts it as a `System` event. The capability module documents that these
  events are replayed into the guest (`world_caps.rs:1-7`). Therefore a
  successful file read's returned bytes become durable world history under the
  current replay model; the client operation itself must never be replayed.
- `pkgs/id/src/world_caps.rs:471-489` has per-capability allowed/denied usage
  counters, not a structured audit record. F12.6 supplies the host audit
  contract; Phase 14 explicitly limits that work to the host side and says
  F13.7 consumes it (`.opencode/plans/phase-14-close-out.md:94-96,108`).

### Prior decisions and the current conflict

The Oct 25 F13.7 design already chose a manifest `side: client`, the
`client.` namespace, an excluded default ceiling, a host broker, routing only to
the actor's originating session, ephemeral pending requests, replay of accepted
results, and `client.file.read` as the first provider
(`doc/2026-10-25T05-37-57Z_design_client_capability_providers/2026-10-25T05-37-57Z_design_client_capability_providers.md:76-121,139-155,163-193,249-309`).
It described both the world and client as grantors (`:123-161`).

The newer Oct 29 capability taxonomy is explicitly “v0, investigation only”
and says each new capability should name one grant authority; capabilities
needing two should be split (`doc/2026-10-29T14-05-00Z_investigation_capability_taxonomy/2026-10-29T14-05-00Z_investigation_capability_taxonomy.md:1-5,48-66`). It does
not explicitly supersede F13.7, but it makes the older “two grantors” wording
ambiguous. This note resolves that terminology: **the local user grants local
resource access; the world grant/ceiling is a separate host policy gate, not a
grant of device authority.** The policy gate still prevents a guest from
requesting a provider that the world owner did not enable.

F13.7's shell-frame path remains subject to the Phase 13 rule that a new frame
kind waits for F11.12 (`.opencode/plans/phase-13-client-shells.md:125`). The
narrower rollback/header work tracked by #227 is closed via #1353, but the
latest #841 reconciliation still lists the broader F11.12 journal-management
work as planned. Do not treat #227's closure as permission to skip that frame
compatibility gate.

## 3. Viable options and trade-offs

### Provider execution and routing

| Option | Benefits | Costs / failure mode | Decision |
| --- | --- | --- | --- |
| Add client resources to the host executor and `CATALOG`/string `match` | Reuses the current actor path and needs no shell protocol | The host does not hold the local resource; it violates the issue's no-`CATALOG`-edit criterion and gives the wrong machine authority | Reject |
| Add a guest Wasm import or a direct guest-to-client channel | Direct-looking request path | A new guest import violates `sandbox.rs:1-11`; a bypass channel could skip host scopes, ceilings, and audit | Reject |
| Register `side: client` and broker over the shell session protocol | Keeps the guest ABI stable; host remains the policy/audit point; client remains the resource authority; fake and real shell adapters share one seam | Needs additive shell frames, a correlated pending-request state machine, and session attribution | **Recommend** |

Use additive, versioned shell-session frames for a provider offer, a host
request, and a client reply. Do not add a new guest `wants` schema or Wasm
import. A v1 shell never advertises providers and never receives these frames.
The host matches replies to an opaque host-minted nonce and the input-derived
session ID from #840; a frame-supplied participant/session claim is not trusted.

### Granting and local authority

| Option | Trade-offs | Decision |
| --- | --- | --- |
| World/admin grants alone | Allows the host operator to cause access to a participant's device without the user's local opt-in | Reject |
| Client user grants alone | Lets any world the user joins ask for the local resource even when that world has not enabled the named provider | Reject |
| Client user grants local access; host world grant/ceiling gates guest requests | Preserves local user control and gives the world owner a refusal gate without claiming the world owner can grant device authority | **Recommend; ask Drew to confirm the refinement in §9** |

This is two required checks but one authority over the local file: the local
user. Grant-on-use must never grant a client provider. The host checks the
manifest, server/world ceiling, world grant, and actor scope; the shell checks
its own local opt-in, root, bounds, and rate limit on every request, even if the
host says it is allowed. Either check can refuse; neither can override the
other.

## 4. Recommended module and protocol

### Seam and responsibilities

The host-owned **client-provider broker** is the module at the seam. Its small
interface is the versioned provider manifest plus offer/request/reply messages;
its implementation hides policy ordering, nonce/deadline tracking, audit
correlation, and delivery of the bounded result into the existing guest
protocol. It never opens a client resource.

Each shell supplies an **adapter** that satisfies that interface for resources
it can safely expose. The adapter independently enforces local consent and
bounds. A fake adapter is the test implementation; a terminal/native adapter
is the first production implementation. A browser shell advertises the
provider only when it has a safe user-selected file handle; absence of that
adapter means “unavailable,” never a weaker fallback. This is a real seam
because test and production adapters differ, not an extra public interface for
each provider.

### Manifest and default

The registry entry uses the F12.4 fields (name, version, argument schema,
bounds, required scope, default ceiling) plus `side: client`. Names use a
reserved `client.` prefix, and `side` is authoritative. A client provider has
no host executor. Its default ceiling is `excluded`; the registry must not
silently add it to existing server or world ceilings when the binary changes.
An administrator must explicitly admit it to the world ceiling and grant the
named provider. The local client user's setting is separately off by default.

Illustrative manifest for the first slice (the exact F12.4 encoding remains
owned by #1061):

```json
{
  "name": "client.file.read",
  "version": "1",
  "side": "client",
  "args": { "path": "relative string", "max_bytes": "optional u32" },
  "bounds": { "max_bytes": 32768, "per_minute": 10, "in_flight": 2 },
  "required_scope": "input",
  "default_ceiling": "excluded"
}
```

The 32 KiB result, ten reads/minute, and two in-flight requests carry forward
the Oct 25 design's starting limits, not claims that F12.4 has already frozen
these exact values (`doc/2026-10-25T05-37-57Z_design_client_capability_providers/2026-10-25T05-37-57Z_design_client_capability_providers.md:88-98,277-293`).
All ceilings compose by minimum: manifest bound ∧ world bound ∧ client-local
bound. Refuse over-bound requests and replies; never silently truncate.

### Request, reply, journal, and audit flow

1. The guest lists a new `{id, cap, args}` request in `wants`, as it does for
   host capabilities (`world_caps.rs:9-20`).
2. The actor evaluates the host policy in order: known manifest, server/world
   ceiling, actor scope, explicit world grant, then provider/session
   availability. Over-ceiling requests are refused before any client frame is
   sent, and F12.6 records the refusal.
3. For an allowed request, the broker binds the pending entry to the actor,
   participant, ephemeral session ID, guest request ID, host-minted nonce,
   effective bounds, and deadline. It sends only the necessary bounded request
   to that session.
4. The shell rechecks its local user grant and bounds, resolves the relative
   path beneath the user-selected root without symlink escape, reads at most
   the effective byte limit, and returns either bounded bytes or a stable
   refusal. A host “allow” cannot bypass this local check.
5. The broker accepts only one reply for the nonce from the bound session,
   validates the result against the manifest, audits the outcome, and feeds
   the ordinary capability result event to the guest. Unknown, duplicate,
   wrong-session, expired, revoked, and oversized replies fail closed.
6. The accepted result is journaled as the existing `System` event and replay
   never contacts a shell. The pending request, nonce, session offer, and local
   opt-in remain ephemeral. After a reopen, a still-listed request with no
   acting input is refused (`actor_denied`, reason `restarted`) rather than
   routed to an arbitrary session; this is the recommendation from the F13.7
   record and the unresolved semantics tracked by #839.

The host F12.6 record is the required world audit trail for allowed and refused
provider use, including ceiling denials. It records provider/version, world,
actor, action/outcome, correlation ID, and an arguments digest—not raw file
content, absolute local path, or credentials (Phase 14
`.opencode/plans/phase-14-close-out.md:94-96,108`). The latest #1063 slice
description does not yet promise provider version or a correlation ID; F13.7
must request those fields from the F12.6 design so a timed-out or client-side
refusal can be matched to its host decision. A separate user-readable
client-local audit entry records that the local adapter read or refused a
resource; it is not presented as an F12.6 host log, because F14.21 is explicitly
host-side. A final serialized-result overflow reuses `result_too_large` as a
last-resort guard (`world_caps.rs:310-329,360-375`).

### Durability disclosure

`client.file.read` returns data that the guest consumes. Under the existing
replay model that result is durable world history, not a transient local read;
the host/operator and anyone with journal access can later see the returned
data. The user must be told this before opting in, and must choose the root
knowing the result leaves the device. Do not claim that the local root alone
keeps contents private from the world. A digest-only or non-journaled data path
would change replay semantics and belongs with the F12.13 journal-replication
design, not as an unreviewed exception in F13.7.

## 5. Invariants

1. **Named and manifested:** no client operation exists outside a versioned
   registry entry; `side: client` entries have no host executor.
2. **Default denied:** a new provider is excluded from server and world
   ceilings by default. Registry growth cannot widen existing worlds.
3. **Separate policy and local authority:** the world grant/ceiling and actor
   scope gate what a guest may request; only the client user grants local
   resource access. Both gates are required; neither can widen the other.
4. **No guest authority expansion:** no Wasm imports or guest ABI change; the
   existing `wants` request and bounded result event remain the guest surface.
5. **Session-bound:** a request is routed only to the connection that caused
   the input; no request is routed by a guest-selected or reply-selected
   participant/session ID.
6. **Bounded and fail-closed:** arguments, path, bytes, request rate, in-flight
   count, deadline, and reply size are checked at host and client; timeout,
   disconnect, revocation, replay, and bad correlation never cause fallback to
   another client or host execution.
7. **Auditable:** every host allow/deny/completion/timeout has a structured
   F12.6 record. Client-side enforcement is separately visible to the local
   user. Audit contains no file content or raw absolute path.
8. **Replay-safe:** only the result event the guest accepted is journaled.
   Replay consumes that event and never repeats local I/O. Unattributed
   post-reopen requests are refused until a new input supplies an actor/session.
9. **Version-safe:** old shell sessions do not advertise or receive provider
   frames; new frame kinds wait for F11.12 per the Phase 13 plan.
10. **Explicit data transfer:** local opt-in explains that returned bytes enter
    the world program and its durable journal; a user can revoke future reads
    immediately.

## 6. Acceptance criteria for implementation

These extend, rather than replace, the acceptance criteria in #789:

- **Registry / no host catalog edit:** a `side: client` manifest is added via
  F12.4 without editing `CATALOG` or the actor's provider `match`; existing
  host provider names, bounds, refusals, and behavior remain unchanged.
- **Default ceiling:** a newly registered client provider is absent from
  default server/world ceilings; a test proves registry addition does not
  widen an existing world. Explicitly configured ceiling and grant permit
  requesting it; excluding it refuses before dispatch.
- **Two-gate authorization:** tests cover world denied/client allowed,
  world allowed/client denied, both allowed, and revocation at either side.
  Client providers never use grant-on-use.
- **Attribution:** two connected sessions issue input; only the originating
  session receives the request. The session ID is opaque and ephemeral, is not
  journaled, and is threaded through `WorldCommand::Input` via #840.
- **First provider safety:** `client.file.read` accepts only paths beneath a
  user-selected root, refuses absolute/parent traversal and symlink escape,
  returns at most the effective byte limit, and does not silently truncate.
  Clients without a safe adapter report unavailable.
- **Error and bound behavior:** wrong args, ceiling denial, missing grant/scope,
  local refusal, unavailable provider, timeout, stale/duplicate/wrong-session
  reply, and oversized result have stable documented outcomes. A serialized
  overflow uses `result_too_large` only as the final guard.
- **Audit:** the host F12.6 sink records every attempted provider use,
  including an over-ceiling denial, without file contents or raw absolute
  paths. The client records local execution/refusal in its own local audit
  store.
- **Replay/reopen:** replay of an accepted result reaches the same guest state
  with no client connected and no new read. Reopen does not silently re-run a
  pending request without actor/session attribution; pin the chosen #839
  semantics with a test.
- **Protocol compatibility:** a v1 shell never receives provider frames; v2
  offers only locally opted-in providers for that world. New frame kinds are
  introduced only after the F11.12 gate.
- **No imports / explicit consent:** guest module import checks still pass;
  the client opt-in states that returned bytes become journaled world data.
- **Grant decision recorded:** implementation docs and tests state that the
  client user grants local access while world policy is a separate required
  gate, resolving #789's “who grants” criterion.

## 7. Phased implementation plan

Each F13.7 slice is separately mergeable behind an excluded-by-default
provider. The prerequisites below are existing issues and are not implementation
work in this design PR.

### Gates before client-provider execution

1. **Ceiling safety, then registry:** land #838 first; then complete F12.4 /
   #1061 with a per-provider default that supports `excluded`, and prove that
   registry additions do not widen existing ceilings.
2. **Structured audit:** complete F12.6 / #1063 on top of the F12.4 registry
   and F14.9 metrics foundation. Its host-side record must cover provider
   allow, deny, and completion, with provider version and an opaque correlation
   ID for client requests; client-local enforcement stays a separate log.
3. **Attribution and restart:** complete #840's ephemeral session ID and
   two-connection test. Resolve #839 and pin refusal of unattributed
   re-execution after reopen, unless Drew chooses the alternative in §9.
4. **Frame compatibility:** complete the broader F11.12 gate before introducing
   additive provider frame kinds. #227's narrower rollback-header change is
   already closed; it does not close the full F11.12 requirement.

### Independently mergeable F13.7 slices

| Step | Deliverable and done check | Depends on |
| --- | --- | --- |
| **1. Provider contract and registry shape** | Add client-side manifest semantics (`side`, namespace, schema/bounds, excluded default) to the F12.4 registry contract and conformance fixtures. No runtime client requests; existing host catalog behavior is byte-for-byte/behaviorally unchanged. | Gates 1-2; registry is owned by #1061 |
| **2. Session protocol v2 types** | Add offer/request/reply frame types and shell-contract conformance rules. A v1 shell is unchanged and cannot receive the new frames. Land types/tests without enabling any provider. | Gate 4; shell contract F13.1 |
| **3. Host broker with fake adapter** | Add a host-owned broker behind the manifest seam: policy checks, session-bound nonce/deadline, reply validation, host audit, and delivery through the existing result event. Fake-adapter tests cover refusal, timeout, disconnect, replay, and malformed replies. | Gates 1-4; Step 2 |
| **4. Client grant and local audit adapter** | Add per-world local opt-in, local bounds, immediate revoke, and a local audit entry in the first supported shell. No provider is enabled by default; a malicious host request still meets the local check. | Step 3 |
| **5. `client.file.read` adapter** | Implement only bounded read-only access under a user-selected root. Enforce safe path resolution, effective minimum bounds, and content/journal disclosure. Register it as excluded until both host and local policy enable it. | Step 4; explicit Drew decision on durable returned content |
| **6. End-to-end hardening and rollout** | Run the acceptance matrix across a real shell and fake adapter; test two clients, both revocations, audit replay, journal replay, and restart. Document how to opt in and how to revoke; keep GPU and notification providers out of this slice. | Steps 1-5; #839 decision |

These are mergeable in order because contract-only and broker-only changes have
no active client provider, and `client.file.read` remains excluded unless both
policy gates and local consent are present. The plan does not file or implement
the upstream prerequisite issues.

## 8. Non-goals

- No host-side filesystem access, new host capability, or edit to the guest
  Wasm ABI.
- No GPU buffer or notification provider in the first slice; they need
  different handle/side-effect and rate-limit models.
- No routing to a different participant's client, another world, or a
  non-originating session. Multi-session selection belongs to F13.8.
- No raw provider payload in the host audit log.
- No digest-only or non-replayable result exception to the existing journal
  model in F13.7.

## 9. Questions for Drew

These do not block this design record. The recommendations are the safe defaults
for implementation; the corresponding slices should not make an irreversible
choice until Drew answers or explicitly accepts the recommendation.

1. **Authority wording / taxonomy.** Should F13.7 keep two required checks but
   define the local client user as the *only grant authority over the device*,
   with the world/admin grant and ceiling as a host policy gate? Options:
   (A) keep the Oct 25 wording that both world and client “grant” the provider;
   (B) follow the Oct 29 taxonomy literally and split the capability into
   separate names; (C) adopt the recommended one-local-authority/two-gates
   model. **Recommend C**: it preserves the security goals of the older design
   while removing the taxonomy's ambiguity and still lets the world owner
   refuse guest requests.
2. **Durability of file-read results.** Is it acceptable that accepted bytes
   enter the guest result event and become journaled world history, provided
   local opt-in clearly warns the user? Options: (A) accept the existing
   deterministic replay model and disclose it; (B) require digest-only or
   non-journaled results, which needs a separate replay/data-model design; or
   (C) remove `client.file.read` from the first slice. **Recommend A** for
   F13.7, with B deferred to F12.13 if the durability model changes.
3. **Unattributed work after reopen (#839).** Should a request still present
   in `wants` after restart be refused until new participant input, or replayed
   at least once? Options: (A) refuse with `actor_denied` / `restarted`; (B)
   journal handled IDs for durable idempotency; or (C) intentionally re-run
   at least once. **Recommend A**: it is fail-closed, avoids attributing a
   device read to nobody, and adds no new journal state. This remains a
   separate #839 decision and test.
