# Design: ID currencies v1

- Date: 2026-11-01
- Status: **design recommendation, with Drew's 2026-11-08 policy rulings folded in** (2026-11-11, [#8576](https://github.com/developing-today/code/issues/8576)) — no implementation code is included in this PR. The six policy questions the original draft left open are decided in the Decisions section below; they are not open questions.
- Issue: [#2043 — ID currencies v1](https://github.com/developing-today/code/issues/2043), parent epic #2056.
- Evidence baseline: this branch after merging `origin/main`; implementation citations below refer to `pkgs/id` at this checkout.

## The decision

Choose one v1 model that reconciles graph-native tokens, real-service grants, and TigerBeetle settlement without pretending they provide the same guarantees:

1. A currency is a signed graph definition whose stable identity is `(issuer public key, definition event/hash)`. Name and symbol are labels, not identity.
2. Each definition selects exactly one binding: **graph-native** (offline, peer-to-peer, fold-derived balances) or **ledger-anchored** (online, gateway-mediated, TigerBeetle balance truth).
3. The graph is the authorization and audit record for anchored operations; the control plane is a rebuildable operational index; TigerBeetle is the balance authority. Graph-native transfers remain claims whose conflicts/double-spends can be detected but not prevented offline.
4. Real-service purchases use the #2042 pending-hold lifecycle and only anchored currencies. A payment receipt records an effect; it is never itself a balance movement.
5. Anchored conversions use one signed, directional `currency.rate_authorisation`, a short-lived event-pinned quote, and one atomically linked TigerBeetle batch. A posted conversion is corrected by a new compensating conversion, never edited.

This follows #2043’s requested synthesis of #2040–#2042 and its four explicit topics (token model, ledger boundary, conversion authorization, and open-source boundary). It also carries forward later decisions rather than treating the earlier graph-token wire format as the newest word: #2741 is the merged snapshot/fold spec, while the newer #2290 record recommends the canonical `currency.rate_authorisation` event and #2063’s latest summary adopts that direction. Their PRs #3831 and #3844 merged on 2026-11-02, so the two vocabularies are settled for implementation. Drew ruled on this design's six policy questions on 2026-11-08 ([#2043 comment 6721988851](https://github.com/developing-today/code/issues/2043#issuecomment-6721988851)); the Decisions section states them and the sections below are reconciled with them. The staged extension of these contracts across the #5676 backends (Redis, multi-Turso, TigerBeetle) is recorded in `doc/2026-11-05_design_id5828.md` (#5828). The load & correctness verification programme those stages must pass — property tests, crash injection, and per-stage performance envelopes — is recorded in `doc/2026-11-08_design_id5829.md` (#5829).

## Context and current footing

### From the issues and prior designs

- #2043 asks for a currencies-v1 synthesis of TigerBeetle mechanics (#2040), issuance in the ID graph (#2041), and real-service grant lifecycle (#2042). Its issue body says the token's public name is TBD (id bucks, d3v, dt, 2d, d2d) and that most software is intended to be open source; both are since decided (Decisions Q1 and Q6): the neutral label is “units”, naming three currencies — units, pending units, revoked units — and all correctness-critical code is open.
- #2041 distinguishes semantic currency identity `(issuer, definition object)` from registry `currency_id` and TigerBeetle `ledger`; it defines graph-native and ledger-anchored bindings and says the latter keeps balances in TigerBeetle while graph events authorize and audit writes (`doc/2026-10-30T19-18-00Z_investigation_token_issuance_id_graph/2026-10-30T19-18-00Z_investigation_token_issuance_id_graph.md:73-102, 132-164`).
- #2040 establishes that TigerBeetle has no cross-ledger transfer, no authentication, and no native rate object. A conversion is an application-composed linked transfer chain through a liquidity provider; the application computes the rate and stores the association itself (`doc/2026-10-28T23-34-15Z_investigation_tigerbeetle_currency_backend/2026-10-28T23-34-15Z_investigation_tigerbeetle_currency_backend.md:110-124, 130-179`).
- #2042’s later lifecycle design makes purchase grants pending TigerBeetle holds, unspendable until the refund window closes; it attaches clawback debt to the grantee, never third-party holders, and treats delisting as separate from revocation (`doc/2026-10-30T11-55-00Z_design_grant_lifecycle.md:7-26, 141-172, 198-200`). It explicitly leaves operator/Drew parameters open in §9.
- #2741 defines graph event shapes, deterministic folds, snapshots and anchored reconciliation. It calls receipts non-monetary, and snapshots checkable assertions rather than trust roots (`doc/2026-10-30T13-25-00Z_design_graph_token_formats_snapshot_anchoring.md:150-204, 206-350, 419-482`). Its `token.offer` is superseded as the preferred authorization name by the newer #2290 record; do not implement two canonical offer objects.
- #2062/#2066 put registration, accounts, authorization and the gateway in one currency service; other ID identity, graph, content and messaging remain peer-to-peer or serverless. The currency-service outage stops currency operations, not the rest of ID (#2066 §§1–2; #2062 §§0, 4).

### Evidence in `pkgs/id`

There is no existing monetary ledger to extend. The similarly named `CapLedger` records allowed/denied capability uses and grant policy, not fungible balances or transfers (`pkgs/id/src/world_caps.rs:471-503, 506-570`). `JoinCapability` is a bearer access secret (`pkgs/id/src/world/mod.rs:281-303`), while web identity tokens are signed client identity payloads with a 30-day age limit (`pkgs/id/src/web/identity.rs:65-104, 324-385`). Currency balances and payment authorization must be a separate domain, not a reinterpretation of either token.

The codebase does provide useful seams and precedents, not a currency implementation: `chain::sign` creates author-chained signed events whose body is committed by the header (`pkgs/id/src/chain.rs:259-309`); the attestation PoC demonstrates ordinary signed events carrying typed objects and deriving state in a viewer (`pkgs/id/src/attestation.rs:6-24, 31-51`), but explicitly labels itself a PoC. The tag index is local and rebuilt from live claims (`pkgs/id/src/tag_index.rs:11-16, 41-60`). The world checkpoint mechanism is for deterministic program-state recovery, not a balance authority (`pkgs/id/src/world_store.rs:1-22`).

The existing world capability model also illustrates why currency authorization needs its own state: delegations narrow inherited scope and bounds, usage is counted against ancestors, and revocation walks the delegated tree (`pkgs/id/src/world/core.rs:705-783, 811-853, 908-929`). These are access-control semantics, not monetary settlement.

## Options and trade-offs

| Option                                                  | Advantages                                                                                                                                 | Costs / failure mode                                                                                                                                            | Decision                                                               |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| **One graph-only token model for every use**            | Offline, P2P, few moving parts; one event vocabulary.                                                                                      | Cannot prevent offline double-spends; cannot supply TigerBeetle pending holds required by #2042; unsafe to promise real-service redemption as settled value.    | Reject as universal model; retain only as the graph-native binding.    |
| **One TigerBeetle ledger for every token**              | Strong online balances and linked-batch atomicity.                                                                                         | Makes every community token depend on an online service; discards the graph-native offline model; TigerBeetle itself does not carry identity, metadata or auth. | Reject as universal model; retain for redeemable/real-service value.   |
| **Dual binding selected once in the signed definition** | Matches #2040–#2042; preserves P2P claims while making ledger-backed promises enforceable; semantics are explicit to wallets and services. | Two balance-read paths, a reconciliation join, and a strict UX distinction are required.                                                                        | **Recommend.** This is the only option that keeps the promises honest. |
| Treat capabilities/web identity tokens as currency      | Reuses existing token-shaped code.                                                                                                         | They authenticate access/identity; `CapLedger` counts authorization decisions and has in-memory usage, not balances or durable transfers.                       | Reject; introduce closed currency event types and a distinct API.      |

## Recommended model

### 1. Currency identity and definition

- The semantic ID is `(issuer verifying-key identity, definition event ID / canonical definition hash)`. A compact derived hash may be used as a lookup key, but it never replaces the pair as the authority. `currency_id` and TigerBeetle `ledger` are registry/runtime identifiers only.
- A signed definition fixes display name, optional ticker, scale, supply policy, revocation policy, binding, and (where required by the binding) a recovery-key commitment. There is no in-place edit. A changed scale, supply policy, or binding is a new definition and currency identity. Scale is chosen once and treated as immutable.
- V1 graph objects are definition, issue, transfer, burn, directional rate authorization, conversion receipt, payment receipt, issuer-key rotation/recovery, and snapshot. Keep the closed schemas and folds in the graph/client package; do not store bearer secrets or session tokens in these events.
- The latest #2804 design recommends that every issuer currency have a hard supply cap so key compromise has a bounded mint ceiling. For v1 a finite cap is required — decided 2026-11-08 (Decisions Q2) — with the single ruled exception of transfers from the supply account; unbounded `open` supply is not a v1 policy. This narrows #2741's earlier `capped | open` wire choice.

### 2. Binding and ledger boundary

**Graph-native.** Definitions, issuance, transfer and burn are graph events; balances and supply are deterministic folds over applied events and causal ancestry. A folder missing ancestry reports pending, not an inferred balance. A fork or overdraft is retained as signed evidence but does not count. Offline double-spends are detectable, not preventable. Do not promise atomic cross-currency exchange for graph-native tokens in v1: #2063’s newest conversion summary limits the conversion engine to ledger-anchored operation; ordinary graph-native transfers remain supported.

**Ledger-anchored.** Required for developing-today’s purchase grants and currencies redeemable for real services. The graph event is signed authorization/audit evidence; the gateway is the only TigerBeetle client and writer; TigerBeetle is balance truth; registry rows map a definition to operational currency and ledger IDs and are rebuildable from the graph. Every ledger operation is joined to its authorization with a `user_data_128` reference and reconciled in both directions. The currency service is the deliberate centralized exception; it must not become a dependency for unrelated ID activity.

The binding cannot be switched by an application per transaction or changed after value exists. The UI must label graph-native value as offline/claim-based and anchored value as online/ledger-backed; never combine their balances merely because labels match.

### 3. Issuance, transfers, and conversion authorization

**Issuance and transfers.** The issuer alone signs issuance events. Graph-native folds enforce the cap against the event’s causal ancestry. For anchored currency, the gateway validates issuer generation, definition/binding, cap and registry mapping before submitting the ledger transfer; an intent without the corresponding executed transfer changes no anchored balance. The one cap exception is the supply account (Decisions Q2): transfers from the account designated for supplying currency are not blocked by the cap. Whether they count against the cap is one of the ruling's recorded unresolved details, so implementations must record supply-account transfers distinctly either way. Ordinary transfers are signed by their sender. All mutating service calls persist and reuse an idempotency key across retries (#2066 §3).

**Rate authorization.** Adopt the newest #2290/#2063 direction: one `currency.rate_authorisation` signed ID-graph event per direction, not parallel `token.offer` and database authorizations. A versioned event carries issuer/LP identity, source and destination semantic currency IDs, exact integer-rational scale-aware rate, per-conversion bounds, total cap, eligible callers, `not_before`, mandatory expiry, optional fee/reversal terms, and version/supersession semantics. The signed event is canonical; gateway state is a rebuildable projection. The gateway also verifies the signer’s LP tier and account control; signature validity alone does not prove liquidity-provider authority (#2290 latest design record, issue comment 6561009233).

An anchored quote is single-use and short-lived (60 seconds recommended), pinned to the exact authorization event ID/version and amounts. At submission the gateway rechecks revocation, expiry, caller, cap and inventory, then reserves the cap atomically before any ledger write. LPs use explicitly bound, conversion-inventory accounts on both ledgers; ordinary shared liquidity accounts are not silently treated as conversion inventory (#2063 latest summary, issue comment 6561075649). Rates are integer arithmetic only; floor in the liquidity provider’s favour; a non-zero input that rounds to zero is rejected. A reverse direction is a separate authorization.

**Conversion execution and recovery.** Persist the conversion intent, idempotency key and every TigerBeetle transfer ID before submission. Submit the source leg, optional separately named fee leg, and destination leg as one linked batch, all stamped with the same 128-bit `conversion_id`. Either the whole linked batch posts or none does. A recovery scan looks up the same IDs after a lost response; it does not mint new IDs and double-submit a second conversion. TigerBeetle linkage is not persisted by the ledger, so the control-plane record and receipt preserve the complete mapping (#2040; #2063 §4–5; #2063 latest summary, issue comment 6561075649).

Posted transfers are immutable. A refund/reversal is a separately authorized compensating conversion, referencing the original; it is not deletion or an assumed seizure of units already moved. Graph-native multi-token conversion is out of v1 rather than a weaker pseudo-atomic implementation.

### 4. Receipts and real-service grants

- `token.receipt` records `{payment event, effect reference}` after the accepting service takes its effect. It has no amount, currency, destination, or fold impact; receipt creation cannot duplicate a payment. The exact schema and non-monetary behavior are already in #2741 §§1.8 and 2.
- A purchase grant is a separate service lifecycle: pending TigerBeetle hold, not spendable during the refund window, then active if no adverse attestation arrives. An adverse event inside the window voids the hold. After activation, only the grantee’s available balance can be clawed back; shortfall becomes an explicit grantee debt. Third-party balances are never seized. Delisting changes service acceptance only and never edits balances (#2042 design §§0–1, 4–6). Pending units are never *spendable*; the 2026-11-08 ruling adds that they are *tradable* between parties who both accept and sign, under the chained option-contract mechanism recorded in Decisions Q5 and on #2296 — trading under contract is not spending, and the mechanism's unclear phrases are not settled design until Drew confirms them on #2296.
- Refund/chargeback attestations, conversion receipts, and payment receipts are distinct record types. An acknowledgement is not a refund; a reversal has its own signed cause and compensating ledger operation. A receipt is emitted only once the corresponding effect is known, with idempotent recovery if the service crashes between ledger and graph writes.
- The grant lifecycle applies only to ledger-backed currencies. A graph-native unit cannot be promised as a refundable purchase grant under the current #2042 design.

### 5. Issuer rotation, snapshots, and folds

**Key rotation.** Adopt #2804’s latest recommendation: a linear per-currency generation chain; routine rotation is an event signed by the current key and countersigned by the successor. Definitions keep stable identity across rotations. Counting views pin the generations and frontiers they count; events after a proven compromise frontier are disputed/excluded rather than silently erased. A compromised mint key cannot authoritatively declare its own compromise, so anchored currencies must precommit a cold recovery-key hash; graph-native currencies may choose the same stronger protection. (Decided 2026-11-08, Decisions Q3: a recovery key is mandatory for ledger-anchored currencies and optional for graph-native ones.) The gateway rejects old-generation writes after it applies the registry update; P2P viewers apply the signed rotation locally (#2804 latest summary, issue comment 6561045617).

**Snapshots.** Keep the #2741 canonical snapshot fields and Merkle-root/reconciliation rules. A snapshot is a signed, frontier-named assertion, not a trust root. Graph-native snapshots are issuer-signed; anchored balance snapshots are signed by a dedicated currency-service identity and include the ledger position and normalized account root. Recommendation: generate a snapshot on demand for high-risk acceptance and after each bounded batch (default 1,000 accounting events or 15 minutes, whichever comes first); tune those limits per deployment. This gives graph-native acceptors a current issuer frontier and anchored operators bounded reconciliation staleness without requiring a shared graph-fold service.

**Fold/index placement.** V1 graph-native folds run in the client/library and use local, rebuildable indexes. Do not introduce a shared currency fold service or a second balance authority in the first release. A read-only hosted projection may be added later as a cache, provided it names its frontier and never decides validity differently from the canonical fold. This follows the P2P contract and fits the existing local rebuilt `TagIndex` pattern (`pkgs/id/src/tag_index.rs:11-16`); it is not an assertion that the tag index already handles currency.

### 6. Open-source boundary

Open-source the complete correctness-critical surface (decided 2026-11-08, Decisions Q6 — open all correctness-critical code): event schemas, graph folds and validators, client/library API, gateway and ledger adapter, currency-service logic, migration/reconciliation tooling, test vectors, and deployment examples. Keep credentials, production keys, customer data, and operator-specific deployment configuration outside the source tree. A hosted currency service can be operated centrally without making its balance rules closed source.

This is consistent with the existing `pkgs/id/Cargo.toml` package license (`MIT OR Apache-2.0`, lines 1–9). The `source_only` world setting is an artifact-ingress policy, not a licensing or product boundary (`pkgs/id/src/world_session/mod.rs:71-83`). The repo currently has no separate proprietary currency module to preserve. No correctness-critical module is excluded; the 2026-11-08 ruling named no exception.

## Invariants and implementation acceptance criteria

The implementation is acceptable only if all of these hold:

1. **Identity:** two same-named currencies from different issuers never collide; definition changes create a new semantic ID; registry and ledger IDs never leak into graph identity.
2. **Definition:** scale/binding are immutable for an identity. Every currency has a finite, explicit issuance cap in v1, with the single ruled exception of transfers from the supply account (Decisions Q2); cap checks are deterministic under causal order and forks.
3. **Binding:** graph-native balances are reproducible folds; unresolved ancestry is pending and double-spends are not described as prevented. Anchored balance reads come from TigerBeetle, not graph intent or a stale cache.
4. **Authorization:** no mint, burn, conversion or ledger write is accepted without a valid signed event, correct issuer generation, caller eligibility, cap, and binding. Old versions/revoked offers cannot revive through stale gateway state.
5. **Exact amounts:** no floating point in money paths; rate and scale normalization have golden vectors, explicit rounding direction, and reject zero-output conversions.
6. **Atomicity/idempotency:** anchored conversion legs are one linked batch; every leg carries the same conversion ID; the write-ahead intent precedes submission; retries reuse intent and ledger IDs; lost responses reconcile without duplicate value.
7. **Reconciliation:** every anchored graph authorization joins to exactly one valid ledger operation (conversions join to a complete leg set); every ledger write has a resolvable graph authorization; mismatches are durable findings, never silently dropped.
8. **Receipts:** payment receipts alter no balance/supply; they identify the payment and effect. Conversion receipts validate the exact authorization, taker intent, amounts, and complete ledger leg set.
9. **Grant safety:** no purchase grant is spendable before its configured refund hold expires; in-window adverse events void pending holds; post-activation clawback never takes from a third party; shortfall/debt is durable and signed.
10. **Rotation:** definitions stay stable; views name pinned generations/frontiers; compromise recovery cannot rely solely on the compromised key; anchored writes stop at the applied generation boundary.
11. **Snapshots:** roots are deterministic and currency-scoped; each snapshot identifies its event frontier and (when anchored) ledger position; a bad join/root is a published reconciliation finding.
12. **Open-source/security:** all correctness-critical code and test vectors are public under the project’s chosen license; keys, bearer tokens, and production secrets never enter graph events, logs, or repository configuration.

### Acceptance tests to require

- Golden vectors for definition identity, scale-aware rate math, floor rounding, zero-output rejection, Merkle roots, and snapshot/frontier verification.
- Fold tests for causal funding, fork resolution, concurrent over-cap issuance, voided overdrafts, burn accounting, and `Pending` when ancestry is incomplete.
- Issuer-generation tests for valid dual-signed rotation, a competing generation fork, compromised-key recovery, pre/post-compromise counting, and anchored gateway cutover.
- Conversion tests for unauthorized/expired/revoked authorization, cap races, insufficient LP inventory, all-or-none linked failure, crash before/after ledger acceptance, and exact-ID retry without duplicate posting.
- Reconciliation tests for missing graph stamp, orphan ledger transfer, incomplete/mismatched conversion leg set, wrong normalized root, and mint-source offset discrepancy.
- Receipt/grant tests for non-monetary receipt folds, effect idempotency, pending-hold void/post race, refund after activation, partial clawback, third-party protection, shortfall/debt, and delisting without balance mutation.
- Acceptance-policy tests demonstrating graph-native risk tiers and online anchored acceptance are not conflated; all unresolved operator values are explicit configuration, not silent constants.

## Phased implementation plan

Each phase is a separately reviewable, mergeable PR with its own tests and feature gate/configuration. Later phases may depend on earlier interfaces, but no partial implementation may advertise a stronger guarantee than it provides. Existing linked follow-ups (#2289, #2290/#3800–#3802, #2804, #2062 and #2042) remain the tracking homes; this design does not duplicate those issues.

1. **Canonical v1 contracts and vectors** (#2251, #3800). Reconcile #2741’s `token.offer` name with #2290’s `currency.rate_authorisation`; settle closed schemas, versioning, issuer generations, receipt/reversal vocabulary, and golden vectors. No runtime behavior changes. Prerequisite to all later phases.
2. **Graph-native currency core** (#2251, #2803). Add definition/issue/transfer/burn/rotation/snapshot types, deterministic fold and client-side rebuilt index; enforce cap/fork/pending rules; keep swaps out of v1. This can ship without the currency service.
3. **Anchored registry and gateway seam** (#2062 F1–F3). Implement registry mapping from semantic definition to `currency_id`/ledger, account factory, single-writer gateway interface, signing/issuer checks, idempotent intents, and two-way reconciliation. Begin with read-only/test adapters; no public purchase flow until reconciliation passes.
4. **Anchored transfer/issuance and snapshots** (#2062 F4–F5, #2298). Implement issuer mint, holder transfer and burn against TigerBeetle, stamps, service-signed snapshots, bounded snapshot cadence and supply-audit/reconciliation reports. Land separately from conversion execution.
5. **Rate authorization and conversion executor** (#3801–#3802, #2289). Implement the #2290 schema/fold and 60-second pinned quotes, then linked-batch execution, durable reservation, write-ahead intent, crash recovery, compensation/reversal, and #2289 PoC validation. Enable conversions only after gateway and reconciliation acceptance criteria pass.
6. **Real-service grant lifecycle and receipts** (#2042, with the Drew decision tracked by #2296). Integrate pending holds, source-specific refund windows, signed adverse attestations, non-monetary payment receipts, effect idempotency, debt/shortfall, and issuer policy snapshots. Ship disabled until the operator parameters in Decisions Q5 are configured; the policy defaults themselves are recorded there.
7. **Client/service UX and OSS release boundary** (#2803). Publish client APIs, identity-aware currency presentation (issuer + name), graph-native risk messaging, anchored online status, local fold/cache behavior, docs and public test vectors. Keep hosted credentials/deployment secrets separate from the open-source implementation.

## Decisions — Drew's rulings (2026-11-08)

Drew ruled on the six policy questions this draft originally posed, in the main chat on 2026-11-08 (recorded verbatim on [#2043, comment 6721988851](https://github.com/developing-today/code/issues/2043#issuecomment-6721988851); ledger item `policy-rulings-2043-six`). They are decisions, not open questions, and the sections above are reconciled with them. Where Drew's modifications carry details his text does not settle, this section says so explicitly — those details are recorded as unresolved on #2043/#2296 and are not adopted as design here.

1. **Public name — units; three currencies.** Ship the neutral label **units** (branding deferred; the name is not part of currency identity). Drew names three currencies: **units**, **pending units**, and **revoked units**. This extends the model above, in which “pending” was a hold state on an anchored currency and revocation an event/policy, not currencies: the representation follow-up (three distinct currency definitions, or named balance classes of one currency) is design work for the implementation phases, to be settled consistently with §1–§4 — the names, and that they are three currencies, are decided.
2. **Supply policy — finite cap, with a supply-account exception.** Every v1 currency has a finite cap, **except transfers from the account for supplying currency**, which the cap does not block. Unresolved in the ruling, recorded verbatim and not settled here: the phrase “named like tiger beetle would be”, and whether supply-account transfers count against the cap. Implementations must record supply-account transfers distinctly (§3) so either settlement remains implementable.
3. **Recovery key — mandatory for ledger-anchored, optional for graph-native.** Confirmed as recommended. Without an independent key, compromise recovery is advisory only (#2804 issue comment 6561045617).
4. **Platform emergency revocation — issuer-only.** Confirmed as recommended: revocation in the graph is issuer-only; a gateway suspension is local and logged, and must not masquerade as an issuer event. This preserves one portable authority (#2290 issue comment 6561009233).
5. **Grant policy — #2296 terms, with pending-unit trading added.** The #2296 base terms stand (14 days for Steam-direct, source-specific publisher terms for retail keys, per-processor chargeback horizons configured never silently defaulted, debt with no expiry and signed public write-off, `for-cause` revocation for the first-party premium currency with issuer-discretion disabled in v1, no default grant expiry, `posting_grace` an explicit operator parameter). Pending units remain never *spendable*. **Modification, as ruled:** pending units may be **traded** when both parties accept/sign, under a chained option-contract mechanism — the originator holds a transfer-cancel option to trade their pending units 1:1 for revoked units, exercisable only within 14 days from Init, which also attaches the notBefore trade from pending units to units; trading is available only as a chained item from the initial grant by us; pending units without a provided option contract will be denied trade-in by us, and our clients require the contract as an input for any pending-unit trade; at 28 days the notAfter signature is enabled, we automatically sign and put the transfer at 14 days, and each user's contracted counterparties can redeem against that user's account using their signed chained contract, resubmitting countersigned contracts to be run as soon as all chains up to them are done. Drew's closing question in the same ruling — whether clients should require all such contracts escrowed to us with all chains up to the original also escrowed, so the whole batch processes atomically — is recorded verbatim on #2296 as his open question, and several phrases of the mechanism are listed there as unclear: **both need Drew's confirmation before they are treated as design.** What is decided is the tradability itself and the contract-chained shape above; the escrow/atomic-batch question and the unclear phrases are not settled design.
6. **Open-source boundary — open all correctness-critical code.** Confirmed as recommended: protocol, gateway, ledger adapter, service and reconciliation code, event schemas, folds/validators, client/library API, tooling, test vectors and deployment examples are open, while secrets, production keys, customer data and operator deployment configuration stay private (§6). No module is excluded.
