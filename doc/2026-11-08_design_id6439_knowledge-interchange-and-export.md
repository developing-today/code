# Design: ID knowledge-layer interchange and full-fidelity export

**Status:** design proposal for #6439; no exporter is implemented here.
**Parent:** #5678 · **object model:** #2048 · **shared mapping/loss convention:** #6436.
**Scope:** two explicitly different export products: an interoperable Markdown bundle and a full-fidelity ID archive.

## Decision summary

1. **Interchange:** export a directory/ZIP whose readable pages are Markdown files with a small, versioned YAML front matter, ordinary relative Markdown links, and referenced attachment files. Include a machine-readable `manifest.json` sidecar for stable identity, typed values, mappings, and losses. Do not make the sidecar the only place a user-visible link or attachment can be represented. Provide deterministic `obsidian`, `logseq`, and `joplin` link/render profiles over the same canonical bundle where a target's native page-link syntax is required; label the profile and its target-version assumptions in the manifest. The portable profile remains standard Markdown and never emits Obsidian-only wikilinks or Logseq-only block references.
2. **Native:** export an integrity-checked, versioned archive of the caller-readable ID snapshot: selected logical objects, revisions/events and causal metadata, blobs, and permitted provenance. It is a backup/migration format for ID, not a substitute for interchange, and not a dump of inaccessible objects or secrets.
3. **Access:** calculate export membership by the ruled read-authority order **object → user default → server config → public** for the requesting actor. Apply that decision before serialization, link rewriting, attachment inclusion, indexing, or producing either manifest. An inaccessible reference must not reveal the target's name, ID, path, existence, or metadata.
4. **Evidence and gate:** the format recommendation below is supported by the target tools' documented import/export contracts and source-level importer tests. This checkout has no Obsidian, Logseq, or Joplin executable installed; therefore no live GUI round-trip is claimed. The pinned-version corpus and checks in §9 are a mandatory pre-implementation verification gate, not results already obtained.

The decision is between formats a user can inspect/edit and formats that can represent the ID model without loss. “Interoperable” means a target can ingest the files and preserve the tested subset; it does not mean every target retains every ID feature.

**Why Markdown wins, with a profile boundary.** It is the only candidate accepted as ordinary note content by all three ecosystems; the sources also show the exact places where its promise ends. The canonical files use CommonMark-style Markdown constructs and relative paths. Where a destination needs native page references for graph navigation, a target profile rewrites only the link syntax while preserving the canonical relationship in the sidecar. Profiles do not change source IDs, membership, or access rules. If a target cannot satisfy a test without custom code, record that as a failed capability, not as a passing “link preserved” result.

## 2. Object mapping contract

The exporter consumes a stable snapshot of the #2048 logical model, not filenames or event IDs as note identity. Per #2048, logical note IDs survive rename; revisions have immutable IDs and causal parents; typed links target stable note IDs and may pin a revision; backlinks are derived. This design does not redefine those model semantics.

### File and link naming

- Canonical page path is generated from a normalized hierarchy plus a short deterministic suffix derived from the opaque export ID, e.g. `Research/Orbit (a1b2c3).md`. The suffix is a collision disambiguator, not an ID oracle. `title` retains the exact display name. This avoids overwriting same-title pages, case-fold collisions, reserved names, and path traversal.
- Normalize path components to Unicode NFC; reject/escape separators, `.`/`..`, control characters, platform-reserved names, trailing dots/spaces, and characters disallowed by the chosen target. Percent-encode relative-link URL segments (UTF-8) and use `/` separators. Never trust source names as paths.
- Resolve duplicate output paths with the deterministic ID suffix; never “first wins” or overwrite an unrelated file. Re-exporting the same snapshot yields the same path. A changed title can change the human path, but stable sidecar IDs let import map it back.
- Encode YAML with a maintained serializer and quote values rather than hand-escaping. Link destinations use URI percent-encoding and Markdown escaping; reject `javascript:`, `data:`, `file:`, and untrusted absolute paths. External web links remain external after scheme allowlisting.
- For Logseq profile, derive unambiguous page refs from its native page identity/name rules, and emit the display title as an alias only when its target version supports it. For Joplin profile, preserve hierarchy and use the tested local-file link conversion path so the importer rewrites links to Joplin IDs. For Obsidian, use standard relative Markdown links; do not require wikilinks. These are adapters over the same source edge, not three different source mappings.

## 3. Loss/omission manifest and repeat exports

Each interchange package has `manifest.json` with `schema: "id-interchange/v1"`, exporter version, created timestamp, target profile (or `portable`), target app/version if supplied, snapshot ID, and:

- included readable object records: export ID, object kind, revision/head ID, relative path, content hash, and safe parent mapping;
- attachment records: owning readable export IDs, path, SHA-256, size, MIME type;
- readable relationship records: source, target, relation type, source revision/block, profile-rendered location;
- mapping ledger entries: `{source_export_id, source_field_or_block, target_location?, class, reason, raw_preserved}` where class is `exact`, `degrades`, `unsupported`, or `user-choice` (shared with #6436's fidelity-report convention);
- counts for included objects/assets and omitted-history items. No counts or placeholders for inaccessible objects or references.

The ledger is complete: every non-exact field/block/relation and every omitted optional category has an entry. For large exports, entries can be grouped by known mapping rule, but the rule must identify exact affected _included_ source objects. The manifest itself must be validated and hashed; package integrity includes every file. It may include a detached checksum for `manifest.json` but must not include a signature that implies an unauthorized actor's endorsement.

Repeated exports are snapshots, not synchronization. The caller chooses a stable snapshot; identical input and profile produce identical paths and payload bytes except explicitly volatile manifest timestamps. An import tool should use `_id_export_id` and sidecar mapping first, then a target-native ID if already associated; never title-only destructive overwrite. A path/title collision creates a conflict/loss entry and requires user choice (skip, create distinct object, or map to existing); no destructive update is implicit. If a target strips the sidecar or front matter, importing the edited target vault without it is lower-confidence and must be reported as such.

### Partial export

Partial selection is allowed, but is closed over authorization, not graph reachability. Only selected objects that pass access evaluation are included. A readable page may refer to a non-exported or unreadable page; its text label may remain, but the export must not contain a URL/path/ID that reveals the omitted target. Do not emit a dangling link that contains a guessed title or stable ID. Do not put omitted target counts, names, IDs, attachment metadata, or dangling-reference lists in the sidecar. A general package-level statement may say “some relationships were not exported because their targets were outside the selected readable set” only if the message does not reveal whether a target exists or is merely unselected; otherwise omit even that distinction.

## 4. Read-authority and privacy boundary

For every candidate object, resolve permission for the export actor using the ruled precedence exactly: **object → user default → server config → public**. Evaluate before serialization and re-check at the snapshot boundary so revoked access cannot leave stale bytes in an export. The same filter is applied to:

1. body rendering and structured properties;
2. links, backlinks, labels, aliases, names, stable IDs, paths, and relation endpoints;
3. attachments and their original names, hashes, MIME metadata, and thumbnails;
4. manifest, index/catalogue, history, errors, and warning text;
5. every event, revision, blob, and relationship in the ID-native archive.

An included readable object's policy metadata may be included only if that metadata is itself readable to the exporting actor. It is inert provenance, not an authorization grant. Import/restore must re-run current destination authorization and must never widen visibility based on exported ACL data. If the policy snapshot cannot safely be disclosed or applied, preserve only a safe effective-policy marker if the model defines one; otherwise omit it and record that the archive is a readable-content snapshot, not a full policy backup. Never export access tokens, private keys, password material, or decrypted secrets.

**No-existence oracle:** for a viewer who cannot read target T, the package output for a source link to T must be observationally indistinguishable from the output for an unresolved or deliberately omitted target: no T ID, title, path, label sourced from T, count, relation type that reveals T, or target-specific warning. A user-authored label already present on the readable source may remain only if it does not reveal T under the same policy review; otherwise replace it with neutral text or omit it. Do not write a manifest entry naming T.

## 5. Full-fidelity ID-native archive

The native export is a versioned archive (`id-native-export/v1`) containing a canonical index plus content-addressed payloads. It is defined separately from Markdown rendering. Its inclusion set must be a **disclosure-safe closure**: every serialized event, revision, field, relation endpoint, and blob reference must be readable under the ruled policy. A signed event cannot be redacted without invalidating its signature. If any selected event would reveal a target or field the actor cannot read, refuse the native export before writing payloads and return only a generic access-closure error. Do not silently omit that event and call the result a full-fidelity snapshot. Use the redacting Interchange mode for a partial view.

### Contents

- Export header: schema/version, source-world/store identity, snapshot/frontier, export time, exporter version, root manifest hash, and an explicit `scope: actor-readable-snapshot` declaration.
- For each included logical object in the disclosure-safe closure: stable object ID, type, current name/claims, all selected revision/event records, event IDs, signatures and authorized public-key identities, causal parents/frontiers, typed links, tags/claims, complete properties, and required object metadata. If any component is not readable, the closure check fails before archive creation; no field-level redaction of signed records is allowed.
- Content-addressed blobs and attachments referenced by those records, with byte length and cryptographic digest; encryption state/algorithm/key identifiers only where safe and necessary. No decryption key, private signing key, token, or secret is included.
- A closure table of references among included objects. Every target whose identity is serialized must also be readable and included in the validated closure. No dangling target ID or placeholder for an inaccessible target is written.
- A validation report and hashes for every entry. A signed snapshot/root may be added only with an existing authorized signing capability; exporting must not mint an identity or imply that a copied event was newly authored.

### Validation and restore/import

1. Verify archive schema, path safety, size limits, root and entry hashes, event signatures against included/known public-key claims, event causal references, blob digests, and internal referential integrity before mutating a destination.
2. Reject malformed/tampered archives atomically or stage them in a quarantine namespace; never partially publish objects as if restore succeeded. If the source-side disclosure-safe closure check fails, produce no archive and return no target-specific reason.
3. Restore to a new or explicitly selected ID store/world. Preserve IDs and event bytes when there is no collision. If an ID already exists with different bytes or lineage, stop with a deterministic conflict report; do not overwrite, renumber, or silently merge. A user may choose an explicit mapping/merge in a later operation.
4. Re-evaluate authorization at destination. Imported ACL/policy snapshots are not grants. A restore that cannot establish access policy fails closed; unreadable bytes never become public by default merely because the export was readable to its original caller.
5. Report counts by included object/revision/blob and integrity result. “Full fidelity” means exact preservation of the included authorized ID records; it does not mean all world data, inaccessible data, private keys, or a guarantee that a different schema version can be restored without migration.

## 6. User choice and UX

Expose two named, non-overlapping actions:

- **Export for another notes app (Interchange):** choose all/selected readable pages, optional target profile (`Portable Markdown`, `Obsidian`, `Logseq`, `Joplin`), and optionally include history. Preview included count and _safe_ loss summary. Produces a directory/ZIP usable in ordinary filesystems. Warning: target app may rewrite/drop metadata; check the manifest.
- **Back up / migrate ID data (ID-native archive):** choose actor-readable snapshot/store and destination-compatible archive version. Show that this is not a Markdown vault and will not open in the other apps. Require explicit destination/restore validation before import.

Do not offer a vague “export everything” button that conflates the modes. The default should be Interchange only if the user has selected a target; otherwise ask which mode. Explain that native archive requires a disclosure-safe closure and may fail when the request combines readable records with a hidden reference. Never enumerate why or what was excluded.

## 7. Shared conventions with #6436

Reuse the importer design's four degradation labels (`clean` → this design's `exact`; `degrades`; `user-choice`; `unsupported`) and one loss-manifest entry per non-clean mapping. For machine interoperability, this document standardizes the serialized class enum as `exact | degrades | user-choice | unsupported`; #6436 may keep its prose term `clean`, but implementations map `clean` ↔ `exact`. Both directions use source identity + mapping location + loss reason + raw-preserved status. Neither importer nor exporter silently merges duplicate display names or tag values.

Before implementation, compare the concrete #2048 page/block/link/tag/property mapping table in #6436 against §2; any divergence needs a linked decision with a reason, not an accidental fork. The importer may use export IDs/manifest to recover exact ID references on a round trip, but it must treat the bundle as untrusted input and validate IDs, paths, hashes, and authorization.

## 9. Reproducible target round-trip corpus and acceptance tests

The applications are not installed in the current execution environment. These are required, objective tests to run in isolated disposable profiles/graphs after Drew's version/edition and evaluation-budget questions are answered. Record exact app/plugin versions, OS, importer options, screenshots or machine-readable DB/file evidence, and the input/output hashes. Do not silently turn a documentation-only check into a claimed live round trip.

### Seed corpus C1

Generate one deterministic ID fixture with:

- P1 and P2: distinct pages with same display title in different namespaces, Unicode title (`Café / 東京`), reserved filename characters, and a rename between runs.
- P3: a page linking P1 and P2 (including forward and cyclic links), one pinned-revision reference, and one ordinary external HTTPS link; one heading link and one block-level link target.
- B1–B5: paragraphs, nested list/child blocks, task checkbox/status, tags and typed properties (string that resembles a date/boolean, number, boolean, date/time, multi-value list, relation), plus an unsupported custom block with a known textual fallback.
- T1/T2: tags differing by case and Unicode normalization, plus a hierarchical tag; assert the manifest records any target normalization/collision.
- A1–A3: two different binary attachments with the same original filename, one identical-byte attachment shared by two pages, and one image embedded in a body.
- P4: a page denied to the export actor, linked from readable P3; use a source-authored neutral label and a target-derived identifying label in separate variants to test the no-existence rule.
- Repeat snapshot: export C1 twice; then modify P1 title/body, add one tag and attachment, and remove/revise one outgoing link.

### Run matrix and pass criteria

For each of Obsidian, Logseq, and Joplin, import the selected target-profile package into a fresh, disposable target; inspect actual target graph/database behavior (not only rendered Markdown); export or copy the edited target data back through its documented Markdown export/import path; then re-import into an isolated ID test store with the same manifest-aware adapter. Also run the portable profile in each app as a separate compatibility probe. Pin versions; if current tooling cannot round-trip an item, record that item as a known loss, not a pass.

- **R1 — Membership/security:** P1–P3 appear; P4's title, ID, path, attachment, existence, and target-specific label are absent from all output files, app indexes, logs, and warnings. Oracle: byte/path scan plus target search/index check against P4's unique canary strings and ID.
- **R2 — Page identity and collisions:** P1/P2 remain distinct after import and round-trip despite identical display names; stable IDs map back to correct source objects when metadata is retained. Oracle: manifest/object-ID mapping and target object count; zero accidental merges/overwrites.
- **R3 — Links:** all readable page links resolve to the intended target inside the app (not merely look like links); cycle resolves both ways; the pinned revision is either preserved or reported as a named loss; target label remains unchanged. Oracle: target-native link graph/database query, plus imported ID edge endpoints.
- **R4 — Tags:** all supported tags remain searchable/associated with correct page/block; any target case-fold/normalization collision has a mapping/loss entry and does not merge ID tags on return. Oracle: target API/database tag membership and re-imported tag IDs/values.
- **R5 — Attachments:** embedded image renders in target; all three attachment references remain attached; duplicate names do not overwrite; identical bytes may deduplicate but both source references remain. Oracle: SHA-256 of returned bytes and target-native attachment/resource rows.
- **R6 — Properties and blocks:** assert each target-specific supported type; unsupported fields/bodies are present in the manifest and no silent drop occurs. Oracle: structured target data/API or parsed target files compared to field mapping table.
- **R7 — Repeat export:** identical snapshot/profile has same relative paths, page content, asset bytes, and manifest records except declared volatile metadata; second export never overwrites unrelated sentinel files. Oracle: normalized tree hash + sentinel unchanged.
- **R8 — Delta/conflict:** modified title/body/tag/link is detected on re-import; an ID-side concurrent edit is not overwritten silently. Oracle: explicit conflict/loss report and source-side value unchanged pending user choice.
- **R9 — Manifest integrity:** every non-exact mapping is represented exactly once or by a documented grouped rule; all listed paths exist and hashes match; no manifest target reference is outside the readable included set. Oracle: schema validator and cross-reference/hash check.
- **R10 — Native archive:** use a fixture whose selected signed records and reference closure are all readable; tamper one event/blob and confirm validation fails before publication; restore an untampered archive to an empty store and compare object/revision/blob IDs and hashes; confirm restore does not widen destination access. Oracle: archive validator, store diff, and policy evaluator.
- **R11 — Native closure failure:** with P3's signed event linking denied P4, request a native archive; it must fail before creating an archive, and the error must not name, count, or identify P4. Oracle: output directory remains empty and error text is identical to a missing/unresolvable target case.

The test suite should use an adapter conformance interface with per-target import/export commands, version capture, and evidence artifacts; it must not rely on screenshots alone. In the absence of a stable public CLI/API, a scripted desktop workflow plus target-native database/filesystem assertions is acceptable. Each test names its oracle above.

## 10. Scope and explicit non-goals

- No exporter/importer implementation, two-way sync, live target-app plugin, or promised lossless mapping into the three third-party apps.
- No attempt to decide the five Drew-owned questions in §8.
- No exporting hidden/inaccessible objects, private credentials/keys, or global indexes.
- No title-only link resolution, silent collision overwrite, implicit ACL grant, or assumption that Markdown syntax is identical across apps.
- No claim that Logseq's standard Markdown export or Joplin's Markdown/front matter is a full-fidelity backup; their native formats remain separate products.
