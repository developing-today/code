## Disposition table

`(a)` means a fresh receipt check is present; `(b)` means the omission is deliberate, with its reason; `(c)` means the audit found a gap and routed it to a named follow-up. Receipt is `ArtifactLog::insert` → `verify` → `parsed`; journal replay uses `store(..., false)` → `verify` → `parsed_for_replay` (`artifact.rs:425–529, 563–620, 733–775`).

## Explicit audit decisions

1. **Unknown `kind` string — forward compatibility wins.** Do not add the chain event's 1–`MAX_KIND_BYTES`/NFC rule to unknown artifact kinds. The artifact contract deliberately stores, but never applies, kinds this version does not know; the fresh frame limit still bounds total encoded size. Known kinds are exact constants.
2. **`document.content` strings — opaque payload.** Enforce serialized JSON size only. The document sibling checks media type, while the recursive NFC rule belongs to the chain event value model; no artifact consumer establishes an all-strings NFC invariant.
3. **`prev` shape — chain relation is sufficient.** Sequence 1 requires empty `prev`; later entries must equal the verified previous hash in the author's chain. An independent syntax check would duplicate the stronger position check.
4. **Builder symmetry — known-kind generic signing needs follow-up.** `SignedArtifact::sign`/`sign_after` are generic and support future kinds (for example, the board artifact producer); `sign_after` enforces `after` but does not call `parsed()` for recognized kinds. The directory's document/tag paths eventually refuse invalid values at `ArtifactLog::insert`, but the public generic signer can return a known-kind artifact that receipt rejects. Since `parsed()` returns `None` for unknown kinds, validating recognized kinds would preserve forward compatibility. This is a rule-1 gap, routed to [#5623](https://github.com/developing-today/code/issues/5623), not fixed in the audit. `Directory::declare_home` already calls its shared check before signing.
5. **`world_id` charset — do not impose hub-name grammar.** `declared()` consumers route to the declared endpoint and do not resolve the world ID; local `WorldCore` also accepts any nonblank ID. Keep the design's 1–64 byte/nonblank/no-`Cc`/no-`Cf` rule, not `validate_world_name`'s ASCII grammar.

## Follow-ups and replay risk

The audit found and routed the following (c) items; no implementation fixes were included here:

- [#5623](https://github.com/developing-today/code/issues/5623) — validate known-kind bodies in generic signing helpers while preserving unknown-kind signing.
- [#5624](https://github.com/developing-today/code/issues/5624) — validate incoming friend-request IDs and keep friendships with already-persisted noncanonical IDs removable.
- [#5625](https://github.com/developing-today/code/issues/5625) — preserve local replay of pre-upgrade duplicate-`after` and non-NFC document/tag artifacts while keeping fresh receipts strict.
- [#4459](https://github.com/developing-today/code/issues/4459) — existing peer-pull compatibility follow-up for pre-upgrade `home_declared` artifacts; the artifact-format cutoff ruling is recorded, but the receive-path implementation remains open.

The local replay distinction is deliberate only where explicitly implemented: `home_declared` skips #3187's new world-ID/duplicate-endpoint rules, and `friend_remove` skips only its newly added duplicate-list refusal. The audit did not broaden those exceptions or change any receipt behavior.
