# Design: the first ID app — sticky notes + did-it tracker

- Date: 2026-11-01
- Status: **design** — no implementation is included in this change.
- Issue: [#2031](https://github.com/developing-today/code/issues/2031), “id: design+PoC: sticky-notes / did-it tracker — the first ID app”.
- Evidence baseline: `origin/main` at `33aefa7f7` (merged into `design/id-2031` before this record).
- Implementation follow-ups already filed: [#3788](https://github.com/developing-today/code/issues/3788), [#3789](https://github.com/developing-today/code/issues/3789), and [#3790](https://github.com/developing-today/code/issues/3790). This record adds a storage/replication prerequisite discovered in the current code; it does not edit those issues.

## Decision to make

How should the first ID app combine shared sticky notes and the did-it tracker on the current `pkgs/id` event substrate, while proving the #2031 bar: identities A and B exchange notes and did-it events; A's view excludes C's claims but leaves them retrievable on demand; and no permanent feature is built on an unreviewed PoC?

**Recommendation:** build the PoC on reusable event and projection behavior, not on an app-only event model. First make arbitrary committed event bodies durable and transferable; then land the did-it schema/evaluator and writer-set projection as independently testable library slices; finally compose those with existing document/blob events in an example. Do not start the PoC until its event bodies can survive restart and cross-device sync.

## Context and current state

The issue asks for a synthesis of the did-it data-model and trust/visibility investigations, not just a demo. Its explicit acceptance bar is the two-identity exchange and the third-party exclusion/retrieval test, with a review-round gate before permanent implementation ([#2031 body](https://github.com/developing-today/code/issues/2031)). The existing follow-up issues turn that into three slices: did-it model/evaluator (#3788), writer-set projection (#3789), and example PoC (#3790). The later routing correction on #2031 is the source of those issue IDs; the earlier phase-suffixed queue keys are superseded ([#2031 correction](https://github.com/developing-today/code/issues/2031#issuecomment-6560836273)).

The current checkout changes two assumptions in the earlier #2031 triage comment:

1. **Writer-set wire types now exist.** `idset.writer` and `idset.rescind` have canonical CBOR body types in `pkgs/id/src/idset.rs:1-28`; the module explicitly leaves expansion, projection, and counting for later (`pkgs/id/src/idset.rs:53-55`). They are exported from `pkgs/id/src/lib.rs:190`. PR #3895 (issue #3854) therefore covers schema encoding; #3789 should implement the remaining view behavior, not recreate these types.
2. **Generic application bodies are not currently durable or range-synced.** `ChainExt` carries a free-string `kind` and optional group (`pkgs/id/src/chain.rs:93-117`), and the signed header commits to a body's hash and size while the body itself is separate (`chain.rs:271-276`). Ingest accepts and verifies a supplied body (`pkgs/id/src/event_store/ingest.rs:226-269,419-443`), but `store_event` writes `event.bytes` (the signed header) only (`pkgs/id/src/event_store/mod.rs:1211-1230`); range sync sends stored events and fork-proof headers (`pkgs/id/src/event_store/sync.rs:15-25`). Thus a `didit.*` CBOR body can be validated at ingest but is not yet available for later retrieval or cross-device replication. A body persistence/retrieval/sync slice is a prerequisite missing from #3788–#3790's current dependency graph.

This is distinct from documents: `document.put` carries a signed `DocumentRef`, while content bytes are a blob moved on request through `iroh-blobs` (`pkgs/id/src/documents.rs:3-10,40-50`). The document path is suitable for note text; it does not provide a generic store for arbitrary `didit.*` event bodies.

The event store also distinguishes storage from application. Ingest retains held events on disk and recognizes events held/applied or held/voided as present (`pkgs/id/src/event_store/ingest.rs:57-65`); tag folding reads applied tag events only (`pkgs/id/src/event_store/claims.rs:32-65`). Group roles include `Write` (`pkgs/id/src/groups/mod.rs:61-75`), but ordinary content is not generally rejected for lacking group membership: `content_applies` checks membership only when the event names a voided dependency (`pkgs/id/src/event_store/resolve.rs:382-399`). Therefore group membership, storage, and a did-it view's decision to count a claim are separate concerns.

## Proposed shape

```text
document.put + content blob ──┐
  note.id / note.supersedes ──┼──► one shared-group timeline
                              │
didit.* event + committed body ─► durable body store + range sync
                                      │
                             event-store resolution
                                      │
signed idset.writer / idset.rescind ─► counted / uncounted view
                                      │
                       pure expectation evaluator
```

The view must report its inputs, not just a rendered result: the writer-set event/version and the event-store causal frontier used to compute it. The same stored history plus those inputs must reproduce the same counted/uncounted projection. The current idset module calls projection and counting out explicitly; the writer-set specification and #3789 provide the intended set semantics.

### Sticky notes

- Store note content as `document.put` content in the shared group; display the first content line as the title. Reuse the document/blob path rather than inventing note-specific content transport (`pkgs/id/src/documents.rs:3-10,31-50`).
- Documents are immutable events. A new edit is a new `document.put`; represent a stable logical note with signed tag claims, for example `note.id=<stable-id>` on each revision and `note.supersedes=<prior-document-event-id>` on a successor. `tag.set` can name any event, carries a signer-attributed text name/value, and travels in the signed header (`pkgs/id/src/tag_claims.rs:3-16,48-64`).
- Derive current revision heads from those explicit links. If two edits are concurrent, show both heads as a conflict; do not silently choose last-writer-wins. This makes “superseding document events” an app-level relation—the document envelope has no supersedes field.
- Reuse `document.remove` as a visible tombstone, not a promise of erasure. The event store retains the document and its content/tags; only the document author's removal marks it (`pkgs/id/src/documents.rs:19-23`; `pkgs/id/src/event_store/documents.rs:3-10,22-25`). The UX must say what “remove” means; see Drew question Q3.

### Did-it events and evaluation

- Use the four kinds recorded in #3788 and the #2031 synthesis comment: `didit.entity`, `didit.record`, `didit.expectation`, and `didit.opinion`. Keep the event envelope unchanged: its `kind` is already a non-empty free string, and group/causal metadata are already in `ChainExt` (`pkgs/id/src/chain.rs:93-117`).
- Store structured event bodies as canonical CBOR, committed by the signed header. The evaluator is a pure function over explicit entities, records, and expectations: do not persist derived “due” state. Treat an empty subject set as invalid and evaluate using the expectation's IANA timezone (#3788); surface a record/expectation offset mismatch instead of silently coercing it (the #2031 synthesis recommendation).
- Opinions are separate linked events, never mutations of a record. Keep the opinion stance and foreign-app summary choices open for Drew as listed below rather than hard-coding a numeric aggregate.

### Trust, visibility, and retrieval

- Ingest verifies event validity and retains the event; a view separately determines whether an event is applied and whether its author is counted. Never copy a claim-supplied “trusted” bit into the projection.
- For the first PoC, count only did-it events whose authors are in the selected writer set. Keep valid but uncounted events and their bodies retrievable on demand; show author and an explicit “not counted” state. If an event is not applied by event-store resolution, distinguish that from “not in writer set” rather than conflating the reasons.
- Build projection from the already-landed `idset.writer` / `idset.rescind` events. Apply the #3789 rules: explicit keys and one-level group references, topic scope, exclusion entries, prospective admission by default, explicit `include_history`, and visible signed rescinds. Computed views name both set version and frontier. Public/sentinel views are out of scope for this PoC per the newer #3789 packet; revisit only with the abuse controls of #2032.
- A group role is not a substitute for this view predicate. The view must be deterministic and must not make ingest discard data merely because a writer is not counted.

## Viable options and trade-offs

| Option | Benefits | Costs / risks | Decision |
| --- | --- | --- | --- |
| One combined app PR (notes + did-it + trust projection) | Fastest single end-to-end demo; one integration surface | Couples unreviewed schema, trust rules, storage, and UI; hard to test or review independently; conflicts with #2031's explicit review gate | Reject |
| PoC first with app-local/ad-hoc did-it records | Fastest visible prototype | Becomes an accidental wire contract; current event store cannot persist/sync the arbitrary bodies; likely discarded or silently divergent from #2029/#2238 | Reject |
| **Reusable substrate and library-first slices (recommended)** | Each semantic layer has focused tests; schema/evaluation and trust projection can be reviewed before app behavior; PoC validates the actual shared protocol | More up-front event-body plumbing and explicit dependency management; does not yield a UI immediately | **Choose** |
| Notes as custom `note.*` body events instead of documents + tags | Gives a single purpose-built note/revision schema | Duplicates document/blob and removal behavior; still needs generic body durability; adds schema before the PoC has shown a need | Reject for PoC; reconsider only if document/tag semantics prove insufficient |

For note versioning, using document events plus explicit tag links reuses existing blob transport and generic tag operations. The trade-off is that the app must define revision-link tags and show concurrent heads; the existing document record does not supply a logical-note/supersedes abstraction. This is narrower than adding a second content protocol.

## Invariants

1. **Transport integrity:** every custom event body is checked against the signed header's hash and size, durably retrievable after restart, and replicated to another identity; the header format remains unchanged.
2. **Three separate states:** accepted/stored, applied by event-store resolution, and counted by a writer-set projection are never treated as synonyms. Counting is derived from the selected set and view inputs, never from event payload claims.
3. **Retrievable exclusion:** an uncounted third-party event is not deleted or silently counted; its author and exclusion reason are available on demand. A computed view identifies its writer-set version and causal frontier.
4. **Stable did-it history:** entity IDs are explicit; empty subjects are rejected; expectation evaluation is pure and timezone-aware; opinions link to records without modifying them.
5. **Note history is explicit:** each edit is a new document event linked to a logical note/revision; concurrent heads remain visible; removal is the existing author-signed tombstone and is not represented as secure erasure.
6. **Same collaboration context:** notes and did-it events in the PoC are shared in one group timeline; only the did-it view's counted/uncounted projection decides which claims affect that view.
7. **Review gate:** the example is labeled as a PoC. Do not build a permanent user-facing feature on it until a review round accepts the schema, trust behavior, and open privacy decisions, as #2031 requires.

## Acceptance criteria for implementation

- **Body substrate:** a test creates a custom-body event, verifies rejection when the body hash/size is wrong, stores the correct body, restarts the store, syncs to a second identity, and retrieves/verifies the exact body there. This is not covered by the three existing follow-up issues and must be assigned before the PoC begins.
- **Did-it library (#3788):** implement the four event types and canonical encoding at the current `pkgs/id` chain/body ownership boundary; run the data-model's golden cases. The pure evaluator handles the documented cadence/timezone cases, rejects empty subjects, and represents opinions as linked events.
- **Writer-set projection (#3789):** use the existing idset schema; test counted and uncounted projection, explicit history inclusion, prospective changes, rescind, set-version/frontier naming, and deterministic recomputation. A third-party event remains stored and retrievable but does not affect the selected view.
- **PoC (#3790):** the example places notes and did-it activity in a shared group timeline. An integration test has A and B exchange both kinds; C's claim is absent from A's counted result but retrievable on demand with author + “not counted”. Notes edit via new document events and explicit revision links; concurrent heads are not silently collapsed. The README calls this a PoC and names the review gate.
- **Scope:** no public/sentinel view, no permanent app feature, and no dependency on the still-open ID-core design issue unless a later decision explicitly requires it. Existing example READMEs establish the `pkgs/id/examples/` convention, though they are world/capability demos rather than an existing event-store application (`roc-counter/README.md:3-6`, `roc-chat/README.md:3-7`, `lounge/README.md:3-16`).

P0–P2 are independently mergeable library/substrate changes and can proceed in parallel; P3 waits for all three. P0 is a newly identified prerequisite, not yet represented by a follow-up issue. This design-only change does not open or edit any other issue; the dependency must be made explicit before #3790 starts.

## Questions for Drew

These do not block P0–P2. Public/sentinel views are omitted from this PoC per the newer #3789 follow-up, so that earlier question is not reopened here.

1. **Opinion stance vocabulary.** Should an opinion be `good` / `bad` / `unsure` plus optional free text, or a numeric rating scale? **Recommend the three named stances plus text**: they preserve a clear semantic distinction without implying cross-author scores are comparable. This follows the #2029 proposal summarized in the #2031 synthesis comment; confirm before freezing the public event schema.
2. **Foreign-app did-it summary.** Should another app see `act` details, or only counts/timing unless the user follows the app link? **Recommend counts/timing only; keep `act` behind the originating app link.** The newest #2031 synthesis comment recommends this, while the underlying data-model note still records behavioral-graph exposure as open. Decide before exposing a summary projection outside the originating app.
3. **What does note removal promise?** Reuse `document.remove` (author-only, visible tombstone, bytes remain retrievable) or require actual content erasure? **Recommend the existing tombstone for this PoC, clearly labeled as removal from the view and not erasure.** A genuine deletion promise needs a separate storage/replica-retention design and should not be implied by the current event.
