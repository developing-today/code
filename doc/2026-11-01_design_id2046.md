# Design: ID serverless edition v1 on Cloudflare Workers

- Date: 2026-11-01
- Status: **design** — no implementation is included in this change.
- Issue: [#2046](https://github.com/developing-today/code/issues/2046), parent epic #2056.
- Source baseline: this checkout's `main` at `a9e976ac2`; the branch was checked against `origin/main` before writing.
- Inputs: [Workers-fit investigation #2044](https://github.com/developing-today/code/issues/2044#issuecomment-6484984323), [hosted-data investigation #2045](https://github.com/developing-today/code/issues/2045#issuecomment-6494944443), and the later hosted provisioning spec. Per this task's source rule, this note prefers the newest recorded decision where sources conflict, using the Oct 30 provisioning lifecycle over #2045's earlier, less precise wording about when the DO is named/provisioned. The Oct 30 spec says #2045 governs if they disagree; where that source-priority note conflicts with this task's explicit rule, this synthesis follows the newer spec.

## The decision

**Ship a hosted personal home-server, not a Cloudflare port of the native Iroh node.** V1 is an HTTP/WebSocket product: one Worker fronts a shared account registry and a lazily provisioned, SQLite-backed Durable Object (DO) per bound ID. R2 holds blob bytes. Native `id` nodes remain Iroh peers and can sync with the hosted home through a new HTTPS/WebSocket bridge that transports the existing signed objects without changing their trust or ordering semantics.

Keep v1 to the personal home-server (Shape B). Do not include shared-world hosting (WorldDO / Shape C), per-user containers, or a new hosted authority for ID keys. Those either have unresolved semantics/cost ownership or contradict the selected serverless shape. A small, isolated proof of concept (PoC) is the first implementation step; no permanent feature should be built on an unreviewed PoC, per #2046.

## Context and constraints

### What #2046 asks to settle

The issue asks this synthesis to combine the Cloudflare Workers fit and hosted-data investigations, specifically deciding what ships first, how per-user data is held, and where the hosted edition stops and the self-hosted ID server begins. It also routes open parameters from #2045—tier numbers, rebind delay, and client-side-encryption default—to this decision rather than treating them as already settled. See [#2046 body and comments](https://github.com/developing-today/code/issues/2046).

### Current `pkgs/id` is a native server, not a Worker runtime

- `cmd_serve` loads a node key and binds an Iroh endpoint; the world hub is shared by the Iroh protocol and the existing web router (`pkgs/id/src/commands/serve.rs:783-819, 887-932, 1221-1250`). `world_net` documents `/id-world/1` as a bidirectional QUIC-stream transport and says that Iroh node identity does not itself grant world authority (`pkgs/id/src/world_net.rs:1-10, 30-32, 57-95`).
- Durable worlds currently use local paths and an append-only, fsynced JSONL journal plus module files (`pkgs/id/src/commands/serve.rs:419-430`; `pkgs/id/src/world_store.rs:1-22, 36-70, 366-398`). The hub already has a `WorldOpener` seam and lazy open/idle-eviction rules (`pkgs/id/src/world_hub.rs:1-19, 62-80, 82-100`), but that does not make the filesystem adapter or Iroh transport portable by itself.
- Current web security is a loopback-by-default, host/origin-checked web server with an optional shared token (`pkgs/id/src/cli.rs:345-363`; `pkgs/id/src/web/security.rs:1-23, 39-49`). Directory accounts use public keys and confirmed email; directory sessions and one-time codes are in-memory and are not journaled (`pkgs/id/src/directory.rs:76-89`; `pkgs/id/src/directory_auth.rs:1-8, 22-28`). This is not Google OIDC, and hosted SSO must not be conflated with the Iroh ID key.

### What the investigations establish

- The Workers-fit result says a Workers edition is feasible only as an HTTP/WebSocket-shaped subset: Workers have no UDP sockets, while Iroh uses QUIC/UDP. It recommends a per-user SQLite-backed DO, with R2 for blobs ([report, verdict and storage limits](2026-10-28T23-34-14Z_investigation_cloudflare_workers_fit/2026-10-28T23-34-14Z_investigation_cloudflare_workers_fit.md#L19-L29), [networking](2026-10-28T23-34-14Z_investigation_cloudflare_workers_fit/2026-10-28T23-34-14Z_investigation_cloudflare_workers_fit.md#L155-L189)).
- The Workers report initially proposes naming a DO from `google:<sub>`. The later provisioning spec instead keys the account registry by Google `sub` and names the user's DO from a stable `binding_id` minted at first key binding; this preserves the user's data store across an ID-key rebind ([Workers report](2026-10-28T23-34-14Z_investigation_cloudflare_workers_fit/2026-10-28T23-34-14Z_investigation_cloudflare_workers_fit.md#L193-L206), [provisioning spec, shape and records](2026-10-30T22-45-00Z_design_hosted_provisioning_sso_binding.md#L14-L46), [lazy provisioning](2026-10-30T22-45-00Z_design_hosted_provisioning_sso_binding.md#L257-L277)).
- The #2045 result says first sign-in creates the account and names its DO. The newer Oct 30 spec is more precise: first sign-in creates only an account row; successful signed-key binding mints the `binding_id` and provisions the DO. This note follows that newer lifecycle. Google authenticates the account, while the Iroh root key remains the ID identity ([#2045 result](https://github.com/developing-today/code/issues/2045#issuecomment-6494944443), [provisioning and binding](2026-10-30T22-45-00Z_design_hosted_provisioning_sso_binding.md#L114-L150)).
- The bridge design says the bridge is a sync peer, not a translator or proxy: it cannot assign order, hold signing trust, or present a hosted snapshot as authoritative. A dual-homed native node initiates the HTTPS/WebSocket session; the hosted endpoint is passive ([bridge semantics](2026-10-29T11-27-00Z_investigation_bridge_semantics_hosted_native/2026-10-29T11-27-00Z_investigation_bridge_semantics_hosted_native.md#L15-L46), [bridge roles](2026-10-29T11-27-00Z_investigation_bridge_semantics_hosted_native/2026-10-29T11-27-00Z_investigation_bridge_semantics_hosted_native.md#L71-L91)).
- The hosted provisioning spec leaves free/paid tier numbers, the exact rebind wait, and the encryption default open. It also leaves Shape-C cost attribution open; those are not settled decisions (`2026-10-30T22-45-00Z_design_hosted_provisioning_sso_binding.md:409-418`).

## Viable options

| Option | What it means | Trade-offs | Decision |
|---|---|---|---|
| **A. Port `id serve` directly to Workers** | Run the current native node and its Iroh protocols inside a Worker. | Does not fit the runtime: the native serve path binds Iroh and the present durable-world store uses filesystem paths; Workers do not expose UDP/QUIC. A rewrite would still not make the Worker an Iroh peer. | **Reject.** Porting the whole native server is both infeasible as stated and the wrong compatibility promise. |
| **B. Hosted personal home-server** | Worker for HTTP/WS, web UI and OIDC; one UserDO per bound ID; D1 account registry; DO SQLite for structured user data; R2 blobs; transport-only HTTPS/WS sync with native nodes. | Requires a new hosted adapter and bridge; cannot provide native Iroh discovery/gossip from the Worker. Per-user DO limits are isolated to that user. | **Recommend for v1.** It matches the Workers runtime and the later Shape-B provisioning spec. |
| **C. Per-user native server/container** | Run a complete `id serve` instance for each hosted user. | Preserves native transport but creates always-on or metered compute and provisioning/operations overhead; not a serverless edition. #2045 rejects per-user containers as a tier (bounded, owner-attributed jobs are a separate exception). | **Reject for the default offer.** Keep self-hosting available; do not disguise containers as Workers. |
| **D. Browser-only/local storage** | Put all state in the browser, with no durable hosted home. | Lowest hosted cost and simplest isolation, but not a hosted home-server and does not provide an always-reachable per-user endpoint or bridge target. | **Not the requested edition.** It can remain a client mode, not the serverless v1. |

## Recommended v1 shape and per-user data story

1. **Account without content.** The Worker verifies Google OIDC and keys a service-operated D1 registry by Google's stable `sub`, not email. First sign-in creates an opaque account row only. D1 contains account/binding/tier and daily meter-rollup metadata; no user graph or blob payloads.
2. **Explicit identity binding.** A separate ceremony challenges the client to prove possession of its Iroh root key by signing a short-lived, single-use transcript bound to the authenticated `sub`. Sign-in alone never claims or rebinds an ID. No custodial user signing keys. The browser or a user's own node keeps the private key; the service stores the public key and signed binding/attestation records. These rules follow the latest spec's ceremony and failure semantics ([§3](2026-10-30T22-45-00Z_design_hosted_provisioning_sso_binding.md#L120-L183)).
3. **Provision on first binding.** A successful first binding mints an immutable `binding_id`; `idFromName(binding_id)` identifies the UserDO. This is intentionally newer than the earlier `google:<sub>` proposal. Key rebinds therefore do not move the user's data. Unbound accounts cannot read or write hosted ID data.
4. **One user, one serialized store.** The UserDO owns that user's structured graph/journal, indexes, memberships/invites and live hibernating WebSockets in strongly consistent SQLite. It lazily runs versioned migrations. Its single-user execution is an isolation and consistency unit, not a shared-world writer. This is a new hosted storage adapter: the current native world's durable journal is filesystem-backed (`pkgs/id/src/world_store.rs:1-22, 36-70, 366-398`), while the Workers-fit investigation recommends SQLite for per-user data ([DO recommendation and limits](2026-10-28T23-34-14Z_investigation_cloudflare_workers_fit/2026-10-28T23-34-14Z_investigation_cloudflare_workers_fit.md#L33-L80)).
5. **Blobs separate from rows.** Store blob bytes in R2 by content hash; keep per-user references, size and accounting in the UserDO. Keep blobs out of SQLite; use KV only for public discovery/cache data. Encrypted blobs, if chosen, deduplicate only within that user (the accepted trade-off in the hosted spec, [§5.1](2026-10-30T22-45-00Z_design_hosted_provisioning_sso_binding.md#L257-L269)).
6. **Bounded, recoverable usage.** Meter current storage gauges separately from monotonic request/session/egress counters. At the storage ceiling, refuse writes without deleting or truncating data; allow export and explicit user-confirmed deletes so the user can recover. At the request ceiling, return a retryable refusal while keeping export available. The behavior is already specified; only the tier numbers/prices remain open ([metering and ceilings](2026-10-30T22-45-00Z_design_hosted_provisioning_sso_binding.md#L279-L326)).

### V1 boundary with the self-hosted server

- **Self-hosted remains native.** `id serve` continues to be the user's Iroh node and local durable server. Its current node key, QUIC endpoint, file journal and native auth are not silently replaced by Google identity (`pkgs/id/src/commands/serve.rs:783-819`; `pkgs/id/src/world_net.rs:1-10`; `pkgs/id/src/world_store.rs:1-22`).
- **Hosted is a new transport/hosting adapter, not a new ID authority.** Browsers and native clients may connect to the hosted endpoint over HTTPS/WebSocket. A dual-homed native node initiates sync; the Worker does not join Iroh, gossip, hole-punch or connect over QUIC. Worker-fit report: [networking conclusion](2026-10-28T23-34-14Z_investigation_cloudflare_workers_fit/2026-10-28T23-34-14Z_investigation_cloudflare_workers_fit.md#L155-L189).
- **Signatures remain the trust source.** Bridge ingest verifies the same signed objects and fork/causal rules as native ID. It never re-signs for a user, assigns event order, treats a snapshot as authoritative, or changes what a native peer accepts. Blob transfer is a separate HTTPS/R2 leg. This follows [bridge semantics §§1–2](2026-10-29T11-27-00Z_investigation_bridge_semantics_hosted_native/2026-10-29T11-27-00Z_investigation_bridge_semantics_hosted_native.md#L17-L45) and [blob separation](2026-10-29T11-27-00Z_investigation_bridge_semantics_hosted_native/2026-10-29T11-27-00Z_investigation_bridge_semantics_hosted_native.md#L104-L126).
- **Not in v1:** shared WorldDOs/Shape C, third-party relay bridging, hosted Iroh/QUIC, custodial keys, per-user containers, or promises that every native feature is available over the hosted subset. Shared-world write/read authorization, throughput and cost attribution need a separate settled design.

## Invariants

1. A Google account is not an ID key. Email is contact metadata, never a lookup or binding key; an authenticated account cannot access content until it completes the signed binding ceremony.
2. The private Iroh root key never leaves its user-controlled client/node and the hosted service never signs on that user's behalf.
3. Every user-content request resolves through the authenticated account's binding to exactly one UserDO. Client-supplied user IDs, DO names or blob keys cannot cross that mapping. Shared D1 and KV contain no private payloads.
4. UserDO storage is lazy and durable across Worker eviction/hibernation. No correctness state depends on a Worker process remaining warm.
5. The bridge transports signed objects; it cannot author, mutate, reorder, authorize by transport identity, or establish a new source of truth.
6. Quota enforcement never silently deletes user data. Export remains possible at a cap, and any data export/import is verified before ingest (hosted spec, [export/import](2026-10-30T22-45-00Z_design_hosted_provisioning_sso_binding.md#L335-L385)).
7. Existing self-hosted defaults and native Iroh behavior remain working independently of the hosted feature and its configuration.

## Implementation acceptance criteria

- **Runtime PoC:** a Worker/DO can durably bootstrap versioned SQLite schema, survive eviction, and handle a hibernating WebSocket; the same signed-event fixtures pass through the chosen portable core/adapter. Record an explicit go/no-go for Rust/Wasm reuse versus a separately implemented Worker adapter. No permanent feature depends on this PoC until it is reviewed.
- **Identity:** valid Google OIDC establishes an account but no content access. Binding requires a fresh, single-use signed challenge tied to `sub` and Iroh key; race, replay, wrong-account, conflicting-key and failed-proof tests create no partial binding or DO. The `binding_id` and DO stay stable through rebind.
- **Tenant isolation:** tests for two accounts prove every operation and blob reference is confined to its bound UserDO. D1/KV contain no private graph/blob payloads; a browser-supplied identifier cannot choose another tenant.
- **Persistence and recovery:** DO migrations are retryable/idempotent; concurrent bootstrap cannot split schema. Store export at normal and capped states, verify all signed objects and blob hashes, then import into self-hosted ID without accepting partial/tampered data.
- **Bridge semantics:** native-to-hosted and hosted-to-native sync passes replay, signature, per-author order, causal/fork-proof and interrupted/resumed-session tests. Worker transport does not change the native event-store result. The bridge is passive; a dual-homed native client initiates it.
- **Caps and privacy:** storage/request ceilings have named errors, no silent data loss, export path, metering-kind separation and explicit-delete recovery. If encryption is enabled, tests prove payload/blob encryption occurs client-side and the UI explains which metadata remains plaintext and which hosted features degrade.
- **Regression:** existing native `id` protocol, local file-backed worlds, directory auth, and self-hosted web security tests continue to pass unchanged.

## Phased implementation plan

Each phase is a separate, reviewable PR and can merge behind an off-by-default hosted route; no phase changes the existing self-hosted path. Dependencies are ordered, and the PoC is deliberately disposable.

| Phase | Independently mergeable packet | Done when |
|---|---|---|
| **0. Runtime PoC** | Throwaway Worker + DO spike: SQLite migration/eviction, hibernating WS, signed-object validation, and portable-core feasibility. | PoC report records runtime limits, chosen reuse strategy and go/no-go; it is reviewed before production work uses its code. |
| **1. Hosted contract and adapter seam** | Define the HTTPS/WS request/session contract and the smallest storage/ingest seam needed by UserDO; retain existing Iroh and file adapters. Add cross-adapter signed-event fixtures. | The same event fixtures preserve signature, replay, causal order and fork handling through native and hosted adapters; native behavior is unchanged. |
| **2. Account and binding** | Worker OIDC + D1 account/binding registry, signed challenge ceremony, immutable binding ID, rebind state machine and notifications. No user-content store yet. | First sign-in creates only an account; binding/replay/race tests pass; rebind delay is configurable with a provisional 7-day default until Drew rules before public enablement. |
| **3. Personal UserDO store** | Lazy DO provisioning, SQLite migrations, R2 blob adapter, user-scoped data routes, metering, caps, export/import and explicit-delete recovery. Keep the hosted route gated. | Tenant-isolation, eviction/reopen, quota/export and integrity checks pass; a bound user can use the hosted personal home without changing self-hosted behavior. |
| **4. Native HTTPS/WS bridge** | Add the native client's dual-homed transport and the hosted passive sync endpoint, with batched/resumable sessions and separate R2 blob transfer. | Round-trip sync tests prove signed-event parity, fork proofs and resume after disconnect/DO hibernation; no bridge-assigned identity, trust or ordering. |
| **5. Closed beta and operational guardrails** | Enable allowlisted users; dashboards/alerts, abuse limits, cost measurements, privacy disclosures and user-facing encryption choice. Do not publish paid tier numbers until they are approved. | Cap behavior and export are demonstrated in beta; cost and usage evidence supports the proposed numeric tiers; Drew has ruled on the remaining product parameters before public availability. |

**After v1, not a phase of this launch:** settle WorldDO authority/replica semantics, shared-world authorization and throughput, Shape-C cost attribution, and optional relay bridging before implementing shared hosted worlds.

## Questions for Drew

These do not block the architecture or PoC; they do block publishing a public offer with final defaults.

1. **Tier ceilings and prices.** Option A: ship an invite-only/free preview with conservative configurable ceilings and no public price until observed usage supports a cost model (**recommended**). Option B: publish free and paid storage/request numbers and prices before beta. Recommendation: A; the provisioning spec already defines safe at-cap behavior, while the numeric values have no measured v1 workload behind them.
2. **Lost-key rebind delay.** Option A: 7 calendar days; Option B: 14 days; Option C: 30 days. Recommendation: 7 days, with notice to every recorded contact and the old key able to cancel or approve early; it provides a meaningful response window without making legitimate key recovery a month-long lockout. The source spec only settles “days, not minutes,” not the exact duration.
3. **Client-side encryption default.** Option A: default off, with an explicit at-binding disclosure and opt-in; hosted search/indexing and previews remain available. Option B: default on, with opaque payloads and reduced server-side search/indexing/previews. Recommendation: A for v1, following #2045's recorded default-off suggestion and the hosted spec's stated functionality trade-off; this is a values decision because default-off means the operator can read payloads at rest. Do not hide that fact or turn encryption off silently.

No Drew ruling is needed before beginning the PoC or adapter-contract work. The provisional rebind value can keep Phases 2–4 moving, but the final delay and encryption default must be explicit before public enablement. Shape-C attribution is deferred because shared worlds are out of v1; challenge/rate-limit thresholds are operational tuning, not an architecture gate.
