## Decision summary

| Question         | Decision                                                                                                                                                                                                                                                                                                                                                                                        |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| What a parcel is | A **capability domain inside a world**: a named extent + a policy bundle + a controlling writer set (§2). It is not a new authority root and not an asset                                                                                                                                                                                                                                       |
| Domain model     | The parcel record is journaled world state: extent descriptor, policy bundle (script permissions, access/ban, asset rules), and the derived ID of its writer set (§2)                                                                                                                                                                                                                           |
| Nesting rule     | **Attenuation only**: effective authority at a parcel is the _intersection_ of the world ceiling, every enclosing parcel policy, and the actor's grant chain. A parcel can only narrow, never widen (§3)                                                                                                                                                                                        |
| Grant shape      | Parcel control is **membership in the parcel's writer set** (`derive_set_id(owner, "parcel:<world>:<parcel>")`); entries admit, excludes un-admit and win. Membership itself is managed by the set's owner only — every set version is owner-signed (§4.1). Use rights are attenuated capabilities, revoked by capability ID. Delegation is a new set version, never a transfer of a token (§4) |
| Server vs author | The server enforces the _invariants_ (monotone narrowing, signature/chain verification, access enforcement, journaling); everything about _which_ parcels exist and what their policies say is world-author policy, and none of it is an interop requirement (§5)                                                                                                                               |
| Tokenized land   | **Ruled out**, per the issue body: no parcel tokens, no scarcity market, no transfer-as-sale. Control moves by grant and revocation only (§6)                                                                                                                                                                                                                                                   |

## 1. What the programme already fixed (not re-decided here)

1. **Attenuation only narrows** (program delegation semantics,
   `doc/2026-10-09T09-59-07Z_design_attenuated_capabilities/`): a holder
   may mint a child capability with a subset of its own functions, an
   earlier or equal expiry, and narrower scope — never more. §3 applies
   this rule to spatial domains; it does not restate or amend it.
2. **World capability ceilings exist and are per-world**: `id world caps`
   sets a ceiling of _known capabilities only, no `*`_
   (`pkgs/id/src/cli.rs`, world caps `--ceiling`). A parcel policy is
   expressed in the same capability vocabulary and bounded by the same
   ceiling mechanism.
3. **The self-hosting frame** (#5975): our permission defaults are
   server-admin choices on a self-hosted server, not protocol
   requirements; the interop contract is what a third-party server must
   implement to interoperate. §5 sorts every parcel rule into exactly
   one of those two buckets.
4. **The prior-art verdicts** (#5989's scope, and the issue body's
   precedent section): Second Life land is the fullest implementation
   of land as a capability domain (parcel permissions, group-deeded
   land, per-parcel ban lists, per-parcel script permissions);
   LambdaMOO/MUSH used room ownership + quota instead of land markets;
   Decentraland-style tokenized land is a dead end for id's purposes.
   §2's model is the Second Life shape translated onto id's substrate;
   §6 records the tokenized-land exclusion.
5. **Writer sets are the authority substrate** (#5545, landed):
   a `WriterSet` (`pkgs/id/src/idset.rs`) is an owner-signed, versioned
   set object — `set_id` derived as BLAKE3 over the owner key and the
   length-prefixed purpose string when scoped, `entries` admit writers,
   `excludes` un-admit them and **exclusions win**, and a `Rescind`
   object erases a target's already-counted writer claims (bounded to
   its causal past — writer-claim semantics only; §4.3 keeps it there).
   §4 names parcels as one purpose of that substrate.

## 2. Parcel domain model

A **parcel** is a record in the world's journaled state with four parts:

| Part              | Content                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Identity**      | The parcel's writer-set ID: `derive_set_id(world_author_key, "parcel:<world-id>:<parcel-id>")`. Identity is derived from the controlling key and the parcel's name inside the world — it is not minted, registered, or tradable                                                                                                                                                                                         |
| **Extent**        | A descriptor of the region of the world the parcel covers, in the world's own coordinate scheme (cell range, room ID, or author-defined region name). The world author defines the scheme; the server treats the extent as an opaque descriptor it can test membership against (is this position/object inside this parcel?)                                                                                            |
| **Policy bundle** | The parcel's rules, in the world's capability vocabulary: (a) _script permissions_ — which capability functions code running in/on this parcel may use, as a subset of the world ceiling; (b) _access list / ban list_ — who may enter, build, and run scripts, expressed through the grant shape in §4; (c) _asset rules_ — which object/asset classes may be placed or must be removed, as author-defined class names |
| **Control**       | The writer set itself: the keys admitted by its current version hold the writer authority the set grants over the parcel (exercise its policy bundle, author inside it). Admitting/excluding members is _not_ among the granted powers — membership changes are new versions signed by the set's owner alone (§4.1)                                                                                                     |

Consequences of this shape:

- **A parcel is a domain, not a thing.** It confers no authority by
  itself; it is the _scope_ at which a policy bundle and a writer set
  apply. Holding parcel control is holding a grant (§4), and the parcel
  record without a live writer-set version is inert.
- **The degenerate cases are free.** A world with no parcels behaves
  exactly as worlds behave today (world ceiling + world-level grants).
  A one-room world is a single parcel under the world ceiling — the
  LambdaMOO room-ownership shape — with no extra machinery.
- **Group-deeded land needs no group primitive.** Second Life's
  group-deeded parcel maps to a writer set whose entries admit several
  keys: the admitted keys share the parcel's writer authority because
  the _set_ admits them. Administration of the set itself is not
  shared by admission — it stays with the set's owner (§4.1); a group
  that needs autonomous administration holds a derived sub-domain set
  under its steward's own key (§4.1), bounded by this parcel's policy
  per §3. Membership changes are journaled set versions, not
  transfers.
- **Subdivision is authoring, not sale.** Splitting a parcel publishes
  two parcel records whose extents partition the original, each with
  its own derived writer set (§3 governs what their policies may say).
  Merging is the inverse. Neither operation creates or destroys
  authority; both are policy edits by whoever holds control of the
  enclosing domain.

## 3. Nesting and attenuation rule

The rule, stated once and applied everywhere:

> **Effective authority at a point = world ceiling ∩ enclosing parcel
> policies (outermost to innermost) ∩ the actor's grant chain.**
> Every layer may only narrow the layer above it. A layer that purports
> to widen — a parcel policy naming a capability outside the world
> ceiling, a sub-parcel admitting a writer the enclosing parcel
> excludes, a delegated grant outliving its parent — is not an error to
> negotiate; it is **void at verification time**, and the narrower
> reading stands.

- **Monotonicity makes depth safe.** Sub-parcels may nest to any depth
  because each level is an intersection with the levels above; depth
  cannot manufacture authority, so the design sets no depth limit.
  (Authoring tools may warn past a small depth for legibility; that is
  author policy, §5, not a server rule.)
- **Exclusions dominate at every level.** Mirroring the substrate rule
  that exclusions win inside a writer set, a ban recorded at _any_
  enclosing level — world ban, parcel ban — excludes the actor from
  the inner domain even when an inner grant admits them. This is the
  per-parcel ban list with the only semantics that make bans worth
  having: an inner domain cannot un-ban what an outer domain banned.
  The converse is false by design: an inner ban excludes locally even
  when the outer domain admits — narrowing is always available.
- **Expiry composes by minimum.** Where grants in the chain carry
  expiries (attenuated-capability child minting), the effective expiry
  at a point is the earliest expiry in the chain; a renewal is a new
  grant from a holder whose own grant is still live.
- **Ceiling changes are prospective.** If a world author lowers the
  world ceiling, parcel policies above the new ceiling are not edited —
  they are intersected at verification time, so the lowering takes
  effect immediately and reversibly. Raising a ceiling likewise does
  not retroactively widen any parcel: each parcel's policy still says
  only what it says.

## 4. Grant shape

Parcel control and parcel rights are grants on the writer-set /
delegation substrate — one shape for all of them:

- **Control grant.** The parcel's writer set (derived ID per §2) is
  the control grant. Publishing a new version of the set — admit a
  co-controller, exclude a banned key — is the only way control
  changes. Versions are the sequence numbers of the publishing events
  on the owner's chain, and the owner signs every version, so the
  control history of a parcel is auditable from the chain alone.
- **§4.1 Membership management is owner-only.** Admission to a writer
  set grants the authority the set exists to grant; it grants no
  authority _over the set_. A member cannot admit or exclude other
  members, because the substrate (§D2 of the writer-set design) gives
  members no power to sign new set versions — every version is the
  owner's. This design does not paper over that: a parcel's membership
  changes always carry the set owner's signature, so shared
  _membership administration_ is obtained only in two substrate-true
  ways: (a) **derived sub-domain sets** — the owner derives a
  sub-parcel (or sub-domain) set under the delegate's own key
  (`derive_set_id(delegate_key, "parcel:<world>:<parcel>:<sub>")`);
  the delegate is that set's owner and manages its membership alone,
  while §3's intersection rule keeps the sub-domain inside the
  enclosing parcel's policy; or (b) **owner countersigning** — members
  propose changes and the owner signs them, which is the honest shape
  when a group wants one flat membership list. Anything that looks
  like member-managed membership without one of these two shapes is
  not available on this substrate and is not promised here.
- **Use grants.** Entry, building, and script-running rights inside a
  parcel are attenuated capabilities minted by a set member: subset of
  the parcel's policy bundle, earlier-or-equal expiry, optionally
  narrowed to a sub-extent. Onward _delegation_ is controlled: a
  holder can mint a further-attenuated child only where the parent
  grant explicitly allows it (delegation defaults to no, per the
  programme's grants model). Onward _sharing_ is **not** controlled,
  and this design does not pretend otherwise: a capability in the
  attenuation design is a bearer secret — anyone holding the secret
  can use it, and the server cannot distinguish the grantee presenting
  it from anyone the grantee handed it to. `may_delegate` governs
  minting children; it does not bind a capability to its grantee.
  Parcel use grants therefore provide _attributable issuance and
  revocability_ (§4, revocation layer (c)), not non-transferability.
  A world that genuinely needs holder-bound rights must layer a
  holder-binding mechanism (for example, presentation bound to a
  session key the server challenges) on top; that mechanism is an
  open point (§7.6), not a property of this substrate.
- **Revocation is layered, deliberately — and each layer uses its
  own mechanism.** (a) _Control_ is revoked prospectively by a new
  writer-set version or an entry in `excludes`. (b) _Writer claims_
  are erased by `Rescind` — and only that: `Rescind`
  (`pkgs/id/src/idset.rs`) names a set ID, a version, a target writer
  entry, and a causal bound; it erases the target's already-counted
  claims in its causal past and leaves future claims untouched. It
  cannot revoke an issued capability, and this design does not ask it
  to. (c) _Use capabilities_ are revoked by capability ID from the
  attenuation design: a capability carries `{id, …, parent?,
may_delegate, revoked}`, the journal records mint / attenuate /
  revoke by `id` and digest, and revoking a capability revokes its
  attenuated subtree (children minted from it carry its `id` as
  `parent`, and a revoked ancestor fails verification at use).
  None of the three un-copies anything the revoked party already
  holds — revocation stops future access and future sync, exactly as
  in the programme's grants model. Bans (§3) are the fast path: an
  exclusion takes effect at the next verification without waiting for
  grant expiry.
- **What a grant is not.** It is not signed over to a buyer, not listed
  anywhere, not priced by the protocol, and its derived ID is not an
  asset identifier. A world author may build rent, dues, or markets
  _as world policy on top of_ grants (§5); the substrate neither knows
  nor cares.

## 5. Server enforces vs world-author policy (inside the #5975 frame)

| The **server** enforces (protocol; load-bearing for interop)                                                                                                                                                                                                                                                                                                                                           | The **world author** decides (policy; never an interop requirement)                               |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| Attenuation monotonicity: verification intersects ceiling, parcel policies, and grant chain (§3); widening layers are void                                                                                                                                                                                                                                                                             | Whether the world has parcels at all, and their extents, names, and layout                        |
| Authenticity: writer-set versions and grants verify against the owner's chain and signatures before they take effect                                                                                                                                                                                                                                                                                   | The content of each parcel's policy bundle: script-permission subset, asset classes, entry rules  |
| Access enforcement at the boundary: every operation is checked against effective authority at the **affected extent**, not merely at the actor's position — entry against the destination parcel, building against the target object's parcel, script execution against the parcel the code runs in/on. An actor standing in a permissive parcel gains nothing over a restrictive parcel they act into | Who receives control and use grants, on what social or economic terms (rent, dues, invitation)    |
| Ban dominance: an exclusion at any enclosing level excludes at every inner level                                                                                                                                                                                                                                                                                                                       | Default policies a new parcel starts with on that server (the server admin's defaults, per #5975) |
| Journaling: parcel records, set versions, and rescinds are journaled world state, replayable and auditable                                                                                                                                                                                                                                                                                             | Subdivision and merging of parcels; sub-parcel creation                                           |
| Resource ceilings: the world's hard limits (compile, fuel, storage budgets owned by the server-invariants work) bound every parcel; a parcel cannot spend the world past them                                                                                                                                                                                                                          | Aesthetic and conduct rules expressed as asset classes and bans                                   |

The interop consequence, per #5975, splits by role — because dropping
a narrowing policy _widens_ effective authority, "ignoring parcels" is
not a safe fallback for an enforcer:

- **Clients** that only omit parcel _presentation_ interoperate at
  world granularity: they see the world ceiling and world-level
  grants, and parcels are invisible to them. Presentation is not
  enforcement, so nothing is widened.
- **Authoritative servers** — any server that hosts a world and
  enforces access to it — must implement the left column for
  parcelled worlds. A parcel-unaware server must **decline to host a
  parcelled world**, or **delegate enforcement to a parcel-aware
  authority**; it may not host the world and skip the parcel layer,
  because §3's bans and narrowings are exactly what skipping would
  silently drop (a world-level grant would admit an actor into a
  parcel that bans them). Hosting a parcelled world _is_ claiming
  parcel-aware enforcement.

## 6. Tokenized land: ruled out

Per the issue body, and not re-opened here: parcels are never tokens.
There is no parcel asset, no on-chain or in-protocol land market, no
scarcity instrument, and no transfer-as-sale operation in this design.
Control and use move exclusively by grant, attenuation, exclusion, and
writer-claim rescission (§4). The negative lessons of tokenized-land systems —
financialised scarcity without better worlds — are recorded in the
issue's precedent section; this design's answer to "who holds the
land?" is a signed set version, not a ledger of ownership tokens.
In-world economies remain possible as author policy layered on grants
(§5); they are not protocol.

## 7. Open points (with assumed defaults)

1. **Extent encoding.** The concrete membership test for extents
   (coordinate ranges vs named regions) depends on the world's spatial
   model, which no programme child has fixed yet. _Default assumed:_
   the extent stays an author-defined opaque descriptor with a
   server-implemented membership predicate per world type, as §2
   states; a concrete encoding is designed with the first world type
   that ships parcels.
2. **Interaction with dynamic user functions**
   ([#5964](https://github.com/developing-today/code/issues/5964)).
   A parcel's script-permission policy is the natural admission point
   for per-user functions inside a live world. _Default assumed:_ §2's
   policy bundle is where #5964's design reads its per-parcel
   admission decision; the DLL mechanism itself, and its gating
   evidence (#5995, #5996), are #5964's to settle — nothing here
   pre-decides them.
3. **Boundary enforcement across bridges/federation** is
   [#5882](https://github.com/developing-today/code/issues/5882)'s
   scope. _Default assumed:_ §3's intersection rule is evaluated by
   the hosting server from journaled state, so a bridged actor carries
   no parcel authority the home server did not journal.
4. **#5989's survey landing.** If the prior-art survey produces a
   capability-domain model that contradicts §2's writer-set mapping,
   this note gets an amendment rather than a silent divergence (the
   fleet's design-amendment rule). _Default assumed:_ the Second Life
   mapping in §1.4, which the issue body already records.
5. **Per-parcel budgets.** Whether resource budgets should be
   attributable per parcel (not just per world) is a server-invariants
   question. _Default assumed:_ budgets stay per-world (§5); parcel
   attribution, if wanted, is metering on top of journaled parcel
   identity, not a new enforcement layer.
6. **Holder-bound use grants.** §4 records that use capabilities are
   bearer <redacted> and cannot be made non-transferable on this
   substrate. If a future world needs holder-bound rights, a binding
   mechanism (session-key challenge at presentation, or equivalent)
   must be designed. _Default assumed:_ bearer semantics stand;
   issuance is attributable and revocable, sharing is unpoliceable,
   and no parcel rule in this note depends on telling a grantee from
   their delegate-by-secret.
