# Design: compile economics — compiled-world/DLL caching, compile-cost penalties, premium gating

- **Date:** 2026-11-05
- **Status:** proposed design for review; no implementation is included here.
- **Issue:** [#5965](https://github.com/developing-today/code/issues/5965), part of the worlds design program [#5955](https://github.com/developing-today/code/issues/5955) (statements S39, S43, S44 of the 2026-11-04 brief).
- **Inputs:** triage of #5965 by task 10334 (verified at main, 2026-11-05); current `pkgs/id` compile and sandbox code at this checkout; sibling sub-scopes of #5955 — the capability model (custom platforms), the DLL design, the server-invariants child (tick/gas budgets), and [#6016](https://github.com/developing-today/code/issues/6016) (per-function gas pricing hooks).
- **Method:** every "current state" claim below is tied to code at this checkout. Where this design spends a budget another child of #5955 owns (runtime fuel, gas pricing), it names the seam and does not redefine that budget.

## Decision to make

Compilation is a server resource. Decide (1) how compiled worlds and DLL-marked libraries are cached and shared, (2) what a compile costs the user who caused it, and (3) which compile capabilities are free, earned, paid, or admin-only — with defaults a server admin can change.

## Recommendation

Build a **content-addressed, server-side compile cache** keyed by everything that determines the output bytes (platform tree hash, source closure hash, DLL dependency closure hash, compiler binary digest, target), with three sharing scopes (author-only, server, public-by-hash) and three eviction tiers (per-job scratch, server LRU, pinned "semi-permanent"). Charge compiles in **compile credits** — measured compiler CPU cost, token-bucket throttled with progressive delay — as a budget **separate from runtime fuel**, so a throttled author's already-published world keeps running untouched. Gate the expensive capabilities (priority compiles, pinning, custom platforms, native targets) behind the contributor / patron / admin tiers of one admin-editable matrix; keep the existing hard sandbox limits as ceilings no tier can buy past.

## 1. Terms

- **Compile job:** one request to compile a `CompileSpec` (ordered files, first `main.roc`) against one platform tree for one target (`wasm32` or native `x64musl`), as in `world_compile.rs` today.
- **Artifact:** the compiled output (world module or DLL-marked library), identified by its content hash, as at install today.
- **Author:** the signing key that requested the compile. All charging and quotas are per author key; the server-admin token is an operator credential, not an author.

## 2. Cache key and sharing rules

### 2.1 Key

A cache entry is keyed by the tuple:

```
key = BLAKE3(
  platform_tree_hash      ||  # platform.roc + every platform module + targets/*/host.*
  source_closure_hash     ||  # ordered (file name, file bytes) of the CompileSpec files
  dll_closure_hash        ||  # sorted content hashes of the DLL artifacts the compile links
  compiler_blake3         ||  # digest of the roc binary, as already computed today
  target                      # wasm32 | x64musl
)
```

- **Platform tree hash**, not platform name: two servers (or two versions) with different platform bytes must never share an entry. The tree is small and fixed per server configuration, so hashing it per compile is cheap.
- **Source closure hash** covers names *and* bytes in request order — file names are semantically load-bearing in Roc module resolution.
- The **seed is not in the key**: the seed parameterises `init` at install/run time, not the compiled bytes (see `CompileSpec` in `world_compile.rs`). One artifact serves every seed.
- Compile **limits are not in the key**: they bound the job, they do not change output bytes. An entry produced under stricter limits is valid under looser ones.
- The entry is stored under its key, and the artifact under its own content hash; a hit is served only after the stored artifact's hash re-verifies against its content-hash name. A cache label is never trusted on its own (no poisoning by mislabelled entry).

### 2.2 Determinism gate

Cross-author reuse is sound only if the same key produces the same artifact bytes. Before server-scope or public-scope sharing (§2.3) is enabled for a compiler/platform pair, a **determinism proof** must be on record for that pair: the same spec compiled twice in clean job directories yields byte-identical artifacts. Until then, that pair's cache operates at author scope only (reuse is still safe there: the author re-verifies the artifact hash at install, and a nondeterministic compiler harms only the author's own hit rate). The proof is re-run when `compiler_blake3` or the platform tree changes — both are in the key, so a stale proof can never bless a new pair.

### 2.3 Sharing scopes

Each entry carries one scope, set by the author's tier and choice at compile time:

| Scope | Who may hit it | Default for |
| --- | --- | --- |
| `author` | the same author key only | unpublished / private source |
| `server` | any author on this server | published worlds and libraries |
| `public` | anyone who can name the key (i.e. present the identical inputs) | DLL-marked libraries and platform trees |

- **What a cross-author hit leaks:** that *someone* previously compiled byte-identical inputs on this server, and (by timing) roughly when the entry was created. It does not leak who, which world, or the source itself — a hit requires already possessing the exact source bytes to form the key. For public worlds and libraries this is acceptable and is the brief's stated feature ("if somebody makes another world with the same platform and source code, it would be reused").
- For **unpublished source** the existence leak can matter (it confirms a guess at private source). Authors compiling unpublished source get `author` scope by default and may opt in to wider scopes; they are never opted in silently.
- **Cross-server reuse** happens only by artifact transfer: an artifact is content-addressed, so a receiving server verifies the bytes against the hash and needs no trust in the sending server. Federated *key* directories (asking other servers "have you compiled this?") are deferred (§7).

## 3. DLL-marked libraries

A DLL-marked library (mechanism owned by the sibling DLL design) is a compile job whose artifact is meant to be linked by later compiles. It uses **the same cache, key, scopes, and penalty rules**, with two differences:

- Its key becomes an input to dependents: a world compile's `dll_closure_hash` is computed from the content hashes of the exact library artifacts it links, so a library change transitively misses every dependent — no stale linkage is possible.
- Libraries default to `public` scope: a library nobody can reuse is just a world with extra steps. Pinning a library (§4 tiers) is how a popular library stays resident.

## 4. Eviction tiers

| Tier | Name | Eviction rule | Who gets it |
| --- | --- | --- | --- |
| 0 | job scratch | deleted when the job ends (today's behaviour) | every compile, always |
| 1 | server LRU | least-recently-hit eviction when the server cache exceeds `cache.lru_bytes` (default 2 GiB) | any entry not pinned |
| 2 | pinned ("semi-permanent") | **no** LRU eviction while the pin is active | per §5 matrix, within the pinner's `pin_bytes` quota |

"Semi-permanent" concretely means: a pinned entry survives LRU pressure indefinitely, and leaves tier 2 only when (a) the pin lapses and a grace period (default 30 days) passes without renewal, (b) the pinner's pin quota is reduced below current usage (coldest pins demoted first), (c) an admin revokes the pin, or (d) the entry is invalidated (below). A demoted entry falls to tier 1; it is not deleted outright.

**Invalidation beats every tier.** An entry whose compiler digest or platform tree is revoked (security advisory, broken compiler build) is hard-evicted from all tiers, pins included. Pins buy retention against *capacity* pressure, never against *correctness/safety* removal.

## 5. Penalty model

### 5.1 Currency

The protocol currency is the **compile credit**, not money. One credit = one compiler CPU-second, measured on the job (wall clock under the job's limits is the fallback where CPU time is unavailable). A server operator may map credits to money, subscriptions, or nothing at all outside the protocol; the design only requires that cost be *attributed*.

- **Cache hit: 0 credits.** Avoiding a compile is the behaviour the economics must reward; charging for hits would punish using pre-cached objects, the opposite of the brief.
- **Successful compile:** actual measured cost.
- **Failed compile** (source errors, validation refusal): 25% of measured cost, minimum 1 credit. Iteration on honest errors must stay cheap, but a zero price on failures is a compiler denial-of-service.
- **Admin compiles:** metered and logged, not charged and never delayed — the operator is the house. (Today all compiles are admin compiles; this stays true until §6's later phases ship.)

### 5.2 Delay, not denial — and never a stalled world

Credits are enforced with a **token bucket** per author: capacity `bucket_burst` credits, refilled at `bucket_refill_per_day` credits/day (both per tier, §6). A compile whose cost would overdraw the bucket is **delayed** until the bucket covers it (or partially started when the bucket covers a bounded first slice — v1 keeps this simple: whole-job delay).

The brief's core invariant is preserved structurally:

- A delayed or throttled compile **never blocks the author's running world**: the world keeps executing its last published artifact under its own runtime fuel budget. The penalty lands on the *next version's arrival time*, which is exactly "they just keep running the code they'd already published in the meantime".
- Compile throttling and runtime fuel are independent: an author can be compile-throttled to zero and their worlds still run; an author with a full compile bucket gets no extra runtime fuel.

### 5.3 Composition with the other budgets

- **Runtime fuel / tick budgets** (server-invariants child of #5955; `sandbox.rs` metering today): unchanged. Compilation happens outside the sandbox guest; no fuel is charged for compiling, and no compile credit buys fuel.
- **Per-function gas pricing** (#6016): consumes runtime metering data. Compile credits are an input to *tier standing* only (an author consistently burning compile credits is visible in the same metering stream), not a term in gas price.
- **Custom-compiled platforms** (capability-model child): a platform compile is a compile job with a bigger closure. **Same cache, same key rules, same penalty rules** — the measured-CPU currency makes the heavier cost fall out naturally. One difference: a platform artifact enters `server`/`public` scope only after admin approval, because a platform defines a capability surface, not just code (§6).

## 6. Gating matrix (defaults; every value is admin-changeable config)

Tiers: **free** (any author key), **contributor** (granted by an admin or by a board/world role attestation), **patron** (premium — however the server operator sells or grants it), **admin** (operator). Cells give the default; the config key follows in parentheses.

| Capability | free | contributor | patron | admin |
| --- | --- | --- | --- | --- |
| Run worlds from pre-cached (`server`/`public`) artifacts | yes | yes | yes | yes |
| Compile own source | delayed, quota (`compile.bucket_refill_per_day`: 10 credits/day, burst 20) | delayed, larger quota (100/day, burst 200) | priority queue, larger quota (1 000/day, burst 2 000) | unlimited, metered |
| Cache scope for own entries | `author`, opt-in `server` | up to `server` | up to `public` | any |
| Pin entries (tier 2) | no | 64 MiB (`pin_bytes`) | 1 GiB (`pin_bytes`) | unlimited |
| Native target (`x64musl`) compiles | no | yes | yes | yes |
| Custom platform compiles | no | propose only (artifact stays `author` scope) | propose only | approve + any scope |
| Compile size/time limits | hard ceilings (§Current state) for **all** tiers — config may lower per tier, never raise past the constants | | | |

**Free-tier shape** (the brief's question, answered): a non-paying author can (a) run any pre-cached popular object, (b) compile their own source with delay under a small daily quota — publishing is never fully paywalled — and (c) reuse their own cached entries forever. What they cannot do is pin, compile natively, or skip the queue.

**Config shape:** one table in server config, keyed exactly as the parentheses above (`compile.bucket_refill_per_day.<tier>`, `compile.bucket_burst.<tier>`, `pin_bytes.<tier>`, `cache.lru_bytes`, `pin.grace_days`, …). Changing a value changes future enforcement only; in-flight jobs and existing pins are honoured to the end of their current terms.

## 7. Phasing (implementation follow-ups, not this design)

1. **P1 — shared cache:** key, scopes, tier 0/1, determinism proof harness. No charging; metering logged only. (This alone delivers the brief's reuse win.)
2. **P2 — penalty:** credits, token buckets, delay queue, failure discount.
3. **P3 — pinning + gating:** tier 2, pin quotas, the §6 matrix as config, platform-approval flow.

Each phase is its own implementation issue referencing this design; none is filed by this design doc itself.

## 8. Explicit deferrals and open questions

- **Money:** whether and how credits map to payment is a server-operator decision, deliberately outside the protocol.
- **Cross-server key federation:** deferred; content-addressed artifact transfer (§2.3) covers manual sharing.
- **Credit pricing calibration:** the §6 numbers are starting defaults chosen to be boring (a 120 s worst-case compile ≈ 120 credits ≈ the free burst). P1 telemetry should re-derive them from real compile-cost distributions before P2 enforcement.
- **Sybil resistance:** free-tier quotas are per author *key*, and keys are cheap. A determined author can shard compiles across keys; the design accepts this for v1 (the cost is still paid in aggregate server CPU only up to the *server's* global compile concurrency cap, which is an operator setting, not a per-author one) and flags per-IP/per-attestation weighting as a P3+ question.
