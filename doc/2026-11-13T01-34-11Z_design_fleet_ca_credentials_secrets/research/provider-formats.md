# Primary-source research: fnox, vault interfaces, SOPS/age, SecureStore

**Checked:** 2026-11-12. **Scope:** current public API/docs and repository baseline for #9160 design. This is not a live account test, performance benchmark, security audit, or authorization. Claims below are deliberately split between what official source says and what remains unverified.

## Findings that affect the design

* `fnox-client` is a real published Rust crate, but its official API is a **read-only client for an already-running fnox daemon** and the `fnox env --json` data model. It sends one environment-resolution request. It cannot start daemon, populate cache, or make provider calls. A miss requires caller to run `fnox env --json` itself. API functions `Client::new`, `.with_timeout`, `.hello`, `.resolve_env`; docs say public API semver-covered, with wire/path/peer details evolving alongside protocol. Therefore it is plausible as optional cache-hit accelerator, not reusable Rust provider implementation, authoritative resolver, or writer.
* fnox daemon holds secrets in memory only, over local Unix socket/named pipe, but any same-user process can ask for cached values. Cache is not provider-change-aware: docs direct caller to `fnox get --refresh` or `fnox daemon clear <key>`. Config/profile/provider settings/relevant environment changes, stop/idle exit clear or partition cache; `--refresh` bypasses stale entry. Reads can auto-start daemon; client crate cannot. Daemon is therefore not an independent authorization boundary or freshness oracle.
* `fnox sync` is an encrypted local file snapshot (`fnox.local.toml` example), requires manual refresh (`fnox sync --force`), and serves cached ciphertext without contacting original provider. It is explicitly an offline snapshot, not auto-invalidating cache. Age target can avoid cloud dependency; hardware age plugins and recipient choices alter bootstrap/recoverability. A lost local identity can make the synced copy unrecoverable; source vault remains authority.
* Provider interfaces are heterogeneous: fnox docs say BWS provider invokes `bws` CLI and can write via `fnox set`; OP and Bitwarden Password Manager providers are read-only. BWS read lookup performs `bws secret list <project>` once then local match, so multiple configured secrets from that project can share a list call, not necessarily an SDK batch/get. OP uses CLI; grouped references use one `op inject`, with a fallback to individual `op read` per secret if inject fails. BW requires a separate `bw` unlocked session or `rbw`. These facts make “one provider-neutral SDK”, “all writes supported”, and “no subprocess overhead” false assumptions.
* BWS official docs scope every CLI operation to machine-account access; CLI supports create/edit/get/list and process injection. Docs warn creating many sessions/token-auths from one IP in short windows can rate-limit. SDK docs show Rust client with async auth/list and warn beta/missing functionality. `op` references, CLI `op read/run/inject`, and service-account vault scopes are first-party documented; service accounts are rate-limited and Connect is a separately operated high-volume/low-latency option. No provider-specific CAS guarantee or rate-limit number was verified; model capabilities conservatively and test conditional writes/races.
* SOPS/age/sops-nix fit the current NixOS deployment workflow but solve a different problem from online vault reads: encrypted structured artifacts, recipient encryption, and runtime provisioning. Private identities remain the recovery/security dependency. Age recipient rotation does not erase prior Git history; rotation of secret value is needed to revoke access to already-copied plaintext/ciphertext by former recipient.
* SecureStore has an ergonomic direct Rust API and portable file format, but upstream documentation specifies AES-128-CBC + HMAC-SHA1 + PBKDF2-SHA1 and symmetric key-file/password custody. Its docs do not establish external audit, robust concurrent-write behavior, Fleet integration, or long-term support policy. No reason to add a second canonical file format while SOPS/age already exists.

## `fnox` public surface — what is verified

### Crates.io/docs.rs (`fnox-client` 1.48.0)

Primary source: <https://docs.rs/fnox-client/1.48.0/fnox_client/> and <https://docs.rs/fnox-client/1.48.0/fnox_client/struct.Client.html>. Docs.rs reports 1.48.0 published 2026-11-09, MIT; repository `https://github.com/jdx/fnox`; dependencies include serde/serde_json, blake3, libc, windows-sys, and it does not depend on fnox-core/provider SDKs. API docs say “read-only client for the fnox daemon” and data types for `fnox env --json`; one request over Unix socket/named pipe, no fnox subprocess. It can resolve only via already-running daemon, never starts it, stores values or causes provider fetch. On miss the calling program performs normal CLI resolution. `resolve_env` returns `EnvOutcome`; `Client::with_timeout` defaults to five seconds; API semver coverage excludes the shared wire/path/peer protocol internals (those track the crate's `WIRE_VERSION`).

**Implication:** investigate as optional, no-provider-dependency, read-only hit path. Do not embed fnox internals or parse private wire protocol. Never equate `Miss` with not-found, `Disabled` with empty, or daemon age with current provider value. Confirm crate's actual MSRV and dependency tree against Fleet before adoption; docs.rs metadata captured here does not establish MSRV compatibility.

### fnox daemon

Primary source: <https://fnox.jdx.dev/guide/daemon> (docs displayed current v1.48.0). Official claims: per-user optional daemon; memory-only values; Unix socket or Windows named pipe; peer checks same user; no network listener; same-user programs can request cached values. Read commands can start it; mutations/admin commands including `set`, `remove`, `sync`, `reencrypt`, `edit`, provider admin and lease creation bypass daemon. Refresh is explicit; automatic drop when daemon stops/idles or relevant config/profile/provider/auth environment changes. `daemon_cache=false` excludes a provider/secret. Non-interactive misses resolve in daemon and do not prompt. Protocol version 6 was displayed in fetched docs at research time; do not hardcode as a stable Fleet contract.

**Implication:** same-user daemon is a local performance mechanism, not access control against a compromised account. Fleet-specific classification, per-secret freshness, revocation tombstones and explicit invalidation must remain authoritative.

### fnox encrypted sync cache

Primary source: <https://fnox.jdx.dev/guide/sync> (docs displayed current v1.48.0). Officially described as reading provider values and saving encrypted copies in gitignored `fnox.local.toml`, using chosen encryption provider; resolution then decrypts copy and skips original provider. Cache is manual refresh; `fnox sync --force` refreshes, can filter names/provider. Can be local age or cloud KMS; latter requires cloud API at read. Age plugin table distinguishes recipient/identity behavior (for example TPM hardware protection vs recovery/multi-machine). In docs, production example deliberately disables daemon cache on both production age and remote provider and avoids syncing production profile.

**Implication:** strong prototype comparator for offline continuity, but its “source of truth” is not freshness; manually synced copy must be owned under a distinct snapshot policy with expiration/revocation rules. Do not import its config or cache wholesale if it duplicates Fleet policy/state.

### fnox provider and injection capabilities

Primary sources: <https://fnox.jdx.dev/providers/overview>, <https://fnox.jdx.dev/providers/bitwarden-sm>, <https://fnox.jdx.dev/providers/1password>, <https://fnox.jdx.dev/providers/bitwarden>, <https://fnox.jdx.dev/providers/age>, and <https://github.com/jdx/fnox> (repository overview). The fetched docs identify fnox version v1.48.0.

| Surface | Documented behavior | Limits relevant to Fleet |
|---|---|---|
| BWS (`bitwarden-sm`) | Requires `bws` CLI + access token; provider type supports remote write through `fnox set`; reads `value`, `note`, `key`. A reference lookup invokes `bws secret list <project>` and matches key locally; docs say duplicate key name uses first CLI result. | CLI subprocess, project-scoped machine account, key/name shape and ambiguity; not Bitwarden Password Manager. CLI value passed as command-line argument for `fnox set` (visible to same-host process listing per fnox docs)—unsafe for Fleet default write path. No native SDK embedding demonstrated. |
| 1Password | Requires `op` CLI; read-only provider. Service-account token or existing `op` session. One `op inject` call for multiple secret references, falling back to one `op read` per secret if inject fails. Discovery can list metadata/tags and uses configured vault; otherwise all accessible vaults. | No `fnox set` write to OP; field references are not full item fidelity/reconciliation; fallback can be N subprocesses; service-account scope still separate. |
| Bitwarden Password Manager | Requires `bw` CLI unlocked session or `rbw`; read-only. Separate from BWS. Can select folder/collection/org; standard/custom fields and TOTP code documented. | Separate authorization/session; do not infer from BWS machine token. `rbw` backend documented experimental. No write or reconciliation. |
| age | fnox can encrypt values into config, re-encrypt to recipients, select key identity and plugins; ciphertext in config. | Private identity/bootstrap and recipient lifecycle remain external policy; Git history retention remains. Not an online provider ACL. |
| process/env | fnox's product model is passing secrets to child command as environment, and `op run` uses the same pattern; BWS `run` also injects to child process. | Environment is inherited/readable by child processes and may leak through diagnostics/core dumps; avoid assuming injection equals no-exposure. Fleet should prefer file descriptor/secure file or narrow explicit API where consumer allows; never shell history/argv. |

Fnox overview also advertises a broader provider catalog (including cloud stores, keychains, password-store and custom Lua). Catalog presence is not evidence of equivalent semantics, supported version, provider scope, CAS, paging, rate limits or secure-write suitability. Validate exact selected provider source, version and failure modes before capability advertisement.

## BWS / OP / BW — credentials, operations, and evidence limits

### BWS official Rust SDK

Primary source: <https://docs.rs/bitwarden/latest/bitwarden/>; repository linked from docs is <https://github.com/bitwarden/sdk-sm>. Docs.rs reported `bitwarden` 2.1.0 published 2026-09-30, describes it as the Bitwarden Secrets Manager Rust SDK, calls it beta/may be missing functionality, and shows `Client::new`, async `auth().login_access_token`, `secrets().list(SecretIdentifiersRequest { organization_id })`. Dependency graph includes optional `bitwarden-sm`; docs do not prove SDK parity with every CLI operation, page model, CAS, throttling semantics, or Fleet-compatible minimal feature/MSRV.

**Decision:** preserve existing BWS CLI path until an SDK prototype proves MSRV (Fleet workspace `rust-version=1.85`), lockfile, async/runtime, small-binary and behavior fit. SDK integration must not be justified by Rust language alone. Source check does not reveal production organization/project/credential scope.

### BWS official CLI / authentication

Primary sources: <https://bitwarden.com/help/secrets-manager-cli/> and <https://bitwarden.com/help/machine-accounts/>. CLI docs say access token belongs to a particular machine account; only secrets/projects that account can access can be operated. CLI has secret create/delete/edit/get/list and `run`; token may be supplied as `BWS_ACCESS_TOKEN`. Docs warn many sessions from same IP in short time can rate-limit. Secret list can be project-filtered and returns JSON records; get is by native secret ID; edit is by ID and supports key/value/note/project. A value can be carried on command line in the documented CLI write operation. This is evidence of CLI shape only, not a CAS guarantee; revision timestamps are exposed but no documented compare-and-swap precondition was found in the accessed CLI page.

**Implication:** authorization scopes are actual permission boundaries; keep capabilities per project and operation, use native IDs, guard writes by read/precondition/read-back, expose race window if provider has no CAS. Do not assume `bws run` creates process isolation—the official docs explicitly say it is not sandboxing. Do not pass secrets as argv in Fleet even if CLI accepts it.

### 1Password official CLI/service accounts

Primary sources: <https://www.1password.dev/cli/secret-references.md>, <https://www.1password.dev/service-accounts.md>, and the coordinator's existing first-party references at <https://www.1password.dev/sdks/manage-items/> and <https://www.1password.dev/connect/server-configuration/>. CLI secret-reference docs show item/vault/field references; `op read`, `op run`, and `op inject` are resolution/injection methods. Service accounts are scoped to specific vaults or Environments and support usage reports; docs say limits are subject to rate limits/request quotas. Same docs compare Connect as self-hosted REST API and best fit for high-volume or low-latency access after first fetch, but requires operating infrastructure; eligibility/plan and configured service were not tested.

The docs fetched describe read/injection and service account security, not a Rust-native library available to this Fleet build, exhaustive item write semantics, provider version/CAS, page size or numeric quotas. Keep a separate capability verification and isolated benchmark before treating `op` as interchangeable with BWS or Connect. No live service account token/vault scope was read.

### BW Password Manager is not BWS

Primary source for fnox's separate `bw` path: <https://fnox.jdx.dev/providers/bitwarden>; Bitwarden CLI source docs: <https://bitwarden.com/help/cli/> (not fetched successfully in this round; fnox provider page documents its own integration contract). fnox requires an unlocked `bw` session or experimental `rbw`; it is read-only. This does not authorize personal vault access and cannot be inferred from `BWS_ACCESS_TOKEN`. The dossier identifies separate Sweep B as approval-blocked. No `bw` session or personal vault was accessed.

### CAS, paging, throttling: negative evidence

Do not assert “provider supports CAS” merely because records have revision timestamps, or “list is complete” because one list call returned. The sources fetched here establish BWS list/get/create/edit and machine-account scoping, OP CLI references/injection and service-account vault scoping, but did **not** establish a documented portable CAS contract, a shared pagination contract, or numerical rate-limit budget. fnox provider docs identify subprocess patterns, not these service guarantees. Every adapter should expose `compare_and_swap=false` and guarded preflight/post-write/read-back until primary API docs and live isolated tests establish stronger semantics. Treat 403, 429, timeout and partial pagination distinctly; do not infer delete from any.

## SOPS, age and sops-nix primary documentation

* SOPS project primary README: <https://github.com/getsops/sops>. States structured encrypted-file editor supporting YAML, JSON, ENV, INI and binary; recipients/backends include cloud KMS, age, PGP. Repository identifies CNCF Sandbox status, MPL-2.0, public maintained source. This supports use as format/tool; not a claim of a particular security audit or age recipient revocation.
* age project primary README/spec link: <https://github.com/FiloSottile/age> and <https://age-encryption.org/v1>. Describes simple file encryption, explicit keys, multi-recipient file encryption, interoperable Rust implementation (`rage`), plugins; age recipients are public keys. Multiple recipients can decrypt the same payload. This gives explicit distribution/recovery mechanism, not policy enforcement or erase of old copies.
* sops-nix primary README: <https://github.com/Mic92/sops-nix>. Describes activation-time decrypt from SOPS files, one secret per file, declarative owner/group/mode, runtime provisioning, atomic replacement and optional rollback when encrypted files are in Nix store. It supports age/GPG (including SSH-key compatibility paths). Home Manager uses user runtime directory. It also states secrets cannot be used at Nix evaluation time. Its own examples show key path as a provisioned path; Fleet must verify target path/persistence and never interpolate private key or decrypted secret into derivation text.

**Design consequences:** use existing standard formats/toolchain with pinned versions; Fleet owns scope, manifest, encrypted-file operations and receipts, not crypto implementation. Private keys are not made safe merely because ciphertext is in Git. Add separate recovery identity held outside ciphertext and offline host bootstrap; check old Git history, Nix store, derivation, CI output, image layers and runtime paths. Declarative encrypted deployment artifacts do not substitute for machine-vault reads or dynamically rotated leases.

## NeoSmart SecureStore primary evidence and evaluation

Primary sources: Rust repository/README <https://github.com/neosmart/securestore-rs>, .NET protocol implementation <https://github.com/neosmart/SecureStore>, docs.rs release/API <https://docs.rs/securestore/0.100.3/securestore/>. Docs.rs showed `securestore` 0.100.3 published 2026-09-21, Apache-2.0 OR MIT, dependencies around AES/CBC/HMAC/PBKDF2/SHA1/subtle with optional OpenSSL, and primary `SecretsManager` API. Rust project README shows `SecretsManager::load`, `get`, set/save API and Rustls feature; protocol is cross-language JSON. .NET project README documents AES-128-CBC, HMAC-SHA1, PBKDF2-SHA1 at 256,000 iterations, and its own key/password choices. The primary source itself says its design does not target protection against compromised machine and cannot guarantee plaintext memory erasure.

**Challenge / limits:** direct Rust API and versioned portable file are genuine advantages for a tightly scoped static application. But that does not establish format suitability for Fleet's high-risk, multi-host deployment: symmetric key distribution is not age's multi-recipient public-key envelope, persistent cache demands rotation/recovery policy, and version-control rollback may resurrect old values. No retrieved source establishes a third-party cryptographic audit or safe multi-process atomic updates; this absence is not proof those properties fail. Need inspect implementation, tests, activity/release cadence, KDF bounds, MAC coverage/order, format migration and concurrency before any adoption.

**Recommendation:** retain as import/export-only test candidate; do not make a new long-lived canonical format or root archive default. SOPS/age is already used and has proper deployment integrations. If SecureStore has a proven interoperability or lightweight runtime advantage, adapter must preserve format in isolated scope and pass independent security review. Do not tune security judgment solely on algorithm names or repository stars.
