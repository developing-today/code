## Current project and implementation status

The current IETF PLANTS Working Group Internet-Draft is `draft-ietf-plants-merkle-tree-certs-08`, last updated 2026-11-01, dated 2026-11-02, active WG document, intended Standards Track, expires 2027-05-06. The former individual draft `draft-davidben-tls-merkle-tree-certs-10` is marked inactive/replaced. The current specification is an Internet-Draft, not an RFC/final standard; implementation must pin a revision and expect changes.

The `ietf-plants-wg/merkle-tree-certs` repository identifies itself as the working area for the WG draft and includes draft source, demo and a size-estimation tool. The separate `bwesterb/mtc` repository README expressly says it implements an outdated pre-“photosynthesis” version of the draft, that it differs from current revisions, and that TLS integration and ACME bits were not present. ## What MTC is and is not

The draft defines a new certificate form: a CA records TBSCertificate statements in issuance logs, signs checkpoints/subtrees, obtains cosignatures from configured cosigners, and supplies inclusion proofs. A standalone MTC carries the assertion and proof/cosignatures. An optional landmark-relative representation can omit signatures when relying parties are up to date with pre-distributed trusted landmark subtrees. This architecture targets logging overhead and certificate-size pressure, including large PQ signatures. It adds CA log, cosigner, mirror, monitor, client update and availability responsibilities.

**MTC certificate signatures do not establish a post-quantum TLS handshake or key exchange.** The subject public key, CertificateVerify scheme and TLS key-exchange group are separate protocol choices. Signing a certificate assertion with an ML-DSA key does not make a classical ephemeral TLS key exchange PQ, and a compact unsigned/landmark-relative form does not add PQ security. Fleet's PQ claim must be made only after a specific end-to-end TLS implementation negotiates and enforces appropriate PQ-capable KEX/signature algorithms and an independently verified trust path. MTC remains separate from and cannot weaken the ML-DSA-44 baseline.

The draft's standalone and landmark-relative modes have different freshness properties. The compact mode relies on current relying-party state; cold or stale clients need a conventional, fully verifiable fallback. Offline clients may not be able to retrieve logs, landmarks, status or cosigner updates. A root/issuer chain is still subject to ordinary algorithm, path, authorization and trust-anchor policy. Do not claim broad client compatibility from ASN.1 or a successful prototype parser.

## Test matrix and oracle

1. **Draft conformance oracle:** exact current draft revision, its normative test vectors and independent implementation output. Never accept solely because producer validates its own output.
2. **Proof oracle:** reconstruct proof/root and compare independent verifier; mutate each field/proof node and assert rejection; test wrong CA ID, issuer key, domain, trust anchor, expiry, signature type and duplicate/forked/stale checkpoint where applicable.
3. **Freshness oracle:** controlled verifier state versions labelled fresh/cold/stale/offline; mutate landmarks/log responses, replay old state, remove network and verify documented fallback or fail-closed result.
4. **Chain oracle:** verify same identity, SAN, validity, constraints, issuer and policy in conventional and MTC paths; require ML-DSA-44 where policy says so; separately capture TLS negotiated KEX. A conventional fallback is not evidence of MTC support.
5. **Size oracle:** count actual serialized certificate flight bytes at protocol boundary, not only abstract proof payload; include all certificates, chain, extensions, proof/cosignature, and separately chart other TLS handshake/KEX bytes. State exact implementations, compression settings and versions.
6. **Availability/recovery oracle:** stop CA, log, mirror, cosigner, monitor and update channel individually; assert issuance, validation and revocation behavior. Restore from backup and check consistency proof/monotonic state.

## Risks and alternatives

Potential upside is lower certificate/log overhead for large PQ signature/key material and integrated transparency. Costs include a non-final standard, scarce compatible verifiers, delayed issuance/batching, state freshness/update infrastructure, log/cosigner availability, monitor operation, revocation design, migration and independent security review. A conventional ML-DSA X.509 certificate with ordinary CT or private transparency monitoring is the baseline comparison. Other alternatives: reduce chain depth with issuer topology, use short-lived certs, benchmark TLS stacks and compression, or defer certificate-size optimization until clients support PQ signatures. Do not sacrifice availability, verifiability or algorithm policy merely to shrink a handshake.

Go is permitted only to continue optional interoperability experimentation when current draft and implementation are pinned, independent verifier tests pass, cold/stale/offline behavior is explicit, actual full-chain byte savings are material for a named relying-party set, and failure/operations costs are acceptable. Production or baseline adoption requires a separate decision and broad interoperability/security review; no outcome of these experiments changes mandatory ML-DSA-44 baseline or V1 acceptance.

## Unknowns and defaults

Unknown: current draft may change; “azul” means unclear; source of asserted Cloudflare implementation/deployment unclear; client/stack support and MTC integration status not established; concrete domain, trust, deployment, traffic profile and size target unknown; no local tests run. Defaults: no production use, no public endpoints, no DNS/trust changes, no MTC-only verifier, conventional certificate chain fallback, independent verifier required, measure complete serialized bytes, treat offline/stale verification as fail-closed or conventional fallback, and do not infer PQ KEX from certificate signature.
