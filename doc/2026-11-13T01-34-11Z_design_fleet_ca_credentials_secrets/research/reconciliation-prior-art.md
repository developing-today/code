# Reconciliation models beyond provider APIs

**Checked:** 2026-11-12. **Scope:** prior-art comparison for Fleet's credential reconciliation design, not an implementation specification or benchmark. All examples and test cases below are synthetic. No provider was accessed and no secrets were used.

## Findings in brief

Fleet can borrow the *shape* of established synchronizers—common-base comparisons, explicit conflict preservation, durable checkpoints, and refusal when the observed scope is suspect—but none solves the hardest Fleet constraints: authorization is not causality, file-level conflict copies do not preserve a credential's native identity, and a preflight read cannot serialize external editors. Keep the verified baseline at item/field granularity, gate destructive action on complete scoped observations, retain `zz.delete` as Fleet-owned immutable history, update the current native item in place, and label an unguarded write as racy rather than protected. No CRDT can magically serialize unguarded provider writes.

This is compatible with the settled reconciliation guard contract in `../architecture-review.md` ADR-S02 and with the requirements summarized in `secrets-prior-art.md`; it adds comparative evidence rather than replacing those decisions.

## Prior art: what the models actually provide

| System/model | Source-backed behavior | Useful borrowing | Boundary / rejection |
|---|---|---|---|
| **Unison** | A bidirectional file synchronizer retains per-replica archives to recognize changes since its last common state; its manual documents merge inputs as current versions from both roots plus the last archive, backup copies, conflict confirmation, and safeguards such as aborting on a missing mountpoint or an apparent whole-replica deletion. It can skip a conflict in batch mode; explicit `prefer`/`force` selects a winner. [U1] | Use a verified common base, distinguish unchanged / one-sided change / two-sided conflict, keep pre-change history, and make whole-scope disappearance an explicit safety stop. | A file archive is not a provider revision or cross-system CAS. `prefer newer`/`force` is not safe secret policy. A path is not a stable logical item ID; file merge programs do not establish secret semantics. Unison's archive is per replica pair and assumes its archive can be trusted, not per-field evidence across independently authorized hosted APIs. |
| **Syncthing** | Its BEP represents each file version with a vector of per-device counters; a device's monotonic sequence plus index ID supports incremental index exchange. Concurrent different file contents produce conflict copies (implementation docs describe modified-time/device-ID choice for which path keeps the ordinary filename); deletion is represented as a versioned tombstone. File version retention is a separate, configurable per-device strategy and may expire old copies. [S1,S2] | Keep causal/version evidence distinct from wall-clock timestamps; represent deletion explicitly; use resumable incremental scans only as an optimization atop a complete inventory model; preserve both concurrent values. | Syncthing's vectors track participating device writes, not arbitrary out-of-band API writers or grants. Conflict files change names and replicate as ordinary files—wrong for native credential identity or login/autofill continuity. Its configurable version retention is not Fleet's indefinite encrypted `zz.delete`. A tombstone says a participant observed deletion, not that Fleet is authorized to delete another provider's copy. |
| **rclone bisync** | bisync persists paired prior listings and supports recovery/resync modes. It explicitly fails when a non-resync listing is empty (to avoid deleting the other side), offers access-check marker files, checks filter-file changes before running, bounds deletion percentage, can keep conflict losers, and has final listing consistency checks. Its docs warn concurrent modifications are unsupported and can cause data loss. [R1] | Borrow fail-closed preflight for empty/unavailable scopes, scope/access sentinels, policy/filter fingerprinting, bounded delete guards, restartable listing state, and end-of-run consistency checks. | Marker files and matching listings do not prove that API permissions are complete; a valid marker can coexist with omitted items or lost field access. Percentage deletion heuristics are supplementary only. A successful listing comparison is not a remote readback, and a lock local to Fleet does not protect against another provider client. Do not make a two-sided file winner rule the secret conflict policy. |
| **CRDT multi-value registers / Automerge** | Automerge merges concurrent edits to independent object properties; concurrent assignments to one property are retained in a conflict set while an LWW value is exposed by default. Its operation IDs/counters and actor IDs, not wall-clock times, order the deterministic exposed winner. A later assignment resolves/removes the conflict from that property view. [C1] | For Fleet-owned metadata, retain causal context and all concurrent candidate values; field-level merge of disjoint edits is preferable to whole-object replacement. A deterministic display value can aid UI only if every candidate remains available. | CRDT convergence assumes edits are represented in the replicated operation history. A remote provider write can be unguarded, overwrite an unseen external value, or have an uncertain response; CRDT merge cannot recover a value never read into the log, nor make a provider apply conditional. LWW is not user intent or authorization. Do not resolve password, private-key, recovery, OTP, signer-policy, or trust-root conflicts via CRDT winner selection. |
| **Transactional outbox / saga** | AWS describes the local dual-write gap and places business-row plus outbox-row in one database transaction, then dispatches events; duplicate delivery requires idempotent consumers and ordering may matter. AWS points to saga orchestration when a transaction spans services. [A1] | Persist Fleet's intent and operation ID durably before remote mutation; replay with idempotency/reconciliation; record each remote acknowledgement/readback; model partial success explicitly. | The atomic transaction covers only Fleet's local database and its outbox. It cannot include independent vault APIs. An outbox is not exactly-once remote mutation or provider CAS. Never acknowledge a cross-provider commit merely because the local journal entry exists. |

## Fleet implications: explicit borrow/reject matrix

1. **Stable IDs:** borrow Unison's stable replica-pair archive identity and Syncthing's separate folder/name identity idea only abstractly. Fleet `global_item_id` must be generated/retained independently from title, path, username, provider-native ID, and field values. Map it to provider-native IDs; never turn a title rename into delete-and-recreate. For the spec's `zz.delete` refresh, snapshot immutable prior values first, then update the existing native login ID in place and read it back. This is a Fleet requirement, not behavior supplied by these synchronizers.
2. **Three-way, field-wise plan:** borrow `(current left, current right, verified common base)`. For each field, classify unchanged, one-side changed, both same, both changed differently, absent, inaccessible, and unknown. Merge independent changes; same-value concurrent edits converge; different sensitive values remain conflict candidates. “One side is newer” is not an acceptable credential oracle.
3. **Causality is not authorization:** vectors/operation IDs can say which edits are concurrent or descended from another known edit. They cannot prove Fleet's principal may read/replicate/delete that item, that a provider response includes the full authorized scope, or that an operator approved a signer/root action. Check grants and operation plan separately from version history.
4. **No global watermark for item truth:** maintain a **verified per-item/per-field baseline** with observed scope identity, adapter/version, authorized grant fingerprint, completion evidence, provider revision where available, readback, and timestamp. A global cursor can optimize discovery only if the provider contract guarantees completeness and replay; it must not advance item baselines for skipped/failed pages or lost permissions. Keep periodic full census separate from cursor lookback. Cursor retention/expiry means resume can require full census, not infer deletion.
5. **Native in-place update and `zz.delete`:** reject Syncthing-style conflict filenames, clone-on-conflict, or replacement of a login where native ID continuity matters. Before a selected routine stale-password update, create a dated Fleet history item in the fixed `zz.delete` convention and verify it, then update the original provider item by stable ID, then read back. A retained old value is history, not revocation or proof of safety.
6. **No CAS inference:** a modification timestamp, revision number, ETag, read-before-write, Fleet lease, or readback does not by itself establish atomic precondition semantics. Until an adapter/operation has documented provider-enforced conditional writes plus an isolated adversarial test, classify it `unguarded`. If a third party changes a value after Fleet's final preflight read and before an unguarded write, a blind update can erase that unseen value; a saved preflight snapshot cannot recover it. The settled ADR-S02 default is stop as `needs-review`, unless an exact named weaker policy is separately approved and its receipt says `applied-with-unprotected-race`.
7. **Outbox / retry:** use a local durable intent and receipt state machine, but reconcile uncertain outcomes by stable IDs and readback; retry the same operation only after determining whether the provider applied it. A response timeout may mean committed. Multiple provider legs produce a saga receipt, not distributed ACID.

## Concrete counterexamples and synthetic decidable oracles

These cases should be model-driven and deterministic. The oracle is the state transition model plus scripted provider responses, not a live vault, a benchmark anecdote, or “the sync command exited 0.”

| Synthetic input / fault | Tempting but wrong outcome | Decidable oracle |
|---|---|---|
| Base has password `P0`, note `N0`; A writes `P1`, B writes `N1`; each reports complete scope | Whole-object last-writer-wins drops one independent edit | Result is `(P1,N1)`, both native IDs unchanged, one item history per actual overwrite, baseline advances only after both readbacks. |
| Base password `P0`; A writes `PA`, B writes `PB`; clocks are skewed so B's timestamp is later | Copy B over A based on wall time | No automatic choice; preserve both candidate values in protected conflict/recovery state, report `conflict`, do not advance that field baseline, no provider writes. |
| API enumerates items but loses permission to read secret fields, or page 4 times out | Treat missing fields/items as deleted and tombstone them | Snapshot is `incomplete`; zero destructive actions, no deletion-derived baseline advancement, retry/census required. |
| Scope cursor says “next page,” but cursor expires between pages | Continue at cursor and mark census complete | Cursor expiry invalidates completeness claim; retain per-item verified baselines and perform full census before any deletion conclusion. |
| Fleet preflight reads provider revision `r7`; human writes `r8`; provider accepts Fleet's unconditional update | Claim lease/CAS prevented lost update; overwrite human value | In guarded default, mock must reject or planner must refuse; provider response `success` alone does not satisfy oracle. For any separately authorized weaker mode, assert exact weaker policy and `applied-with-unprotected-race`; explicitly do **not** assert unseen value recovery. |
| Provider accepted create/update; response packet lost; retry occurs | Duplicate native item or duplicate history record | Replay same operation ID; lookup by stable global/native mapping and readback. At most one logical item/history record for that operation; ambiguous result is `needs-review`, not blind create. |
| Side A changes item, side B returns 403 after A succeeds | Report “in sync” or roll back A destructively | Durable partial saga receipt records A verified, B unknown/failed; preserve recovery payload; only retry B when scope/auth revalidated. |
| Listing unexpectedly returns zero after a token/scope change | Treat all records as deleted | Fail precondition, report zero-result suspicious/incomplete, no tombstones. Access marker is a useful guard, not proof of comprehensive field permissions. |
| CRDT operation set has two concurrent password assignments but one writer bypassed Fleet and overwrote provider state before observation | Claim Automerge-style merge retained both | This premise is unobservable without an audit/event source. Test should show no algorithm can assert the unseen value; require atomic precondition, all-writer serialization, or explicit weaker risk. |
| `zz.delete` history write succeeds; in-place current-value update fails | Advance baseline to new password or create replacement item | History is durable but item remains unchanged; receipt marks partial failure; native ID stable; baseline unchanged. Resume by readback. |

Property/model invariants: incomplete authorization or pagination never yields delete; only verified readback advances baseline; stable logical/native IDs survive rename/refresh; replay is idempotent at logical operation level; independent-field edits merge; divergent same-field secrets never disappear; no baseline cursor leaps across failed items; no CRDT causality token grants mutation authority; and no test labels an unguarded write as race-free.

## Scale and operations: census, memory, cursors, history

* **Census cost:** full census cost grows with item count and provider page/read limits. A scan with per-item fetches is often O(N) API calls; page-based enumeration lowers list calls but does not prove field reads complete. Do not claim benchmarked throughput from these algorithm descriptions. Measure list pages, detail reads, permission denials, retries, bytes, memory high-water, and complete-census duration using synthetic item counts and throttling.
* **Memory shape:** do not hold every plaintext item value, every conflict branch, and every provider response in one process heap. Stream pages into a protected local store; keep public planner inputs redacted; encrypt recovery/history payloads; cap concurrent item reads/writes. For very large scopes, bounded batch sizes and per-item checkpointing trade extra I/O for bounded memory and crash recovery.
* **Cursor vs correctness:** provider cursors, Syncthing sequence/index IDs, and rclone listings all reduce repeated discovery under their respective protocols. A Fleet cursor is an optimization, not a substitute for periodic full census, scope/grant identity, or item-level verified baselines. Cursor invalidation, retention, permission drift, and adapter upgrades require explicit fallback to full scan.
* **Tombstone/history growth:** `zz.delete` has no automatic provider-style age/quantity cleanup. History volume grows with rotations and retained items. Separate encrypted historical values from active indexes; define access/audit, restore, migration, and capacity measurement without silently deleting history. Keep metadata and equality proofs free of plaintext secret values.
* **Conflict fan-out:** vectors and CRDTs can grow with participant/actor count; long-lived offline actors and causal history require compaction policy. Compaction is safe only if it preserves necessary conflict evidence and does not convert forgotten participants into false deletion. Fleet should not adopt distributed causal metadata unless actual offline multi-writer requirements justify its storage and recovery burden.

## Alternatives and adoption/reversal triggers

* **No-op / borrow existing:** if current needs are read-only broker/BWS resolution, do not build synchronization. Reuse the existing resolver, keep explicit manual updates, and revisit only when a concrete two-way update/rotation workflow has an owner and failure cases.
* **Single-writer provider:** if all authorized writers can be forced through one serialized control plane and that scope is enforceable, a serialized-by-contract guard could be simpler than per-field causal history. Reverse to this only with evidence no external writers exist and the adapter test proves the contract.
* **Provider CAS:** prefer native conditional updates when documented and tested against every writer/API path. Revisit automatic apply for guarded fields only after stale-revision writes are rejected in a hermetic adapter conformance test.
* **CRDT:** consider for Fleet-owned collaborative policy/config metadata if offline concurrent editing is a demonstrated requirement and all operations are captured. Keep secrets, deletion authority, signer authorization, and provider effects outside auto-merge; discard this option if conflict retention/compaction cannot be auditable.
* **Global event/outbox architecture:** adopt more machinery only when multiple remote legs and crash recovery justify the durable log; a small read resolver should not acquire a database and sync daemon merely because outbox is established prior art.
