# PKI systems, post-quantum interoperability, and Fleet's reference graph

**Checked:** 2026-11-12. **Scope:** compare public PKI tools and standards with Fleet's settled reference design; this is research, not a replacement architecture or production readiness claim. No production CA, keys, certificates, or service was accessed. Synthetic plans only.

## Executive comparison

PKI products solve different operational slices. Smallstep `step-ca` is an online issuer with a deliberately simple offline-root/online-intermediate model, provisioners, policy and renewal. CFSSL is a signing/bundling toolkit and HTTP API with signer policy configuration and multiroot support. OpenBao PKI is an authenticated secret-engine interface for dynamic certificate issuance and issuer/key management. cert-manager issues and renews Kubernetes workload certificates; trust-manager distributes certificate trust bundles. Sigstore Fulcio issues short-lived identity-bound signing certificates and Rekor provides an append-only transparency log—not a Fleet private-root escrow, general X.509 lifecycle database, or revocation service.

These systems are useful design references or optional future adapters, but no one maps without qualification onto Fleet's fixed reference graph and explicit root-sign authorization. In particular, adopting a turnkey CA would not by itself satisfy the exact four root identities, 20 CA key pairs, 65 certificate variants, fixed-three escrow destinations, transaction-bound authorization, stable current-CDP behavior, or the 4.1 alias exception. The graph/profile contract is in the source spec §§3.2, 3.3, 24.2 and 33.2; root transaction authorization is ADR-S01; the fixed escrow and CDP decisions are ADR-S05 and ADR-S04. This note adds prior art and test obligations without replacing them.

## Systems comparison: responsibilities, borrow, and limits

## Reference graph and two cross-signing profiles

Fleet's stipulated reference graph is **4 independent root keys** plus **2 purposes × 2 partitions × (3 classical issuer keys + 1 ML-DSA issuer key)** = **20 CA key identities**. Four self-signed roots plus nine classical-controlled root cross-certificates give 13 root-level certificate variants. In the reference `both` graph, each of four purpose/partition issuer sets has 3 classical issuer keys × 3 classical root signers + 1 ML-DSA issuer key × 4 root signers = 13 direct issuer certificate variants, yielding 52 issuer cert variants and **65 total CA certificate variants before leaves**. These counts follow source spec §§3.2, 3.3, and 24.2. Cross-certificates are path-building candidates, not trust anchors.

**Important terminology:** `roots-only` and `both` are cross-signing graph profiles, not choices of which trust anchors to install. In either profile, the selected root trust set is independently one of the same bundles: all four self-signed roots, the three classical self-signed roots, or the single ML-DSA self-signed root. Neither profile installs untrusted root/issuer variants as anchors. The PQ-only verifier boundary is unchanged: explicitly trust only the ML-DSA root and require an all-ML-DSA path and eligible PQ endpoint authentication.

| Cross-signing graph profile | Issuer variants retained | Count for the same fixed 20-key Base + Internal Web reference keys | Tradeoff (reasoned, not measured) |
|---|---|---|
| **Roots-only** | Keep all 13 root-level cert variants and one direct, matching-root certificate per issuer key: 16 direct issuer certificates for the 16 issuer keys. | **29 CA cert variants** for these two purposes/partitions. This lowers artifact count and reduces candidate certificates, signing work, revocation inventory, and (if the variants would otherwise be published) publication obligations relative to `both`; it does **not** reduce or alter the chosen trust-anchor set. A client that trusts an alternate single root may need an extra root-cross certificate/hop where a direct issuer variant would provide a shorter chain. |
| **Both / required reference** | Keep all 13 root-level variants and every eligible direct issuer signature variant (13 per purpose/partition issuer set). | **65 CA cert variants** for this reference. Direct issuer paths offer shorter chain candidates across the signer roots but add certificate/serial/revocation/publication state and compatibility candidates. This is mandatory for the reference build; 29 is a counterfactual count comparison, not an alternative reference acceptance profile. |

**Performance and cost are hypotheses, not promised outcomes:** more direct variants necessarily increase the number of generated, stored and inventoried certificate objects (and, if all variants are published, publication objects), but shorter chains may reduce presented-chain bytes or path-building work for some clients. Whether that lowers total bytes, CPU, handshake latency, or compatibility failures depends on exact path selection, DER sizes, cache behavior, and client implementation. Measure both profiles against the same synthetic keys, selected root bundles, and named client/version matrix. Do not claim roots-only is faster or both is more compatible before those measurements; do not invent browser-size thresholds.

## Standards facts and ML-DSA-44 interoperability boundary

* **RFC 5280** defines X.509 certificates, path validation, CA constraints/key usage, CRL structure, AIA and CRL Distribution Points. A trust anchor is a local input to path validation; a certificate chain or cross-certificate is not automatically trusted merely because it is sent. The RFC defines algorithm identifier and certificate structure but does not assert deployment support for any specific ML-DSA implementation. [S1]
* **FIPS 204** finalizes ML-DSA and defines parameter sets; for ML-DSA-44 the raw public key is 1,312 bytes and signature is 2,420 bytes. FIPS standardization does not imply every TLS library, browser, OS trust store, HSM, PKCS#11 module, CA tool, CMS parser, or Rust binding implements it. NIST page lists final publication and current errata notice. [S2]
* **RFC 9881 (October 2025, Standards Track)** defines ML-DSA-44/-65/-87 identifiers for PKIX certs and CRLs, requires absent algorithm parameters, defines SPKI/signature encoding over DER TBS data, and requires conforming CA/client implementations that process ML-DSA certs/CRLs to use/recognize these OIDs. It specifies pure ML-DSA and prohibits HashML-DSA in these PKIX contexts for interoperability. It is a protocol format standard, not proof a deployed endpoint implements it. [S3]
* **OpenSSL 3.5** release notes state support for ML-KEM, ML-DSA and SLH-DSA. This establishes an OpenSSL version-family capability, not that every downstream build, provider/property configuration, CLI path, TLS stack, or OS/browser uses that implementation. Pin exact OpenSSL build/provider and verify algorithm availability in the consuming path. [S4]
* **RustCrypto `ml-dsa`** docs.rs currently describe a pure-Rust FIPS-204 implementation with ML-DSA-44/65/87 and explicitly say it has never been independently audited. The docs expose Rust signing/verifying/key traits and optional PKCS#8 module, but this alone does not establish X.509/RFC 9881, CMS, TLS, trust-store, side-channel, or production custody integration. Treat as an optional client-side capability experiment, not the root signer by default. [S5]

**No unsupported browser/client claim:** do not state “browser support,” “universal PQ path,” or “browser rejects this certificate” based on RFC, OpenSSL, or RustCrypto support alone. Client capability is a tuple of exact binary/version, crypto provider, certificate parser/path builder, TLS signature-scheme negotiation, trust store, protocol mode, and configuration. A static certificate-path test and live TLS handshake test answer different questions.

### Standards-vs-client versioned test plan (synthetic artifacts only)

1. Create fixture certs/CRLs for each required algorithm/variant from synthetic keys; parse DER and assert RFC 5280 profile, RFC 9881 OIDs/absent params, exact TBS bytes, signature verification, Basic Constraints/key usage, path length, AKI/SKI, serial uniqueness, validity, SAN, AIA and CDP. Independent oracle: at least two separately implemented ASN.1/X.509 parsers plus explicit profile assertions. A parser accepting DER is not proof policy correctness.
2. For each pinned validator/client family and exact version (OpenSSL command/API builds and selected Rust crate/backend versions at minimum), test trust-anchor selection, alternate cross-path construction, ML-DSA issuer signatures, ML-DSA leaf signatures, CRL parsing/signature/serial status, and rejection of malformed parameter-present/noncanonical variants. Record unsupported as `not_supported` rather than silently substituting a classical path.
3. Separately run TLS client/server handshakes with named versions, algorithms, policy and trust bundle. Record handshake signature algorithms and selected path. No claim about browser/device clients until those exact clients are part of the matrix and tested; standards-conformant static path validation is insufficient.
4. Test CMS issuance kit independently: exact cert/CRL membership, no implicit trust-anchor change, round-trip parse by named CMS implementations, and explicit error if a client cannot parse an ML-DSA structure.
5. Track version expiration and upgrade results as evidence. RFC conformance, crypto primitive support, X.509 path support, TLS negotiation, trust-store support and application acceptance remain separate columns.

## Signing, revocation, publication, and aliases

Fleet ADR-S01 requires transaction-bound root authorization after the exact **SPKI, serial, and TBS** are finalized; signer invocation must be bound to exact approved artifact tuple(s). This parallels the protocol fact that certificate signatures cover DER-encoded `TBSCertificate` (RFC 5280/RFC 9881), but the approval ceremony and grant format are Fleet policy, not RFC mandates. The signer returns a receipt for exact authorized bytes; key possession or an online CA endpoint does not mint Fleet approval.

Separate three things:

1. **Active signing:** a transaction-scoped operation authorized for exact artifact digests. It need not imply key export or restore authority.
2. **Escrow:** exactly three approved independent destinations already fixed by ADR-S05: encrypted laptop storage, authorized BWS project, and authorized 1Password vault. Each copy requires isolated restoration evidence; this note does not expand that list.
3. **Immutable publication/archive:** certificates, numbered CRLs, kits, receipts and evidence have immutable bytes and immutable versioned URLs/content IDs. A current-CRL pointer is a different object with a controlled update policy.

**Stable current CDP vs immutable archive:** an embedded CRL Distribution Point in a long-lived certificate must keep resolving to the current CRL for its particular signing issuer/key and generation as revocations advance. Keep numbered historical CRLs immutable; maintain the embedded CDP as a durable stable alias (or stable content endpoint) whose new signed CRL monotonically supersedes prior current state. Never leave the certificate pointing only to its original empty archived CRL; never silently redirect it to a different issuer key/generation. Test original certificate → original CDP URL → newer CRL number, valid signature/thisUpdate/nextUpdate, and the revoked serial. ADR-S04's §4.1 alias exception is intentional: preserve alias stability only for current CDP; immutable archival artifacts remain immutable. AIA is a best-effort certificate location, not a universal path-fetch guarantee.

## Failure cases and synthetic, decidable test oracles

| Counterexample | Bad inference | Oracle |
|---|---|---|
| RFC 9881 OID parses in one OpenSSL build; target TLS client uses an older/different provider | “ML-DSA-44 is supported by all clients” | Versioned capability matrix separates ASN.1 parse, static path validation, TLS negotiation and trust-store install; unsupported tuples fail closed without algorithm substitution. |
| A cross-certificate forms a path to a classical root | “This is a PQ-authenticated path” | Strict PQ oracle requires ML-DSA trust anchor, ML-DSA signatures along all CA path edges, and eligible PQ leaf authentication key/protocol. A classical leaf key under a PQ issuer is not PQ endpoint authentication. |
| A PQ signature appears in a certificate but parameters are present or HashML-DSA OID is used | “Same family, accept it” | RFC 9881 profile validator rejects parameter presence and HashML-DSA PKIX usage; compare exact OIDs and DER against independent test vectors. |
| Bundle contains all 65 variants and gets installed as trust store | “More certificates means more safe paths” | Oracle asserts only explicitly selected self-signed roots are anchors; cross-certificates remain untrusted candidates; report bundle size/path selection separately. |
| Renewal rotates root source and trust-manager immediately drops old root while old leaves remain | “Bundle reconciled successfully, so rollover is safe” | Synthetic staged rollout must trust old+new roots concurrently until old leaf census reaches zero, then remove old root only after explicit gate. |
| Current CDP returns archived initial empty CRL after a later revoke | “The CRL object is immutable, so publication is done” | Fetch the exact original embedded CDP URL after revoke; require newer CRL number, signer key/generation match, valid freshness/signature and revoked serial. |
| CRL publication endpoint changes to another generation/key under same alias | “URL did not change, so identity is stable” | Verify CRL issuer/signing key against certificate's actual issuing key and generation; reject unexpected key substitution. |
| Root certificate or CRL is fetched successfully from archive | “The root key has been escrowed/restorable” | Separate public artifact availability from each of exactly three encrypted private-key copies and isolated restore tests. |
| Key exists in signer vault and API responds | “This request is authorized” | Reject absent/replayed/expired transaction-bound grant or any mismatch in SPKI, serial, TBS digest, profile, validity, signer, purpose, output destinations. |

All crypto fixture keys must be synthetic. Do not use production roots, live services, browser profiles or credentials in these tests.

## Adoption, reversal, and no-op options

* **No-op / use existing primitives (default where appropriate):** a finite offline artifact generation/validation workflow can remain a CLI/library process with current OpenSSL/Rust primitives and existing encrypted formats; do not operate an always-on CA service solely because `step-ca`, CFSSL, OpenBao or cert-manager exists. Reuse existing trust distribution only when its ownership, scope and staged-rotation behavior meet requirements.
* **Smallstep trigger:** consider an optional online-intermediate/provisioner integration when a concrete workload needs ACME/OIDC/cloud/Kubernetes enrollment or automated renewal. Reverse/decline if its one-intermediate model, key algorithm support, revocation model, or deployment availability cannot meet Fleet graph/guardrails. Test exact versions and retain Fleet root/custody boundary.
* **CFSSL trigger:** evaluate as a library/tool or adapter if measured signing/bundling work benefits from its policy and path-building features. Reverse if required ML-DSA encoding, deterministic profile controls, transaction-scoped external signing, or reproducible cross-client validation is missing; toolkit breadth is not sufficient.
* **OpenBao trigger:** evaluate only with a distinct, owned dynamic credential/short-lived issuance requirement and an operator team for its service lifecycle. Keep it outside static root escrow and do not automatically add it as root destination. Gate on exact versioned ML-DSA, issuer/key, API authorization, backup/restore, CRL/CDP and failure-domain evidence.
* **cert-manager/trust-manager trigger:** adopt for Kubernetes workload issuance/trust-bundle delivery when Kubernetes is the target, while Fleet owns profile/governance or delegates explicitly. Reverse if its reconciliation semantics or namespace/source scope cannot stage trust changes safely. Never use it to publish roots into general browser/system stores without consumer-specific proof.
* **Sigstore trigger:** use for software artifact signing where OIDC identity, short-lived certs, and public transparency are desired. It is not a substitute for private Fleet TLS/device PKI. Avoid transparency logging when metadata disclosure conflicts with policy.
* **Roots-only vs both:** retain `both` for the fixed reference proof obligation; allow roots-only for ordinary profiles only with exact-client path tests. Increase direct variants only if a named client/version reproducibly needs a path unavailable under roots-only and the additional revocation, publication, inventory and operator burden is accepted. Reduce variants only if the reference contract itself is explicitly changed by the parent decision owner, never as a silent optimization.
