**Decisions to retain:** One logical PKI bundle with four distinct root keys, asymmetric cross-signatures, separate root keys and post-quantum trust policy, purpose-specific Base/Internal Web issuer sets with A/B independent partitions. **Credential provider distinctions:** `bws` Bitwarden Secrets Manager, `bw` Bitwarden Password Manager and `op` 1Password are **different** sources, permissions, data models, clients and identities. Do not use a KV-only BWS record as a substitute for a full 1Password login without a vetted typed sidecar mapping and recovery validation.

**Current recommended backend composition** (proposal, subject to measurements and real permissions):

## Mandatory scope: unified secret record and continuous reconciliation

Implement a canonical stable `Credential` identity, typed fields/metadata/relations, provider-native IDs and revision mappings, lossless sidecars, versioned field mapping, creator/target host/user metadata where known, aliases and standard paths. `bw` and `bws` are **different products**. A `bws` value must stay usable by existing machine consumers; rich 1Password fields/attachments cannot be silently dropped just because `bws` has only key/value/note/project. Full Bitwarden login/autofill mirroring requires the `bw` provider. Use authorized scopes, least-privilege service accounts and no raw secrets in logs or SQL.

Build a once-daily laptop-run reconciliation system with a first-run full inventory/backup/plan, typed three-way merge against the last verified common state, configurable 1–2h overlap plus periodic full census, incremental updates, pair resolution, conflict preservation and read-back verification. Absence because of API failure or changed permission must **not** count as deletion. Stable IDs survive renames. Two independently edited protected fields become explicit conflicts, not whichever timestamp is newer. New unmatched items copy in both directions when representable, with disambiguated `.op` / `.bws` identities when uncertain.

**Never physically delete `zz.delete` records.** Preserve old credentials in both stores with dated linked history items before changing stale active passwords, then update the **original native item in place** to keep autofill and references intact. Verified removed/missing-side items create/mirror tombstones in both stores; unsafe/incomplete scope cannot trigger retirement. Notes are store-neutral and rich; every event gets an append-only structured record, bounded recent summaries on item notes, durable journal and indexed Supabase/Postgres event schema. Support per-field events, operation saga checkpoints, idempotent replay, partial writes, audit, metrics, conflict review, safe restore and tested backups. The initial real reconciliation runs only after backup, a reviewed plan, provider auth and rollback/read-back proof.

Expand `fleet secrets put|get|inspect|rotate|adopt|reconcile|history|audit|runs|providers|conflicts|tombstones|doctor`, using shared Rust modules. `rotate` must preserve old value, not relink autofill, and distinguish vault update from actual target-service credential activation. Honor auto-mirroring to both approved stores where allowed; private offline CA keys require explicit custody approval, never routine machine-secret sync.

## Mandatory scope: four-root asymmetric PKI and purpose-specific issuers

Create one **logical** root bundle with four independent keys/root certs: Ed25519, P-256, RSA and ML-DSA-44. Root graph: classical roots sign one another (six cross-certificates), and each classical root certifies the ML-DSA root key (three); **ML-DSA root never signs classical roots by default**. Root total: four self-signed + nine cross-signed certs. PQ-only clients must validate to the ML-DSA trust anchor using an entirely ML-DSA-signed path. A four-root all-trust client is compatibility-oriented, not guaranteed PQ-secure.

The second user input **requires A and B independent key partitions per enabled algorithm** in the reference Base and Internal Web issuer sets. They also want direct intermediate cross-signing by every eligible root signer, in addition to root cross-signing; make signing graph configurable (`roots-only|issuers-direct|both|none`) but actually produce direct issuer variants in the reference run. For each issuer set: 8 intermediate keys and 26 intermediate certificates (three classical issuer keys × three classical root signatures, plus ML-DSA key × four root signatures, times A/B). For the two named issuer sets plus roots: **20 total CA private key pairs and 65 CA certificate variants**, excluding leaves. No PQ-root-to-classical CA signing. Generate purpose-appropriate root/base/web CA names with trailing `G1` generation marker, organization `developing.today LLC`, `C=US`, descriptive web OU; default exact reference root expiry **2050-07-07T12:00:00Z**, Base/Web **2032-07-07T12:00:00Z**. General default root 20y, issuer 5y, leaf usually 90d. User requested RSA-2048 compatibility: explicitly support it, but gate long-lived RSA-2048 root usage behind a cryptographic policy review; prefer RSA-3072/4096 for new long-lived roots.

Root private-key signatures **always require an explicitly passed authorized root signing source**; discovering a default public root must not silently exercise root private keys. Add high-level `fleet cert bundle create` to create root+Base with one authorized command, plus individual `root create`, `issuer create`, `leaf issue`, `renew` (same-key certificate reissue) and `rotate` (new key generation), custom algorithms, partitions and purposes. No root key/key material/production secret committed to public Git. Provider-backed offline signer/HSM workflows and safe resumption required.

Generate real X.509 DER `.crt/.cer`, PEM, certs-only CMS `.p7c`, CSR, CRL, chains, bundles, key references and appropriate per-client delivery kits. Include issuer-correct AIA CA Issuers entries, CDPs pointing to signer-issued CRLs, optional **functional** OCSP only when served, three configurable HTTP mirrors (two public, one `.internal`), exact immutable object paths/MIME/health checks and DNS zone-file/JSON/YAML change manifests. Support fallback AIA as an opportunity, but never assume clients fetch all URLs or explore alternate chains. Proactively distribute needed chains/trust bundles. Only add ML-DSA signature algorithms according to RFC 9881; never force RSA/ECDSA SHA-256 encoding onto Ed25519/ML-DSA. Create complete Base one-year test leaf kit and Web 90-day kit for developing.today, *.developing.today, developing-today.com and *.developing-today.com, with minimal/full output modes. Generate trustworthy installation instructions for main OS/app stacks. Plan public ACME (LE/ZeroSSL), CT/CAA/DCV, cert-manager/trust-manager and revocation serving without claiming a private CA is globally trusted.
