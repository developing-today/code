# Fleet v0.3 — Architectural Decision Review and Research Agenda

**Status:** v0.3 design decisions, not production-state assertions. **Date:** 2026-11-06. **Primary source:** user's three requirement sets; supplemental official/project-primary research compiled in `SECRETS_BACKEND_RESEARCH_2026-11-06.md`. Decisions are proposals until verified against the live providers and committed project ADRs.

## A. The architecture I would choose first

Do **not** replace all credential services or build a new Vault-like server as the first Fleet milestone. Make `fleet-secrets` the consistent typed interface, initially backed by **1Password** for human credentials and selected automation items, **Bitwarden Secrets Manager (`bws`)** for currently authorized machine credentials, and **encrypted local snapshots/SOPS+age** for narrowly scoped recovery and declarative deployments. The existing Fleet broker becomes a policy-aware high-performance retrieval tier and does not automatically become the canonical source of truth.

Before any production reconciliation, distinguish **Bitwarden Password Manager (`bw`)** from **Bitwarden Secrets Manager (`bws`)**. Their API objects, access grants, UX, and implementation are different; BWS permission alone does not grant the personal password vault. The user may later grant a separate additional identity for a more comprehensive inventory and second sweep. **Never silently include unsurveyed personal items or offline root keys** in a new sync policy.

Neither 1Password nor BWS should be an irrevocable single point of failure. To meet the user's availability objective, use independently recoverable encrypted backups, scoped provider fallbacks, a bounded and encrypted offline cache, and explicit source-version/TTL policies. Two full plaintext-equivalent remote replicas have higher compromise exposure; recoverability and blast radius must both be measured.

## C. Important review findings and corrections

1. **The attached 1,796-line document was read as 20 numbered sections plus closing refinements.** See §47 of the full specification for the source-to-requirement crosswalk. Its advice on manifests, composable adapters, long-term recovery, independent validation and security boundaries is now normative. It is not treated as proof that any source code or deployment already exists.
2. **Root and issuer cross-signing options conflict across inputs.** For the specific reference run, keep four independent root keys, nine asymmetric cross-signatures, and A/B intermediate key partitions, direct issuer variants **and** root cross-signing. That produces **20 CA key pairs and 65 CA certificates**, excluding leaves. For future purposes with many issuers, retain `roots-only` mode to avoid unnecessary matrix growth. This is a configurable compatibility policy, not permission to silently omit the reference matrix.
3. **Post-quantum paths and trust stores are distinct.** A verifier that trusts classical roots for the same unrestricted names is not automatically PQ-assured. ML-DSA-only clients must enforce ML-DSA signatures/path to a separate PQ trust anchor. No classical-root-to-ML-DSA cross-certificate can give a crypto-incapable legacy client ML-DSA implementation.
4. **Public Web is a name, not a trust guarantee.** Privately issued `developing.today` certificates are not trusted by ordinary Internet browsers; use public WebPKI/ACME for public trust, private PKI for managed trust and mTLS. Keep CAA/DCV/CT procedures distinct from private X.509 packaging.
5. **AIA can contain multiple `caIssuers` entries or point to certs-only CMS.** Some clients stop at a first candidate or do not fetch AIA. Supply DER single-certificate URLs and bundles, preinstall needed intermediates and distribute known chains. Do not claim universal cross-root discovery.
6. **Certificate dates:** ordinary root `20y`, issuer `5y`, leaf `90d` unless explicitly overridden; reference root `2050-07-07T12:00:00Z` and **both** Base/Internal Web reference issuer sets `2032-07-07T12:00:00Z`. An older draft left a Web special expiry unspecified; the later reference build set it explicitly.
7. **RSA lengths:** implement RSA-2048 as a compatibility-capable adapter, while recommending a stronger policy for new long-lived root keys (RSA-4096 default). Do not silently override an explicit reviewed compatibility request; warn and require scoped authorization for weaker CA use.
8. **Secret history needs two mechanisms:** native provider versions (when available) and immutable recoverable `zz.delete` history. Avoid rewriting native record IDs, breaking autofill, leaking secret metadata or treating access errors as user deletions. Batch sync must operate against a persisted common-state baseline with per-field conflicts and read-back receipts.
9. **Secret storage and backup are not equivalent.** A second online copy gives resilience against one provider's outage but can spread compromised credentials; separately encrypted offline snapshots with tested restores may be preferable for high-impact secrets. Root and intermediate signing key custody have distinct policies.
10. **Long-term provider portability depends on a manifest and tested adapters**, not filenames: versioned stable IDs, serials, algorithm IDs and OIDs, signer references, key generations, cert revisions, A/B partitions, policy profiles, source stores, generated artifact hashes and human-readable instructions. Do not put raw secrets or provider credentials in metadata manifests.

## D. Focused research priority

**High-confidence near-term work:** First, establish a truthful repository/provisioning census and run authorized synthetic end-to-end provider tests. Then build the canonical typed records and provider inventory/capabilities, daily reconciling plan/backup/history engine, explicit custody metadata, event journal and corresponding CLI/library interfaces. In parallel, build PKI manifest/key adapter/test harness; validate AIA/CDP/CRL and ML-DSA support across real client versions before shipping production materials. Integrate SOPS/age for a limited NixOS/Flux trial.

**Pilots with explicit go/no-go decisions:** (a) measure BWS read/list latency with CLI, SDK and Fleet broker and compare `fnox` warm cache; (b) run OpenBao one-node **synthetic** test for storage/transit/PKI/SSH lease, then HA/unseal/backup/restore test; (c) test whether metadata/field fidelity makes a BWS↔1Password human-login mirror worthwhile; (d) test `securestore` API and cryptographic format against SOPS/age; (e) compare Cozystack Flux/Helm against Argo CD; evaluate Tekton only where CI pipelines are actually needed.

**Deep future design:** SPIFFE/SPIRE and authenticated workload identity, Teleport/Tailscale access control, service mesh Istio/Linkerd selection, KubeVirt/Lima/NixOS image tooling, mise as developer bootstrap alongside Nix, OpenTofu state custody, passkeys/TOTP, SSO/OIDC/OAuth/SAML and Fleet `id`/iroh/OCapN capability systems, and eventual cross-region Cloudflare/edge encrypted secret gateway. None of these should block the present CLI design, but their capability and API seams must be preserved.

## E. Items that require real evidence or explicit approval before production action

- Verify source-controlled provider versions, BWS project/machine-account limits for **the actual plan**, 1Password service-account access/grants, BW Password Manager access scope, API/SDK field support and actual SDK latency. Marketing tables and general benchmarks cannot establish account-specific privileges or performance.
- Obtain an authorized vault inventory and reliable backup/restore path before any first-run global reconciliation. Initial `zz.delete` duplicates or modifications are production writes and require a reviewed plan/rollback evidence; the design document itself is **not permission to perform them**.
- Determine custody and export policies for root signing keys and whether provider access remains possible during 1Password, BWS, laptop, Cloudflare, WAN, K8s and home-cluster outages. Bootstrap/root escrow cannot circularly depend on the same unavailable service.
- Establish issuer policy and application interoperability for ML-DSA before offering PQ authentication to general TLS browsers, SSH clients, or code-signing products; explicitly record `UNSUPPORTED` where appropriate.
- Decide whether OpenBao's full service operation is justified by dynamic leases, auth, and PKI rather than an unproven expectation that it will be faster or cheaper. Evaluate OpenBao high availability and DR as an independent service design.
- Never deploy a Cloudflare custom encrypted secret service without approved auth design, key management, replay/throttling/audit tests, and independent security review.
