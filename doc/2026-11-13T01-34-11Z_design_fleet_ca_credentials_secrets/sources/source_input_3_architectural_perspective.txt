

I would turn these notes into a single implementation specification and execution prompt, rather than simply cleaning up the wording. The goal is for the implementing agent to make sound architectural decisions, build the tooling, test it, and then use that tooling to generate the actual PKI artifacts.

There are several important refinements I would incorporate.

First, I would retain the four-algorithm architecture we developed, with RSA-4096, P-256, Ed25519, and ML-DSA-44. The three classical roots should support mutual cross-signing, while the ML-DSA root remains a distinct post-quantum trust boundary. Classical roots may certify the ML-DSA root key for compatibility, but the reverse must not occur by default. Fully post-quantum clients must be able to enforce ML-DSA-only paths.

Second, I would distinguish root key generations, independent key partitions, certificate renewals, and cross-signature variants. They are different concepts and should not be conflated into a single `g4b` identifier. A predictable identifier can still be generated for filenames and secret-store paths.

Third, I would make the root bundle a portable, versioned object with a manifest, rather than merely a directory of PEM files. The manifest would carry identities, algorithms, generations, issuance relationships, security policies, secret references, validity periods, and artifact hashes. This makes long-term regeneration and migration much more reliable.

Fourth, I would distinguish X.509 certificates from native SSH certificates. The same `fleet` command family can manage both, but OpenSSH certificates are not interchangeable with X.509 certificates, and the CLI must not pretend otherwise.

Finally, I would make the implementation library-first, transactional, idempotent where appropriate, and security-conscious. An agent should be able to run a high-level command without needing to understand the internal implementation, while advanced callers can use the same underlying Rust crates without writing temporary files.

The specification below is written to be given directly to the implementing agent.

# Fleet: Unified Secrets, Cryptography, PKI, and Certificate Lifecycle System

## 1. Mission and authority

Design, implement, test, document, and use a production-quality, extensible Rust-based system within the existing `fleet` tooling for cryptographic key generation, certificate authority management, certificate issuance, secret-store synchronization, artifact packaging, distribution preparation, and long-term lifecycle management.

This is an implementation assignment, not merely a request for an architectural proposal.

The final result must include:

1. Working Rust libraries and `fleet` CLI subcommands.
2. Integrated 1Password (`op`) and Bitwarden Secrets Manager (`bws`) support, consistent with the existing secrets infrastructure.
3. A complete four-algorithm PKI root bundle.
4. A general-purpose base intermediate issuer set.
5. A restricted internal-web intermediate issuer set.
6. A general-purpose leaf artifact package.
7. A web certificate package for `developing.today` and `developing-today.com`.
8. Machine-readable manifests, DNS publication records, deployment instructions, and generated documentation.
9. Automated unit, integration, compatibility, security, and end-to-end tests.
10. Verification that the artifacts were generated through the completed `fleet` interface rather than through one-off manual procedures.

You have authority to improve the architecture, introduce additional functionality, restructure the proposed implementation, and select appropriate libraries.

**The requirements below are minimum acceptance criteria, not an exhaustive feature ceiling.**

Prefer a coherent, secure, maintainable system over literal adherence to speculative examples in this document. Where a proposed interface or mechanism is technically unsuitable, replace it with a better implementation, document the reason, and preserve the intended user experience.

Do not silently discard requirements.

The intended users include experienced developers, automation agents, occasional administrators, and someone returning to the system after twenty years with little recollection of its internal structure.

The system must remain understandable, recoverable, extensible, and operable under those circumstances.

# Part I — Architecture and Security Model

## 2. Architectural principles

Follow these principles throughout the implementation.

### 2.1 Library-first design

Implement reusable Rust crates that expose the underlying capabilities independently of the CLI.

The `fleet` executable must be a thin orchestration and presentation layer over those libraries.

An application should be able to invoke the same operations without spawning a process, constructing command-line arguments, or writing intermediate files.

### 2.2 Declarative desired state

Represent PKI bundles, issuing CAs, certificate profiles, storage locations, and lifecycle policies as versioned, machine-readable configuration.

Commands should resolve configuration into an explicit execution plan.

Support:

- Interactive execution.
- Noninteractive execution.
- Dry-run planning.
- Machine-readable plans.
- Repeatable execution.
- Resume and recovery after partial failure.
- Reconciliation of actual and desired state.

### 2.3 Safe defaults

The simplest command should produce a secure, complete result whenever sufficient information is available.

Defaults must be discoverable and overridable.

Potentially dangerous operations require explicit authorization. Distinguish ordinary overwrite controls from security-sensitive operations such as exporting a root private key, weakening certificate constraints, or replacing active trust anchors.

### 2.4 Extensibility

Algorithms, certificate profiles, storage providers, serialization formats, secret backends, signing providers, and distribution methods should be independently extensible.

Adding another algorithm in five years should not require rewriting the issuance pipeline.

Changing the preferred algorithm should generally be a configuration or policy change, provided the implementation supports it.

### 2.5 Performance

Optimize routine leaf issuance and verification without sacrificing security.

Avoid unnecessary subprocesses, temporary files, repeated parsing, redundant secret-store requests, and heavyweight packaging operations on the critical issuance path.

Support a minimal fast path and a comprehensive artifact-generation path.

### 2.6 Security boundaries

Treat root keys, intermediate keys, leaf keys, and secret-store credentials as distinct security classes.

Never assume that a certificate being cryptographically valid means it satisfies an application's intended trust policy.

Maintain explicit boundaries between classical compatibility and post-quantum assurance.

## 3. Cryptographic algorithms

The initial implementation must support:

| Identifier | Algorithm   | Role                             |
| ---------- | ----------- | -------------------------------- |
| `rsa4096`  | RSA-4096    | Classical compatibility          |
| `p256`     | ECDSA P-256 | Classical compatibility          |
| `ed25519`  | Ed25519     | Preferred classical algorithm    |
| `mldsa44`  | ML-DSA-44   | Post-quantum signature algorithm |

Use standards-compliant implementations and certificate encodings.

Do not confuse ML-DSA-44 with legacy experimental Dilithium encodings.

Do not assume every algorithm is supported by every backend, TLS stack, operating system, or certificate consumer.

### 3.1 Algorithm adapter interface

Create a well-defined adapter abstraction exposing capabilities such as:

- Key generation.
- Public-key encoding.
- Private-key serialization where permitted.
- Signing and verification.
- Algorithm identifiers and OIDs.
- Supported certificate formats.
- Backend compatibility.
- Key validation.
- Security-strength metadata.
- Supported usage profiles.
- Hardware-backed or nonexportable key support.
- Optional external signing providers.

Algorithm adapters must declare unsupported operations rather than silently substitute another algorithm.

### 3.2 Aliases

Support reasonable aliases, including:

- `rsa`, `rsa4096`
- `ecc`, `ec`, `ecdsa`, `p256`, `p-256`, `secp256r1`
- `ed`, `ed25519`
- `pq`, `quantum`, `mldsa`, `ml-dsa`, `mldsa44`, `ml-dsa-44`, `dilithium2`

Aliases should resolve to canonical identifiers and be documented.

Do not accept ambiguous aliases such as `dsa` without clarification or a documented unambiguous interpretation.

The preferred algorithm selection must be configurable.

# Part II — Root Trust Architecture

## 4. Root bundle

Create one logical root bundle containing four independent root key pairs and their corresponding self-signed certificates.

Each algorithm must have its own key pair.

The default root bundle should include:

- RSA-4096 root.
- P-256 root.
- Ed25519 root.
- ML-DSA-44 root.

The bundle represents one administrative PKI identity, not one cryptographic key.

### 4.1 Cross-signing architecture

Use asymmetric trust relationships.

The three classical roots should mutually cross-sign one another.

The classical roots may also certify the ML-DSA root public key to provide compatibility paths.

The ML-DSA root must not cross-sign classical roots by default.

| Signing root / Certified root | RSA   | P-256 | Ed25519 | ML-DSA |
| ----------------------------- | ----- | ----- | ------- | ------ |
| RSA                           | Self  | Cross | Cross   | Cross  |
| P-256                         | Cross | Self  | Cross   | Cross  |
| Ed25519                       | Cross | Cross | Self    | Cross  |
| ML-DSA                        | No    | No    | No      | Self   |

This initially produces:

- Four self-signed root certificates.
- Six classical-to-classical cross-certificates.
- Three classical-to-ML-DSA cross-certificates.
- Thirteen root-level certificates total.
- Four independent root key pairs.

Cross-signing must not be implemented as sharing private keys between algorithms.

Each cross-certificate contains the public key of the certified CA and is signed by the issuing CA.

### 4.2 Trust profiles

Generate explicit trust profiles.

**Full compatibility**

Trusts all four self-signed roots.

**Classical compatibility**

Trusts the three classical roots, or a selected subset.

**Post-quantum enforced**

Trusts only the ML-DSA root and requires an entirely acceptable post-quantum certificate path.

**Single-root compatibility**

Supports a client trusting only one selected root, using cross-certificates where algorithm support and path-building behavior permit.

The system must not claim that cross-signing provides cryptographic algorithm support absent from the client.

The system must also recognize that trusting a classical root for an unrestricted identity can weaken the assurance of that identity even if it also has a post-quantum certificate.

### 4.3 Root cross-signing versus intermediate cross-signing

Root-level cross-signing is the default architecture.

Purpose-specific intermediates should normally be issued once by their designated parent root.

Alternative paths should use root cross-certificates instead of multiplying intermediate certificates unnecessarily.

Nevertheless, intermediate-level cross-signing must remain supported as an explicit advanced operation for migration, compatibility, and application-specific requirements.

Do not assume every client can construct alternative paths reliably.

### 4.4 Root trust and certification policy

Implement certificate policy identifiers, appropriate constraints, and validation profiles.

Distinguish:

- Constraints encoded in certificates.
- Local trust-anchor configuration.
- Application-enforced signature algorithm policy.
- Issuance authorization.
- Intended key usage.
- Certificate path-building behavior.

Do not represent certificate policy OIDs as automatically enforced security controls.

## 5. Root validity and generations

Default root validity should be twenty years, subject to an explicit policy decision regarding exact validity semantics.

Support both absolute expiry timestamps and human-readable durations.

Examples:

```
fleet cert root create
fleet cert root create --expires 2050-07-07T12:00:00Z
fleet cert root create --valid-for 20y
fleet cert root create --valid-for "15 years 7 days"
```

Use RFC 3339 timestamps for displayed and persisted absolute times.

For durations involving calendar years, define whether they mean calendar arithmetic or fixed elapsed time. Prefer calendar arithmetic for years and months, with documented handling of leap days.

Store both the original duration expression and the resolved timestamp where useful.

Never silently extend a CA certificate beyond an explicitly requested expiry.

### 5.1 Renewal and rotation

Support:

```
fleet cert root renew --bundle <reference>
fleet cert root rotate --bundle <reference>
fleet cert root renew --cert <reference>
```

Clearly distinguish:

- Reissuing a certificate with the existing key.
- Generating a replacement key pair.
- Replacing a trust anchor.
- Creating an overlapping migration generation.
- Replacing an individual algorithm within a bundle.

Root renewal must not accidentally rotate a private key or change the trust identity.

Where the requested operation requires changing the key, the CLI should explicitly identify it as rotation.

### 5.2 Generation and partition identifiers

Use separate fields for:

- Logical identity.
- Key generation.
- Certificate issuance revision.
- Independent key partition or shard.
- Cross-signature variant.
- Algorithm.
- Parent CA identity.

For example:

```
rsa-root-g4-b
rsa-root-g4-b-cert-r2
rsa-root-g4-b-by-p256-g2-a
```

These are illustrative, not mandatory exact filenames.

A generation identifies a key lifecycle generation. A partition identifies an independently generated key of the same logical role. A certificate revision identifies reissuance using the same key.

Provide concise human-readable identifiers, but never use them as substitutes for cryptographic fingerprints or globally unique internal identifiers.

The naming scheme must scale to many generations and partitions without collisions.

# Part III — Intermediate CA Architecture

## 6. Intermediate issuer sets

An intermediate set is a logical collection of issuing CAs, issuance profiles, signing policies, distribution artifacts, and associated metadata.

The default configuration must create:

1. A base or standard issuer set.
2. An internal-web issuer set.

Future sets must be creatable without changing source code.

Examples:

```
fleet cert issuer create --root <bundle>
fleet cert issuer create Standard --root <bundle>
fleet cert issuer create "Public Web" --root <bundle> --usage server-auth
fleet cert issuer create "Device Identity" --usage client-auth
```

An issuer set may contain multiple algorithm-specific CAs.

The default should generate the appropriate algorithm set from the parent bundle, subject to security policy and compatibility requirements.

### 6.1 Default parent inference

If no parent is specified, discover the configured canonical root bundle using the secrets and bundle-resolution subsystem.

Support:

```
fleet cert issuer create
fleet cert issuer create "Public Web"
fleet cert issuer create "Public Web" --root ./root-bundle
fleet cert issuer create "Public Web" --root op://...
```

The exact command grammar may be improved, but the simple cases must remain concise.

Do not silently choose among multiple ambiguous parent bundles.

### 6.2 Inherited metadata

Intermediates should inherit appropriate organization, country, naming conventions, distribution configuration, algorithm defaults, and security policies from their parent.

Allow explicit overrides.

Do not blindly copy root-only extensions or constraints into subordinate certificates.

Generate an appropriate intermediate subject name from the parent identity and the requested purpose.

### 6.3 Purpose-specific constraints

Support issuance profiles such as:

- General-purpose.
- TLS server authentication.
- TLS client authentication.
- Device identity.
- Code signing.
- Email protection.
- Document signing.
- Other explicitly defined X.509 usages.

Do not assume all usage restrictions are universally enforced on intermediate certificates.

Implement appropriate EKU, key usage, certificate policy, name constraints, and issuance-policy controls where applicable.

When an application cannot reliably enforce a constraint, document the limitation and consider separate trust configuration.

### 6.4 Base issuer set

Generate a standard issuer set from the root bundle.

Use the explicitly requested expiry:

```
2032-07-07T12:00:00Z
```

The default intermediate validity should otherwise be five years, subject to parent validity and policy constraints.

The base set should support multiple authorized certificate profiles but must not become an unrestricted signing authority by accident.

### 6.5 Internal-web issuer set

Generate a second issuer set dedicated to internal web services.

Accept a human-friendly name such as:

```
Internal Web
```

Infer appropriate subject naming and descriptive metadata.

Support an explicitly supplied OU, but do not rely on OU for security enforcement.

Use appropriate server-authentication issuance restrictions.

Do not issue client-authentication or code-signing certificates through this set unless explicitly authorized by a changed policy.

The original notes request a special expiry override for this issuer set but do not specify its exact date. Make the date configurable and do not invent an override.

### 6.6 Future issuer sets

The system must support:

```
fleet cert issuer create "Public Web" --usage server-auth
fleet cert issuer create "Code Signing" --usage code-signing
fleet cert issuer create "Hardware Devices" --usage client-auth
```

The name should determine human-readable metadata and predictable filesystem and secret-store identifiers.

The usage profile should determine cryptographic constraints and operational policy.

The name alone must not silently grant broad signing permissions.

# Part IV — Certificate Issuance

## 7. Leaf issuance

Provide a concise interface for leaf generation.

Examples:

```
fleet cert leaf create laptop-amd
fleet cert leaf create laptop-amd --issuer standard
fleet cert leaf create --issuer ./standard-bundle --valid-for 1y
fleet cert leaf create --type web --dns developing.today
fleet cert web create developing.today
```

The CLI may support aliases, but it must have one clearly documented canonical command grammar.

### 7.1 Required identity information

Do not generate a misleading production certificate when essential identity information is missing.

If no identity is supplied, allow a clearly labeled test or generic artifact where appropriate, or require an explicit `--test` or equivalent option.

An unattended production command must fail clearly when required identity information cannot be inferred.

### 7.2 General-purpose leaf example

Generate a one-year leaf from the base issuer set.

The command should inherit all appropriate defaults and produce the comprehensive artifact package.

Where the general-purpose issuer permits multiple usages, require or infer a specific leaf profile rather than producing an unsafe all-purpose leaf by default.

### 7.3 Web leaf example

Generate a web certificate package for:

```
developing.today
developing-today.com
```

Support both exact DNS SANs and wildcard expansion.

Examples:

```
fleet cert web create developing.today developing-today.com
fleet cert web create --wildcard developing.today developing-today.com
fleet cert web create --san DNS:developing.today --san DNS:developing-today.com
```

For the wildcard convenience mode, include both the apex domain and its single-label wildcard:

```
developing.today
*.developing.today
developing-today.com
*.developing-today.com
```

Do not assume a wildcard covers the apex domain or arbitrarily deep subdomains.

Provide explicit controls for SAN expansion, exact SANs, and name validation.

### 7.4 Algorithm selection

Support commands such as:

```
fleet cert web create developing.today --algorithms ed25519,p256,rsa4096
fleet cert leaf create laptop-amd --algorithms all
fleet cert leaf create laptop-amd --algorithm mldsa44
```

Algorithm selection should operate on the relevant certificate/key profiles.

When multiple algorithms are requested, generate separate leaf key pairs and certificates unless a standardized, explicitly selected composite mechanism is supported.

Do not pretend one ordinary X.509 certificate can contain four independently selectable issuer signatures.

### 7.5 Default leaf package

The comprehensive mode should generate a portable directory containing the appropriate:

- Private keys.
- Public keys.
- DER certificates.
- PEM certificates.
- Certificate chains.
- Full chains.
- Relevant trust bundles.
- Cross-certificate variants.
- CMS/PKCS#7 certificate collections.
- PKCS#12 identity containers where appropriate.
- Manifest and artifact checksums.
- Installation instructions.
- Application configuration examples.
- Security and compatibility notes.

Only generate formats that can be represented correctly for the selected algorithm and use case.

Protect private keys and PKCS#12 files appropriately.

Do not place sensitive material in a public distribution package.

### 7.6 Minimal output mode

Support:

```
fleet cert web create developing.today --minimal
fleet cert leaf create laptop-amd --format pem --stdout
fleet cert leaf create laptop-amd --no-package
```

Minimal mode should avoid unnecessary documentation, packaging, conversion, and filesystem work.

Provide separate controls for:

- Keys only.
- Certificates only.
- Chains only.
- Full package.
- Public artifacts only.
- Selected output formats.

Do not output private keys to stdout or logs accidentally.

# Part V — AIA, CRLs, OCSP, and Distribution

## 8. PKI publication conventions

Use the following general URL layout:

```
http://pki.<domain>/certs/
http://pki.<domain>/crl/
http://pki.<domain>/ocsp
```

Support configurable hostnames and path layouts.

Prefer stable, immutable URLs for issued certificate artifacts.

Use HTTP for embedded AIA, CRL, and OCSP endpoints by default, with optional HTTPS publication.

Do not require HTTPS redirects for certificate-discovery endpoints.

### 8.1 AIA issuer discovery

Generate appropriate AIA `caIssuers` references for leaf, intermediate, and cross-signed CA certificates.

Support:

- Individual DER issuer certificates.
- Multiple AIA issuer locations.
- Certs-only CMS/PKCS#7 issuer collections where supported.
- Explicit alternative-chain artifacts.
- Proactive distribution to managed clients.

Do not rely on clients fetching every AIA URL.

Do not assume a client will continue searching after retrieving an unsuitable issuer certificate.

Do not assume all clients support CMS responses through AIA.

Generate stable individual issuer URLs as the compatibility baseline, with optional multi-certificate containers and client-specific chain distribution.

The implementation must verify that every AIA location points to the actual issuer certificate or a valid issuer-certificate collection.

### 8.2 Cross-certificate publication

Publish root cross-certificates individually and in suitable collections.

Example:

```
/certs/roots/rsa.crt
/certs/roots/p256.crt
/certs/roots/ed25519.crt
/certs/roots/mldsa44.crt

/certs/cross/rsa-by-p256.crt
/certs/cross/rsa-by-ed25519.crt
/certs/cross/mldsa44-by-rsa.crt
```

Support additional collections such as:

```
/certs/cross/rsa.p7c
/certs/cross/mldsa44.p7c
```

A collection named for a CA must contain certificates for that CA's public key, not merely certificates that CA issued.

### 8.3 CRL distribution

Generate CRL distribution point URLs and valid initial signed CRLs.

Support:

- Empty initial CRLs.
- Scheduled CRL regeneration.
- Revocation recording.
- CRL number tracking.
- `thisUpdate` and `nextUpdate`.
- Revocation reason codes.
- Issuer-specific CRLs.
- Publication staging and atomic replacement.
- Validation that CRLs are signed by the appropriate authority.

Never embed a CRL URL without defining how that CRL will be maintained.

### 8.4 OCSP

Support OCSP responder configuration and artifact generation as an optional subsystem.

Do not advertise OCSP in issued certificates until the responder is operational and has an appropriate signing and revocation-data model.

Support multi-issuer responders where practical.

Document the distinction between publication of revocation information and client enforcement of revocation checking.

### 8.5 DNS publication records

Generate a standards-compatible DNS zone fragment as the primary DNS artifact.

For example:

```
dns/
  proposed.zone
  proposed.json
  README.md
```

Include records required or recommended for the chosen publication architecture.

Support DNS provider adapters later.

Do not invent DNS records when the target IP addresses, CNAME targets, or other required values are unknown.

Instead, produce a validated proposal with explicit unresolved inputs.

### 8.6 Publication instructions

Every issuer and root bundle should contain a generated publication guide describing:

- Which files to publish.
- Their relative paths.
- Their destination URLs.
- Their MIME types.
- Their DNS dependencies.
- Required server behavior.
- Cache-control considerations.
- How to test successful retrieval.
- How to verify certificate and CRL signatures.
- How to detect stale or missing publication.
- Which artifacts must remain private.

Generate instructions specific to the bundle and its actual artifacts.

# Part VI — Bundles, Manifests, and Storage

## 9. Canonical bundle format

A bundle is a logical, versioned PKI object.

It may be represented as:

- A directory.
- ZIP archive.
- TAR archive.
- TAR.GZ archive.
- TAR.ZST archive.
- A secret-store reference.
- A canonical bundle identifier.
- A manifest and associated remotely stored artifacts.

The system should use a consistent internal representation regardless of input transport.

### 9.1 Manifest

Each bundle must include a versioned manifest describing:

- Schema version.
- Logical bundle ID.
- Bundle type.
- Organization and subject metadata.
- Parent bundle.
- Algorithms.
- Key identities.
- Certificate identities.
- Generations and partitions.
- Certificate revisions.
- Cross-signing relationships.
- Certificate validity.
- Key usage and policy.
- AIA, CRL, and OCSP configuration.
- Secret references.
- Public artifact references.
- Artifact checksums.
- Issuance history.
- Tool version.
- Relevant compatibility information.

Avoid storing secrets directly in manifests.

Include enough metadata to reconstruct the intended configuration, audit the existing artifacts, and perform future rotations.

### 9.2 Example structure

```
root-bundle/
  manifest.yaml
  README.md
  policy.yaml
  public/
    roots/
    cross/
    trust/
    crl/
  private/
    key-references.yaml
  dns/
    proposed.zone
  docs/
    installation.md
    publication.md
    recovery.md
    renewal.md
  verification/
    checksums.json
    results.json
```

This is illustrative.

Prefer a coherent structure over exact adherence to the example.

### 9.3 Portable bundle resolution

A bundle reference should accept:

```
./root-bundle/
./root-bundle.zip
./root-bundle.tar.zst
op://...
bws://...
pki.<org>....
```

Implement an extensible resolver.

Support omitted conventional prefixes and suffixes when unambiguous.

Support a configured canonical default root bundle.

Do not silently choose between conflicting or stale copies.

### 9.4 Secret-store synchronization

Integrate with the existing `fleet secrets` subsystem rather than implementing unrelated PKI-specific secret handling.

Support 1Password and Bitwarden Secrets Manager.

Provide:

- Provider discovery.
- Authentication checks.
- Read and write operations.
- Canonical path resolution.
- Sync planning.
- Conflict detection.
- Version tracking.
- Integrity verification.
- Safe retries.
- Partial-failure recovery.
- Provider-specific capabilities.

Default automatic synchronization should occur only for approved destinations and key classes.

**Root private keys must not be automatically uploaded to every configured secret store merely because synchronization is enabled.**

Support explicit root-key export and storage policies, offline custody, hardware-backed signing, and nonexportable keys.

Never silently duplicate highly sensitive key material across providers.

### 9.5 Canonical secret naming

Use predictable, lowercased, hyphenated identifiers.

Start from a structure resembling:

```
pki.<organization>.<scope>.<role>.<bundle>.<algorithm>.<generation>
```

But improve it to account for:

- Independent partitions.
- Certificate revisions.
- Cross-signatures.
- Issuer relationships.
- Storage provider constraints.
- Long-term stability.
- Human readability.

Provide a migration mechanism if naming conventions change.

- Concise description.
- Examples.
- Required inputs.
- Inherited defaults.
- Available profiles.
- Security implications.
- Supported formats.

- Automation examples.

```
--yes
--dry-run
--allow-unsafe

```

### 11.4 Input and output

Support:

- Stdin.
- Stdout.
- JSON.
- YAML.
- Human-readable output.
- Structured diagnostics.

## 17. Operational correctness

The system must handle partial failure without corrupting existing bundles or silently losing keys.

Distinguish between:

- Repeating a read-only command.
- Rebuilding a public artifact from existing state.
- Reissuing a certificate.

- Revocation.
- Expiration.
- Key compromise.
- Key rotation.
- Root migration.
- Intermediate replacement.

### 17.5 Automation safety

## Additional architectural decisions I would make before execution

There are four areas where I would tighten the implementation further.

1\. Don't let the base issuer become a universal signing authority. The Standard set can provide multiple certificate profiles, but unrestricted issuance for arbitrary purposes is a significant security risk. I would make profile authorization explicit and eventually use separate issuer sets for SSH, code signing, and other sensitive purposes.

2\. Treat ML-DSA as a separate security domain, not merely a fourth algorithm. Your root cross-signing design is compatible with this. However, the critical enforcement happens at the verifier: an ML-DSA-only device must reject classical signatures in its selected certification path, even if the relevant identities have cross-certificates.

3\. Make the manifest the durable source of identity and lifecycle state. Filenames are presentation details. Key IDs, certificate fingerprints, issuer relationships, serial numbers, and generation identifiers must be independently represented. This becomes particularly important when reissuing certificates with existing keys twenty years later.

4\. Don't confuse a root bundle with a distributable trust bundle. Your canonical root bundle may contain private key references, cross-certificates, manifests, and operational policies. A client-facing `roots.pem` should contain only the trust anchors appropriate to that client's profile. The tool should generate both automatically.

One final implementation detail: the base intermediate expiry is specified, but the internal-web intermediate's special expiry is not. I deliberately left that configurable rather than assigning an arbitrary date.

The resulting specification gives the implementing agent substantial discretion while preserving the architectural requirements and the specific end-to-end commands and artifacts you want.tha
