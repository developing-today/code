## Labels, urgency, lifecycle, and queue contract

- Live `fleet gh label list --repo developing-today/code --limit 500 --json name,description` confirmed `priority/critical`, `priority/high`, `priority/normal`, `priority/low`; `kind/design`, `kind/feature`, `kind/test`, `kind/security`, `kind/docs`, `app/fleet`, `epic/fleet-ca-secrets`, `status/ready`, `status/blocked`, `status/parked`, and `status/needs-triage` also exist. #9156 live labels were `kind/design`, `app/fleet`, `epic/fleet-ca-secrets`. Every child receives `app/fleet` and `epic/fleet-ca-secrets` plus its score-derived priority label. The script does **not create labels**: publishing performs a read-only label preflight and refuses before its first write if a mapped label is not already present. `kind/research`, `kind/migration`, and `kind/operations` are absent, so these proposal kinds do not get fabricated/misleading kind labels; their exact kind remains in the body. `status/ready` is described as “Triaged and ready for queued implementation work”; `status/blocked` and `/parked` have matching descriptions. There is no semantically equivalent generic Backlog label; Backlog is recorded in the body/receipt only.
- Intrinsic urgency is a numeric score, lower means sooner, and is never replaced in issue metadata/body/receipts: the companion charter defines 0–99 Emergency, 100–199 Supercritical, 200–399 Critical, 400–799 High, 800–1199 Standard, 1200–1599 Low, 1600–1999 Someday, and 2000+ Cold backlog ([source §3–4](../sources/COMPANION_pm_charter_shared_conventions.md#L26-L48)). Coordinator §11 says derive labels from canonical scores and keep scheduling/status axes distinct ([source](../sources/COORDINATOR_summit_handoff.md#L275-L284)). Existing labels collapse these score bands to `priority/critical` (0–399), `/high` (400–799), `/normal` (800–1199), `/low` (1200+). The publisher preserves the exact numeric score and band; it does not edit source proposals or normalize their scores.
- Queue packet priority is a separate, explicit projection of the issue score band: Critical 10, High 20, Standard 40, Low/Someday/Cold 70. These are queue priority values from the repo-queue contract, not the intrinsic issue score. `dispatch/README.md:41` records named queue values 10/20/40/70; `validate.rs:20-34,52-53` allows only 10,20,30,40,50,70,90. Stage, lifecycle, importance, hard blockers, and dispatch directive remain distinct; none is inferred from urgency.
- The script preserves the exact lifecycle in the issue body and dry-run plan; it adds existing `status/blocked` or `status/parked` only where descriptions match. It deliberately does **not** apply `status/ready` before initial triage because its live description says “Triaged and ready for queued implementation work.” Ready and Backlog are body/receipt only; Backlog also has no equivalent label. No Project fields are written.
- Queue validator currently accepts only `repo-task/v1` kinds `triage`, `pr_shepherd`, `small_fix`, and `ci_investigation`, not a generic design/implementation task kind (`validate.rs:52-53`). Therefore each newly published issue gets a deterministic **initial triage** packet, keyed by the established family `repo-health:v1:triage:developing-today/code:issue:<number>` (see `validate.rs:73-78`), not a fictitious implementation task. ## Publisher behavior and safe invocation

`tools/publish_issues.py` accepts the common JSON array objects exactly as handed between domain workers:

```json
[{"id":"stable-id","title":"…","parent":9158,"kind":"design",
  "source_ranges":["spec §…"],"requirement_ids":["REQ-…"],"stage":"design",
  "lifecycle":"Ready","urgency":450,"depends_on":[],"body":"…"}]
```

It validates exact proposal fields (including duplicate JSON keys), all §4.2 body sections, numeric urgency bands, dependency DAG, and the **complete rendered UTF-8 body** against the issue-size limit before any subprocess/network/temp/receipt write. It verifies #9155 is OPEN before the batch and via the guarded command path before every remote mutation: create, label repair, native parent/blocker POST, and queue enqueue. The append-only JSONL receipt is restricted to `evidence/publication/<canonical-proposal-digest>.jsonl` (SHA-256 of sorted-key, compact JSON, emitted as `proposal_digest` in dry-run output); preflight rejects symlinked path components/targets, hard links and tracked files, and append uses `O_NOFOLLOW` plus fsync. Each issue create has a fsynced, unique per-proposal `create_intent` (stable marker + rendered-body hash) before POST; a response URL is durably recorded immediately. An intent without a result plus zero search hits is indeterminate and **cannot authorize another POST**. Recovery can use an exact marker/body search or directly fetch the previously returned URL and reverify marker/body; otherwise it stops for manual reconciliation. Existing child markers are checked against a bounded issue-events scan, and receipts record explicit closed/reopened flags. Receipt issue numbers/database IDs never seed dependency links: every run walks the DAG and resolves fresh live issue/API IDs. Native child parent pointer plus parent-list membership must agree; the actual blocker set must equal expected (extras stop, never delete); conflicts are never normalized silently.

Queueing is a separate durable `queue_intent`/`queue_ack`/`task_verified` phase. The task uses the canonical issue-number dedupe key and deterministic issue `created_at`; the queue priority is checked against the explicit score-band projection, separately from intrinsic urgency. The ACK must identify the expected queue and dedupe key. On resume, an existing queue intent is read-reconciled only; it is never enqueued a second time to force visibility, even if an earlier process lost the ACK. The queue receipt records the ACK, each status-scan query scope/limit/completion and timestamp, and the exact same-row ID/key/status/priority observation. If no exact row is found within the bounded status scans, the receipt records the issue as known but queue coverage unverified, and the publisher stops for supervisor reconciliation. It does not claim coverage from the enqueue ACK alone and does not infer absence from a truncated/not-found scan. These are initial `triage` tasks only: packets retain lifecycle/dependency context and prohibit implementation/production changes under #9155 safety gates. `fleet gh` owns token failover; the publisher retries only an explicit pre-execution rate-limit response, honors surfaced `Retry-After`, otherwise waits 1/2 seconds, and never retries an ambiguous issue create.

```bash
# Plan only; no network calls or writes (default, --dry-run is explicit alias)
python3 -I doc/2026-11-13T01-34-11Z_design_fleet_ca_credentials_secrets/tools/publish_issues.py \
  --manifest proposals.json --queue repo-health-code-pilot

# After coordinator review, use proposal_digest from the dry-run output:
python3 -I doc/2026-11-13T01-34-11Z_design_fleet_ca_credentials_secrets/tools/publish_issues.py \
  --manifest proposals.json --queue repo-health-code-pilot --publish \
  --receipt doc/2026-11-13T01-34-11Z_design_fleet_ca_credentials_secrets/evidence/publication/<canonical-proposal-digest>.jsonl
```

The publisher rejects any queue except the verified code pilot `repo-health-code-pilot`. `--publish` requires the exact digest-named receipt path; unknown arguments and abbreviations fail. No production secrets are part of the manifest or receipts. Even after a future receipt is fully verified, final backlog coverage requires a separate actual live snapshot; the initial enqueue ACK is not sufficient.
