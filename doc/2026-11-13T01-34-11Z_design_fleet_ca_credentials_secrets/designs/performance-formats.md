## Decision in brief

1. **V1 is the current-state census, not an implementation stage:** retain BWS as current machine source, existing Fleet broker as deployed primary read path, and established `op`/SOPS-age workflows. `fleet-secrets` has no cache and performs BWS CLI list+get fallback; broker has TTL cache, timestamps/age/source and per-key singleflight. Important correction: #6767 is OPEN, but per-secret refresh/install, timestamps and age/source mitigation landed in PR #8491 (`c676d1c41c07`) with reported tests 59/59. Remaining work is deployment verification/live canary, **not authorized in this run**. Do not duplicate the implementation or claim deployed/canary proof. Measure before claiming BWS latency is intrinsic. All proposed implementation starts at V2-foundation.
2. **V2 (near-term, benchmark-gated):** implement benchmark and explicit per-secret freshness/max-age policy tests, then prototype `fnox-client` as an **optional, read-only daemon-cache adapter**, not Fleet's provider API, source of truth, or reconciliation writer. Its current public crate is real, but exposes one read-only environment-resolution request against a running daemon; it cannot start/populate that daemon or call providers. Initial default: no mandatory fnox dependency. Promote only if exact versions, Rust 1.85 compatibility, lifecycle, policy mapping, latency and error behavior pass the gates below. `fnox exec` remains a subprocess/injection comparator, not assumed to be the best embedding.
3. **V3 (measured next):** add a Fleet-owned, bounded in-memory cache contract and encrypted offline snapshot only where measurement proves need. Keep authority and freshness decisions in Fleet policy. Each ordinary entry carries provider/item identity, version/revision when available, fetched-at, classification, max age, revocation semantics and source provenance. Successful writes/rotation/revocation invalidate exact ordinary-secret entries synchronously; provider events invalidate if available; no event means bounded TTL and explicit refresh. Singleflight by canonical secret identity + provider scope; never let a failed refresh silently reset age or turn an inaccessible scope into absence. Serve stale only where policy explicitly permits and max age is met; fail closed for revoked, high-risk, dynamic/lease-bound and signing values. **Root private keys are categorically excluded from ordinary hot caches and offline snapshots, even live-only cache: a separately authorized, bounded in-memory signer operation may load only the specific key for that operation and must clear it after use. Escrow is separately encrypted, recipient-restricted and governed by root-custody policy, never a cache tier.** Offline snapshots never authorize writes or reconciliation.
4. **V4 (future / separate decision):** compare service backends (OpenBao, later options) and hardware/TPM cache protection only after the isolated pilot; not prerequisites for Fleet v0.3. Root escrow is separately policy-gated and never inherited from general cache/replication.

V1 is the observed current-state label from the intake; it is not an implementation stage. V2-foundation is the first proposed implementation stage below.

### Why this is not “fnox solves caching”

The current fnox docs describe three distinct surfaces: provider resolution by its CLI; a disk-persistent, encrypted `fnox sync` snapshot (manual refresh, no self-updating freshness); and a memory-only per-user daemon. The published `fnox-client` 1.48.0 crate is expressly read-only: it can ask an already-running daemon for the result of `fnox env --json`, but cannot start the daemon, store resolved values, or trigger provider fetches. The daemon documentation says values remain until explicit per-key clear/refresh, process/config/environment lifecycle changes, or daemon stop/idle exit; rotation is not automatically observed. Thus a client can reduce repeated reads but cannot satisfy Fleet freshness or write/reconciliation semantics alone.

An embedded private daemon protocol would couple Fleet to a wire version; a subprocess adds startup and environment-injection exposure. The crate marks its public API semver-covered but wire/path/peer APIs are shared and change with protocol. A measured adapter can depend only on its public API, handle `Miss`/`Disabled`/transport errors distinctly, and fall back to Fleet's existing authoritative path; no direct wire parsing. Before adding it, confirm current crate MSRV against Fleet workspace Rust 1.85 and the locked toolchain (currently 1.99.0 per dossier). If dependency or policy incompatibility is material, use a CLI boundary or reject integration.

## Cache and resolution contract

### Required result metadata

An internal resolution result should carry `SecretValue` (or equivalent redacted type), selected provider and native reference, optional provider version/revision, `fetched_at`, `age`, cache state (`authoritative`, `memory`, `encrypted_snapshot`), classification, freshness decision, and a nonsecret operation/trace ID. Never include values in `Debug`, errors, logs, metrics labels, benchmark output, URLs, process arguments or ordinary JSON. Do not expose a cache's age as proof that upstream is current; it is only age since last verified read.

### Freshness/invalidation rules

* Cache key: canonical logical secret ID **plus provider/account/project/vault scope and policy/profile**. Names alone can alias distinct records; never cross scopes or identities. Root private-key bytes are categorically outside this cache key space.
* On successful Fleet-mediated write, rotate, restore, or authoritative delete, invalidate memory and encrypted snapshot entries for that logical secret and affected native IDs before success is reported. If provider write succeeds but read-back/receipt fails, return partial/unknown and keep the old cache unusable for an authoritative freshness claim.
* Provider-side changes not mediated by Fleet: use provider revision/event/watch where truly supported; otherwise finite TTL with explicit per-class maximum stale age and optional forced refresh. Manual `fnox sync` cache is not self-refreshing; daemon does not watch vault changes. Document this distinctly in config and CLI.
* Revocation is stronger than ordinary rotation: maintain deny/revocation tombstones at Fleet policy layer, invalidate all copies, and do not serve older snapshots when revocation status is unknown for a class requiring fresh status. A provider 403/timeout/partial list is `unavailable`/`inaccessible`, not `NotFound` and never deletion.
* Singleflight must deduplicate concurrent misses only for the same scoped key; wake all waiters with identical success/error, remove the gate after completion, bound waits, and allow unrelated secrets/providers to proceed. Bound provider concurrency and honor backoff/Retry-After where present.
* Freshness classes should be policy data, not magic global TTL: `no-cache / live-only`, `short-lived`, `machine-static`, `deployment-snapshot`, and separately governed `root-escrow`. Lease/dynamic/revocable values default to live-only absent an explicit reviewed exception. Root private keys are categorically excluded from ordinary cache/snapshot paths; bounded authorized signer use is distinct from cache, while escrow has its own custody policy. Snapshot has independent recipient/bootstrap and recovery, versioned schema, expiry and integrity verification; never store plaintext to disk.
* The broker source contains the per-secret install/timestamp/age/source mitigation merged in PR #8491 (`c676d1c41c07`), with reported tests 59/59. Coordinator verified #6767 remains OPEN for deployment/live canary. This design reuses that baseline, does not duplicate its fix, and does not claim deployment or canary proof; the live canary is not authorized here. New work is the policy-owned max-age/freshness decision layered on observable age. Preserve no-eviction-on-partial-list and make incomplete/failed inventory visible.

Method: pin code/tool/provider SDK versions and fixture inventory; separate warm-up; randomize/interleave path order with a recorded seed; use a monotonic clock; retain every attempt and raw anonymized timings. For each comparable cell, define p99 as the nearest-rank empirical quantile `x_(ceil(0.99 n))` of successful completed-operation latencies; `x_(i)` is the one-based i-th sorted observation and ties remain repeated values (never jitter them). Under the stated IID/stationary-trial assumption, compute a two-sided equal-tail, at-least-95%-coverage nonparametric order-statistic interval: let `B ~ Binomial(n, 0.99)`; choose the **largest** lower rank `k` with `P(B < k) <= 0.025` and the **smallest** upper rank `l` with `P(B >= l) <= 0.025`; report `[x_(k), x_(l)]`, n, k/l, endpoints and exact quantile convention. Ties may make endpoints equal and must be reported as observed. A 100-sample cell is exploratory, **not** reliable p99. Any p99 used for comparison/gating requires at least 10,000 measured operations per cell and that interval; the floor alone does not imply a narrow/reliable interval. If dependence, nonstationarity or censoring invalidates the IID assumption, label p99 exploratory/unavailable or preregister block bootstrap and block-length rule before observing outcomes; do not choose a method post hoc. Report interval width; a wide or unavailable interval cannot support a superiority claim. Count all attempts and report failures, timeouts and throttles separately; p99 over successes does not replace failure rate, and timed-out/censored attempts are not silently dropped. Include RTT control and identical payload sizes. The 24-hour low-concurrency soak is only required before claiming systemic provider slowness. Do not compare cached local answers with uncached network fetches as if freshness-equivalent.

### Acceptance thresholds are learned, not made up

First land a baseline, with no performance assertion. After baseline, implementation owner proposes numeric p95/p99 and regression budgets with workload rationale in the report; reviewers may refine them without blocking progress or waiting for another user response. Until then, the oracle is accurate, reproducible measurement and no security/correctness regression—not a guessed threshold. Promote fnox only if (a) bounded daemon hit materially improves the measured workload versus Fleet's corrected broker/cache under the documented proposed target, (b) no stale-read violations, secret exposure, or lost error distinctions, (c) dependency/toolchain and platform support pass, and (d) an explicit kill switch and fallback exist. If no meaningful gain, retain evidence and do not add a dependency. Require a separate decision for persistent fnox sync cache; its manual refresh is not continuous freshness.

## File formats and NixOS integration

**Default: use age/SOPS/sops-nix for deployment ciphertext; do not introduce a parallel new encrypted-file format.** SOPS is an encrypted structured-file editor with supported YAML/JSON/ENV/INI/BINARY forms and age/KMS/PGP recipient backends. `sops-nix` decrypts at activation into runtime files with declarative owner/mode and atomic replacement; it does not make the private identity unimportant. Existing repository NixOS provisioning already uses sops-nix patterns; Fleet should add a provider/artifact adapter and controlled commands, not fork SOPS crypto or claim to replace Nix evaluation/activation.

* Commit only explicitly scoped ciphertext and public recipient/config metadata. Age private identities, SOPS credentials, root keys and decrypted values remain outside Git, Nix derivations/store paths, build outputs, CI logs, prompts, image layers and ordinary flake interpolation. Verify actual derivation/store paths in a clean synthetic build. Provision private identities at a protected runtime path (`/run`/persisted protected storage as applicable), outside the store; test rebuild/bootstrap and impermanence behavior.
* Use per-host/site recipients and an independently protected recovery recipient when policy authorizes it. Age re-encryption changes current ciphertext recipients but cannot retract old Git-history copies: remove recipient + rekey, and rotate underlying secret if former recipient access must end. Keep recipient inventory/version and old-identity recovery policy; test overlap, offboarding, lost host, key rotation and restore while disconnected.
* sops-nix runtime file paths and service owners are the deploy interface; never place decrypted values into Nix options that become store strings. Tests inspect both store closure and activation output for plaintext. Flux decryption and Kubernetes Secret materialization are separate later delivery surfaces with separate etcd/RBAC/backup controls.
* SOPS/age is not a live ACL/lease/audit service or browser vault. Do not synchronize every BWS/OP object into Git; per-secret class/replication/recipient policy and plaintext-risk review precede export. Ciphertext still leaks names, shape, history, recipient metadata and timing; scrub filenames/metadata where sensitive.
* Fleet should preserve SOPS-compatible files and use pinned external SOPS tooling unless a specific stable library API and maintenance case is proved. Interface owns manifest validation, policy, recipients, safe temp/output handling, rekey plan, verification and receipts; SOPS/age own their established format/crypto.

### SecureStore and AEAD-envelope evaluation (not a cryptographic audit)

`securestore-rs` 0.100.3 exposes a native Rust `SecretsManager`, file-backed JSON format and get/set/save API. Official project docs describe v3 as AES-128-CBC + HMAC-SHA1 and password derivation PBKDF2-SHA1 (256,000 rounds); Rust docs show optional OpenSSL or RustCrypto backend features. This does **not** establish a practical break, nor does repository activity/release date establish an independent audit or robust long-term maintenance commitment. Its symmetric key-file/password model and whole-store read/modify/write format do not provide SOPS/age's multi-recipient public-key workflow, deployed Nix integration, per-host rekey model or Fleet's provider policy. It also creates a redundant ciphertext format and must independently answer atomic update/concurrent-writer, rollback, metadata authentication, KDF upgrade, version migration, corruption recovery and cross-language compatibility questions.

The bounded technical evaluation itself is required in V2; do not condition research on first finding a gap. Compare SecureStore with SOPS/age **and** a plausible modern AEAD-envelope alternative built from maintained, reviewed primitives (for example, a versioned envelope with AEAD payload encryption and explicit data-key wrapping/recipient lifecycle). Determine whether the alternative adds value beyond the already-supported SOPS/age recipient model; document a reasoned no-prototype decision if it does not. Do not invent or adopt a new format during this research. Recommendation remains **do not adopt SecureStore as Fleet's canonical cache, escrow or deployment format now**. Any import/export adapter, AEAD prototype or deployment adoption remains conditional on a concrete need, independent crypto review, maintenance/MSRV/dependency review, concurrency and format-evolution tests, migration/recovery proof, and a demonstrated capability gap. `pass` remains an optional GPG/Git import/export comparator, not a machine provider default; `scrt` explicitly reports not production-ready and is UX/threat-model prior art only.
