# Fleet v0.3 design: operational plans, evidence and generated guidance

**Status:** design proposal; no live operations, issue writes, production keys, provider writes, deployments, or repository policy edits were performed.  
**Scope:** operations, evidence and operator-facing output around credentials/generators/PKI; issue proposals are children of #9165.  
**Current evidence:** Fleet has an established multicall and feature/capability model plus `fleet secrets get/list`; the v0.3 plan/apply/verify operations, generated docs, batch runner, SSH writes, and reference artifact evidence are not current implemented behavior. Cross-cutting decisions in `architecture-review.md` ADR-S01/S03/S06 and `source-precedence.md` apply.

## 1. Architecture and truth labels

Operations live in the existing Fleet binary and library; there is no competing CLI. The proposed command names in spec §§25 and 43 are canonical design examples only. Keep `fleet secrets get/list` semantics and broker/BWS resolver intact. The actual code has a registry with capability stubs (`pkgs/fleet/crates/fleet-registry/src/lib.rs`, lines 1–20) and optional full/serve/connect Cargo feature sets (`pkgs/fleet/crates/fleet/Cargo.toml`, lines 40–95); generated/help capability output must reflect compiled support, not aspirational docs. Current `fleet-secrets` is read-only by API contract and persists no values (`pkgs/fleet/crates/fleet-secrets/src/lib.rs`, lines 1–28, 139–193). `fleet secrets get` intentionally prints the returned secret to stdout (`pkgs/fleet/crates/fleet/src/secrets.rs`); errors/logs are redacted. #6767 mitigation merged as PR #8491, while the issue remains open pending deploy/canary per the cross-cutting census; this design authorizes no deployment.

Each canonical Fleet logical object has a stable opaque ID, separate from mutable path/name and provider-native IDs. Rename preserves identity; distinct objects do not merge merely because names match. Root private material is not an ordinary `SecretRef` and is excluded from ordinary resolver hot paths, caches, prefetch, benchmark datasets and equality indices. Blinded equality still leaks equality and is not anonymization. Signer and escrow capabilities/policies are separate; escrow never grants ordinary resolution. These are architecture-review ADR-S01/S03 and source-precedence §2.

Every run and artifact carries a truthful stage enum: `planned`, `validated`, `synthetic`, `test-environment`, `production-authorized`, `applied`, `verified`, `partial`, `blocked`, `rolled-back`, `unsupported`. A green schema-validation or dry-run is not evidence of provider authorization, filesystem mutation, service activation, deployed trust, valid client interoperability, or production readiness. A command’s success receipt names its precise stage; downstream receipts cannot upgrade prior status without new evidence.

Proposed common operation lifecycle:

1. **Plan:** parse input; resolve types/capabilities/versions and ownership; check scope, path, provider/auth references without revealing secret values; compute deterministic action list and consequences; issue stable plan ID, canonical plan hash, expiry, preconditions, required approvals, rollback/recovery map and evidence requirements. Read-only. No private export or mutation.
2. **Validate:** verify schema/version, authorization provenance, requested build capabilities, destination constraints, source revisions/fingerprints and current preconditions. Reject unknown fields unless a versioned schema explicitly allows safe extensions. Stale plan, changed target, insufficient permission, incomplete provider inventory or changed SSH host key invalidates apply.
3. **Approve:** separate approval capabilities by hazard: private material export, local overwrite, remote host change, provider/store write, credential retirement, root signing/custody, DNS/trust/deployment. Bind approval to plan hash, stable opaque object ID plus current locator/revision, scope, target, expiry and approver/policy evidence. A normal SecretRef/provider lookup is not root signer capability. Global `--force` never substitutes. Signed/integrity-bound noninteractive approvals are a future implementation, not permission in this design.
4. **Apply:** prepare immutable journal entry and backups first; use per-sink/per-host receipts and idempotency key; perform staged operations; never silently choose an alternate provider or weaken freshness/security policy. Multi-sink non-atomic writes are a saga with per-step commit/compensation state, not a claim of transactionality.
5. **Verify:** read back at each destination, compare typed semantic object/revision/hash/fingerprint and expected policy, independently validate generated crypto/formats and target-client results where relevant. Never log private payloads. A verified file write is not service activation.
6. **Recover/rollback:** reconcile journal and observed state before retry. Rollback only the precise plan-owned mutations after checking no intervening human change; never overwrite newer unrelated edits. For credential/key rotation, retaining old material is not equivalent to reactivating it at its origin. If removal/remote activation cannot be reversed, report the remaining state and recovery steps; no fabricated “rolled back”.

Batch YAML/JSON plans should be versioned, typed DAGs: unique operation IDs, explicit `after`, typed output references, idempotency key, exact source/target refs, policy, output sinks, and `on_failure` compensation/stop behavior. `validate` resolves schema/types/dependencies offline and identifies required scopes without generating secrets. `plan` returns immutable redacted operations. `apply` accepts only a plan whose hash, expiry, approval, scope and object revision still match. `verify` is read-only and yields per-operation and whole-plan status. Secrets enter through protected stdin/FD/file-ref inputs; never argv/env/history. Output separates redacted human progress on stderr from machine JSON/YAML on stdout. Atomic filesystem bundles stage in a same-filesystem temporary directory, safe-canonical paths, symlink/traversal and archive-bomb checks, content hashes and manifest, then atomic rename when supported; if the platform/filesystem cannot meet the declared contract, fail or clearly use a separately approved encrypted staging mode.

## 2. Run evidence and independent oracles

Machine-readable receipts should include schema/version, plan/run IDs, parent IDs, stable opaque logical object IDs (not names as identity), idempotency key, Fleet source revision and derived version, binary variant/capability list, tool/library/provider/client versions, fixture identity (synthetic vs authorized test), timestamps, scope IDs with privacy classification, action names, precondition/result hashes, per-sink status, verifier identities/results, approval reference and rollback/recovery pointer. Exclude credential values, private keys, raw provider tokens, passphrases, OTP seeds, root equality tokens, and unkeyed equality hashes of low-entropy secrets. Receipt debug/serialization tests must prove redaction. Preserve exact command and logs only after structured redaction; never rely on manual cleanup of a leaked value.

Test oracle discipline follows repository `AGENTS.md`: each test names a decision procedure. Use PBT for format/path normalization, serializer round trips, unique batch IDs, manifest invariants, safe file transaction states and generator policy invariants; MBT for plan/apply/retry/recover, reconcile saga, SSH rotation and install state transitions; fuzz untrusted schema/PEM/SSH/config/archive input; crash/fault injection around fsync/rename/provider partial writes. Independent verification uses OpenSSL 3.5+ and separate Rust X.509 verifier where supported, OpenSSH tools, pinned native iroh APIs, platform-specific trust/client tests, provider test vaults and typed model/reference fixtures. Expected success must be independently derivable; mock success is not a production oracle.

Status of eventual reference proof: only after implementation, use the **built Fleet binary** to make synthetic/authorized-test password/token/ID/SSH/iroh and PKI outputs, then validate with those independent oracles. Record command, version, fixture identity, manifest/artifact hashes, verifier version, positive and negative outcome. `fleet` itself must be the producer; hand-written OpenSSL generation scripts cannot stand in for Fleet generation. No production root key generation, signing, escrow, export, vault writes, trust/DNS changes or remote rotation is authorized by these issue packets.

## 3. Generated docs, manpages, skills and deployment kits

Use the same typed command/API/capability descriptors that drive Fleet help to generate compact `--help`, long help/offline Markdown and man pages; completion schemas for bash/zsh/fish/PowerShell; JSON/YAML batch schemas; samples; and selected agent skill bundles. No hand-maintained second command tree. Each generated page reports status (`implemented`, `partial`, `planned`, `unsupported`), build/profile/backend requirements, authentication scope, output confidentiality, error codes, hazard/approval class, side effects, examples and links to recovery. Diff generation is deterministic and fails if a command/capability lacks docs, examples, negative tests or status.

Skills and AGENTS guidance are proposals, not edits in this task. A future `fleet skills install` must choose explicit project/user/system and agent target, validate manifest/version, avoid overwriting user-authored `AGENTS.md`, stage/backup atomically, record an idempotent install receipt, and support inspect/upgrade/remove with ownership boundaries. The install command itself must be inside Fleet’s existing multicall surface. Skill content repeats core invariants: inspect/capability-check, plan first, never echo secrets, no implicit root signer, preserve `zz.delete`, distinguish stored from activated rotations, verify host keys out of band, no production mutation without scoped approval, and report test vs production status.

Generated deployment kits are per-client and per-trust-profile, not “install all roots everywhere.” Kits contain only public artifacts unless a distinct approved private sink is requested: versioned manifest, hashes, relevant chain/trust bundle, formats the client supports, tailored install/verify/rotate-overlap/remove instructions, privilege constraints, rollback and negative trust test. Support profile distinction between compatibility and strict PQ-only; never claim public WebPKI/browser trust for a private CA. AIA/CRL links are hints; package known-good chains. Include SSH instructions separately from X.509. Each client guide names exact tested OS/runtime/library and version; unsupported rows say untested/unsupported rather than “works.”

## 4. Issue-ready operations/evidence packets — parent #9165

All packets are proposals, not issue writes. Content is aligned with coordinator §4.2. Initial status Backlog; dependencies use IDs within this design and cross-design `GEN-xx` IDs, to be made native blockedBy links during issue creation. Numeric priority recommendation: 450/High only where required to prevent unsafe mutation or unlock implementation; Standard otherwise.

### OPS-01 — Versioned plan, approval and receipt schema

* **Kind / requirement:** design + implementation. OPS-003, OPS-005; spec §§10, 25.2–25.3, 43, 48.2 `V3-S02`, `V3-S13`, `V3-S18`, `V3-S25`.
* **Why/outcome:** typed, immutable machine-readable plan, scoped approval, run receipt, lifecycle status and rollback/evidence references shared by generator and operation commands.
* **Current evidence / boundary:** current Fleet already has version/capability reporting and std-only registry; current secret API resolves names but has no operation journal/write contract. Own common schema/API and validators, not workflow implementation, provider writers or approvals authorizing live work.
* **Acceptance:** JSON Schema and Rust types are versioned; round-trip preserves semantics; IDs and plan hash deterministic for same canonical inputs; secret fields are excluded/redacted; unknown schema/version, duplicate operation ID, expired/incorrectly bound approval, malformed precondition and unsupported status fail closed; examples cover planned/test/partial/blocked/verified without implying production.
* **Oracle / negative:** JSON Schema validator vs Rust validator on a shared golden corpus; property tests canonicalize/re-encode; secret sentinel scanner checks serialized receipts. Reject `--force` as approval and tampering with one plan byte.
* **Dependencies:** none; blocker for OPS-02–OPS-06 and GEN-07 onward. **Files:** operation schema/API and fixture corpus. **Safety/rollback:** no approval is issued; schemas are additive with explicit migrations. **Urgency/size/stage:** High / L / V2; Backlog.

### OPS-02 — Offline batch DAG schema and validation

* **Kind / requirement:** design + implementation + tests. PKI-050, GEN-008, OPS-003; spec §§6.2, 6.3, 6.5, 25.1, 25.4, 28.1, 31 `PKI-050`, 43.
* **Why/outcome:** one batch format can validate named operations, typed references, dependency DAGs, outputs, idempotency and compensation without executing them.
* **Current evidence / boundary:** Fleet’s proposed batch commands are design-only; preserve the existing multicall and one command grammar. Own v1 manifest/schema/validator; no secret generation, file/provider/network mutation.
* **Acceptance:** schema enforces unique operation IDs, legal typed refs, no cycles, declared output/sink types, deterministic topological order, bounded size/depth and supported command capability; validate emits redacted plan and required capability/scope list; JSON and YAML equivalent fixtures canonicalize identically; invalid/unknown version rejects before any entropy or I/O call.
* **Oracle / negative:** MBT/reference DAG evaluator checks generated valid DAGs; property tests ensure acyclic order and type preservation; fuzz parsers. Reject unresolved refs, cycles, duplicate IDs, path traversal, unsafe private output and a write command presented to validate as mutation.
* **Dependencies:** OPS-01, GEN-01. **Files:** batch schema/parser/validator. **Safety/rollback:** validator is side-effect-free; explicit fake IO asserts zero writes. **Urgency/size/stage:** High / L / V2; Backlog.

### OPS-03 — Plan/apply/verify/recover execution engine

* **Kind / requirement:** implementation + fault-injection review. OPS-002–OPS-003; spec §§10, 21.7, 25.2–25.4, 28.1–28.2, 43; handoff §§10 and 48.1.
* **Why/outcome:** safe, resumable operations shared across local files and future provider work, with idempotency, precondition checks, journal-before-side-effect and per-step receipts.
* **Current evidence / boundary:** no current Fleet plan/apply/recover contract; current secret resolver is read-only and doesn’t persist values. Own generic execution orchestration and filesystem/test sinks only. No production backend adapter or deployment lifecycle.
* **Acceptance:** `plan` cannot mutate; `apply` rejects stale/changed target plan hash, missing approval, unsupported build capability or revision mismatch; journal is durable before side effect; retries after each injected crash do not duplicate completed operation; `verify` is read-only; recover observes state and never overwrites intervening edits; multi-sink operations report partial saga, not atomic success; distinct hazard approvals enforced.
* **Oracle / negative:** MBT compares generated retries/faults against an operation-state reference model; crash tests at journal/fsync/write/rename/readback; independent before/after snapshots. Negative: API timeout/403/partial list not absence; global force cannot bypass approval; unapproved apply has zero side effects.
* **Dependencies:** OPS-01, OPS-02. **Files:** operation engine, journal contract, tests. **Safety/rollback:** synthetic temp directory backends only; production adapter remains disabled until its own issue/gates. **Urgency/size/stage:** High / XL / V2–V3; Backlog.

### OPS-04 — Atomic, recoverable file and bundle transaction library

* **Kind / requirement:** implementation + platform test. GEN-008–GEN-009, SSH-002/003/005, PKI-048/055/057; spec §§23.2, 25.3, 28.1–28.2, 48.2 `V3-S21`.
* **Why/outcome:** safely materialize public/private output layouts and edit controlled local files without truncation, permission leak or losing user changes.
* **Current evidence / boundary:** no generator file sink exists in Fleet; id uses working-directory-relative identity/store files (`pkgs/id/src/main.rs` lines 213–244) and must remain untouched. Own reusable Fleet file transaction module; test temp roots only, no operator-home modifications.
* **Acceptance:** reject symlinks/traversal/archive bombs/duplicate paths; enforce target ownership/mode/private-public separation; stage and fsync before commit; support interrupted multi-file saga with exact per-file status; readback validates hashes/manifest; rollback refuses if user changed target after apply; injected failure yields original bytes or explicit recoverable partial state on every supported filesystem.
* **Oracle / negative:** independent archive/path parser, file hash snapshots, crash/fault injection and mode/UID/GID checks in temp directories. Negative covers symlink swap, case-collision path, disk-full/fsync error, changed original, world-readable private key, and unsafe temp filesystem.
* **Dependencies:** OPS-01, OPS-03, GEN-08 for SSH integration. **Files:** file I/O library and tests. **Safety/rollback:** no real credentials/files; platform cannot meet atomic contract → refuse rather than overclaim. **Urgency/size/stage:** High / XL / V3; Backlog.

### OPS-05 — Generated help, manpages, completions and schemas

* **Kind / requirement:** implementation + documentation. OPS-004–OPS-005; spec §§6, 12, 25.1, 29, 31 `OPS-004`–`OPS-005`, 48.2 `V3-S24`.
* **Why/outcome:** actual executable contract drives concise/long help, Markdown, man pages, shell completions and JSON/YAML schemas from one command registry.
* **Current evidence / boundary:** `fleet-registry` already renders full domain surface and capability stubs in all variants; `pkgs/fleet/README.md` documents it. Current domain help is not the v0.3 generator help. Own registry/doc generator adaptation; no unimplemented command advertised as active.
* **Acceptance:** generated artifacts deterministic and checked in or reproducibly built; every command has synopsis, flag types/defaults, error/status/approval classes, feature/capability and sensitive-output annotation; snapshot tests compare actual `fleet --help` and variants; hidden/unavailable verbs have truthful stub messaging; docs build fails on registry/doc drift or missing tested example.
* **Oracle / negative:** command descriptors are source of truth; golden CLI output and shell completion parser validation. Negative: unsupported command must not autocomplete as available in narrowed profile, no private values in completion/help, and an aspirational command cannot carry implemented status.
* **Dependencies:** OPS-01, GEN-01, existing fleet-registry. **Files:** registry descriptor/generators and snapshots. **Safety/rollback:** additive help changes; revert generated artifacts if parity fails; preserve command compatibility. **Urgency/size/stage:** Standard / L / V2–V4; Backlog.

Skill references only commands actually marked available in target variant.
* **Oracle / negative:** manifest validator and filesystem snapshot; golden install/remove pairs; blind-run test by fresh agent using only installed skill + Fleet help, no unapproved mutation. Negative verifies user text is unchanged and unknown agent adapter is refused.
* **Dependencies:** OPS-05, OPS-01, GEN-05–GEN-09 documentation contracts. **Files:** proposed Fleet skill registry/template/installer only. **Safety/rollback:** synthetic temp config trees; no write to real AGENTS.md or agent settings in design task. **Urgency/size/stage:** Standard / L / V4; Backlog.

### OPS-07 — Per-client deployment kit generator and verify guides

* **Kind / requirement:** implementation + documentation/test. PKI-028–029, PKI-035, PKI-039, PKI-059; spec §§7, 12, 25.3, 28.1, 29, 44–44.2.
* **Why/outcome:** reproducible public-only (default) distribution kits provide chains, formats, hashes, install/verify/rotate/remove steps and explicit trust-profile/client limits.
* **Current evidence / boundary:** Fleet has no PKI commands or emitted kits; source includes detailed client matrix and private-vs-public trust caveats. Own generic kit assembly/schema/docs; no production certificates, DNS, HTTP mirror, trust-store install or private key packaging.
* **Acceptance:** generate synthetic compatibility and strict PQ-only kits from a Fleet manifest; kit contains only profile-approved public artifacts, fingerprints/hashes, exact format/client requirements and rollback; wrong profile cannot include disallowed trust anchors; generated install instructions validate on named tested clients; unsupported client says so; no claim private roots are internet/browser trusted.
* **Oracle / negative:** hashes and independent OpenSSL/Rust verifier plus actual supported client matrix; negative trust tests ensure classical path rejected under PQ-only, prevent private key inclusion, and prevent an untested client from “supported” status.
* **Dependencies:** OPS-01, OPS-05, GEN-04/GEN-10, PKI manifest/engine implementation (separate issue). **Files:** kit renderer/docs templates and synthetic fixture tests. **Safety/rollback:** synthetic only; install commands are examples, not run. **Urgency/size/stage:** Standard / XL / V3–V4; Backlog.

### OPS-08 — Synthetic Fleet-generated reference evidence pipeline

* **Kind / requirement:** integration test + security evidence. GEN-002–GEN-006, GEN-010, IROH-001/002, PKI-064, OPS-006; spec §§28.3, 31 `OPS-006`, 48.1 phase 8, 48.3.
* **Why/outcome:** after features exist, a scripted acceptance suite uses the built Fleet executable itself to generate reference synthetic password/token/ID/SSH/iroh and PKI outputs, then independently checks formats, redaction, key material handling and the 4-root/A/B reference graph.
* **Current evidence / boundary:** no generator/reference artifact pipeline exists in current Fleet; the source explicitly calls this a future release gate. This packet tests implemented Fleet outputs and fixture keys only; cannot create production keys or publish trust artifacts.
* **Acceptance:** capture pinned source revision, Fleet derived version/build variant, command lines (no secret args), fixture IDs, artifact hashes, verifier versions, valid and intentionally invalid results; producer is Fleet, verifier is independent; expected PKI reference count is 20 CA key pairs/65 cert variants only when the PKI implementation stage is ready; generated private keys live in ephemeral isolated test storage and are destroyed by test harness after receipts contain no bytes.
* **Oracle / negative:** OpenSSL 3.5+ plus Rust verifier, OpenSSH, native iroh parser, typed expected manifest/matrix and negative-path oracle. Negative cases include broken signature, wrong EndpointId, invalid key-format identity, accidental classical path in PQ-only, unexpected private output, and test command reaching provider/network. Fail if output is generated by helper scripts instead of Fleet.
* **Dependencies:** GEN-02–GEN-06, OPS-03/04, PKI generation/manifest work; test pipeline can land later. **Files:** isolated integration harness, fixtures, report schema. **Safety/rollback:** opt-in local/CI tests only, synthetic keys, no external endpoint/vault or production artifact. **Urgency/size/stage:** High / XL / V3 release gate; Backlog until all producers exist.

### OPS-09 — Client and operating-system compatibility matrix

* **Kind / requirement:** test + documentation + research as needed. PKI-061–062, PKI-059, SSH-001/005/008, IROH-001/002, OPS-006; spec §§11, 23, 28.2, 44, 44.2, 48.2 `V3-S15`–`V3-S17`, 48.3.
* **Why/outcome:** maintain exact, versioned capability statements for OpenSSL/Rust, Linux distributions, Windows/macOS, browsers/JVM/mobile/embedded, OpenSSH, and iroh. Test only reachable/relevant clients; unsupported algorithms are explicit.
* **Current evidence / boundary:** source spec lists target families; no current generator/client capability claims exist. Own matrix/evidence harness; no global trust installation or browser production trust change.
* **Acceptance:** every row has tool/version, supported format/algorithm/path policy, command, positive and negative result, date, evidence hash; PQ-only tests demonstrate full ML-DSA path and rejection of classical path on capable policy verifier; distinguish path validation from TLS key exchange; OpenSSH signature auth distinct from PQ KEX; unrun rows remain unverified.
* **Oracle / negative:** each client’s actual verifier plus generated trust profile; independent expected chain model. Negative includes missing/unsupported algorithm, malformed/ordered chain, classical fallback, wrong trust anchor, invalid host identity and SSH non-X.509 conversion.
* **Dependencies:** GEN-04–GEN-06, OPS-07/08. **Files:** versioned matrix and harness adapters. **Safety/rollback:** tests use disposable local trust stores/VMs; do not mutate system store. **Urgency/size/stage:** Standard / XL / V3; Backlog.

### OPS-10 — Approval, custody and production-operation gates

* **Kind / requirement:** security/operations design. OPS-002; spec §§10, 17, 25.2, 28.3, 48.2 `V3-S08`, `V3-S25`; addendum §5; handoff §§10, 7.5.
* **Why/outcome:** map operation hazards to narrow approvals, custody checks, prerequisites, stop conditions and tested recovery. Preserve temporary initial root escrow intent (encrypted laptop, authorized BWS and OP copies) without treating this design as authorization; R2 is research only and no automatic expansion to future stores.
* **Current evidence / boundary:** no operator approval/custody contract for v0.3 is implemented by this design; current Fleet resolver does not offer writes. Own design and synthetic gate harness, not actual vault/key/production operations.
* **Acceptance:** hazard matrix separates private export, overwrite, remote key change, provider write, retirement, root signing/custody and DNS/trust/deploy; each gate specifies exact authority scope, preconditions, evidence, backup, rollback and stop criteria; root signer is explicit with no ambient default; `plan` works without secret export and `apply` requires plan-bound approval; root replicas require exactly the approved set and no implicit future provider.
* **Oracle / negative:** approval policy model + fault-injected state machine; all unapproved or stale decisions must show zero mutation. Restore proof is synthetic only until separately authorized; no shared bootstrap/circular recovery assumption.
* **Dependencies:** OPS-01/03; GEN-09 for remote changes; separate PKI custody design. **Files:** policy docs/schema/tests. **Safety/rollback:** design only, no production roots or credentials generated/exported/synced. **Urgency/size/stage:** High / L / V2–V3; Backlog; production actions Blocked pending explicit approval.

* **Oracle / negative:** fresh-context operator walkthrough on disposable environment; command snippets validated against built Fleet `--help` and test fixtures; no successful path depends on hidden state. Negative rejects absent command/capability rather than inventing syntax.
* **Dependencies:** OPS-05, OPS-06, GEN-05–GEN-09. **Files:** generated docs/templates/runbooks. **Safety/rollback:** documentation only; no live command execution. **Urgency/size/stage:** Standard / L / V3–V4; Backlog.

## 5. Sequencing, non-goals and decision gates

Suggested sequence: OPS-01 → (GEN-01, OPS-02) → (GEN-02–GEN-06, OPS-05) → OPS-03 → GEN-07 and OPS-04 → GEN-08 → GEN-09 → OPS-06/07/09 → OPS-08 release evidence. OPS-10 runs before any production operation and blocks it until explicit authorization/custody proofs. PKI references are deliberately dependent on the separate PKI engine/issues; these operations packets do not pull unrelated PKI implementation into generator issues.

Keep current behavior while layering: registry surface → typed library → generator/adapters → safe sinks/adoption → local edits → remote lifecycle → docs/evidence. Do not add an unreviewed `--force`; do not generate a second CLI; do not alter Fleet secrets resolution contract to simulate full secret management; do not use `pkgs/id` or Atlas as proof Fleet supports their domain; do not merge user guidance into `AGENTS.md` now. No live operation or issue write was performed.
