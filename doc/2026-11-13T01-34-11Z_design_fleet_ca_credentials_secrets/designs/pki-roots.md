# PKI root set, graph, and custody design

**Status:** proposed design for implementation planning; no production roots or signer capability have been verified or created here. This document is subordinate to the complete Fleet v0.3 specification and its dated addendum. Where the original Appendix A differs from later decisions, §§24, 30–33, 44 and 48 plus the addendum control. “Current verified capability” below means only evidence actually inspected in this work; it is not an assertion of deployed PKI functionality.

## Decision summary

1. The reference root generation has exactly four independent CA key identities: Ed25519, ECDSA P-256, RSA-4096, and standardized ML-DSA-44 (FIPS 204; X.509 encoding per RFC 9881). Each has one self-signed root certificate. All 13 root certificate variants (4 self-signed and 9 cross-signed) in the reference profile use exact `notAfter=2050-07-07T12:00:00Z`. If a signer/parent/policy cap would shorten any variant, fail with `ReferenceValidityMismatch` or require an explicitly named non-reference profile and newly authorized plan; never pass a shortened artifact as the requested reference. Ordinary profiles still obey their own parent/policy caps.
2. Generate exactly nine asymmetric root cross-certificates: six classical-to-other-classical directed edges and three classical-to-ML-DSA edges. Never generate ML-DSA-root-signed classical roots by default. Cross-certificates are path-building candidates, not trust anchors.
3. For each of Base and Internal Web, generate A and B as independent keys for each of the four algorithms. The requested reference direct-issuer graph produces 13 certificates per partition, 26 per purpose, and 52 issuer certificates total. Together with 4 root keys and 13 root certificate variants, this is **20 CA key pairs / 65 CA certificates**, before leaves.
4. Root private-key operations require a caller-specified, authorized signer source and a transaction-bound authorization on every operation. No ambient/default discovery or automatic use of escrow is permitted. Root signing is distinct from escrow and requires its own durable anti-replay authorization and audit transaction.
5. Initial root escrow is exactly these three authorized destinations: encrypted laptop storage, the authorized BWS project, and the authorized 1Password vault. R2 is research-only, not a fourth replica. Escrow copies are encrypted, integrity checked, least-privileged and restoration-tested; recovery must not depend circularly on the failed destination or the key being restored.
6. Root replacement is a new generation, with explicit trust migration and retirement; certificate renewal is not key rotation. Unsupported algorithms, path profiles, provider operations, or client combinations fail closed with a precise unsupported result—never silently substitute cryptography.

## Root identities, certificates, and graph

Canonical algorithm identifiers and key identities are stable machine IDs (`ed25519`, `p256`, `rsa-4096`, `ml-dsa-44`); presentation names are metadata, not identity. Root subjects default to `C=US, O=developing.today LLC`; use unique, unambiguous CA CNs ending in generation token `G1` (for example `developing.today LLC Root CA Ed25519 G1`). Do not invent DNS SANs for CA subjects. Record independent generation/partition structure; roots start at G1, with no A/B root partition implied. (§§3.1, 5.1–5.2, 24.4.)

Certificate inventory:

| Class | Keypairs | Certificates | Construction |
|---|---:|---:|---|
| Four roots | 4 | 4 | One self-signed certificate per distinct root key |
| Root cross-certificates | 0 additional | 9 | Classical roots each sign the other two classical public keys (6 directed certs); each of three classical roots signs the ML-DSA root public key (3 certs) |
| Base issuer A/B | 8 | 26 | 4 algorithms × 2 distinct keys; for each partition: classical issuers each signed by all 3 classical roots (9), ML-DSA issuer signed by all 4 roots (4) |
| Internal Web issuer A/B | 8 | 26 | Same matrix, distinct keys from Base and from the other partition |
| **Total** | **20** | **65** | Excludes leaves and CRLs |

For each same-key issuer cross-signed variant, Subject and SPKI (and therefore SKI) remain identical; issuer, AKI, serial, signature, fingerprint and path/revocation metadata differ. A and B are distinct keypairs and SKIs, not certificate copies. The ML-DSA root signs ML-DSA issuer keys only by default; classical roots sign each ML-DSA issuer key, as §24.2 specifies. A configurable graph may disable edges for future profiles, but the reference run is exactly `both` (root and direct issuer cross-signing). (§§3.2–3.3, 24.2.)

### Key and certificate profiles

- Use provider-backed implementations only when the selected provider supports the exact named algorithm, key encoding, signature scheme and required X.509 extensions. ML-DSA means standardized ML-DSA-44, not pre-standard Dilithium2. RSA-4096 root signatures use SHA-256 or stronger validated compatible schemes; P-256 uses ECDSA with an approved digest; Ed25519 uses its intrinsic signature algorithm; ML-DSA follows RFC 9881 algorithm identifiers and pure ML-DSA rules. Do not force a SHA-256 wrapper onto Ed25519 or ML-DSA. (§§3.1, 24.6.)
- CA certificates: critical `basicConstraints` with `CA=TRUE`; critical `keyUsage` containing `keyCertSign,cRLSign`; `pathLenConstraint=0` for issuers directly signing leaves, and root path length chosen consistently with the single issuer tier. Add unique issuer+serial identity, SKI derived from subject public key under documented method, and AKI identifying the actual signing issuer. Keep SKI stable across same-key cross-signed cert variants. (§§3.3, 5.2, 24.3.)
- Root self-signed and root-cross certificates have the root public key as SubjectPublicKeyInfo; cross-certificates identify the actual signing root in issuer DN/AKI. Do not mark cross-certs as installed anchors. Root self-signed anchors normally omit AIA/CDP; certificates that embed revocation/distribution URIs must refer to real planned resources. (§§3.5, 24.7.)
- Issuer certificate validity normally ends no later than signing root and profile cap. For the reference profile, **all 52** Base/Internal Web issuer certificate variants must use exact `notAfter=2032-07-07T12:00:00Z`. If a parent/policy cap would shorten any variant, fail with `ReferenceValidityMismatch` or require an explicitly named non-reference profile and newly authorized graph/plan; never count the shortened variant as reference output. The issuer-set policy/manifest encodes purpose, profile OID policy where defined, generation and partition. OU/CN are descriptive only, not authorization controls. Web leaf EKU is `serverAuth`; constrain names in supported verifier profiles and test relying-party behavior. (§§3.3, 24.4.)
- Serial numbers are positive, unique per issuer, high entropy and reserved collision-safely in an issuance ledger; never use filenames or timestamps as uniqueness. Every certificate includes full validity times and stable algorithm/OID data. Keep clock/skew policy explicit. (§§5.2, 5.4, 24.2.)
- Never accept an unsupported OID, invalid key-strength profile, weak signature, unknown encoding, or incompatible path by parsing alone. Fail closed with `unsupported_algorithm` / `unsupported_path` diagnostics and remediation, retaining the source object for forensic review without trusting it. (§§10.1–10.4, 11.1.)

## Trust path selection and distribution

Trust policy is an input to path construction, not an inference from available certificates:

1. `pq-only`: trust only the ML-DSA self-signed root; require ML-DSA issuer key and ML-DSA signatures at every CA edge. Reject any classical root, classical-signed intermediate, fallback, or path whose algorithm is unknown. The cross-certificates signed by classical roots do not provide a PQ path. This policy must be independently verified, not inferred from a successful generic validator run.
2. `classical-compat`: trust only explicitly selected classical anchors (or a named subset); permit a path only if every signature/key is implemented by the target validator. It does not assert PQ assurance. Classical root cross-cert edges may enable alternate paths but classical trust anchors have coupled scope, as spec §3.2 warns.
3. `all-compatible`: installs the four self-signed roots where deployment policy explicitly chooses it. This is compatibility, not a PQ security claim. A verifier must still select a chain it supports.
4. Never install the nine root cross-certificates or intermediate certs as trust anchors by convenience. Provide the self-signed roots separately: `roots-all.pem`, `roots-classical.pem`, `roots-pq.pem`; provide `cross-certs.pem` as untrusted candidates. Precompute root-specific issuer/leaf chains and distribute them proactively because AIA retrieval may be ignored or stop early. (§§3.2, 3.5, 7.2, 11.1, 24.7.)

Validation must explicitly construct candidate chains for every supported trust-anchor/issuer combination. PQ-only tests must reject RSA, P-256 and Ed25519 issuer paths even when those algorithms are available to the verifier. Include negative cases for reverse forbidden cross-sign, expired cert, invalid AKI, altered SPKI, duplicate serial, revoked CA, bad pathLen, unsupported OID, invalid EKU/name constraints and chain substitution. A “PASS” is conditional on actual verifier support and the exact supplied chain. (§§11.1–11.2, 44.2, 48.)

Interoperability claims are capability-reported per validator/client version. Validate DER/PEM consistency, cert-only CMS/P7C, trust installation bundles, and chain order with OpenSSL (version pinned) and an independent Rust X.509 path verifier with real algorithm support. Attempt Java PKIX/Windows or other clients where practical; report unsupported ML-DSA instead of treating parse success as verification. TLS ML-DSA is out of scope unless both ends have confirmed support. Never claim universal browser trust or that cross-signing adds missing crypto support. (§§7.5, 11.2, 44.)

## IDs, manifest, and serial ledger

Use versioned canonical `manifest.json` for the logical root set and each issuer set. At minimum record schema/bundle IDs and versions; creation time; policy and source/build revision; organization and structured subject; algorithm registry/provider versions; root key IDs and opaque storage handles; exportability; public key and DER hashes; certificate fingerprints, serials, issuer, SKI, AKI and validity; constraints/usages/policies; every graph edge and parent reference; generation/partition; trust-path variants; CRL/URL status; per-file visibility, media type, encryption and checksum; authorized provider sync receipt IDs without plaintext; validation results, warnings and predecessor bundle. A separate public manifest omits provider paths, private handles and sensitive infrastructure metadata. Signed/attested manifest support is recorded as available only when an authorized signing mechanism exists; checksums alone are not authenticity. Never derive authoritative state from directory names. (§§5.2–5.3, 7.1–7.2, 24.9.)

Assign each root/key/certificate a stable opaque UUID/ULID independent of display name, filesystem path, DNS name, provider-native ID, and logical secret path. Store the canonical logical path (`pki/developing-today/root-set/default/g1/<algo>/<artifact>`) as a mutable locator/attribute mapped through provider-specific adapters, never as object identity. Persist fingerprints, parent IDs and provenance separately. A durable serial ledger reserves collision-safe serials per issuer before signing and records aborts. Separately classify provider writes per adapter and operation as `atomic-precondition`, `serialized-by-contract`, or `unguarded`; do not assume portable CAS. A Fleet-local lease qualifies as `serialized-by-contract` only when **all writers**, including human apps and other clients, must honor that same lock. Otherwise the target is `unguarded`: the default stops in `needs_review` before any conflict-sensitive overwrite, and post-write readback is not protection against loss of an unseen concurrent value. Only a separately approved named weaker policy may proceed, with its lost-update window in plan and receipt; it cannot claim preservation. Additive immutable archive creates are not conflict-sensitive. Resume must not issue a duplicate after crash. Public bundle checksums cover public artifacts; encrypted private archives have independent authenticated integrity checks. (Architecture review ADR-S01/S02, A-1.)

## Authorized signing and escrow boundaries

Three distinct concepts must not be conflated:

- **Signer source and authorization:** each root operation supplies an explicit signer source and consumes a transaction-bound `SigningAuthorization` through the shared ARCH-06 signer seam. The authorization binds a finite enumerated set of per-signature tuples `(signer key fingerprint/handle, subject public-key identity, signature algorithm + parameters, profile/purpose, exact notBefore/notAfter, TBS/artifact-plan-entry SHA-256, authorized output/escrow destinations)` plus the canonical digest of the whole tuple set and a transaction ID. The tuple set is fixed before authorization; no tuple may be added or altered after approval. Single-tuple use is the default; bounded batch use is allowed only over the finite enumerated tuple set. The signer durably consumes each tuple/authorization before signing, preventing replay across process restart; a lost/uncertain response burns that tuple until reconciled by the signer receipt/audit, never blind-retried. The signer refuses any mismatch and returns a receipt naming the transaction and tuple. Inventory lookup, escrow read access, or merely holding key bytes never mints authorization. (Architecture review A-2; review/architecture-challenge.md A-2 precision note; spec §24.3; Claude handoff §25.)
- **Active signing custody:** the deliberate, authorized mechanism that can perform a root signature. It may later be an offline signer or hardware-backed interface. The design does not assert such an environment currently exists. A laptop or online vault escrow copy is not automatically an active signer.
- **Escrow/recovery copies:** encrypted, non-active recovery material. Exactly three initial destinations are approved by the addendum: (1) encrypted local laptop storage, (2) the specifically authorized BWS project, and (3) the specifically authorized 1Password vault. Do not infer personal `bw` vault access from BWS. No fourth destination is enabled by this design. Cloudflare R2 is research-only and needs a separate future authorization/decision. (Addendum §5; coordinator handoff §§7.5, 10.)

The three destinations form a closed enumerated `RootEscrowDestinations` policy type, not a generic provider list. Define two artifact forms explicitly: one independently encrypted archive per root and an optional complete four-root bundle archive; never assume either fits one provider field/object. Before any eventual write, probe each destination's supported write modes, encoding and maximum encoded size in an isolated synthetic scope, then preflight actual archive sizes; the exact BWS/OP limits and access rights are currently unverified. BWS values/notes are not general-purpose attachments, so do not assume the full archive can be stored in one BWS field or silently truncate it. If chunking is required, use immutable versioned chunks plus an authenticated manifest containing order, count, encoded length and per-chunk hashes; validate reconstruction/readback and isolated restoration before considering that destination complete. No provider's atomic commit/CAS is presumed: use per-destination receipts and report incomplete until the full archive independently restores. The escrow design uses authenticated encryption and separately protected recovery recipient(s); compression such as zstd is packaging, not encryption. Encrypt before provider upload. Keep plaintext/private keys out of repository, public artifacts, logs, telemetry, issue comments, shell arguments and default distributable archives. Enforce per-destination least privilege, private ACLs, opaque references, checksums/authentication, receipt and version metadata, and explicit partial-failure status. Custody is complete only when all three destinations are present and each destination can be restored in isolation while the other two are unavailable; otherwise report incomplete. The policy must never expand automatically to R2 or future providers. Recovery requires an independent recovery credential/device and documented procedure, not access solely through the compromised provider or the key being recovered. Restoration tests use synthetic keys until separately authorized. (Architecture review A-3; spec §§7.1–7.2, 10.2, 24.3; addendum §5.)

Generation, escrow synchronization, signing, and trust publication are separate transactions with approvals and receipts. A normal secret-provider sync must categorically exclude root private material. Root material is also excluded from ordinary resolver hot caches, prefetch, benchmark datasets, and metadata/equality indices; only a bounded, explicitly authorized signer session may hold it for its operation. **Before the first escrow copy exists**, bind the exact BWS project/native IDs and OP vault/item compartments to trusted policy and make ordinary broker/legacy resolver principals unable to list/read those scopes (prefer separate least-privilege grants). V1 broker refresh lists all accessible BWS records and caches values; the legacy name-only fallback can resolve accessible names. A `DataClass` supplied by a caller or mutable sidecar alone is not an exclusion. Test original broker-compatible list/refresh/cache and name-only get paths with synthetic encrypted root records; exclude/quarantine root scopes before enumeration or resolution. Unknown/adopted records require classification review before replication. This is a safety prerequisite for ROOT-09/OPS-10, not permission to change grants or create a BWS project; exact production identities remain approval-gated. The initial root ceremony may provision the three escrow copies only after explicit applicable authorization, verified broker isolation, destination identity checks, and rollback/recovery review; this design document is not that authorization. No production root generation, export, signing, vault write, DNS change, or trust-store modification is authorized here. (Coordinator handoff §§7.5, 10; Claude handoff §42; architecture-review ADR-S01; owner V1 broker safety finding, 2026-11-12.)

## Lifecycle, states, and rollback

Root key identity is immutable for a generation. `renew` means certificate reissue with same key only under an explicit policy and increments certificate revision; `rotate` creates a new private key and generation; `replace` orchestrates new generation, trust distribution, verification, activation and deprecation. Root replacement defaults to new key material. Never delete an old root/CRL/history while issued dependents remain valid. (§5.2; Appendix A PKI-042–044.)

Key ceremony approval and signature authorization are separate state transitions. Synthetic key generation follows the same typed model with test-only approval, while production key-generation/storage/escrow approval is not a signing grant. For each certificate/CRL signature, after the public subject key is known, durable serial is reserved, exact validity is selected and TBS/artifact-entry hash is frozen, request per-tuple `SigningAuthorization`; do not create a final signature grant earlier. Signature states are `PlanFrozen → SignatureAuthorizationPending → SignatureAuthorized → TupleDurablyConsumed → Signed → SelfVerified → IndependentlyVerified`. Tuple consumption is atomic and durable before signer invocation; uncertain/lost responses burn the tuple until authoritative signer audit reconciliation, never blind retry. Root bundle lifecycle is composed from these per-signature operations plus separate escrow and publication states; any failure has typed receipt and resumable/compensating action. Production transitions remain approval-gated. Rollback means stop activation/publication, restore last verified public bundle and trust policy, publish a corrected higher-number CRL when needed, and preserve audit/CRL history; it does not erase a generated private key or pretend a distributed trust-anchor change is reversible. Recovery is separately designed in ROOT-10 and isolated-restored after adapter work in ROOT-09.

## Implementation boundaries and current evidence

- **V1 — current-state census only:** the existing Fleet/Nix/broker behavior and missing PKI capability are recorded as the baseline. No implementation is proposed as V1.
- **V2 — synthetic PKI graph and adapter proofs:** root algorithm registry, opaque IDs and manifest/serial contract, 13-certificate root graph, issuer reference sets with independent Base/Internal Web A/B keys, exact 52 issuer-cert matrix, trust bundles, preconstructed chains, per-client capability matrix, exact reference validity, independent verification and negative PQ tests. Synthetic keys only; no provider or production custody writes.
- **V3 — explicitly authorized custody adapters:** three destination adapter flows, encrypted archives, approvals, receipts, partial-sync repair, restoration and recovery tests. Requires separate access/operational approval; implementation does not self-authorize writes. R2 remains excluded pending research and separate approval.
- **V4 — production ceremony and migration:** offline/hardware signer, production root generation/signing, live escrow, publication, trust installation and retirement only under explicit owner authorization and tested rollback. This is not part of design or synthetic proof.

**Observed in this task:** source package documents the intended Rust/Fleet architecture and required acceptance; the source files above were read. No source inspection or command in this task verified an implemented root generator, any supported cryptographic backend version, live BWS/op project access, laptop encryption/ACLs, an offline signer, HSM, provider write capability, or real client ML-DSA path validation. Treat all such items as **unverified/proposed**, not current capability. The handoffs explicitly prohibit production root generation/sync and require current-vs-proposed distinction (coordinator handoff §§1, 10; Claude handoff §§29, 42). Implementation must perform a repository/provider capability census before assigning “verified”.
