# Federation and infrastructure design (nonblocking)

**Status:** research-backed proposal, not a deployment authorization. **Research checked:** 2026-11-12. **Parent:** #9166. **Scope:** future service/infrastructure seams around Fleet credentials, PKI and identity. This design does not add any production dependency. Read with [`../architecture-review.md`](../architecture-review.md) and [`../source-precedence.md`](../source-precedence.md); the cross-cutting ADRs control where this document is more general.

## Decision summary

V1 means only the pinned existing system/census, including known defects and absent APIs; this document proposes no V1 implementation. Do not wait for OpenBao, Kubernetes, SPIFFE, Cloudflare, or a federation service as a V1 prerequisite. Treat each as a bounded option gated by evidence. The addendum's three-node OpenBao cluster is an isolated synthetic lab only; three processes on one laptop are one failure domain, not HA. Advance through V2 isolated synthetic lab, V3 one real failure-domain evaluation with no production secrets, and V4 federation across independently administered/failure-isolated sites only after explicit security/operations review.

## Design principles and ownership boundaries

* **Fleet owns** a stable opaque logical ID distinct from display name, path/name, provider-native ID, certificate fingerprint and key identity; typed references; classification and per-credential replication policy; source-of-truth choice; dry-run/reconciliation plans; conflict/tombstone semantics; cross-provider provenance; authorization; and integration contracts. Provider paths are locators, not identity. A successful provider write is not a global atomic transaction. `fleet secrets get` intentionally emits the requested value to stdout; diagnostics/errors remain redacted. Do not claim that the command suppresses requested output.
* **Existing password managers own** human login/autofill/passkey experience and their native identifiers. BWS is distinct from Bitwarden Password Manager (`bw`); access to one does not imply access to the other. Fleet does not rebuild password-manager UX.
* **OpenBao owns, if adopted** policy-enforced online secret serving, dynamic credential issuance/leases, Transit operations, and/or PKI/SSH issuance only where a capability test demonstrates a fit. It owns its Raft state, auth, policies, audit devices, seal/recovery, snapshots and operator lifecycle. It is not Fleet's reconciliation database or root-custody oracle. Provider-specific CAS may be used only when documented and tested; the common Fleet contract must not presume portable CAS.
* **Kubernetes operators own** in-cluster reconciliation/delivery: cert-manager for Certificate lifecycle, trust-manager for trust bundle distribution, ESO for copying provider secrets into Kubernetes Secret objects, and Secrets Store CSI for mounted external values. Select one delivery path per workload; avoid parallel controllers over the same Secret/certificate. Fleet remains authority for cross-store policy and globally scoped intent, not a replacement cluster controller.
* **SPIRE owns** node/workload attestation and SVID lifecycle when selected. Fleet may map authenticated SPIFFE IDs to narrowly scoped grants or distribute explicitly approved trust-domain relationships; Fleet must not accept self-asserted workload identity as attestation.
* **Tailscale / Teleport / Cloudflare Access own** connectivity/access or user authentication in their chosen roles, not canonical credential state. Tailnet membership or a public Worker URL is not by itself permission to read every secret. #9077 owns the separate SSO/OIDC relying-party/identity program; this work links its eventual interface and does not absorb SSO implementation, account lifecycle, passkey UX or authorization policy.
* **Cloud object storage** (e.g. R2) may be an encrypted artifact/backup sink only; client-side encryption and independent keys remain mandatory for private material. Cloudflare Secrets Store is for Worker-bound deployment secrets, not a general vault: current docs list 100 strings per account, one store, 65,536-byte max, and no readback by dashboard/API.

| V3 one site/failure domain | If V2 passes, one nonproduction physical/VM site, narrowly scoped synthetic or explicitly classified low-risk test data | Tested host loss, disk loss, restart, backup restore, network partition, audit sink failure, seal dependency failure; measured service objectives and cost; named operators and rotation/recovery runbooks | Do not call one site HA; no production secrets/roots by default; no active-active writes |

OpenBao HA with Integrated Storage/Raft is leader/quorum based; read scaling capability does not turn a same-host topology into independent availability. Three VMs/containers on one physical host share power, kernel, storage and operator failure. A 3-voter Raft cluster tolerates one unavailable voter only if two remain connected and healthy; loss of quorum blocks writes. Never use replica count as an availability claim without failure-domain mapping and tested recovery.

## OpenBao operational findings and design implications

Official OpenBao 2.7.x docs inspected 2026-11-12 (see sources). KV v2 retains configurable versions (default ten), supports CAS, soft deletion and undelete, while hard destroy is explicit. Transit performs encryption/sign/verify and does not store submitted application data; current docs enumerate ML-DSA-44 signing, but this is not evidence of ML-DSA TLS interoperability or OCSP support. Dynamic secrets and service tokens have leases; consumers must renew before TTL or obtain replacements, and revocation can invalidate them immediately. PKI offers dynamic X.509 issuance and short TTL patterns; SSH engine supports SSH certificates and OTP.

Integrated Storage/Raft replicates persisted data and elects an active node. HA is not a read/write scaling promise; docs describe horizontal read scaling for supported versions/backends. Shamir seal requires threshold unseal separately on each node after restart. Auto-unseal transfers lifecycle dependency to an external seal mechanism; losing that mechanism/key can make backups unrecoverable. Audit is fail-closed when all devices cannot record requests, and blocked audit writes can block API requests; configure two independently reachable sinks and test sink loss. Raft snapshots, restore, seal material/recovery shares and audit logs are different recovery assets. Recovery mode is an expert repair path, not a routine backup plan.

### Prototype deployment contract

* Pin exact OpenBao version, image digest, Helm chart (if used), Kubernetes version, plugin/provider versions and config schema; record SBOM and source links. Do not rely on mutable `latest` in reproducible tests.
* Start with local three-node Raft using separate data volumes and loopback/network isolation. Label this **single-host functional cluster**. Inject process/container loss, restart, full host stop, volume corruption, disk full, partitions, split-brain attempts, audit sink failures and restore from a separately stored snapshot. Measure recovery and data loss windows; do not imply measured from docs.
* Require TLS on listeners and inter-node traffic; define distinct admin/operator/client identities and policies, short token TTLs, no root token persistence, non-root process, restricted network, encrypted storage/backup, metrics without secret values, time sync and alert ownership.
* Exercise init output handling, Shamir share custody in synthetic test only, node-by-node unseal; separately test an available auto-seal provider and recovery share semantics. No unseal/recovery material in repo, command logs or test artifacts.
* Enable two audit sinks before representative requests. Test sink unavailable/hung, rotation, storage exhaustion, log HMAC/redaction, retention and export. If strict fail-closed causes unacceptable availability, document the trade; do not turn off audit silently.
* Verify KV v2 namespace and policy boundary, metadata/list leakage, CAS conflict, soft-delete/undelete/destroy; dynamic engine create/renew/revoke and orphan lease; Transit key version/rotation, sign/verify with ML-DSA in the API only; PKI certificate chain/profile/CRL/OCSP capability and SSH certificate constraints. Include wrong identity, missing auth, stale token, replay, malformed values, overlong requests and network disconnect negative cases.
* Backup test includes snapshot consistency, encrypted off-host copy, restore to clean isolated cluster, service/policy/auth/audit configuration, seal dependency restoration and point-in-time inventory. A successful snapshot command alone is not DR evidence.

## Cross-provider federation model

Use explicit per-record policy rather than “sync all”: `logical_id`, data class, permitted destinations, authoritative source(s), each native object ID, adapter capability/version, replication mode (`none`, `one-way`, `approved-bidirectional`, `encrypted-archive`), freshness/lease behavior, conflict policy, last verified revision and audit receipt. Treat dynamic values as leases, never generic copies. Inbound provider outage is `unavailable`, never deletion. Bidirectional static-value sync requires field-level three-way merge and idempotent operations; a provider write can succeed while another fails, so journal a partial saga and resume/compensate rather than promise atomicity.

Root CA key custody is a special authority plane: the dated addendum calls for an initial three-destination escrow policy (encrypted laptop, authorized BWS, authorized 1Password) and asks to investigate R2. Root material is excluded from ordinary `SecretRef` resolution, generic read paths, ordinary caches/prefetch, benchmark datasets and equality indices; only a separately authorized signer session may use it, and escrow is not signing authority. That three-destination policy is not permission to include roots in generic replication. R2 is not approved by this research. Any execution still requires the program's root-generation/escrow safety gate; no root is created or copied here. Plan future movement to offline signing/hardware with explicit active-key vs escrow semantics and restore drills.

SPIFFE federation is directional: accepting another trust domain's bundle is not reciprocal. Endpoint URL, profile and trust-domain name must be explicitly bound; keep bundles distinct, distribute rotation additions ahead of use, and revoke relationship by removing the local bundle and propagating that removal. This is a candidate identity federation protocol, not a general secret replication protocol. For human SSO/OIDC integrations, coordinate with #9077 only through agreed issuer/client/claim contracts.
