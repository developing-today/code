# Fleet credential reconciliation, history, journal, and recovery

**Status:** proposed V3 design; no live inventory or provider mutation was performed or authorized. **Owner:** domain starter #9159. **Depends on:** [secrets.md](secrets.md) / #9158 for typed credential and provider seams. **Source baseline:** `34faffbff26615e313488f6d04705a444342e41e` (2026-11-12); the intake census recorded its then-current short revision `6a7843cae598`.

## Decision and safety invariants

Implement reconciliation as a deterministic planner plus durable per-item saga, not an “upsert everything” loop. Every plan compares **two current provider observations against an encrypted, last-verified common baseline**. Provider inventory completeness is explicit and independent per account/container/scope. Plan generation is read-only; application requires a separately authorized policy and approval token tied to an exact plan hash and scope. Each side effect has a durable intent before it starts, a receipt after it returns, and readback verification before advancing the baseline. Cross-provider writes are never described as atomic.

Hard invariants:

1. **No false deletion.** Timeout, 401/403, rate limit, pagination gap, unavailable attachment, stale cursor, unknown scope, partial listing, parser failure, moved-out-of-scope item or one failed field read is `unknown/incomplete/inaccessible`, never `deleted`. Separate `ObservedAbsent` (not returned in the current read-visible set) from `ConfirmedDeleted` (authoritative deletion evidence). A complete-looking list only proves complete enumeration of what the principal can see; per-item ACL loss may be masked as 404 or omission without changing account, token, or configured scope. Two complete-looking scans plus the same token hash do not prove deletion. An absence candidate requires prior verified binding plus backend-documented deletion-authoritative visibility and evidence the item remained in scope, a provider-native deletion/trash/revision event, or explicit reviewed operator confirmation. If per-item visibility cannot be proven, classify `missing_unverifiable`/`needs-review`; no automatic tombstone, retirement, propagation, or per-item baseline advance. Scope shrink is not deletion.
2. **Separate item baselines from the scope watermark.** Every logical item/field has a last verified common baseline component, including both provider bindings/revisions and readback evidence, bound to a declared `scope_epoch_id`. A fully read, successfully reconciled item may atomically advance its own verified component even if a different item conflicts, is inaccessible, or a scope inventory is incomplete. Unresolved/unavailable items keep their prior component and per-item cursor; conflict records retain current observed revisions/cursor/run evidence for review. Never replace a base with an observation not verified on both peers. The scope-wide `since-success` watermark advances only when the entire declared scope inventory/cursor is complete and every in-scope item is terminal with no unresolved conflict or unknown outcome. A partial scope or unresolved item keeps the global watermark behind. This allows successful items to avoid repeated side effects while preserving a conservative scope-level scan boundary.
3. **Fieldwise three-way merge.** For each field, compare baseline `B` with current `L` (left) and `R` (right). Neither changed → no-op; only L changed → plan L→R if policy/field mapping permits; only R changed → plan R→L; both changed to semantically equal value → no-op/metadata confirmation; both changed differently → preserve both observations and conflict. Modification timestamps only help order/display; they do not choose truth.
4. **Per-adapter/per-operation guard level.** Declare `atomic-precondition`, `serialized-by-contract`, or `unguarded`, established by current primary documentation plus an isolated test, never inferred from a revision timestamp. `atomic-precondition` means the provider itself rejects a stale revision for every writer. `serialized-by-contract` means every writer for that scope is proven to use the same serialization mechanism; a Fleet-local lease does not qualify if humans/apps/other tools can write. `unguarded` means neither property holds. Automatic apply to conflict-sensitive fields (every secret value and any field both sides may edit) requires one of the first two levels. For `unguarded`, stop the plan step as `needs_review`, or use only a separately approved, explicitly named weaker policy with the lost-update window stated in both plan and receipt. Additive writes (new item or immutable history record) are not gated by this rule. Until primary docs plus isolated tests prove otherwise, BWS, `op`, and `bw` are all `unguarded`.
5. **Journal before side effect; verify before checkpoint.** A crash/retry cannot create duplicate history, overwrite a newer value, or claim success based on process exit code. Ambiguous provider write outcomes are reconciled by idempotency key/marker plus lookup/readback before repeating.
6. **Retain rather than destroy.** `zz.delete` is immutable recoverable history, not a physical delete/automatic purge. The required §20.5 password-rotation saga creates and reads back protected history records in each policy-approved store, then updates the existing stale native item ID in place, verifies projected fields, then checkpoints. Under default guard policy, conflict-sensitive automatic updates require adapter-operation guard `atomic-precondition` or `serialized-by-contract`; until proven, BWS/OP/BW are `unguarded` and such apply stops `needs-review`. The required saga remains deliverable through a separately approved, explicitly named weaker policy that records residual lost-update risk in plan and receipt; it must not claim an external edit remains recoverable if an unguarded update overwrites it. Any failed step stops the item and leaves a resumable partial state.
7. **Never treat equality tokens as harmless metadata.** HMAC comparison tokens avoid unsalted guessing but leak repeat equality/change/access patterns and become enumerable if key leaks. Keep the key independent, versioned and access-controlled; do not place raw values or public unsalted hashes in events/indexes.
8. **Recovery is non-authoritative.** Cached/stale data can be served only when explicit class policy allows it and max age/revocation checks pass. It never authorizes a write or overwrites a provider; root/recovery/transient default deny offline stale use.

## Inventory and baseline protocol

### Inventory completeness is a typed result

One `InventoryResult` per provider/account/container/scope should include records, opaque pagination/cursor evidence, requested and granted scope, filter semantics, expected/received page count where available, provider snapshot/revision token where available, list start/end and consistency semantics, per-item visibility/permission evidence when exposed, inaccessible field/attachment set, warnings, and a status. Capability metadata separately declares deletion visibility `read-visible-only` or `deletion-authoritative`, with versioned documentation/test evidence. `Complete` is a read-visible completeness claim, not deletion authority by itself. An unchanged token/account/config/scope digest is not evidence that per-item permissions remained unchanged.

- `Complete`: all pages and requested permitted fields enumerated; authoritative only for the exact declared scope and time interval.
- `Incomplete`: a page/filter/record/attachment/timeout/error was skipped or response was malformed. May support safe reads of observed records and per-item commits only where that item's full required observations and both peer readbacks are independently complete; cannot prove absence or advance the scope completeness watermark.
- `Inaccessible`: auth/scope denial, expired token, network/provider outage, permission loss. No absence claims.
- `ScopeChanged`: grant or configured scope differs from prior run; requires operator review and new baseline, not deletes.
- `Unsupported`: provider cannot enumerate a required record class/field. Preserve observed records; no lossless-sync claim.

Absence states are also separate: `ObservedAbsent` means a record was not in a complete read-visible listing; `MissingUnverifiable` means omission/404 cannot be distinguished from per-item ACL filtering; `ConfirmedDeleted` requires deletion-authoritative evidence or explicit reviewed operator decision. When the adapter cannot prove the needed visibility contract, it must return the unverifiable state; do not invent or assume an ACL introspection endpoint.

The provider's list may not be a transactional snapshot. If no stable snapshot revision exists, use bounded start/end inventory, change cursor and second confirmation scan for missing candidates; record that a concurrent mutation window remains. A full inventory's completeness only proves what the provider exposed to the granted identity. It never proves unseen personal vaults are empty. Attachments/OTP/passkey reads have per-field accessibility, not blanket “record complete”.

Pairing is by prior native binding, verified stable global ID/reference, or explicit reviewed strong match. Title/path alone never merges. For independent same-name additions with no strong match, preserve both and generate conflict references (spec permits `.op`/`.bws` disambiguation). Rename/move is resolved by stable native ID and scope transition, not tombstone. Preserve exact provider IDs, native title/case, field names/order/types, URLs/URI matching, visibility, tags, attachments and unknown native attributes.

### Baselines: per-item transaction boundary; scope watermark is separate

Store verified common-baseline components as encrypted, versioned snapshots referenced from durable local state, not plaintext SQL rows. A component covers one logical item (and field versions where the planner can advance independently) with exact `scope_epoch_id`, per-provider native refs/revisions, policy/mapping versions, readback proofs, verified time, item cursor and causal event IDs. Canonical secret values live only in the separately protected encrypted payload; metadata can carry eligible-field HMAC version/tokens, never root-private/recovery values or their equality tokens. Store the scope-wide scan watermark and inventory-completeness manifest separately from these item components. Do not put secret bytes in Supabase or an unencrypted local JSONL journal.

Advance algorithm:

1. Create `SyncRun` and record exact policy version, source scopes, prior checkpoint ID, time, caller/host, `full|incremental`, allowed mutation count/class and run ID. Persist `planned` state and an immutable plan digest.
2. Fetch both inventories independently. Validate pagination, field retrieval and scope. Persist encrypted observations and manifest. If either side is not `Complete` for deletion-sensitive reconciliation, set run `incomplete`; safe non-destructive work may continue only under policy. Fully observed items with verified peer readbacks can still commit per-item components; incomplete/unavailable items retain their prior base, and the scope watermark does not advance.
3. Build three-way plan against checkpoint and create conflict records for ambiguous pair/field changes. For every adapter+operation attach guard level. Under default policy, unguarded conflict-sensitive field operations become `needs-review`; they may be re-planned only under a distinct named weaker policy with explicit approval and stated lost-update window. A plan is immutable; approval is bound to plan digest, scopes, expires-at, max sensitive changes and exact operation set. Plan drift invalidates approval.
4. Execute each item saga in durable order (below). Persist step result/receipt after each external response. An operation in `unknown_outcome` is reconciled before retry.
5. Re-read changed provider objects and verify all projected typed fields, preserved native IDs, expected revisions, sidecar/attachment hashes and history references. Readback of unsupported/hidden fields remains incomplete, never inferred.
6. Append verified operation events and fsync the required local journal. Remote metadata projection has an independent outbox receipt/status. Outbox lag does not undo or block a locally durable, provider-readback-verified per-item baseline component unless an explicit deployment policy names the remote sink as a required durability dependency. Never perform an external write without the required local journal.
7. For each item whose required provider operations and readbacks are verified, write its new encrypted baseline component to a temp artifact, fsync the artifact, atomically rename, fsync its containing directory, then commit a local checkpoint/operation-state transaction referencing the content hash and durable event IDs. On restart, reconcile any local transaction boundary with the operation journal before replay. Orphan artifacts are harmless and may be garbage-collected only after reachability verification. This per-item commit is independent of other items' outcomes and the remote SQL/outbox projection.
8. Advance the separate scope watermark only after the exact scope inventory/cursor is complete and every item in scope is terminal with no unresolved conflict, inaccessible record, unknown write outcome, or pending operation. Keep the previous global watermark if any such item remains. `SyncRun` may be `partial`/`needs_review` while recording a set of independently verified per-item checkpoints; use `incomplete` when inventory completeness is missing. Under the default local-journal durability policy, remote metadata projection may remain `pending` while the locally verified sync run completes; only a separately named policy requiring the remote sink makes that projection acknowledgement a run-completion gate. Either way, outbox lag does not undo per-item baseline commits.

Do not use `since-success` as absence proof. It is an optimization hint; periodic full scans (initial full, then weekly/periodic and after cursor/scope error) close missed-change gaps. The global common watermark advances across the **entire configured policy scope**, not whichever provider happened to answer, and stays unchanged if scope is partial or any item remains unresolved. Per-item verified baselines advance independently and suppress repeated work after restart; per-provider observation cursors and global completeness watermark remain separate.

## Reconciliation state machine

Run states: `created → inventorying → planned → awaiting_approval → applying → verifying → checkpointing → completed`. Alternate terminal/hold states: `plan_only`, `incomplete`, `blocked`, `needs_review`, `partial`, `unknown_outcome`, `failed`. Terminal states are immutable; replay creates a new run linked by `replay_of` and emits compensating events rather than editing the old run.

Per-item operation states:

```text
observed
  -> matched | unpaired | inaccessible | unsupported | observed_absent
matched -> unchanged | one_sided_change | converged | conflict | moved_or_renamed
one_sided_change -> planned -> approved -> guard_checked
guard_checked -> guarded_ready | needs_review
needs_review -> separately_approved_named_weaker_policy -> weaker_mode_ready
guarded_ready | weaker_mode_ready
  -> history_intent -> history_created -> history_verified
  -> write_intent -> write_accepted -> readback_verified -> event_durable -> baseline_eligible
any external intent -> unknown_outcome (timeout/crash) -> reconcile_receipt -> resume | needs_review
any precondition mismatch -> conflict / needs_review; never overwrite blindly
observed_absent -> missing_unverifiable (default if visibility authority unknown)
missing_unverifiable -> needs_review (retain prior item baseline; no mutation)
observed_absent -> confirmed_deleted (authoritative native evidence or reviewed operator decision)
confirmed_deleted -> zz_delete_plan -> zz_delete_intent -> zz_delete_created
  -> zz_delete_verified -> retire_in_place -> retirement_verified
```

For each operation, record `operation_id`, idempotency key, logical ID, direction, action, exact source/target native refs and revisions, per-operation write-guard level, class/policy/mapping versions, before/after HMAC refs (never root-private or recovery material), planned effect, stage, provider request receipt, readback status, retries and recovery action. Retrying must preserve operation/idempotency keys. Use provider idempotency keys if available; otherwise deterministic client marker in restricted metadata plus post-write lookup. If neither idempotency nor lookup is supported, an unknown create result is not automatically retried: quarantine for manual search/review.

### Field-level semantics

- Compare values only after mapping version, type normalization and sensitivity policies match. Do not normalize away case/order/URI match semantics unless the mapping declares a reversible semantic normalization and tests prove equivalence.
- `Absent`, `Null`, empty string, inaccessible, redacted, unknown are separate states. Inaccessible is not a deletion or an instruction to erase peer data. Unknown native field values round-trip as encrypted provider envelope; if destination cannot represent/reconstruct them, block that item with `lossless_projection_unavailable`.
- A field update is not a whole-record replacement unless provider API forces it. If forced, merge freshly read target record and preserve unrelated current fields immediately before write. If provider lacks such capability, disclose and require conflict review.
- Sensitive fields (password, API token, access key, TOTP seed, private key, recovery code, passkey) default to preserve-both conflict and prohibit timestamp/LWW. Non-secret metadata may be auto-merged only when types are compatible, policy permits it, and neither side changed same field differently.
- For attachment content: identity includes protected ref, type, size and keyed or cryptographic content proof; inaccessible bytes block claiming equality. Re-read destination attachment after upload and verify hash under approved rules.
- In-place password update retains existing OP/BW login item ID, URI/autofill associations, folder/vault/container and provider-native record relationships. Native `revision` expected to change; the identity must not.

### `zz.delete`, tamper detection, and revocation semantics

Keep separate lifecycle facts: `retired_superseded`, `deleted_on_source`, `moved`, `scope_removed`, `revoked`, `compromised`, `inaccessible`, `unknown`, `duplicate_invalid`. A verified provider deletion does not mean the secret is safe to reuse; a rotation history value is sensitive and may remain usable. Fleet treats `zz.delete` as immutable: Fleet never edits or purges history. Do not claim a hosted provider's copy is WORM/immutable unless that exact version/capability is proven; the provider may allow deletion or editing. Each created history copy therefore needs a separately protected authenticated snapshot/receipt binding its history event, content proof, metadata and native reference. On readback, tamper or disappearance is an `integrity_incident`: preserve evidence, stop retirement, and restore from the authenticated snapshot only through an additive new history copy plus a linked compensating event after review; do not silently overwrite the suspect record. History records are not normal login suggestions: exclude from autofill through tested provider behavior, or explicitly report that provider cannot guarantee it. Never physically delete history automatically.

For a deletion candidate, require prior verified baseline and native binding plus deletion-authoritative evidence for this exact scope, provider version, filters and item visibility; or an explicit reviewed operator confirmation. Two full read-visible inventories with omission/404 alone are insufficient when per-item ACL filtering can hide records. Record the proof basis and approval in the plan/event. If proof cannot be obtained, use `missing_unverifiable`, retain prior item baseline/cursor and require review; other independently verified items may checkpoint, but the scope watermark remains behind. When deletion is confirmed, preserve the desired `zz.delete` saga: if the old value exists only in the peer or last verified encrypted baseline, create protected history there; if no recoverable prior value exists, record `unrecoverable` without fabrication. Create copies only in policy-approved replicas. Before retiring any active copy, ensure at least one valid recoverable history ref and verify each required store. Never auto-delete Fleet history.

## Durable ordering, crash recovery, and cross-provider semantics

External stores have no shared transaction. Use an item saga with write-ahead operation log and outbox; do not promise two-phase commit unless provider primitives actually exist. The required order for a stale password update in two approved stores is:

1. **Plan/approval:** dry-run plan includes exact source/target, old binding, expected revisions, field mapping, history destinations, max changes, rollback/recovery description; approval digest exact-match.
2. **Read/guard:** read full current objects and encrypted baseline; verify source/target observations unchanged. For conflict-sensitive changes, default apply requires `atomic-precondition` or `serialized-by-contract`; `unguarded` stops as `needs-review`. A separately approved named weaker policy may authorize §20.5 in-place update but must state the residual lost-update window in plan and receipt. A preflight read or Fleet lease is not CAS/serialization.
3. **Journal intent:** append/fsync local `history_create_intent` for each destination, reserve deterministic `zz.delete` logical/native identity and idempotency key. Required local journal must be durable before remote write.
4. **History writes:** create protected history copy in each policy-approved store; persist receipt immediately. If response lost, query exact deterministic history identity and verify content, do not blindly duplicate. Re-read each history item and verify old value under protected comparison and metadata/field completeness.
5. **Active update:** only after all mandatory history refs verified, journal `update_intent`; update stale active item **in place** using exact original native ID and provider precondition where available. Preserve unrelated fields from the freshest read. In explicitly approved weaker mode, if provider offers no guard this update has a real external-edit race; record that risk rather than promising to preserve a concurrent edit that may be overwritten. Record each provider separately.
6. **Readback:** retrieve active item by stable native ID and verify mapped fields, exact stable item ID, returned revision, URLs/autofill/custom fields and history linking. For default guarded mode a concurrent-write oracle must reject before overwrite. In weaker mode verify only the written outcome and label residual race; readback cannot recover an unseen overwritten value.
7. **Durability:** append immutable field-change/history/write/verification events to local journal. Queue metadata-only SQL/index projection in outbox; idempotent key `(event_id, sink)`. Remote index acknowledgement is stored as receipt; replay safe.
8. **Per-item checkpoint:** once this item's required peers meet policy and its reads/writes are readback-verified, commit its encrypted baseline component and local operation/checkpoint reference even if another item conflicts or is unavailable. A failed peer leaves only that item `partial`; it does not undo already verified components. **Scope watermark:** update the separate `since-success`/completeness checkpoint only after the full declared scope is completely inventoried and every item has no unresolved conflict or unknown outcome. A partial run may therefore contain committed per-item baselines while retaining the prior global watermark; do not describe the whole run as completed.

Crash table (all cases must be injected in tests):

| Crash/failure point | Recovery behavior |
|---|---|
| Before journal intent | No provider effect expected; operation can be replanned. |
| After intent, before request | Query provider by idempotency/marker; if absent, retry same key; if inconclusive, `unknown_outcome`, never create a second history item blindly. |
| Provider accepted request but response lost | Read by stable ID/marker and verify exact content/revision; append recovered receipt. Do not infer failure from timeout. |
| First `zz.delete` succeeds, second fails | Keep first verified history; no active update. Mark partial and resume second destination with original intent. Never compensate by deleting history. |
| All history succeeds, active update fails | Old active remains; history is retained (acceptable duplicate history), retry guarded update after re-read. Do not restore/delete history. |
| Active update accepted but readback fails | Mark unknown outcome; stop item; re-read later by native ID before any retry. Do not say update failed or apply stale write. |
| First provider update succeeds, second fails | Keep successful side, issue event, block baseline; retry remaining side only if current revision still matches and guard policy permits it. For unguarded sensitive fields stop for review unless separately approved weaker policy applies; weaker receipt names possible lost-update window. |
| Journal append fails before side effect | Fail closed; no external write. |
| SQL/Supabase/outbox unavailable | Keep local immutable journal and queued metadata event; according to policy either safe provider writes continue with local fsync or stop. Never report remote index committed. |
| Crash during baseline temp write | Ignore unreferenced temp/orphan artifact; prior checkpoint remains authoritative. Verify content hash then atomic rename/checkpoint. |
| Item artifact renamed, crash before its local checkpoint transaction | Treat artifact as orphan; prior item component remains authoritative. Reconcile journal, verify peers/events, then retry only that item checkpoint. |
| Per-item checkpoint committed, remote metadata outbox not delivered | Keep the item baseline committed because its local journal and peer readbacks are durable; resume only outbox projection. Never reapply provider writes because the remote index lags. The scope watermark remains governed by scope completeness and unresolved-item state. |
| Batch stops after 99 of 100 item checkpoints; item 100 conflicts | Preserve 99 committed item components and do not repeat their history/provider writes on restart. Keep item 100 on its prior base with conflict observations/receipts. Keep global scope watermark unchanged until the conflict resolves and the full-scope condition is met. |
| Scope change or partial pagination | No delete classification, no common watermark; keep observed subset as non-authoritative. |

No physical delete is used as “compensation”; compensation for a bad active write is a new forward correction with human review and new event. Event log is append-only; corrections and outbox delivery receipts are new events. Provider native version history is useful evidence but not assumed present/available.

## Outbox and data partitioning

Local journal (0600 file, 0700 parents) is the durable source-of-replay for operation intent and evidence. It may contain restricted identifiers and eligible-field HMACs, never plaintext secret values or raw credentials. Encrypted baseline/history payloads are separate encrypted artifacts keyed by a key not stored inside the same encrypted payload. Use append-only event IDs, schema version, sequence number, previous-event chain digest and integrity check. A chain alone cannot detect suffix rollback/truncation if an attacker can replace the journal and its local head with an older valid prefix. To claim tail-rollback detection, anchor monotonic sequence/head receipts in an independently protected durable domain; absent that anchor, explicitly limit the claim to detecting internal inconsistency relative to the retained head, not compromise of the host or rollback of all copies. Hash chains do not prove authorship or protect confidentiality. Signed audit records require separate signer custody/rotation, not an unreviewed “sign everything” addition.

Supabase/Postgres, if adopted, is a **metadata-only projection**. Rows include run/event/operation refs, scope digest, policy/mapping versions, redacted action/outcome, revisions where allowed, conflict IDs, status, outbox receipt, nonreversible metadata-safe snapshot reference. Do not store plaintext secrets, raw attachment bytes, unkeyed low-entropy digests, auth tokens, or overly revealing item IDs/paths in public metrics. HMAC tokens are restricted metadata with leakage described above. Restrict RLS/service role; report-only role read-only. Local event journal remains replay authority; SQL rows are deduplicated projection by event ID. Never advance provider baseline merely because SQL insert succeeded.

## Concurrency, locks, and conflict policy

The laptop executor must prevent overlapping runs and credential rotation operations over intersecting scopes. Use an OS lock for same-host mutual exclusion plus durable lease/run ownership if multiple executors are possible. Locks reduce accidental overlap; they do not replace native CAS and do not serialize external human edits. Lease expiry cannot authorize automatic takeover of an operation with unknown provider outcome. A stale lock may be reclaimed only after inspecting persisted stage and reconciling receipts.

Plan concurrency: bind approval to scope+plan digest+expiry; any changed source revision or scope invalidates only affected item approval or whole plan (default whole affected item; whole plan if scope manifest changed). Enforce per-item preconditions only where declared guard level provides them. A Fleet lease/readback does not serialize external writers. For `unguarded`, conflict-sensitive updates stop as `needs-review` unless a separately approved named weaker policy states its lost-update window in plan and receipt. Synthetic schedule preflight → external edit → apply under the default policy; oracle: external value stays recoverable and operation reports conflict/unsupported guard, not success. Under weaker policy, the oracle is that operation is explicitly risk-labeled and does not claim external value preservation; the test must not assert impossible recoverability. Multiple independent items may proceed with bounded concurrency; shared run checkpoint commits only after all required effects verified. Respect rate limits and Retry-After, bounded retries with jitter; do not retry non-idempotent writes absent outcome reconciliation.

Conflict resolution choices include `preserve_both`, `choose_left`, `choose_right`, `manual_merge`, `keep_unpaired`, `mark_scope_moved`, `confirm_deleted`, `reject_plan`. Resolution is a typed human/system decision with actor and reason; protected-field `choose_left/right` requires refreshed observations and explicit plan approval. Timestamps cannot auto-resolve protected fields. Conflicts remain durable until a resolution event and verification completes.

- **Acceptance:** stale expected revision causes `PreconditionFailed`; retry with same idempotency key returns same logical operation; ambiguous timeout enters `unknown_outcome`; receipt distinguishes accepted/pending/readback-verified; no false atomic pair status. **Negative:** never blindly retry create after lost response when lookup unsupported; revision changes between plan and apply stop item; provider success with contradictory response isn't verified.
- **Deps:** SEC-03 and REC-02. **Boundary:** no real credentials/provider APIs. **Rollback:** no default mutation entry point until receipt/recovery contract accepted. **Recovery:** replay reconciles provider by stable ID/idempotency metadata before applying. **Open:** supported providers may have different CAS semantics; descriptor reflects version-tested evidence.

### REC-05 — Implement protected `zz.delete` history lifecycle and in-place update saga

- **Kind / urgency / priority:** implementation+test+security review; High, intrinsic urgency 650. **Lifecycle:** Backlog for synthetic implementation; production rollout separately approval-blocked. **Estimate/stage:** L, V3. **Reqs:** spec §§20.4-20.6, 36.2; addendum §1 lines 7-11; V3-S04/S05/S08/S25; ADR-S02/A-1.
- **Current evidence:** no write/reconcile surface in V1; expected algorithm is specified at spec §20.5 lines 1154-1162. Intake explicitly disallows live reconciliation in this phase.
- **Deliverable:** append-only history identity generator and state-machine saga. Create encrypted dated history records in all policy-approved replicas, verify each, then update original stale active item by native ID in place, verify and link event. Fleet never edits/purges a `zz.delete`; do not claim hosted-provider WORM semantics unless versioned capability evidence proves them. Preserve an authenticated protected snapshot/receipt independent of the provider copy. Detect provider tamper/disappearance as `integrity_incident`; after review, restore only by additive history copy from that authenticated snapshot plus a linked compensating event, preserving the suspect record/evidence. Default policy refuses conflict-sensitive updates on `unguarded` operations. To fulfill §20.5 where provider guards cannot be proven, support a separate named weaker policy requiring fresh plan-specific approval and explicit lost-update risk in plan/receipt. Default-mode preflight→external-edit→apply reports conflict/needs-review without overwriting the external value. Weaker-mode fixture may apply only with named approval and risk receipt; it does **not** claim an unseen concurrent edit is recoverable. **Negative:** no title-match overwrite; no timestamp-winner; no physical delete call; history failure blocks update; missing prior value records unrecoverable tombstone without fabricated value; no unproven provider WORM claim.

Root private material is excluded; ROOT-09 owns root custody. **Rollback:** forward corrective event only; never delete history as rollback. **Recovery:** resume from per-step receipt and reread before each action; if copy integrity fails, compare against authenticated protected snapshot and require reviewed additive restoration. **Open:** provider retention/immutability and incident recovery guarantee must be version-tested; retention/access roles for obsolete credentials require operator review; no automatic purge.

## Verification strategy: PBT, MBT, and explicit oracles

Use property tests for pure invariants and model-based tests for lifecycle. Do not rely on a pile of hand-written happy paths.

- **Planner PBT:** random baseline/left/right typed fields and revisions. Oracle is independent reference merge function. Invariant: no output write when neither side changed; one-sided changes only write unchanged peer; divergent two-sided protected fields always conflict; unknown/inaccessible never become delete; apply twice after verified receipt is idempotent.
- **Inventory PBT:** generator varies page count, cursor uniqueness, malformed row, truncated response, auth/scope errors, attachment availability. Oracle is explicit completeness predicate. Invariant: `Complete` iff every required page/field is observed under same declared scope; any failure blocks absence proof.
- **Operation/scope-watermark MBT:** reference state machine drives provider fakes and durable journal through create-history/update/readback/per-item-checkpoint/global-watermark, lost response, incomplete scope, one unresolved conflict and restart. Oracle is expected per-item component plus scope-epoch/watermark state. Invariant: each item component advances only after that item's required peer readbacks and local journal are durable; 99 verified items stay committed across restart while a 100th conflict retains its old base and holds the global watermark; remote outbox lag cannot trigger provider replay; no unknown result gets blind retry; event history is append-only.
- **Identity/fidelity PBT:** generate arbitrary native unknown fields, order, Unicode, null/absent/empty, URLs, type tags, attachments and ID revisions. Oracle is exact source fixture round-trip or semantically normalized fixture where explicitly declared. Invariant: native ID stable through update; unknown fields preserved or explicit lossiness conflict.
- **Redaction oracle:** insert known synthetic secret/token/low-entropy marker strings into values/errors/provider stdout; scan journal, logs, errors, JSON summaries and SQL projection; assert absent. HMAC tests confirm no unkeyed digest emitted and key-version mismatch does not equal “changed”.
- **Crash matrix:** use deterministic fake store fault injection before/after each request and response, journaling/fsync, readback, per-item component rename/checkpoint, global watermark update and outbox delivery. Oracle is model's committed effects and durable stage; tests assert no duplicate `zz.delete`, no unsafe overwrite, no falsely advanced scope watermark and no false completed run.

Acceptance references: spec §20.5 and §§21.1-21.6 lines 1154-1244, §36.2-36.4 lines 2230-2247, §48 gates V3-S03-S10 lines 2651-2666. No test result or benchmark is claimed here.
