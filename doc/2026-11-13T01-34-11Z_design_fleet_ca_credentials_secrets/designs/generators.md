# Fleet v0.3 design: generators, key formats, SSH and iroh

**Status:** design proposal; no generator or production operation was executed here.  
**Scope:** generator/key portions of the v0.3 design; issue proposals are children of #9162.  
**Evidence inspected:** `architecture-review.md` ADR-S01/S03/S06, `source-precedence.md`, `pkgs/fleet/README.md`, Fleet registry/secrets code and manifests, `pkgs/id/README.md`, `pkgs/id/src/lib.rs`, `pkgs/id/src/local.rs`, and the checked-in Fleet multicall design. Current-state statements below describe this checkout, not deployed artifact versions.

## 1. Decision and current boundary

Fleet stays the only human- and agent-facing command surface. Add generator domains to the existing `fleet` multicall registry and reusable Rust APIs in the existing workspace; do not create a generator binary, second CLI, parallel secret resolver, or a Fleet-owned iroh identity authority. Keep the old `fleet secrets get/list` behavior and capability stubs intact.

The source spec’s `fleet generate`, `fleet ssh`, `fleet iroh`, formats, store sinks, and typed library APIs are **proposals**, not current behavior (§§22–23, 25, 43). In this checkout:

* `pkgs/fleet/README.md` lines 1–18 and 39–47 describe the existing multicall, `fleet-secrets` as secrets-by-name, broker-first then `bws` fallback, and no persistence of resolved values. `crates/fleet/src/secrets.rs` documents and implements only `get` and names-only `list` (lines 1–18, 73–92); **`get` intentionally prints the resolved secret to stdout**, while errors/logs are redacted. The #6767 cache-staleness mitigation merged as PR #8491; the issue remains open pending deploy/canary per the cross-cutting census; this design authorizes no deployment. `crates/fleet-secrets/src/lib.rs` contains the broker/BWS resolver and a redacted `SecretValue` (lines 1–28, 36–58, 139–193). These are V1 facts/compatibility floor, not a general CRUD/generation API.
* `crates/fleet-registry/src/lib.rs` is the std-only surface registry compiled into every variant (lines 1–20); the full, serve and connect capability sets are distinct (lines 115–138). `crates/fleet/Cargo.toml` excludes `fleet-secrets` and generator-related domains from connect builds (lines 40–95); `pkgs/fleet/README.md` lines 183–223 documents variant narrowing and unavailable-command semantics. New features must preserve this separation and the ≤2 MiB connect hard budget documented at README lines 318–320.
* `pkgs/id` already owns a real Iroh application identity: its README describes a P2P file-sharing CLI and `id key` export/import (lines 1–3, 105–110); `src/lib.rs` identifies a node key and public node ID (lines 17–18), and documents `.iroh-key` / `.iroh-key-client` (lines 166–170). `src/local.rs` uses `iroh_base::{EndpointId, SecretKey}` and can generate/open with a native key; `src/main.rs` implements named `--new` data directories (lines 213–244). The `key` CLI uses the app’s passphrase-wrapped identity-key envelope (`src/cli/mod.rs` lines 1412–1413, 1537–1551; `src/key_envelope.rs`). This is integration/format evidence, not an invitation to replace, migrate, or equate the running `id` identity.
* Atlas is a separate service/client contract, not a credential generator or identity authority. The Fleet README lines 66–101 says Fleet consumes the existing Atlas client/service surface. `pkgs/atlas-search/docs/memory-integration-design-8567.md` lines 62–108 keeps caller identity, sensitivity ceiling, corpus scope, and audit at the MCP boundary. Do not reuse Atlas caller credentials as generated credentials or bypass its policy boundary.

## 2. Versioned rollout

### V1 — existing census only (not a proposed implementation phase)

This label means the current pinned code and known defects only; every implementation proposal starts at V2. Keep current Fleet and `id` behavior unchanged. No issue may claim generators exist because there is a proposed command tree in the source spec. Preserve broker/BWS name resolution, intentionally revealed `get` stdout, redacted errors/logs, no persistent Fleet resolver cache, empty-value failure, capability stubs, and build/profile boundaries. Treat existing `id` node/client identities as externally owned objects whose current files and active references remain untouched unless a separately approved adoption plan explicitly names them.

### Authority and identity invariants (ADRs S01/S03/S06)

Each canonical Fleet logical object has a stable opaque ID independent of mutable display name/path and provider-native IDs. Name/path is a locator, not identity; a rename preserves identity and separate objects do not merge by matching names. Root private material is never an ordinary `SecretRef`: exclude it from normal resolver hot paths, caches, prefetch, benchmark data and equality indices. Equality tokens, including blinded/keyed tokens, leak equality and are not anonymization; do not create them for root material. Root signing is an explicit, bounded signer capability; escrow is a separate policy/authority and never ordinary replication. This permits design of the three specifically approved escrow destinations without making root keys generally resolvable, cached, benchmarked or mirrored.

### V2 — generation and format APIs

Implement common typed generation requests/results and in-memory Rust primitives first, then expose them through Fleet’s existing full/admin surface. A vetted OS CSPRNG is the sole production entropy source; RNG injection is test-only. Entropy failure is fatal. Generation APIs return typed artifacts, algorithm/format identifiers, provenance-safe metadata, and explicit secret/public classification. They do not silently write a store, display private bytes, sign with an implicitly discovered key, or create a new identity in an external application.

For passwords and random strings, candidate alphabets and required classes are separate inputs. Reject unsatisfiable policy before drawing; sample uniformly over the valid output set (rejection sampling or a proven unbiased construction), not by predictable prefix/suffix insertion. Report estimated entropy only from the actual candidate set, length/unit model, and constraints; for passphrases use independently uniform word indices from a versioned wordlist. Provide conservative `standard` default and explicit `short`, `long`, `website`, and `unrestricted` profiles. Keep emoji/CJK/other Unicode support explicit, versioned and honest about normalization, grapheme/scalar/byte semantics and target compatibility. Entropy estimates cannot imply a website accepts a value.

Distinguish raw random bytes from their encoding. Base16/32/36/58/62/64/64url/85/91/122/32768 are registry entries with explicit standard/nonstandard status and versioned alphabet; character-uniform token alphabets use unbiased sampling and are not mislabeled as byte encodings. IDs have separate algorithms and parse/validation APIs: UUIDv4 (122 random bits) is the immediate `--uuid` alias; sortable/time-bearing IDs must disclose information and are never asserted to be bearer-token-safe. Signature algorithms, public-key identities, and wire encodings are typed separately; verify each generated keypair/signature before persistence or output. Do not treat an X.509 certificate as an SSH key, SSH certificate authority, OpenPGP key, JWK, or iroh endpoint ID.

### V3 — adoption, atomic local edits and remote SSH rotation

Adoption parses and validates before it writes. Preserve original bytes/comment/ordering in protected source metadata when representation normalization would lose information; record fingerprints and typed algorithm/encoding. Unknown/malformed inputs fail closed and do not mutate. Private-key encryption status is detected and surfaced; never silently decrypt, strip a passphrase, downgrade key protection, or send a passphrase in args/env/logs. Import/export requires explicit destinations and private-export approval, with mode/owner/path validation. Keep public and private outputs separable. No private material in normal JSON receipts.

Local installation uses same-filesystem staged temp files, restrictive creation modes, flush/fsync, permission recheck, atomic rename, parent-directory fsync where supported, and a bounded recovery journal. For multi-file transactions, stage all files and a manifest, check every precondition, then commit with a recoverable per-file journal; do not promise a filesystem-wide atomic rename where the OS cannot provide one. Existing SSH `config`, `authorized_keys`, and `known_hosts` are parsed and edited surgically: preserve unrelated lines, comments, ordering and permissions; reject ambiguous blocks and symlinks/path traversal. Back up exact originals with restrictive permissions before mutation. Failure leaves either the old complete state or a machine-readable partial-state receipt with exact recovery instructions; never silently restore over subsequent human edits.

Remote rotation is an explicitly approved staged operation, not key generation plus string replacement: establish working old access; verify host identity out-of-band / against an approved known-host reference; preflight remote user, permissions and authorized-key state; stage new key as a second authorized key; verify a fresh independent login using it; only then remove the old authorization if the plan allows. Keep the old key and rollback route until new access is proven. If any verification fails, leave old access enabled, stop, record partial status and make no unsupported claim that rotation completed. Remote execution needs host/user/key references, narrow approval scope, no shell interpolation of private bytes, bounded timeout/retry, and per-host receipt. SSH CA/user/host certificates and KRLs stay distinct from X.509 PKI.

### V4 — adapters and extensibility

Expose algorithm, encoding, key-format, storage-sink and signature capabilities through versioned typed registries with explicit capability discovery. An adapter declares parse/encode/generate/sign/verify/derive-public/import/export support independently; “format supported” never implies algorithm, encryption, storage, client or signer support. Registry additions require compatibility fixtures and an independently checkable oracle before an identifier is marked supported. Keep heavy providers and optional formats out of `fleet-connect`; preserve the existing binary-size and feature matrix. `iroh` integration pins the exact crate/API version and uses its native `SecretKey`/`EndpointId` parser/derivation/signature APIs. It must be possible to adopt an iroh key as a Fleet-managed object without Fleet becoming the owner of `id`’s active identity or treating the endpoint ID as X.509 trust.

## 3. iroh adoption and identity non-conflation

The canonical object records `identity_kind = iroh-endpoint`, iroh crate/version, native serialization version, secret-key reference (never secret bytes in manifest), EndpointId, public fingerprint, source, owning application, and rotation/peer-update status. Store and display key material only through explicit secret-output policy. Import: parse using the pinned native API, derive EndpointId, compare it to any claimed ID, and reject mismatch before writes. Export: produce the exact supported native representation and verify a parse/derive round trip. Sign/verify only where the pinned native API exposes the operation and the semantics are documented; do not invent a generic signature encoding.

Adoption is read-only until the operator reviews a plan. An `id`-managed key keeps its app-specific envelope, active file path and authority. If the same key is adopted, Fleet records a reference/relationship and does not re-export or rewrite it. A request to rotate an identity used by a running `id` node is blocked until an explicit peer discovery/authorization update plan identifies all dependents and a rollback/recovery identity. `EndpointId` is not a password/token, X.509 subject, CA identity, certificate fingerprint, or proof that a remote peer is authorized. Likewise Fleet logical credential IDs, OpenSSH fingerprints, Atlas caller identities, and application-specific IDs remain distinct typed namespaces.

### GEN-01 — Typed in-memory generation contract

* **Kind / requirement:** design + implementation. GEN-001, GEN-010; spec §§22.1, 22.4, 26, 48.1 phases 5–6.
* **Outcome:** one reusable `GenerationService` contract shared by CLI, secrets, SSH, iroh and later PKI callers; typed `GenerateRequest`, generated artifact/material classification, deterministic policy validation, stable opaque logical IDs distinct from paths/names, semantic algorithm/format IDs, writer/signer/entropy seams. In-memory callers work with no filesystem/provider dependencies.
* **Current evidence / boundary:** existing `fleet-secrets` resolves named strings only (`pkgs/fleet/crates/fleet-secrets/src/lib.rs`); the workspace already separates std-only registry and optional domain crates (`pkgs/fleet/crates/fleet-registry/src/lib.rs`, `pkgs/fleet/crates/fleet/Cargo.toml`). Own the API crate/interface and contract tests only; no second CLI, provider mutations, PKI ceremony or production key generation. V1 is census only. Root signing/escrow are separate from ordinary resolver authority.
* **Acceptance:** (1) unit and API parity tests generate an explicitly synthetic fixture through in-memory API and CLI adapter with identical typed metadata; (2) path rename preserves opaque ID and separate objects at different paths do not alias; (3) errors distinguish invalid request, unsupported capability, entropy failure, signer failure and sink failure; (4) private values are redacted in `Debug`, errors, tracing and receipts; (5) API has no implicit provider/network/disk behavior; (6) root material is excluded from ordinary resolver/cache/prefetch/benchmark/equality-index paths; (7) connect build does not acquire the generation dependency graph.
* **Oracle / negative:** compile-time type/API tests plus deterministic fake entropy/signers/writers; inject entropy failure and sink failure and prove zero successful artifact receipt; try using X.509 cert as private signer or a public-only key for private signing and require typed refusal.
* **Dependencies:** none; foundational blocker for GEN-02–GEN-09. **Files:** proposed new crate/API and registry/feature wiring, only as selected by implementation design. **Safety/rollback:** synthetic test material only; remove/disable feature on regressions, preserve existing `secrets get/list` and every variant surface. **Urgency/size/stage:** High / L / V2; Ready only after the exact downstream workspace and variant constraints are verified.

### GEN-02 — CSPRNG passwords, passphrases and policy sampler

* **Kind / requirement:** implementation + security review. GEN-001–GEN-005; spec §§22.1–22.2, 28.1, 28.2; requirement register §31 `GEN-001`–`GEN-005`.
* **Outcome:** password/token-string/passphrase generator with independent alphabet and required-class policy, short/standard/long/website/unrestricted profiles, exclusions and explicit Unicode units/normalization. Strong default proposal: 32 printable random chars in the documented default candidate set; profiles never silently broaden it. Passphrases use a versioned curated wordlist and independent uniform choices.
* **Current evidence / boundary:** no Fleet generation path in the current registry or `fleet` domain code; preserve current `fleet-secrets` resolver semantics. Own sampler and policy API/CLI under GEN-01. No target-site API checks or secret-store sync.
* **Acceptance:** for a small exhaustive test alphabet, every valid output has equal probability under the sampler’s construction; property tests show all outputs satisfy required classes/exclusions/no-repeat rules; unsatisfiable policy fails before RNG call; entropy failure propagates; test Unicode NFC/none and byte/scalar/grapheme lengths; output lengths 16/32/64 and custom bounds validated; no secret text in logs/Debug.
* **Oracle / negative:** exhaustive enumeration + exact-count oracle for small policy spaces; proptest invariants for large cases; mutation tests remove rejection/unbias branch and fail. Reject constrained alphabet with insufficient entropy floor, malformed UTF-8 charset, invalid lengths, empty sets and accidental entropy downgrade. Statistical tests are smoke only, not sole proof of uniformity.
* **Dependencies:** GEN-01. **Files:** generation module/API, CLI command registration, tests. **Safety/rollback:** no live credentials; old path unaffected; opt profile behind feature on failure. **Urgency/size/stage:** High / L / V2; Backlog until GEN-01 API is accepted.

### GEN-03 — Token encodings, UUIDv4 and ID registry

* **Kind / requirement:** implementation + format review. GEN-006–GEN-008; spec §§22.2–22.3, 31 `GEN-006`–`GEN-008`, 48.1 phase 5.
* **Outcome:** separate raw-byte token generation, protocol encoding, character-uniform base-N alphabets, and ID algorithms. Ship UUIDv4 alias and parse/validate first; add only explicitly versioned alphabet/ID variants. Identify nonstandard base-N choices, normalization, collision/ordering/information leakage and entropy semantics.
* **Current evidence / boundary:** Fleet currently has no generator registry; Fleet’s name validation is a resolver-path safety contract, not an ID format (`fleet-secrets/src/lib.rs` lines 117–137). This packet owns tokens/UUID/format metadata; keypairs and signature encodings are GEN-04.
* **Acceptance:** round-trip each registered reversible encoding; UUIDv4 version/variant bits conform and 122 random bits are reported; base-N character sampler is unbiased over an uneven byte range; parser rejects malformed/case-ambiguous values per registry; time-ordered IDs are labeled non-bearer-safe; generated IDs have collision-resistant batch names.
* **Oracle / negative:** independent standard parser/reference implementation for UUID/standard encodings; exact small-alphabet enumeration for unbiased sampling. Reject unsupported aliases, false “standard” labels, malformed padding, entropy claims based on encoded character count, and time-order ID use where API declares a bearer token.
* **Dependencies:** GEN-01; share sampler with GEN-02. **Safety/rollback:** no external database migration; registry versioning allows deprecate-not-reinterpret. **Urgency/size/stage:** Standard / M / V2; Backlog.

### GEN-04 — Typed asymmetric keys, signing, verification and fingerprints

* **Kind / requirement:** implementation + security review. GEN-010; spec §§22.4, 28.1–28.2; §31 `GEN-010`; §48.2 `V3-S20`, `V3-S21` as key/format guardrails.
* **Outcome:** typed key adapters and `generate/derive-public/fingerprint/sign/verify/inspect` in-memory API for only explicitly supported combinations; protocol-specific signature encodings; capability discovery. Validate keypair consistency before any sink. No automatic PKI graph creation.
* **Current evidence / boundary:** current Fleet secret path handles string values only; existing `id` signing APIs have their own receipt contract (`pkgs/id/src/lib.rs` lines 54–103). Do not import/copy that implementation or weaken its receipt checks. Own Fleet adapter interface and synthetic tests only.
* **Acceptance:** each enabled key type signs and independently verifies a fixed fixture; wrong key, tampered message, unsupported digest/encoding and public-only signing all fail; fingerprint encoding algorithm is explicit; generated keys round-trip through the declared native format; feature builds prove unused algorithm providers are absent from connect artifact.
* **Oracle / negative:** OpenSSL 3.5+ or independently maintained verifier for supported standard algorithms, plus a separate Rust implementation where feasible; golden vectors from authoritative standard/project documentation. Reject claims that changing extension converts key semantics, and fail closed on unsupported ML-DSA or provider combinations.
* **Dependencies:** GEN-01. **Files:** crypto adapter crate, Cargo features, tests. **Safety/rollback:** test-only ephemeral keys, no roots/export/store writes. **Urgency/size/stage:** High / XL / V2 (before PKI consumes adapters); Backlog.

### GEN-05 — SSH native key format and policy

* **Kind / requirement:** implementation + interoperability test. SSH-001, SSH-004; spec §§23.1–23.2, §31 `SSH-001`, `SSH-004`, §§28.1–28.2.
* **Outcome:** default Ed25519; supported RSA-3072/4096 and P-256; hardware-backed modes only if explicitly supported. Generate/inspect/get/import/export for OpenSSH-native formats and valid conversions; policy rejects obsolete DSA/short RSA except a separately named audited legacy policy. No assertion that hybrid PQ key exchange makes Ed25519 authentication PQ-safe.
* **Current evidence / boundary:** current Fleet has no SSH identity domain; `pkgs/fleet/README.md` describes proxy SSH transport but not key lifecycle. Existing `pkgs/id` is separate. Own key format/API and CLI only; not SSH CA signing or remote edits.
* **Acceptance:** `ssh-keygen` and `ssh` accept enabled keypairs; public derivation/fingerprint matches independent OpenSSH; import/export preserves comment and parse semantics; encrypted private key import does not silently remove encryption; unsupported conversion is an explicit error; private export requires explicit approval.
* **Oracle / negative:** OpenSSH tools and known fixture keys with synthetic material; tamper, wrong passphrase, unsupported algorithm, DSA/short RSA, bad permissions, and format-substitution cases reject.
* **Dependencies:** GEN-01, GEN-04. **Files:** SSH adapter, registry and tests. **Safety/rollback:** synthetic keys; no `~/.ssh` installation in this issue. **Urgency/size/stage:** High / L / V2; Backlog.

### GEN-06 — iroh SecretKey/EndpointId adapter and versioned format

* **Kind / requirement:** implementation + compatibility design. IROH-001–002; spec §23.4, §31 `IROH-001`–`IROH-002`, §§27.4, 28.1–28.2, 43.
* **Outcome:** pin the chosen iroh crate version and support native key generation, parse/import, export, public `EndpointId` derivation, inspect, and sign/verify only when the pinned API documents it. Introduce a versioned Fleet manifest/reference without replacing the `id` application envelope or storing plaintext keys in the manifest.
* **Current evidence / boundary:** `pkgs/id/Cargo.toml` pins major `iroh = "1"`, `iroh-base = "1"`; `pkgs/id/src/local.rs` uses native `SecretKey`/`EndpointId`; `pkgs/id/src/key_envelope.rs` defines a version-1 passphrase-wrapped `id` envelope. `pkgs/id/README.md` documents `id key import/export`. The concrete lockfile versions and serialization API must be pinned at implementation time. Fleet has no iroh domain now. Do not change `pkgs/id` or its active identity as part of the Fleet adapter. Fleet opaque IDs remain distinct from path/name, EndpointId and provider-native IDs.
* **Acceptance:** generate a synthetic native key, derive matching endpoint ID, serialize/parse with pinned native library, and round-trip; reject a tampered/malformed/unsupported version, mismatched claimed ID, or certificate falsely presented as an endpoint identity; no implicit rewrite of `.iroh-key` or `.iroh-key-client`; root material is not routable through ordinary resolver/cache/prefetch/benchmark/equality-index paths.
* **Oracle / negative:** native pinned iroh parser and EndpointId derivation are primary oracle; cross-check canonical text/bytes against iroh’s official docs (`https://docs.rs/iroh/latest/iroh/` and `iroh-base` versioned API). Integration fixture proves `id` files are only read in an explicit plan and never rewritten. Version bump breaks fixture intentionally until reviewed.
* **Dependencies:** GEN-01, GEN-04. **Files:** optional iroh adapter/manifest schema and tests; separate Cargo feature. **Safety/rollback:** synthetic-only; active identity change is blocked for a separate approved lifecycle plan. **Urgency/size/stage:** Standard / L / V2; Backlog.

### GEN-07 — Safe key/credential adoption and round-trip

* **Kind / requirement:** implementation + test. SSH-004, SSH-006, IROH-002; spec §§22.4, 23.2, 23.4–23.5, 25.3, 28.1.
* **Outcome:** staged adoption parses source file/reference read-only, derives identifiers/fingerprints, records provenance and plans exactly which metadata/relationships will be added. Preserve exact source sidecars for unsupported/unknown fields; support protected original bytes where authorized; no copy to provider unless a later explicit sync operation is authorized.
* **Current evidence / boundary:** Fleet resolver only reads by name. `id key` already has its own encrypted import/export format and active identity lifecycle. Own Fleet adoption plan/apply for isolated fixtures; no global personal vault scan, SSH filesystem traversal or live provider mutation.
* **Acceptance:** malformed/ambiguous files produce no writes; an adopted SSH key matches independent fingerprint; native iroh ID matches derived key; original comments and unknown bytes survive lossless re-export when the format allows; metadata marks unknown/unrepresentable fields instead of dropping them; dry-run creates no files/store changes.
* **Oracle / negative:** independent OpenSSH/iroh parsers and byte hashes; filesystem snapshot + syscall/write audit fixture proves zero mutation on plan and parse failure. Reject private key in a public-only sink and reject `id` envelope as raw iroh serialization unless the importer explicitly handles its authenticated envelope.
* **Dependencies:** GEN-05 and GEN-06; OPS-01 schema/receipt. **Files:** adoption API and fixture tests. **Safety/rollback:** initial implementation test-only/read-only; apply only to explicit path in a later controlled test. **Urgency/size/stage:** Standard / L / V3; Backlog.

### GEN-08 — Atomic local SSH installation/config merge

* **Kind / requirement:** implementation + security review. SSH-002, SSH-003, SSH-005, SSH-006; spec §§23.2, 23.5, 25.3, 28.1–28.2.
* **Outcome:** install private/public files separately with validated owner/mode/path, and exact structured merges for `config`, `authorized_keys`, `known_hosts`. Preserve unowned entries, comments, order and existing content. Private key default 0600, `.ssh` default 0700, public/config appropriate 0644 only where policy permits. Correct target-user resolution under sudo is explicit and testable.
* **Current evidence / boundary:** no Fleet SSH mutation surface exists. Own local file mutation only; no network/remote host, trust-on-first-use or global trust installation. Implementation must not change `pkgs/id` paths.
* **Acceptance:** first plan is read-only and hashes every target; commit uses staged sibling temp, fsync, permission/owner recheck and atomic rename; injected failures before/after each step preserve old file or return exact recoverable partial receipt; parse/merge leaves unrelated lines/comments byte-identical; sudo test targets only verified user; unsafe symlink, traversal, ACL/owner/mode mismatch fails before writes.
* **Oracle / negative:** parse/render reference grammar plus golden files; file-system snapshot and crash/failure injection; test under temp dirs with test users. Reject overwrite-whole-file, unauthenticated new host key, ambiguous managed blocks, and insecure private key mode.
* **Dependencies:** GEN-05, GEN-07, OPS-01. **Files:** SSH installation API/CLI and tests. **Safety/rollback:** fixture-only until operation approval; preserve original backup and never overwrite a newer edit during rollback. **Urgency/size/stage:** High / XL / V3; Backlog.

### GEN-09 — Staged remote SSH key rotation with lockout recovery

* **Kind / requirement:** implementation + isolated security validation. SSH-007–008; spec §23.3, §31 `SSH-007`–`SSH-008`, §§25.2, 28.1–28.2.
* **Outcome:** explicit preflight, stage-new-alongside-old, fresh-login verification, authorized removal, status and guarded rollback; per-host reports. Separate OpenSSH CA/principal/KRL operations from X.509 and from local user key rotation.
* **Current evidence / boundary:** no Fleet SSH remote control exists. Own API/state machine and an isolated SSH test lab; no production host, Fleet proxy policy changes, root keys or unattended broad policy.
* **Acceptance:** MBT covers each stage and restart/retry; old authorization remains active until a fresh login with new key is proven; injected network loss, bad ownership, key rejection, timeout, and partial remote write stop before old-key removal; rollback never overwrites intervening edits; failure ends `partial/blocked`, not `rotated`; approval is bound to host/user/fingerprint/plan hash and expires per policy.
* **Oracle / negative:** two disposable SSH server/user fixtures, OpenSSH client exit/result, remote authorized-key hash/permissions, and state-machine model. A counterexample in any generated transition is a test failure. Negative: wrong host key, no old access proof, mismatched new key, revoked/expired approval, and remove-old-first path all refuse.
* **Dependencies:** GEN-08, OPS-01, OPS-02, OPS-04, OPS-10. **Files:** remote rotation state machine and lab tests. **Safety/rollback:** synthetic implementation may proceed after prerequisites; live use requires distinct explicit remote-change authorization, reviewed host recovery path and successful lab gates; no network operation in unit/integration CI. **Urgency/size/stage:** High / XL / V3; production rollout Blocked absent explicit authorization.

### GEN-10 — Extensible algorithm/format/sink capability registry

* **Kind / requirement:** design + implementation. GEN-006, GEN-010, PKI-073/074/076; spec §§22.4, 25, 26, 27, 48.2 `V3-S14`, `V3-S21`.
* **Outcome:** versioned registries declare capabilities across algorithm, key format, signature encoding, store/output sink and runtime feature. Future adapters are additive and do not change prior identifier meaning. Each adapter reports supported operations and unsupported combinations explicitly.
* **Current evidence / boundary:** `fleet-registry` already gives a std-only, complete-but-capability-gated command surface; Atlas likewise treats protocol as a versioned boundary (Fleet README lines 26–47, 66–86). Reuse these patterns, not a second binary or unbounded dependency aggregation. This packet does not implement future OpenPGP/JWK/ML-DSA/PKCS#11 adapters.
* **Acceptance:** registry schema includes stable ID/version, parse/encode/generate/sign/verify/public-derive/encrypt/decrypt/export/import flags, feature prerequisites, standards status, and test oracle; duplicate IDs/version ambiguity fail build/validation; capability report matches actual compiled feature matrix; one synthetic plugin/new-format fixture can be registered without touching core generation contracts.
* **Oracle / negative:** schema validator + Cargo feature-tree/artifact inspection; conformance test suite must be passed before capability advertises support. Negative tests prevent declared support when a function is stubbed, unsupported encoding silently substituted, or feature leaks into connect build.
* **Dependencies:** GEN-01, GEN-04. **Files:** registry/API schema, command capability output and tests. **Safety/rollback:** unknown capability fails closed; registry version supports deprecation; no new format declared production-ready without independent verifier. **Urgency/size/stage:** Standard / L / V4; Backlog.

## 5. Cross-cutting test standard and unresolved design points

* PBT must state invariant and oracle: password output is in the valid policy language; sample-space uniformity is proved/exhaustively enumerated on reduced domains; ID parser round trips; path normalization cannot escape output root; format parse/encode preserves declared semantic model; atomic write either old/new state or explicit recoverable partial; iroh key→EndpointId identity is stable under parse/serialize.
* MBT applies to multi-step key installation/remote rotation: generate legal and faulted transitions, compare implementation receipt/state with the model, and cover retry after each checkpoint. Fuzz untrusted PEM/OpenSSH/config/archive/manifest/iroh input with no writes before successful validation.
* Independent oracles: OpenSSH for SSH formats/clients; pinned native iroh parser/EndpointId derivation for iroh; OpenSSL 3.5+ plus a separate Rust verifier for algorithms it actually supports; protocol/reference implementation for standard encodings; exact reduced-domain enumeration for bias tests. Report unsupported algorithms/clients rather than substituting.
* Open decisions for implementation issue review: exact password entropy floors by profile; exact passphrase wordlist/license/version; Unicode unit policy; accepted base-85/91/122/32768 registries and interop names; exact iroh crate/serialization API version (pin from lockfile at implementation); encryption KDF/limits accepted for adopted external files; supported filesystem atomicity matrix; timeout/retry and unattended remote SSH approval schema.
* Production safety: all generator and key format tests here are synthetic. No root generation/signing, live provider writes, SSH install on user home, remote SSH rotation, identity replacement, trust-store/DNS changes, or `AGENTS.md`/skill policy edits are authorized by this design. User guidance/AGENTS/skill changes are proposals in OPS issues only, not edits made here.
