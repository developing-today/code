## Preliminary pattern read (2026-11-23 — PRELIMINARY)

Seeded with 35 observations from 2026-11-22/23: **25 flagged, 9 clean,
1 transport-failed.**

What the seeded data supports so far:

- **Route alone does not determine the outcome.** The Commander route is
  clean for light work (row 3: read-only git in a small checkout, /tmp
  scratch) and flagged for a worktree-add of code main (row 14) — while a
  fetch over the same Commander route, same lane, minutes earlier,
  completed clean (row 13). The wrapper route is flagged in most rows and
  clean in rows 2, 6, 8, and 32.
- **The same content can flag in one session and run clean in another.**
  The opencode#2648 content flagged five separate Muse lanes at
  worktree creation (rows 16–20); a different seat's session then executed
  the prepared fix on that content cleanly (row 21). The code config
  content flagged a fetch (row 1) and then ran a full edit/PR/merge cycle
  clean in the same checkout (row 2).
- **Approvals do not clear the check.** Firings 2–5 on opencode#2648,
  2–3 on opencode#2770, and 2–5 on PR #13097 all happened with
  item-specific or batch approvals already recorded. Conversely, several
  post-approval runs were clean (rows 2, 6, 8, 32) — so approval is
  neither sufficient nor clearly the deciding variable; session identity
  is confounded with approval state in every one of those comparisons.
- **Checkout-creation operations dominate the flagged rows** — 18 of the
  25 flagged rows are a clone or a worktree-add — but they are not the
  only triggers: two fetches (rows 1, 29), one pure read of local draft
  files (row 31), and one dependency install inside an already-created
  worktree (row 33) also flagged.
- **The flag rides the result, not an operational failure.** In rows 1,
  24, and 29 the operation itself completed with correct output (a fetch
  that landed, a clone that finished, a FETCH_HEAD at the right SHA) and
  the result still carried the flag.
- **Re-flagging is content-sticky across attempts.** The same items
  re-flagged across fresh clones, fresh worktrees, varied clone shapes,
  and varied routes (rows 22–24: three different clone shapes of the same
  fork content, three firings).

What the seeded data does **not** support yet:

- Any claim that a specific route is "safe." The Commander sample is
  four uses (2 clean, 1 flagged, 1 transport-failed) and its clean uses
  were light content. The laptop-local-session sample is one clean run
  (row 11) plus the routed work still in flight.
- Any claim about a specific repo, file type, or time of day as the
  trigger: code, the opencode fork, and the fleet repo all appear in
  flagged rows; the clean Commander sample is a different repo _and_
  lighter operations _and_ a different session — inseparable at this n.
- Any explanation of the row-21 difference (seat? session context?
  chance?) — it is a single observation.

**Confounders, named:** most Muse lanes share one parent session's
accumulated context, so "session" is not an independent variable across
most rows; content kind, operation kind, route, invocation form, and
approval state all vary together in the natural record; and flagged
checkouts are never re-entered, so no within-checkout replication
exists. The standing practice (alternate-mechanic attempts, occasional
bounded probes) exists to pry these apart.
