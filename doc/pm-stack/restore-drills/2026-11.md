## Fencing evidence (old writer fenced throughout)

- **Namespace:** the restored stack ran only as `drill10300-*`
  containers on the dedicated `drill10300-net` network with
  loopback-only ports and drill-only credentials (drill Postgres
  password; a dummy `AUTH_SECRET`). No production volume was mounted
  by any drill container; production's `DATABASE_URL`/`AUTH_SECRET`
  were never fetched.
- **Drill → production:** a sentinel table `drill10300_sentinel` was
  created in the restored database (1 row); production's
  `information_schema` shows **0** tables of that name. Drill Grist/Pad
  wrote only under the scratch bind mounts.
- **Production → drill:** at baseline, production held **3,008 rows
  created after the backup generation** (activity 2,073, session 20,
  task 152, label 407, external_link 356 — live writes the archive
  cannot contain); the restored database contains **0**
  post-generation rows. The drill read only the off-machine archive,
  never the live store.
- **Production undisturbed:** all four production containers
  (`pm-stack-kaneo-1`, `pm-stack-postgres-1`, `pm-grist`, `pm-pad`)
  show identical `StartedAt`/status before and after — never
  restarted; production's post-generation counters advanced during
  the drill on its own writers' activity (e.g. activity 2,073 →
  2,084); production Grist (302) and Pad (health 200) were still
  serving at the end. In a real loss the runbook's step-1 fence
  (stop the three writers; an unreachable host is fenced by
  definition) applies unchanged — here the laptop was kept live by
  design and the restored writer existed only inside its namespace
  until teardown.

## Gaps and follow-ups

1. **Kaneo RPO miss** (20 h 47 m vs 1 h): the daily #1514 dump cadence
   cannot meet the 1 h target pre-cutover — already recorded on
   #10300; the fix is #6816 criterion 1 (Supabase canonical home), not
   a drill defect.
2. **Aggregator RPO miss** (20 h 40 m vs 15 min): the daily dashboard
   archive is the only restore source for the aggregator's local JSON
   stores while they remain canonical (#6815).
3. **NEW — `globals.sql` carries the production role password.** The
   Kaneo globals dump contains exactly one password-bearing statement
   (`ALTER ROLE kaneo … PASSWORD '<production hash>'`), so after a
   globals restore the app cannot authenticate with a fresh local
   password (run 1's app boot failed 28P01 until the role password was
   reset inside the drill DB). A real restore must set the restored
   role's password from Bitwarden by name; a drill must reset it
   inside the drill database. Runbook steps 3 and 6 amended in the
   same PR as this record.
4. **NEW — Drive leg throughput:** a full byte-download of the
   archive from Drive ran at ~8 KB/s in run 1 (2 MB in ~4.5 min) and
   was abandoned; identity was proven by stored MD5 instead. Filed as
   #13024 (queued as task 21145): measure the leg properly; if R2 were
   the lost leg, a Drive-only restore of today's archive would take
   ~1 h at that rate.
5. **Thin Grist/Pad margin:** the 24 h target was met with ~3.5 h to
   spare only because the drill ran ~20 h after generation; a loss
   late in the daily cycle lands at ~24 h. The cadence question
   belongs to #1514 / #1258.
6. **Still unmeasured:** true new-host provisioning — no second Docker
   host exists on this seat (the same constraint the rehearsal
   recorded). The #1258 cadence (quarterly full-stack, annual
   laptop-off) still needs a real second host to close this fully.
