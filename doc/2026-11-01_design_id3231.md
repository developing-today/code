# Design: one receipt contract for `pkgs/id` artifacts

- Date: 2026-11-01
- Status: **design** — implementation is represented by the existing origin issues listed in §7; none is implemented by this record.
- Issue: [#3231](https://github.com/developing-today/code/issues/3231).
- Evidence: issue #3231's pass-28 design and 2026-11-01 intake review, checked against `pkgs/id` at `927f3830742078c50254b7eb23ec9eb8ce9026ba`. The relevant artifact, chain, document, tag, and directory files are unchanged from the checkout's prior pushed base.

## 1. Decision to make

What does it mean for a signed artifact to be valid when it arrives, and where is that contract enforced?

The decision must make a known-kind artifact acceptable on receipt only when it satisfies the structural rules that the crate's supported producers are meant to create. It must also keep signature authenticity, chain position, and unknown-kind forward compatibility distinct from known-kind body validation. Receipt must not rewrite signed bytes to make them pass.

## 2. Context and constraints

`pkgs/id` already states the desired builder/decoder symmetry for signed documents and chain events: `documents.rs` says the builder and decoder apply the same rules (`pkgs/id/src/documents.rs:83–119`), and `ChainExt::validate` documents the same property for events (`pkgs/id/src/chain.rs:186–200`). The artifact module instead has separate envelope and known-body checks. `SignedArtifact::verify` checks the envelope and signature, while `parsed()` dispatches known kinds and returns `None` for an unknown kind (`pkgs/id/src/artifact.rs:270–309, 318–391`). `ArtifactLog::store` composes verification, parsing, frame-size and chain-position checks (`pkgs/id/src/artifact.rs:425–478`).

That distinction is intentional for unknown kinds: the module documents that they may be stored but are never applied (`pkgs/id/src/artifact.rs:1–9`); `parsed()` returns `Ok(None)` for them, and tests cover storage without directory effects (`pkgs/id/src/artifact.rs:1152–1161`; `pkgs/id/src/directory.rs:2003–2020`). The receipt contract should therefore be strict for the envelope and known kinds, not a rule that makes old or future unknown kinds unparseable.

The four omissions in #3231 are confirmed in this checkout:

| Area | Current evidence and consequence |
| --- | --- |
| `after` frontier | Artifact envelope validation checks its length and hash shape, but not duplicate hashes (`pkgs/id/src/artifact.rs:275–295`). Both artifact signing paths currently pass the list through (`pkgs/id/src/artifact.rs:242–262, 545–564`), while `ChainExt::validate` refuses duplicate hashes (`pkgs/id/src/chain.rs:186–193`). |
| `friend_remove.requests` | Known-kind parsing checks the account keys, distinct accounts and signer, but does not inspect `requests` (`pkgs/id/src/artifact.rs:319–333`). The directory producer constructs at most three requests and sorts/deduplicates them (`pkgs/id/src/directory.rs:1710–1722`); envelope IDs are 16 random bytes rendered as 32 lowercase hexadecimal characters (`pkgs/id/src/directory.rs:355–378`). Every supplied string is added to the permanent removed-request set (`pkgs/id/src/directory.rs:1698–1705`), so junk values are not inert. Existing low-level tests use placeholder IDs such as `"r1"` and will need valid fixtures (`pkgs/id/src/artifact.rs:1043–1050, 1070–1080`). |
| `home_declared` | Parsing caps the server list and validates each endpoint, but does not reject repeated endpoints; `world_id` is only checked for emptiness (`pkgs/id/src/artifact.rs:334–355`). `Directory::declare_home` currently passes its caller's list through to publish (`pkgs/id/src/directory.rs:1312–1329`), so builder-side symmetry must be part of this change. `WorldCore::new` accepts any non-whitespace ID (`pkgs/id/src/world/core.rs:44–58`); the separate hub-name validator has a 64-byte lowercase-ASCII grammar (`pkgs/id/src/world_hub.rs:36–59`), but the current outbound directory view uses the endpoint and not `world_id` (`pkgs/id/src/directory_view.rs:1441–1459`). |
| Text | Artifact `document.media_type`, `tag.name`, and `tag.value` currently have emptiness/size checks but no NFC check; document content is only constrained by serialized JSON size (`pkgs/id/src/artifact.rs:356–382`). Sibling document and tag validators do require NFC for their corresponding media-type/name/value fields (`pkgs/id/src/documents.rs:83–119`; `pkgs/id/src/tag_claims.rs:113–155`). Chain validation goes further for event text, recursively checking CBOR text including map keys (`pkgs/id/src/chain.rs:194–200, 361–380`). |

Receipt validation is also replay validation. `ArtifactLog::open` reads complete stored lines and calls `store(..., false)`, re-running signature, known-kind and chain checks while skipping only the frame-size check (`pkgs/id/src/artifact.rs:418–429, 574–607`). `Directory::open` then loads that log and reapplies eligible friend removals (`pkgs/id/src/directory.rs:463–491`). Therefore no new rule may refuse legitimate producer output or existing valid history without an explicit compatibility decision and evidence.

One error-classification mismatch must be resolved with the implementation: `verify()` currently maps every `check()` failure to `Refusal::Unauthenticated`, while known-kind validation uses `Refusal::Forbidden` (`pkgs/id/src/artifact.rs:210–218, 270–272, 318–391`). The issue's recorded rule asks for `Forbidden` naming the violated rule. Structural policy refusal must not be confused with a bad signature.

## 3. Viable options

### A. Keep filing each omission as a local fix

- **Benefit:** smallest immediate changes and each fix can be reviewed narrowly.
- **Cost:** it preserves separate, easy-to-drift rules across envelope checks, known-kind parsing and builders. The current artifact arms already mirror some sibling caps but omit their NFC checks; the four filings in #3231 are evidence of that drift.
- **Disposition:** reject as the overall design. Keep the existing issues as independently mergeable implementation packets, but have them implement one contract.

### B. Enforce the contract at receipt, not when an artifact is later applied

- **Receipt path:** validate the envelope in `check()` / verification and known bodies in `parsed()` before `ArtifactLog::store` persists or replays them.
- **Application-time path:** defer checks until `Directory` applies an artifact.
- **Trade-off:** application-time checks might protect one effect, but the log would already store and serve the invalid artifact; `ArtifactLog::open` would replay it through the same admission path later. `store()` is the shared gate for insert/open/pull (`pkgs/id/src/artifact.rs:425–478, 574–607`).
- **Disposition:** choose receipt-time validation.

### C. Refuse ambiguous signed values, or normalize/deduplicate them on receipt

- **Normalize/deduplicate benefit:** callers could continue despite redundant or noncanonical input.
- **Cost:** changing signed lists or text on receipt changes the signed evidence and can change its hash. Deduplication also hides what the signer actually supplied.
- **Disposition:** refuse invalid values; never silently normalize or deduplicate receipt bytes. Builders should reject the same invalid input before signing/publishing.

### D. Put this under the JS/TS parsed-JSON contract in #3068

- **Benefit:** one broader shape-validation effort might appear to reduce duplicate policy.
- **Cost:** this gate is Rust signed-statement verification and artifact replay; #3068 is the distinct JS/TS parsed-JSON contract. They have different inputs and failure modes and neither gates the other, as #3231 records.
- **Disposition:** keep this design and implementation separate; cross-reference #3068 only.

### E. Apply every sibling rule to every string, including unknown kinds and document content

- **Benefit:** maximal uniformity.
- **Cost:** the module intentionally stores unknown kinds without applying them, and current sibling contracts do not establish that every string in artifact document content is NFC. Broadening the rule risks rejecting historical content without producer evidence.
- **Disposition:** start with the explicitly identified fields and preserve unknown-kind behavior. Phase 3 must record a field-by-field disposition for the remaining cases rather than silently extending the rule.

## 4. Recommendation

Adopt one **build-and-receipt contract**:

1. For every known kind, a value rejected by the supported in-tree builder must also be rejected before receipt. Apply each field rule both at its production seam and at `parsed()`; apply envelope rules both where the envelope is built and at `check()`.
2. For unknown kinds, keep the existing forward-compatible rule: validate the common envelope, store the signed bytes, and do not parse or apply the body. Do not add kind-specific body or text rules to unknown kinds.
3. Refuse duplicate signed list entries; do not rewrite them. For endpoint uniqueness, compare the validated endpoint identity produced by `check_target`, not merely the raw string, so equivalent accepted spellings cannot evade the uniqueness rule (`pkgs/id/src/envelope_outbox.rs:403–417`). Add tests for equivalent spellings if the parser accepts them.
4. Enforce the recorded pins: `friend_remove.requests` has at most three entries; each is exactly 32 lowercase hexadecimal characters; entries are unique. NFC-check `document.media_type`, `tag.name`, and `tag.value`. Constrain `world_id` to 1–64 bytes, not whitespace-only, and no `Cc` or `Cf` characters, but do not impose the full hub-name character grammar in this change. These are the recorded #3231 decisions; the current source evidence does not show a `world_id` consumer that requires that fuller grammar.
5. Make a policy-rule refusal `Refusal::Forbidden` and name the rule, including envelope policy failures such as duplicate `after`. Keep invalid signatures/authenticity failures `Refusal::Unauthenticated`. The current `verify()` mapping makes this an explicit implementation requirement, not an automatic consequence of adding a check.
6. Use `ArtifactLog::store` as the receipt seam and keep its chain-position checks for `prev`/sequence. Do not create a second application-only validator. `store()` already checks sequence zero, gaps, forks and the expected chain head (`pkgs/id/src/artifact.rs:434–478`).

This is the smallest contract that closes the four observed gaps without changing the intentional unknown-kind behavior or treating display sanitization as storage validation. The nearby plain-output rendering family (#2839, #3111, #3089) governs presentation, not signed artifact storage, and is not adopted by #3231.

## 5. Invariants and implementation acceptance criteria

- A valid signature does not by itself make a structurally forbidden envelope or known-kind body acceptable. A rule failure returns `Refusal::Forbidden` with the rule named; a signature failure remains unauthenticated.
- Every known-kind receipt passes the same applicable rule set as the supported builder. Each newly added restriction has a builder-side check and a receipt-side check (or a documented reason why the builder seam is shared).
- Duplicate `after` hashes, friend-remove request IDs, and home-server endpoints are refused. Receipt never deduplicates or normalizes the signed input.
- Friend-remove requests are limited to three valid, unique 32-character lowercase-hex IDs. Tests use real-shape IDs, and tests demonstrate that values which would poison `removed_requests` are refused before persistence/application.
- Artifact media type and tag name/value use NFC. `world_id` has the recorded byte, blankness and Unicode-category constraints; no full `a-z0-9-_` grammar is added without evidence from a consumer.
- Unknown kinds retain envelope-only validation and remain storable/unapplied. Existing tests for unknown-kind storage and no directory effect continue to pass.
- `ArtifactLog::open()` replays valid existing chains unchanged. Tests exercise rejection at insert and reopen for each new rule, and demonstrate that legitimate producer output still replays. Existing replay, torn-tail, blank-line and corruption-location behavior remains intact (`pkgs/id/src/artifact.rs:1207–1278`).
- The field-by-field closing audit records every envelope and known-kind field, including unknown `kind` values, strings inside `document.content`, `prev` beyond the existing position check, serde-ignored extra object fields, and builder symmetry for generic `sign` paths.
- `artifact.rs` module docs state the receipt contract alongside the documents and chain contracts.

## 6. Non-goals

- Changing the JS/TS shape contract in #3068.
- Sanitizing signed values for display or changing the plain-output rendering family.
- Silently deduplicating lists, normalizing text, or rewriting stored artifacts.
- Rejecting unknown kinds or requiring their body to conform to a known schema.
- Pinning `world_id` to the world hub's entire name grammar without a demonstrated consumer requirement.
- Changing sequence/`prev` chain-position semantics already enforced by `store()`.

## 7. Independently mergeable implementation plan

Adopt the four existing origin issues named by #3231; do not create parallel issues. Steps 1 and 2 are independent and may land in either order. Step 3 is gated on both.

### Step 1 — List integrity (Phase 1)

**Existing packets:** #3196 and #3146. Each packet is independently mergeable.

- **#3196 — `after` frontier:** reject duplicates in envelope receipt and in `sign_after`; preserve existing length/hash checks. Ensure a validly signed but duplicate frontier is a named `Forbidden` policy refusal, not an `Unauthenticated` signature failure. Add builder and receipt regression tests. Primary source: `pkgs/id/src/artifact.rs:242–262, 270–309, 545–564`; sibling behavior: `pkgs/id/src/chain.rs:186–193`.
- **#3146 — `friend_remove.requests`:** enforce the count, 32-lowercase-hex shape and uniqueness at receipt and every in-tree production path. Update placeholder test IDs. Add a test proving invalid entries cannot enter the permanent removal set. Primary source: `pkgs/id/src/artifact.rs:319–333`; producer and effect: `pkgs/id/src/directory.rs:1698–1705, 1710–1722`.

**Done when:** focused tests cover duplicate frontier refusal at build and receipt, valid/invalid request list shape and count, and the error classification; targeted `pkgs/id` tests pass.

### Step 2 — Text and home-declaration integrity (Phase 2)

**Existing packets:** #3192 and #3187. This step is independent of Step 1; each packet is independently mergeable.

- **#3192 — NFC fields:** require NFC for `document.media_type`, `tag.name` and `tag.value` on both builder and receipt paths, using the same `unicode_normalization::is_nfc` rule as the sibling validators. Do not extend this step to internal strings in `document.content`. Primary source: `pkgs/id/src/artifact.rs:356–382`; comparison: `pkgs/id/src/documents.rs:83–119`, `pkgs/id/src/tag_claims.rs:113–155`.
- **#3187 — `home_declared`:** refuse repeated validated endpoint identities; add the recorded `world_id` size/blankness/Cc/Cf checks; and close the producer-side gap in `Directory::declare_home` so it cannot publish a value receipt would refuse. Keep the full hub-name charset open as recorded. Primary source: `pkgs/id/src/artifact.rs:334–355`, `pkgs/id/src/directory.rs:1312–1329`, `pkgs/id/src/world/core.rs:44–58`.

**Done when:** focused tests cover builder and receipt symmetry, endpoint identity (including equivalent accepted spellings), `world_id` boundaries/categories, and accepted existing producer outputs; targeted `pkgs/id` tests pass.

### Step 3 — Closing audit and contract statement (Phase 3)

**Existing packet:** #3232, gated on Steps 1 and 2.

- Complete the field-by-field disposition table required by #3231. Specifically answer whether document content strings need NFC, what limits (if any) apply to unknown `kind` strings, whether `prev` needs anything beyond `store()`'s position check, how generic `sign` is constrained for known kinds, and how serde-ignored extra object fields are treated.
- Verify legitimate producer outputs and stored-chain replay against the final rules; if a stricter rule could reject historical data, retain compatibility or document the evidence and explicit disposition before changing it.
- Add the concise receipt-contract statement to the `artifact.rs` module docs.

**Done when:** the audit table has no undispositioned fields, tests demonstrate insert/open symmetry and preserved unknown-kind behavior, module docs state the contract, and `ArtifactLog::open()` passes the replay compatibility checks.

## 8. Open implementation questions and defaults

These are code-audit questions for Step 3, not owner-policy questions. The implementation should proceed using the defaults below and record any evidence that changes one.

| Question | Options | Default recommendation |
| --- | --- | --- |
| Does `world_id` need the world hub's full lowercase ASCII grammar? | Keep the #3231 1–64-byte/nonblank/no-Cc-or-Cf rule; or require `WorldHub::validate_world_name`'s grammar. | Keep the recorded narrower rule. `WorldCore::new` accepts any non-whitespace ID, and the current outbound directory view uses the endpoint rather than `world_id` (`pkgs/id/src/world/core.rs:44–58`; `pkgs/id/src/directory_view.rs:1441–1459`). Revisit only if a consumer demonstrates the stricter requirement. |

Audit the document producers and consumers in Step 3, then explicitly record a change if they establish a construction invariant. |
| How are unknown `kind` strings constrained? | Add kind-string bounds/NFC; or keep the unknown body opaque and envelope-only. | Preserve the module's deliberate forward-compatibility rule; add no new kind-specific constraint. |
