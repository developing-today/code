# Design: multiplayer edit sessions — UX, lifecycle, and participation (issue #5832)

Status: decision record for issue #5832, a design child of #5677 (note↔board
reference model). It settles the five questions the issue names — merge model,
presence, terminal form, join/view permissions, session lifecycle — for live
multiplayer editing in `pkgs/id`, reconciled with the merged #2048 design
(doc/2026-11-01_design_id2048.md) and the durable checkpoint/merge boundary
owned by #3819. Parent decisions (#5677: reference model, sovereignty rule,
approval flow; #2048: stable identity, immutable revisions, explicit merge)
are consumed, not re-decided; §7 lists what this record does NOT reopen.

## 1. Current state (grounding)

- Live collaboration today is `CollabState` in `pkgs/id/src/web/collab.rs`:
  documents held in process memory in a `HashMap` keyed by **filename**,
  created lazily by `get_or_create(filename, hash, initial_content)`, dropped
  by `remove_document`. There is no participation model, no presence record,
  and no defined terminal artifact: when the map entry goes away, whatever
  was not separately saved is gone.
- The #2048 design already rules the storage side: a note's collaboration
  room is keyed by **stable note ID**, live steps stay ephemeral, a
  successful checkpoint emits a **durable signed revision**, concurrent or
  offline work that produces distinct parents is retained as **separate
  heads requiring an explicit merge**, and the system is explicitly **not a
  CRDT** with no promise of conflict-free offline editing.
- #3819 owns the durable side of the boundary (checkpoints and merges as
  journal artifacts). This record owns everything on the live side of that
  boundary: who is in the room, what the room shows, and how it ends.

## 2. Decision summary

| Question (#5832) | Decision                                                                                                                                             |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Session identity | Room keyed by `(note_id, base_revision_id)` — never filename                                                                                         |
| Lifecycle        | forming → live → draining → closed, with four terminal forms (§4)                                                                                    |
| Merge model      | In-session: server-ordered ProseMirror steps. Across sessions: multi-head + explicit merge per #2048/#3819; sessions never auto-merge                |
| Presence         | Ephemeral, server-relayed awareness (identity, cursor, selection); never journaled; TTL expiry                                                       |
| Participation    | Roles owner / editor / commenter / viewer derived from the note's read/write policy (#2048); capability checked at join and re-checked at checkpoint |
| Terminal form    | Exactly one of: checkpointed, superseded, expired, crashed (§4.2) — each leaves a defined artifact, none is silent                                   |

## 3. Session identity and participation

### 3.1 Room key

A session is identified by the pair `(note_id, base_revision_id)`: the note
being edited and the durable revision the session forked from. Filename is
never a key — a rename mid-session must not split the room (the current
filename keying does split it, which is a defect this design retires).
Two sessions on the same note with different base revisions are different
rooms; §5 covers how a joiner is routed when several exist.

### 3.2 Roles

Participation roles derive from the note's existing policy (the #2048 design
keeps read and write policy separate; this record maps them, it does not
invent a second policy store):

| Role      | Source policy             | May submit steps | May comment (anchored remarks) | Sees presence                                 |
| --------- | ------------------------- | ---------------- | ------------------------------ | --------------------------------------------- |
| owner     | note owner                | yes              | yes                            | yes, plus full roster history for the session |
| editor    | write grant               | yes              | yes                            | yes                                           |
| commenter | read grant + comment flag | no               | yes                            | yes                                           |
| viewer    | read grant                | no               | no                             | yes                                           |

Rules:

- **Join is a capability check, not a link.** Possession of a session URL
  grants nothing; the server checks the joiner's identity against the note
  policy at join time. There is no anonymous join and no anonymous presence:
  every participant is an ID identity (sovereignty rule from #5677 — the
  owner can always answer "who was in my note").
- **Mid-session revocation demotes live.** Policy is re-checked at every
  checkpoint and on a policy-change event: a revoked editor is demoted to
  viewer in place (their client switches to read-only with a visible notice),
  not silently disconnected — their already-accepted steps stay, because
  acceptance was valid when it happened; their un-accepted local steps are
  discarded and the client says so.
- **Board-linked notes take the stricter policy.** Where a note is referenced
  from a board (#5677 reference model), effective participation is the
  intersection of note policy and board visibility: a board viewer who lacks
  note read access sees the reference, not the session.
- **Commenter is a v1 role, not a phase-2 nicety**: anchored remarks are how
  a reviewer participates without step rights, and the approval flow in #5677
  assumes reviewers can be in the room.

## 4. Lifecycle

### 4.1 States

1. **forming** — first join creates the room: the server loads the base
   revision's content as the session document and records the session's
   opening (note, base revision, opener) — the opening record is the one
   session fact that IS durable from the start, written through the #3819
   boundary, so a crashed-forming session is distinguishable from one that
   never existed.
2. **live** — steps flow (§5), presence relays (§6), periodic checkpoints
   per #3819's cadence each emit a durable revision and advance the
   session's `checkpointed_revision`.
3. **draining** — entered when the last step-capable participant (owner or
   editor) leaves, or when the owner closes the session explicitly. A grace
   window (default 120 s) lets a dropped connection rejoin without churn;
   viewers/commenters remaining do not hold the room open for editing but may
   keep reading the final state.
4. **closed** — terminal; the room is removed from memory (today's
   `remove_document`) only after the terminal artifact (§4.2) is durable.

Server restart kills every room: in-memory state is not recovered, and the
design does not pretend otherwise. Recovery is at the note level — the next
join forms a new session from the last checkpointed revision — and §4.2's
"crashed" form makes the loss explicit rather than silent.

### 4.2 Terminal forms

Every session ends in exactly one terminal form, recorded in the session
record (participants, base revision, checkpointed revision, form, timestamps)
written through the #3819 boundary:

- **checkpointed** — normal end: a final checkpoint emitted a durable
  revision; the session's work is fully durable. This is the only form that
  advances the note's head by itself.
- **superseded** — at final-checkpoint time, another session's checkpoint
  landed first on the same base, producing a sibling head. This session's
  final state is checkpointed as that sibling head (not discarded, not
  merged) and the note is multi-head until an explicit merge (§5). The
  participants are told their session ended as a separate head.
- **expired** — draining grace elapsed with no steps since the last
  checkpoint: no new revision is emitted; the session record alone is the
  artifact. Read-only sessions (no editor ever joined) always end expired.
- **crashed** — the server lost the room (restart or failure). Detected by
  the absence of a closing record for an opened session; the next session
  forming on that note surfaces "previous session ended without a final
  checkpoint; work after <checkpointed_revision time> was not saved" to its
  first joiner. Un-checkpointed steps are lost — bounded by the checkpoint
  cadence, disclosed, never silently presented as saved.

## 5. Merge model (applied, not re-decided)

- **Inside a session**, convergence is the ProseMirror step protocol:
  clients submit steps against a session version, the server orders and
  broadcasts them, clients rebase local steps on rejection. The server is
  the single ordering point; there is no peer-to-peer step path.
- **Across sessions**, the #2048 rule applies unchanged: divergent
  checkpoints are separate durable heads and merging them is an explicit,
  human-initiated operation owned by #3819. A session never auto-merges, and
  a checkpoint never overwrites a sibling head.
- **Joining a multi-head note** forces a choice before editing: the joiner
  picks which head the new session forks from (the UI defaults to the most
  recently checkpointed head and labels the others). Two live sessions on
  different heads of one note are legal and are how a merge's inputs get
  edited before the merge.
- Offline editing is out of scope for convergence promises (per #2048): a
  client that disconnects keeps its local state, and on rejoin its steps are
  admitted only if they still apply to the current session version;
  otherwise the client is offered its divergent state as the seed of a new
  session on the same base — which will terminate as its own head, per the
  superseded rule, rather than being force-fit.

## 6. Presence

- Presence is an **ephemeral awareness channel** relayed by the server:
  participant identity (display name + identity key fingerprint), role,
  cursor/selection anchor, and a last-seen timestamp. It is never written
  to the journal and never part of a revision — presence is about _now_.
- Entries expire on a short TTL (default 15 s without heartbeat) so a crashed
  client leaves the roster by itself; explicit leave removes immediately.
- Presence follows participation: only joined participants see presence, and
  what a participant sees is the whole roster (there are no invisible
  observers — a viewer is visible as a viewer).
- The durable trace of "who was there" is the session record (§4.2), not
  presence data: it lists participants and their roles, not cursors.

## 7. What this record does NOT reopen

- Note↔board references, the sovereignty rule, and the approval flow (#5677).
- Stable note identity, immutable revisions, signed checkpoints, explicit
  multi-head merge (#2048), and the checkpoint/merge journal mechanics
  (#3819). If implementation finds a conflict with any of these, the
  conflict is escalated on #5677 — not resolved by forking here (per
  #5832's own instruction).

## 8. Rejected alternatives

- **CRDT rewrite (Yjs/Automerge-style convergence)** — rejected by #2048 and
  reaffirmed: it replaces the step protocol and the explicit-merge model to
  buy offline convergence the programme explicitly does not promise.
- **Filename-keyed rooms (status quo)** — a rename splits the room and two
  notes sharing a filename collide; stable-ID keying is already the #2048
  ruling.
- **Journaling every step** — makes live transport durable at journal cost
  per keystroke and contradicts the ephemeral-steps ruling; checkpoints are
  the durability unit.
- **Auto-merge on supersede** — violates the explicit-merge invariant and
  would hide exactly the divergence a human must see.
- **Link-based (capability-URL) joining** — conflicts with the sovereignty
  rule; the owner must be able to enumerate and revoke participants, which
  bearer links defeat.

## 9. Invariants implementation must hold

1. A room's key is `(note_id, base_revision_id)`; no filename participates
   in session identity anywhere.
2. No step is accepted from a participant whose current role lacks step
   rights, re-evaluated at acceptance time, not only at join.
3. Presence data never reaches durable storage; the session record is the
   only durable participation artifact.
4. Every opened session reaches exactly one terminal form, and the form is
   recorded durably; a missing closing record is itself the crash signal.
5. A session's checkpoint only ever appends a head; it never overwrites or
   merges a sibling head.
6. Un-checkpointed work is always represented to users as unsaved; no UI
   state claims durability the checkpoint boundary has not granted.
