# Design: importer design — Joplin into the #2048 object model

- Date: 2026-11-08
- Status: **decision-ready proposal** — design only; no importer code is implemented here.
- Issue: [#5848](https://github.com/developing-today/code/issues/5848), parent programme [#5678](https://github.com/developing-today/code/issues/5678), programme epic [#2056](https://github.com/developing-today/code/issues/2056).
- Object model: [#2048](https://github.com/developing-today/code/issues/2048) as landed in `doc/2026-11-01_design_id2048.md` (PR #3885, closed 2026-11-07): stable logical notes (`note.create` = stable note ID), signed immutable revisions (`note.revise` naming parents and a content blob), structured typed references (target note ID, sigil/type, authored surface, optional pinned revision), tags as signed observed-remove claims, names/aliases as claims, tombstone removal, group `Read`/`Write` as the authority model. This design **consumes** those decisions; it does not re-decide them. The one place it touches a parent decision is flagged explicitly in §7.
- Splits filed from this design: [#7675](https://github.com/developing-today/code/issues/7675) (Joplin revision-history import), [#7676](https://github.com/developing-today/code/issues/7676) (continuous sync target vs one-shot import).

## Decision to make

How does a Joplin vault — Markdown notes with Joplin IDs, hierarchical notebooks, global tags, separately-stored attachment resources, and `:/<id>` internal references — enter the #2048 object model such that (a) the imported graph uses the model's stable identity, typed references and claims rather than a file dump beside it, and (b) a later export back to Joplin keeps links, tags and attachments intact?

## Recommendation

**Import is a mapping into the object model, recorded in a persisted import manifest, and it is one-shot plus idempotent re-import — never a sync emulation.** Concretely:

1. **Notes → logical notes.** Each Joplin note becomes one logical note: a signed `note.create` whose initial revision's blob is the note's Markdown body after reference rewriting (§3), signed by the importing identity. The note ID is newly minted by ID; the Joplin ID is *not* reused as the note ID (§6, alternative 2).
2. **The manifest is a first-class artifact.** The import writes a manifest into the world: Joplin ID ↔ note ID for every note and resource, plus source-vault identity and import time. The manifest is what makes re-import idempotent, link rewriting auditable, and round-trip export (§5) possible at all. An import without a manifest is a failed import.
3. **Notebooks → collection notes.** Each notebook becomes a logical note acting as a collection, with typed membership references to its member notes and to its child collections; a note's Joplin notebook placement is exactly its membership in one collection chain. Notebook nesting is collection nesting (§2).
4. **Tags → tag claims, verbatim.** Joplin's global tags map 1:1 to the model's observed-remove tag claims, names unchanged (§2).
5. **Resources → blobs.** Each Joplin resource's bytes become a content blob; in-body resource references are rewritten to blob references; resource metadata (title, MIME type, original filename) is recorded as claims on a per-resource record tied to the manifest (§4).
6. **Internal links → typed references.** `:/<note-id>` references in Markdown are rewritten during import to the model's structured typed references (target note ID via the manifest, authored surface = the original link text). Dangling targets degrade exactly as #2048 prescribes: stored surface + unresolved state (§3).

## §1 Source shape (what Joplin actually gives an importer)

The design is stated against Joplin's export shapes, in preference order:

- **JEX** (a tar of Markdown files with Joplin metadata headers, plus resource files) is the canonical import source: it is the only common export that carries notes, notebooks, tags, resources and their IDs together.
- **Markdown directory export** is accepted as a degraded source: IDs and some metadata are absent, so the manifest is built from paths and content hashes, link rewriting covers only resolvable filename references, and the import report must name the degradation. Designing for JEX and tolerating Markdown is deliberate; designing for Markdown first would discard the IDs the round-trip depends on.
- **ENEX** is Evernote's format that Joplin can itself import; it is out of scope here (an Evernote importer is a sibling design under #5678, not a Joplin concern).

Relevant Joplin facts the mapping relies on: notes and resources have stable per-item IDs within a vault; a note belongs to exactly one notebook; notebooks nest; tags are global and many-to-many; note bodies reference resources and other notes by `:/<id>`; notes may be to-dos (flag, due, completion) and may carry source timestamps (created/updated) distinct from import time.

## §2 Entity mapping

| Joplin item | #2048 mapping | Notes |
| --- | --- | --- |
| Note | Logical note (`note.create` + initial revision) | Body blob after §3/§4 rewriting. Joplin title → alias/filename claim (names are claims, never identity, per #2048). Created/updated timestamps recorded as provenance claims, not as event times. |
| To-do note | Logical note + to-do claims | `is_todo`, due, completed recorded as claims on the note; a to-do is a note with claims, not a second note type (the model has no second note type to map to). |
| Notebook | Collection note (a logical note whose content is its membership) | Typed membership references to member notes and child collections. The root of the vault is a collection with no parent. Renaming a notebook is an alias-claim change on its collection note. |
| Tag | Tag claim (observed-remove) | Name verbatim, including case; Joplin tag identity is its name in practice, so no ID mapping is kept for tags — the manifest records tag names only. |
| Resource (attachment) | Content blob + resource record | §4. |
| Note↔note link | Typed reference in revision content | §3. |
| Folder/notebook path | Not stored separately | It is derivable from the collection chain; storing it twice would create a second, divergent placement fact. |

## §3 Internal links

- During import, every `:/<note-id>` occurrence in a note body is rewritten to a structured typed reference: target = the manifest's note ID for that Joplin ID, sigil/type = note reference, authored surface = the original link text (or the target's Joplin title where Joplin itself would have rendered it).
- A `:/<id>` whose target is a resource is a §4 blob reference, not a note reference — the manifest distinguishes the two ID spaces, and conflating them is the classic importer bug this section exists to pre-empt.
- A reference whose target is absent from the vault (dangling in Joplin itself, or excluded from the export) is preserved with its authored surface and marked unresolved, per #2048's degradation rule. The import report counts dangling references; it never invents targets and never drops the reference silently.
- Round-trip (§5) turns typed references back into `:/<joplin-id>` using the manifest — which is why the authored surface is preserved: export must be able to reproduce a link a Joplin user recognises.

## §4 Attachments / resources

- Resource bytes are stored as blobs, content-addressed by the substrate; the import records (in the manifest and a resource record) Joplin resource ID ↔ blob reference, plus title, MIME type and original filename as claims.
- In-body resource references are rewritten to blob references in the imported revision. The resource record — not the body — is where "this blob is an attachment named `budget.pdf`" lives, so a rename in Joplin terms is a claim change, not a content change.
- Export restores resources as Joplin resource files with their recorded filenames/MIME types and rewrites body references back to `:/<resource-id>` (§5). Byte identity is the acceptance bar: attachment bytes must hash-equal across the round trip (§8 oracle).

## §5 Round-trip export expectations

Export from ID back to JEX is part of this design's contract, with these expectations, stated as testable equalities over canonical sets:

1. **Notes:** the set of exported notes corresponds 1:1 (via the manifest) to the imported set, plus any notes created natively in ID since import, which export with freshly minted Joplin IDs recorded back into the manifest.
2. **Links:** every typed note reference exports as a `:/<id>` reference to the corresponding Joplin ID; unresolved references export with their authored surface intact.
3. **Tags:** the tag set per note is equal after the round trip (as sets of names).
4. **Attachments:** resource bytes are hash-equal; filenames and MIME types preserved.
5. **Notebooks:** the collection nesting exports as the same notebook tree (names and parentage).
6. **Timestamps and to-dos:** original created/updated claims and to-do state export to the corresponding Joplin fields where the target format carries them.

**Stated lossy list** (the round trip does *not* promise these, and the export report must say so): Joplin revision history (v1 imports current state only — history is split #7675); Joplin-internal plugin markup, which is preserved verbatim as body content but not interpreted on either leg; end-to-end-encrypted items, which are never imported encrypted (§6 invariant 5); and any ID-side structure with no Joplin counterpart (extra heads from ID-side concurrent edits export as the merged/current head only — see §7).

## §6 Invariants implementation must hold

1. **Stable identity is ID's.** Imported notes get ID note IDs; Joplin IDs live in the manifest only. Renames (either side) never change a note ID.
2. **Append-only import.** Import writes signed `note.create`/`note.revise` events under the importing identity; it never edits or deletes existing world content. Re-import of a changed Joplin note creates a new revision under the *same* logical note (found via the manifest), joining heads explicitly if ID-side edits created a divergent head — never last-writer-wins, per #2048.
3. **Idempotency.** Re-importing the same export into the same world creates no duplicate notes, collections, or blobs: dedupe keys are (source-vault identity, Joplin ID) via the manifest, and content blobs dedupe by hash in the substrate.
4. **No silent drops.** Every item in the source export is accounted for in the import report: imported, deduplicated, degraded (Markdown-source case), dangling, or refused with a reason. A count mismatch fails the import.
5. **No key handling.** The importer never handles Joplin E2EE keys or encrypted payloads. Encrypted items are refused and reported; decryption is the user's act, outside the importer, before export.
6. **Parent decisions stand.** Anything not settled here or in #2048 — cluster features, other importers, the graph view — is out of scope; where an implementation choice would change a #2048/#5678 decision, it is recorded on the parent, not forked here (§7 is the worked example).

## §7 The one explicit parent-decision touch

#2048 keeps concurrent heads visible until an explicit merge, and this design holds that for import (invariant 2). **Export** is where the models genuinely differ: Joplin has one current body per note, so exporting a multi-head note must pick or merge a head. This design records the rule here rather than silently forking #2048: export uses the world's current merged head when one exists; for a note with unmerged concurrent heads, export takes the head descended from the last import (the Joplin-lineage head) and the export report names the note and the unexported head(s). Nothing is merged or discarded in ID by exporting. If Drew prefers a different export rule, this paragraph is the decision to amend — on #5678/#2048, not in importer code.

## Viable options

| Option | Trade-offs | Decision |
| --- | --- | --- |
| **Manifest-recorded model mapping (this design)** | Import lands in the object model with stable identity, typed references and claims; round-trip and idempotent re-import are possible *because* the manifest persists the ID mapping. Costs an importer that understands both models and a manifest to maintain. | **Recommend.** It is the only option that satisfies the issue's round-trip expectation. |
| One `document.put` per note (files with frontmatter) | Minimal new machinery; mirrors a Markdown export on disk. | Reject: #2048 already rejected per-put identity (its option 1) — event IDs change per save, so links/backlinks cannot survive edits, and there is nowhere for the manifest or typed references to live. |
| Markdown-only import, no manifest | Simplest possible importer; fine for a one-way migration the user never revisits. | Reject: without the manifest, link rewriting is guesswork, re-import duplicates everything, and §5's round-trip equalities are untestable — the issue explicitly asks for round-trip expectations. |
| Joplin sync-target emulation (ID as a Joplin sync backend) | Would give continuous two-way sync instead of import/re-import. | Reject for v1 and split as #7676: it couples ID to Joplin's sync protocol churn and its conflict semantics fight #2048's multi-head model; the manifest design keeps the option open without paying for it now. |

## §8 Test corpus plan

The corpus is the oracle for §5 and §6; per the fleet testing doctrine, each check names its oracle — here the oracle is **canonical set equality**: notes, per-note tag sets, typed-reference targets, notebook tree, and attachment byte hashes, compared modulo the §5 lossy list.

- **Synthetic corpus (generated fixtures, committed with the importer):** nested notebooks (≥3 levels, an empty notebook); notes with duplicate titles in different notebooks; a link graph including a cycle, a self-link, and a dangling link; attachments of each common class (PNG, PDF, audio, an unrecognised binary) including one resource referenced by two notes and one orphan resource; to-do notes (open, completed, with due dates); Unicode/emoji and very long bodies; a note whose body contains literal `:/<id>`-looking text that is *not* a reference.
- **Round-trip property:** for every corpus vault — import → export → import into a *fresh* Joplin → canonical comparison against the original export. Generators vary vault shape (counts, nesting, link density) property-style rather than only the fixed fixtures above.
- **Idempotency property:** importing the same JEX twice yields a world whose canonical projection is unchanged by the second import (invariant 3), and importing a one-note-changed JEX produces exactly one new revision (invariant 2).
- **Real-vault sample:** one anonymised real-world JEX (Drew's or a volunteer's, scrubbed per the corpus README) run through the same properties, to catch shapes generators do not imagine. The corpus plan names this as a corpus *requirement*, not a fixture this design provides.

## Implementation slicing (follow-on issues, not this design)

1. **JEX reader + manifest:** parse JEX, build/persist the manifest and import report (invariant 4's accounting), no content written yet — report-only mode.
2. **Notes, collections, tags:** `note.create` mapping per §2 with idempotency (invariant 3).
3. **References and resources:** §3 rewriting and §4 blob storage, dangling accounting.
4. **Re-import:** changed-note revision path and head-joining (invariant 2).
5. **Export:** JEX writer satisfying §5, with the lossy-list report.
6. **Corpus:** §8 fixtures + round-trip/idempotency properties wired into the importer's test suite.
