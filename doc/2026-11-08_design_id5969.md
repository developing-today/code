# Design: library typing & upload taxonomy — subtypes, entity attachment, DLL vs compile-in, libraries by URL

- **Date:** 2026-11-08
- **Status:** proposed design for review; no implementation is included here.
- **Issue:** [#5969](https://github.com/developing-today/code/issues/5969), part of the worlds design program [#5955](https://github.com/developing-today/code/issues/5955) (statements S59–S65 of the 2026-11-04 brief).
- **Inputs:** triage of #5969 by task 10338 (2026-11-05) and re-triage by task 12411 (2026-11-08, verdict: confirmed real-and-current); current `pkgs/id` code at this checkout; sibling sub-scopes of #5955 — library imports, the capability model, compile economics ([#5965](https://github.com/developing-today/code/issues/5965), `doc/2026-11-05_design_id5965.md`), content identity ([#5997](https://github.com/developing-today/code/issues/5997)), and the licensing children; KDL as the manifest language ([#5753](https://github.com/developing-today/code/issues/5753)); invites ([#5751](https://github.com/developing-today/code/issues/5751)) as the nearest existing entity-attachment mechanism.
- **Method:** every "current state" claim below is tied to code at this checkout. Where this design spends a concept another child of #5955 owns (compile caching economics, capability semantics, license vocabulary, content identity), it names the seam and does not redefine that child's part.

## Decision to make

Libraries are uploaded, discovered, and depended on, but today the system has no type for them: a library is indistinguishable from any other artifact. Decide (1) the registry kinds an upload can be, (2) the library manifest — its type, its arbitrary subtypes, its attachment to entity IDs, and its build mode, (3) what attachment *means* (discovery, eligibility, or restriction), (4) how subtype conformance is defined and checked, and (5) how a library that is "just a URL" gets identity and integrity.

## Recommendation

Give the registry **four upload kinds** — `world`, `dll-library`, `source-library`, `url-library` (§1) — and give every library **one manifest**, a KDL profile (§2), that carries its kind, zero or more **subtype conformances** (§4), zero or more **entity attachments** (§3), and a **build mode** (`dll`, `compile-in`, or `dual`, §5). Decide attachment as **discovery + eligibility by default, restriction only on the author's explicit opt-in** (§3) — the reading that makes genre/game attachment useful without letting attachment become a lock-in or a takedown lever. Subtypes are **published interfaces**: the world/game-type author publishes a named, versioned, content-hashed interface; a library declares conformance in its manifest; conformance is *checked* at upload/compile time where the bytes are available and degrades to *declared* for URL libraries until their pinned bytes are fetched and verified (§4). A URL library's identity is **URL + pinned content hash + version** — the URL is a locator, never the identity (§6).

## 1. Upload taxonomy: registry kinds

Every upload to the registry is exactly one kind. The kind is declared in the manifest (for libraries) and is a first-class registry field: listings, search, and filters key off it (§7).

| Kind | What is uploaded | Identity | Notes |
| --- | --- | --- | --- |
| `world` | A world (module + state genesis), as today. | World id + module content hash. | Not a library; listed here because the registry shows worlds and libraries side by side (§7) and the taxonomy must say where the line is: a world *runs*; a library is *depended on*. |
| `dll-library` | A precompiled library artifact, built to be loaded as a DLL. | Artifact content hash. | Eligible for precompile-and-cache treatment; the economics are #5965's, the mark is §5's. Expected to be the most common library upload alongside worlds (per the brief: "most uploads would probably be worlds or DLL code"). |
| `source-library` | Library source, built to be compiled into a consuming program. | Source closure hash (ordered file names + bytes, as in #5965's cache key). | Compiles in the consumer's compile job; participates in the consumer's source closure hash. |
| `url-library` | Nothing but a manifest pointing at an external URL. | URL + pinned content hash + version (§6). | The brief's "other libraries can just be a URL, essentially". A URL library *becomes* a `dll-library` or `source-library` for build purposes once its pinned bytes are fetched and verified; the kind records how it was *published*, and the fetched form is recorded alongside. |

Kinds are closed: a new kind is a taxonomy change (a design amendment), not a new manifest field value invented by an uploader. Subtypes (§4) are the open axis; kinds are the closed one. That separation is deliberate — it is what keeps the registry queryable.

## 2. The library manifest (KDL profile)

One manifest per library, a KDL document (profile of #5753). Fields:

```kdl
library "petname-chess-clocks" version="1.2.0" {
    kind "dll-library"              // one of §1's library kinds
    build-mode "dll"                // dll | compile-in | dual (§5)
    hash "blake3:…"                 // content hash of the artifact / source closure / pinned bytes
    license "…"                     // vocabulary owned by the licensing children of #5955 — a seam, not defined here
    platform {                      // requirements, semantics owned by the capability-model child — a seam
        requires "…"                // capability/platform identifiers, by reference
    }
    subtype "chess/timed-game" version="3" hash="blake3:…"   // zero or more (§4)
    attach "genre:chess" mode="discover"                     // zero or more (§3)
    attach "game:01J…" mode="restrict"
    source url="https://…"          // url-library only (§6)
}
```

Rules:

- **Required:** name, version, kind, build mode, hash, license. A manifest without a content hash is not a library — it is a claim about a library, and the registry refuses it.
- **Name** is a petname-style local name (author-scoped); the registry identity is the hash, not the name. Names can collide; hashes cannot.
- **Version** is author-assigned and monotonic per (author, name): re-uploading the same name with a lower or equal version and a different hash is rejected — that combination is how mutable-URL confusion (§6) would otherwise enter through the front door.
- **Platform requirements** and **license** are carried by reference into the sibling designs that own them. The manifest fixes *where they sit and that they are mandatory*, not their vocabularies.
- The manifest itself is content-hashed; the registry stores (manifest hash → library record). Anything that displays a library can cite the manifest hash it resolved.

## 3. Attachment semantics: discovery + eligibility by default, restriction by opt-in

A library may attach to **any entity ID** — a genre, a specific game/world, another entity — or to **nothing** (unattached = globally visible, the default state of a library with no `attach` nodes). Attachment is a manifest declaration by the library's author; the target entity does not have to consent (resemblance to invites, #5751, noted: attachment is a claim *about* the library, displayed next to the entity, not a write *into* the entity).

The three candidate meanings are different designs, so the decision is explicit:

- **`discover` (default for every attachment):** the library is *discoverable in the entity's context* — it appears in the genre's / game's library listings and searches scoped to that entity. 
- **`eligible` (implied by every attachment, including `discover`):** worlds/games under that entity may depend on the library, and subtype/capability checks treat the attachment as satisfying "for this genre/game" scoping.
- **`restrict` (explicit opt-in per attachment):** the library may *only* be depended on within the attached entities' contexts. Restriction is the author's choice about their own library — never the entity's choice about the library, and never a default: an author who attaches for discovery has not silently restricted their audience.

Invariants:

1. Attachment never changes what a library *is* — removing an attachment is a manifest revision, not a new library; the hash lineage is preserved.
2. Restriction composes as an intersection over `restrict` attachments and is ignored outside them: a library with one `restrict` attachment to game A and a `discover` attachment to genre B is restricted to A's context — B's discover listing shows it with its restriction marked, so nobody discovers a library they cannot use without seeing why.
3. Attachment targets are resolved by entity ID at display/dependency time, not snapshotted: if the entity is renamed or forked, the attachment follows the ID (fork behaviour follows the entity system's own fork semantics — a seam, not redefined here).

## 4. Subtypes: published interfaces, declared conformance, checked where bytes exist

A **subtype** is how "built for a specific world or game type" is expressed. 

- **Who defines one:** the author of the world / game type (or genre) publishes a **subtype definition**: a named interface (name under the author's scope, e.g. `chess/timed-game`), a version, and a content hash over the interface definition itself — the signatures/shapes a conforming library must provide, expressed in the same terms the library-imports design uses for an import surface (a seam: the interface *language* is the imports design's; this design fixes the publication/conformance mechanics).
- **How a library claims one:** a `subtype` node in the manifest naming the definition's name + version + hash (§2). Pinning the hash matters: a library conforms to the interface *as published at that hash*, not to whatever the name means later.
- **How it is checked:**
  - `dll-library` / `source-library`: checked mechanically at upload (and re-checked at dependency resolution) against the pinned interface — signatures present, shapes compatible. A failed check means the conformance claim is dropped from the registry record (the library itself still exists, unsubtyped); it is never silently displayed as conforming.
  - `url-library`: conformance is **declared** at publish time and becomes **checked** the first time the pinned bytes are fetched and verified (§6); the registry displays the distinction (`declared` vs `checked`) wherever conformance is shown. A hash change at the URL is a new version (§6) and resets conformance to `declared`.
- **What conformance buys:** eligibility under §3 in contexts scoped to that subtype, and filterability (§7). Non-conformance is not a defect — a library with no subtypes is a general library, which is a normal and expected case.

## 5. Build mode: DLL vs compile-in

The manifest's `build-mode` is the flag #5965's compile economics consumes:

- **`dll`:** the library is built to be used as a DLL — a precompiled artifact, loaded at runtime. DLL-marked libraries are the ones that "could be precompiled and cached" (the brief); the cache key and economics are #5965's, keyed by the artifact's content hash recorded here.
- **`compile-in`:** the library is built to be compiled into another program — source form, part of the consumer's compile job and source closure.
- **`dual`:** the author publishes both forms under one manifest; the two forms carry separate hashes, and dependency resolution picks the form the consumer's build needs. A `dual` library is one library, not two registry entries — splitting it into two entries would break attachment and subtype lineage for no benefit.

Rules: build mode must agree with kind (`dll` mode ⇔ `dll-library` or the DLL form of a `dual`; `compile-in` ⇔ `source-library` or the source form of a `dual`; a `url-library` declares the mode its pinned bytes take once fetched). The registry validates the agreement against the fetched/compiled artifact where one exists. Build mode is part of the manifest, so it is versioned with it: changing modes is a new manifest version, visible in history — never a silent flag flip on an existing record.

## 6. URL libraries: identity is URL + pinned hash + version

A URL is mutable; a library must not be. Therefore:

- **Identity:** the triple (URL, pinned content hash, author-assigned version). Two records with the same URL and different hashes are different versions; the same URL and hash under a new version label is a relabel and is rejected (§2's monotonicity rule).
- **Integrity:** consumers fetch the URL and verify the bytes against the pinned hash before any use — build, capability checking, or subtype checking (§4). A mismatch means *this is not the library the manifest names*: the fetch fails as that library, full stop (it may be fine bytes, but they are some other, unnamed thing).
- **Capability participation:** a URL library participates in capability-subset checking through its fetched manifest + bytes, checked at pin/fetch time under the capability-model child's rules (a seam). Until fetched and verified, it participates as an opaque dependency whose declared requirements are its manifest's `platform` block — displayed as declared, like subtype conformance.
- **Re-pinning:** when the upstream content legitimately changes, the author publishes a new manifest version with the new hash. There is no "track latest" mode: an unpinned URL dependency would make every downstream build non-reproducible, which contradicts the content-hash discipline the whole program already uses at install.

## 7. The taxonomy in the registry

- **One listing, kind-marked:** worlds and the three library kinds appear in the same registry surfaces, each entry badged with its kind; kind is a filter, as are attachment entity, subtype (with `checked` before `declared` in result ordering), and build mode.
- **Entity pages show their libraries:** a genre/game page lists libraries attached to it, with restriction (§3) visibly marked.
- **A library's page** shows: manifest (by hash), attachments, subtype conformances with their checked/declared state, build mode and per-form hashes, provenance of the record (uploaded directly / fetched-from-URL + last verification), and version history. Everything displayed is resolvable to a manifest hash (§2), so two viewers arguing about "the same library" can settle it by comparing hashes.

## Alternatives rejected

- **Attachment as restriction by default** — makes every genre attachment a lock-in decision, discourages the discovery attachments the feature exists for, and hands entities a de-facto veto the brief never asked for ("attach to whatever, or to nothing").
- **Attachment requires the target entity's consent** — turns a metadata claim into a write against someone else's object; discovery claims about public entities must be free to make, with display-side filtering as the remedy for junk attachments.
- **Subtypes as free-form tags** — tags are uncheckable; "built for chess" as a tag tells a consumer nothing it can rely on. Tags can still exist elsewhere for search; they are not subtypes.
- **URL as identity** — a mutable locator cannot name an immutable dependency; every consumer would silently build against different bytes over time.
- **Kind per form for `dual` libraries** — two registry entries for one library splits its attachments, subtypes, and history; the form is an attribute, not an identity.

## Invariants implementation must hold

1. Every registry upload is exactly one of the four kinds; kinds are closed, subtypes are open.
2. No library record exists without a content hash (artifact, source closure, or pinned URL bytes).
3. Attachment defaults to discover+eligible; restriction exists only where the author opted in per-attachment, and restricted libraries display their restriction wherever they are discoverable.
4. Subtype conformance is displayed as `checked` only when mechanically verified against the pinned interface hash; URL-library conformance starts `declared` and resets on re-pin.
5. DLL-marked = build mode `dll`/`dual` with an artifact hash — the exact flag and hash #5965's cache consumes.
6. A URL fetch whose bytes mismatch the pinned hash is never used as that library, for any purpose.
