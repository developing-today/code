# Design: effect-language borrowings — which Koka/Unison properties id tooling emulates, approximates, or skips

- **Inputs:** prior-art research (Lane B item 7) in the 2026-11-04 worlds capabilities brief; the compile-economics design [#5965](https://github.com/developing-today/code/issues/5965) (`doc/2026-11-05_design_id5965.md`), which already adopted content-hash cache identity.

## Decision summary

| Property (source) | Verdict | Shape in id tooling | Cost in one line |
| --- | --- | --- | --- |
| Effect-row inference (Koka) | **Approximate** | Call-graph derivation of the used-capability set over the closed platform-function namespace; no effect rows in types | A derivation pass to build and keep in sync with the platform ABI, and a set-valued (not row-polymorphic) result that must be recomputed or conservatively unioned at higher-order boundaries |
| Content-addressed definitions (Unison) | **Emulate** (identity layer only) | Hash-of-(canonical AST, dependency hashes) as library/artifact identity, continuous with the #5965 compile-cache key | Canonical serialization + hash discipline, a determinism gate before cross-author sharing, and a name↔hash metadata layer for humans |
| Ability-checked signatures (Unison) | **Emulate the check, approximate the signature** | Declared capability ceiling in tooling metadata; derived used-set must be a subset, checked at compile/admission time, failing closed | A manifest format and a checker in the compile/admission path; declarations drift unless derivation (§1) — not hand-writing — is the source of truth for the used set |
| Untyped effects (OCaml 5) | **Skip** | Standing constraint: no runtime-discovered capability may ever be a security boundary in id | None — this closes a design direction, it does not open one |
| Comptime context structs (Zig) | **Keep as the mechanism** | Capabilities keep travelling as explicit context values (`context.platform.fn` shape); inference/checking is an audit layer on top, never the passing mechanism | Verbosity at call sites, accepted deliberately — see §5 |

## 1. Effect-row inference (Koka) — approximate

**What Koka proves.** Koka's book (§2.2, *Effect Typing*) states the core fact plainly: "Koka infers and tracks the effect of every function in its type" — a function type has three parts (arguments, effect, result), effects are inferred rather than annotated, and they are *polymorphic*: `map` over `a -> e b` has exactly the effect `e` of the function it is given. So the used-effect set of a program is not an analysis bolted onto the language; it falls out of type inference, exactly, including through higher-order functions. The book (§2.4) also records that handlers compile via evidence passing to plain C with no runtime system, so the guarantee costs nothing at runtime. Two cautions come from the same primary source: the book's front page says Koka "is a research language that is currently under development and not ready for production use" — we borrow the theorem, never the toolchain.

**Why id cannot have the real thing.** Roc has no effect rows and no user-defined effect system: effects in Roc *are* calls to platform-provided functions, and the platform interface is a fixed, closed namespace. There is no type-level row for inference to produce, and this note does not propose changing Roc.

**The approximation.** Because the effect namespace is closed and every effect is a named platform function, the used-capability set of a world or library is computable by call-graph reachability over that namespace — the second of the three proven derivation techniques the research brief catalogued. That is what id tooling emulates Koka *with*: same output (a used-effect set the tooling can check and display), different engine (reachability, not row inference).

**Where the approximation leaks — stated, not hidden.**

- *Higher-order boundaries.* Koka's row variable `e` is exact per instantiation. A reachability set is not polymorphic: passing a capability-using function as a value forces the tooling to either recompute the set per instantiation (cost: derivation runs per compile, cacheable by §2 identity) or take the conservative union over everything the value *could* be (cost: over-approximation, i.e. worlds that look more capable than they are and fail §3 checks they should pass).
- *Dynamic loading and reflection* break reachability exactness entirely. The brief's conclusion stands as a rule for certification: a library whose capability set id certifies may not use dynamic loading or reflective dispatch to reach platform functions. Uncertifiable shapes are not an inference failure to paper over; they are outside the certified subset.

**Cost of emulation.** One derivation pass in the compile tooling, keyed to the platform ABI version (a platform change re-derives everything — §2's identity makes that cacheable), plus the recomputation/union policy above. No runtime cost: derivation is compile-time, exactly as Koka's inference is.

## 2. Content-addressed definitions (Unison) — emulate, at the identity layer

**What Unison proves.** Unison's own overview (*The big idea*) defines the model in one line: "Each Unison definition is identified by a hash of its syntax tree" — dependencies are replaced by their hashes inside the tree being hashed, names are separately stored metadata that do not affect the hash, and because a definition never changes, parse/typecheck results go in "a cache which is never invalidated". Dedup, cache identity, and the impossibility of diamond-dependency conflicts are all corollaries of that single choice.

**What id emulates.** The identity layer, for libraries and compiled artifacts — not the codebase model. This is mostly a ratification of a decision already taken: the #5965 compile-economics design keys its server compile cache by a BLAKE3 tuple over platform tree hash, source closure hash, DLL closure hash, and compiler digest, and compiled artifacts are already stored under a content hash at install today. This note extends the same discipline one step down, to the *definition* level the Unison model names: a library's identity is the hash of its canonical AST with dependency hashes substituted, so the §1 derivation result and the §3 declared set can both be keyed by an identity that cannot silently change under them.

**What id skips, deliberately.** Unison's full model — code stored as a database of hashes, names as mutable pointers, "no builds" as a way of life — does not transfer. Roc source stays text, name-based, and built by ordinary tooling. Nothing in this note proposes a hash-addressed codebase for id.

**Cost of emulation.** (a) A canonical AST serialization stable enough to hash — the hard part; formatting or desugaring changes must not change identity unless semantics change. (b) The determinism gate #5965 already specified: cross-author cache sharing is sound only for compiler/platform pairs with a byte-identical-recompile proof on record. (c) A name↔hash metadata layer, because humans navigate by names and every tooling surface (errors, reviews, capability displays) must translate. Unison pays all three inside its codebase format; id pays them inside its tooling only.

## 3. Ability-checked signatures (Unison) — emulate the check, approximate the signature

**What Unison proves.** Unison's abilities documentation describes abilities as the language's algebraic effects: an ability pairs operations with handlers, and the docs' follow-on section covers how abilities are *represented in function type signatures* — the research brief's example is `I ->{A} O`, a function whose type names the ability set `A` it requires. The consequence that matters for id: a computation that uses an ability nobody granted is a **compile-time** failure, not a runtime surprise. The signature is simultaneously documentation, contract, and enforcement point.

**What id emulates.** The enforcement, which is the security boundary: every world and library carries a *declared* capability ceiling; §1 derivation produces the *actual* used set; the tooling checks `used ⊆ declared ∩ granted` at compile time and again at admission (install/load), and fails closed on any violation. A capability a world was never granted cannot be reached, and that fact is established before the world runs — the Unison guarantee, restated in id's vocabulary.

**What is only approximated.** The signature itself. Roc types cannot carry an `->{A}` annotation, so the declaration lives in tooling metadata — a capability manifest attached to the world/library, in the same spirit as capabilities already travelling as explicit record values in the platform context (§5). That is weaker than Unison in one specific way worth naming: an in-type signature cannot drift from the code, while a manifest can. The mitigation is structural, not procedural — the manifest's *used* side is never hand-written; it is §1's derivation output. Humans declare ceilings; machines compute usage; the check compares them.

**Cost of emulation.** A manifest format (small: a set of capability names plus the §2 identity of the artifact it describes), a checker in the compile path and the admission path, and the §1 derivation pass as a hard dependency. No runtime cost beyond the admission check.

## 4. The OCaml caution — skip untyped effects

OCaml 5's manual (*Effect handlers*) is explicit, in its own comparison: "Unlike languages such as Eff and Koka, effect handlers in OCaml do not provide effect safety; the compiler does not statically ensure that all the effects performed by the program are handled. If effects do not have a matching handler, then an `Effect.Unhandled` exception is raised at the point of the corresponding perform."

That is the one model of the four that is disqualified for id, and this note records it as a standing constraint, not a preference: **a capability failure in id must be discoverable at compile or admission time; any design in which an ungranted capability is first discovered by a runtime exception is rejected on that ground alone.** OCaml's design is reasonable for OCaml's goals (a retrofit onto a mature language, per the same manual's framing of handlers as a thin wrapper over runtime primitives); copied into a system whose capability sets are a *security* boundary, it converts every missing grant into a runtime denial-of-service against the world that discovers it. Dead end — do not revisit without answering this paragraph.

## 5. The Zig comparison — explicit context is the floor, and id already stands on it

Zig is the mainstream control case: no effect system, no inference, and — per its language reference's comptime model and the standard library's conventions — capabilities passed *explicitly*: there is no global allocator, so functions that allocate take an `Allocator` argument; more generally, context (allocators, writers, configuration) travels as ordinary struct values and `comptime` parameters, and referencing a field the context type does not have is a compile error because the type is simply checked. Absence of a capability is unrepresentable-as-written, which is a compile error — the same guarantee class as Unison's, bought with verbosity instead of inference.

id's platform model is already this shape: capabilities reach a world as explicit context values (the `context.platform.fn` pattern the #5963 programming-model topic is built around). This note's position is that the Zig shape is the correct **mechanism** and §§1/3 supply the **audit** Zig lacks:

- *Passing* stays explicit and value-level (Zig-like): no hidden ambient authority, nothing inferred at runtime.
- *Derivation and checking* (§§1, 3) are compile/admission-time tooling over that explicit surface — they exist so authors do not have to hand-maintain the used set (Zig's known cost: manual, verbose, and only as accurate as the author's patience), not so the mechanism can become implicit.

If the derivation tooling were deleted tomorrow, id would degrade to exactly Zig's position — explicit, safe, manual — and not one step further. That is the test this layering is designed to pass.
