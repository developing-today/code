# Design: knowledge graph view cluster — local/global, edges, filters, scale, live behaviour

- Date: 2026-11-08
- Status: **decision record** — design only; no graph-view code is implemented here, and implementation timing is explicitly deferred (see §8).
- Issue: [#5837](https://github.com/developing-today/code/issues/5837), parent programme [#5678](https://github.com/developing-today/code/issues/5678), programme epic [#2056](https://github.com/developing-today/code/issues/2056).
- Baseline: `origin/main` `d2c2a05b5e` at drafting.
- Object model: [#2048](https://github.com/developing-today/code/issues/2048) as landed in `doc/2026-11-01_design_id2048.md`: stable logical notes (`note.create` event ID = stable note ID), signed immutable revisions (`note.revise` naming causal parents and a content blob; concurrent heads retained, joined only by an explicit multi-parent revise), structured typed references in revision content (target note ID, sigil/type, authored surface, optional pinned revision), backlinks as a derived inverse projection over active heads, tags as signed observed-remove claims, names/aliases as claims (never identity), tombstone removal, group `Read`/`Write` as the authority model, per-store rebuildable projections, and no global index. This record **consumes** those decisions; it does not re-decide them. The one place it touches a parent decision is flagged explicitly in §7.
- Query direction consumed, not re-decided: the parent programme's canonical data model is atomic triples with ANSI SQL/PGQ as the query model ([#5688](https://github.com/developing-today/code/issues/5688), filled in by the #5906 record `doc/2026-11-08_decision_id5906_kdl_json_contract.md`). The graph view is a **consumer** of that triple store, not a new store and not a new query language.

## Decision to make

What is the Obsidian-style graph view over #2048 ID objects: how do local and global graphs relate, which edges exist, how filtering works, what performance target the view must hold on large vaults, and what a viewer sees while other writers change the graph live?

## Recommendation (summary)

**One bounded-subgraph query, two viewports.** Local and global are the same SQL/PGQ query over the per-store triple projection, differing only in a focus constraint; the server (store) side always returns a _bounded_ subgraph, never the whole vault. Edges are exactly the #2048 facts — typed references, their derived inverse (backlinks), tag claims, and typed relations — rendered from triples, with read-authority filtering applied inside the query before anything (including degree counts) reaches the viewer. Live behaviour is projection-delta subscription over revision heads: eventually consistent, causally attributable, with concurrent heads shown rather than silently resolved. Detail and rationale in §1–§5; rejected alternatives in §6; invariants in §9.

## §1 Local vs global graph

- **Global graph** = the query with no focus constraint, over one store scope (the viewer's open vault/world). "Global" never means cross-store: #2048's non-goal of a global index stands, and cross-store fan-out remains an explicit later query, exactly as #2048 left it.
- **Local graph** = the same query with a focus note and a depth bound (ego network): the focus note, its neighbours to depth _d_ (default 2, range 1–4) along the enabled edge families, rendered around the focus.
- Local is a **viewport**, not a data structure: switching focus or depth re-runs the query; nothing is cached as "the local graph" server-side. This kills the classic divergence where a local graph and a global graph disagree about the same facts — here they cannot, because both are projections of the same triples at the same store state.
- The default landing view is the local graph of the currently open note (the Obsidian behaviour users are trained on); the global graph is one explicit action away, and returning preserves the last focus.

## §2 Edge types

Edges are triples `(subject, predicate, object)` over note IDs and tag names, sourced only from #2048 projections. Four families, no others in v1:

| Family     | Source fact                                                                                                                                                                           | Direction                                 | Rendered as                                                                                                                                               |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `link`     | A structured typed reference in an active head revision's content, whose type is a plain note reference                                                                               | directed, source → target                 | the primary edge                                                                                                                                          |
| `backlink` | The derived inverse of `link` (the #2048 backlink projection)                                                                                                                         | directed, target → source when traversed  | **not a stored edge**: the same triple read in the other direction. Rendering may style an edge by whether it is mutual, but no second edge record exists |
| `tag`      | An observed-remove tag claim on a note                                                                                                                                                | undirected membership                     | note ↔ tag node; tag nodes are rendered only when the tag family is enabled (§3), and are the first family dropped under scale pressure (§4)              |
| `relation` | A structured typed reference whose sigil/type is a declared relation type (e.g. collection membership, as the #5848 importer design's collection notes produce; `part-of`, `relates`) | directed, labelled with the relation type | a labelled edge, visually distinct from `link`                                                                                                            |

Explicitly **not** edges: alias/name claims (names are presentation, not structure — #2048), revision parentage (that is history; a "show history" affordance may exist later but is not the graph view), co-tag similarity or any computed/embedding edge (no inferred edges in v1; every rendered edge must trace to a signed fact a viewer could inspect).

Pinned-revision references still produce a `link`/`relation` edge to the target _note_; the pin is a property of the reference (shown in the edge inspector as an exact-revision citation), not a separate node.

## §3 Filtering

- A filter is a composable predicate set evaluated **inside the SQL/PGQ query**, not by thinning a full graph client-side: edge-family toggles (§2), tag include/exclude, collection scope (restrict to a collection note's membership closure), alias/surface text match, resolved-only (hide unresolved placeholder nodes), orphans-only / hide-orphans, and — for the local graph — depth.
- **Read-authority filtering is not a filter option.** It is applied first, unconditionally, inside the query, per the #5678 read-authority ruling (resolution order: object → user default → server config → public; default public read). A note the viewer may not read does not appear as a node; an edge to it degrades per §5; and **degree/count badges are computed after authority filtering**, so counts cannot leak the existence of unreadable neighbours beyond what a readable referencing revision itself already states.
- Saved filter sets are viewer configuration (claims/config on the viewer's own objects), never graph facts; sharing a filter set shares a recipe, not data.

## §4 Performance on large vaults — concrete target and budget

Design point and budgets (these are the acceptance numbers an implementation is measured against; "fast" without numbers is not accepted, per the task packet):

- **Scale target:** a single store of **100,000 notes and 1,000,000 edges** (triples in the §2 families) must remain interactive under the budgets below.
- **Query budget (store side, p95, warm projection):** local-graph query at depth ≤ 3 ≤ **50 ms**; bounded global-graph query ≤ **250 ms**. Both are served from the #2048 per-store adjacency projections (outgoing references + inverse backlinks, maintained incrementally from revision events and rebuildable from the event log) fronted by SQL/PGQ — never by scanning revision content at query time.
- **Render budget:** first render of a bounded subgraph ≤ **500 ms** at the visible-node cap on a mid-range laptop browser.
- **Visible-node cap:** default **2,000** nodes, hard cap **5,000**. The cap is enforced in the query (bounded subgraph), not after transfer: beyond the cap the query aggregates — tag nodes and collection nodes become supernodes with post-authority-filter counts, and the lowest-degree leaf nodes fold into an "and N more" aggregate attached to their neighbour. A user may raise focus/depth and re-query; the client never receives an unbounded graph.
- **Degradation order** when a store exceeds budget: (1) drop tag nodes, (2) reduce default local depth to 1, (3) aggregate harder (lower visible cap). Correctness (authority filtering, head attribution) never degrades.
- Layout is computed client-side over the bounded set only; positions are ephemeral view state and are never stored as facts.

## §5 Multiplayer / live graph behaviour — consistency model

The graph view is a **live projection over signed revision heads**, and its consistency model is stated plainly so implementation cannot drift into accidental promises:

- **Eventual consistency with causal attribution.** A node appears when its `note.create` is in the viewer's store; an edge appears when a head revision carrying the reference is in the store. There is **no cross-node snapshot isolation**: two nodes on screen may reflect different arrival times. What is guaranteed: every rendered edge is attributable to a specific source head revision, and the view never renders an edge that no received head asserts.
- **Concurrent heads are shown, not resolved.** Where a note has divergent heads, the node carries a multi-head marker and its edge set is the **union over active heads**, each edge attributable to its head on inspection — the graph projection follows #2048 exactly (divergent-head backlinks stay attributable; no arrival-order or last-writer-wins choice). An explicit multi-parent revise (merge) collapses the marker when it arrives.
- **Read-your-writes, session-monotonic.** A viewer's own checkpointed revision is reflected in their view immediately (it is already a signed event in their store). Within a session, the set of heads a viewer has seen for a note never silently shrinks except by an explicit merge or tombstone arriving — both of which are themselves visible events, not silent rewrites.
- **Live updates** arrive as projection deltas (node/edge added, node/edge removed, head-set changed) pushed over the existing live-collaboration transport family (#2048 reuses ProseMirror session transport for live editing; the graph subscription is the same class of ephemeral channel). A disconnected viewer re-runs the bounded query on reconnect; deltas are an optimisation, never the source of truth.
- **Presence is not a graph fact.** "Who is editing this note now" (from the live session layer) may render as a transient halo on a node; it is never stored, never an edge, and disappears with the session.
- **Tombstones and unreadable targets.** A tombstoned note leaves the graph (its history does not — #2048 removal semantics). A reference whose target the viewer cannot read, or that has not resolved, renders as a **placeholder node carrying only the authored surface** from the referencing revision, per #2048's degradation rule — no title, no metadata, no existence claim beyond what the readable referencing revision itself contains.

## §6 Alternatives considered

| Alternative                                                                                                   | Why not                                                                                                                                                                                                                                                                  |
| ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Client-side whole-vault graph** (Obsidian's local-files model: ship everything, filter and lay out locally) | Fails all three ID constraints at once: the §4 scale target (100k notes cannot be shipped to a browser tab), multiplayer (no single local copy is the graph), and read authority (shipping unreadable notes' structure to the client _is_ the leak §3 forbids).          |
| **Backlinks stored as their own edges**                                                                       | A second, divergent copy of one fact; #2048 already settles backlinks as a derived inverse projection. Storing them invites exactly the drift the object model exists to prevent.                                                                                        |
| **A separate graph database / graph service beside the triple store**                                         | Forks the query direction the programme already decided (triples + SQL/PGQ, #5688/#5906) and creates a second synchronisation and authority boundary to get wrong. The graph view's needs are bounded-subgraph queries, which the projection + SQL/PGQ direction serves. |
| **Strongly-consistent live graph** (lock/sequence the whole graph per edit)                                   | Contradicts the replicated, multi-head object model: replicas legitimately hold different head sets. The honest model is §5's causal, attributable eventual consistency.                                                                                                 |
| **Computed similarity edges in v1** (co-tag, embedding neighbours)                                            | Inferred edges have no signed fact behind them; they would render claims the data does not make. Revisit only as a clearly-labelled, separate family after v1.                                                                                                           |

## §7 Parent-decision touchpoint (explicit, per the packet rule)

One clarification touches a #2048 non-goal and is recorded here rather than silently forked: #2048 lists "a global or ambient index; cross-store fan-out" as a non-goal. This record's **global graph is a per-store bounded query, not an index and not cross-store** — it introduces no new stored structure beyond #2048's own per-store projections. The parent decision therefore stands unchanged; "global" in this cluster's name means _whole-store viewport_, and any future cross-store graph is a new decision for the parent, not an implication of this record. No #2048 or #5678 decision is changed by this record; if Drew reads the clarification differently, this section is the place to overrule.

## §8 Implementation timing and splits

Per the issue body, implementation timing is a separate decision, possibly months out. This record therefore **files no implementation issues and splits nothing**: the design does not subdivide further — its five facets are one coherent view, and §1's "one query, two viewports" decision is precisely the refusal to split local and global into separate designs. When implementation is approved, the natural first packet is the bounded-subgraph SQL/PGQ query + adjacency-projection read path (§1/§4), with the §4 budgets as its acceptance numbers; filing it belongs to that approval, not to this record. Issue #5837's design obligation is discharged by this record; the issue is closed by the PR that lands it, with implementation explicitly deferred per this section.

## §9 Invariants implementation must hold

- Every rendered node is a stable note ID the viewer is authorised to read (§3), or a §5 placeholder carrying only an authored surface from a readable revision. Renaming a note (an alias-claim change) never changes its node identity or its edges.
- Every rendered edge traces to a signed fact: a typed reference or tag claim in a received event. No inferred edges; backlinks are never stored separately from the references they invert.
- Authority filtering happens inside the query, before counting, aggregation, and transfer. No endpoint returns an unbounded graph.
- Divergent heads are surfaced (marker + per-head edge attribution), never silently resolved by arrival order, in the graph exactly as in the object model.
- The §4 budgets (100k notes / 1M edges; 50 ms local / 250 ms global p95 store-side; 2,000 default / 5,000 hard visible-node cap) are acceptance criteria, not aspirations; the §4 degradation order is the only permitted response to exceeding them.
- Live deltas are an optimisation over re-queryable state; a viewer who misses every delta and re-queries converges to the same bounded subgraph for the same store state and filter set.
- Presence, layout, and filter sets are view state — none of them is ever written back as a graph fact.
