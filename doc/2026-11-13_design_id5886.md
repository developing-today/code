# Design: service-held keys — key custody variant (a) for `id`

- Date: 2026-11-13
- Status: **decision-ready proposal** — design only; no custody code is implemented here.
- Issue: [#5886](https://github.com/developing-today/code/issues/5886), parent design [#5684](https://github.com/developing-today/code/issues/5684), programme epic [#2056](https://github.com/developing-today/code/issues/2056).
- Parent decisions consumed, not re-decided: identity is a keypair (iroh-style; the public key is the identifier, no central registry mints or revokes it); simplicity-first is a hard requirement and login UX must be indistinguishable from ordinary logins; custody honesty (for every variant, state who can sign as the user, who can lock them out, who can recover them); the signed-hash setup artefact is the acceptance root; issuer rotation and compromise recovery mechanics belong to [#2804](https://github.com/developing-today/code/issues/2804) and are inputs here. Sibling records consumed: variant (b) user-held keys ([#5887](https://github.com/developing-today/code/issues/5887), `doc/2026-11-10_design_id5887.md`) and variant (c) security codes ([#5888](https://github.com/developing-today/code/issues/5888)). The one place this design touches a parent question is flagged in §8 (it answers the parent's "should variant (a) exist at all" question; it does not change any parent decision).
- Splits: none filed from this design. The implementation follow-ons are named in §10 as queue-ready scopes; filing them is the parent's decomposition bookkeeping, and this issue's acceptance is the recorded decision, not new tickets.

## Decision to make

In custody variant (a), where does the user's key live, who can cause it to sign, what does the signing audit guarantee (and not guarantee), and how does a user later migrate out to a self-held key — given that the service holds the key, and that a non-technical user must be able to walk every flow?

## Recommendation

**The service holds the key inside a non-exportable hardware-backed signer, signs only on an authenticated user's request, and writes every signature to an append-only, user-visible audit log. Variant (a) is the default on-ramp, disclosed in plain language, and migration out is a key rotation to variant (b) under the #2804 mechanics — never a new identity.** Concretely:

1. **The key never exists outside the signer.** The keypair is generated inside an HSM/KMS-backed signing service and is non-exportable: there is no API, admin path, backup format, or support flow that returns the private key in any form. The service exposes exactly one key operation: "sign this artefact for this authenticated user." (§2)
2. **Authentication gates signing; step-up gates sensitive signing.** An ordinary authenticated session (Google / OIDC / username-password — the same login as every other variant) may request day-to-day signatures, which in practice means issuing and using scoped pseudo-login delegations (variant (d) of #5684), so the root key signs rarely. Sensitive operations — key rotation (migration out), delegation widening, recovery changes — require a fresh step-up authentication. (§4)
3. **Every signature is audited, and the audit is the user's, not just the operator's.** Each signature appends a hash-chained record (time, authenticated account, device/client, artefact hash, delegation scope) to an append-only log the user can view and export at any time, with alerts on sensitive signatures. The audit **detects** signing the user did not intend; it cannot **prevent** the service from signing — §5 states that plainly instead of overselling the log. (§3)
4. **The honesty statement is part of the product, shown at setup in one screen:** the service can sign as you; the service can lock you out; the service can recover you. A user who does not accept that shape is offered variant (b) at the same setup step, not buried in settings. (§5)
5. **Migration out is a rotation, available from day one.** The user generates a self-held key (variant (b) blob flow), the service signs the #2804 rotation statement naming the successor key on the user's step-up-authenticated request, and the service key is then retired: it refuses all further signatures. The identity's history and the audit chain make the handover verifiable by relying parties. (§6)

## §1 Roles and artefacts

| Party                         | Holds                                                                                          | Never holds                                                                                     |
| ----------------------------- | ---------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Signing service (HSM/KMS)     | The private key, non-exportable, inside the signer boundary; the signing policy per identity   | An export path for the key; the user's login password                                           |
| Login / authorizer service    | The account record, the public key, the signed-hash setup artefact, the audit log (§3)         | The private key; any ability to invoke the signer except through the authenticated request path |
| User's client (app / browser) | Nothing key-shaped in this variant — session tokens and delegation artefacts only              | The private key (that is the definition of this variant)                                        |
| Relying parties / worlds      | The public key, delegation and rotation artefacts they verify against                          | Any key material                                                                                |
| Service operators (humans)    | Operational control of the service (deploy, config, account administration under dual control) | A way to sign as a specific user outside the audited request path                               |

Two consequences are load-bearing and must survive implementation unchanged:

- **Custody is the trust shape, not a bug to be mitigated away.** Every mitigation in this record (HSM, audit, step-up, dual control) narrows _who inside or outside the service_ can abuse custody or makes abuse visible. None of them changes the headline fact of §5: the service, as a system, can sign as the user. Any implementation or copy that blurs that fact fails this design.
- **Separation inside the service is real or the audit is theatre.** The request path that invokes the signer must be the only path; operators administer the service through a separate plane that cannot mint an authenticated user request. If an operator action can produce a signature, that action must itself appear in the user's audit log as an operator-initiated signature — there is no silent path. (§3, §7)

## §2 Custody architecture

- **Generation and storage.** One keypair per identity, generated inside the HSM/KMS boundary at setup (§4.1), marked non-exportable at creation. Per-identity keys (never a shared service signing key): compromise, retirement, and migration are per-user operations.
- **The signing interface.** The signer accepts (identity, artefact hash, signature context) and returns a signature. It enforces the per-identity policy recorded at setup: which request classes are ordinary vs step-up (§4), and whether the key is retired (§6). Policy changes are themselves sensitive operations.
- **Backups are signer-to-signer only.** Key backup/replication, where the HSM vendor supports it, is wrapped key material moving between signer boundaries. There is no plaintext or password-wrapped export "for backup purposes" — an exportable backup is an export, and §5's statement would become false.
- **Availability is a custody property.** Because the service can lock the user out (§5), signer availability, account-recovery availability, and a published data-export path (public artefacts + audit log) are part of the custody design, not operational afterthoughts.
- **What the service stores besides the key:** the account↔identity binding, the setup artefact, delegation records, the audit log, and the key's policy/retirement state. All of it is public-artefact or metadata material; none of it helps an attacker sign without the signer.

## §3 The signing audit

- **Append-only, hash-chained.** Each record commits to the previous record's hash, so post-hoc deletion or reordering of entries is detectable by anyone holding an earlier state (the client pins the latest chain head it has seen; the user-visible export includes the chain).
- **Record contents:** timestamp; identity; artefact hash and artefact class (setup, delegation issue/renew/revoke, rotation, recovery change, other); authenticated account and session age (ordinary vs step-up); client/device label as presented at login; delegation scope where relevant; operator-initiated flag where relevant (§1).
- **User visibility.** The activity view (shared with the variant (d) delegation management view) shows signatures in plain language ("Signed a sign-in for a new device", "Approved a key change"), newest first, exportable in full. Sensitive classes (rotation, recovery change, delegation widening) additionally push an out-of-band alert (email/push) at signing time.
- **Stated limits.** The log is detective, not preventive: a signature the service chose to make is valid the moment it exists, whether or not it is logged, and a compromised service could sign without logging — the chain makes _later tampering with what was logged_ evident, and an unlogged signature discovered in the wild is itself proof of compromise, but neither property unmakes a signature. Recovery from a rogue signature is revocation/rotation under #2804, plus this log as the evidence trail. Copy and docs must say this; "audit log" must never be presented as "the service cannot sign without your knowledge" in a way that implies prevention.

## §4 Flows

### 4.1 First-time setup

1. User chooses "Sign in with Google" (or username/password) and authenticates — ordinary, nothing key-shaped is shown.
2. The service generates the keypair inside the signer (§2), signs the setup artefact (statement: hash over public key ‖ account binding ‖ creation time ‖ "id setup v1" domain separator), and records the per-identity signing policy.
3. The user sees the one-screen custody disclosure (§5's three sentences, in plain language) with two buttons: "Continue — the service holds my key" and "Hold my own key instead" (variant (b) setup). Choosing (a) is one tap; the choice is recorded in the setup artefact's context so later claims of uninformed consent are checkable.
4. The client is issued the first scoped pseudo-login delegation (variant (d)); day-to-day use proceeds exactly as in every other variant. User-visible novelty over an ordinary sign-up: the single disclosure screen.

Note the honest difference from variant (b): there, the setup artefact is signed by a key the user holds, proving the user's custody from the first artefact. Here the artefact is signed by the service-held key on the authenticated user's behalf — it proves continuity of _the identity_, and its trust root is the service's custody claim, which is exactly what §5 discloses.

### 4.2 Everyday login and signing

Identical surface to the other variants: ordinary login; the live pseudo-login delegation does day-to-day work; the root key is invoked only for delegation issuance/renewal and sensitive operations. The user never sees a key, a hash, or a signing prompt for routine actions (simplicity-first); the signatures they cause appear in the activity view (§3).

### 4.3 Sensitive operations (step-up)

Rotation/migration (§6), delegation widening, recovery-method changes, and custody-variant changes require step-up authentication (fresh login factor, not just a live session) and produce an audit alert (§3). A session hijack therefore yields day-to-day misuse bounded by the live delegation's scope — bad, and auditable — but not identity takeover via rotation. This bound is the main thing step-up buys, and it is worth stating in the record because it is the difference between "account compromise" and "identity compromise" in this variant.

### 4.4 Account recovery

Recovery is ordinary service account recovery (the login provider's recovery, or the username/password reset flow), after which signing resumes. This is the variant's genuine convenience advantage and its stated risk in the same breath: whoever completes account recovery controls the identity. Variant (c) codes may additionally be registered as a step-up factor for sensitive operations, but they are not the recovery root here — making them the root would silently convert the user to a (c)-shaped recovery model; the setup copy must not imply otherwise.

## §5 Custody honesty — who can sign, lock out, recover

Plain-language statements, suitable for user-facing copy at setup (§4.1 step 3):

- **Who can sign as you:** "The service can sign as you. When you are signed in, it signs only what you ask it to, and every signature is recorded in your activity. If the service itself were compromised or acted against you, it could sign without asking — the record would show it afterwards, but the signature would be real."
- **Who can lock you out:** "The service can. If your account is suspended, deleted, or the service shuts down, you cannot sign until access is restored or you have migrated out (§6). Nobody else can lock you out."
- **Who can recover you:** "The service can, through ordinary account recovery (§4.4). If you lose your login, support processes can restore your access — the same process an attacker would target, which is why sensitive changes ask for a fresh sign-in (§4.3)."

Comparison anchor (for the parent's synthesis, not re-decided here): in variant (b) the answers are "only you / nobody but you / nobody"; in variant (a) all three answers name the service. That is the whole trade, and it is why (a) is offered with a disclosure and an exit, not as a silent default with no alternative.

## §6 Migration out to self-custody

- **Mechanism: rotation, not a new identity.** Migration uses the #2804 rotation construction: a rotation statement signed by the current (service-held) key naming the successor public key, after which relying parties accept the successor as the identity's current key and the setup/rotation chain as its history. The identifier's continuity artefact is the signed chain, as in #2804; the user keeps their name, artefacts, and delegations' provenance.
- **Flow:** (1) the user runs variant (b) setup client-side, generating the new keypair and its encrypted blob (no service involvement); (2) signed in with step-up authentication (§4.3), the user submits the successor public key; (3) the service signs the rotation statement and records it; (4) the service key's policy flips to **retired**: the signer refuses all further signature requests for it, permanently; (5) the user verifies the new key controls the identity (one client-side signature checked against the rotation record) before the flow reports success. The audit log shows the whole handover, and the alert for the rotation fires at step 3.
- **Properties stated plainly:** migration is one-way per rotation (going back to service custody is a second rotation to a new service-held key, not an un-retire); a user who migrates out _before_ any compromise is fully out — the retired key can sign nothing further; migration cannot retroactively fix a compromise that already happened (a rogue signature or a rogue earlier rotation is a #2804 compromise-recovery case, and the audit log is the evidence).
- **Migration in (b → a)** is the same construction in reverse (successor key generated in the signer, rotation signed by the user's held key) and must be offered with the §5 disclosure shown again — custody is being given up, and the record of that choice matters.
- **Lockout escape hatch:** because the service can lock the user out (§5), migration must remain available to any account in good standing without support involvement; an account that cannot authenticate cannot migrate — stated here so the parent synthesis does not later describe migration as a lockout remedy. It is a remedy for _anticipated_ distrust, not for lost access.

## §7 Threat model

| Threat                                                       | Effect in this variant                                                                                             | Mitigations in this design                                                                                                                                          |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Signing service compromise (attacker reaches the signer)     | **Identity compromise for every (a) user**: attacker can sign as any of them. This is the variant's defining risk. | HSM non-exportability bounds key _theft_ (signing oracle abuse remains); §3 audit as evidence; #2804 recovery. Detection and response, not prevention — §5 says so. |
| Login/account takeover (attacker completes the user's login) | Day-to-day signing within live delegation scope; sensitive ops blocked without step-up (§4.3).                     | Step-up for sensitive classes; audit alerts on sensitive signatures; delegation scoping via variant (d).                                                            |
| Malicious or coerced operator / insider                      | An operator who can forge an authenticated request can cause signatures.                                           | §1 separation of planes; dual control on account administration; operator-initiated signatures are flagged in the user's own log; no silent path.                   |
| Legal compulsion against the service                         | The service can be compelled to sign or to deny service; the user may not be notified where law forbids it.        | None available inside this variant — stated as a fact of the custody shape; migration out (§6) is the pre-emptive remedy.                                           |
| Service shutdown / account suspension                        | Lockout (§5) for users who have not migrated.                                                                      | Published export of public artefacts + audit; migration available without support involvement while the account stands.                                             |
| Phishing at the login surface                                | Same as ordinary logins everywhere; yields a session, bounded as in the account-takeover row.                      | Nothing variant-specific; the login UX is deliberately ordinary (parent requirement), so platform anti-phishing applies unchanged.                                  |

## §8 Where this touches a parent question

The parent's open questions ask whether variant (a) should exist at all, given it concentrates compromise risk, or whether refusing it simply excludes the users who need it most. This record answers: **it exists, as the default on-ramp, because the alternative is that convenience-first users — the majority of ordinary people — either never adopt `id` or adopt it through an unofficial custodian with none of §2/§3's discipline; the concentration risk is answered with honesty (§5), an audited and bounded custody shape (§2–§4), and a real exit (§6), not with denial.** Everything else in this record stays inside the parent's fixed decisions; nothing here changes variant (b), (c), or (d), the setup-artefact construction, or #2804's mechanics.

## §9 Invariants implementation must hold

1. No code path returns the variant-(a) private key, in whole, wrapped-under-a-user-secret, or reconstructable, from the signer boundary — including backups, exports, debug, and support tooling.
2. Every signature the signer produces is written to the §3 audit log with its class and authentication context, or the signing request fails; operator-plane actions that cause signatures are flagged as operator-initiated in the user's log.
3. Sensitive signature classes (§4.3) require step-up authentication recorded in the audit entry; a live ordinary session alone never suffices.
4. A retired key (post-migration, §6) refuses all signature requests; retirement is irreversible in the signer policy.
5. The §5 disclosure is shown, and the user's choice recorded, before the first signature is ever produced for a variant-(a) identity.
6. Migration out (§6) completes without support involvement for any account that can step-up authenticate, and ends with a client-verified successor-key signature before reporting success.
7. Day-to-day operation uses scoped pseudo-login delegations (variant (d)); the root key is not invoked for routine actions.

## §10 Alternatives rejected

- **Refuse variant (a) entirely.** Rejected for the reason in §8: it excludes exactly the convenience-first users the parent's simplicity-first requirement centres, and custody would reappear unofficially without the audit or the exit.
- **Service stores a password-wrapped key and unwraps it server-side at sign time.** Rejected: the server transiently holds the plaintext key at every signing, conflates the login password with key custody (the failure mode the variant-(b) record names), and inherits the worst of both variants — service-side exposure _and_ a user secret whose loss is unrecoverable — while marketing itself as self-custody.
- **Exportable keys in an encrypted database (no HSM).** Rejected: "encrypted at rest" with the decryption key held by the same service is exportability with extra steps; one database-plus-config compromise takes every key, silently and permanently, where an HSM bounds the same compromise to a signing oracle whose use is auditable.
- **Threshold / MPC split custody (service share + user-device share).** Rejected _for now_, not forever: it genuinely improves the compromise story, but every flow gains a co-signing device dependency that breaks the parent's "login indistinguishable from ordinary logins" requirement for users who lose the device, and it is a different variant, not a variant of (a). Recorded as the known hardening direction if (a)'s risk profile needs revisiting.
