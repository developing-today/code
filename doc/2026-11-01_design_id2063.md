# Design: ID conversion engine — linked transfer pairs and rate authorisation

- Date: 2026-11-01
- Status: **decision-ready design** — no implementation is included in this PR.
- Issue: [#2063](https://github.com/developing-today/code/issues/2063), under #2056.
- Feeds: the currencies v1 synthesis [#2043](https://github.com/developing-today/code/issues/2043).
- Depends on: the currency registry, account factory, and single-writer gateway in
  [#2062](https://github.com/developing-today/code/issues/2062); the later
  issuance/graph model in [#2041](https://github.com/developing-today/code/issues/2041).
- Existing follow-ons: [#2289](https://github.com/developing-today/code/issues/2289)
  (executor/recovery PoC) and [#2290](https://github.com/developing-today/code/issues/2290)
  (RateAuthorisation design), with implementation packets
  [#3800](https://github.com/developing-today/code/issues/3800),
  [#3801](https://github.com/developing-today/code/issues/3801), and
  [#3802](https://github.com/developing-today/code/issues/3802).

## The decision

Build v1 conversion as one application-authorized, **single TigerBeetle linked
chain** containing the source-ledger debit/LP credit, an optional separately
audited source-ledger fee leg, and the destination-ledger LP debit/user credit.
Submit all legs together; never implement a conversion as two independent
transfers. Persist an intent and every transfer ID before submission. Make the
conversion record the recovery authority, and use one opaque 128-bit
`conversion_id` in every leg's `user_data_128` field.

The engine consumes the graph-event offer, gateway verification, revocation,
and quote contract now recorded by #2290 and split into #3800–#3802; it does not
define a second schema. It supports ledger-anchored conversions only. A
conversion is admitted at the durable-intent transaction: the offer must be
live then, and a later expiry or revocation does not invalidate an already
admitted intent. A posted conversion is immutable; correction is a new
authorized conversion, never a rollback.

```mermaid
sequenceDiagram
  participant U as Caller
  participant G as Single-writer gateway
  participant C as Control plane
  participant T as TigerBeetle
  U->>G: signed convert request + client idempotency ID
  G->>C: verify caller, offer/quote, cap; reserve cap; persist intent + leg IDs
  G->>T: one linked chain [source, fee?, destination]
  alt all legs succeed
    T-->>G: all posted
    G->>C: mark POSTED; commit cap; write receipt
  else definite linked-chain rejection
    T-->>G: leg error + linked_event_failed
    G->>C: mark FAILED_ATOMIC; release reservation
  else lost response / crash
    G->>C: recovery looks up the exact persisted leg IDs
    alt every leg exists
      C->>C: mark POSTED; commit cap
    else none exist
      C->>T: resubmit the identical chain with identical IDs
    else partial or conflicting result
      C->>C: quarantine; alert; never report success or retry blindly
    end
  end
```

## Context and evidence

The issue premise is that TigerBeetle has no native cross-ledger conversion;
the #2040 investigation says a conversion is two atomically linked,
same-ledger transfers through an LP's accounts, with the application computing
the rate and stamping the association in `user_data_128` (#2063 body; #2063
design-result comment; #2040 investigation result). The #2063 intake review
identifies mid-pair failure as the key risk and asks for an explicit recovery
invariant. This note settles that invariant below.

The newer #2041 investigation formalizes the graph boundary: a rate offer is
per ordered pair and direction; an offer may come from an issuer or any liquidity
holder; execution references a specific offer version/frontier; the Conversion
Receipt records the offer and both leg references; and #2290 owns the exact
RateAuthorisation schema, revocation set, and quote binding (#2041 §§2, 6; in
particular lines 112–125 and 246–284). The same report says graph-native swaps
are honestly non-atomic (#2041 §6, lines 271–277), so this engine is for the
ledger-anchored binding only. The still newer #2290 design record makes the rate
offer an ordinary signed `currency.rate_authorisation` chain event, binds
`issuer_id` to the event's verifying key, and specifies a versioned fold,
issuer-signed revocation, and a 60-second quote pinned to event hash/version
(#2290 [design-record comment](https://github.com/developing-today/code/issues/2290#issuecomment-6560877718),
2026-11-01). This note follows that decision.

The current control-plane design is the execution boundary: the gateway is the
only TigerBeetle writer, verifies request signatures and registry authority,
and uses the account factory (#2062 §§3–4). It also currently labels the shared
`liquidity` accounts unconstrained (#2062 §3.2, lines 239–258); that is not
sufficient to enforce a hard inventory floor under concurrent conversions.
The account contract required by this design is made explicit in §2.3.

## 1. Viable options and trade-offs

### Settlement and failure model

| Option | Trade-off | Decision |
| --- | --- | --- |
| One linked chain in one TigerBeetle batch | Atomic across the source and destination legs; a failed leg fails the chain. Requires one gateway to build and submit the complete chain. | **Recommend.** Matches #2040 and the #2063 acceptance criteria. |
| Two independent posted transfers, then compensate on failure | Creates a real interval with only one side posted. A compensating transfer can itself fail if funds have moved. | Reject for conversion settlement. A posted conversion is corrected by a new conversion, not a presumed rollback. |
| Two separately orchestrated pending/two-phase flows | Each hold has its own lifecycle, but there is no atomic commit across the two ledgers; it reintroduces a split outcome. | Exclude from v1. A delayed-finality conversion needs a separate failure-matrix design. |

### Conversion identity and ledger linkage

| Option | Trade-off | Decision |
| --- | --- | --- |
| Put the 128-bit `conversion_id` in `user_data_128`; receipt and control-plane record both carry it | Directly reconstructs the leg group without packing other fields. The ledger does not directly contain a full graph-object hash. | **Recommend.** Matches the pinned #2063 approach and the later #2041 receipt carrying a conversion ID. |
| Put a graph-object identifier directly in `user_data_128` | Conflicts with the 128-bit field if the graph identifier is a full content hash; truncation can collide. | Reject unless the wire contract explicitly defines a collision-safe 128-bit ID. Do not silently truncate. |
| Pack offer, rate, or party data into `user_data_128` | Loses space and makes decoding/versioning fragile. | Reject. These fields belong in the receipt and conversion record. |

The #2062 general write-path note says to stamp the signed graph-object ID in
`user_data_128` (§7.1); #2041 §1 repeats that general rule while §6 says both
conversion legs carry a conversion ID; #2063 §5 also specifies a u128
`conversion_id`. The sources do not say these identifiers are equal, and
`pkgs/id` event IDs are BLAKE3 digests of canonical bytes. Recommendation:
`user_data_128` is the dedicated 128-bit `conversion_id`; the Conversion Receipt
contains that ID and both leg references, while the control-plane index maps it
to the complete receipt event ID. Do not truncate or conflate them. The #2043
synthesis must reconcile this conversion-specific mapping with #2062's generic
write-path rule before permanent implementation.

### Rate-authority and LP eligibility

| Option | Trade-off | Decision |
| --- | --- | --- |
| Signed `currency.rate_authorisation` chain event, folded into gateway state | One auditable issuer-signed offer is discoverable in the graph; gateway materializes it for fast checks. | **Recommend; settled by #2290 and #2041.** The graph event is authority, not a TigerBeetle feature. |
| Detached control-plane-only rate record | Easier to query, but splits the offer's authority/audit story from the graph and requires a second canonical record. | Reject; #2290's latest record rejects a detached DB object. |
| TigerBeetle-side authorization | Would appear close to settlement, but TigerBeetle has no identity/auth layer and the offer schema belongs to ID. | Reject; the gateway enforces policy before ledger submission. |
| Currency issuer is the only possible LP | Simple default, but excludes a separate funded liquidity holder. | Reject as a global restriction; #2041 §6 allows an issuer or any registered liquidity holder. |
| Issuer or registered/funded liquidity holder, with no inventory check | Flexible, but permits signed offers against accounts the LP does not control or fund. | Reject. Eligibility must bind the event author to both LP accounts and enforce destination inventory in the ledger. |
| Issuer or registered/funded LP with account binding and constrained inventory | Supports issuer offers and independent LPs, while keeping authority and available liquidity separately verifiable. | **Recommend.** A platform LP uses the same registered/funded path; it gets no bypass tier. |

## 2. Recommended contract

### 2.1 Accounts and legs

For caller `U`, source currency/ledger `X`, destination `Y`, and LP `P`:

| Leg | Debit → credit | Ledger | Link flag |
| --- | --- | --- | --- |
| Source principal | `U_X → P_X` | `X` | linked |
| Optional fee | `U_X → fee_X` | `X` | linked |
| Destination | `P_Y → U_Y` | `Y` | final / unlinked |

All legs are one ordered linked chain in one TigerBeetle submission. `X` and
`Y` remain distinct ledgers; no transfer has accounts on different ledgers.
The optional fee is a separately visible source-currency leg, not hidden in the
rate. A quote records `source_principal`, `source_fee`, and `destination_amount`
so the caller can see the total source debit before signing. A zero destination
amount after rounding is rejected, not treated as a free conversion.

`user_data_128` on every leg is the same opaque 128-bit `conversion_id`; use
distinct transfer IDs per leg. The transfer `code` identifies each role
(`conversion_source`, `conversion_fee`, `conversion_destination`) within the
reserved conversion range in #2062 §4.4. The durable conversion record and
Conversion Receipt contain the full offer/version, parties, accounts, amounts,
scale snapshot, leg IDs, fee, and any `reversal_of` reference. The 128-bit
identifier is unique in the control-plane store; it is not a truncated hash.

### 2.2 Rate, rounding, quote, and authority

- One offer is one ordered direction; the reverse direction requires a distinct
  offer and its own rate. Offerer may be the currency issuer or another
  registered liquidity holder (#2041 §6, lines 255–262).
- Rates are exact positive integer rationals, never floating point. For a rate
  `rate_num / rate_den` expressed as destination major units per source major
  unit, source raw amount `x`, and ledger scales `sX` and `sY`, compute:
  `y = floor(x * rate_num * 10^sY / (rate_den * 10^sX))`.
  Use checked/reduced integer arithmetic with a sufficiently wide intermediate;
  reject overflow, invalid scale, zero output, and amounts outside the offer's
  min/max. The rounding remainder stays with the LP, as in #2040 §2 and the
  #2063 design-result comment.
- #2290 owns the canonical `currency.rate_authorisation` event, signature
  identity, version/revocation fold, gateway projection, and quote binding
  (#2290 design-record comment, 2026-11-01; #2041 §6, lines 248–284). The
  event's `issuer_id` must equal its verifying key; the control plane binds that
  LP identity to its source and destination inventory accounts. The engine
  takes an exact offer event hash/version and quote; it must not create a rival
  schema. The quote pins that event hash/version, ordered currencies, caller,
  source amount, computed destination amount, fee, and expiry; #2290 adopts a
  60-second lifetime. Its gateway-issued record includes quote ID,
  authorisation ID/version/event hash, amounts, fee, and issue/expiry times;
  revalidate live offer state at admission, not merely when displaying a quote.
- Total-cap units are source-ledger raw units, as the newer #2290 schema
  decision specifies. The conversion reserves the source principal, not the
  separately disclosed fee, against that cap. Per-conversion min/max use the
  same source-unit convention.
- If the offer includes `fee_bps`, compute and quote the fee from the source
  principal in source units as `floor(source_principal * fee_bps / 10_000)`, then
  submit it as the separate source-ledger fee leg. If absent, fee is zero. If
  `reversal_window_secs` is absent or elapsed,
  a correction uses a then-current valid offer; any fee refund must be explicit
  in the reversal terms and remains a separate auditable leg.
- Before admitting an intent, the gateway verifies the standard signed request,
  resolves the request key to its account, checks the caller is an eligible
  taker, checks the LP offer event's author key equals its `issuer_id`, resolves
  that LP to its registered accounts, and verifies the offer is the latest valid
  version at the offerer's current chain frontier, unrevoked, unexpired, and
  within per-transaction and total caps. The offer signature is verified on the
  signed chain event; group-scoped device delegation alone is not an LP
  authorization.
  The durable intent transaction is the **admission point**. Expiry/revocation
  after that point blocks new intents but does not invalidate an already
  authorized in-flight intent or its recovery retry.
- Reserve total-cap capacity in the same control-plane transaction that stores
  the intent. Commit the reservation only when the chain is confirmed posted;
  release it on a definite atomic failure; retain it while submission outcome is
  ambiguous. This prevents concurrent requests from over-consuming a cap and
  makes recovery deterministic. The single logical writer remains mandatory
  (#2062 §4.5, lines 391–398).

### 2.3 Liquidity-provider eligibility and inventory

An LP is the `issuer_id` key that signed the offer event, bound by the control
plane to its LP identity and source/destination accounts. An LP may be a
source/destination issuer or any registered liquidity holder, in line with the
later #2041 decision. Before admission, verify both currency accounts are the
deterministic accounts for that LP, active, and not closing/closed. The caller
must control the source holder account; the destination holder is the same
account identity resolved for the request. `pkgs/id` can resolve public keys
that belong to an account, but currency policy must explicitly decide which
account-bound keys may act; do not infer currency authority from group device
delegation.

Do not rely on a balance read followed by a write to protect inventory. #2062
currently calls the shared liquidity account unconstrained. For conversion
inventory, recommend a dedicated per-(currency, LP) account kind with
`debits_must_not_exceed_credits` and history enabled, or an explicit change to
the existing liquidity-account flags. The destination LP account's cluster-side
debit constraint is authoritative under concurrent submissions; a preflight
balance read is only for a clearer error. The source holder and fee accounts
also retain their debit constraints. The account-factory owner must reconcile
this adjustment with #2062 before production implementation; no unconstrained
account may be treated as a hard inventory guard.

### 2.4 Intent state and failure semantics

Before the first TigerBeetle call, persist a unique request key and an intent
containing the `conversion_id`, all transfer IDs, all amounts/accounts/ledgers,
offer ID/version/frontier, quote, cap reservation, and caller. Transfer IDs are
chosen once and never regenerated on retry. The latest #2041 decision requires a
client-generated idempotency ID to be persisted before submission; a retry with
the same key returns the existing conversion, while an `exists_with_different_*`
result is a hard conflict (#2041 lines 322–326). The exact transfer-ID
generation strategy must also honor the TigerBeetle guidance; #2062 §9 leaves
hash-vs-monotonic generation open, so recommend a durable monotonic allocator
for transfer IDs and resolve it in the gateway implementation packet, not by
hashing an ID after a crash.

| Case | Required outcome |
| --- | --- |
| Invalid signature, caller, offer, quote, expiry, revocation, cap, scale, or amount | Reject before TigerBeetle; no intent or ledger change (except a stored terminal rejection if needed for request idempotency). |
| Insufficient source funds, fee funds, or destination LP inventory | One linked chain fails atomically; persist typed failure and release cap reservation. The cluster-side account flags are the balance guard. |
| Definite linked-chain leg failure | No legs move. Persist `FAILED_ATOMIC`, original leg error, and `linked_event_failed` for dependent legs; release reservation. |
| Process crash or lost response | Recovery reads the exact stored leg IDs. All present and matching the intent → `POSTED`; none present → retry the identical chain/IDs; partial presence or mismatched data → quarantine and alert as an invariant violation. Never create fresh IDs or claim success from an ambiguous result. |
| Offer expires/revokes after durable admission | Existing intent may finish/recover under its recorded offer snapshot; new intents are rejected. This gives expiry/revocation a clear linearization point. |
| Conversion has posted and a correction is needed | Do not delete, mutate, or claw back the posted transfer. Submit a new conversion referencing the original. Use the original rate only if its signed terms permit a reversal window; otherwise use a currently valid offer. Any refund of fees must be explicit in the quote/offer. |

State transitions are monotonic: `PREPARED → SUBMITTED → POSTED` or
`PREPARED/SUBMITTED → FAILED_ATOMIC`; uncertain results remain recoverable, not
terminal. The core invariant is: **no TigerBeetle write without a persisted
intent and fixed leg IDs; no successful partial conversion; no silent loss of
an admitted conversion; no rollback of a posted conversion.**

## 3. Invariants and implementation acceptance

Implementation is acceptable only when all of the following hold:

1. One conversion is one TigerBeetle batch with all source, optional fee, and
   destination legs linked in order. Any definite failure has no balance effect.
2. Every leg carries the same `conversion_id` in `user_data_128`, a role-specific
   transfer code, and a distinct persisted transfer ID. The receipt/control-plane
   record can reconstruct every leg without decoding packed fields.
3. Callers, LPs, and authorized takers are checked through the gateway's signed
   request/account authorization path; a valid signature alone never grants
   conversion rights (#2062 §4.2, lines 332–348).
4. Expiry, revocation, offer version, taker scope, min/max, and total caps are
   checked at admission. Cap reservation is concurrency-safe, survives crash,
   and is committed/released only after a definitive ledger outcome.
5. Inventory cannot be overspent under races: conversion LP debit accounts are
   cluster-constrained. A read-then-write check against an unconstrained LP
   account does not pass acceptance.
6. No floating-point operations touch amounts/rates. Tests cover scale pairs,
   exact division, rounding remainder, integer overflow, amount limits, fee math,
   and the zero-output case.
7. A repeated request with the same client idempotency ID produces the same
   conversion and leg IDs. A conflicting reuse is a typed hard error.
8. Fault-injection tests cover a crash before submit, response loss after submit,
   restart during recovery, all IDs present, no IDs present, and unexpected
   partial/mismatched ledger state. No ambiguous outcome is silently retried
   under new IDs.
9. Tests prove expiry/revocation before admission rejects; expiry/revocation
   after admission does not strand the intent; a concurrent total-cap race
   cannot exceed the cap; and concurrent LP spends are rejected by TigerBeetle.
10. Posted conversions are immutable. Reversal is a separate conversion and
    receipt that references the original; two-phase conversion and graph-native
    atomicity are not claimed.
11. The conversion receipt contains the exact offer version, both leg references,
    conversion ID, and outcome, consistent with #2041's object model. Reconcile
    the conversion-ID vs graph-object-ID linkage with #2062 before production.

## 4. Phased implementation plan

Each phase is a separate reviewable PR and can merge independently behind an
unused interface or disabled route. Dependencies are explicit; no permanent
feature is promoted from a PoC without the review round required by #2056.

| Phase | Mergeable deliverable | Depends on / existing issue | Done when |
| --- | --- | --- | --- |
| A. Rate event and fold | Implement the signed `currency.rate_authorisation` event, version fold, issuer-signed revocation event, and golden cases. | #3800, owned by #2290. | Latest non-revoked version and event author/`issuer_id` binding are tested. |
| B. Gateway authorization | Materialize and check the current offer, LP account binding, eligible taker, expiry, caps, and revocation before creating an intent. | #3801; depends on A and #2062 gateway/account interfaces. | Wrong issuer key, wrong LP accounts, unauthorized taker, stale version, expiry, and revocation fail before TigerBeetle. |
| C. Quote issue and bind | Issue the 60-second gateway quote pinned to offer ID/version/event hash and exact amount/fee fields; revalidate live offer state when the conversion request is admitted. | #3802; depends on A and B. | Altered, stale, or expired quote cannot be executed; exact quote execution is idempotent. |
| D. Account and ledger contract | Define conversion-specific LP inventory accounts/flags, role transfer codes, durable `conversion_id` mapping, and receipt linkage. Resolve #2062's unconstrained-liquidity and graph-ID-vs-128-bit-field tensions. | #2062 account factory and gateway; feed the decisions to #2043. | Deterministic constrained inventory accounts cannot be overdrawn; every ledger conversion ID maps to the full receipt. |
| E. Pure quote and linked-batch builder | Implement scale-aware rational arithmetic, source-unit cap/fee presentation, policy validation, and ordered transfer construction with fixed IDs. No TigerBeetle or database effects in the pure layer. | A–D interfaces. | Unit tests cover arithmetic, flags, IDs, codes, and batch invariants in §3. |
| F. Durable executor and recovery | Persist the client idempotency key and intent first; reserve caps; submit one linked chain; reconcile exact IDs and resolve terminal outcomes. | A–E; #2289 is the executor/recovery PoC. Review it before using PoC code in a permanent service. | Test-cluster fault injection satisfies §2.4 and §3; no second writer can bypass the single-writer boundary. |
| G. Receipt, reversal, and operational reconciliation | Emit the #2041 Conversion Receipt; map conversion IDs to full graph/control-plane records; expose quarantined intents and reversal references to operators. | F and the #2041 graph object model; feed #2043. | A posted or reversed conversion is auditable from receipt to every ledger leg; unresolved states alert and never disappear. |

The already-open #2289 and #2290 (with #3800–#3802) cover the PoC and
authorization work. This docs-only task does not open or modify additional
issues; the currencies v1 synthesis should turn phases D–G into permanent
implementation packets after reconciling the stated #2062 integration points
and the #2056 review gate.

## 5. Open questions

### Question that genuinely needs Drew

**Q1 — May the platform emergency-revoke another LP's RateAuthorisation?** This
is inherited from the newer #2290 design record and affects which revocations
the engine must honor; the execution and recovery contract does not depend on
the ruling.

- **Option A (recommend):** only the offerer can publish a graph revocation;
  the platform may locally suspend gateway acceptance as a logged control-plane
  policy. This keeps the signed graph's authority unambiguous.
- **Option B:** add a platform-signed graph revocation event that the gateway
  also honors. This gives a stronger incident-response path but adds a second
  revocation authority all verifiers must interpret.

No other Drew decision blocks this design. Offer direction, rational rates,
expiry, and linked-pair settlement are already decided by #2063 and the newer
#2041/#2290 records.

### Engineering decisions to carry forward (recommendations recorded)

1. **Protect LP inventory:** either change `liquidity` account flags or introduce
   a conversion-specific constrained account kind. **Recommend the separate
   constrained kind** so general liquidity semantics do not silently change.
2. **What does `user_data_128` identify?** #2062's generic graph-object pointer
   conflicts with a full content hash's width and #2063's dedicated
   `conversion_id`. **Recommend the 128-bit conversion ID**, with the receipt
   carrying it and the control-plane index mapping it to the complete graph
   object; no truncated hash.
3. **Transfer-ID generation:** #2062 §9 left hashed vs monotonic IDs open;
   #2041 later requires client idempotency IDs to be persisted before submit.
   **Recommend persisted client idempotency keys plus durable monotonic transfer
   IDs**, with retry reusing the exact stored IDs.

## Non-goals

- No exchange-rate discovery, AMM, order book, best-rate routing, or competing
  LP selection.
- No cross-cluster settlement, graph-native atomic swap, or two-phase/pending
  conversion.
- No replacement for #2290's graph offer / authorization / quote schema or its
  #3800–#3802 implementation packets.
- No mutation or deletion of posted TigerBeetle transfers; reversal is a new
  conversion.
- No implementation or promotion of the #2289 PoC in this docs-only design PR.
