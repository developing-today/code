## Decision to make

How should ID represent a note/wiki page, its revisions and its topic links so that friendly names are useful to people, while the graph remains stable under renames, multiple writers and replication?

## Context and current state

ID already has signed, hash-identified events with a generic `kind`, causal `after` frontier and document/tag/removal operations (`pkgs/id/src/chain.rs:93–117,271–320`). That gives the design an immutable event substrate, but today a `document.put` is a document event, not a stable logical note with a revision lineage: document history gathers one put and its tag/removal history rather than grouping successive puts as revisions (`pkgs/id/src/documents.rs:1–23,153–165`; `pkgs/id/src/local_events.rs:374–423`). A saved document is blob-backed; the web save route publishes a signed put and a filename claim (`pkgs/id/src/web/routes.rs:1233–1264`).

The existing name and tag layers are useful but do not define the note graph. Tags are signed observed-remove claims (`pkgs/id/src/tag_claims.rs:1–13,48–64`), not typed, directed links. Alias values are claims rather than unique identities, and contested aliases are not silently selected (`pkgs/id/src/aliases.rs:1–17,146–158`). Search currently covers tag metadata and explicitly excludes full-text search (`pkgs/id/src/search.rs:1–21,72–96`). The #2047 investigation’s resolution rule is compatible: resolve within the viewer’s configured stores, show provenance and ties, and persist the stable target ID plus the chosen surface; the #2259 document is explicitly a PoC spec, not production behavior (`doc/2026-10-30T13-25-00Z_design_friendly_name_references.md:1–10,14–29,31–47,73–79`).

Live ProseMirror collaboration is currently transient server state: sessions are held in memory and keyed by filename; steps must match the session’s current version and are broadcast from that session (`pkgs/id/src/web/collab.rs:207–228,300–345,989–1056`). Save persists a document blob and signed put, but live steps are not durable graph events (`pkgs/id/src/web/routes.rs:1233–1264`). This is a useful live transport to reuse, not a replicated conflict-resolution model.

There is an important access-control boundary to preserve. Group roles distinguish `Read` and `Write` (`pkgs/id/src/groups/mod.rs:61–75`), but the event-sync handler uses an open pull gate and `id serve` does not apply per-world membership policy there (`pkgs/id/src/event_sync.rs:14–25,70–74`; `pkgs/id/src/commands/serve.rs:979–983,1012–1030`). The blob gate’s reference index has no producer and is not wired into `id serve` (`pkgs/id/src/blob_gate.rs:19–21,90–118`; `pkgs/id/src/commands/serve.rs:858–863`). The separate `world_records` projection is not a multiplayer note log (`pkgs/id/src/world_records.rs:1–14,141–156,182–199`).

Also, do not treat the #2238 writer-set/view design as a read ACL: its rule is that valid events are stored while a view counts only its configured writer set, and it explicitly distinguishes stored events from per-view counting (`doc/2026-10-30T13-15-00Z_design_id_writer_set_view_projection/2026-10-30T13-15-00Z_design_id_writer_set_view_projection.md:30–45,112–114`). The #2048 issue comment correctly separates shared-write authority from visibility, but this design makes the missing read-authorization boundary explicit.

## Viable options

| Option | Benefits | Costs / why not selected |
| --- | --- | --- |
| **1. Each `document.put` is the note.** | Reuses the document event and blob path with little new schema. | The event ID changes on save, so it cannot be the continuing note identity; history does not group puts into a note lineage. Links and backlinks cannot reliably survive edits or renames (`local_events.rs:374–423`). |
| **2. Filenames and generic tags define notes and links.** | Fits current save and tag behavior; easy to display. | Filenames are mutable locators (and currently key collab sessions); generic tag claims do not express directed, typed edges. It still leaves live edits transient (`web/collab.rs:207–228,300–345`; `tag_claims.rs:48–64`). |
| **3. Stable logical note + signed immutable revisions + typed references.** | Separates identity from revision and presentation; retains causal history; links and backlinks have explicit semantics. Reuses signed events, blobs and claim-based aliases. | Adds event kinds, projections and explicit conflict handling. Shared use must wait for a real event/blob access policy; current sync wiring does not provide it. **Recommended.** |
| **4. Sign every editor step, or make the live server session authoritative.** | Per-step events could preserve a fine-grained edit stream; session authority is initially simple. | Signing every keystroke multiplies permanent event volume; a process-local, server-sequenced session is not a replicated source of truth. Neither is needed for the first coherent multiplayer model (`web/collab.rs:207–228,989–1056`). |

## Recommendation

### Stable identity and revision history

Create a logical note with a signed `note.create` event containing or referencing its initial content; its event ID is the stable note ID and initial revision head. Each later saved snapshot is an immutable signed `note.revise` event naming that note ID, one or more parent revision IDs, and the content blob reference. Revision IDs support exact citations; note IDs are the targets for aliases and topic references. A concurrent edit creates another head. Joining heads requires an explicit signed `note.revise` naming all parents. Never select a concurrent head by arrival order or overwrite a head silently. This extends the event/hash/causal-frontier substrate rather than treating each current `document.put` as the logical note (`pkgs/id/src/chain.rs:93–117,271–320`; `pkgs/id/src/documents.rs:1–23`).

Names remain claims, not IDs: renaming a note changes its displayed alias/filename claim, never its note ID. Duplicate names are allowed; resolution returns candidates and provenance, and contested claims require a choice. This follows current alias semantics and the #2047 resolution design (`pkgs/id/src/aliases.rs:1–17,146–158`; #2048 “Decision-ready design record”; `doc/2026-10-30T13-25-00Z_design_friendly_name_references.md:14–29,62–79`).

### Typed links and local projections

Store each topic reference in revision content as a structured value: target note ID, sigil/type, authored surface, and optional pinned revision ID. The surface is presentation, not identity; a pinned revision remains an exact citation. This extends #2259’s target-ID/sigil/surface representation with an exact-revision pin (`doc/2026-10-30T13-25-00Z_design_friendly_name_references.md:12–29`). Derive backlinks from outgoing references in the active revision heads. Keep divergent-head backlinks attributable to their source head until an explicit merge; do not hide a conflict in an arrival-order projection. Generic tags remain available for labels and aliases, not as the canonical directed edge (`pkgs/id/src/tag_claims.rs:48–64`).

Build rebuildable, per-store projections for titles/aliases, topic tags, outgoing references and inverse backlinks. Resolution/search is viewer-relative and store-scoped; preserve provenance and ambiguity, and return no private target content or existence metadata to a viewer who cannot read it. Do not create a global index. Full-text search is not part of the initial packets: current search excludes it, and any later full-text index must be scoped to content the viewer is authorized to read (`pkgs/id/src/search.rs:1–21,72–96`; #2048 “Decision-ready design record”). Keep phrase resolution with #2259 rather than duplicating its PoC.

### Editing, replication and authority

Reuse the current ProseMirror collaboration session for live transport, but key a note’s collaboration room by stable note ID rather than filename. Live steps remain ephemeral; a successful checkpoint emits a durable signed revision. If concurrent or offline work produces distinct parents, retain the revisions as separate heads and require an explicit merge. This is not a CRDT or a promise of conflict-free offline editing (`pkgs/id/src/web/collab.rs:207–228,300–345,989–1056`).

Use existing group `Write` as the recommended append-authority model if Drew approves, and group `Read` as the recommended notebook visibility boundary. However, neither role should be assumed to secure note sync merely because the roles exist: before multiplayer sharing, enforce the chosen read/write policy at event and blob access boundaries. The current open event pull gate and unwired blob gate make that a concrete implementation prerequisite (`pkgs/id/src/groups/mod.rs:61–75`; `pkgs/id/src/event_sync.rs:14–25,70–74`; `pkgs/id/src/blob_gate.rs:19–21,90–118`; `pkgs/id/src/commands/serve.rs:858–863,979–983,1012–1030`). #2238’s writer-set projection is not a substitute for that policy.

For removal, recommend v1 tombstone/clear semantics with immutable history and replicated bytes retained, consistent with current `document.remove` behavior; do not label it permanent erasure. Keep cryptographic or physical erasure out of implementation until Drew decides the promise (`pkgs/id/src/documents.rs:153–165`; #2048 “Decision-ready design record”).

## Invariants and implementation acceptance criteria

- Renaming a note never changes its stable note ID; two notes may share a friendly name. A name lookup surfaces ties and provenance rather than silently choosing (`pkgs/id/src/aliases.rs:1–17,146–158`; #2048 “Decision-ready design record”).
- Every create/revision/merge event is signed and immutable; revisions identify the logical note, causal parent revision(s), and a verified content blob. Exact revision IDs remain citeable (`pkgs/id/src/chain.rs:93–117,271–320`; `pkgs/id/src/documents.rs:1–23`).
- Replicas converge on the same set of heads regardless of event arrival order. Concurrent heads remain visible until a merge explicitly names the heads it joins; no last-writer-wins behavior.
- A reference resolves by stable note ID, preserves its authored surface, and may pin an exact revision. Backlinks are a derived inverse and identify their source revision/head.
- Search, resolution, backlinks and blob fetches disclose only what the viewer is authorized to read. Ambiguous names are visible as ambiguous; inaccessible references degrade to their stored surface and an unresolved state. Do not infer access from a name search or from #2238’s view-counting projection (`doc/2026-10-30T13-15-00Z_design_id_writer_set_view_projection/2026-10-30T13-15-00Z_design_id_writer_set_view_projection.md:30–45,112–114`; #2048 “Decision-ready design record”).
- Live steps are not durable facts. A successful checkpoint creates a signed revision; a restart or another replica can reconstruct note heads and backlinks from durable events (`pkgs/id/src/web/collab.rs:207–228,989–1056`; `pkgs/id/src/web/routes.rs:1233–1264`).
- Do not claim CRDT/offline conflict-free editing. Do not expose shared content until read and write policy is actually enforced at event and blob boundaries (`pkgs/id/src/event_sync.rs:14–25,70–74`; `pkgs/id/src/blob_gate.rs:19–21,90–118`).
- Under the recommended v1 removal choice, removal is a tombstone, not guaranteed byte erasure. UI wording and acceptance tests must reflect that (`pkgs/id/src/documents.rs:153–165`).
- This is a design record only. The #2056 review round remains required before treating a PoC as a production feature, per the #2048 intake and #2259 PoC spec.

## Phased implementation plan

The issue’s latest routing comment has already filed these as separate implementation packets. Each phase is a separate mergeable change; later phases depend on the earlier data model rather than landing as one broad PR.

1. **Stable note identity and revision graph — #3814.** Add note create/revise event shapes, blob references, deterministic multi-head history and tests; a multi-parent revise is the explicit merge. Preserve existing document behavior during migration. **Done when:** a note keeps its ID across revisions; replicas derive the same heads from the same events; a concurrent branch is retained and can only be joined by an explicit merge.
2. **Local topic links and backlinks — #3816** (after #3814). Add structured stable-ID references, authored surfaces, optional pinned revisions, and rebuildable per-store outgoing-link/backlink projections. Keep resolver ownership with #2259. **Done when:** rename does not break a reference; pinned revisions remain exact; backlinks rebuild from history and expose head conflicts without silently choosing.
3. **Durable multiplayer checkpoints and merges — #3819** (after #3814 and Drew’s authority decision). Re-key live collaboration by note ID, checkpoint to signed revisions, preserve concurrent heads and support explicit merges. Before shared content is enabled, specify and enforce the read/write policy at event and blob gates; #2238 does not supply that access control. **Done when:** restart/replica reconstruction succeeds, unauthorized reads/writes fail at the access boundary, and conflicting edits are retained until an explicit merge.

The #2048 routing comment records #3819 as waiting for #3814 and Drew’s answer to the shared-write question. The access-boundary acceptance above is an additional prerequisite visible in the current source; it should be resolved in that implementation packet, not assumed complete from the writer-set view work.

## Questions for Drew

1. **What does “delete note” promise?** (a) v1 tombstone/clear, history and replicated bytes retained (**recommended**; call it removal, not erasure); (b) cryptographic erasure, requiring a per-note key and lifecycle design; or (c) best-effort physical deletion, which cannot promise removal from replicas. Keep a user-facing erase operation out of v1 unless this is settled.
2. **Who may append revisions to a shared notebook?** (a) group members with `Write` (**recommended**, provided the permission is enforced at event/blob boundaries); (b) a new per-note ACL/owner model; or (c) any group member. This is the existing #2048 Q2 and gates #3819.
3. **Who may read a shared notebook?** (a) group `Read` membership (**recommended** for v1, with an enforced read boundary); (b) per-note ACLs; or (c) public-by-default notes. The current sync/blob path does not implement this policy, and #2238’s writer-set view only determines what a view counts. Until settled and enforced, keep multiplayer content sharing disabled.

## Non-goals

- A global or ambient index; cross-store fan-out remains an explicit later query.
- Replacing or taking over the #2259 resolver PoC.
- Per-keystroke durable signing, CRDT semantics or guaranteed conflict-free offline editing.
- Guaranteed erasure of content already replicated to other peers.
- Any implementation change in this PR.
