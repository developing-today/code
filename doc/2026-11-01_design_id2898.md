# Design: reconstruction is admission in `pkgs/id`

- Date: 2026-11-01
- Status: **decision-ready design**; this note records the shared contract and implementation plan, not implementation changes.
- Issue: [#2898](https://github.com/developing-today/code/issues/2898)
- Evidence baseline: this checkout after fast-forwarding `origin/main` to `ec305bf00`.
- Source precedence: use the latest per-issue triage decisions over earlier design-agent notes. The later rulings below refine, rather than replace, the six adopted origins in #2898.

## 1. Decision to make

When `pkgs/id` rebuilds authority-bearing state from a journal, decoded object, manifest, or other persisted/supplied input, should it trust the input because its writer or signature was valid, or re-admit it against the invariants the live path enforces?

**Recommendation: reconstruction is admission.** Validate at the boundary that rebuilds the state, against canonical state already held by the verifier. Refuse invalid input; do not partially apply it or silently repair it. Use path-specific checks under one shared rule rather than inventing a generic validator: journal history, agreement semantics, schedule state, and manifest keys have different sources of truth.

The rule is limited to authority-bearing semantics. It does not require every persisted value to be re-executed or every guest payload to be understood by the host. The closing audit must identify the authority boundary and give evidence for each exemption.

## 3. Viable options and trade-offs

| Option | Benefits | Costs / failure mode |
| --- | --- | --- |
| **A. Revalidate at each reconstruction boundary under one contract (recommended)** | Uses the state available at the decision point; prevents replay, decoding, or parsing from granting more authority than live admission; keeps each predicate near its source of truth. | A few checks are intentionally repeated across mint/replay or signing/viewing paths; each needs regression coverage. |
| B. Validate only when writing or signing | Keeps reconstruction simpler and avoids repeated checks. | Journals, backups, and signed objects can be copied, corrupted, or supplied by peers; their verifier is the first place both the input and authoritative context coexist. This leaves the reported holes open (the write-time-only alternative rejected in #2898). |
| C. Repair malformed inputs or validate at downstream consumers | Can preserve availability for some old data and may appear localized. | Repair can silently widen or alter meaning; downstream consumers multiply, and no consumer can recover a missing capability author. This violates the issue’s refusal contract and risks inconsistent authorization. |
| D. Version-gate strictness or add a generic admission framework | A version gate may ease migrations; a common framework might reduce repeated code. | The affected invariants are already enforced on valid live writes, so a gate admits invalid old artifacts. A generic framework obscures domain-specific facts and does not solve missing provenance. Prefer explicit boundary predicates; add versioning only if a verified historical valid artifact requires it. |

## 4. Contract and implementation invariants

1. **Use the verifier’s ground truth.** A caller flag, an input’s assertion about its own authority, and a signed-but-malformed agreement are not substitutes for state held by the verifier.
2. **Reject rather than launder.** Invalid reconstructed state returns an error before it is exposed or applied. No partial replay, silent defaulting of an unknown authority-bearing key, or best-effort repair.
3. **Journal authorship is historical.** For Committed and Checkpoint events, accept participant 0 where the host event kind permits it; otherwise require the participant to have been issued earlier in the same journal and not revoked before that event. Check the matching scope for non-host Input/Chat. A later revocation does not rewrite earlier history. The System envelope is separately constrained to its sequence-0/participant-0 System-event shape. (#2894; `core.rs:310-363`.)
4. **Issued capabilities are valid capabilities.** Reject unnamed scope bits with `WorldScopes::from_bits` and require JOIN. Do not reject a delegate solely because its scope bits exceed the parent’s implied scopes; the effective chain intersection is the selected control. Separately, restore currently checks only parent existence (`core.rs:197-200`), while live delegation authorizes the parent first (`core.rs:755`); the closing audit must disposition a child issued after its parent was revoked. This is not the triaged parent-scope rule in #2890. Recommendation: reject the child at that journal position unless evidence establishes an equivalent control.
5. **Attestation requires two valid seats and valid positions.** Duplicate players yield `Proposed`; `sign_genesis` refuses to create such an agreement. Only the exact documented outcome domain counts toward claim slots or forks; invalid claims are ignored. Preserve `draw`, either seat’s lowercase 64-character ID hex, normal agreement, one-claim, disagreement, and genuine same-player fork behavior. (#2863, #2868; `attestation.rs:101-113`, `223-260`.)
6. **Live schedule admission matches replay.** Determine replacement by checking the schedule map in `check_schedule_replacing`; duplicate detection and the capacity discount use that same fact. Test the absent-ID-at-cap and empty-map boundaries. (#2882; `core.rs:613-637`.)
7. **Manifest strictness stays at the format boundary.** Unknown top-level TOML fields and unknown `[profile]` fields fail with the key named. Keep `WorldExecutionProfile` forward-tolerant for host JSON; test both TOML rejection and the existing host/round-trip paths. (#2876; `world_manifest.rs:147-202`, `world_limits.rs:37-58`, `commands/world.rs:1054-1061`.)
8. **Do not claim a provenance check that the format cannot perform.** Several replayed policy journal entries contain state changes but no actor/proof field (`pkgs/id/src/world/mod.rs:555-595`); restore applies them directly (`core.rs:243-275`), while live setters authorize admin operations (`pkgs/id/src/world/actor.rs:857-942`). The audit must either demonstrate an equivalent integrity/authority boundary for their stored source or record this as a remaining gap. The same check applies to directory replay: it changes capability ceilings and membership, while several entries have no actor/proof (`pkgs/id/src/directory.rs:141-245`, `500-544`, `800-821`, `1481-1495`; ceiling is used by `core.rs:793-797`).

## 5. Implementation acceptance criteria

Implementation is complete when all of the following hold:

- Every authority-bearing reconstruction seam named by this design is either checked against its authoritative state or explicitly dispositioned with evidence; an unproven trust boundary is not called safe.
- Journal restore refuses future/unknown/revoked-before authors, missing non-host kind scopes, invalid scope bits, JOIN-less capabilities, and invalid journal/event-kind pairings. Participant 0 host Chat and `ProgramInstalled`, valid historical fixtures, and later revocation of an earlier event remain accepted.
- Attestation regression tests show duplicate seats cannot reach `Agreed` or `Disputed`, signer construction refuses duplicate seats, out-of-domain claims are ignored before slot/fork accounting, and documented in-domain controls retain their outcomes.
- Schedule replacement is derived from the map; tests cover a full map with an absent ID and replacement on an empty map, with no underflow or replay-incompatible schedule count.
- Manifest TOML rejects unknown top-level and `[profile]` keys; the host JSON profile path remains forward-tolerant and existing round-trip behavior is preserved.
- The issue’s minimum regression evidence exists for journal restore and attestation, and the shared rule is documented in the world restore and attestation module docs. (`#2898`, Acceptance criteria; `world_manifest.rs:488-549` for existing manifest round-trip/unknown-key coverage.)

## 6. Phased, independently mergeable implementation plan

The phases retain the adopted origins in #2898. Each numbered item can land as its own PR; where items edit the same file, serialize or rebase the PRs rather than combine unrelated decisions. Phases 1 and 2 are independent. Phase 3 is the close-out inventory and can proceed after the overlapping `core.rs` work is rebased.

### Phase 1 — world-journal admission (`#2894`, `#2890`)

- **1a — #2894:** validate Committed and retained Checkpoint authors against prior Issued/Revoked history and required non-host scopes. Preserve host Chat and `ProgramInstalled`; constrain System-entry/event-kind shape. Add ghost, future-issued, revoked-before/revoked-after, wrong-scope, and valid-host regression cases.
- **1b — #2890:** decode restored scopes with `WorldScopes::from_bits`, require JOIN, and add unnamed-bit/JOIN-less rejection tests plus valid GUEST and BUILDER/MODERATOR controls. Retain the triaged no-parent-scope-refusal ruling; the separate revoked-parent case is dispositioned by the closing audit, not silently added to this issue’s scope.
- **Acceptance:** valid v1/v2, fork, delegate-expiry, and host-event fixtures still restore; crafted journals fail with entry context and without partial application. The relevant corpus constraint is recorded in #2898 and #2894.

### Phase 2 — attestation admission (`#2868`, `#2863`)

- **2a — #2868:** finish the in-flight outcome-domain change (PR #3508 is currently open); filter invalid outcomes before claim position/fork accounting, with lower-case/length and `draw` controls.
- **2b — #2863:** require distinct seats in `compute_state` and reject duplicate-seat agreements in `sign_genesis`; preserve the pure `MatchState` API and return `Proposed` for malformed duplicate-seat agreements.
- **Acceptance:** forged duplicate-seat and out-of-domain objects never become `Agreed` or `Disputed` by reusing one player or invalid claims; existing valid two-player controls remain unchanged. Rebase 2b after 2a because both touch `compute_state`.

### Phase 3 — aligned live admission and closing audit (`#2882`, #2876, audit)

- **3a — #2882:** remove `replacing: bool`, derive it inside the core helper, and add the capacity/underflow boundary tests.
- **3b — #2876:** already complete in PR #3493; keep the landed top-level + TOML-profile strictness and wire-lenient profile type. No duplicate implementation work.
- **3c — closing inventory:** disposition every remaining reconstruction seam as **already validating**, **fixed**, or **exempt with evidence**; record the rule in the world restore and attestation module docs. The required inventory includes sandbox snapshot restore, `world_store::restore_program`, directory replay, and petname persistence, as #2898 specifies. Also inspect the System/Committed shape, revoked-parent delegation, and policy-journal provenance noted above.
- **Audit disposition guidance:** sandbox restore bounds message size/fuel and poisons failed restores (`pkgs/id/src/sandbox.rs:670-713`), but the native snapshot adapter does not perform the sandbox’s restore/re-snapshot probe (`sandbox.rs:884-906`, `pkgs/id/src/world_native.rs:308-310`; contract and restore path: `world/mod.rs:911-915`, `world_store.rs:595-639`). Prove snapshots cannot alter host authorization, or treat the missing verification as a gap; do not assume opaque means safe. Petnames are display labels, not capability authorization (`pkgs/id/src/petname.rs:1-6`, `58-96`, `125-161`), so may be explicitly exempt from this authority contract while preserving their separate display-integrity rules.
- **Acceptance:** the audit gives file:line evidence for every disposition, explicitly records any unproven trust boundary as unresolved (not “already validating”), and the module docs make the admission rule discoverable. This phase supplies the closing-audit evidence; it does not authorize silently absorbing new fixes into the six adopted issues.

## 7. Questions and boundaries

**No decision genuinely requires Drew.** The latest #2898 triage comment says the same: the remaining items are engineering dispositions for the closing audit, not product or authority-policy choices.

The following are technical questions for the implementation/audit, with a recommendation so work need not block:

- **Policy and directory provenance:** either (A) prove the persisted store provides an equivalent integrity boundary, or (B) add verifiable provenance before treating those replayed transitions as equivalent to live authorization. **Recommendation:** require evidence for A; otherwise record B as a concrete security gap, not an exemption.
- **Snapshots:** either (A) prove snapshots cannot mutate host-side authority, or (B) verify them at the native and sandbox reconstruction boundaries. **Recommendation:** establish the host/guest boundary first; if the proof fails, use B.
- **Replay payload shape:** validating business payloads during program execution is execution policy, not reconstruction admission. Keep it out of this design unless it changes host authorization; this boundary is explicitly noted in #2898.
- **Future agreement types / revocation semantics:** the current pins cover the documented duel outcome domain and current Revoked ordering. A future non-duel domain or changed Revoked semantics must declare its own validity rule rather than weakening these checks.
