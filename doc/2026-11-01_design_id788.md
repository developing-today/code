# Design: Native reference shell for `id` (F13.6)

- Date: 2026-11-01
- Status: **design — recommendation recorded; two scope/gating questions remain**
- Issue: [#788](https://github.com/developing-today/code/issues/788), Phase 13 F13.6; umbrella [#538](https://github.com/developing-today/code/issues/538)
- Evidence checked against `origin/main` at `f7c942b1f` after fast-forwarding this issue branch.

## Decision to make

Choose the reference native-client framework and define how it relates to the
existing shell protocol and the F12.8 WIT/component-model decision. Also make
explicit whether F13.6's first shell must deliver 3D/audio/native-widget
content, or whether that requires a later presentation-contract extension.

**Recommendation:** use **Bevy** for the reference client; keep the shell on the
existing F13.1 `ClientFrame`/`ServerFrame` contract; record that WIT does **not**
change that client-facing contract; and keep the Bevy dependency in a separate
native-app crate. The first vertical slice should render legacy `data` and the
existing typed `Screen` surface and emit only existing input/paste/resize
frames. Rich 3D/audio/widget payloads need a separately designed, versioned
presentation extension; they cannot be claimed by a shell that only implements
today's screen/text view. Q1 (§8) asks Drew whether that extension is part of
this XL issue or a follow-on. Q2 (§8) asks whether the roadmap's #840 gate is
intentional for F13.6.

F13.6 implementation remains gated by the Phase 13 plan's F12.7 dependency.
The roadmap also lists #840 as a prerequisite, but #840's own scope and the
latest #788 triage do not establish it as an F13.6 gate; Q2 (§8) records that
conflict. F13.1/#783 is already done. F12.8/#1065 remains the guest-ABI
decision, not a blocker for this shell-boundary decision.

## 1. Context and current state

Issue #788 asks for a native shell (Bevy or Qt) that implements the shell
contract, renders the same world and emits the same input events as the
terminal without a host change, passes the F13.1 conformance check, and records
whether WIT changes the interface. Its context names 3D, audio, and native
widgets as the reasons for a native client. The issue names #534/F12.7 and
#564/F13.1 as prerequisites. The Phase 13 plan more specifically says F13.6
depends on F13.1 and F12.7 and recommends Bevy because it shares Rust with the
server (`.opencode/plans/phase-13-client-shells.md:87-90, 99-107, 128-134`).

The current shell contract is version 1, revision 3. It describes the same
session protocol over Iroh, WebSocket, and SSH exec, with a 1 MiB frame limit
(`pkgs/id/contract/shell-contract.v1.json:1-23`). The client input vocabulary
is `input` with `data_hex`, `paste` with bounded text, and ephemeral `resize`;
the server `view` contains `data` and an optional object-valued `surface`
(`pkgs/id/contract/shell-contract.v1.json:230-252, 271-283`). The Rust frame
types encode those same shapes (`pkgs/id/src/world_session/types.rs:244-255,
283-289`).

The typed presentation currently has exactly one variant, `WorldSurface::Screen`;
legacy text remains valid and the parser only recognizes the versioned screen
document (`pkgs/id/crates/id-core/src/world_presentation.rs:1-6, 25-45,
258-272`). The host validates screen dimensions and cells before attaching
that surface to the view (`pkgs/id/src/world_session/mod.rs:2059-2067`; limits and validation are
in `pkgs/id/crates/id-core/src/world_presentation.rs:16-23, 278-304, 315-420`). There is no scene,
audio, or native-widget payload in this type or the v1 contract. Therefore a
native renderer alone cannot provide those richer semantics while staying a
contract-only client; they require a separately specified presentation
extension and host-side validation before the shell can consume them.

There is already a usable client seam. `WorldClient::connect` opens an Iroh
world session; `send_json` and `recv_json` exchange framed JSON, and
`WorldClient` is exposed from the `world`-gated public `world_net` module
(`pkgs/id/src/world_net.rs:173-200, 239-247, 728-738`;
`pkgs/id/src/lib.rs:238-249`). The existing shell-contract tests exercise
real host sessions and assert terminal and web shell frames against the same
contract (`doc/2026-10-25T05-54-40Z_reference_shell_contract/2026-10-25T05-54-40Z_reference_shell_contract.md:223-253`).

### Gates and recent decisions

- **F13.1 / #783: complete.** The contract artifact and conformance checker
  are present; tests pin frame variants/fields and run real sessions through
  the checker (`pkgs/id/src/shell_contract/tests.rs:87-134, 201-251`;
  `pkgs/id/src/world_session/contract_tests.rs:111-209, 212-229`; summarized
  in `doc/2026-10-25T05-54-40Z_reference_shell_contract/2026-10-25T05-54-40Z_reference_shell_contract.md:223-253`).
- **F12.7 / #1064: still open.** The Phase 13 plan explicitly places F12.7
  before F13.6 (`.opencode/plans/phase-13-client-shells.md:89, 101-107`);
  the latest #1064 triage says only its first slice (spec/version export) is
  queued and the conformance suite remains. The gate here means the complete
  F12.7 exit—versioned ABI spec, `plaza_abi_version`, and conformance suite
  passing with the Roc examples unchanged—not merely the first queued slice.
  This preserves the formal phase sequence even though the newer shell
  reference puts the guest ABI on a separate layer.
- **Session identity / #840: open; roadmap prerequisite status is ambiguous.**
  The roadmap lists #840 on the F13.6 row (`planning/roadmaps/id.md:48-55`),
  but #840's body says it was found while designing F13.7 and names F13.7/#789
  and F13.8/#790 as dependents; neither the #788 body nor its latest triage
  lists #840. Resolve this rather than treating the roadmap row alone as a
  confirmed hard gate (Q2, §8).
  `WorldCommand::Input` currently contains only token, bytes, and reply, and
  the actor attributes the event to a participant but not a connection
  (`pkgs/id/src/world/actor.rs:100-104, 1132-1144`; the handle constructor is
  `pkgs/id/src/world/handle.rs:608-617`). The #840 issue proposes an opaque,
  ephemeral per-connection ID, never journaled. If it lands, it is host-local
  attribution; F13.6 must not add it to the wire contract or ask the shell to
  generate it.
- **F12.8 / #1065: open, owned separately.** The newest shell-contract
  reference says the guest ABI is a distinct layer beneath the session
  protocol: a shell never sees the ABI (`doc/2026-10-25T05-54-40Z_reference_shell_contract/2026-10-25T05-54-40Z_reference_shell_contract.md:26-35`).
  This supersedes the earlier Phase 13 open-question wording that a WIT choice
  might require a WIT-shaped shell-contract edition
  (`.opencode/plans/phase-13-client-shells.md:133`). F12.8 may select WIT for
  guest SDKs, but F13.6 should continue to consume the JSON session contract.

## 2. Viable options

| Option | Benefits | Costs / risks |
| --- | --- | --- |
| **A. Bevy reference client (recommended)** | Matches the plan's Rust-toolchain rationale and the issue's 3D/audio motivation without introducing another language boundary. Bevy's input, rendering, and presentation code can live in an app crate while the network and host remain unchanged. | It is a substantial engine for a first shell and is less directly centered on conventional desktop widgets than Qt. It adds native build/package work; keep that cost out of the default `id` CLI dependency graph. |
| **B. Qt reference client** | Strong fit when native desktop widgets and platform integration are the primary goal; explicitly named alongside Bevy in the issue and plan. | The conventional Qt/C++ route does not share the server's Rust toolchain and introduces a second build/runtime surface. Rust Qt bindings are an alternative, but this repo has no comparison spike; less code/type reuse is available than with the existing Rust client seam. |
| **C. Defer a native shell; keep web/terminal only** | No new engine dependency or packaging surface while the Phase 12 gates are open. | Does not deliver F13.6 or exercise the native-shell/conformance claim; it only postpones the issue. |

Option A is the narrowest reference choice that still leaves room for the
native-rendering ambition. The Phase 13 plan already recommends Bevy for the
shared Rust toolchain and identifies Qt as a broader app-surface alternative
(`.opencode/plans/phase-13-client-shells.md:128-133`).

## 3. Recommended module and interface

Put the desktop application in a separate package (candidate path
`pkgs/id/crates/id-native-shell`) that depends on the public `id` client and
presentation surface. It should be a member of the existing workspace, but
excluded from `default-members`, so ordinary root builds do not build the
native app. Configure its `id` dependency with `default-features = false,
features = ["world"]`; the root `world` feature forwards to `id-core/world`,
while `sandbox` is what enables Wasmtime (`pkgs/id/Cargo.toml:18-29, 52-56,
135-139`). Keep Bevy and platform-window dependencies in the app crate, not
the `id` package's default graph.

The app must reuse the CLI's client identity: use the public
`CLIENT_KEY_FILE` (`.iroh-key-client`) and `load_or_create_keypair` APIs
(`pkgs/id/src/lib.rs:280, 295-299`; `pkgs/id/src/store.rs:91-99`).
`WorldClient::connect` requires an existing `Endpoint`
(`pkgs/id/src/world_net.rs:183-200`); the CLI endpoint builder is private
(`pkgs/id/src/commands/world.rs:26-48`). The implementation should either own
its endpoint configuration using the same key file or extract a small shared
public client-endpoint helper, rather than silently creating a second identity
or copying private CLI policy.

The current workspace root already includes `crates/id-core` and has explicit
default members (`pkgs/id/Cargo.toml:18-20`). The crate-split design's planned
layout remains consistent with an `id-native-shell` member and facade
dependency (`doc/2026-11-01T16-53-00Z_design_id_crate_split/2026-11-01T16-53-00Z_design_id_crate_split.md:126-146`).

```text
Bevy app (window, input, renderer)
  ├─ consumes `WorldClient` JSON session frames over Iroh
  ├─ renders `view.data` and validated `WorldSurface::Screen`
  └─ maps native keyboard/paste/resize into existing client frames
       │
       └─ F13.1 contract checker / transcript fixture (same test seam as other shells)
```

`WorldClient` is the initial Iroh adapter, not the definition of the shell
protocol: it already opens a session and sends/receives JSON frames. The app
must not create a host, modify host behavior, add shell-specific frames, or
require guest code to know whether the presenter is Bevy, web, or terminal.
Leave transport choice open at the contract seam; do not build an abstraction
for hypothetical transports until a second native transport adapter is in
scope.

The initial renderer should use validated screen cells or fall back to
`view.data`; the contract reference explicitly says a shell that does not
understand an optional surface renders the data text
(`doc/2026-10-25T05-54-40Z_reference_shell_contract/2026-10-25T05-54-40Z_reference_shell_contract.md:188-192`; the view carries both fields in
`pkgs/id/contract/shell-contract.v1.json:280-283`).
Native keyboard events map to the existing byte-input grammar. Paste and resize
use their existing frames; focus and other richer events must not be invented
in Bevy-only messages (`pkgs/id/contract/shell-contract.v1.json:235-251`).

## 4. WIT / component-model decision

**Decision for F13.6: WIT does not change the shell contract.** The shell
speaks the client↔host session protocol; WIT is a possible guest↔host ABI
representation. The contract reference explicitly separates these layers and
says a shell never sees the guest ABI (`doc/2026-10-25T05-54-40Z_reference_shell_contract/2026-10-25T05-54-40Z_reference_shell_contract.md:26-35`).
Therefore:

- F13.6 adds no WIT interface, WIT-shaped edition, or WIT-specific shell
  frames.
- F12.8/#1065 remains responsible for whether the guest ABI and SDKs use the
  component model. A later WIT decision is implemented behind the host's
  existing session protocol.
- Revisit this decision only if a future design intentionally lets a shell
  implement guest imports or directly exchange component-model values. That
  would change the stated three-layer model and needs its own proposal.

This resolves the older plan's “may need a second, WIT-shaped edition” note
without pre-empting F12.8's actual guest-ABI decision. New client frame kinds
remain subject to the F11.12 gate (`pkgs/id/contract/shell-contract.v1.json:5`;
the reference explains the forward-only rule at
`doc/2026-10-25T05-54-40Z_reference_shell_contract/2026-10-25T05-54-40Z_reference_shell_contract.md:44-61`).

## 5. Invariants

1. **Protocol parity:** the native shell sends and receives only frames and
   fields named by the current shell contract. Every recorded native session
   passes `id world contract --check`, just like terminal/web sessions.
2. **Host independence:** adding or changing the native presenter does not
   require a host change; any richer presentation schema is a separately
   reviewed, additive contract/host change before the shell consumes it.
3. **Layer separation:** WIT decisions affect the guest ABI only; no WIT values
   or guest exports leak into the client shell protocol.
4. **Journal semantics:** `input`, `paste`, and `chat` remain committed event
   frames; `resize` is ephemeral. The contract classifies resize as ephemeral
   and input/paste as events (`pkgs/id/contract/shell-contract.v1.json:230-251`).
   If #840 lands, its connection ID stays host-local and ephemeral.
5. **No new frame kind without its gate:** the first shell uses existing
   frames. Any future new client/server frame follows F11.12 and updates the
   machine-readable contract and conformance tests.
6. **Client-only:** the Bevy process connects to worlds but does not start a
   world host or gain ambient host authority; server capability rules remain
   unchanged.
7. **Dependency isolation:** the standard `id` build does not acquire Bevy or
   desktop-platform dependencies merely because the native app exists.

## 6. Implementation acceptance criteria

- [ ] A separate Bevy app target/package builds without adding Bevy or native
      windowing dependencies to the default `id` package build; the app is a
      workspace member excluded from `default-members`.
- [ ] A scripted native session joins a world, handles the initial snapshot,
      events and views, sends input/paste/resize, and its complete transcript
      passes the existing F13.1 checker.
- [ ] A parity test drives the same scripted input through the native and
      terminal shell adapters and proves the same contract frames and durable
      world outcome; it does not compare pixels or terminal escape sequences.
- [ ] The native presenter renders `view.data` and the existing validated
      `Screen` surface, safely falls back to `data`, and does not interpret
      guest-provided HTML, CSS, or terminal escapes as executable UI
      (`pkgs/id/crates/id-core/src/world_presentation.rs:1-6`).
- [ ] The host is unchanged for this shell implementation; `id` remains the
      source of protocol validation and authority.
- [ ] The shell sends no session-identity field; if #840 is accepted as a
      prerequisite, its separate test proves the ID is opaque, ephemeral, and
      distinguishes two connections. F13.6 does not duplicate that host test.
- [ ] No F13.6 shell frame depends on WIT, and the result passes the current
      shell contract revision regardless of F12.8's guest-ABI selection.
- [ ] If Q1 selects rich 3D/audio/widget support for this issue, the selected
      surface schema has explicit versions, bounds, safe fallback behavior,
      contract/conformance coverage, and host-side validation before the Bevy
      renderer consumes it. Any new frame kind also waits for F11.12.

## 7. Phased implementation plan

**Implementation gate (not an implementation step):** wait for the complete
F12.7/#1064 deliverable (versioned ABI spec, `plaza_abi_version`, conformance
suite, and Roc examples passing unchanged); the plan explicitly orders it
before F13.6. F13.1/#783 is already complete. Treat #840 as a gate only if Drew
confirms Q2; its current roadmap row conflicts with #840's stated dependents
and #788's latest triage. Do not wait for F12.8/#1065 to build the shell
against the client contract.

Each numbered step is a separate reviewable PR after the gate. Steps 1–2 are
the minimum F13.6 vertical slice; steps 3–4 are included in F13.6 only if Drew
answers Q1 “include”. If Q1 is “defer”, file the rich-presentation work as a
separate follow-up rather than expanding the first shell PR.

1. **Native app package and transcript harness.** Add the Bevy app crate as a
   workspace member outside `default-members`, dependency isolation, and
   connection/configuration bootstrap. Reuse `CLIENT_KEY_FILE` and
   `load_or_create_keypair`; extract a small shared endpoint helper only if
   needed to keep relay/key policy in one place. Add a fixture exercising the
   public `WorldClient` interface. Keep UI rendering minimal. **Done when:**
   `cargo build -p id` remains free of Bevy, `cargo build -p id-native-shell`
   succeeds, and the fixture passes `id world contract --check`.
2. **Contract-parity shell.** Implement join/snapshot/event/view handling,
   fallback text plus `Screen` rendering, and mappings for existing input,
   paste, and resize. Add scripted terminal/native frame and world-outcome
   parity tests. **Done when:** acceptance criteria 1–6 pass without host
   changes or new contract frames.
3. **Portable rich-presentation contract (conditional on Q1).** Design and
   validate the minimal typed scene/audio/widget payloads in the existing
   optional `surface` slot (or propose a separately versioned alternative if
   that slot cannot express them). Update host validation, contract data, and
   conformance/fallback tests in its own PR. **Done when:** old shells still
   render `data`, and malformed/oversized rich surfaces are refused. Do not
   introduce new frame kinds before F11.12.
4. **Bevy rich-surface renderer (conditional on Q1).** Add the renderers and a
   deterministic example world for only the payloads accepted in step 3; keep
   world input on the same contract frames. **Done when:** a real session
   demonstrates each selected surface, transcript conformance passes, and
   an older shell's text fallback remains usable.
5. **Package and user-facing docs.** Document install/run, required connection
   inputs, platform build prerequisites, the current surface support, and how
   to record/check a session. **Done when:** a clean build and smoke test are
   repeatable from the documented commands and the documented limitations
   match the contract.

## 8. Questions for Drew

**Q1 — Does the first F13.6 implementation include rich native surfaces, or
only a native shell that proves parity with today's contract?** The issue's
motivation names 3D, audio, and native widgets, but its exit criteria require
contract parity with no host change. Today's typed surface is only `Screen`;
the richer semantics need an additive schema and host validation.

- **A. Contract-parity first; defer rich surfaces.** The first Bevy shell
  renders `data`/`Screen` and proves equivalent input/session behavior; file a
  later contract extension for richer presentation. **Recommended:** matches
  the explicit no-host-change and conformance acceptance criteria, keeps the
  first PR independently mergeable, and avoids inventing an unvalidated
  payload in the app.
- **B. Include rich surfaces in F13.6.** Add a host-validated additive
  presentation schema before the Bevy renderer and include that work in the
  issue's implementation plan. **Viable if 3D/audio/widgets are required for
  the issue's exit**, but it expands scope and means the overall feature
  includes a host/contract change even though the shell remains swappable once
  that extension lands.

**Q2 — Is #840 a hard prerequisite for F13.6?** The current roadmap lists it
on the F13.6 row, but #840's own body scopes it to F13.7/#789 and F13.8/#790,
and the latest #788 triage names F12.7 as the remaining gate without #840.

- **A. Keep #840 as an F13.6 gate.** Wait for the input-attribution change
  before any native-shell work. **Viable if** F13.6 is expected to exercise
  multi-session attribution or a capability path that needs connection
  identity; this matches the current roadmap row.
- **B. Limit #840 to its stated F13.7/F13.8 dependents.** Start F13.6 after
  F12.7/#1064 and F13.1/#783; do not require connection identity for a
  contract-parity shell. **Recommended:** the shell sends the existing input
  frame and does not mint or consume the host-local ID, so the cited F13.6
  acceptance does not depend on #840. If confirmed, reconcile the roadmap in a
  separate docs change before implementation.

No other Drew decision is required for this record: Bevy is the recommendation
already called for by the Phase 13 plan, and the WIT question is resolved at
the shell layer without choosing F12.8's guest ABI. F12.8 remains Drew's
separate decision in #1065.
