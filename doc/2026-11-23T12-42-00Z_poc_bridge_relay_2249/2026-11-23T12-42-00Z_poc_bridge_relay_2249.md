## What this PoC is

The #2035 investigation's relay model, exercised end to end for the
first time with automatic fan-out: five in-process endpoints
{A, B, C, D} mutually visible plus E reachable only through D,
chained-class messages over direct Iroh connections on the
`/id-chained-relay/1` ALPN, each relay's gate validating before
forwarding (the #3796 phase-3 machinery). The PoC's one new piece is
the forwarding sink: the `ChainedSink` contract says "deliver
locally, then fan the same value out to next peers" — until now no
implementation did the second half, and the #3796 tests forwarded by
hand. That sink lives in the test file and is disposable by design.

**Explicitly NOT the permanent feature.** No production code changes
in this slice; the harness, the measurements, and this report are the
deliverable. The report is linked from #2036 as #2249 requires.

## Method

- Each node runs a real Iroh endpoint (loopback, relay mode disabled)
  serving `ChainedRelayProtocol` with an `AllowlistFrontier`
  authorizing the origin for `group-1`, and a `ForwardingSink` that
  records the delivery and fans out to the node's visible neighbours,
  excluding the neighbour the message arrived from (read off the hop
  chain: the hop before this node's own, or the origin for a direct
  delivery).
- "E firewalled from all but D at the application layer" is enforced
  by the sender neighbour sets: only D ever dials E. E's router would
  still accept a connection from anyone who learned its address —
  there is no transport-level block in this PoC.
- Latency: 20 messages, origin timestamp taken at A before fan-out,
  delivery timestamps recorded in each sink. Medians reported; no
  ordering asserted (loopback timing is environment-dependent).
- The allowlist frontier is the stand-in, not the graph-backed
  `GraphFrontier` a production host wires in (that backing is already
  covered at the ingest call site by the #3796 tests).

## Latency (measured, GitHub-hosted runner, loopback)

| Path                            | Median over 20 messages |
| ------------------------------- | ----------------------- |
| Direct A→B (one hop, no bridge) | **15.098 ms**           |
| Bridged A→D→E (via the bridge)  | **192.494 ms**          |

The bridged path costs ~12.7× the direct path in this harness.
That ratio is a harness measurement, not a protocol verdict: each
`forward_message` opens a fresh connection per send, so the bridged
path pays one connection setup per hop (plus the fan-out races that
decide which path reaches D first — one failing run showed the
delivered chain at E as `[B|C, D, E]` when B/C fan-out raced ahead
of A's direct send; the test accepts either valid shape and asserts
the chain ends `[…, D, E]`). Connection reuse for relay
sends is the obvious next measurement: it should collapse the
per-hop setup cost, and it belongs to the permanent feature's work,
not to this PoC. The absolute numbers are loopback numbers on a
shared runner; the ratio and the setup-cost finding are the durable
part.

## Limitations (stated, not hidden)

- In-process loopback only: no real network, no NAT, no packet loss.
  Swarm sizing at n=5 with one bridge-only member (#2035 §5 risk 1)
  is demonstrated for the ID-controlled forwarding path, not for
  stock gossip (which the gate-verification finding already rules
  out as a carrier).
- E's "firewall" is sender-set enforcement, not a transport block.
- Allowlist frontier, not the signed-graph frontier, in the harness.
- No media, no privacy-relay mode, no retention — all out of scope
  for this PoC by the #2035/#2036 design.
- Latency medians are single-run numbers from one runner; re-running
  the test re-measures them.
