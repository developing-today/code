## 1. What Atlas is today

Atlas is Drew's personal corpus / search infrastructure: every conversation and corpus he cares about ingested into one canonical store (`sessions → messages → chunks`), classified (scheme-1.0: kind / topics / projects / sensitivity), embedded, and searched hybrid (FTS + vector). Its program home is the epic [#8983](https://github.com/developing-today/code/issues/8983) — "epic: Atlas program — unified search and memory index over every corpus" — whose goal text states: "every corpus (conversations, memory files, notes, repo docs, research) ingested through corpus connectors into one staging index, with embedding unification and per-corpus model identity, a query surface (including the mcpx MCP namespace), and standing cross-agent eval sets as the quality oracle."

### 2.2 The Cloudflare Worker (`pkgs/atlas-search/worker/`)

Per `worker/README.md` and `worker/src/index.ts` (issue [#6788](https://github.com/developing-today/code/issues/6788)): "a Worker that pulls all databases for search" — the cross-database search surface. Shape:

- The Worker **holds no database credentials**: fan-out, embedding, and merge live in the fleet search service (`worker/src/service.ts` calls `fleet serve search` — `POST /v1/embed`, `POST /v1/search` — via the `atlas-search.security.cab` tunnel hostname + a Cloudflare Access service token; `SERVICE_BASE = "https://atlas-search.security.cab"` in `worker/wrangler.toml`). New `atlas-core-*` databases join the fan-out through the service's manifest discovery, not a Worker-side shard list.
- Per query it stores a **Durable Object** (`worker/src/cache_do.ts`, class `QueryCache`, one DO per query key; state machine absent → embedded → complete): the query is automatically inserted **as an embedding** (the pinned Snowflake space, `worker/src/space.ts`), and the result is **cached indefinitely** (no TTL/eviction in v1 — §7). DO key = sha256 over the normalised query + a pinned config fingerprint (ceiling, model revision, vector table, k) (`worker/src/key.ts`) — a cached entry is never served across ceilings or embedding spaces.
- Routes (`worker/src/index.ts`): `GET /health` (open), `POST /v1/search {query, k?}` (gated, k clamped 1–50, default 10 — `worker/src/search.ts`), `GET /v1/cache/inspect`, `POST /v1/cache/purge` (both gated), `POST /mcp` (gated — §2.3). **One search execution path** (`executeSearch` in `worker/src/search.ts`): REST and MCP both call it, keyed under the pinned disclosure context (#12622), "so the ceiling/context pinning and the cache keying can never drift between surfaces."
- The service enforces this client's **`personal` tier ceiling**; the Worker is a `cf-worker` client identity of the search service.
- Tests: `worker/test/{worker,mcp,hot_cache,key,space,body}.test.ts` (vitest + @cloudflare/vitest-pool-workers). Deploys go through the sanctioned `cf` binary's versions flow (never a silent overwrite); `cloudflare.config.ts` is the deploy source of truth, `wrangler.toml` drives local dev/tests.
- D1 hot-cache binding present but **flag off** (`HOT_CACHE_ENABLED = "false"` in `wrangler.toml`; §4.3).

## 3. Embeddings

### 3.1 The production model — Snowflake Arctic Embed m v2.0

Verified in code, in three places that agree:

- `pkgs/atlas-search/crates/atlas-core/src/types.rs`: `pub const DEFAULT_MODEL: &str = "Snowflake/snowflake-arctic-embed-m-v2.0";` and `pub const DEFAULT_VEC_TABLE: &str = "vec_snowflake_m_v2_768_f32";` — i.e. the Hugging Face id carries the **`Snowflake/` prefix**, the stored vector table is named for **768 dimensions, f32**. (This is the `Snowflake/`-prefixed model id the fleet book survey saw printed by the search surface; the fleet CLI help shortens it to "Snowflake arctic-embed-m-v2.0".)
- `pkgs/atlas-search/crates/atlas-embed/src/lib.rs`: "atlas-embed — the Snowflake `snowflake-arctic-embed-m-v2.0` embedder": a native Rust ONNX implementation — the model's own `tokenizer.json` (SentencePiece Unigram), **CLS pooling**, `pub const EMBED_DIM: usize = 768`, model context 8192 (the shipped sentence-transformers config truncates at 512 by default; atlas-embed does not inherit that cap), Matryoshka truncation supported at query time. Load cost is the expensive part: one resident session is ~1.6 GB RSS (`embed.rs` comment) — hence one shared embedder per process, mutex-serialised.
- `pkgs/atlas-search/crates/atlas-core/src/embed.rs`: the query-side contract ported from the Python `embed_query` — sentence-transformers applies the model's query prompt (`prompt_name="query"`; for this model the shipped query prompt is the string prefix **`"query: "`**), then Matryoshka truncation slices, then L2 renormalisation (NumPy pairwise f32 summation replicated exactly). **Documents are embedded prompt-free**; only queries pass through the prompt step. The Rust binary reproduces the Python vectors **bit-identically** (the parity claim gated by the golden set — §4.4, and the premise of [#12900](https://github.com/developing-today/code/issues/12900) thread 3).
- The Python reference agrees: `MODEL = "Snowflake/snowflake-arctic-embed-m-v2.0"` in `pkgs/atlas-search/atlas_search.py`, with `--model / --vec-table / --embedder / --trunc` (or `ATLAS_SEARCH_MODEL` / `ATLAS_VEC_TABLE`) overrides.
- The Worker pins the same space: `worker/src/space.ts` pins (ceiling, model revision, vector table) into every cache key, and the fleet service loads "the Snowflake `snowflake-arctic-embed-m-v2.0` model at a pinned snapshot revision" (model dir from `ATLAS_MODEL_DIR` or the Nix closure; `atlas-search fetch-model` / `fleet`-side `fetch_model.rs` fetches the pinned snapshot).

### 3.3 Where vectors live

- **Canonical/Turso:** chunk vectors in the Turso monolith's vec table (`vec_snowflake_m_v2_768_f32`) plus the 29 topic shards. Known limitation recorded on [#3125](https://github.com/developing-today/code/issues/3125) (2026-10-31): "`vector_top_k` does not work on the current plain-BLOB vec table (no libsql vector index) — the CLI uses `ORDER BY vector_distance_cos(vec, vector32(?))` (~4 s unfiltered full scan)"; a v3 publish with a libsql vector index (DiskANN) is the recorded fix direction. The Rust CLI exposes `--vector-backend scan | index-fill | index-fixed` (default `scan`).
- **Local laptop:** the v3 local corpus/vector DBs under `~/atlas/v3/` and the delta DBs (§1.3), read by the local backend.
- **Query vectors:** computed at query time by the one shared embedder (service / standalone binary / Worker-via-service), cached in the query-embedding cache (`atlas-core/src/embed_cache.rs`, keyed on the raw full-dimension vector before truncation/renormalisation) and, on the Worker path, persisted inside the per-query Durable Object before the search runs.
- **D1 is NOT a vector store in the current design:** the D1 hot cache (§4.3) caches _results and content payloads_ (classes A/B/C), not an ANN index. **UNVERIFIED / no evidence found** of any sqlite-vec / LanceDB / Qdrant-style external vector DB in the Atlas serving path; the recorded options stay inside libSQL/Turso + in-process scan/index backends.

## 7. Known gaps / limitations (as recorded on issues and in code)

**Query planning / query understanding.**

- [#9092](https://github.com/developing-today/code/issues/9092) (verified 2026-11-12): "Contract flags for the query planner, spell correction, query-class hint, and `rewritten|both` variants are **accepted but unimplemented**." Search v1 scope item 1: implement the dead contract surface or formally retire each flag — planner per [#5773](https://github.com/developing-today/code/issues/5773) ("query-understanding front-end — spell correction + LLM query planner/rewriter as toggleable stages, dual submission with provenance", OPEN), parameter surface per [#5774](https://github.com/developing-today/code/issues/5774) ("every retrieval knob as a CLI flag / raw-query field, no hardcoded constants", OPEN). The versioned parameter set that _does_ exist is `atlas-proto`'s `SearchParametersV1` (k, pool, expand, RRF k, per-signal weights).
- Branch execution was serial in the Python until [#12900](https://github.com/developing-today/code/issues/12900) thread 1 landed 2026-11-23; the Rust serve path supplies a concurrent branch executor (`atlas-core/src/search.rs`: "serve mode supplies an executor that runs the FTS and vector branches concurrently while preserving this module's exact validation, fusion, and rendering semantics").
- Vector retrieval is an exact scan by default (~4 s unfiltered over Turso; session-filtered vector queries cost ~15 s server-side per the Python header's join-chain note, 20–60 s for naive joins per [#3125](https://github.com/developing-today/code/issues/3125)); index backends (`index-fill` / `index-fixed`) exist as CLI options but the publish lacks a libsql vector index (§3.3). Shard fan-out is a hidden experimental flag, not the default ([#9092](https://github.com/developing-today/code/issues/9092)).

**Fusion today; reranking — what exists and what doesn't.**

- What exists: **reciprocal rank fusion only.** `atlas-core/src/fusion.rs` fuses the FTS (FTS5/BM25) and vector pools: `score += weight / (rrf_k + rank)` per branch (defaults from `SearchParametersV1`), ordered by (−score, best rank, chunk_id). The FTS match expression is a heuristic builder (content words >3 chars OR-joined as quoted phrases, plus short digit-bearing tokens). Sensitivity/classification filtering is **filter-before-rank** inside the backend's branch construction.
- **No learned / cross-encoder reranker exists in the serving path.** A code search for `rerank` across developing-today/code returns 10 hits, none of them an Atlas serving reranker (eval tooling `eval/gate5733.py` and a Worker `service.ts` mention are the closest). **UNVERIFIED** as a negative beyond that search + tree inspection — but no rerank stage, model, or issue-scoped implementation was found.
- Third-signal candidates are at the _evaluation_ stage, not adopted: **Jaccard rescore** (gate #5733 — results in `eval/gate-5733-results.md`; [#9092](https://github.com/developing-today/code/issues/9092) scope: "Jaccard third signal per #5733 where it earns its place") and **SPLADE** (in the #5741 ablation matrix design, §4.4; a SPLADE issue draft exists in the design archive `doc/atlas-scratch-sweep-2026-11-14/atlas-splade-issue.md`). Shingle machinery for near-duplicate/Jaccard work exists in the engine (`atlas-core/src/shingles.rs`).
- Feedback exists as _capture_, not as a ranking input: `atlas-core/src/feedback.rs` implements `atlas-feedback/v1` (#9976, design `doc/2026-11-10T20-41-01Z_design_atlas_retrieval_stats_feedback.md` §6) — append-only thumbs votes keyed to `(query_id, chunk_id)` result identity (never rank position), with a derived supersede view and requester-kind weighting known to the aggregation; query traces (`atlas-query-trace/v1`, #9973) are captured alongside. Whether any ranking/recommendation path _consumes_ aggregated feedback today: **no consumer found in the tree — UNVERIFIED negative**, and the retrieval-stats/feedback loop is a design-stage follow-on family of #6027.

**Recommender.** Design-stage only — §4.5: recommendation objects/retention ([#9140](https://github.com/developing-today/code/issues/9140), OPEN), the fan-out-worker + DO-accumulator "next 10" shape ([#9109](https://github.com/developing-today/code/issues/9109) Part C), and exactly one implementation slice in flight (snapshot paging, [#10158](https://github.com/developing-today/code/issues/10158) / PR [#12873](https://github.com/developing-today/code/pull/12873), both OPEN). No candidate generation, no serving endpoint, no feedback-driven personalisation exists today.

**Freshness / incremental indexing.**

- Worker result cache: **indefinite, no TTL, no eviction, no invalidation** in v1 (Worker README); [#6805](https://github.com/developing-today/code/issues/6805) (eviction & invalidation policy) is OPEN, with deferred triggers recorded in the README (add corpus generation to the cache key at the first same-space re-ingest changing >5% of chunks or on a stale-result complaint; add an LRU sweeper at 10,000 cached queries or 1 GB aggregate). A gated per-query purge route exists (§2.2). The standalone CLI has **no result caching** (#5668, via [#9092](https://github.com/developing-today/code/issues/9092)).
- [#9092](https://github.com/developing-today/code/issues/9092) scope item 4 defines the target semantics — results cached until the corpus changes; on change, a short specified staleness window unless the caller passes a real-time requirement or a cache-disable flag (both to become first-class flags at CLI/service/Worker); the corpus-change signal is the ingest watermark from [#9097](https://github.com/developing-today/code/issues/9097). The service client already exposes `--no-cache` (bypasses cache reads; the fresh result still lands in cache).
- Incremental indexing: delta-only ingestion + offset embeds are designed ([#6028](https://github.com/developing-today/code/issues/6028), via [#9097](https://github.com/developing-today/code/issues/9097)) and a CDC-feasibility research exists (`doc/2026-11-14T12-20-00Z_research_atlas_cdc_feasibility_6040/`), but with ingestion itself manual (§6.1) there is no incremental index pipeline in production; the D1 hot-cache invalidation slice that would consume ingest events ([#13106](https://github.com/developing-today/code/issues/13106)) is flag-held.

**Multi-DB vector resolution.** Working in the small (content_hash resolution across the monolith + topup/delta DBs, §1.3.2; Worker fan-out across service-discovered `atlas-core-*` DBs, §2.2) and unbuilt in the general form ([#3125](https://github.com/developing-today/code/issues/3125) phase 4: catalog DB + collection×month shards + resolve/fetch-span as MCP tools). Cross-tier vector comparability is a recorded decision (`doc/2026-11-08T10-44-00Z_decision_atlas_cross_tier_vector_comparability/`); mixed-embedder corpora are a v1 requirement, not a landed feature ([#9092](https://github.com/developing-today/code/issues/9092) / [#8623](https://github.com/developing-today/code/issues/8623)).

**Other recorded limitations.**

- Cold start: ~35 s for the Python CLI (ST model load dominates); the Rust service amortises this with one resident embedder (~1.6 GB RSS) but serialises vector queries on its mutex.
- Corpus counts freeze silently between manual publishes — a recount procedure is an explicit [#9097](https://github.com/developing-today/code/issues/9097) acceptance item.
- Sensitive rows still live in the production monolith + a local replica ([#8479](https://github.com/developing-today/code/issues/8479), OPEN) — query-time ceilings are the current mitigation; embed-time classification enforcement is open ([#12403](https://github.com/developing-today/code/issues/12403)/[#12404](https://github.com/developing-today/code/issues/12404)/[#12406](https://github.com/developing-today/code/issues/12406)).
- Per-agent identity/scoping for MCP consumers is unbuilt ([#8625](https://github.com/developing-today/code/issues/8625)); all hosted MCP callers share `hosted-per-user`.
- atlas-core carries 22 pre-existing clippy warnings ([#13056](https://github.com/developing-today/code/issues/13056)) with the cleanup PR [#13097](https://github.com/developing-today/code/pull/13097) still open.
