## Decision summary

| Question | Decision |
| --- | --- |
| Addressing | One adapter endpoint per **browser profile + origin**. A foreign collection is one object store, addressed `idb://<origin>/<database>/<store>` (§2). The database alone is never a collection |
| Selection | Explicit allowlist of (database, store) pairs in adapter configuration. Unlisted stores are not exposed, not enumerable, and their existence is not confirmable through the adapter (§2.2) |
| Live vs materialized | **Both, per store, chosen by owner configuration**; a query hint may narrow (force a fresh live read or pin a snapshot) but never widen. Default for any store not configured live-capable is **materialized snapshot** (§3) |
| Liveness | Live reads require a live bridge (an open tab on the origin, or the extension's background context) holding a heartbeat lease. No live bridge ⇒ a named `adapter_unavailable` outcome for the owner; for grantees the outcome is indistinguishable from "not granted" (§3.2) |
| Direction & writability | v1 is **read / materialize only**, per the parent's non-goal. No write-back to IndexedDB is designed here (§3.4) |
| Type mapping | Structured-clone values map to ID types per the table in §4. Functions, symbols, `Promise`, `WeakMap`/`WeakSet`, DOM nodes, and live handles (`Blob`/`File` in live mode, `IDBRequest`, etc.) are **unsupported** and named; cyclic values are rejected at materialization with a lossy-corner report entry, never silently truncated |
| Query shapes | Key lookup, key range, index range, and bounded full scan (cursor). Anything else is **refused with a named error**, never silently degraded to a scan (§4.3) |
| Storage | The adapter writes nothing to the origin's storage except a small bookkeeping store in its own database. Materialization into ID is bounded by a configured byte cap and a preflight quota check on the ID side; on the browser side the adapter must tolerate whole-origin eviction at any time (§5) |
| Credentials | There are none to store: IndexedDB has no credential separate from the browser profile and the user's per-origin consent in the bridge. The adapter conforms to the parent's "referenced, not stored" rule trivially — it holds a consent reference, never a secret (§6) |

## 1. What the parent already fixed (not re-decided here)

#5672 fixes, and this record takes as given:

1. **The grants model** — per-object and per-collection grants (with
   per-table/per-database as shorthand expanding to collections);
   grant dimensions of who / what / operations / duration; revocation
   stops future sync and access but cannot un-copy plaintext a peer
   already holds; delegation defaults to no and must be explicit,
   attenuated, and visible. The detailed design of the model itself
   is ticket #5799; nothing in this record changes a grant semantic.
   Collections in this adapter are object stores (§2), so a
   per-collection grant names exactly one store.
2. **Existence privacy** — partial replication and shared access must
   not leak counts, IDs, or metadata of ungranted objects. §2.2 and
   §3.2 apply this rule to browser storage: unselected stores are
   indistinguishable from nonexistent stores to anyone looking
   through the adapter, and a grantee cannot distinguish "store
   exists but is not granted" from "no such store", nor "bridge
   offline" from "not granted".
3. **The adapter-contract framing** (Part B, general): every adapter
   states how a foreign store is named/addressed, what schema/type
   mapping is promised, whether it is live or materialized, read-only
   vs writable, how credentials are handled (never in ID data itself;
   referenced, not stored), and the error/latency behavior when the
   foreign store is slow or gone. §2–§6 are exactly those six answers
   for IndexedDB.
4. **Non-goals for v1** — adapters are read/materialize-first; no full
   bidirectional sync with foreign stores; REDB remains ID's native
   store. §3.4 conforms.

This record proposes **no change to any parent decision**. Where a
question below is genuinely the parent's or #5803's to settle, it is
recorded as an open point with an assumed default (§6.2), not decided
here by silence.

## 2. Addressing and store selection

### 2.1 Address shape

IndexedDB is scoped by the web platform, not by ID: a database is
identified by (origin, database name) inside one browser profile, and
data lives in named object stores inside the database. The address
mirrors that exactly:

```
idb://<origin>/<database>/<object-store>
```

- `<origin>` is the serialized origin (scheme, host, port) of the
  page or extension context that owns the database, e.g.
  `https://app.example.com`. Opaque origins (sandboxed iframes,
  `file:` in some configurations) have no stable serialization and
  are **not addressable** in v1 — refused with a named error, not
  given a synthetic name that would collide across sessions.
- `<database>` and `<object-store>` are the platform names,
  percent-escaped. Names are case-sensitive and are never normalized.
- The **browser profile and bridge instance are part of the
  connection, not of the address.** The same address in two profiles
  is two different datasets that happen to share a name; an adapter
  endpoint binds an address space to exactly one (profile, bridge)
  pair, and a share or materialization records which endpoint produced
  it. Rebinding an endpoint to a different profile is a configuration
  change that invalidates existing snapshots' provenance (§5.3).

### 2.2 Selection: explicit allowlist, no discovery

An endpoint exposes only the (database, store) pairs listed in its
adapter configuration. There is no wildcard selection and no
"list all databases" operation in v1:

- `indexedDB.databases()` (where the platform even offers it) is not
  surfaced through the adapter. Enumeration of unselected stores
  would leak exactly the shape existence privacy (§1.2) forbids.
- A query against an unselected or nonexistent store returns the
  same outcome in both cases for any caller without owner
  credentials on the endpoint. The owner-facing configuration UI may
  distinguish them locally in the browser; the adapter wire surface
  may not.
- Selection is per store, not per database, because the store is
  the unit that maps to an ID collection (and therefore to a grant).
  Selecting a whole database is configuration shorthand that expands
  to its current stores at configuration time — the same expansion
  rule the parent's grants model uses for coarse grants — and does
  not auto-include stores created later.

## 3. Live vs materialized semantics

### 3.1 The two modes

- **Materialized:** the adapter reads a store through the bridge in
  cursor order and writes a snapshot into ID (REDB) with a recorded
  provenance: endpoint, address, snapshot time, store schema version
  (the database version and the store's key path / index set as
  observed), and a content digest over the snapshot. Queries then run
  against ID and never touch the browser. A snapshot is refreshed
  only by an explicit re-materialization or a configured schedule —
  there is no change-feed in IndexedDB to subscribe to, and polling
  is not disguised as one.
- **Live:** a query is forwarded through the bridge and executed as
  an IndexedDB read transaction at query time. The result carries
  the read timestamp; nothing is retained in ID beyond the query's
  own result handling.

Owner configuration chooses the mode per store. A query may carry a
hint to use a snapshot even for a live-capable store, or to require
freshness (live-or-fail) — hints narrow, never widen: a hint cannot
make a snapshot-only store answer live, and cannot make either mode
return a store that is not selected.

### 3.2 Liveness: the bridge must be alive, and silence is a result

Live access exists only while a **bridge** for the endpoint is
alive. For a page-owned database the bridge must execute in an
origin-resident context — a page open on the origin running the
adapter's bridge code, or extension content-script code injected
into such a page: IndexedDB handles opened from the extension's own
background context (service worker / persistent background page)
address the extension origin's storage, not the page's, so a
background context can never serve a page-owned database. The
extension background context may act as the bridge only for
extension-owned databases (databases under the extension's own
origin), and a bridge registration names which of the two cases it
is; an endpoint whose only live bridge is a background context is
`adapter_unavailable` for page-owned stores, never silently live. The
bridge proves liveness with a heartbeat lease to the ID side
(heartbeat interval and lease are bridge configuration; defaults are
an implementation choice, the lease must be short enough that a
closed tab fails queries within seconds, not minutes).

- Tab closed, browser closed, service worker terminated and not
  restarted, or database deleted in another tab ⇒ the endpoint is
  **down**, and live queries fail with the named outcome
  `adapter_unavailable`. `adapter_unavailable` is never converted to
  an empty result: "the store is empty" and "the browser is gone"
  are different facts, and conflating them would corrupt every
  downstream decision (this is the parent's "error behavior when the
  foreign store is gone" answer for this adapter).
- For a caller holding a **grant** rather than owner access,
  `adapter_unavailable`, "not granted", and "no such store" are one
  indistinguishable outcome (§1.2). The owner sees the distinct
  outcome; the wire format for grantees must not carry the
  distinction even in error text.
- `versionchange` / blocked-upgrade events: if another tab holds the
  database at an older version and blocks an upgrade the bridge
  needs, the bridge reports the endpoint as degraded (materialized
  reads continue from the last snapshot; live reads fail as
  `adapter_unavailable` with an owner-visible "blocked by another
  tab" detail). The adapter never force-closes another tab's
  connection.
- Materialized reads are unaffected by liveness. Staleness is
  surfaced, not hidden: every snapshot answer can report its
  snapshot time, and a query that requires fresher-than-snapshot
  data against a down endpoint fails rather than silently serving
  the snapshot.

### 3.3 Consistency within a read

A live read executes as one IndexedDB `readonly` transaction over
the stores it touches, so a single query sees one consistent store
state. A materialization snapshot is one `readonly` transaction's
cursor pass for the same reason. Cross-store joins are performed on
the ID side over snapshots or over per-store live results; the
adapter does not promise cross-store atomicity for live queries
spanning multiple transactions, and says so in the result metadata
when a query was split.

### 3.4 Writability

Read/materialize only in v1. Writing ID data back into a page's
IndexedDB raises consent, conflict, and partial-failure questions
(two writers, one of them the web app itself) that no parent ticket
has scoped; a follow-on design may propose it. Nothing in the
addressing or type mapping below forecloses a later writable design.

## 4. Type mapping: structured clone → ID types

IndexedDB values are structured-clone values, and record keys are
IndexedDB keys (number, string, `Date`, binary — `ArrayBuffer` or a
buffer view — or arrays of those). The
mapping is the adapter's promise; anything not in the table is
unsupported, by name, in §4.2.

### 4.1 Mapping table

| Structured-clone value | ID type | Notes |
| --- | --- | --- |
| `null` | null | |
| boolean | boolean | |
| number (finite) | float64 | Integers within the safe-integer range additionally carry the integer refinement; see `bigint` row for the boundary |
| `NaN`, `±Infinity` | — | **Lossy corner:** not representable as ID float64 values in query position. Materialization records them as the tagged string form in a wrapper record and lists the field in the snapshot's lossy-corner report; live query predicates over such values are refused |
| string | string | |
| `Date` | timestamp | Millisecond precision; dates outside the ID timestamp range are a lossy corner, reported as above |
| `ArrayBuffer`, typed arrays, `DataView` | bytes | The view's byte range, not the whole backing buffer, unless the value is the buffer itself |
| Array | list | Element type is per-element; heterogeneous lists are preserved |
| Plain object (incl. null-prototype) | record | Own enumerable string-keyed properties. Symbol-keyed properties are dropped and counted in the lossy-corner report |
| `Map` | record *or* list of pairs | If every key is a string, a record; otherwise a list of (key, value) pairs in insertion order. The choice is recorded in the store's mapped schema so it is stable per store |
| `Set` | list | Insertion order; duplicates impossible by construction |
| `RegExp` | record `{ source, flags }` | Queryable as data, not as a predicate type |
| `Blob`, `File` | bytes (materialized) / **unsupported (live)** | Materialization reads the bytes once and records size + digest + the original type/`name` (File) as metadata. Live queries may return metadata only; byte content requires materialization, because streaming a Blob through a query result has no ID-side type |
| Error objects | record `{ name, message }` | The stack is not carried (it is environment-specific text, and routinely contains paths); counted as a lossy corner |
| Class instances (non-plain prototypes) | record, **lossy — upstream, unobservable at read** | The prototype and methods are lost when the producer writes the value: structured clone serializes own enumerable properties and the stored value is already a plain object when this read-only adapter sees it, indistinguishable from an originally plain object. The adapter therefore cannot count flattened class instances, and the lossy-corner report makes no such promise: it reports only losses the adapter itself observes at read time. This upstream loss is observable only if the producer supplies explicit type metadata (e.g. a type tag written alongside the value); where such metadata exists the adapter surfaces it as provenance, it does not reconstruct the prototype |
| `undefined` | absent | A property whose value is `undefined` maps to the property being absent; a stored record that *is* `undefined` (possible with out-of-line keys) maps to a record carrying only its key |
| `bigint` | integer if it fits in signed 64-bit, else decimal string | Numeric predicates are refused over the string form |
| IndexedDB key (number / string / `Date` / binary / key array) | ID key | Binary keys map to ID bytes keys holding the key's byte sequence; their order is bytewise lexicographic over that sequence, which is exactly the IndexedDB binary-key ordering, so key lookups, key ranges, and materialization order are defined for binary-keyed stores and indexes. Cross-type key ordering follows the IndexedDB order (number < `Date` < string < binary < array). Key arrays map to tuple keys in order. Auto-increment (`autoIncrement`) and key-path extraction are schema facts recorded in the mapped schema; a store with out-of-line keys whose values lack their key maps the key as the record's ID key field |

### 4.2 Unsupported, by name

The following structured-clone-carrying values have **no** ID
mapping in v1 and make the containing record fail materialization
with a named error (and a lossy-corner report entry identifying the
store, key, and value kind — never the value): functions; symbols
(as values); `Promise`; `WeakMap`; `WeakSet`; DOM nodes and other
platform objects (`ImageData`, `ImageBitmap`, `OffscreenCanvas`,
`AudioData`, etc. — binary ones may be revisited individually, none
is silently mapped to bytes); `IDBRequest`/`IDBCursor` and any other
live handle.

**Cycles:** structured clone permits cyclic graphs; the ID record
model is a tree. A cyclic value is rejected at materialization with
the same named-error path; live mode returns the record as
unsupported. Unrolling or reference-table encodings are a possible
future extension and are explicitly not improvised here.

### 4.3 Query shapes the adapter promises

Against a store, live or snapshot, the promised shapes are: key
lookup; key range (bounded/unbounded, either direction); index range
over a declared index; bounded full scan (cursor with an explicit
row cap, returning a truncation marker when the cap is hit — a
truncated scan is never presented as a complete one). Predicates
that do not reduce to these (arbitrary predicates over record
fields, cross-store joins in one live query) are refused with a
named `query_shape_refused` outcome rather than silently degraded;
the ID query layer may still answer them over a materialized
snapshot, where the snapshot — not the browser — bears the cost.
This refusal discipline is the same principle the parent states for
the Postgres-over-HTTP adapter (B2): refused, not silently degraded.

## 5. Storage limits and eviction

### 5.1 The browser side: quota is shared, opaque, and revocable

IndexedDB storage is per-origin, shared with everything else the
origin stores, and governed by the browser: `navigator.storage.estimate()`
gives an estimate, not a promise, and under storage pressure the
browser may evict a whole origin's data (least-recently-used first)
unless the origin holds persisted storage (`navigator.storage.persist()`),
which the browser grants at its own discretion (engagement heuristics,
installed-app status, user prompt — platform-dependent).

Decisions:

- The adapter **owns exactly one database of its own** on the origin
  (bookkeeping: endpoint identity, snapshot provenance, consent
  record) and keeps it small — kilobytes, not data. It never writes
  ID data into the page's databases (v1 is read-only, §3.4), so the
  adapter cannot be the cause of the origin's quota filling.
- The bridge **reports** `storage.estimate()` (usage and quota,
  where the platform exposes them) and the persisted/not-persisted
  state with every snapshot and on liveness heartbeats. These are
  advisory facts for the owner, labelled as estimates.
- **Eviction is an expected event, not corruption.** If the bridge
  finds its bookkeeping database or a selected database gone
  (evicted, or deleted by the user or the web app), the endpoint
  reports the affected stores as `adapter_unavailable` (owner view)
  and marks existing materialized snapshots **orphaned**: still
  queryable as snapshots, permanently labelled with
  "source store no longer exists as of <time>", never silently
  re-linked to a later database that reuses the name. Name reuse is
  not identity.
- The adapter never requests persisted storage on the user's behalf
  for an origin it does not belong to (a page's origin is the page's
  to persist). The ID **extension's own origin** may request
  persistence for its bookkeeping database, and records whether the
  request was granted; lack of persistence is a durability warning
  on the endpoint, not a failure.

### 5.2 The ID side: materialization is bounded

A materialization is bounded before it starts, not after it hurts:

- **Preflight:** the bridge reports the store's record count
  (`store.count()`) and, where available, a size estimate. Two
  configured caps apply — a maximum record count and a maximum byte
  budget per snapshot (owner configuration; the adapter ships finite
  defaults rather than unlimited). A store over either cap is not
  partially snapshotted by default: materialization refuses with a
  named `snapshot_too_large` outcome naming the cap and the observed
  size, and the owner may raise the cap or select a key range to
  materialize instead (range materialization is a first-class
  option, producing a snapshot whose provenance records the range).
- **Receiving-side control:** consistent with the parent's
  receiving-side rule for shares (a peer can cap accepted share
  size, pause, or drop a share), a snapshot is droppable at any time
  without touching the source store, and dropping it is recorded.
- Refresh of a snapshot replaces it atomically on the ID side: a
  failed or interrupted refresh leaves the previous snapshot intact
  and labelled with its original time, never a half-written mix.

### 5.3 Provenance is part of the data

Every materialized record set carries: endpoint identity (profile +
bridge), full `idb://` address, snapshot time, database version,
mapped schema (key path or out-of-line keys, indexes, the §4 mapping
choices made for this store), content digest, and the lossy-corner
report (§4). Two snapshots of "the same" address from different
profiles are different datasets and are never merged.

## 7. Parent decisions: conformance statement

- **Grants model (#5672, detailed design #5799):** not re-decided.
  This record only fixes what a *collection* is for this adapter
  (one object store) so grants have something concrete to name.
- **Existence privacy (#5672, detailed design #5800):** not
  re-decided; applied in §2.2 (no enumeration) and §3.2 (collapsed
  grantee outcomes).
- **Encrypted shares (#5801) and public shares (#5802):** untouched.
  A public share can never be backed by an IndexedDB store in v1: a
  browser store is reachable only through a live, consenting profile,
  so it cannot meet the parent's "discoverable, queryable by anyone"
  bar; if a future design wants public browser data, it publishes a
  materialized snapshot (which is ID data by then, under the normal
  public-share rules), never the live store. This is an application
  of the parent's rules, not a new one.
- **Proposed changes to parent decisions:** none. Nothing found in
  this design requires one; per the parent ticket's instruction,
  had one been needed it would be recorded on #5672 explicitly
  rather than forked here.

## 8. Alternatives considered and rejected

1. **Database-as-collection** (address a whole database as one ID
   collection, stores as record kinds). Rejected: it breaks the
   grant unit — a per-collection grant could no longer name one
   store — and it forces one mapped schema across unrelated stores.
2. **Live-only.** Rejected: the bridge is alive only while a tab or
   the browser is open, so most stores would be unqueryable most of
   the time; the parent's own use cases (query foreign data from ID,
   including from other machines) need snapshots.
3. **Materialize-only.** Rejected: freshness-sensitive reads (the
   web app's current state) are the main reason to connect a live
   browser at all; snapshot-only would also hide the liveness facts
   §3.2 exists to surface. The pair (both modes, owner chooses)
   covers strictly more, at the cost of the §3.2 error discipline,
   which is needed either way.
4. **Eager whole-origin materialization** (snapshot every store on
   connect). Rejected: quota and privacy — it copies data nobody
   selected, into a second store with its own exposure, and §5.2's
   caps exist precisely to prevent unbounded copies.
5. **SQL-shaped translation over IndexedDB.** Rejected: IndexedDB
   has no query planner to translate to; §4.3's refused-not-degraded
   discipline is the honest version of the same surface.
6. **Synthetic names for opaque origins.** Rejected (§2.1): an
   unstable name that silently rebinds to different data is worse
   than a named refusal.

## 9. Invariants implementation must hold

1. An endpoint binds addresses to exactly one (profile, bridge)
   pair; rebinding invalidates snapshot provenance (§2.1, §5.3).
2. Unselected stores are not enumerable and not confirmable through
   the adapter by any caller (§2.2).
3. For grantee callers, "not granted", "no such store", and
   "adapter down" are one indistinguishable outcome — in codes and
   in error text (§3.2).
4. `adapter_unavailable` is never returned as, or converted into, an
   empty result (§3.2).
5. A snapshot is produced by one read transaction, replaced
   atomically, and carries the full §5.3 provenance including its
   lossy-corner report.
6. Materialization enforces its caps *before* copying; an over-cap
   store is refused or range-materialized, never partially copied by
   default (§5.2).
7. Every value in §4.2 fails by name; no value is ever silently
   truncated, stringified, or dropped without a lossy-corner entry.
8. A truncated scan is marked truncated; a refused query shape is
   refused by name; neither is silently degraded (§4.3).
9. The adapter writes nothing to any database but its own
   bookkeeping database, and nothing anywhere that contains a
   credential (§3.4, §5.1).
10. Eviction or deletion of a source store orphans its snapshots
    with a label; it never deletes them silently and never re-links
    them to a name-reusing successor (§5.1).

## 10. Splits and follow-ons

No further design split is needed: the four questions the ticket
posed are settled above, and the remaining unknowns are #5803's and
the parent's open points, already tracked there (§6). Implementation
is **not** filed from this record: per the parent programme,
implementation timing is a separate decision. When it is taken, the
implementation work is filed as its own ticket(s) referencing this
record and #5804 — one for the bridge + live reads, one for
materialization — rather than reopening this design.
