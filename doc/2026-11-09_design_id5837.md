    to this cluster — the v1 span (§2.3).

## 1. The one idea everything follows from

The graph view is **a view, not a model**. It renders one thing: the
viewer-filtered edge set of the existing link and tag projections
over #2048 objects at a named causal frontier of one store. It owns
no edges, stores no graph, and invents no relations. Every facet
below — local/global shape, edge types, filtering, scale, live
behaviour — is a consequence of that: anything the projections do
not assert is not in the graph, and anything the viewer may not read
never reaches the renderer.

## 2. Decision: local and global are two queries over one edge set

1. **Local graph is the default entry.** The local graph is the
   ego network of a focus note: the focus, its outgoing references
   and backlinks, expanded to a bounded depth (default 1,
   maximum 3) over the link projection. It is a query against the
   projection, not a separate data structure.
2. **Global graph is the same edge set, aggregated.** The global
   graph covers every note visible to the viewer in the current
   store scope, rendered only through the level-of-detail rules of
   §5 — never as a raw full render. "Global" means global *to a
   store and a viewer*: #2048 forbids a global index, and this
   record creates none; there is no cross-store graph in v1.
3. **Span: knowledge objects in v1.** This settles #5678's open
   question for this cluster: v1 nodes are #2048 notes (and tag
   terms, §3). The edge model is triples over stable IDs, so other
   ID objects (boards, files, chat) can become node types later by
   adding projections that assert edges about them — an additive
   extension, not a redesign — but no such projection is designed
   or implied here.

## 3. Decision: edge types are exactly what the projections assert

1. **Typed topic references** are the canonical note-to-note edges:
   the structured references of active revision heads (target note
   ID, sigil/type, authored surface, optional pinned revision),
   asserted by `note.link` events. The sigil/type is carried onto
   the rendered edge; the surface is display text, never identity.
2. **Backlinks are an inverse view, not an edge type.** A backlink
   is the same topic-reference edge read from the target side.
   Nothing stores, counts, or renders a backlink as a second edge.
3. **Tag edges** come only from the live-claim tag projection:
   `(note, tagged-with, tag-term)`, rendered with tag terms as a
   visually distinct node class, with claim provenance (supporting
   claim IDs and authors) available on inspection. A tag edge is
   never rendered as, merged with, or counted as a topic reference,
   and a cleared claim removes its support exactly as the triples
   record specifies — the visible tag edge survives while another
   live authorized claim supports it.
4. **A pinned revision is an edge annotation, not an edge type.**
   A reference pinning an exact target revision renders with a pin
   marker; the edge still names the target note. Following the edge
   lands on the pinned revision.
5. **Not edges in v1:** name/alias claims (resolution metadata, not
   relations), attachment containment, co-occurrence or inferred
   similarity, and presence/activity (§6.3). Each would need its own
   projection design asserting it as a triple before it can appear.

## 4. Decision: filtering is access first, then a query over triples

1. **Access filtering precedes everything and is not a user
   filter.** The edge set is first reduced to what the viewer may
   read under #5678's resolution order (object → user default →
   server config → public), using the projection's query-time
   access view: an edge to an inaccessible target is dropped whole
   (its existence is target metadata); a backlink from an
   inaccessible source is dropped with its surface (the surface is
   the source's authored content). The renderer never receives an
   edge it would have to hide — filtering out what must not be seen
   is the projection's job, not the client's.
2. **User filters are a query document over the triple model**,
   expressed in the programme's query direction (triples queried
   via SQL/PGQ shapes) and executed against the store's projection:
   edge-type and sigil/type toggles, tag include/exclude (by tag
   term ID, never by display string), depth and focus for the local
   graph, and label/text search scoped to content the viewer may
   read. There is no unfiltered full-graph download that the client
   then filters.
3. **Truncation is honest.** When a filter result or a §5
   aggregation cap cuts the edge set, the result says so (counts of
   what was withheld by the cap, never of what access denied). A
   partial graph never presents itself as complete.

## 5. Decision: performance — concrete scale target and budgets

1. **Scale target.** One store holding **100,000 notes and
   1,000,000 asserted edges** (topic references plus live tag
   claims) is the design point for every budget below. Vaults
   beyond it degrade by the same aggregation rules, not by failure.
2. **Local graph budget.** A depth-2 local query returns at most
   **500 rendered nodes** (focus-selected, highest-degree first,
   truncation signalled per §4.3) and answers in **≤ 100 ms p95**
   against a warm per-store projection on the local machine. The
   local graph never waits on a network round trip beyond the
   store query itself.
3. **Global graph budget.** The global view renders at most
   **2,000 node glyphs**: above that, the store-side query
   aggregates — low-degree notes collapse into cluster glyphs
   carrying their member counts, and only the top-degree notes
   render individually. Aggregation is computed by the triple query
   (degree and grouping over the projection), answers in **≤ 1 s
   p95** at the scale target, and the rendered cluster/count
   signalling follows §4.3. Client-side layout runs only on the
   aggregated glyph set.
4. **Projection cost.** The edge set is the existing incremental,
   rebuildable per-store projection; the graph view adds no second
   index and no write path. A full rebuild at the scale target is a
   background operation and is never on the read path of an open
   graph view.
5. These numbers are **acceptance budgets**: implementation must
   demonstrate them with a benchmark at the scale target (a
   generated 100k-note / 1M-edge store), not assert them from small
   fixtures.

## 6. Decision: multiplayer/live — a snapshot view over signed heads

1. **What a viewer sees.** A graph view is a snapshot: the edge set
   asserted by the revision heads present in the viewer's store at
   a named causal frontier. Two viewers at the same frontier see
   the identical graph — the projection fold is deterministic and
   arrival-order independent — and a view may name its frontier/age
   rather than pretend to be instantaneous.
2. **Live updates.** New signed events (revisions, `note.link`
   asserts, tag claims and clears) fold into the projection as they
   arrive; an open view updates by re-running its query against the
   new frontier. An edge appears exactly when its asserting
   revision becomes a head, and disappears when that revision stops
   being a head or the assertion is retracted. There is no separate
   live graph channel and no edge that exists only in a live
   session.
3. **Concurrent heads are shown, not resolved.** While a note has
   divergent heads, each head's references are edges of the graph,
   attributable to their source head (per #2048: divergent-head
   backlinks stay attributable until an explicit merge). The view
   never silently prefers one head. A merge revision replaces the
   divergent edges with the merged head's edges by the same rule
   as §6.2.
4. **Presence is not graph data.** Who is viewing or editing is
   ephemeral transport state: a note under live edit may carry a
   presence marker (collaboration rooms are keyed by stable note
   ID, per #2048), but uncheckpointed edits assert no edges, and
   presence never becomes a node or an edge.
5. **Consistency statement.** The model is eventual consistency
   with deterministic convergence: replicas that have folded the
   same events render the same graph, and a stale replica renders
   its own frontier honestly (§6.1). This is the #2048 editing
   model — explicitly not a CRDT and not a promise of conflict-free
   offline editing — restated for the view, not extended.

## 7. Rejected alternatives

1. **Render the whole vault client-side from a full edge
   download.** Rejected: it cannot satisfy §4.1 (the client would
   receive edges it must never see) and fails the §5 scale target
   by construction.
2. **Store backlinks as canonical edges.** Rejected: #2048 and the
   projection record make backlinks a derived inverse; a stored
   copy is a second source of truth that can disagree with the
   fold.
3. **One undifferentiated "links" edge combining references and
   tags.** Rejected: the triples record forbids inferring either
   from the other; merging them in the view would re-decide it.
4. **A cross-store / global index for a universal graph.**
   Rejected: #2048 says projections are per-store and "do not
   create a global index"; §2.2 scopes "global" accordingly.
5. **Live-first graph with edges asserted by editing sessions.**
   Rejected: only signed revisions assert references (#2048);
   session-asserted edges would be unattributable and
   non-convergent (§6.2, §6.4).
6. **Force-directed layout over the unaggregated edge set as the
   global view.** Rejected at the §5 scale target: layout cost and
   glyph count grow with the vault, not with what a human can
   read; aggregation (§5.3) is the global view.

## 8. Invariants implementation must hold

1. The view renders only edges asserted by the link and tag
   projections; it introduces no stored graph state of its own.
2. No edge, node, count, or surface reaches a viewer whom the
   read-authority resolution order denies; access filtering is
   applied by the projection query, never by the renderer.
3. Backlinks are always the derived inverse of outgoing references
   in active heads; divergent-head edges remain attributable to
   their source head until an explicit merge.
4. Tag edges keep claim provenance and are never presented as
   topic references, nor topic references as tags.
5. Every truncation or aggregation states itself (counts withheld
   by caps); a partial graph is never presented as complete.
6. At the §5 scale target, the local and global budgets hold under
   benchmark; the view adds no write path and no second index.
7. All replicas at the same causal frontier render the identical
   graph; presence and uncheckpointed edits assert no edges.
