# Track A — Distributed priority: state of the art and design space

**Research date:** 2026-11-13 UTC (retrieval occurred during this session, approximately 03:27–03:34Z; exact per-source request timestamps were not retained)
**Scope:** priority as a distributed contract spanning Fleet producers/consumers and PM/GitHub/hosted projections—not a replacement scheduler. Research-only; proposed directions are candidates for the parent design owner, not settled architecture or implementation authorization.

**Architecture alignment:** The parent has since recorded the shared direction in [`../architecture.md`](../architecture.md): existing broker authority, shared `Command`/`Result`, string-pair identity, authenticated principal separate from `actor_ref`, pinned snapshot evaluation, existing crate internal modules, granular blockers, and hosted conformance. That parent document governs shared interface details; this research remains comparative evidence and design rationale.

## 1. Research question and source requirements

Track A has to make one explainable urgency decision survive multiple writers and readers: human rulings, authenticated labels/comments/directives, work-item metadata, hard dependency changes, the existing Fleet queue/broker and claimant, Project/PM Stack projections, and eventual hosted targets. The governing handoff explicitly asks for precedence, stable identity, versioned payloads, provenance/reason codes, replay/reconciliation, and a way to validate cross-target ordering. It also says to reuse the current broker, keep the PM Project single-writer, and distinguish urgency, importance, effective scheduling pressure, workflow state, ownership, and one-shot dispatch directives. [Local intake: note.md §3, source 01 §§“Requirements that must survive refinement” and “Distributed priority”; source 02 §§3–9; source 04 Part 1 §§2–17; source 05.]

The historic score and exploration settings are **candidate configuration**, not mandates: lower numeric urgency is sooner; 450/High and the earlier 1000/default scale must map into the current ratified taxonomy without renumbering it; preserve 4% exploration, 3 distinct candidates, `r=1.25`, `d=200`, `alpha=0.5`, bucket width 200, and optional `epsilon=0.05` as testable candidate values only. A Do Now/direct-session instruction is a distinct dispatch directive and cannot turn into an urgency score or bypass authorization, lease/concurrency, or hard-blocker checks. Do not replace the source's 50→25/10/5/singles clumping example with a mandatory exact algorithm. [source 01 §§41, 53–59, 71; source 02 §§3–9; source 04 Part 1 §§2–17.]

## 2. What primary-source precedents establish

This is a selection of applicable mechanisms, not a claim that any one system implements Fleet's policy.

| Precedent | Documented mechanism | Transferable lesson / limit |
|---|---|---|
| Kubernetes Pod Priority and Preemption | Pod priority is a numeric ordering input; scheduler can preempt lower-priority pods when necessary. | Keep priority and resource/placement feasibility distinct; priority does not itself make an infeasible item eligible. **Do not borrow preemption** as a default for claimed agent work: a live lease/session has recovery and side-effect semantics unlike evictable pods. [S01] |
| Kubernetes API Priority and Fairness (APF) | API requests are classified into priority levels and flows; queues and fair dispatch control sharing of API-server concurrency. | Priority answers “which first”; fairness answers “who gets a share.” A deterministic top item alone can starve low-priority work. APF is request admission/concurrency control, not a drop-in backlog scheduling algorithm. [S02] |
| Temporal Workflows | A workflow's ordered event history records events; deterministic replay reconstructs state after failure. Signals are asynchronous state-changing messages; Updates are trackable synchronous requests with validation/acceptance/result; update IDs can support deduplication. | Borrow explicit durable command/message identity, ordered history, validation, replay constraints, and a distinction between accepted and completed. **Do not adopt a new Temporal-like runtime or event-store as a prerequisite**; its per-workflow histories and runtime are much larger than a priority contract. Replay of non-deterministic aging must pin time/policy inputs. [S03, S04] |
| CloudEvents | Stable event envelope has `specversion`, `type`, `source`, `id`; `source + id` identifies a unique occurrence; optional `subject`, `time`, `dataschema`; payload schemas can evolve separately. Spec advises compact events and linking to large data. | A useful minimum envelope for webhooks/commands and traceability, with Fleet-specific schema/policy version in the payload. It standardizes event format, **not** ordering, delivery guarantees, field authority, or priority semantics. [S05] |
| Kafka | Events sharing a key are placed in a partition; consumers of one topic-partition read in write order. | Key all priority-change events by canonical work-item ID if a log transport is ever used. Ordering is partition-local; it does not create a total order across keys, topics, snapshots, or external APIs. This is not a reason to introduce Kafka for the existing system. [S06] |
| SQLite / Turso (current storage family context) | SQLite provides serializable transactions by serializing writes (one writer at a time); WAL allows concurrent readers/writer snapshots, not simultaneous writers. Turso's Embedded Replicas docs say reads are local, writes by default go to the remote primary and then update the initiating replica (read-your-writes); other replicas observe changes on sync/periodic sync. Turso distinguishes the newer local-first Turso Sync product. | A single-writer authority and transactionally paired state/outbox fit the current broker boundary. Define what snapshot/version a consumer observed. Do not infer cross-region linearizability, conflict semantics, or ordering beyond the exact deployed Turso product/API; verify those against the repo's actual connection path before design freeze. [S07, S08] |
| GitHub webhooks and Projects | GitHub asks webhook receivers to return 2xx within 10 seconds, recommends async work for longer processing, exposes `X-GitHub-Delivery`, and reuses the delivery ID on redelivery. Projects are API-readable/writable projection fields/items and expose item `POSITION`; GraphQL mutations can update fields. | Persist/ack quickly, deduplicate deliveries, then enqueue a command; separately reconcile Project desired/observed state. The GitHub Project's visible position is not enough to establish Fleet's canonical score, policy version, or atomic ordering across surfaces. [S09, S10] |
| Linear project priority and Jira ranking | Linear documents optional priority groups and manual reorder within a priority group. Jira documents manual ranking and rank/board configuration; Atlassian's LexoRank support material discusses rebalance and rank-length/system maintenance. | Useful UX precedent: categorical priority plus a human-controlled within-group order; rank is a separate field from priority. Sparse/fractional lexical keys can postpone bulk shifts but need collision and rebalance procedures. Vendor internals are not a guarantee that a DIY rank is safe or cross-target portable. [S11, S12] |

### Primary-source evidence caveats

The cited public docs establish only the listed behaviors. In particular, CloudEvents is an envelope, Kafka partition ordering is not global ordering, and a Project's `POSITION` is projection-local. Linear/Jira pages document product UX, not underlying public API consistency guarantees. Turso's embedded-replica docs are not evidence about the exact `libsql`/Turso deployment used by this repository. The sources do **not** prove current Fleet producer authority, current live queue semantics, exact hosted implementation, or actual deployed schemas; those remain census/repository/deployment evidence work, not this report's assumptions.

## 3. Four distinct architecture shapes

These alternatives are deliberately different. Recommendation below favors the smallest change that fulfills the contract, subject to the repo census and Queue Table Improvements compatibility.

### A. Existing broker as canonical authority; versioned command and projection snapshots

Treat authorized external edits as **commands** to the current Fleet broker, not independent owners of the canonical score. The shared command interface carries `(authority_id,work_id)` string identity, operation/idempotency/request digest, actor/source refs, expected work version, reason/evidence and snapshot reference; authentication supplies principal/capabilities (a client actor ref is not authorization). The broker accepts canonical changes and required operation intent under the shared local-transaction contract; the existing creation outbox is not evidence of an already-general outbox. PM Project, labels, hosted targets, and claimant read versioned observations. Consumers compare authority-qualified identity + work revision + policy version; projections report their observed revision/watermark and reconcile forward.

* **Ordering/precedence:** Explicit precedence table in the contract. Suggested candidate: authorized human exact-score/manual ruling wins over lower-authority derived suggestions; an authorized priority-label edit is a normalized command (add/change maps to configured band; removing the final label preserves score and requests triage); dependency pressure and deadline/opportunity are derived, not score writes; directive and hard eligibility are separate. Project field writes remain through one orchestrator. Concurrent stale commands reject or become explicit conflicts rather than silently last-write-wins.
* **Cost:** Ranking `O(N log N)` for a full eligible snapshot/sort; indexed/top-k selection can reduce typical query work, but only if eligibility and effective score indexes remain consistent. On one item, durable history/outbox write is `O(1)` plus projection work. Reconciliation scans are `O(N)` per full pass, avoidable with dirty-item indexes plus periodic full audits.
* **Advantages:** Reuses current broker/claim transaction and established single-writer projection; simplest authoritative order; easy to explain and compare across deployment targets; no event-bus dependency.
* **Risks:** Broker is a write/availability bottleneck; strict synchronous external fan-in requires durable intake; careful contract/version migration needed; keeping event history purely as an audit record does not provide arbitrary full-state reconstruction unless snapshots and policy versions are retained.
* **Fit:** Best V1/V2 candidate if the repository census confirms current broker is the canonical queue boundary and supports an atomic state+outbox write. This is a recommendation, not a pre-judgment of schema ownership or Queue Table Improvements.

### B. Event-sourced priority aggregate and rebuildable projections

Each work item has an ordered log of accepted domain events (priority assigned, manual override, label command normalized, dependency edge changed, boost expired). A reducer under pinned policy produces current canonical state, while Project/labels/hosted views are rebuilt projections. Durable checkpoints/snapshots cap replay.

* **Ordering/precedence:** Per-item event sequence is authoritative; event ID idempotency plus expected aggregate revision detects concurrency. Cross-item dependencies need graph-version/snapshot semantics; per-item sequences alone cannot give a consistent whole-queue instant.
* **Cost:** Append `O(1)` per accepted event; replay from checkpoint is `O(k)` recent history per item and full rebuild `O(E)` events plus projection writes; large payloads and replay fanout dominate. History retention, compaction, policy-version compatibility, and event migration are permanent operational costs.
* **Advantages:** Excellent provenance, reason-code/audit fidelity, deterministic replay, historical “why was it ranked so?” answers; projections are replaceable and hosted parity can consume the same contract.
* **Risks:** Much more architecture than the user asks for; mutable external facts need correction/compensation events; old reducer versions must remain replay-compatible; graph-derived urgency can have cross-item snapshot drift; storing every low-value recalculation creates noisy history and payload skew.
* **Fit:** A future seed if audit, event volume, recovery, or projection divergence justifies it. Do not adopt a standalone event store merely to get reason codes; the broker can retain append-only decision records and versioned snapshots first.

### C. Federated intent reconciliation (systems stay authorities for their own fields)

Human intent can originate in GitHub labels/comments, PM mobile/API actions, queue metadata, or a hosted service. Each source emits a signed/identified intent; a reconciliation layer resolves field-specific authority and writes canonical Fleet state, then publishes projections. This is federation of **inputs**, not peer replicas of the same score.

* **Ordering/precedence:** Per-field authority and source revision are mandatory. Source clocks alone are unsafe for precedence (clock skew, webhook delivery delay); use broker-assigned revision, expected-version CAS, or explicit conflict queue. One authenticated user's separate commands still need deterministic arbitration; “last observed wins” is not equivalent to “last intended.”
* **Cost:** Routine ingestion/reconciliation `O(events)`; recovery scan `O(N)` plus remote pagination/rate-limit and outbox retries; identity mapping and reconciliation cursors add steady-state complexity. Large webhook payloads should be normalized to compact intents and retain references/hash rather than duplicate documents.
* **Advantages:** Allows usable PM/mobile and GitHub control surfaces; protects canonical ownership while supporting multiple input routes; aligns with single-writer Project projection and GitHub's at-least-redelivery behavior.
* **Risks:** Human-facing conflict UX and source attribution are harder than local sorting; stale replicas may show old rank; exactly-once external delivery cannot be assumed; many consumers can accidentally create feedback loops unless outbound projections are recognizable and idempotent.
* **Fit:** Needed at the boundary even if A is chosen. Use it for authenticated commands and reconciliation, not for multi-master score writes or a generic CRDT ranking field.

### D. Lease-time derived scheduling (canonical intrinsic fields; effective order computed at claim)

Persist intrinsic urgency, distinct importance if adopted, state/ownership, directive, dependency edges, and evidence; calculate effective scheduling pressure at selection from current eligibility, dependency, deadline/boost, lane capability, fairness state, and policy version. PM displays both base and derived explanations; claim revalidates all predicates and records the decision snapshot.

* **Ordering/precedence:** Base score/manual source stays durable; derived score is a function of a named policy version and an identified queue/dependency snapshot. Hard blockers gate selection before sorting. Manual ordering may remain secondary rank; fairness may adjust lane choice separately without mutating intrinsic urgency.
* **Cost:** Naive per-claim all-work scan is `O(N)`; graph-derived computation over reachable subgraph is `O(V+E)` worst case; cached incremental values reduce common reads but require invalidation/reconciliation on changed edges, boost expiry, and time. For large candidate pools, index only mathematically safe prefilters and always revalidate before claim.
* **Advantages:** Avoids priority inflation and stale effective-score storage; time and dependency effects remain explainable; policy changes can be shadow-evaluated; aligns with source distinction between intrinsic and effective urgency.
* **Risks:** Ordering changes when the same data is evaluated at a different time/policy version; projections can disagree without recording inputs; computational tail latency and graph cycles; deterministic urgent order can starve ordinary work unless fairness is explicitly modeled.
* **Fit:** A useful policy boundary layered on A; scope effective pressure carefully and keep formulas in a versioned contract. Avoid “compute everything afresh from all services on every claim.”

## 4. Cross-cutting design analysis

### Authority, precedence, and causality

Define **field authority**, not a universal producer hierarchy. Distinguish at least: (1) human-authored intrinsic urgency/importance/override; (2) authorized external input command (label normalization, slash command, mobile action); (3) system-derived effective pressure and age/boost evaluation; (4) workflow state/lease; (5) one-shot `do_now`/`direct_session`, separate from the ratified `expedite=15` band; `manual_only` is persistent eligibility, not a directive; (6) projection-only values such as display band or Project position. Use the common `Command` fields and snake_case wire names from `architecture.md`; do not create an independent schema or a client `authorized` flag. Keep sensitive/untrusted comment text out of public audit detail unless existing retention/security policy permits it.

Precedence should be an ordered decision table, not whichever system delivered last. Candidate semantics worth testing: explicit authorized manual score beats automatic aging/clump moves; high-confidence verified incident/deadline can bypass hysteresis but not field authority; dependency pressure is effective-only and cannot rewrite intrinsic priority; external priority label maps through configured normalization and removal preserves canonical score while setting needs-triage; a Do Now request changes directive/dispatch receipt but not score/eligibility; stale `expected_revision` requires retry/triage rather than blind overwrite. The full source list remains non-renumberable: live urgency means lower numeric value is sooner.

### Versioned payloads, replay, and reconciliation

Use the shared `Command`/`Result` in `architecture.md`, with snake_case wire keys and `(authority_id,work_id)` string identity; unsafe integer-like IDs/revisions/ranks use canonical decimal strings. Keep command schema, priority profile, taxonomy mapping and derived-policy versions distinct. CloudEvents `source/id/type/specversion` remain an envelope precedent, not Fleet's wire contract/version authority. Operation/idempotency key + request digest, source delivery reference, per-work version, relay lease generation and cross-item read snapshot are distinct identities. Never use timestamps for write ordering. The shared comparator is hard eligibility, effective urgency ascending, exact peer rank within equal effective urgency, creation time, then normalized authority-qualified identity.

For replay, reconstruct only from accepted normalized commands/decisions and pinned inputs. Time-sensitive evaluation pins as-of time, boost/deadline evidence, graph/work snapshot and policy hash; otherwise replay today can differ from yesterday. Use shared `Result` outcomes/effects to distinguish requested, observed and verified state. The existing creation outbox is not evidence of a general priority/lifecycle outbox: required canonical-state + journal + remote-intent local transaction is a future implementation contract, not current proof. Full rescan is recovery oracle; incremental dirty sets are optimization. GitHub redelivery ID deduplicates transport; shared idempotency key + request digest deduplicates semantic commands.

### Ordering across broker, GitHub, PM board, claimant, and hosted targets

A total order requires the same authority-qualified canonical identity, profile/taxonomy, policy, eligibility/capability and graph snapshots, as-of time, and tie keys. Matching is two conjunctive predicates: task requirements satisfied by claimer **AND** claimer's explicit filter matches task. Both default empty/true; OR/NOT only compose inside that filter expression. A task requiring `platform=linux` is not claimable by Windows claimer even if caller filter `repo=code` matches. Broker atomically rechecks both predicates, hard gates, work version and lease. Comparator is effective urgency, exact peer rank within equal urgency, creation time, normalized authority-qualified identity. Project `POSITION` and vendor rank are view-specific; before/after routes through Fleet rank command within equal effective urgency, cross-urgency requires explicit urgency change or conflict. Hosted fixtures compare same authority and snapshot.

### Dependency inversion, inheritance, and cycles

Analogue to priority inversion: a high-urgency eligible task is blocked by a low-urgency hard prerequisite, while unrelated work runs. Candidate response is *bounded effective pressure* on true hard blockers along the dependency path—not changing the blocker’s intrinsic value. Explain the path (`blocked item → blocker`, downstream score, edge type, path, cap, effort/alternatives); cap propagated urgency and consider blocker effort/availability and alternate paths so one low-value blocker does not become Emergency just because it blocks many items. Advisory/parent/related edges never inherit urgency or block claim.

With canonical hard-block direction blocker→dependent, adding `u→v` creates a cycle iff `u=v` or current graph has directed path `v→u`; check that exact orientation. Serialize edge writes or validate the graph revision atomically. Concurrent opposite-edge requests `A→B` / `B→A` must not both pass independent checks against the initially empty graph; one commit wins and the other rechecks/rejects. Worst-case reachability is `O(V+E)` for the checked component. Effective-pressure traversal uses visited nodes and a deterministic graph revision. Incomplete evaluation fails closed rather than silently truncating blockers. For accepted DAGs, full recomputation is topological `O(V+E)`; per-item invalidation marks downstream dependents. Do not emulate OS lock-owner priority inheritance literally: no preemption or resource-owner semantics are implied here.

### Aging, hysteresis, and anti-oscillation

Bidirectional aging should be an evidence-backed triage proposal or a deterministic derived factor, not a daily score write that accumulates unbounded drift. Use last meaningful triage/evidence time, opportunity expiry, progress/pivot signals, and bounded review intervals. A temporary boost has start/expiry and explicit `retriage` behavior; expiry is an event/input, not deletion of base score. Hysteresis at band crossings requires a configured boundary, confidence threshold, cooldown, and named bypasses (authorized manual move, verified deadline/incident/high-confidence blocker); each change retains previous/new values, reason, evidence, confidence, policy version, and event ID. Bound ordinary automated moves per item per sweep and require an evaluation oracle that demonstrates both promotion and de-escalation; age alone never guarantees Critical.

### Sparse rank, collision, and rebalance

Urgency score and within-score manual order are separate. Equal urgency is valid; deterministic fallback is necessary even with equal score. The source explicitly requires before/after placement, so manual peer order is not a speculative need. Candidate: exact signed integer peer rank within equal **effective** urgency, represented losslessly across JSON/Rust/TypeScript; null legacy rank normalizes to common `0`, with created-at and authority-qualified identity as final ties. A move across urgency requires explicit score-change confirmation/conflict, not hidden rank override. Options for storage/allocation: sparse integer gap keys with rank epoch and deterministic bounded local rebalance (preferred candidate); fractional/lexicographic keys (collision/key-growth and rebalance); ordinal position (`O(N)` rewrites). Jira documents a mature rebalance problem for LexoRank; that supports treating rebalance as first-class, not copying its implementation. Rebalance uses rank epoch and local group revision/lock; stale neighbors conflict, bounded local range uses fixed stride, and oversized window fails atomically. Never encode order by nudging urgency scores or use binary floating-point rank keys.

### Deterministic urgency versus fairness and density-corrected exploration

Keep **normal selection** and **exploration** separate. Normal selection is highest effective urgency among hard-eligible items for a compatible lane, then deterministic tie-break, with atomic claim revalidation. Fairness is a lane/worker allocation constraint (for example, bounded service shares or aging a lane's opportunity), not random perturbation of the canonical urgent ordering. A strict global urgent-first queue can starve cold work; a fairness mechanism should have explicit limits and preserve urgent-work service objectives. APF is useful precedent for separating priority from fair concurrency shares, but it is not the same problem.

Exploration is only eligible when no Emergency/Supercritical/Critical/Do Now work **requiring this lane** is being starved. Sample three distinct eligible candidates without three exclusive claims; persist every disposition before extended work and make unfinished decisions recoverable. Preserve historic candidate config as simulation hypotheses, not production mandates: 4%, 3 candidates, `r=1.25,d=200,alpha=.5,width=200,epsilon=.05`. Lower score has higher weight; density uses unique eligible identities in the pinned population. Freeze density and compute initial masses once: `q_i=(1-epsilon)*Pweighted(i)+epsilon/N` (or `Pweighted` at epsilon zero); draw without replacement by removing selected mass and renormalizing remaining fixed `q_i`, without recomputing density/weights/epsilon. Test first draw analytically and later marginals against exact sequential fixed-mass oracle. Do not fabricate importance; any future axis mixture is a separate policy.

Verify behavior under duplicate/reordered webhook deliveries, stale snapshots, partial projection failures and replay; preserve fail-closed eligibility and visible degraded/stale status. Hosted parity means same semantics, not identical storage implementation.

### Candidate design decisions for parent (not decided here)

* Prefer broker-authoritative canonical state with normalized external commands + versioned snapshots (A+C), and derive scheduling pressure at a pinned claim snapshot (D). Retain event-sourced provenance as compact append-only accepted decisions; defer full event sourcing (B) until evidence justifies its maintenance cost.
* Do not call this a “distributed scheduler”: there is one reusable existing Fleet broker/claim authority, with distributed producers and projection consumers. Do not create a second queue, scheduler, database, or frontend scoring engine.
* Prefer explicit field-level command precedence and optimistic version checks over last-delivery-wins or peer-to-peer conflict resolution. Make the highest-authority path and rejection outcome visible to operators.
* Treat a PM board order action as an authenticated command to shared Fleet service; keep Project as projection/control surface and single writer. Avoid promising a Project's rendered order equals the broker's total order unless its supported view/order semantics are verified.

### What not to borrow

* Kubernetes preemption/eviction for active Fleet sessions: an active worker has leases, checkpoints, remote side effects, and recovery obligations.
* A new Kafka/event-bus, Temporal runtime, generic CRDT/multi-master score, or global event store just because those products solve related problems at larger scale.
* A single priority number that folds importance, dependency, deadlines, workflow state, lane eligibility, ownership, and Do Now together.
* Last-write-wins based on arrival time, webhook order, local clocks, or UI drag order across multiple services.
* Automatic score uniquification, unbounded score drift, age-only Critical escalation, dependency propagation through advisory edges, uncapped graph recursion, or exploration claims without recorded disposition.
* Persisting time-dependent “effective score” without its policy version, as-of input, and dependency snapshot; or ranking one surface using hidden UI-only state.

## 6. Offline conformance and simulation specification (no production code)

The following is a **test design proposal**. The oracle for each test is explicit; this report does not implement it.

### Deterministic contract conformance oracle

Build a small reference evaluator from the approved contract, not production implementation code. Input fixture includes string-pair `(authority_id,work_id)` identities, intrinsic urgency, optional importance, status/lease, lane capabilities, task requirements, caller filter AST, typed dependency DAG, deadline/boost evidence and expiry, shared commands with actor/source refs/idempotency key/request digest/work version, as-of time, policy/taxonomy version, and expected outputs. Authenticated principal/capabilities are test context, never a client `authorized` field. Oracle is the reference model plus invariants:

1. **Sign and separation:** lower urgency sorts sooner; changing `do-now` never changes intrinsic score; importance never appears from null; blockers affect eligibility/effective pressure only; advisory/parent edges do not block.
2. **Stable total order:** same authority/snapshot and contract version yield byte-identical ordered identity pairs; equal effective urgencies permit exact rank; created-at then normalized identity breaks remaining ties; source-surface serialization order does not change result.
3. **Authority/concurrency:** high-authority manual command accepted; principal lacking capability rejected; stale `expected_work_version` cannot overwrite accepted newer value; same idempotency key+digest returns original operation while changed digest conflicts; label removal preserves score and yields needs-triage.
4. **Dependency graph:** with blocker→dependent edges, adding `u→v` is rejected iff `u=v` or current path `v→u` exists; test serial opposite-edge insert pair to prove concurrent write revalidation. Imported cycles terminate/quarantine; hard-blocker path/cap is explainable; stale graph revision forces rescore before claim.
5. **Aging/hysteresis:** week-old still-valuable Medium can move up with evidence; post-pivot High can move down; a low-confidence boundary oscillation is suppressed during cooldown; manual/verified bypass works; boost expiry removes boost and triggers retriage; no item auto-rises past configured ceiling from age alone.
6. **Reconciliation/replay:** replay accepted events under pinned policy/as-of/snapshot recreates canonical snapshot hash; duplicate and reordered remote deliveries converge to same broker state; outbox failure remains pending/retryable and remote verification prevents duplicate side effect; compare desired/observed watermark finds drift and full-rescan repairs projection.
7. **Hosted parity:** run identical fixture corpus against each target contract adapter and compare normalized output (IDs, eligibility, score components, tie fields, reason codes, policy version), not database row layouts.

### Property/model-based generators

Generate (a) score arrays with dense clusters/ties/cold backlog/shuffled input; (b) both independent matching predicates, including OR within filter expression but AND between task requirements and caller filter; (c) typed DAGs with opposite-edge concurrent writes/cycles; (d) duplicate/reordered commands, stale work versions, competing authorities and delayed webhooks; (e) boosts/deadlines around expiry; (f) lane/capability/eligibility variations; and (g) projection outages/retry histories. Invariants: no unauthorized transition; no duplicate accepted operation for same key+digest; one accepted work version has one predecessor; fixed snapshot order is deterministic; hard-ineligible item never claimed; dependency traversal is bounded; replay parity holds; projection drift converges or is visibly conflicted/stale.

### Statistical exploration oracle and evidence

For each candidate tuple (including 4%, 3, `r=1.25`, `d=200`, `alpha=.5`, width 200, optional `epsilon=.05`), run a deterministic seeded simulator across synthetic and scrubbed/representative anonymized queue shapes: uniform scores; large same-score clumps; heavy-tail cold backlog; sparse eligible lanes; mixed skills/ownership; hard dependencies; urgent arrivals during exploration; score ties; changing eligibility; and importance absent/present. Sample **without replacement** from the eligible pool; never claim the draw set as a side effect. Use explicit oracle/statistics:

* Independent implementation of weight/probability calculation; exact fixed-mass `q_i` sum tolerance and no-negative/NaN weights.
* Seeded Monte Carlo first-draw frequency vs analytical `q_i`, and later marginals vs exact sequential renormalization over frozen initial `q_i` masses, with preregistered confidence intervals/tolerance—not “looks random.”
* Measure per-band/per-density-bucket inclusion rates, cold-item time-to-first-review, high-urgency service/latency, starvation probability, lane workload fairness, and exploration-trigger suppression when qualifying urgent work exists. Define acceptable thresholds with owner rather than inventing thresholds in this report.
* Compare baseline uniform and no-density-correction controls; demonstrate density correction mitigates, but does not erase, large-cluster advantage; optional epsilon mixture is incorporated once before drawing and remains fixed through conditional removal/renormalization.
* Keep every disposition durable in model state; crash/restart simulation confirms selected/triage/defer/release intent is recovered and no second exclusive lease is acquired.

The simulator can establish policy behavior against synthetic assumptions, not production benefit or live dispatch proof. Use production-like read-only snapshots and observed distributions before enabling anything; do not turn a simulation pass into a migration/dispatch approval.
