# Track B state of the art: work-item lifecycle and reliable orchestration

**Research date:** 2026-11-13 UTC (2026-11-12 America/Chicago). **Scope:** research input for #9196/#9206–#9209, not an implementation report or a settled ADR. Repo-specific claims below are grounded in the preserved intake documents and the pinned census, not a live deployment check. Proposed behavior is distinguished from verified platform behavior. Keep the existing Fleet queue, storage, services, and multicall binary; this research does not authorize a second database/queue/scheduler or production/schema/dispatch change.

**Route context:** this worker was explicitly assigned `opencode-route/workhorse`; it is not an authorization or recommendation to change live routing. No route configuration/usage was inspected or changed as part of this research.

## Executive findings

1. Work identity is the pair `(authority_id, work_id)`, both serialized as strings; `fleet://work/842` is shorthand only in unambiguous local authority context. Keep typed, many-to-many external refs using stable provider/repository/resource IDs; GitHub owner/repository/number is a locator, not a global Fleet identity. Follow shared `../architecture.md` wire contract (snake_case, decimal strings for unsafe JSON integers, authenticated principal for auth), not a component-specific identity or envelope.
2. Model operations as durable intents plus observed effects. A local transaction can atomically persist Fleet state and an outbox intent; it cannot atomically commit GitHub's mutation. Outbox delivery is at-least-once. Stable IDs, idempotent set-state operations, remote read-before-retry, and post-write verification produce *effectively-once where the remote API permits*, never universal exactly-once.
3. A lease alone does not fence an already-running remote request. Use a monotonically increasing local generation/fencing number and verify it at every Fleet write/transition. Before an external side effect, check lease generation; after it, record the result conditionally on that generation, but retain the remote effect even if the worker became stale. GitHub does not accept the Fleet fencing token. For irreversible remote writes, use operation-specific remote preconditions (notably PR head SHA on merge), and reconciliation/compensation rather than pretending the remote honors the lease.
4. Complete directly: after the command verifies each requested GitHub effect, it must atomically close Fleet work and record the verified receipt without waiting for webhook/polling. If acknowledgment is lost, `completing` is a durable recovery state: read remote state, verify the same requested effect, and finish locally. Never equate accepted merge request with merged (the async API distinguishes queued/accepted from completed).
5. Use controller-style reconciliation for recovery, but keep the normal synchronous completion path explicit. Webhooks are hints/low-latency triggers, not truth or prerequisites. Controllers are eventually convergent; direct completion is required for immediate user-visible correctness.
6. Hydration and incremental activity need per-resource/per-endpoint cursors and durable page ingestion. A timestamp is not a total-order cursor: comments can be edited, records deleted/minimized, page boundaries shift, and a response can be interrupted. Persist each page's items/events and next cursor atomically; advance only after durable processing; overlap/re-read and deduplicate by source-native stable ID plus revision/updated-at. Surface uncertain attribution and partial retrieval.
7. GitHub's public issue-comment API documents create, update-by-ID, pagination, updated timestamps, and IDs, but no idempotency key or conditional `If-Match` contract for comment/body mutation in the endpoint contracts reviewed here. Managed body/comment edits therefore need read/merge/re-read conflict checks and an explicit conflict state; markers help discovery, not atomic uniqueness. Comment creation's “search then create” has a race. Prefer one known comment ID; for first creation, tolerate duplicate race with reconciliation and avoid promising exactly one.
8. Keep the CLI contract small and composable: explicit Fleet work ID, typed resource refs, operation/idempotency key, expected Fleet version/fence, machine-readable result/error envelope, dry-run/verify/wait. Stable error codes and partial effect receipts matter more than a large set of one-off subcommands.
9. Typed edges need orientation, kind, hardness, status/history, source/provenance, and uniqueness; validate hard dependency cycles transactionally. Preserve resolved edges. Private notes and append-only journal events are distinct from public comments and mutable projections.

## Evidence and implications by design seam

### Work identity, lifecycle, and CLI surface

**Proposal.** `WorkId` is a stable Fleet identifier. External refs are normalized tuples (`provider`, `account/owner`, `repository`, resource kind, stable remote ID, display number); one Fleet item can link to many. Enforce unique link identity but allow association lifecycle (active/superseded/unlinked) and audit. Distinguish lifecycle state (`available`, `claimed`, `in_progress`, `parked`, `blocked`, `completing`, `completed`, `cancelled`, `failed`) from GitHub issue/PR state and lease (`holder`, `session`, `generation`, expiry). Use transitions with explicit preconditions, not arbitrary status assignment.

CLI primitives operate on one explicit resource/aggregate and return a versioned JSON envelope (`schema_version`, `operation_id`, `work_id`, `state_version`, outcome, effects[], warnings[], next_action). Domain errors carry stable `code`, retryability, conflict/current-version, field/resource, and remediation; partial success is a successful transport response with an explicit incomplete domain outcome, not a generic opaque failure. Human output is a renderer of the same result. High-level `work next/open/park/resume/complete` compose the same commands/services; no alternate policy engine. Require `--work` when repository/issue resolution is ambiguous. Use an idempotency key scoped to actor + operation + canonical request digest; reusing key with different digest is a conflict.

Examples of stable errors: `NOT_FOUND`, `AMBIGUOUS_RESOURCE`, `INVALID_TRANSITION`, `LEASE_LOST`, `FENCE_STALE`, `VERSION_CONFLICT`, `DEPENDENCY_BLOCKED`, `DEPENDENCY_CYCLE`, `REMOTE_CONFLICT`, `REMOTE_UNAVAILABLE`, `HYDRATION_INCOMPLETE`, `COMPLETION_PARTIAL`, `IDEMPOTENCY_KEY_REUSED`. Include retry hint (`never`, `after_refresh`, `same_key`, `operator`) and operation receipt. Do not expose secrets or confuse HTTP/API errors with domain errors.

### Transactional outbox and completion

Microservices.io's outbox pattern stores the message in the same local database transaction as aggregate change, then a relay sends it; the relay can publish twice if it crashes after publication but before recording success, so consumers must be idempotent ([S1]). For Fleet this guarantees durable intent, **not** remote exactly-once. An operation record should have immutable operation ID + request digest, aggregate/version, actor/session, fencing generation, target, expected precondition, state (`pending`, `delivering`, `confirmed`, `conflict`, `retryable`, `terminal`), attempt timestamps/count, remote IDs/result, and verification evidence. Lease the outbox row for relay work with a relay-generation fence; old relay cannot finalize a row after a newer relay takes it. Remote effect may nevertheless have happened; reconcile by reading remote state before retry.

Recommended completion protocol (design candidate):

1. In a short local transaction: verify lifecycle/version/lease generation/dependencies; record `completing`, expected PR head SHA/check policy, requested issue refs and stable completion operation IDs/outbox rows. Do not hold a DB transaction over network calls.
2. Refresh actionable external activity and preconditions; if a new external review/comment/commit changes task assumptions, pause in `completing`/conflict with exact cause. This is a best-effort freshness check, not a global lock against GitHub changes.
3. Execute each remote effect idempotently or conditionally. For PR merge, submit expected head SHA; GitHub REST merge documents 409 on SHA mismatch. For async merge, 202 means accepted for background processing and its merge-queue result may be merely enqueued; wait/verify actual merged state (S2). Close issues only when authorized and explicitly selected.
4. Verify each effect from authoritative API reads; record effect receipt and observed IDs/SHA. If remote succeeded but process lost the response, query and identify the requested effect before retry. If cannot distinguish, retain `unknown`/`needs_reconcile`; do not duplicate non-idempotent creation.
5. In one local transaction conditional on expected local state (but not requiring a still-active worker lease once operation is valid): append final event, set completed only if all required effects verified, store receipt, release ownership. If external effects partial, remain `completing` with per-effect statuses; never falsely claim all-or-nothing.

Direct verified local completion in step 5 is part of the initiating `work complete --wait --verify` command. The same command may return `pending_remote`/`partial` on timeouts; retries resume by operation ID. A later reconciler can finish the same operation but is not required in normal success.

### Leases and fencing

Kubernetes Lease docs show leases as coordination/heartbeat and leader-election primitives, including holder identity, duration, and renew time ([S3]); a lease's expiry is not itself proof an old process stopped. Fleet needs local compare-and-set semantics: claim atomically increments monotonically increasing `fence`; every Fleet mutation checks `(work_id, holder/session, fence, expiry)` in the same transaction. Expiry test uses the database's time source and a documented clock-skew bound; clients do not supply authoritative time. Renewal must be conditional on current generation. A reclaimed item gets a strictly higher generation; old worker writes fail.

Critical limitation: an external service is fenced only if it validates the token. GitHub REST merge accepts an optional head SHA precondition, but no Fleet token; comment creation/update APIs likewise do not expose fencing. A stale sender can pass a local check, pause, lose lease, then send. Reduce window by authorizing remote operation durably first, capturing its generation/operation ID, and treating that already-authorized intent as a saga step—not by claiming lease revocation cancels an in-flight request. A newer owner must see pending operations and either wait/reconcile or explicitly supersede only safe operations. Remote operation IDs in body markers can correlate, not prevent stale write. Completion should be operation-scoped: once a remote merge has been authorized and accepted, recovery may finish its receipt even if the original lease expires; it must not authorize unrelated later mutation.

### Hydration, cursors, and attribution

GitHub pagination docs require following response `Link` URLs; endpoint docs impose per-endpoint caps (for example PR commits list max 250 and files max 3000 in S2). Therefore manifest records each source/endpoint, API version, fetched-at, page count/next link, resource IDs, freshness and truncation/errors; never call a capped result “complete” absent explicit cap handling. Keep content artifacts outside queue row; manifest hashes and provenance tie the bundle to source snapshots.

Comments API exposes stable comment IDs and `updated_at`, sorts issue comments by ascending ID, supports `since` based on last update, and paginates; a page can omit deletions/old records or edits to old IDs if relying on creation cursor only ([S2]). Use separate cursor per `resource + endpoint + filter + API version`, persist pagination checkpoint and ingested records atomically. Cursor can be opaque continuation token or `(max stable ID, observed update watermark)` with a deliberate overlap; do not advance on request completion alone. Re-read recent overlap and dedup by source ID; detect edits by updated_at/revision/body hash; deletions/minimization require event feed or periodic full reconciliation where available. `occurred_at`, `observed_at`, and `source_updated_at` are distinct. Pagination is not a consistent snapshot: mark generation and completeness; a late mutation can fall behind page boundary, so overlap + reconciliation is necessary.

Attribution is first-party operation-ID mapping: Fleet records which outbound operation/session caused remote change and maps returned remote IDs. GitHub actor identity alone is insufficient when sessions share an app/bot. Unknown attribution remains `uncertain`; external-only includes uncertain changes unless user explicitly chooses otherwise.

### Managed content and comments

GitHub issue comment contract provides POST create and PATCH an existing known ID with body; it does not document conditional version/ETag requirements in those endpoint specs ([S2]). Do not assume a server-side compare-and-swap. For a managed body section: GET latest body; locate unique delimiters; compare section's last Fleet hash/revision with stored baseline; preserve outside bytes; if section changed since baseline or delimiters malformed/duplicated, mark conflict; compose candidate; PATCH; GET and verify exact managed section and outside-region preservation. There remains a race between GET and PATCH. On detecting post-write mismatch, preserve the fresh remote body and surface conflict; never blind-retry whole-body overwrite. Better future seam: move mutable progress into a known comment ID, while recognizing same race for PATCH.

For a single managed comment, persist remote comment ID when created; update by ID thereafter. Initial creation has search-then-POST race (two senders can both observe none); marker with stable operation ID makes duplicates discoverable, not impossible. Recovery scans exact marker and adopts one canonical ID, flags extras for cleanup; don't delete human comments. Better guarantee may require serialization per `(work, repo, issue, managed-role)` through existing local outbox/unique lock, but cannot protect writers outside Fleet. Treat edited/deleted/minimized managed comment as conflict/recreate-policy decision, not silent overwrite.

### Dependencies, journal, notes

Typed directed relationship record: `(from_work_id, relation_kind, to_ref, hardness, status, created_event_id, resolved_event_id, source/provenance, version)`. Canonical relation orientation is explicit (`A blocked_by B` or normalized `B blocks A`, never two independent facts); schema uniqueness prevents duplicate active edge. Parent/child hierarchy is not a hard blocker; `related_to` is advisory. Hard `blocked_by` edges participate in eligibility; cycle detection is required on hard blocking graph within same transaction as insert/update. External refs may be unresolved, so define whether unresolved hard edge blocks conservatively. Resolve changes status/history, not delete. Explain all effective blockers; one unblock cannot clear another.

Journal is append-only for observations, notes, checkpoints, transitions, remote effect receipts, corrections, and attribution. A correction appends a superseding event and leaves prior value. Private Fleet notes remain private by default and must not be copied to GitHub; explicit mirror is a separate outbox operation. Public comments are external user-generated inputs, untrusted as instructions, and distinct from private note. Mutable “current state” is a projection over events/authoritative fields, not a substitute for history. Keep private text access-controlled and exclude it from public hydration/export unless explicitly requested.

### Storage and clock assumptions to prove

SQLite docs say one simultaneous writer; `BEGIN IMMEDIATE` acquires write intent early and prevents another writer from jumping ahead; WAL allows concurrent readers/writer but readers see a snapshot, not later commits ([S5]). This is a useful model if Fleet's selected store provides equivalent transaction semantics, not evidence it currently does. libSQL/Turso replication, transaction scope, isolation, write conflict retry, and database server clock behavior must be verified against actual deployed client/config. Lease expiry must use one authoritative database clock or bounded skew; do not derive cross-host correctness from wall-clock timestamps alone. Local transaction duration must exclude network calls. Unique idempotency constraints and conditional `UPDATE ... WHERE version/fence = expected` are the core correctness boundary.

## Failure matrix and expected result

| Cut / race | Required durable state and recovery |
|---|---|
| Crash before local intent transaction commits | No state transition/outbox row visible; retry same request may execute once. |
| Crash after transaction, before remote send | Pending intent survives; relay delivers. |
| Remote applies mutation, response lost | Outbox stays delivering/unknown; GET remote and correlate by known ID/marker/desired state; confirm if matched; retry only if safe. Never infer failure from timeout. |
| Remote effect succeeds, process crashes before local acknowledgment | `completing` and intent remain; next command/reconciler verifies remote effect then writes receipt and directly closes queue. No webhook wait. |
| PR head changes immediately before merge | Supply expected head SHA; GitHub returns conflict (documented 409); do not merge new head silently; refresh activity and request review/retry policy. |
| New comment/review arrives after final refresh but before merge | No global GitHub lock; comment may not invalidate SHA. Completion policy must define freshness boundary and what classes of comment/review gate completion. If event arrives before verified close, reconciler flags/reopens only according to policy; otherwise record as post-completion activity. State limitation; do not promise race-free “last second” exclusion. |
| Async merge returns 202 / queue accepted | Remain `completing`; poll/read operation/result and PR state. Do not mark merged from accepted/enqueued acknowledgment. |
| Issue close succeeds, PR merge fails | Partial effect receipt; remain `completing`/blocked; do not rollback by reopening issue automatically; next action explicit. |
| Worker lease expires while request in flight, new owner claims | Fence stops old worker's local writes; remote request may still take effect. Preserve authorized operation receipt and reconcile; new owner sees pending remote operation and cannot duplicate it. |
| Stale outbox relay returns after relay lease stolen | Its conditional outbox-row finalization fails by relay generation. Remote effect may have happened; newer relay verifies before retry. |
| Fleet DB clock jumps / clients disagree | Use DB clock and fencing; record expiry only as liveness hint; monotone fence is authority. Alert if clock invariants unavailable. |
| Last-page/pagination interrupted | Persist page items + next cursor atomically; no cursor advance without durable item processing; resume exact page/link, deduplicate IDs. |
| Comment edited/deleted between pages or `since` polls | Re-read overlap; track ID+updated_at/content hash; full/incremental reconciliation catches deletions where API allows; report known blind spots. Never call a creation-ID cursor complete for edits. |
| Attribution same app user, multiple sessions | Match outbound operation ID/remote ID, not actor name; otherwise `uncertain` and include in external activity. |
| Managed body changes externally between GET and PATCH | No CAS guaranteed by reviewed endpoint contract; post-write GET detects divergence but cannot prevent clobber at precise race. Restrict patch to merged latest body; retain snapshots and emit conflict; no blind retry. |
| Two workers create managed progress comment concurrently | Local unique serialization prevents Fleet/Fleet race; external/nonparticipating writer may race. Search marker and adopt one, flag duplicates, do not claim exactly-one. |
| Comment ID lost after POST timeout | Search exact stable operation marker before POST retry; if one match adopt; multiple mark conflict; none may be eventual consistency, so retry policy must delay/recheck rather than duplicate blindly. |
| Dependency edge races with reverse edge insertion | Unique transaction + cycle validation serializes graph edit; one fails `DEPENDENCY_CYCLE`; no partial edge. |
| Cursor advanced but event write failed | Forbidden by atomic ingest+cursor transaction; tests assert no skipped item. |
| Completion webhook delivered twice | Event dedupe on provider delivery ID plus effect idempotency; duplicate is no-op and no duplicate journal/transition. |
| Remote verify unavailable | State is unknown, not success/failure; leave recoverable, surface `REMOTE_UNAVAILABLE`; don't close Fleet item. |

## V2/V3/V4 roadmap and contract recommendations

**V2 — settle contracts before shared schema changes.** Freeze Fleet ID/resource-ref normalization; lifecycle transition table; lease/fence/version semantics; CLI result/error envelope; operation/idempotency identity; outbox state transitions and remote effect receipt; hydration manifest/cursor semantics; typed dependency orientation/cycle rules; private-note/public-comment boundary. Decide completion gates and meaning of `--wait` (wait until terminal or timeout; return partial receipt). Record storage assumptions against Queue Table Improvements. No migration implied.

**V3 — staged implementation as linked issues.** First tests/model for claim and state machine; transactional intent/idempotency and journal; hydration/cursor; dependency graph; comment/body conflict policy; outbox executor/reconciler; completion saga and direct local close; webhook dedupe. Migration/backfill/rollback separately gated by Queue Table Improvements and current database authority. Each unit is independently deployable behind capability/config where needed.

**V4 — hosted parity.** Preserve contract and conformance tests across fleet binary and hosted PM/Fleet boundaries. Reuse service/API and existing source-of-truth owners; do not duplicate scheduler/database. API contract compatibility is versioned; hosted target may differ internally but must pass identical transition, fence, idempotency, cursor, and completion scenarios. Validate route-specific scaling/latency and retention before claiming parity.

### Concrete contract shortlist

- Claim transaction: conditional eligible-state update + fence increment + lease record + append claim event, one commit; return secret lease token only if required by existing authority, never expose in logs. All subsequent local writes carry `expected_version` and generation.
- Operation record: immutable `operation_id`, idempotency key/digest, `work_id`, kind, target ref, request/expected state, originating session, authorized fence, attempt state, remote effect ref, verification result. Unique `(actor, idempotency_key)` and same digest retry returns original receipt.
- Cursor: `(source_ref, endpoint, query_shape, api_version, cursor_generation, opaque_position, high_watermark, overlap, last_durable_event_id, status, checked_at)`; page ingestion + cursor advance atomic; manifest reports complete/partial/truncated/unavailable.
- Activity item: source-native stable ID + revision/update marker + created/occurred/observed/source-updated + actor + operation attribution confidence + immutable payload/artifact ref.
- Dependency: typed relation, explicit hardness, status, provenance and history; graph mutation validates cycle and version atomically.
- Completion response: requested/verified effects, remote refs/SHA, queue state, final operation ID, `complete | partial | pending | conflict`, exact next action. “Verified complete” means all policy-required remote states read back and Fleet local terminal transition committed.
- Managed content: baseline digest + managed-region digest + returned remote ID + operation marker; conflict policy explicit. Never silently overwrite user-owned region.

## Test design: model/property/concurrency/crash oracles

These are design/test requirements, not tests claimed to exist. Use a small executable reference model for lifecycle, lease generation, outbox/effect status, cursors, and dependency DAG; generated command sequences compare implementation to model (MBT). Property invariants: at most one active lease generation per work item; fences strictly increase on reacquire; stale generation cannot mutate lifecycle/notes/completion; completed implies all required effects verified; an unverified or unknown effect never yields completed; each logical idempotency key has at most one operation row and same digest yields same operation ID; cursor never exceeds highest durably processed page; duplicate source event does not duplicate journal effect; active hard dependency graph acyclic; resolved history retained; outside managed region unchanged in conflict-free patch; private note never appears in public mirror absent explicit consent.

Inject crash at every local transaction boundary and every remote send/response/verify/ack boundary; restart and assert eventual same terminal state as reference model, no duplicate non-idempotent effect, and no false completion. Deterministic fake GitHub oracle records calls and supports apply-then-timeout, 409 SHA mismatch, delayed async merge, stale ETag/changed body, edit/delete/minimize, pagination insert/edit between pages, duplicate webhook, unavailable read, and comment create race. Concurrency tests run two claimers, two dependency edge insertions, two same-key requests, two outbox relays, stale owner/new owner, and `complete` against new activity. Oracle must be named: reference state machine, invariant, exact fake remote state/call ledger, or golden serialized contract. Add real API contract smoke tests only as separate integration evidence; mocks prove orchestration logic, not GitHub production semantics.

## Evidence limits / open questions

- This is state-of-art/research, not a pinned-revision census. Need #9198 to establish existing queue schema, actual storage/service reuse, transaction behavior, outbox implementation, lease/claim invariants, GitHub adapter, PM projection ownership, and hosted service boundaries.
- GitHub docs were fetched as public API reference; the API behavior in an actual target repo/app installation, permissions, branch rules, merge queue policy, rate limits, and point-in-time API version require integration verification. The endpoint contracts reviewed do not establish comment ETag/CAS support; do not infer absence across every GitHub API version/product without testing or further docs.
- GitHub's merge SHA precondition closes the changed-head race for that merge request, not late comments/reviews. No API can provide a transaction spanning issue comments, PR merge, Fleet DB, and issue closure.
- “effectively once” is an operational guarantee scoped to recognizable/idempotent effect types and retention horizon, not universal delivery semantics.
- Temporal docs establish its durable execution model, not a recommendation to adopt its service; adoption cost/availability/integration with the Fleet environment is unresearched.
- SQLite docs are platform reference; don't assume the queue DB is SQLite. Need actual libSQL/Turso semantics, remote transaction size, and clock source evidence.
- Controller reconciliation describes convergence, not prompt SLA. Cadence and repair ownership should be specified using existing fleet schedules and queue workflows.

### Existing PM projector as a bounded V1 observation adapter

Pinned source `pm-stack/projector` is relevant integration substrate, not a competing authority or scope limit. `src/webhook.ts:7–28,31–57` bounds the raw body and validates HMAC-SHA256 via constant-time byte comparison; `src/server.ts:150–199` requires delivery ID/signature before apply and records `github:<delivery>` freshness identity; `README.md:23–30` lists existing supported GitHub event kinds and per-`(repo,stream)` reconcile cursors. Tests `test/webhook-delivery-id.test.ts:90–155` prove bad signature/missing GUID leave projector tables and freshness sink untouched and same GUID applies once; lines 157–180 prove retry behavior when the freshness sink fails. `src/reconcile.ts:211–243` stores a cursor per repo/stream; `test/reconcile.test.ts:62–137,237–267,286–359` covers pagination and stream-level cursors. `src/store.ts:602–739`, `README.md:145–179`, and `test/hot.test.ts:65–117` establish projector hot events with stable event IDs, bounded pages, server-issued high-water and monotone consumer acknowledgment. The ACK protocol expects consumer-after-sweep ordering and server-checks monotonicity/bounds; it cannot verify consumer-side durability. `README.md:3–8` explicitly calls projector disposable/rebuildable glue that does not write back to GitHub/Kaneo/Pad/Grist; `README.md:113–133` describes queue-view consuming an exported broker task JSON plus hot list in read-only JSON/HTML with no broker fetch or persistence.

Design consequence: #9203 should reuse HMAC/authenticated ingress and avoid a second webhook verifier; forward an authorized command through the shared command interface. Distinguish transport `x-github-delivery`, projector `event_id`, Fleet `operation_id`, and remote-effect/outbox ID. Projector delivery dedup/application is not Fleet command acceptance or verified effect. #9207 may consume the hot feed or repo/stream reconciliation as a source adapter, with source confidence, but retains Fleet's own durable cursor ingestion, hydration provenance and operation attribution; a hot-list checkpoint is not Fleet page durability. #9209 keeps operation/outbox truth in canonical Fleet authority, never disposable `pmp_` projection tables. No general Fleet journal, all-provider API coverage, session attribution, merge outbox, or completion guarantee is established by this projector evidence. Tests/source are pinned evidence, not deployment evidence.

Parent architecture supersedes a possible ambiguous reading of the census/one-queue prose: eligibility requires both task requirements and claimant filter predicates (logical AND, each defaults true/empty); identity is not a hidden filter. Persistent `manual_only` is an eligibility property, not Do Now. The architecture also fixes `(authority_id, work_id)` identity and shared wire envelope, makes #9073–#9076 consume-only existing metadata/session interfaces, and keeps the exact storage/CLI ownership boundaries in one `architecture.md`. Existing Fleet `gh.rs` is the adapter; do not create `fleet-gh`. These are design rulings, not source/deployment facts.
