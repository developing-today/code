# Fleet priority, urgency, PM Stack visibility, and direct dispatch

**Track:** A · **Status:** integrated design proposal; no implementation, migration or rollout authorization.  
**Scope:** priority dimensions/distribution, triage, selection/exploration, PM/mobile projections and control, authenticated event/direct-dispatch paths.  
**Shared contract:** [`architecture.md`](architecture.md). **V1 evidence:** [`census/track-a.md`](census/track-a.md), [`census/track-b.md`](census/track-b.md). **Requirements:** [`components/9198-requirement-crosswalk-current-state-census.md`](components/9198-requirement-crosswalk-current-state-census.md).

## 1. Outcome and boundaries

The existing Fleet queue/broker remains the target claim and canonical work-state authority. Multiple authenticated producers submit field-scoped commands; PM Stack, GitHub labels and hosted services consume versioned observations or route authorized commands through the same boundary. This is a shared command/projection design, not multi-master priority replication or a new scheduler. The target does not erase current nonconforming producers: pinned PM dispatch still has a Supabase/PostgREST enqueue/task-PATCH path tracked by #9028; reconcile or quarantine it before canonical dispatch cutover. Temporary adapter forwards only, no dual writes or fallback bypass.

Do not create another queue/database/scheduler, PM authority, GitHub client, secret resolver, or browser-side policy engine. Project #4 remains single-writer through the orchestrator. Existing Fleet `gh` / #9016 is the GitHub operation boundary. Existing PM aggregator/action/projector interfaces remain projections/control intents, not canonical claim order. #9079/#9081 are future hosted consumers. Schema-coupled work is gated on QTI/#9241 and #3424/#8575/#8579 compatibility; offline contracts and reference models can proceed.

## 2. Priority model and authority

All priority-write paths also enforce the existing Drew-only protected expedite policy in
[`architecture.md`](architecture.md#protected-owner-priority-policy). Generic manual permission,
automatic triage, mutable labels and hysteresis bypass cannot amend its membership/value/rank.
The exact byte-framed digest DTOs and domains in the shared architecture are normative;
track-level summaries are not alternate wire protocols.

Keep intrinsic urgency, nullable importance, derived effective pressure, workflow/readiness, ownership/lease, peer rank, provenance, and one-shot directive separate. Lower numeric urgency is sooner. Preserve exact `expedite=15` / `next-up=25` as the #7030 ratified stored bands; current `resolvePriority` snapping `15→10`, `25→20` is a compatibility defect. Do not re-ask ratification, silently round, transplant charter `450/1000` into live values, or turn `expedite=15` into Do Now. Do Now changes one-shot dispatch handling only. Persistent `manual_only` is eligibility and cannot be bypassed by Do Now.

For an authorized command, authenticate principal/capabilities outside client-provided `actor_ref`; enforce field/action authority, expected work version, source/event identity, policy/taxonomy version and reason/evidence. Explicit manual decisions outrank automated suggestions within assigned field authority; stale writers conflict, not timestamp-LWW. Label additions/removals are normalized commands; removing final priority label preserves score and requests triage. Projection echoes do not become new human intent. Dependency/deadline/opportunity factors may affect effective pressure but cannot silently overwrite intrinsic value. Explain every computed result against pinned policy, inputs, as-of time and graph snapshot.

The principal authority/provenance contract and source-specific alternatives are detailed in [#9200 §§29–99, 124–153](components/9200-priority-distribution.md); dimension, taxonomy, tie rank, aging/hysteresis and dependency pressure details in [#9199 §§22–68](components/9199-distributed-priority.md). Proposed corresponding records: [FDR-PMO-001](decisions/FDR-PMO-001-canonical-broker-command-seam.md), [FDR-PMO-002](decisions/FDR-PMO-002-priority-profiles-ordering-provenance.md).

## 3. Deterministic eligibility, order and fairness

Candidate inclusion requires **both** task-declared requirements of the claimant and the claimant's explicit filter of tasks; each empty predicate is true. Apply hard eligibility after those predicates: lifecycle, blockers, capabilities, ownership, lease/concurrency, policy, manual-only and valid complete graph. A PM projection, sorted list or exploratory sample cannot grant a lease. Claim atomically validates item/work version, graph revision, active policy/profile, lane/ownership/lease inputs and time-sensitive conditions at broker-authoritative time; stale snapshot means recompute/reselect or typed stale result. If a target cannot provide this, it cannot advertise atomic claim capability.

Within a fixed authority/lane snapshot: compare effective urgency ascending, exact explicit rank among equal urgency, creation time, then canonical identity: `authority_id` bytewise, and this queue's unsigned decimal `work_id` by arbitrary-precision numeric order (digit count then digits), not lexical string order. Thus 9 precedes 10; opaque provider/session IDs remain opaque and are never parsed as work IDs. This numeric comparison preserves V1 list tie behavior and is distinct from RFC 8785 property-name ordering used for intent digests. Equal urgency is legitimate. Support before/after peer order and audited bounded rank rebalance; cross-urgency movement requires explicit urgency change or conflict. The current claim query lacks a final ID tie and differs from list order; fix with compatibility fixture rather than claim existing determinism. Hard blockers use blocker→dependent graph orientation, cycle-safe serialized edits and fail-closed incomplete evaluation. See [#9204 §§21–44](components/9204-queue-selection-bounded-exploration.md) and #9199 §“Candidate order and rank semantics”.

For new work-command v1 intent fingerprints only, use RFC 8785 JCS plus SHA-256 and a purpose/version separator over the validated/default-expanded typed intent DTO. Do not rewrite the legacy creation-outbox hash. Reject duplicate JSON properties, invalid Unicode/surrogates, non-finite values and lossy numeric IDs before hashing; preserve string values without Unicode normalization. Exclude operation/key/delivery IDs, timestamps, output/wait/timeout and dry-run mode; changed target/args/preconditions/reason conflict. Recheck current authorization independently of matching digest. Rust/TypeScript golden vectors and manifest self-digest exclusion belong to existing `CLI-02` and `HYD-01` fixtures; this is a design constraint, not shipped behavior. See [RFC 8785 evidence](research/canonical-json-evidence.md).

Normal selection remains deterministic urgent-first. Fairness is a separate lane/worker service-allocation policy, not random score perturbation; #8097 owns actual filtered lane set. Its objective/thresholds remain open to owner measurement, not invented. Exploration is a separate feature-disabled sampler, eligible only when no qualifying urgent work requiring that lane is delayed. Historical 4%, three candidates, `r=1.25`, `d=200`, alpha .5, width 200 and epsilon .05 remain hypotheses for simulation; do not apply broad-scale `d=200` blindly to live 10–90. Freeze eligible population/density/initial masses, sample without replacement, persist every disposition before extended action; only selected item goes through ordinary claim. Sampling creates no lease and no automatic priority change. Importance remains null unless independently sourced.

## 4. Producers, consumers, PM and direct dispatch

Producers: authorized human/CLI, PM action, signed GitHub event/comment, priority-label input, dependency event and approved policy triage. Consumer/effect boundaries: Fleet broker owns accepted work/urgency and atomic claim; Project orchestrator is sole writer; GitHub owns its issue/PR content and discussions; session provider owns session state; hosted #9079/#9081 implementations consume shared schemas. A single shared `Command`/`Result` handles commands, with delivery ID distinct from event/resource revision, request idempotency and per-item accepted revision. Older events cannot overwrite newer accepted state; missing/unordered revision triggers fresh read/triage, not timestamp LWW. Uncertain/unattributable events remain visible.

PM mobile is a source-freshness-aware projection with preview/action intents through shared Fleet operations. Offline board is read-only; stale drafts require fresh preview and reconfirmation. UI must not calculate canonical urgency/order, mutate Project/GitHub/queue/session directly, or infer active execution from label, queue row or shell alone. Receipts distinguish accepted request, running, pending sync, partial/conflict/uncertain and verified effect. Preserve the original 15 mobile actions in #9201 §3.3; accessibility and latency figures there are acceptance targets, not measured V1 facts.

Reuse the existing `pm-stack/projector/src/webhook.ts` bounded HMAC ingress and delivery-dedup/read-projection hot ledger as an authenticated intake seam. Do not create a second webhook service or place canonical policy/remote mutation authority in the projector: it is disposable projection glue. Projection delivery ACK is distinct from accepted Fleet command. After ingress, authorize/resolve/normalize and durably accept a typed operation at canonical Fleet authority. Never execute comment shell text or let classifier authorize. On active work, route only to verified bound capable session. Parked direct start is explicit authorized action through #9178/#9179 gates and canonical reservation; it does not just raise priority. Stage receipts separately: requested, adapter accepted, session created, task bound, prompt delivered, acknowledged, meaningful progress, terminal. Ambiguous launch timeout must reconcile before retry; no blind duplicate start. #8187 remains baseline but does not satisfy #6533 live launch-and-bind proof.

See [#9201 §§1–3, 5](components/9201-pm-projection-mobile-control.md), [#9203 §§1–3, 5–6](components/9203-direct-dispatch-slash-commands-event-routing.md), and source/census evidence. Direct dispatch V3 requires #9028 reconciliation; actual #6533 acceptance remains separate.

## 5. End-to-end scenarios

1. **Label reprioritization:** signed authorized label addition → delivery/event idempotency → resolve stable repository/resource/work identity → lossless #7030 profile normalization → expected-revision command → accepted broker revision/journal/remote intent → Project writer projection → readback receipt. Duplicate delivery is a no-op. Removal of final label retains score and sends triage request, not emergency or execution.
2. **Mobile reprioritize / Do Now:** user sees source/revision/explanation, previews typed action, server reauthenticates and checks revision; urgency write and directive are separate effects. Hard blocker/manual_only/lease/capacity cannot be bypassed. Stale preview conflicts and requires reconfirmation.
3. **Active-session comment:** signature and actor permission pass, strict command or triage classification; current task/session binding and adapter send capability read back. Deliver message with operation ID, record accepted/delivered/ack separately. Bot name alone does not establish session origin.
4. **Parked direct start:** authorized `/fleet start`/mobile intent does not wait in normal queue. Resolve task, inspect park and hard blocker, apply current #9178/#9179 rule, revalidate both claim predicates and concurrency at atomic claim; then launch, bind session, verify prompt delivery and meaningful progress. Any ambiguous response reconciles by operation key before retry; no second session.
5. **Exploration:** same lane snapshot shows no urgent eligible work requiring lane; sample three unique candidates without claiming, persist select/triage/defer/release dispositions and evidence; only selected candidate attempts normal claim after fresh urgent-gate and eligibility recheck. Crash preserves dispositions but no unsupported score mutations.

## 7. Alternatives and explicit non-goals

Prefer one broker plus field-scoped command ingress over multi-master/LWW/CRDT canonical urgency: source clocks and delivery order cannot settle human authority, and multiple queues undermine one claim order. Defer Kafka/global event bus, Temporal runtime, new scheduler, and full event store absent measured scale/reliability need; they do not fix remote API atomicity. Keep compact append-only accepted decisions and projections first. Project position is not canonical claim order. Don't convert urgency into one scalar mixing importance, lifecycle, dependency, directive and eligibility. Do not infer project/epic closure as child completion. Details of alternatives and complexity are in #9200 and prior art `research/track-a-state-of-art.md`.
