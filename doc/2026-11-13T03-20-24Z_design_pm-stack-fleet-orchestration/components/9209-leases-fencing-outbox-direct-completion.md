## 2. Alternatives and recommendation

### A. Lease/worker-ID only (reject as stale-write safety)

Expiry supports recovery/liveness, but an expired worker may continue and write after another worker claims. Existing lease metadata is useful baseline, not proof of fencing. Adding a random bearer token improves authentication if secret-handling contract exists, but random token alone does not order generations or stop external request already in flight.

### B. Monotone compare-and-set fence + expiry hint (recommended local authority)

Each successful claim/takeover increments per-work-item integer `fence_generation`; claim transaction validates current eligibility and writes holder/session, lease-until, generation and work version. Every local mutation includes expected generation/version and performs conditional update/append in same transaction. Generation strictly increases at reclaim; old process fails `LEASE_LOST`/`FENCE_STALE`. Lease token may be opaque capability if existing Fleet auth boundary supports it; do not treat it as replacement for generation. Store/service DB clock is authority for expiration, not client clock. Expiry enables takeover but itself does not stop old process. Atomic claim revalidates current status, eligibility, dependency, lane requirements and lease at commit, not just earlier selection.

### C. Full Temporal execution service (defer platform adoption)

Provides durable orchestration/replay, timers, retries and activity histories but does not make GitHub side effects transactional or exactly-once; Activities still require stable operations and idempotent/reconcile logic. New service/worker/SDK/runtime and migration are out of scope. Reuse explicit saga lessons from Temporal; no Temporal deployment absent separate architecture decision.

### D. Controller/reconciler (use as recovery mechanism)

Reconciliation repeatedly compares intended effect to remote observed state and repairs/records divergence. It is well-suited for stuck outbox and missed webhook recovery but eventually consistent and cannot be the normal direct completion dependency. Keep reconciliation inside existing Fleet service/ops mechanisms; no new scheduler. Existing fleet schedule registry must be updated if an actual recurring schedule is later approved.

### E. Dual write or webhook-only completion (reject)

DB+GitHub cannot be one transaction; dual-write crash creates untracked effect. Webhooks can duplicate/miss/delay and cannot close Fleet synchronously. Use local transactional outbox plus direct remote readback and local finalization; webhooks are hint/recovery.

## 3. Lease/fencing and existing one-queue contract

### 3.1 Claim semantics

One queue is the only queue; per-repo `queue` value is a stream label, not an isolated queue. Eligibility requires **both** task requirements and claimant filter predicates (logical AND, default true/empty). Identity is not an implicit filter. Persistent `manual_only` is eligibility, not Do Now; honor #9178's explicit authorized manual claim/takeover/resume paths where allowed, without bypassing hard blockers or active leases. `work next --claim` atomically revalidates predicates. If a candidate changed, reselect under policy or return typed conflict. Honor #9179 park semantics. `BATCH_CLAIM_MAX` remains unresolved.

Proposed lease record (logical contract; actual storage owner/schema pending census/Queue Table Improvements): work ID, holder worker/agent, session ID, generation, claimed/expiry/heartbeat time from authoritative DB clock, expected state version, lease status. Claim transaction does conditional row update, increments generation, records claim event and returns one receipt. Heartbeat/renew/release/park/complete carry same generation; stale generation cannot mutate local work, notes, dependencies, cursor pointers or lifecycle. Renewal must not revive a reclaimed generation. Failed CAS returns current version/generation but never token to unauthorized caller.

Clock: one DB-authoritative time function for lease writes/eligibility. Client times are observational only. Expiration requires skew/clock-jump limits and operational observability; if actual DB cannot provide stable shared clock, use conservative takeover margin and document that lease expiry is liveness, while fence remains safety. Do not compare host wall clocks as authority. Never hold DB write transaction across remote calls.

### 3.2 Fence boundary limitation

Fence generation prevents stale *local* writes because Fleet storage checks it. GitHub does not accept this token; a request authorized locally may be paused, lease expires, and request later takes effect. For a side effect, first create immutable, policy-authorized operation intent tied to fence, aggregate version and request digest. Once sent, that intent is a saga action, not a continuing grant for worker to issue arbitrary future writes. If worker is stale at acknowledgment, it cannot mutate lifecycle or create new operations; recorder may append the remote result to that exact operation as evidence, then reconciler/authorized current owner evaluates it. Outbox worker's own claim has independent generation/fence so old relay cannot overwrite newer relay state.

Remote constraints are effect-specific. PR merge can carry expected head SHA; issue/comment APIs reviewed here do not document Fleet fence or universal idempotency key. For non-CAS managed body/comment writes, #9208 chooses conflict-safe policy; this design must not claim the lease makes them fenced. Existing Fleet local ownership must serialize Fleet-managed operations per resource, but external GitHub writers still race.

## 4. Outbox operation model

One local transaction performs authoritative Fleet state mutation + journal event + outbox intent. The outbox is an append-preserving logical operation with current status projection; it is not merely webhook queue. Existing storage/transaction engine must be verified before naming tables. Operation identity: globally unique `operation_id`; idempotency key scoped to actor/client and stable request digest; work ID; kind; target canonical ref; immutable intended payload/hash; expected remote precondition (head SHA/body baseline etc.); originating actor/agent/session; authorized work version/fence generation; creation timestamp; sequence within work item; state and attempt history; remote response/resource IDs; verified evidence; last error code/retry class.

Suggested states: `pending`, `delivering`, `confirmed`, `retryable_failure`, `conflict`, `terminal_failure`, `unknown` (request outcome uncertain). State transition table must forbid regression from confirmed without explicit compensating/new operation. Same idempotency key + same digest returns existing operation/receipt; same key + different digest is deterministic conflict. Ordering: preserve per-work-item causal sequence for operations with same remote target. An outbox row lock/lease only permits one active sender; fence protects local finalization. A newer operation cannot blindly overtake an older unresolved mutation on same target.

### Supersede / stale operation policy (must be explicit)

An old durable operation can outlive the worker lease. Never silently drop it: accepted/sent remote effects may already exist. New owner may (a) wait and reconcile operation, (b) mark it superseded *before send* via CAS and record actor/reason, (c) create compensating/new operation after observing result, or (d) re-authorize/replay same operation ID if intended state remains valid. Once remote send may have occurred, status moves to `unknown` and supersede requires remote readback; no cancellation fiction. For a newer desired state, preserve order: reconcile older op first, then enqueue correction. Security/policy revocation can stop future send, but does not undo in-flight effect. Stale sender's late success records operation-scoped effect and cannot finalize unrelated work state.

Retry classes: deterministic validation/auth/permission/invalid target are terminal pending operator; SHA/version mismatch or body baseline conflict is `conflict`, refresh/re-authorize; network timeout after request send is `unknown`, read back before retry; rate limit/transient server errors use provider-specified retry-after/backoff and caller deadline, without hard-coded count/ceiling invented here; 5xx before write may be retryable but effect uncertainty depends on API guarantees. Retry budgets derive existing fleet policy and endpoint rate limits, retain attempt history, and return exact next attempt/owner. No unbounded immediate retry loop.

## 5. Direct completion protocol and receipt

`fleet work complete <work-id> --merge-pr <repo#n> --close-issues <repo#n> --close-queue --verify --wait` is illustrative CLI, not registered syntax; preserve source plural spelling `--close-issues` in compatibility inventory and make any later alias explicit. Explicitly enumerate authorized remote resources; never close all linked issues or parent/epic/components by inference. Completion policy identifies required vs optional effects; each required ref needs explicit allowlist/config and authorization.

### 5.1 Phases

1. **Prepare local:** validate auth and active fence; verify lifecycle transition, no unresolved hard dependency, completion policy, explicit resource allowlist, idempotency digest. Capture work version and expected PR head SHA. In one short local transaction create completion operation, transition to `completing`, append event and one ordered outbox effect per remote action. No HTTP in transaction.
2. **Final refresh/check:** invoke #9207 source-aware refresh and surface activity since execution start/checkpoint. Validate current PR head, required checks/reviews, branch policy/merge readiness and any configured comment/review gate. If conflict/new actionable event, keep `completing`/conflicted with evidence and require agent/operator decision. A last refresh cannot lock GitHub; disclose TOCTOU.
3. **Merge:** submit merge with expected head SHA. GitHub REST says SHA mismatch returns 409. If merge queue or async endpoint returns accepted/enqueued (202), remain `completing`; poll/read result within command deadline or return `pending`, never report merged from acceptance. Verify remote PR `merged`/merged timestamp/result and record merge commit SHA.
4. **Merge verification semantics:** expected head SHA protects against merging a changed head at execution. For merge-commit strategy, verify merge result links expected head as second parent/merge relationship per GitHub returned merged commit/PR record; for squash, verify GitHub's merged PR metadata and returned squash commit SHA, not “head SHA is ancestor of base” (squash rewrites history). For rebase, verify merged PR state and final base commit relation/result as returned by API; ancestry may differ. Endpoint integration must check what fields are authoritative for chosen strategy and record limitation. Do not infer successful merge merely from closed PR (`merged` distinct from closed).
5. **Issue closure:** close only explicitly designated issues after merge policy says so; verify each issue state closed and record returned state/timestamps. Issue closure can partially succeed; do not reopen automatically to simulate rollback.
6. **Direct Fleet finalization:** after all required effect receipts are confirmed, one local transaction conditionally appends completion event, writes per-effect receipts and terminal `completed` state, and releases lease. Completion operation is valid operation scope; it may finalize after initiating worker lease expires if effects were authorized and verified. It cannot permit stale worker to make new mutation or overwrite newer state; local finalize checks the completion operation/version, current work lifecycle still `completing`, and no newer cancel/hold/revocation. No later webhook/sweep is needed on normal success.
7. **Return:** response names work ID, operation ID, each requested/verified/pending effect, remote refs/SHA/close state, queue terminal state, verification time, status `complete|partial|pending|conflict`, and exact next action. `complete` only after Fleet transaction commits. A lost final response can be retried with same idempotency key and returns receipt.

### 5.2 Lost acknowledgment and recovery

If remote mutation succeeded but response was lost, mark effect `unknown`, query remote state. If exact intended result is identifiable, confirm without replay. For merge: PR merged and merge result matches policy; record returned merge SHA and strategy. For issue close: issue is closed; if actor/reason attribution unavailable, remote state may satisfy desired state but report attribution confidence. For comment create, query exact stable operation marker, adopt exactly one; zero matches may be eventual visibility, delay/recheck under policy; multiple is conflict. Never POST a second comment solely because first response timed out. For body/comment update, GET current and compare managed-region intended digest and known comment ID; #9208 policy resolves mismatch. If unknown cannot be resolved, retain recoverable state and operator action.

Partial effects remain in `completing` with per-effect receipts. Merge succeeded/issue closure failed is a partial completion, not transaction rollback and not `completed`; preserve merge receipt and retry only allowed issue closure. User can inspect `sync/outbox` equivalent after command returns. No webhook required to get Fleet normal success closed; webhook is duplicate/hint and must be deduped.

### 5.3 Late activity TOCTOU

Last-second external comment after the final refresh but before/after merge cannot be excluded atomically: GitHub and Fleet have no shared transaction or lock. Define policy classes: changes that invalidate expected code state (head SHA, checks/reviews) guarded by remote merge precondition/current checks; comments/review events that require human/agent review are detected by refresh but remain vulnerable in the read→merge interval. Record refresh watermark and merge timestamp; if late event observed before Fleet terminal commit, hold in `completing` for policy evaluation. If observed after completion, append external activity and apply configured post-completion reopen/triage policy, never rewrite history. Do not promise “no comments can arrive between check and merge.”

## 6. Managed comment/body limitation and integration with #9208

The GitHub REST comment update endpoint reviewed in S2 requires only body and comment ID; no conditional CAS token is documented. Therefore GET-compare-PATCH is not optimistic concurrency control against simultaneous humans; it can still overwrite a change between GET and PATCH. This design does not promise prevention. #9208 should prefer private journal plus explicit mirror, known managed comment ID, and conservative conflict/re-read policy; avoid whole-body replacement and automatic recreation/overwrite without owner policy. Per-resource outbox order can prevent Fleet/Fleet races only. A managed-content conflict blocks required completion sync if policy marks it required; otherwise receipt explicitly states not mirrored.

## 7. End-to-end states/errors

Lifecycle and GitHub state remain separate. `completed` means policy-required effects read back verified and local finalization committed. `completing` includes pending/unknown effects; `conflict` is an operation outcome that may be represented on work lifecycle by the approved model, not an assumption of a new status. Error envelope stable codes include `LEASE_LOST`, `FENCE_STALE`, `VERSION_CONFLICT`, `DEPENDENCY_BLOCKED`, `REMOTE_CONFLICT`, `REMOTE_UNAVAILABLE`, `COMPLETION_PARTIAL`, `COMPLETION_PENDING`, `IDEMPOTENCY_KEY_REUSED`, `AUTH_DENIED`, each with operation ID, per-effect status, retryability and recovery action. Claim conflict reselect vs stale holder must be distinguishable. Do not convert post-claim lane/session bind failure into an ordinary error that invites a second claim: census points to `claim-flow` partial result behavior in queue broker around current `main.rs` handler; verify exact pin and preserve that no-replay property.

## 8. Failure matrix

| Race/cut | Required result |
|---|---|
| Two claimers select same item | Atomic eligibility revalidation permits one; loser reselects/returns conflict, never double holder. |
| Takeover after lease expiry while old process alive | Increment fence; all old local writes fail; remote in-flight side effect remains possible and is operation-reconciled. |
| Worker clock ahead/behind DB | DB time controls expiry; client timestamp cannot claim authority. |
| Crash before prepare transaction commit | No completing transition/effects; retry same key starts once. |
| Crash after prepare before send | Durable pending operation retried. |
| Remote write applied, HTTP response lost | `unknown`; GET and correlate before retry; no false failure or duplicate. |
| Relay lease reclaimed, old relay returns success | Old relay cannot update row state due relay fence; records effect only against its immutable operation; new relay readbacks. |
| Newer desired op arrives while old op unresolved | Per-target ordering; old is reconciled or safely superseded pre-send; later correction not sent out of order. |
| Lease expires after merge before local finalize | Completion operation can finish direct local receipt if still authorized/current completing; stale worker cannot issue next action. |
| Newer worker changes/cancels work while old completion returns | Conditional operation-scoped finalize checks current `completing` state/revocation; retain remote receipt, do not clobber newer state. |
| PR head changes just before merge | Expected-SHA precondition fails; conflict, rehydrate/review, no implicit new-head merge. |
| Check/review changes without head change | Re-fetch immediately before merge; branch protection/API is final gate; still no cross-system atomic snapshot. |
| Late comment after refresh | Watermark and policy disclosed; hold if observed before finalize, post-completion activity policy if afterward; no magical lock. |
| Async merge accepted but not merged | `pending`; await/read eventual result; no direct queue close. |
| Squash/rebase result | Verify `merged` and appropriate merge result fields/strategy; don't require expected head ancestry for squash. |
| Merge succeeds, issue close fails | Preserve merge receipt; `completing` partial; retry authorized closure, no auto-reopen. |
| One of many designated issues closes, next fails | Record individual effect receipts; no all-or-nothing claim. |
| Two comment creators race | Local same-target serialization; remote marker recovery; duplicates discovered/conflict, no exactly-once promise. |
| Managed body edit races with human | Potential lost update exists absent API CAS; do not claim protected; preserve snapshot and surface conflict per #9208. |
| Duplicate webhook for own completion | Delivery ID dedupe + operation/effect idempotence; no double lifecycle transition. |
| Epic or component issue closes incidentally | Only explicit refs/policy effects apply; never infer parent/epic/component closure. #9196 must not be completed by bot epic closure absent active-task and completion-proof gates. |
