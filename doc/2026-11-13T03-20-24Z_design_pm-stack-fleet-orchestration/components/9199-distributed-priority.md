### Taxonomy mapping; do not transplant the historic scale

The queue/dispatch adapter has a discrete target profile `[10, 20, 30, 40, 50, 70, 90]`, with named values documented in `validate.ts`; ratified #7030 evidence also has `expedite=15`, `next-up=25`, and queue-task `10`. **Adapter defect:** `resolvePriority` accepts off-scale integers in 10–90 but snaps to the nearest target value (ties down), so `15→10` and `25→20`. The broker/task readback records 15/25 as actual values; therefore passing them through this adapter changes their meaning. Preserve current ratified inputs and broker values; resolve a lossless, explicitly versioned producer/consumer contract rather than rejecting or silently snapping these inputs. This statement is bounded to the cited function; higher values are subject to its documented 10–90 range.

The charter's `450/High` and `1000/new ordinary default` belong to a **historical charter profile** for interpreting source examples (`430` is also inside its proposed 400–799 High band). They may map by named intent to a current band only if a dated policy explicitly establishes that mapping. Do not use an affine conversion, assume adapter rounding (`430→400`) is a valid cross-profile mapping, silently rewrite live integers, or claim a charter number is a canonical queue score. Keep profiles separately versioned so historical examples remain reproducible.

The historical weighted formula's `d=200` is calibrated in the charter's broad 0–2000 profile. It cannot be applied as-is to a current scale whose live values span 10–90: on that range the exponent nearly collapses distinctions. Preserve it as a named candidate hypothesis; calibration/parameters require #9204 simulation and approval, with no automatic rescaling of live values.

### Candidate order and rank semantics

Proposed claim comparator for V2, subject to #9200/#9204 and current rank discovery:

1. Eligibility is a **gate**, not a sortable score: lane capabilities, both matching predicates, hard blockers, #9178's persistent `manual_only` flag, policy/state, current lease/concurrency.
2. Compare effective urgency ascending (lower first), or intrinsic urgency if that policy profile has no derivation.
3. Compare an explicit sparse exact-integer peer rank within equal effective urgency. Before/after relative-order operations are a source requirement; do not omit them. They cannot jump across unequal effective-urgency values: request an explicit urgency change/confirmation or return `cross_priority_move_requires_confirmation`.
4. Compare stable creation time ascending, then normalized canonical `(authority_id,work_id)` identity.

This proposed tuple repairs V1's no-final-ID claim tie and reconciles queue/list order. Rank is an exact signed integer represented losslessly across Rust/JSON/TypeScript (integer-string encoding on wire; never JS floating point). The contract normalizes legacy `NULL` rank to the documented common rank `0` on read, then uses deterministic created-at+ID ties; writes store an explicit rank and never rely on SQL NULL ordering. An authorized before/after command includes effective-urgency group, authority-qualified neighbor identities, neighbor work versions, and `rank_epoch`; it is accepted only if neighbors remain adjacent/in the named group. Allocate an unused integer gap; if none, take a per-group epoch lock and rebalance only a deterministic bounded local range using a fixed stride, increment epoch atomically, and record every changed identity/old/new rank. Oversized range fails typed `rank_rebalance_required` without partial updates. A stale epoch/neighborhood returns conflict. Before/after across different effective urgency requires explicit urgency-change confirmation or returns `cross_priority_move_requires_confirmation`; rank never overrides urgency. Do not uniquify urgency scores to force order.

### Triage mechanics

All priority-affecting paths first apply the versioned protected-owner gate in
[`architecture.md`](../architecture.md#protected-owner-priority-policy). Drew's existing
protected expedite membership/value/peer placement is not editable by routine manual
`priority.write`, automatic aging/clump moves, label normalization, or a hysteresis bypass.
Only the specifically authenticated owner amendment (or that exact authorized operation)
may change protected policy. Validate `owner_policy_ref` with the work mutation; stale policy
conflicts and denied mutations change no score/rank/membership. This consumes #7030, not a
new ratification request. PRI-01/PRI-05 and AUTH-01 share protected/ordinary/owner/stale-policy
oracle cases, including label removal that must not remove protection.

* Triage may compare candidates in categories (much more/slightly more/equal/slightly less/much less/custom/research); ordinary automated policy permits at most one move per item per sweep except a separate high-confidence event. Preserve original cluster intent `50 → rough 25/10/5/singles` as an illustration, not fixed group sizes or a deterministic flattening rule.
* Adjustments require a reason, evidence, confidence, as-of, previous/new score or component, policy version, and next-review/retriage time. ±10/±25 and source examples are candidate operations, not mandates.
* Aging is bidirectional and evidence-based: meaningful triage age, freshness, pivots, effort, deadlines, opportunities and value matter. Age alone never escalates to Critical. A pivot can lower a formerly High task; useful stagnant work may rise only with evidence.
* Hysteresis is a bounded buffer/cooldown/confidence threshold around band edges, not a wall. Authorized manual action and verified deadline/incident can bypass the resistance but not authorization or eligibility. Prevent churn and unbounded cumulative drift.
* Temporary opportunity boosts are separate from base urgency, have explicit start/expiry and `expiryAction=retriage`; expiration removes only the temporary factor and initiates reassessment. Cold backlog remains searchable and eligible for periodic review.

### Dependency pressure, cycle safety and resource bounds

Only true hard dependency edges gate eligibility or contribute inheritance. Parent/child hierarchy and advisory/related/duplicate edges do not automatically block or inherit pressure. Preserve blocker intrinsic urgency; calculate effective pressure from downstream urgency/critical path with bounded consideration of effort, actionability, probability and alternatives. The explanation includes source item(s), edge type, graph revision, path, values/cap, effort/alternative evidence. Never unconditionally promote a large speculative blocker to Emergency.

Canonical hard-block edge direction is **blocker → dependent**. For proposed insertion `u→v`, a cycle is created iff `u==v` or the current graph has a directed path `v→u`; check this exact orientation before commit under a serialized graph revision/edge-write transaction. Opposite-edge race fixture: concurrent requests insert `A→B` and `B→A`; independently checking an initially empty graph is insufficient—one commit wins, the second rechecks the new revision and rejects/quarantines. Imported cycles are quarantined/reported and traversal uses visited nodes. A full DAG propagation is `O(V+E)`; cache invalidation marks downstream dependents for eligibility effects and upstream blockers for inherited-pressure recomputation: a blocker effective pressure derives from its dependents, so a dependent urgency change also invalidates the inherited-pressure caches of its blockers (post-review correction, task 15381). Selection takes a pinned graph revision and retries/rejects if it changed before claim. Resource budget/cancel behavior may bound work, but **must not silently truncate a blocker graph and return an apparently valid eligibility result**; return `graph_evaluation_incomplete` and fail closed for dependent decisions.
