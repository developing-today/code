Purpose Fleet and PM Stack need a consistent way to represent the relative urgency, importance, readiness, ownership, and lifecycle of work. The same underlying work should be understandable through: - Fleet CLI. - Fleet queue. - GitHub issues. - GitHub Projects. - PM Stack dashboard. - Agent scheduling. - Triage workflows. - Mobile browser. - Live agent sessions. These interfaces should not evolve separate, conflicting interpretations of what is important or what should happen next. The system must support both human and automated prioritization. It should also resist the common failure modes of priority queues: - Old tasks becoming permanently forgotten. - Everything gradually becoming high priority. - High-priority tasks remaining high after strategic pivots. - Small blocking tasks remaining buried because their intrinsic importance is low. - Large clusters receiving disproportionate selection probability. - Equal-priority items having unstable order. - Repeated automated updates causing priority oscillation. - GitHub labels diverging from database values. - Immediate requests being delayed behind background workers. - Agents picking up work without publishing a visible lifecycle state. - Parked work losing its history and continuation context. The goal is a system that remains legible, adaptable, and self-maintaining. --- # 2. Separate the Major Concepts Do not force every scheduling decision into a single priority number. At minimum, distinguish: ## 2.1 Intrinsic urgency How soon should the item receive attention under its own circumstances? Represented initially by a numeric score. **Lower numbers mean greater urgency.** Example: urgency_score = 600 This score should be durable, editable, and explainable. ## 2.2 Importance / impact How valuable or consequential is the work? Examples: - Strategic importance. - Business or user impact. - Risk reduction. - Architectural significance. - Expected benefit. Importance should eventually have its own representation. A high-importance architectural project may not be immediately urgent. A short-lived minor opportunity may be urgent despite modest importance. ## 2.3 Effective scheduling urgency How urgent is the item to execute right now, considering its surroundings? Derived from: - Intrinsic urgency. - Blocking relationships. - Deadlines. - Current project phase. - Time-sensitive opportunities. - Explicit dispatch directives. - Resource availability. - Other applicable policies. This may differ temporarily from intrinsic urgency. Do not necessarily rewrite the canonical numeric score every time scheduling pressure changes. ## 2.4 Workflow state What is happening to the item? Examples: triage backlog ready claimed in_progress review parked blocked completing completed cancelled State is not priority. ## 2.5 Dispatch directive What should happen operationally? Examples: normal expedite do_now direct_session hold manual_only A `do_now` directive should not inherently change numeric urgency. It should influence dispatch behavior. ## 2.6 Ownership and assignment Who has responsibility for the item? Distinguish: - Human owner. - Assigned agent. - Currently running agent/session. - Lease holder. - Reviewing agent. - Supervising or escalation recipient. Do not equate "assigned" with "actively executing." --- # 3. Proposed Numeric Urgency Bands Use a broad numeric scale that leaves room for gradual adjustment. Recommended initial convention: | Range | Band | Meaning | |---|---|---| | 0–99 | Emergency | Active severe incident or similarly extraordinary need | | 100–199 | Supercritical | Immediate critical-path or severe operational work | | 200–399 | Critical | Strong near-term need; major blockers or deadlines | | 400–799 | High | Should receive attention ahead of ordinary work | | 800–1199 | Standard / Medium | Normal actionable work | | 1200–1599 | Low | Useful, but not currently time-sensitive | | 1600–1999 | Someday / Deferred | Weakly time-sensitive or speculative work | | 2000+ | Cold backlog | Explicitly retained but not regularly selected | **Default for new, ordinary work: 1000.** Examples: Emergency: 50 Supercritical: 150 Critical: 300 High: 600 Standard: 1000 Low: 1400 Someday: 1800 These are provisional ranges. Before implementing, compare them with existing queue values and migration constraints. Do not blindly reinterpret existing numeric scores without an explicit migration plan. ## 3.1 Avoid the shadow backlog Scores above 2000 must not become a hidden deletion mechanism. Cold backlog items should remain: - Searchable. - Visible through appropriate filters. - Eligible for periodic review. - Eligible for manual escalation. - Eligible for opportunity-based reconsideration. - Included in explicit archive or retention policy. Do not indefinitely bury an important item simply because its score was set too high once. ## 3.2 Manual control Authorized users and agents should be able to: - Move to a band's default. - Set an exact numeric score. - Move ahead of a particular item. - Move behind a particular item. - Increase or decrease urgency by a fixed amount. - Pin an explicit ordering override. - Request recalculation. - Request triage. - Request immediate dispatch. Examples of desired interfaces: fleet priority set 842 high fleet priority set 842 475 fleet priority move 842 --before 761 fleet priority move 842 --after 903 fleet priority adjust 842 --delta -10 fleet priority explain 842 These may be implemented under `fleet metadata priority` instead if that better matches the established CLI. Manual explicit moves should not be blocked by automatic prioritization hysteresis. Every change should still be recorded. --- # 4. Stable Total Ordering Numerical urgency does not need to be unique. Many items may reasonably share: urgency_score = 1000 Nevertheless, the queue must have a deterministic total order. Recommended logical ordering: 1. Effective scheduling urgency. 2. Explicit relative-order key, if present. 3. Original queue-entry time, oldest first. 4. Stable work-item ID. For items with identical intrinsic urgency and no explicit ordering override, **oldest first** is a reasonable default. A newly created item that truly needs to run sooner should receive a more urgent score or explicit placement. ## 4.1 Separate the score from the tie-breaker Do not continually modify numeric urgency solely to force unique values. Introduce a secondary ordering mechanism. Possible implementations: - Fractional rank. - Lexicographic rank. - Sparse integer order key. - Another stable insert-before/after representation. Use the architecture that best fits the existing queue backend. An explicit `move before` request must remain meaningful even when two items share a score. ## 4.2 Gentle spacing Natural priority clusters are acceptable. However, triage may gradually distinguish items within a cluster. For example: Before: 1000: 50 items After initial comparison: 980: 25 items 1000: 10 items 1020: 10 items 1050: 5 items Later reviews may refine the clusters further. The purpose is to improve comparative ranking, not force every item onto a unique score. ## 4.3 Collision handling If an automatic adjustment lands on an occupied score: - Permit identical scores when justified. - Preserve deterministic order. - Optionally choose a nearby score, such as ±5. - Prefer minimal local changes. - Avoid cascades of mass renumbering. - Respect explicit exact-score requests. A score collision is not an error. ## 4.4 No uncontrolled priority drift Automatic spacing must not collectively push every item upward or downward over time. Each adjustment requires a documented reason. Triage should preserve relative scale and distribution unless the actual work priorities have changed. --- # 5. Dynamic Reprioritization Priority should evolve as circumstances change. But aging alone must not guarantee that every item eventually becomes critical. The system should evaluate actual urgency signals. ## 5.1 Relevant signals - Age since creation. - Age since last meaningful triage. - Time since last execution attempt. - Deadlines. - Dependency relationships. - Project urgency. - Epic or parent-item urgency. - Current strategic direction. - Active incidents. - Changes in expected value. - Implementation effort. - Availability of required resources. - User requests. - Maintainer feedback. - Explicit deferment decisions. - Opportunity windows. - Recent execution or failure history. ## 5.2 Example: old medium item escalates An idea is initially: urgency = 1000 importance = medium After a week it remains untouched. A review finds that: - The opportunity is still relevant. - Implementation is straightforward. - Its delay is now affecting current work. It may move to: urgency = 780 This crosses into High. However, the mere passage of seven days should not automatically produce the same change for every idea. ## 5.3 Example: strategic pivot An item was previously: urgency = 520 A project pivot makes it less immediately relevant. It may move to: urgency = 1010 The system should not preserve outdated urgency simply because the previous classification was High. ## 5.4 Example: stable priority A speculative architectural idea remains useful but has no clear deadline. It may stay at: urgency = 1400 for weeks or months. Repeated triage can explicitly confirm that this is still appropriate. ## 5.5 Example: urgency decreases with time A short-lived integration opportunity becomes less valuable after its ecosystem changes. The item may gradually move downward. If the opportunity disappears, the system should reconsider whether to defer, replace, close, or retain the work. Do not blindly add a large number such as 9999 and abandon it. --- # 6. Time-Limited Opportunities Some work has modest importance but high temporary urgency. Example: > A useful integration can be implemented during the next three days before an upstream release. It is not strategically critical, but doing it now would be convenient. Represent this explicitly: intrinsic_urgency: 900 importance: low opportunity_deadline: date/time temporary_scheduling_boost: active expiry_policy: re-triage During the opportunity window, its effective scheduling urgency may be substantially higher. When the window expires: 1. Remove the temporary boost. 2. Review the item's remaining value. 3. Recalculate scheduling urgency. 4. Preserve the original decision history. 5. Decide whether to defer, close, or rescope. Do not automatically convert an expired opportunity into a permanently forgotten item. ## 6.1 Escalation If an agent believes a low-importance opportunity has unusually high potential value, it should be able to escalate the question. Suggested routes: Agent → Triage Agent → Supervising agent Agent → Human decision channel Escalations should contain: - The opportunity. - Expected benefit. - Deadline. - Cost or effort. - Risk of delay. - Recommended action. Avoid escalating every small opportunity. --- # 7. Dependency-Driven Urgency A low-importance task may become urgent because it blocks something important. Example: Work A: urgency = 500 importance = high blocked_by = Work B Work B: urgency = 1450 importance = low effort = small Work B is intrinsically low importance but operationally urgent because Work A cannot proceed without it. The system must recognize this. ## 7.1 Intrinsic versus inherited urgency Recommended approach: Keep Work B's intrinsic score: base_urgency = 1450 Compute temporary scheduling pressure: blocking_pressure = high And optionally: effective_urgency = 480 This allows Work B to execute promptly without permanently rewriting its long-term classification. After the dependency is resolved, the inherited pressure disappears. ## 7.2 Dependency graph Support: blocks blocked_by related_to parent_of child_of duplicates supersedes Differentiate hard blockers from advisory dependencies. A hard dependency can affect execution eligibility. A soft relationship may only affect ranking or context. ## 7.3 Propagation rules Urgency propagation should consider: - Downstream urgency. - Whether the dependency is truly required. - Number of blocked items. - Critical-path position. - Estimated effort. - Probability of resolution. - Availability of alternatives. - Whether the blocker is actionable. Avoid indiscriminately promoting a giant speculative task to Emergency just because a high-priority item references it. If the blocker is large or uncertain, escalate for design or project-level planning rather than blindly increasing its score. ## 7.4 Cycle detection Detect dependency cycles. Do not let cyclic blocking relationships produce unbounded priority escalation. ## 7.5 Explainability Example: fleet priority explain 761 Desired result: Intrinsic urgency: 1450 (Low) Effective urgency: 480 (High) Reason: Blocks item 842 (urgency 500) Hard dependency Estimated effort: small Recommended action: Execute dependency before item 842 This distinction should be visible in the PM Stack board. --- # 8. Automatic Triage and Priority Refinement Regular triage should improve ordering without generating excessive changes. ## 8.1 Triage dimensions Items may be compared along categories such as: Much more urgent Slightly more urgent Roughly equal Slightly less urgent Much less urgent Custom urgency Needs investigation The same conceptual categories can later be applied separately to importance. ## 8.2 Gradual adjustment A typical minor adjustment might be: -10 = more urgent +10 = less urgent Larger moves should be possible when supported by evidence. Examples: -25 -50 +25 +50 Manual repositioning can be much larger. These values must be configurable. ## 8.3 Progressive cluster refinement Suppose 50 items have approximately equal urgency. A first pass might separate them into broad groups: 25 / 10 / 10 / 5 Later passes compare more closely related items: 10 / 10 / 5 Then: 5 / 3 / 2 Eventually, a few items warrant individual ordering. Do not require fixed group sizes. Use this as a strategy for progressively refining partially ordered sets. ## 8.4 Sweep ordering A reasonable approach is to examine lower-urgency cohorts first and proceed toward more urgent cohorts. However, avoid repeatedly processing the same ticket within one sweep merely because it moved into a later cohort. Recommended invariant: **Each item receives at most one automatic priority adjustment per ordinary sweep unless a separate high-confidence event requires immediate reconsideration.** This prevents runaway escalation loops. ## 8.5 Triage explanation Each adjustment should record: previous_urgency new_urgency source reason evidence confidence evaluated_at next_review_at Not every adjustment needs a public comment, but it must be auditable. --- # 9. Resistance at Urgency-Band Boundaries A useful objective is to prevent low-confidence automatic adjustments from repeatedly bouncing items across bands. For example: Standard: 800–1199 High: 400–799 An item approaching 800 from the Standard band should not cross merely because of tiny, noisy ranking changes. ## 9.1 Proposed hysteresis Support: boundary_buffer: configurable automatic_crossing_confidence: configurable review_cooldown: configurable For example: boundary_buffer = 30 automatic_crossing_confidence = 0.8 Within the boundary buffer, require stronger evidence for automatic promotion or demotion. This is a policy example, not a universal mathematical law. ## 9.2 Allowed exceptions Crossing should remain immediate for: - Authorized manual action. - Confirmed hard deadline. - Active critical incident. - Explicit high-confidence dependency pressure. - Verified major project reprioritization. ## 9.3 Avoid permanent band trapping Hysteresis is resistance, not a wall. An item that consistently deserves promotion must be able to cross. Record the evidence and allow persistent signals to accumulate. --- # 10. GitHub Priority Labels GitHub labels should make urgency visible without creating a competing source of truth. Possible canonical names: priority:emergency priority:supercritical priority:critical priority:high priority:standard priority:low priority:someday priority:cold Adapt these names to the repository's existing label conventions. Do not create parallel labels when equivalent ones already exist. ## 10.1 Normal direction Fleet numeric urgency determines the canonical band. Fleet should maintain the corresponding GitHub priority label. Example: urgency_score = 600 GitHub: priority:high Changing the numeric score from 600 to 1000 should remove the old priority label and add the new one. ## 10.2 GitHub labels as commands GitHub label changes may also represent intentional human input. When an authorized actor adds: priority:critical Fleet should treat it as an input event. Suggested behavior: 1. Validate the label and actor. 2. Read the current work-item state. 3. Map the label to the configured band default or appropriate retained intra-band position. 4. Update numeric urgency. 5. Remove conflicting priority labels. 6. Record the source and reason. 7. Reproject GitHub and PM Stack views. 8. Reconsider scheduling. Example: priority:critical → default 300 Do not repeatedly reset an item's carefully tuned intra-band score when merely reconciling an unchanged label. ## 10.3 Priority label removed If the last priority label is removed: - Do not invent an emergency urgency. - Do not silently reset to 1000. - Preserve the existing numeric score pending review. - Mark the item `needs-triage`. - Put it at the front of the **triage queue**, not necessarily the execution queue. - Record why triage was requested. If another valid priority label remains, normalize according to that label. ## 10.4 Conflicting labels If a new priority label is added while an old one remains: - Prefer the newly authorized, explicitly added label when event ordering is reliable. - Remove conflicting labels. - Update numeric urgency. If event ordering or authorization is ambiguous: - Preserve the existing canonical value. - Mark a priority-label conflict. - Send the item to high-priority triage. ## 10.5 `needs-triage` Adding a `needs-triage` label should: - Create or update a triage request. - Expedite triage selection. - Preserve the underlying work-item urgency. - Avoid automatically launching an implementation agent. A command or policy may explicitly request immediate triage. --- # 11. Do Now and Immediate Dispatch Introduce an explicit directive such as: do-now The exact label name should follow existing conventions. ## 11.1 Semantics `do-now` means: > Begin the appropriate authorized action immediately, or explain why it cannot safely begin. It must not simply mean: > Increase the item's numeric urgency. The directive may be transient. ## 11.2 Mechanical handling On an authorized `do-now` event: 1. Validate actor and permission. 2. Deduplicate the event. 3. Resolve work-item identity. 4. Inspect current lifecycle and blockers. 5. Determine whether a live session exists. 6. If live, route the request to that session. 7. Otherwise, directly dispatch a session through the established mechanism. 8. Claim or bind the item appropriately. 9. Record task/session identity. 10. Update visible status. 11. Acknowledge the result. Do not merely append an ordinary queue item and hope it gets picked soon. ## 11.3 Blocked items A blocked item should not automatically lose its hard blockers just because someone applies `do-now`. Possible outcomes: - Dispatch an inspection/unblocking agent. - Escalate for human approval. - Reject the start with an actionable explanation. - Begin a permitted independent subtask. Do not silently bypass dependency policy. ## 11.4 One-shot behavior The directive should have a durable request identity. Repeated webhook deliveries should not launch duplicate sessions. Once handled, Fleet may clear the label, record it as consumed, or maintain an explicit request status according to policy. --- # 12. GitHub and PM Stack Workflow Visibility The GitHub and PM Stack views should agree on a task's lifecycle. ## 12.1 Suggested board columns Inbox / Triage Backlog Ready / Todo In Progress Review Blocked Parked Done The actual PM Stack schema should determine the final representation. ## 12.2 Suggested default projections **Inbox / Triage** - Newly created untriaged items. - Explicit `needs-triage`. - Priority-label conflicts. - Missing classification requiring attention. **Ready / Todo** - Unblocked, executable High-and-above work. - Explicitly expedited work. - Items assigned to the owner for near-term action. - Items directly designated ready. **Backlog** - Standard and lower-urgency work not otherwise ready. - Work awaiting normal selection. **In Progress** - Actively claimed/executing work. - A verified bound agent session. **Review** - Implementation completed but awaiting review, checks, or approved merge. **Blocked** - Work with unresolved hard blockers. **Parked** - Work previously picked up and intentionally set aside. - Checkpoint and reason preserved. **Done** - Verified completed work. A blocked or parked status should take precedence over a simple urgency-based Ready classification. ## 12.3 Picked-up work When an agent claims work, Fleet should: - Update queue ownership and execution state. - Update configured GitHub labels. - Update the task-level GitHub Project status to In Progress. - Update PM Stack projections. - Create or update a managed progress comment where appropriate. - Record the agent/session identity. - Record the claim timestamp. Avoid adding a new public comment on every lease heartbeat. ## 12.4 Parked and blocked work A previously claimed item should visibly retain its history. At minimum: previous_agent previous_session last_checkpoint reason blocked_by next_action last_activity Triage agents and subsequent workers should be able to see why the item stopped. The board should not misleadingly return previously worked, blocked items to a generic untouched Backlog column. ## 12.5 Views Useful board views include: - All work. - Ready / Todo. - High urgency. - Critical path. - Blocking other work. - My work. - Active agents. - Awaiting review. - Parked / Blocked. - Needs triage. - Recently changed. - Cold backlog. - By repository. - By project or epic. - By owner or execution lane. Each view should derive from a shared canonical model. --- # 13. Mobile-Friendly PM Stack PM Stack should work well on a phone and in a standard desktop browser. Exploration must not displace an available critical task. ## 15.3 Three-item exploration draw An exploration event selects three distinct work items. Example: fleet queue explore \ --count 3 \ --strategy weighted \ --explain The agent reviews all three before choosing what to do. Weighted Random Selection Formula Use exponential weighted random selection with configurable lower-value preference and density correction. Default values: Value preference: 1.25× per 200-point difference Density correction: 0.50 Numerical bucket width: 200 For item i: w_i = r^(-(u_i - u_ref) / d) × n_b(i)^(-alpha) Where: u_i = item's numeric urgency u_ref = reference score, e.g. 500 r = preference multiplier, default 1.25 d = point distance, default 200 n_b(i) = item count within the score bucket alpha = density correction exponent, default 0.50 The reference value does not affect relative probabilities when applied uniformly. Lower urgency scores receive greater weight. Density correction reduces the advantage of large clusters without eliminating it. ## 16.1 Interpretation If: r = 1.25 d = 200 then an item 200 urgency points lower receives 1.25 times the base weight of the higher-numbered item, before density adjustment. If: alpha = 0.5 then a bucket containing many items receives less total weight than it would under pure per-item selection. The approximate total bucket effect becomes proportional to the square root of its item count when item scores within the bucket are similar. ## 16.2 Probability normalization For eligible items: P(i) = w_i / sum(w_j) Sample without replacement when selecting multiple items. ## 16.3 Optional minimum exploration floor To prevent extremely low-weight items from becoming practically invisible in large queues, support an optional uniform mixture: P_final(i) = (1 - epsilon) × P_weighted(i) + epsilon × (1 / N) Suggested starting value: epsilon = 0.05 This is optional and should be benchmarked against the actual queue distribution. ## 16.4 Cluster correction Calculate bucket population over the relevant candidate pool, not unrelated queue records. Do not include completed or otherwise ineligible work in the density count for executable selection. For triage exploration, a broader population may be appropriate. ## 16.5 Configurable controls Expose: preference_multiplier preference_distance density_exponent bucket_width uniform_floor exploration_probability exploration_count Support seeded simulation and an explain mode. ## 16.6 Extend to importance When a separate importance scale exists, support selecting an exploration axis. Illustrative policy: urgency_axis_probability = 0.70 importance_axis_probability = 0.30 The chosen axis determines the relevant weighting and filtering. Initially, when only urgency is available, use urgency exclusively. Do not fabricate importance values from the urgency score. An alternative multi-dimensional weighted strategy may be preferable after observing the data. This should be evaluated before locking in the final API. --- # 17.
