## Decision summary

| Question | Decision |
| --- | --- |
| What this framework is | A **capability catalogue plus one declaration format**: the shared vocabulary every surface (#2283/#3397/#3398) uses to say *which boundary, on what evidence, enforced where, failing how*. It is not a policy engine and not a compliance product (§2) |
| Default state | **Off, always.** Every boundary is an opt-in capability an admin or user enables for a scope they control. No deployment inherits a boundary it did not choose. An enabled boundary with no declaration is a configuration error, not an implicit deny (§1, §2.3) |
| Subject / scope | A boundary is declared on a **scope** (server / world / account) for a **subject class** (user / org / server / world). Scope is assigned locally and a peer cannot remove it — the `Scope` type already encodes this (§2.2) |
| Evidence model | Evidence is a typed record with **assurance level** (self / org-attested / provider-verified), **provenance**, **lifetime** (expiry, renewal, revocation), and **privacy class**. Declarations are evidence; IP is weak evidence; signatures prove authorship, not location (§3) |
| Public IP | **Never sufficient alone** for a deny that removes existing access. It may corroborate, warn, or trigger step-up/review. Contradiction between declaration and IP resolves to **review**, not silent deny (§4) |
| Sanctions | The list is **data, not code**: versioned, dated, operator-supplied or shipped, with propagation, grandfathering, and an appeal path. A sanctions boundary declares which interactions it covers (§5) |
| Intranet mode | A boundary type over **network identity** (IP ranges / overlay / mTLS / org IdP assertion), gating generic activity, with 2FA step-up points, fail-closed default, and a logged break-glass (§6) |
| Composability | **Intersection, always.** Server ∧ world ∧ user preference can only narrow. A user preference can never widen a server boundary; a conflict is a deny-with-reason, not a merge (§7) |
| Enforcement | The existing `evaluate()` is the decision procedure at every surface; each surface supplies hops. Denials and step-ups are logged with the evidence *classes* used, never the dossier (§8) |
| Reuse vs new code | Reuse `residency.rs` unchanged for plane/jurisdiction/resource evaluation. Extend with an evidence-assurance layer and a declaration record — additions, not replacements (§9) |

## 1. What is fixed before this record (not re-decided here)

Drew's framing on #5683 is a hard requirement, restated so children can cite
it rather than re-derive it:

1. **Capabilities, never defaults.** Restrictions are capabilities a server
   admin or user enables for their server / world / account. Nothing turns a
   restriction on by default, and no deployment inherits a boundary it did
   not choose.
2. **Basic frameworks first.** Ship the declaration, evidence, and
   enforcement skeleton in its simplest useful form before policy language,
   automated classification, or jurisdiction-specific rule packs.
3. **Not a GDPR product.** EU privacy is one possible use, not the design
   centre. Nothing here assumes a legal regime; the operator's obligations
   are the operator's.

Also fixed by the three closed source threads, cited not re-decided:

- **#3398 / `residency.rs`:** four independent planes (storage, processing,
  transport, metadata); a scoped path is denied unless every required plane
  has current, trusted, resource-bound evidence in a permitted jurisdiction;
  missing/unknown/expired/revoked/mismatched evidence all deny; a peer's own
  location statement is never evidence.
- **#2283:** jurisdiction may pin where a user's store / world data lives.
- **#3397:** a world may be partitioned or pinned by jurisdiction.

## 2. Framework shape

### 2.1 Three layers, one vocabulary

The framework is deliberately thin. It defines:

1. **A capability catalogue** — the closed set of boundary types this
   skeleton understands: `residency`, `citizenship`, `sanctions`, `network`
   (intranet). Each is a capability with a declared default of *off*.
2. **One declaration format** (§2.3) shared by all surfaces.
3. **One decision procedure** — `residency.rs::evaluate()` (§8), extended
   only where assurance and declaration lifetime require it.

Surfaces (#2283 signup/login, #3397 world membership/blobs, #3398 bridge/
federation/relay) do not each invent a model; they *supply hops* to the one
evaluator and *render* the one `Decision`.

### 2.2 Scope and subject

| Term | Meaning | Source |
| --- | --- | --- |
| **Scope** | The unit that *owns* a boundary: a server, a world, or an account. Assigned locally; a peer cannot remove it | `residency.rs::Scope` |
| **Subject** | What a boundary is *about*: a user, an org, a server, or a world | new `SubjectClass` |
| **Plane** | Which of storage / processing / transport / metadata a hop crosses | `residency.rs::Plane` |
| **Resource** | The exact store, host, relay or sink a hop uses | `residency.rs::ResourceId` |

The distinction that keeps the model honest: **scope owns the rule, subject is
judged by it.** A world scope (a world) declares a residency boundary; the
subject is a user joining it. Conflating the two is what produces designs
where a user "has" a boundary rather than being subject to one.

### 2.3 The declaration record

One format, used by every capability:

```
BoundaryDeclaration {
  id:            DeclarationId          // content-addressed; edits are new ids
  capability:    CapabilityKind         // residency | citizenship | sanctions | network
  scope:         ScopeRef               // server | world | account that owns it
  subject_class: SubjectClass           // user | org | server | world
  evidence_req:  EvidenceRequirement    // minimum assurance + accepted sources (§3)
  enforcement:   [EnforcementPoint]     // where checked (§8); empty = not enforced
  failure:       FailureBehaviour       // deny | warn | step-up | quarantine (§2.4)
  data_ref:      Option<ListVersionRef> // sanctions/network list version, if any
  enabled:       bool                   // MUST be true only by explicit admin/user action
  version:       u64                    // monotone; every change is a new version
  declared_by:   ActorId                // who enabled it
  declared_at:   Timestamp
}
```

Rules that follow from the framing:

- **`enabled: false` is the only default.** A record with `enabled: true` and
  empty `enforcement` is rejected at declaration time — a boundary nobody
  enforces is a false promise, worse than no boundary.
- **Every change is a new version.** There is no in-place edit of a live
  declaration; the version is what makes a logged decision reproducible
  (the #5883 decision log records the version applied).
- **Declarations are data.** They are stored and replicated like other
  scoped state, not compiled into the binary. The *capability kinds* are
  code; *which* boundary a scope enables is data.

### 2.4 Failure behaviours

Four, and no more, in the skeleton:

| Behaviour | Meaning | When appropriate |
| --- | --- | --- |
| `deny` | Refuse the action | A boundary whose whole point is exclusion, and whose evidence is strong enough (§3.4) |
| `warn` | Allow, tell the user, log | Weak evidence (IP) contradicting a declaration |
| `step-up` | Allow after a stronger authentication | Network boundaries, privilege escalation (§6) |
| `quarantine` | Allow into a holding state pending review | Contradictions needing a human (§4.3) |

`deny` is the *strongest* action and therefore the one with the strictest
evidence bar. This ordering is the framework's main safety property: the
easier a signal is to spoof, the weaker the action it may drive.

## 3. Evidence model

### 3.1 What counts as evidence

Evidence is a typed record, extending `residency.rs::Evidence` with the
fields the declaration model needs:

| Field | Purpose |
| --- | --- |
| `issuer` | Locally trusted identity of who asserts this (already in `Evidence`) |
| `resource`, `plane`, `jurisdiction`, `source` | What it establishes (already in `Evidence`) |
| `expires_at`, `serial`, `signature` | Lifetime and authenticity (already in `Evidence`) |
| **`assurance`** | `Self` \| `OrgAttested` \| `ProviderVerified` — **new** |
| **`basis`** | Free-text/structured provenance: on what basis was this declared (§3.2) — **new** |
| **`privacy_class`** | `Exact` \| `Derived` \| `VerdictOnly` — what may be revealed downstream (§3.3) — **new** |
| **`subject`** | The user/org this evidence is about — **new** |

The existing `EvidenceVerifier` trait already decides signature validity and
revocation; the assurance level is an *additional* operator-side judgement
about how the claim was established, not a cryptographic property.

### 3.2 Assurance levels

| Level | Meaning | Who can assert | Typical basis |
| --- | --- | --- | --- |
| `Self` | The subject says so | The subject | A form field |
| `OrgAttested` | An organisation vouches for the subject | An org the operator trusts | HR record, membership roster |
| `ProviderVerified` | A trusted third party verified a document or fact | A configured provider | Document check, government/IdP assertion |

The framework **stores the level; it does not pretend the levels are equal.**
A declaration's `evidence_req` names the *minimum* level it accepts. A
sanctions boundary may accept `Self` plus review; a residency boundary that
pins storage may require `OrgAttested` or better.

**Signatures prove authorship, not truth.** An `OrgAttested` claim signed by
an org proves that org said it — the operator's trust in that org is the
real content of the assurance. This is the same discipline `residency.rs`
already applies to location: "a signature proves authorship, not physical
location."

### 3.3 Privacy of the declaration itself

The evidence store must not become a dossier. Three privacy classes, chosen
per declaration by the declaring scope:

- **`Exact`** — the value is stored and readable by the subject and by
  scope admins. Never exposed to other subjects.
- **`Derived`** — only a derived form (e.g. country, not address) is stored.
- **`VerdictOnly`** — *nothing* about the value is stored beyond "satisfies
  boundary X at time T". This is the default for IP evidence (§4).

Cross-subject visibility is **never** granted by default: a user cannot learn
another user's declared citizenship. An admin sees evidence *classes* and
verdicts in the decision log (§8), not raw values, unless the declaration is
`Exact` and the admin's role specifically grants it.

### 3.4 What each assurance may drive

| Evidence | May `warn` | May `step-up` | May `quarantine` | May `deny` new access | May `deny` existing access |
| --- | --- | --- | --- | --- | --- |
| `Self` declaration | yes | yes | yes | only if `evidence_req` accepts it | **no** |
| `OrgAttested` | yes | yes | yes | yes | yes, with appeal path |
| `ProviderVerified` | yes | yes | yes | yes | yes, with appeal path |
| IP-derived (any) | yes | yes | yes | only as declared and only for new access | **no** |

The last column is the load-bearing rule: **no weak signal removes access a
subject already has.** Removing existing access requires either strong
evidence or a human decision (§5.4, §4.3).

## 4. Public IP as evidence

### 4.1 What is derived

The public IP a connection arrives from is a *signal*, never an identity.
The framework permits deriving, in increasing privacy:

1. a **country/region verdict** (default),
2. a **boundary verdict** — "inside / outside boundary X" (`VerdictOnly`),
3. the **raw IP** only when a scope explicitly enables it for a stated
   retention window and purpose.

Default retention for derived IP evidence is **short** (the connection's
lifetime plus a bounded window), because IP is personal data in most
regimes and the framework's job is to need less of it, not more.

### 4.2 Known error modes (must be stated in any UI that uses IP evidence)

VPN / commercial proxy, CGNAT (many users behind one address), corporate
egress (all staff appear in one country), mobile networks (address changes
mid-session), satellite / Starlink (egress country ≠ user country), and
relay/bridge connections where **the visible IP is the relay's, not the
user's**. The last one means IP evidence is *structurally unavailable* on
federated paths — the framework must say so rather than silently treat a
relay's address as the user's.

### 4.3 Contradiction handling

When declared evidence and IP evidence disagree:

| Situation | Behaviour |
| --- | --- |
| Declaration admits, IP contradicts, action is *new* access | `warn` by default; admin may raise to `step-up` or `quarantine` |
| Declaration admits, IP contradicts, action is *existing* access | `warn` only. Never deny on IP alone (§3.4) |
| No declaration, IP only | May gate *new* access per the declaration's `evidence_req`; never removes existing access |
| Two IP signals disagree (e.g. X-Forwarded-For vs socket) | Treat as **unknown** — unknown denies new access under a scoped policy, per `residency.rs` |

**X-Forwarded-For trust is explicit and off by default.** A scope must
declare which proxies it trusts to set forwarding headers; an untrusted
header is ignored, not believed. This is the same "peer's own statement is
never evidence" rule `residency.rs` already enforces.

## 5. Sanctions boundaries

### 5.1 The list is data

A sanctions boundary references a **versioned list**, never hard-coded
country or entity names:

```
ListVersion { id, source, effective_from, effective_to, entries, signature }
```

- **Source:** operator-supplied (their own list) or a list shipped with the
  software as a *starting point*, clearly labelled as not legal advice.
  The framework does not fetch external feeds in the skeleton — that is a
  later step (§11).
- **Updates propagate as new versions.** A decision log entry names the list
  version applied, so a past decision is reproducible against the list that
  produced it.
- **Effective dates** are part of the data: a list entry may be scheduled.

### 5.2 Scope of "interaction"

A sanctions boundary must declare **which interactions it covers**, because
"interact" is not one thing:

| Interaction | Typical default when a sanctions boundary is enabled |
| --- | --- |
| Account creation / signup | covered |
| Login to an existing account | covered, with grandfathering (§5.3) |
| World membership | covered |
| Blob storage | covered |
| Bridge / federation traffic | **declared explicitly** — often *not* covered, because transit ≠ service |
| Relay transit | **declared explicitly** — a relay transiting a jurisdiction it does not serve is a different act |

An empty `enforcement` for an interaction means *not covered*, and the
declaration must say so rather than leave it ambiguous.

### 5.3 Grandfathering and list changes

When a list entry **appears**, existing accounts / worlds / federation links
are **grandfathered** by default: they keep working and are flagged for
review, rather than being cut off by a data update nobody was warned about.
When an entry is **removed**, grandfathered subjects are cleared and the
removal is logged.

This is a deliberate asymmetry: adding a restriction must not silently
destroy existing work, and the framework's default is the gentler one.

### 5.4 False positives and appeals

Name collisions, dual citizens, residents vs citizens, and travellers
temporarily present are *expected*, not exceptional. The framework therefore
requires:

- an **exception path** — a subject can be recorded as an exception to a
  boundary, with the evidence and the actor, as a new declaration version;
- a **review queue** for flagged subjects (the #5883 audit/appeals design
  supplies the UX; this skeleton supplies the data);
- **no hard block without recourse** — a `deny` on a sanctions boundary must
  name the appeal path in the user-facing message.

## 6. Intranet-mode servers

### 6.1 Boundary definition

A `network` capability whose boundary is declared as one or more of:

| Mechanism | Strength | Note |
| --- | --- | --- |
| Source IP ranges | weak | spoofable at the edge; CGNAT/VPN error modes apply |
| VPN / overlay network membership | medium | identity of the overlay peer |
| mTLS client identity | strong | cryptographic client identity |
| Org IdP assertion | strong | signed assertion from a trusted IdP |

An admin declares which mechanisms satisfy the boundary; the strongest
available should be used for privileged actions.

### 6.2 Gating generic activity

Connections from **outside** the declared boundary cannot perform ordinary
user activity. The framework does not invent a new gate: it supplies hops to
`evaluate()` with `Plane::Transport` and the declared boundary as the
resource, and the surface renders the `Decision`.

### 6.3 2FA step-up points

Step-up is required at, at minimum:

- entering from a **new network** (first time from this boundary context),
- **privilege escalation**,
- **admin actions**.

A step-up grants a bounded window (declared per scope, default short); after
it expires the next privileged action steps up again. Step-ups are logged.

### 6.4 Org-escrowed credentials

The org escrows credentials and **proxies required details** to the server on
the user's behalf, so the server can enforce its requirements without holding
raw user data it does not need:

- **Escrowed:** the credential material, by the org, under the org's control.
- **Proxied:** *assertions* — "member of group G", "residency attested",
  "identity verified" — not raw values, wherever an assertion suffices.
- **Audit:** every proxy use is logged with what was asserted and to whom.
- **User visibility:** the user can see what was shared about them and when.
- **Un-escrow:** the user (and the org, per its own policy) can revoke; the
  server then loses the assertion and re-evaluates.

Consent model (per-use vs standing vs org-authority-alone) is an open point
(§11) with a recorded default: **standing consent, visible and revocable**,
because per-use prompts train users to click through.

### 6.5 Degraded behaviour

Boundary unreachable, IdP down, VPN down: **fail closed for generic
activity** — the safe default, since the boundary's purpose is exclusion.
A **break-glass** path exists, held by a named role, its use logged loudly
and surfaced to admins. Break-glass is a human action, never an automatic
fallback.

## 7. Composability

Server boundary ∧ world boundary ∧ user preference. The rule is
**intersection, always**:

```
effective = server_boundary ∩ world_boundary ∩ user_preference
```

- A **user preference can never widen** a server or world boundary. It can
  only add restrictions the user chooses for themselves.
- A **world cannot widen** its server's boundary.
- A **conflict is a deny with a reason** naming which scope denied, not a
  silent merge. The user-facing message says which boundary excluded them
  and offers the appeal path.
- The intersection is computed over the same `Policy`/`Plane` vocabulary, so
  there is no second merge algorithm to reason about.

A user belonging to worlds under contradictory boundaries is **allowed**:
the contradiction is resolved per-action by intersection, and the user sees
which world's boundary excluded them. It is not the framework's job to
forbid the membership.

## 8. Enforcement surfaces

Each surface supplies hops and renders the decision; none re-implements
evaluation.

| Surface | Hops supplied | Extends |
| --- | --- | --- |
| **Signup / login** | transport (connection), storage (where the account store lives) | #2283 |
| **World membership / world blobs** | storage (world blob store), processing (world turn host) | #3397 |
| **Bridge / federation / relay** | transport (peer, relay, bridge), with **peer-asserted evidence marked unverified** unless the operator trusts that peer | #3398 |
| **Capability grants / delegation** | the boundary of the grantee and the exercise location | new, minimal |

**Peer-asserted evidence** is the sharp edge: a federated peer's claim about
a user's location is `Self`-grade evidence from that peer until the operator
adds the peer to its trust roots. The skeleton's default is *unverified*.

**Audit:** every decision that denies, steps up, or quarantines is logged
with the scope, the boundary version, the evidence **classes** and assurance
levels consulted, the outcome, and the actor — following the #5883 decision
log. Raw evidence values are not logged (§3.3).

## 9. Reuse of `residency.rs`

| Need | Reuse | Extend |
| --- | --- | --- |
| Plane / jurisdiction / resource vocabulary | `Plane`, `Jurisdiction`, `ResourceId` — unchanged | — |
| Scope ownership | `Scope::{Unscoped, Scoped}` — unchanged | — |
| Per-plane allow-lists, trust roots | `Policy`, `PlanePolicy` — unchanged | — |
| Evidence authenticity + revocation | `Evidence`, `EvidenceVerifier` — unchanged | add `assurance`, `basis`, `privacy_class`, `subject` |
| Decision procedure | `evaluate()`, `DenyReason`, `Decision` — unchanged | a thin pre-step that maps a declaration + subject evidence to the `Hop`s `evaluate()` consumes |

The extension is deliberately **additive**: `evaluate()` keeps its current
signature and semantics, so #2283/#3397/#3398 code that already calls it is
unaffected. The new layer answers "which hops does this declaration imply,
and does the subject's evidence satisfy the assurance bar?" and then hands
off to the existing evaluator. No second evaluator is introduced.

## 10. Worked examples

### 10.1 A sanctions-enabled public server

- Admin enables `sanctions` on the server scope, `enabled: true`, with a
  list version `L7`, covering signup + login + world membership, **not**
  federation transit.
- A new signup from a listed country: `deny` at signup, message names the
  appeal path.
- An existing account whose country appears in `L8`: **grandfathered** —
  flagged for review, access continues until a human decides.
- A dual citizen appeals; admin records an exception as a new declaration
  version; the decision log shows the exception and who granted it.

### 10.2 An intranet-mode org server

- Admin enables `network` on the server scope with mTLS client identity as
  the boundary mechanism; generic activity requires it.
- A connection from outside: `deny` for generic activity, with a message
  naming the boundary — no silent failure.
- An admin action from inside still triggers `step-up` (2FA), window 15
  minutes, logged.
- The IdP goes down: generic activity **fails closed**; break-glass is
  available to the named role and its use is logged and surfaced.

### 10.3 A jurisdiction-pinned world

- A world enables `residency` on its own scope, requiring `OrgAttested`
  evidence for `Plane::Storage` in jurisdiction `eu`.
- A joining user with a `Self` declaration only: `deny` with reason
  `NoEvidence(Storage)`-equivalent — the assurance bar is not met, and the
  message says an org attestation is required.
- A user with `OrgAttested` eu storage evidence: `allow`; the world's blobs
  land in the eu store per #3397 partitioning.
- The user's own preference adds a stricter metadata restriction: the
  intersection applies; the user's preference narrows, never widens.

## 11. Open points (with assumed defaults)

| Question | Assumed default for the skeleton | Why |
| --- | --- | --- |
| Minimum evidence for a sanctions boundary | `Self` declaration + human review; IP may flag | Weak signals must not hard-block (§3.4) |
| Declaration vs IP disagreement | `warn` by default; admin may raise to step-up/quarantine | Contradiction is information, not proof (§4.3) |
| Who is authoritative for a sanctions list | Operator-supplied; shipped list is a labelled starting point | No external feed in the skeleton (§5.1) |
| Org-escrow consent model | Standing consent, visible and revocable | Per-use prompts train click-through (§6.4) |
| Contradictory world memberships | Allowed; resolved per-action by intersection | Forbidding membership over-reaches (§7) |
| Evidence retention after account closure | Derived/verdict evidence deleted with the account; `Exact` per operator policy | Least data (§3.3) |
| Federation peer assertions | Unverified (`Self`-grade) until the peer is a trust root | Peers are not evidence by default (§8) |
| External sanctions feeds | Out of scope for the skeleton; a later step | Basic frameworks first (§1) |

## 12. Decomposition into implementation issues

The skeleton is one design; its implementation splits along the seams above.
Issues are filed and linked from #5683 in the same pass as this record:

1. **Evidence assurance layer** — `assurance`, `basis`, `privacy_class`,
   `subject` on the evidence record; assurance-bar check before `evaluate()`.
2. **Declaration record** — the `BoundaryDeclaration` type, versioning,
   `enabled`-only-by-explicit-action, rejection of empty `enforcement`.
3. **Public-IP evidence derivation** — country/boundary verdicts, retention,
   X-Forwarded-For trust configuration, contradiction → `warn`.
4. **Sanctions list data model** — versioned lists, effective dates,
   propagation, grandfathering, exception records.
5. **Intranet-mode gating** — network boundary mechanisms, step-up points,
   fail-closed, break-glass logging.
6. **Surface wiring** — #2283 signup/login, #3397 world membership/blobs,
   #3398 federation/relay, each supplying hops to `evaluate()`.

Each is a separate implementation issue; none is implemented by this record.

## 13. Non-goals

- Turning any restriction on by default, for any deployment.
- Jurisdiction-specific rule packs (a GDPR compliance suite, a specific
  country's sanctions enforcement) in this pass.
- Legal advice or a legal determination — the framework provides
  capabilities; the operator's obligations are the operator's.
- Replacing #2283 / #3397 / #3398 — those remain the surface-specific
  designs; this is their shared vocabulary.
- Fetching live external sanctions feeds, automated classification, or a
  policy language.
