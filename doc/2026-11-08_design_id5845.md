# Obsidian importer — design record for the #2048 object model

Design record for issue #5845 ("id: design: importer design: Obsidian
(from #5678)"). Origin issue: #5845. Parent programme: #5678 (design
cluster decomposition; this record composes with its decisions and
does not re-decide them — §8). Target model: #2048, whose record is
`doc/2026-11-01_design_id2048.md`: a note is a logical object with a
stable note ID (the signed `note.create` event ID), immutable signed
revisions (`note.revise`, multi-head until an explicit merge), typed
links stored as structured values (target note ID, sigil/type,
authored surface, optional pinned revision), backlinks derived from
outgoing references in active heads, and names as claims, not IDs
(duplicate names allowed; resolution returns candidates + provenance).
Sibling importer designs — #5846 (Evernote), #5847 (Logseq), #5848
(Joplin), #6438 (OneNote) — are each their own record; this one covers
Obsidian only and shares with them only the import-manifest shape in
§7. Status: v1 design, settled except the items explicitly deferred
in §9. No implementation is authorized by this record alone.

## 1. Problem

An Obsidian vault is a directory of Markdown files plus attachments,
with meaning carried in conventions Obsidian layers over plain files:
wikilinks (`[[Note]]`, `[[Note#Heading]]`, `[[Note|alias]]`), embeds
(`![[file.png]]`, `![[Note]]` transclusion), YAML frontmatter,
inline and nested tags (`#project/alpha`), block references
(`[[Note#^block-id]]`), and `.canvas` files (a JSON graph of nodes
and edges). A naive file copy imports the bytes and loses exactly the
parts that made the vault a knowledge graph: links become dead text,
frontmatter becomes inert YAML, canvas structure vanishes. This
record settles, per construct, what maps cleanly into the #2048
model, what degrades (and how the degradation is recorded), and what
is refused.

## 2. Decision in one paragraph

Import is a **two-phase, manifest-first** operation. Phase 1 scans
the vault read-only and produces a signed import manifest: one entry
per source file with its content hash, its proposed note title claim,
its parsed links/tags/frontmatter, and the disposition each construct
will receive under §3–§6. Phase 2 executes the manifest: each
Markdown file becomes one note (one `note.create` carrying the
converted body as its initial revision); each attachment becomes a
content-addressed blob plus an attachment record; each wikilink
becomes a typed #2048 link whose target is the *stable note ID* of
the resolved target and whose authored surface preserves the original
wikilink text verbatim. Re-import is deduplicated by content hash
(§7): an unchanged vault re-imports as a no-op, never as duplicate
notes. Canvas files are **degraded, not imported as graphs** (§6):
their text/file nodes become notes or references and their edges
become typed links, but canvas layout is preserved only as manifest
data, not as a #2048 object.

## 3. Markdown and attachments: mapping and loss classification

Classification key: **clean** = round-trips semantically into the
#2048 model; **lossy-recorded** = imported with a named, manifest-
recorded loss; **refused** = not imported, named in the manifest with
the reason (never silently dropped).

| Obsidian construct | Disposition | Class |
|---|---|---|
| Markdown body (CommonMark + GFM tables/task lists) | Note body, carried verbatim except link/ embed rewriting (§4) | clean |
| Headings, lists, code blocks, math (`$...$`), footnotes | Verbatim in body; no structural extraction in v1 | clean |
| Attachment files (images, audio, PDF, other binaries) | Content-addressed blob + attachment record; references rewritten to the attachment record | clean |
| `![[image.png]]` embeds of attachments | Attachment reference in the importing note's revision | clean |
| `![[Note]]` transclusion | Typed link with sigil `transclusion` + the authored surface; the target's body is **not** inlined into the importing note (inlining would fork content identity) | lossy-recorded (render-time expansion is a presenter concern, later slice) |
| Callouts (`> [!note]`) | Verbatim blockquote text; callout type preserved as surface syntax only | lossy-recorded (no callout semantics in the #2048 model) |
| Highlight (`==text==`), comments (`%%...%%`) | Verbatim surface text | lossy-recorded |
| HTML embedded in Markdown | Verbatim; presenters apply their own sanitisation policy (not an importer decision) | lossy-recorded |
| `.obsidian/` configuration, plugin data, workspace state | Not imported | refused (application state, not knowledge content; named in manifest) |
| Files with extensions Obsidian treats as notes but that are not Markdown (e.g. `.base`, exotic plugin formats) | Not imported in v1 | refused (no settled mapping; a future importer slice may claim them) |
| Encrypted/binary plugin blobs | Not imported | refused (opaque, undecodable) |

Attachment identity is the blob's content hash, so the same image
used by nine notes is stored once and referenced nine times; this
composes with, and does not re-decide, the attachments & media
cluster design (#5844) — if #5844 settles a different attachment
record shape, the importer emits that shape, and only the manifest's
attachment section changes.

## 4. Wikilinks and backlinks

- **Resolution order** (per wikilink, deterministic, recorded in the
  manifest): (1) exact vault-relative path match (`[[folder/Note]]`);
  (2) exact file-name match; (3) Obsidian alias match (frontmatter
  `aliases`); (4) case-insensitive file-name match. The first step
  that yields exactly one candidate wins. A step yielding more than
  one candidate makes the link **ambiguous**: it is imported as a
  typed link in unresolved state carrying the authored surface and
  the candidate list — never silently resolved to the first
  candidate. This follows #2048's names-are-claims rule: duplicate
  names are legal, and resolution surfaces ties with provenance.
- **Resolved links** become typed links per #2048: target = stable
  note ID of the target note, sigil/type = `wikilink` (or
  `transclusion` for `![[...]]`), authored surface = the exact
  original text inside the brackets (including any `|display` part),
  pinned revision = none (Obsidian links name notes, not revisions;
  pinning the import-time head would freeze links Obsidian itself
  leaves live).
- **Heading links** (`[[Note#Heading]]`) and **block links**
  (`[[Note#^id]]`): target note as above; the heading/block part is
  carried in the link's authored surface and in a manifest note, but
  v1 has no sub-note anchor object, so the anchor is
  **lossy-recorded** — presenters may best-effort scroll to a heading
  of that name; the graph edge itself is note-to-note.
- **Unresolved links** (`[[Note]]` naming a file that does not exist
  — a common, deliberate Obsidian idiom for planned notes): imported
  as typed links in unresolved state with the authored surface,
  exactly as #2048 prescribes for inaccessible/unresolved references
  (degrade to stored surface + unresolved state). They are **not**
  turned into empty stub notes in v1: creating content-free notes
  for every dangling link pollutes the graph and invents authorship;
  if the target is imported later (or created), ordinary resolution
  binds the link then. Rejected alternative recorded in §8.
- **Backlinks** are never imported as data. They are derived by the
  #2048 projection from outgoing references in active heads; the
  importer's job is only to make the outgoing links correct.
- **Markdown links** (`[text](other.md)`, `[text](https://…)`) stay
  as authored in the body; vault-relative `.md` links are *also*
  recorded as typed links (same resolution order) so they participate
  in backlinks; external URLs remain plain body text links only.

## 5. Frontmatter and tags

Frontmatter is parsed as data, never carried into the body verbatim.

| Frontmatter field | Mapping |
|---|---|
| `title` | The note's title claim (display name), if present; otherwise the file name is the claim — renaming never changes the note ID (#2048) |
| `aliases` / `alias` | Additional name claims for the note, each with provenance "obsidian-frontmatter" |
| `tags` | Tag claims per #2048 (`tag_claims` semantics: labels/aliases, not canonical directed edges) |
| `cssclasses`, `publish`, `permalink` and other Obsidian-/plugin-specific presentation or publication fields | **Dropped**, named in the manifest with the reason: they encode one app's presentation/publication state, not knowledge content; importing `publish: false` as a visibility fact would invent an access decision this importer has no authority to make |
| All other fields (arbitrary user/plugin keys) | Preserved as typed properties on the note's initial revision under their original key names, values limited to YAML scalars/lists of scalars; nested maps are stringified and the loss recorded in the manifest |

Inline tags (`#tag`, `#project/alpha`) become tag claims with their
full nested path preserved as the claim string; hierarchy is a
projection concern (a presenter may split on `/`), not extra graph
edges. A `#` heading marker is never a tag; the parser distinguishes
them by Obsidian's own rule (tag `#` is not followed by a space).

## 6. Canvas

**Decision: degrade.** A `.canvas` file's nodes and edges are
imported, its layout is not a graph object:

- File nodes referencing vault notes/attachments resolve to those
  notes/attachments; text nodes become notes of their own (title
  claim from their first line, per the manifest); link nodes (URLs)
  become notes whose body is the URL, or attachments of nothing —
  v1: a note whose body contains the URL as a plain link.
- Edges become typed links between the corresponding notes with
  sigil/type `canvas-edge` and the edge label (if any) as authored
  surface.
- Node positions, sizes, colors, and grouping are recorded in the
  import manifest only (**lossy-recorded**). The #2048 model has no
  layout object; inventing one inside an importer would pre-empt the
  graph-view design (#5837), which owns spatial presentation.
- A canvas referencing a missing file follows §4: unresolved link,
  no stub.

Rejected: refusing canvas outright (loses real authored structure —
the edges), and importing canvas as a first-class object (forks a
#5837 decision). Degrade keeps the knowledge, records the loss, and
leaves layout to its owner.

## 7. Deduplication and re-import

- Identity on import is **content-derived**: each source file's
  manifest entry carries the SHA-256 of its bytes. The importer
  records, per imported note, a provenance entry `(vault-relative
  path, content hash, import manifest ID)` in the manifest, not in
  the note body.
- Re-importing the same vault: a file whose content hash equals the
  hash recorded for its path is **skipped** (no new revision, no
  duplicate note). A changed file at a known path becomes a new
  `note.revise` on the existing note ID, parented on the current
  head(s) per #2048 — if heads have diverged (the note was edited
  in-app since import), the import revision is a new head, never a
  silent overwrite; joining heads is the user's explicit merge, per
  #2048.
- A moved/renamed file (path changed, content hash known) is a
  rename: the note gains the new title claim; its ID does not
  change. A file whose hash is known at *two* paths is imported
  once; the second path is recorded as an additional claim source,
  not a second note.
- Two different files with the same name are two notes with the same
  title claim — legal under names-are-claims; §4's ambiguity rule
  governs links to that name.
- Attachments dedupe by blob hash (§3), within and across imports.
- The manifest is the audit record: every skipped, revised, renamed,
  degraded, and refused item appears in it with its reason. An import
  with no manifest is not complete.

## 8. Alternatives rejected, and the parent boundary

- **Stub notes for unresolved links** — rejected (§4): graph
  pollution and invented authorship; unresolved-state links carry
  the same information honestly.
- **Inlining transclusions** — rejected (§3): duplicates content
  under a second identity and breaks revision provenance.
- **Canvas as a first-class layout object** — rejected (§6):
  pre-empts #5837.
- **One note per folder / folder-as-note hierarchy** — rejected:
  Obsidian folders are filing, not content; folder paths survive as
  manifest provenance and may become tag claims only if a future
  slice settles that — v1 does not, because silently tagging by
  folder invents metadata the author did not write as tags.
- **Importing `.obsidian` plugin data as properties** — rejected
  (§3): application state, undecodable in the general case.

Parent boundary: this record does not re-decide #5678 programme
decisions, #2048's identity/link/revision model, #5844's attachment
record shape, or #5837's graph-view ownership; it composes with
them. No answer above changes a parent decision. If implementation
finds a conflict (e.g. #5844 settles an incompatible attachment
shape), the conflict is recorded explicitly on both this issue and
the owning sibling before code lands — never silently forked.

## 9. Test corpus specification

Implementation acceptance requires a fixture vault corpus, committed
with the importer, covering at minimum:

1. **Wikilinks + backlinks**: notes A→B→C with plain, aliased
   (`|display`), path-qualified, and case-variant links; expected
   derived backlink set asserted per note.
2. **Aliases and ambiguity**: two notes with the same file name in
   different folders; a frontmatter alias colliding with a third
   note's name; links to each — asserted ambiguous-or-resolved per
   §4's order, with the manifest recording the step that decided.
3. **Unresolved links**: links to nonexistent notes, including one
   whose target is added in a second import (asserted: binds on
   re-import, no stub ever created).
4. **Nested tags**: `#a`, `#a/b`, `#a/b/c` inline and in
   frontmatter; a `# Heading` that must not parse as a tag.
5. **Frontmatter edge cases**: no frontmatter; empty frontmatter;
   `aliases` as scalar and as list; nested-map values (stringified,
   loss recorded); `publish: false` (dropped, recorded).
6. **Attachments**: the same image embedded from two notes (one
   blob); an attachment with no referencing note (still imported —
   it is vault content); a missing attachment file (manifest
   refusal, import continues).
7. **Canvas**: one canvas with file, text, and link nodes, labelled
   and unlabelled edges, and a missing-file node; asserted edge set
   and manifest layout record.
8. **Re-import idempotence**: importing the §1–§7 corpus twice
   yields identical note/revision/blob counts and an all-skipped
   second manifest; then one file edited, one renamed, one added —
   asserted: one new revision, one rename claim, one new note.
9. **Transclusion + callouts + heading/block links**: the
   lossy-recorded set, asserted present in the manifest with their
   losses named.

The corpus oracle is the manifest + graph state, not golden body
text: bodies are verbatim by §3, so the assertions that matter are
link targets, claims, dedupe counts, and recorded losses.

## 10. Invariants implementation must hold

- Import never invents content, authorship, or access decisions:
  no stubs, no visibility facts from frontmatter, no silent
  resolutions of ambiguous names.
- Every loss, refusal, skip, and degradation in an import appears
  in that import's manifest with a reason; silent drops are bugs.
- Note identity across rename/revision follows #2048 exactly:
  stable IDs, names as claims, multi-head revisions joined only by
  explicit merge.
- Backlinks are always derived, never stored by the importer.
- Re-import of unchanged content is a no-op (§7), verified by
  corpus fixture 8.
