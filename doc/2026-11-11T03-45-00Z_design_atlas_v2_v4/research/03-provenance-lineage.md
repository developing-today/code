# Provenance-complete resolution, lineage, and reversible curation

Research appendix for [#6020](https://github.com/developing-today/code/issues/6020); 2026-11-11 UTC. This is an option analysis, not a selection of a graph framework, storage schema, or deployment claim. Completeness means complete with respect to a specified ingested, retained, authorized snapshot, not the web or all historical copies. A public response must not leak the existence, count, paths, or graph degree of forbidden occurrences.

## Primary-source findings

Sources below were retrieved 2026-11-11 UTC with the ordinary web fetcher, without substituted user agents.

1. [W3C PROV-DM](https://www.w3.org/TR/prov-dm/) (W3C Recommendation, 2013): entities, activities, agents, derivations, responsibility, alternate/specialization, and named bundles allow provenance _of provenance_. Use and generation alone do not prove derivation: influence must be established. Multiple incompatible provenance descriptions can coexist. This is useful conceptual vocabulary and potential interchange, not proof that Atlas needs RDF or a particular graph database.
2. [Git internals: Git objects](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects) (Git project's official book): a blob is addressed by a hash of type/size and bytes, a tree adds name and placement, and a commit adds snapshot, parent(s), author/committer claims and time. Equal blobs do not establish equal placement, authorship, history, or authorization. Hash algorithm and exact canonical bytes must be identified; do not reproduce the book's SHA-1 example as a new security recommendation.
3. [OpenLineage object model 1.55.0](https://openlineage.io/docs/spec/object-model/) (project specification): a job definition, an individual run, and input/output datasets are distinct. Run events are additive observations; static job/dataset metadata is distinct from run events; dataset versions and per-run input/output facets can carry snapshot and subset context. A dataset-level edge alone does not prove row-, document-, span-, or claim-level lineage, nor does an absent event prove no dependency.
4. [W3C Web Annotation Data Model](https://www.w3.org/TR/annotation-model/) (W3C Recommendation, 2017), especially selectors and states: a specific resource can identify both a segment and a particular state; quote and position selectors are different tools. Quote text can be duplicated or sensitive; positions depend on the chosen representation and can drift. Source properties copied into an annotation are hints, not authoritative source statements.
5. [SLSA 1.2 attestation model](https://slsa.dev/spec/v1.2/attestation-model) (project-approved specification, software supply-chain scope): an authenticated envelope signs a statement binding a subject to a typed predicate. Signature authenticates the attester's statement, not its truth, completeness, author's identity, permission to disclose, or freshness. Atlas may borrow the separation and verifier policy; software-build provenance is not automatically an ingest-attestation specification.
6. [PostgreSQL 18 recursive queries](https://www.postgresql.org/docs/18/queries-with.html#QUERIES-WITH-RECURSIVE) (PostgreSQL project documentation, retrieved 2026-11-11 UTC): recursive CTEs iterate through working tables and support explicit cycle detection; tracking path/depth can defeat simple row deduplication. A parent `LIMIT` is not a reliable production bound, especially with outer sorts or joins. This establishes feasibility, not an Atlas database selection or benchmark.

## Identity and evidence boundaries

- **Content** is a specific byte sequence or explicitly named normalized representation, identified with algorithm, encoding and normalization/version. Content equality is not semantic equivalence, occurrence identity, or authorization. Retain raw-to-derived transformation evidence where permitted.
- **Occurrence** is an observation or placement of content in a source context at a particular time, including source-native locator, tenant/security domain and capture identity. Two mirrors of identical bytes are separate occurrences; repeated fetches may be separate observations of the same placement. Specify idempotence rather than deduplicating away evidence.
- **Version** is a source or Atlas representation at a stated revision/snapshot/time; a mutable URL is not a version. Versions may have identical content, and observed time is not necessarily effective/source time. Version ancestry is asserted, not inferred from equal text.
- **Authority** is a scoped, time-varying right or responsibility of a principal to make a particular claim or perform an action, established by evidence and policy. Claimed writer, authenticated ingester, publisher, curator and access-control principal can differ. Signature validity does not confer any of these roles.
- A **claim/link** is a separately attributable assertion, not the entity itself. Same-as, alias, derived-from, cites, contradicts, supersedes, and possible-match are distinct and can be conditional on version and valid time. Record evidence, method/model and version, claimant, timestamps, scope, confidence if calibrated, and decisions. Missing evidence remains unknown rather than false.

Illustration: two sites publish the same paragraph. One revises it while the other retains the old version; an extractor builds an answer with one supporting span from each. There is one shared content identity for the exact matching bytes but two source occurrences, independently changing versions and potentially different permissions and writers. The answer needs two separately authorized support paths; losing one path does not prove the other was derived from it.

## Resolution and lineage options

| Option                                                                                  | Advantages                                                                                                                                        | Costs and limits                                                                                                                                                                                                                              |
| --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. Exact source-native identifiers and version-pinned spans only                        | Deterministic, cheap lookup, low false-merge risk, easy audit. Good initial floor.                                                                | Misses cross-source aliases, paraphrases and derivations. Native identifiers can be reused or reassigned; still need namespace and time.                                                                                                      |
| B. Evidence-backed candidate links and reversible curated decisions, with exact anchors | Preserves ambiguity, supports multiple conflicting sources, incremental matching and human correction; can trace answers through transformations. | More write/read amplification, adjudication and policy complexity. Matching scores are not universal probabilities; record model and candidate-generation coverage.                                                                           |
| C. Global canonical entity or automatic transitive same-as closure                      | Simple-looking query and aggregated recall.                                                                                                       | **Dead end as sole truth:** one false match contaminates transitive groups, different versions/permissions collapse, and a later split is expensive. Can be a rebuildable, scoped projection over B, never destructive authority.             |
| D. Full synchronous global lineage graph on every query                                 | Potentially rich explanation.                                                                                                                     | **Dead end as mandatory hot path:** unbounded fan-out, cycles, distributed failure, inconsistent freshness and authorization side channels. Bounded, snapshot-consistent traversal with continuation and explicit incomplete status is safer. |

Prefer B as a design direction, with A as an independently useful baseline and optional export mappings to PROV/OpenLineage. Candidate links remain provisional until supported; negative match is not proof of different real-world entities. Do not collapse contradicting claims into a single chosen fact. Time-scoped aliases and relations should support many-to-many joins, revocation and later splits; keep original source claims intact.

### Implementation and interchange alternatives (orthogonal choices)

| Alternative                                                | Query/space and reliability tradeoffs                                                                                                                                                                                                                                                                                                                                                                                                                                                       | Consistency and failure boundary                                                                                                                                                                                                                                                                                                       |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Lean relational typed edges, evidence records and indexes  | For V nodes and E recorded edges, base records and forward/reverse adjacency indexes are O(V+E), excluding evidence payloads and index overhead. Indexed direct neighbors cost approximately O(log E + degree); a bounded visited-node traversal visits O(Vr+Er) reachable nodes/edges plus index, authorization and sorting costs. Enumerating _all paths_ can be exponential even in a DAG; cycle/path bookkeeping adds space. Recursive SQL is an option, not a guarantee of fast plans. | Single-store transactions can align decisions, versions and edge writes where they share a transaction; async indexes/cross-store sources still lag. Recursive queries require explicit cycle and resource bounds. Authorization and tombstones cannot be postponed until after traversal.                                             |
| Optional specialized graph engine, as a derived projection | May offer convenient path operators or better performance for a measured multi-hop workload; no universal complexity or speed advantage. Base adjacency is O(V+E), plus replicated properties, indexes, paths and operational overhead. Dense or all-path workloads still explode.                                                                                                                                                                                                          | Replication lag, partial updates, competing graph/relational snapshots and deletion/revocation propagation introduce new failure modes. Require a checkpoint/watermark, idempotent rebuild, access-aware traversal, fail-closed stale policy and reconciliation. Do not let the projection silently become writer or policy authority. |
| PROV concepts and optional interchange                     | Entity/activity/agent and attribution/derivation vocabulary make external explanations portable; mappings and bundles can preserve claims of provenance. Serialization and expanded evidence consume space proportional to exported facts and qualifiers; it is neither a query engine nor a guarantee of actual provenance completeness.                                                                                                                                                   | Mapping can lose local occurrence semantics, authorization and uncertainty if flattened. PROV compatibility alone does not require RDF storage.                                                    |
| OpenLineage run/ingest observations                        | Run/job/dataset events can express actual process observations and coarse inputs/outputs. Event storage grows with emissions and facets; per-span evidence is extra and not implied by dataset edges. Batching lowers overhead but loses granularity unless locators survive.                                                                                                                                                                                                               | Events arrive late, duplicated, partial or not at all; static job definitions are not run evidence. Match run IDs, sequence/watermark and idempotency keys; distinguish declared, observed, completed and inferred lineage. Existing batch attestation remains a separate provenance assertion and verification boundary.              |

The above complexity is an analytical model, not a measured claim or a commitment to Postgres or a graph product. Compare alternatives using representative branching factors, deep and high-degree cases, authorized traversal, concurrent revocation, memory and storage amplification, tail latency, rebuild time, and consistency under failures. A graph engine is justified only if a measured requirement outweighs its additional authorization and recovery surface; GraphRAG is not implied.

## Retrieval, anchors, curation and failure behavior

For a resolution, first establish caller and requested snapshot; obtain candidates within authorized scope, then traverse permitted claim → evidence span → representation/version → occurrence → permitted source and any declared transformation/run/agent edges. Enforce authorization on every node and edge _before_ aggregation, ranking, snippets, counts and caches. Return supporting and opposing authorized evidence, interpretation and uncertainty, and distinguish complete-for-snapshot, partial, stale, inaccessible-in-a-privileged-audit-context, unavailable, and deleted. Public interfaces must use a non-revealing response for both nonexistent and forbidden evidence. Never substitute a newer version silently when the pinned one is gone.

An anchor should specify the exact representation/version, offset unit and interval convention, extraction/normalization pipeline version, plus quote/context or a digest where policy permits. Verify the target before rendering. Exact version + position is fast; quote/context helps recovery after change but repeated text can yield multiple candidates, so do not silently choose a match. OCR, Unicode normalization and PDF layout complicate mapping; return ambiguous/unmapped when evidence cannot be established. Avoid retaining quote text in unrestricted indexes or immutable logs when deletion/access policy prohibits it.

Curation is append-or-versioned decision evidence only where retention permits: propose merge, reject, split, suppress, annotate or supersede with actor, rationale, evidence scope, effective time, prior decision and operation version. Recompute affected projections; rollback changes a decision rather than rewriting source evidence. Concurrent curation needs conflict handling, explicit precedence/authority and a compare-version or equivalent guard. Reversibility is subordinate to legally required erasure: do not preserve prohibited source text merely for audit. Consider minimum non-identifying deletion receipts only when allowed; even hashes, IDs and edge counts can leak information.

## Reliability and scale

Ingest and projection events should be idempotent and replayable where retention permits, with durable checkpoints, ordering/version rules, duplicate detection, dead-letter/reconciliation and observability for missing or late events. A pipeline run's declared inputs/outputs are observations, not automatic fine-grained causation. Clearly record uninstrumented boundaries and partial runs. Access and deletion changes must invalidate or fence stale caches and derived indexes; define propagation acknowledgments and a fail-closed serving policy while unsettled. Measure completeness against a named inventory and watermark, not an unknowable universal denominator.

Index direct references both directions, partition by tenant/security boundary and source/version, and bound graph traversal by depth, fan-out, time and result size; use continuation tokens bound to snapshot and authorization. Materialized lineage and entity clusters are rebuildable projections with watermarks and an authoritative source-of-record decision log; monitor lag, stale results, deletion backlog, candidate precision/recall and adjudication reversals. Hashing and source/occurrence indexes are near-linear in ingested size; broad transitive traversal can expand with reachable edges and high-degree nodes. Indexing spans and multiple evidence paths increases storage and write amplification; retention, sampling and granularity should be workload-tested, not selected from asymptotics alone.

## Evaluation and open decisions

Use a permission-labelled, versioned corpus with repeated boilerplate, conflicting claims, source revisions, OCR/normalization drift, duplicate ingests, delayed events, revoked access, and deletion across source and derived paths. Oracles: exact span bytes against pinned representation; independently annotated entity/lineage links and explicit no-link/unknown labels; authorization noninterference comparing public responses with and without hidden records; deletion convergence over enumerated permitted stores. Measure false merges/splits, link coverage and calibration, provenance-path completeness, unauthorized disclosure, p95/p99 latency, write amplification and propagation lag. Exercise concurrent curate/reverse/replay and crash recovery. Include cases where the original evidence no longer exists: honest unavailability is success, not fabricated provenance.

Open decisions: legal retention of identifiers/receipts and quotes; authoritative writer/occurrence contracts; permitted cross-tenant deduplication and side-channel mitigations; snapshot isolation and watermarks across services; minimum granularity per source; human-review thresholds; acceptable deletion and access-revocation service objectives; and proof that downstream consumers actually honor revocation. These need explicit owners before implementation, not assumed answers.

## Local Atlas design dependencies and limits

These are design records, not evidence of runtime implementation or deployment:

- [Offset matching](../../2026-11-08T10-26-00Z_design_atlas_offset_matching/2026-11-08T10-26-00Z_design_atlas_offset_matching.md#L27) compares an immediate predecessor with 64-byte rolling-hash windows, verifies copy bytes, and requires a gapless, nonoverlapping copy/literal stream. Whole embedded spans may be reused; partial spans require re-embedding unless already a whole embedded span. Span resolution depends on #6035. This optimization is not a cross-source identity oracle.
- [Content versioning and retention](../../2026-11-08T10-26-00Z_design_atlas_content_versioning_retention/2026-11-08T10-26-00Z_design_atlas_content_versioning_retention.md#L38) uses stable `file_id`, immutable `(file_id, version_seq)` versions, paths as version attributes, and occurrences tying shared chunks to version spans. A chunk is deletable only after its final occurrence is gone. Retirement requires a trigger and class permission; a report is not deletion. Cross-source resolution must not override these local ownership boundaries.
- [Deletion propagation](../../2026-11-09T00-42-59Z_design_atlas_deletion_propagation.md#L63) removes a first absence from default serving before confirmation, distinguishes rights-driven purge from retention, and calls for all-version text, vectors and derived indexes to be purged with a content-free tombstone; backup replay must not resurrect purged material. Reappearance is fresh lineage. Apply these rules to any new lineage projection and curation artifacts as well.
- [Ingest attestation](../../2026-11-09T05-12-32Z_design_atlas_ingest_attestation/2026-11-09T05-12-32Z_design_atlas_ingest_attestation.md#L58) describes one sealed, in-toto-shaped statement per gate run binding chunk hashes and occurrence spans to source hashes and marks, including published, rejected and quarantined batches. Its registry and archived statement are lookup mechanisms; signing or adopting a SLSA predicate is not assumed. Audit retention must still respect deletion rules.
- [Scaler revision](../../2026-11-04T21-27-34Z_design_atlas_scaler_revision/2026-11-04T21-27-34Z_design_atlas_scaler_revision.md#L220) assigns parallel work to separate staging units and the aggregator sole core-writer responsibility for bounded promotions; [manifest filter surface](../../2026-11-05T13-03-49Z_design_atlas_manifest_filter_surface/2026-11-05T13-03-49Z_design_atlas_manifest_filter_surface.md#L89) assigns manifest writes to classification/publish. A curator or matcher proposes changes through the owning authority rather than becoming an additional core writer by assumption.
