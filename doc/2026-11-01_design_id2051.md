# Design: ID chat v1

- Date: 2026-11-01
- Status: **decision-ready design** — no implementation is included in this PR.
- Issue: [#2051 — ID chat v1](https://github.com/developing-today/code/issues/2051)
- Inputs: [IRC-first chat investigation #2049](2026-10-30T19-40-00Z_investigation_irc_first_chat_on_id/2026-10-30T19-40-00Z_investigation_irc_first_chat_on_id.md)
  and [graph-object retrieval investigation #2050](2026-10-30T19-28-00Z_investigation_bittorrent_chunk_retrieval_for_graph_objects/2026-10-30T19-28-00Z_investigation_bittorrent_chunk_retrieval_for_graph_objects.md).

## The decision

Build the smallest IRC-shaped channel layer outside game worlds. Reuse ID's signed event chains, group membership and encryption, blob addressing, and existing transports. Do not add a global nickname/channel directory, a new trust system, or Discord-shaped features to v1.

**Recommended v1:** a channel is a group ID with a local-only name; each settled message is a causally ordered signed event, authored by an account or authorized device key and projected to the account, whose private payload is encrypted and stored separately by content hash; group membership controls read/write; real-time delivery extends the existing envelope handler without adding an ALPN; presence is a separate, TTL-based gossip signal and is never journaled. A DM is a two-account friendship group with encryption enabled. Graph links are references, not embedded bytes.

The signed-event choice follows the newer #2049 synthesis input: ordinary channel chat settles per-channel, while presence does not. The #2058 bridge decision further says that unsigned live traffic is not synced or replayed. The older retention investigation's “durable by default for IRC-style channels; bounded for high-chatter channels” is retained as a policy alternative, not silently treated as the latest settlement decision. The remaining durability/retention choice is called out for Drew in §8.

## The shape

```text
local channel name ─► group ID + signed membership/policy
                           │
client ─► chat module ─────┼─► signed event header (author, seq, backlink, after)
                           │       └─ group-encrypted message payload, stored by hash
                           │
                           ├─ live: ChatFrame over existing /id-envelope/1, per member
                           ├─ history: group-scoped event sync + authorized payload fetch
                           ├─ links: blob/event references ─► existing resolver (holder-set shaped)
                           └─ presence: separate per-channel gossip, short TTL, never stored
```

The module boundary is deliberately below the client UI: callers use channel/message/history/topic/roster operations; the module owns signing, ordering, authorization, encryption, payload storage, and transport selection. The existing `/id-envelope/1` transport and `/id-range-sync/1` event sync are adapters, not protocol authorities.

## 1. Context from the issue and current code

### What already exists

- **World chat is real, but world-scoped.** `WorldEventKind::Chat` is a sanitized, world-authorized journal event ([`world/mod.rs:315-355`](../pkgs/id/src/world/mod.rs#L315-L355), [`world/core.rs:976-1007`](../pkgs/id/src/world/core.rs#L976-L1007)). Its current limits are 2,048 UTF-8 bytes, 50 messages per 10 seconds, and 1,024 recent events for reconnect catch-up ([`world/mod.rs:53-67,87-100`](../pkgs/id/src/world/mod.rs#L53-L100)). It does not provide channels outside worlds or graph-wide chat history.
- **World presence must not be reused for channel liveness.** The world actor turns join/leave transitions into program events ([`world/actor.rs:804-855`](../pkgs/id/src/world/actor.rs#L804-L855)); accepted system events are journaled ([`world/actor.rs:401-439`](../pkgs/id/src/world/actor.rs#L401-L439)) and replayed on restore ([`world/core.rs:310-332`](../pkgs/id/src/world/core.rs#L310-L332)). The new channel heartbeat therefore needs a separate, ephemeral path.
- **The event store already provides the right ordering/integrity substrate.** `ChainExt` has `kind`, optional `group`, and causal `after`; the signed header supplies author sequence and backlink ([`chain.rs:4-16,93-117`](../pkgs/id/src/chain.rs#L4-L16), [`chain.rs:259-307`](../pkgs/id/src/chain.rs#L259-L307)). Ingest is idempotent, verifies signatures, holds missing dependencies, and records forks; applied state depends on the event set, not arrival order ([`event_store/ingest.rs:5-35`](../pkgs/id/src/event_store/ingest.rs#L5-L35)).
- **Groups are the roster and policy seam.** A group has account-key members, roles and policy; friendship is already a canonical two-member group ([`groups/mod.rs:1-14,58-75`](../pkgs/id/src/groups/mod.rs#L1-L14), [`groups/friendship.rs:1-6,12-43`](../pkgs/id/src/groups/friendship.rs#L1-L6)). Petnames are local, never replicated or sent ([`petname.rs:1-6`](../pkgs/id/src/petname.rs#L1-L6)).
- **Identity has an account/device distinction.** Group membership uses account keys ([`groups/mod.rs:58-59`](../pkgs/id/src/groups/mod.rs#L58-L59)); presence/discovery identifies an Iroh `EndpointId` ([`discovery.rs:324-365`](../pkgs/id/src/discovery.rs#L324-L365)); invites bind an account key, group, role and endpoint ticket ([`invites/event.rs:32-45`](../pkgs/id/src/invites/event.rs#L32-L45)). Device grants are separate from group membership ([`groups/fold.rs:180-221`](../pkgs/id/src/groups/fold.rs#L180-L221)). Existing local graph writes are signed with the node's key ([`local_events.rs:1-12`](../pkgs/id/src/local_events.rs#L1-L12)). The design must not silently treat an endpoint as an account.
- **Current envelope transport is only friend-envelope delivery.** `/id-envelope/1` carries one JSON frame and returns `Applied`, `Duplicate`, `Refused` or `Retry` ([`envelope_net.rs:1-7,27-51`](../pkgs/id/src/envelope_net.rs#L1-L7)); its current application payload is friend request/accept ([`directory.rs:290-329`](../pkgs/id/src/directory.rs#L290-L329)). `id serve` already registers the envelope and gossip ALPNs ([`commands/serve.rs:971-1005`](../pkgs/id/src/commands/serve.rs#L971-L1005)), but chat dispatch is new work. Reusing the ALPN means extending its tagged frame handler, not pretending it already accepts arbitrary chat frames.
- **The graph event store does not store general event bodies.** `chain::sign` commits a body hash/size into a signed header, but the body is not in the event bytes ([`chain.rs:271-307`](../pkgs/id/src/chain.rs#L271-L307)); the store keeps verified event bytes/headers ([`event_store/mod.rs:1-20`](../pkgs/id/src/event_store/mod.rs#L1-L20)). Local document events sync through `/id-range-sync/1` ([`local_events.rs:1-12`](../pkgs/id/src/local_events.rs#L1-L12)). Chat must explicitly persist and replicate its encrypted payload; signing a body hash alone is not enough.
- **Both confidentiality and sync scope need deliberate wiring.** The group-encryption adapter can encrypt application payloads, but it is one device's in-memory session for one group ([`encryption/scheme.rs:234-279,476-518`](../pkgs/id/src/encryption/scheme.rs#L234-L279)); it is not wired to signed chat events or durable message payloads. Friendship policy defaults to no encryption scheme ([`groups/policy.rs:132-147`](../pkgs/id/src/groups/policy.rs#L132-L147)). Meanwhile event sync currently opens the whole store to any peer and has no group/topic subset ([`event_sync.rs:14-25,70-100`](../pkgs/id/src/event_sync.rs#L14-L25), [`event_store/sync.rs:298-303`](../pkgs/id/src/event_store/sync.rs#L298-L303), [`pull_policy.rs:1-19`](../pkgs/id/src/pull_policy.rs#L1-L19)). Private chat cannot be implemented by putting plaintext in that store and relying on group membership alone.
- **Links already have a content-addressed precedent.** `DocumentRef` names a BLAKE3 content hash, size and media type ([`documents.rs:40-50`](../pkgs/id/src/documents.rs#L40-L50)). The blob gate describes membership-based serving but its reference index has no producer and is not wired into `id serve` ([`blob_gate.rs:1-21`](../pkgs/id/src/blob_gate.rs#L1-L21)). The #2050 investigation says chat v1 need not wait for multi-provider swarming, but its retrieval interface must accept a holder set even if v1 passes one holder ([#2050 hand-off, §9](2026-10-30T19-28-00Z_investigation_bittorrent_chunk_retrieval_for_graph_objects/2026-10-30T19-28-00Z_investigation_bittorrent_chunk_retrieval_for_graph_objects.md#L330-L342)).

### Newest recorded decisions and current gaps

- #2049's October 30 proposal says channel text settles, presence never settles, and history is catch-up rather than a hosted bouncer ([§2.2, §2.4, §2.5](2026-10-30T19-40-00Z_investigation_irc_first_chat_on_id/2026-10-30T19-40-00Z_investigation_irc_first_chat_on_id.md#L134-L208)). #2058 says ephemeral traffic is not journaled/synced/replayed and bridges cannot assign order or trust ([§3, §7](2026-10-29T11-27-00Z_investigation_bridge_semantics_hosted_native/2026-10-29T11-27-00Z_investigation_bridge_semantics_hosted_native.md#L128-L154), [§7](2026-10-29T11-27-00Z_investigation_bridge_semantics_hosted_native/2026-10-29T11-27-00Z_investigation_bridge_semantics_hosted_native.md#L240-L249)).
- The latest transport follow-ups are still **open PoCs**, not shipped behavior: #2808 asks for two nodes exchanging channel frames over `/id-envelope/1` with no new ALPN; #2809 asks for TTL-based presence over gossip, stale detection and no journal/sync/replay ([#2808](https://github.com/developing-today/code/issues/2808), [#2809](https://github.com/developing-today/code/issues/2809)). Review/sign-off remains a gate before permanent transport code.
- The October 29 retention investigation proposed durable IRC-style channels and a bounded mode for high-chatter channels ([§3, §4](2026-10-29T10-45-00Z_investigation_ephemeral_live_data_retention/2026-10-29T10-45-00Z_investigation_ephemeral_live_data_retention.md#L63-L75), [§4](2026-10-29T10-45-00Z_investigation_ephemeral_live_data_retention/2026-10-29T10-45-00Z_investigation_ephemeral_live_data_retention.md#L101-L106)). The newer #2049 direction is to settle channel text. This design follows the newer settlement boundary, while making the still-unspecified retention policy an explicit Drew question.

## 2. Recommended decisions

### 2.1 Addressing, identity and membership

- A named channel is backed by a group ID. Names, aliases and display labels are local UI state; do not build a globally unique channel-name service. Creation/join/roles use the existing signed group policy and invite flows. World chat remains as-is under its existing world address.
- Use the group account as the logical chat identity; sign each event with the account key or an authorized device key, then project device authors to their account through the group device-grant mapping. Use `EndpointId`/ticket only to route to an active device and report liveness; render the logical account through its local petname. Existing device grants do not automatically add a device key to the encryption roster, so v1 must either constrain an account to one active chat device or explicitly extend the crypto roster. Do not claim multi-device works by implication. The original phrase “Iroh ID is the nick” remains ambiguous; see Q2.
- A DM is the friendship group's two-member channel, not a second message protocol. Enable group encryption for DMs explicitly; friendship policy currently defaults to no encryption scheme. Group `Write` authorizes sending, `Read` authorizes receiving/decrypting, and `Manage`/`Admin` authorizes membership and topic changes.

### 2.2 Messages, history and ordering

- Represent a chat message as an event in the existing signed chain: `kind = chat.message`, `group = channel ID`, signer/author and per-author sequence/backlink from the header, and `after` as the causal frontier. The existing `id.events.v1` signature commits to the encrypted payload's hash and size. Do not add duplicate `author`, `seq`, `after` and `sig` fields to the JSON payload or introduce a second signature format.
- The encrypted payload contains `{v, text, links}`. Store that ciphertext as a separate content-addressed payload and make it available to authorized members; the signed event header commits to its hash. `EventStore` currently does not persist or sync generic body bytes, so payload storage/fetch is an explicit slice, not an assumption.
- Every ordinary channel message settles as a signed event, following the newer #2049 direction. Event order is per-author sequence plus causal `after`; there is **no global total order** and receipt time is not an ordering rule. Clients render a deterministic topological order; an event-ID tie-break among concurrent events is presentation only. A topic is a signed channel event; concurrent authorized topic edits remain concurrent until a later edit causally observes both—never “last packet received wins.”
- The existing event store keeps accepted events; the world chat's 1,024-event reconnect buffer is not a general chat-retention policy. Recommend durable history for ordinary IRC-like channels, with no silent eviction. If high-chatter channels need bounded history, introduce an explicit per-channel retention policy and checkpoint/compaction design first; do not pretend the current event store already prunes.

### 2.3 Private content and event-sync scope

- Encrypt private channel and DM payloads with the existing group-encryption module. Persist enough encryption state to survive restart, define history for late-joining devices, and connect the encrypted payload to the signed event/blob path. Existing encryption session state is in memory, the group scheme is not wired to event storage, and history transport is caller-driven; these are implementation requirements, not solved capabilities.
- Add a group-scoped read path for private chat headers and encrypted payloads before shipping private channels. The present range-sync session serves the whole event store to any connected peer, with no group subset. Extend the event-store sync seam to enforce channel membership (and the blob access seam to authorize payload hashes), or use an equivalent channel-scoped store. Do **not** expose private chat headers or plaintext through the current open sync path. Public channels may opt into public visibility.
- Even with group-scoped sync, authorized members can retain copies after removal; membership removal cannot revoke history already read. State that limitation in the UI/protocol rather than implying recall.

### 2.4 Delivery

- Use the existing envelope ALPN and one tagged `ChatFrame` per message, fanned out to the channel's current members. Preserve the existing `Applied`/`Duplicate`/`Refused`/`Retry` contract. Add a new chat frame type/dispatch path; do not change the semantics of friend request/accept payloads and do not add a chat ALPN in v1. The transport carries bytes; the signed event, not the Iroh node or relay, establishes author trust.
- Catch-up uses the signed event set and encrypted payload retrieval, not delivery receipts and not a server-owned chat transcript. A duplicate delivery is harmless; missing causal parents wait and are fetched through normal sync.
- The hosted edition can add a WebSocket delivery adapter later. Per #2058, a hosted Durable Object is passive/always-reachable and can fan out ephemeral traffic internally, but it must not assign event ordering or trust. Hosted v1 is not on the native IRC critical path.

### 2.5 Presence and roster

- Keep channel liveness out of the world journal and event store. Publish only live information—account/device identity, the channel being advertised and status—on a per-channel gossip topic; expire locally after 90 seconds without a heartbeat, with stale treated as gone and no required leave message. Typing, if enabled, uses the same path with a shorter TTL. This adopts #2809's 60–90 second range and makes the channel identity implicit in the topic rather than broadcasting a global channel list.
- Presence is advisory, not membership or authorization. The roster is the signed group-member fold annotated with currently live endpoints. Validate account/device association and membership on receipt; do not reinterpret the existing peer-discovery `PeerAnnouncement` as chat presence.
- Never sync, journal or replay channel presence or typing. This is intentionally different from world-session presence, which currently is journaled and restored.

### 2.6 Graph links

- Message links are references `{kind, hash, author, hint?}`. V1 allows `blob` and `event`; a game result is an event rendered by the client, not a new link kind. The message's signed/encrypted content authenticates the reference; the referenced content hash verifies the bytes. The hint is best-effort routing metadata, not a capability.
- Resolve local first, then author/hint, then known holders through a provider-set-shaped retrieval call. V1 may pass one known holder; do not bake single-source retrieval into the interface and do not make the #2050 swarm scheduler a v1 prerequisite. Fetches still obey channel/world access policy; a link does not grant access.

## 3. Viable options and trade-offs

| Option | Benefits | Costs / reason not to choose |
| --- | --- | --- |
| **Reuse world journal for every channel** | Existing sanitization, rate limits, snapshots and reconnect history. | The journal is a world-authoritative game session, with bounded catch-up and replayed system presence; it is not an independent peer/group chat store. It would make IRC channels depend on a world host. |
| **Ephemeral envelope/gossip messages; save only selected messages** | Smallest implementation and least durable data. | No normal channel history/catch-up; users lose messages when peers are offline. It conflicts with #2049's newer recommendation that channel text settles. |
| **Signed event headers + encrypted content-addressed payloads, with group-scoped sync** (**recommended**) | Reuses author chains, fork proofs, causal frontiers and event sync; group crypto protects content; group policy supplies roster and roles; links fit ID's hash model. | Requires durable ciphertext payload storage/fetch, group-scoped sync/access checks, encryption-state persistence and account/device integration. Those are real slices, not already-wired code. |
| **A new independent channel journal/protocol** | Can make membership, privacy and retention channel-native from day one. | Duplicates chain/fork/catch-up behavior already provided by the event store, creates a second history model and risks a new ALPN despite #2808's no-new-ALPN direction. Keep only as a fallback if the existing sync seam cannot support scoped chat safely. |

For live delivery, **extend the tagged frame dispatcher on `/id-envelope/1`** rather than add a chat ALPN or send durable messages as gossip. This matches the latest PoC hand-off while keeping messages signed and replayable. For presence, use separate gossip topics rather than world-session presence. For channel names, use local aliases rather than a global registry.

## 4. Invariants and acceptance criteria for implementation

1. Existing world chat wire/journal behavior is unchanged; group chat does not require a game world.
2. Every settled message and topic update has a valid signed chain header with channel group, per-author sequence/backlink and causal frontier. Duplicate, reordered and late delivery converge to the same applied event set; forks are surfaced by existing proof semantics. Wall-clock arrival is never a conflict rule.
3. Private message bodies and link lists are encrypted before persistence or transmission. A non-member cannot obtain private event headers or encrypted payload through sync/blob serving. Public-channel visibility is explicit. An already-authorized member may keep prior copies after removal.
4. The encrypted payload survives restart, can be fetched by its signed content hash, and can be decrypted by an authorized member after reconnect. Tests cover a late-joining device under the selected history policy and a removed member receiving no new content.
5. Realtime delivery uses `/id-envelope/1` with a new tagged chat frame; existing friend envelopes retain their current behavior. A two-node round trip verifies Applied/Duplicate handling and retries without changing message identity.
6. Text retains the world-chat baseline unless a measured limit says otherwise: sanitize control characters, max 2,048 UTF-8 bytes, 50 messages per sender per rolling 10 seconds ([`world/mod.rs:53-55`](../pkgs/id/src/world/mod.rs#L53-L55), [`world/core.rs:976-1007`](../pkgs/id/src/world/core.rs#L976-L1007)). Links are structured fields, not raw markup or inline payloads.
7. Topic updates are group-authorized, signed events. Concurrent updates converge without arrival-time last-writer-wins; clients display the conflict until a causal resolution event.
8. Presence and typing have bounded TTLs, are absent from the event store and world journal, and recover correctly across a simulated netsplit/stop-resume. A roster distinguishes group membership from live endpoints.
9. A link resolves from local storage or a permitted holder; its call interface accepts a holder set. Missing content is reported as unavailable, not as a signature/hash failure.
10. Petnames and display aliases never go on the wire; account/device IDs do. Transport nodes and hosted bridges confer no signing authority.

## 6. Explicit non-goals

- Discord/Slack/Teams feature parity; threads, durable reactions, servers/guild directories, bots or hosted bouncers.
- A global nick or channel-name registry, mandatory registration, or a new trust root.
- New chat ALPN, a central chat server, global content-discovery DHT, or a new swarm scheduler.
- Replacing world chat or changing world-session presence semantics.
- Silent expiration or revocation of already-delivered chat history.

## 7. Risks to keep visible

- **Open sync is a real privacy blocker, not a policy flag already in use.** `PullPolicy::Members` is a documented world-scoped idea, but `id serve` currently opens whole-store event sync ([`pull_policy.rs:1-19`](../pkgs/id/src/pull_policy.rs#L1-L19), [`event_sync.rs:14-25,70-100`](../pkgs/id/src/event_sync.rs#L14-L25)). Private chat must wait for group-scoped sync or an equivalent isolated store.
- **Encryption is not persistence.** `Session` currently keeps held envelopes/session state in memory and has no production chat writer; group encryption alone does not make history survive restart or sync to members. Existing friendship groups also have no encryption scheme by default.
- **Membership does not equal device authorization.** Group and encryption rosters are account-key based; gossip presence is endpoint based. Multi-device support needs a deliberate account-to-device adapter, not a node-ID cast.
- **Retention is a user promise.** Current event-store accepted rows persist; world chat's 1,024-event ring is only reconnect history. Do not advertise bounded or erasable chat until a retention/checkpoint design exists.
- **Iroh blob access for chat is not wired.** The current blob gate's reference-index producer is missing; chat links and encrypted payload blobs need authorized serving before private media is enabled.

## 8. Questions for Drew

These do not block this design record; the recommendation is the v1 default until Drew chooses otherwise.

1. **History durability:** Should every ordinary channel message be signed and synced as durable history, or should v1 settle only explicit saves/quotes (with a bounded recent-history mode such as the older 90-day proposal for high-chatter channels)? **Recommend:** settle every ordinary IRC-style message and make it durable by default; do not silently evict. Add bounded per-channel retention only with an explicit policy/checkpoint mechanism. This follows #2049's newer “chat text settles” direction and avoids presenting ephemeral delivery as IRC history.
2. **What is “Iroh ID” as a chat identity?** Options: account key (one logical identity with one or more authorized signing devices) or each EndpointId/node as a separate nick (closest to a literal node-ID nick, but one person appears as multiple members across devices). **Recommend:** account key is the roster/display identity; an event is signed by its authorized account/device key and EndpointId is only a route/liveness handle. Multi-device support needs the explicit account-to-device and crypto-roster adapter in §2.1; until then v1 documents a one-active-device limit per account.
3. **DM scope:** Options: encrypted two-account friendship channel with group roster/history, or transient one-to-one envelopes with no shared channel history. **Recommend:** the friendship channel, encrypted, using the same message/event model as a group channel. If the intended v1 is deliberately history-free DMs, that should be an explicit product choice rather than an accidental transport limitation.
4. **Private-channel metadata:** The current event-sync path exposes headers (including author, group and causal structure) to any connected sync peer even if message bodies are encrypted. Options: make private chat sync group-scoped before shipping, or accept this header metadata as visible to all event-sync peers. **Recommend:** group-scoped sync for private channels and DMs; public channels may be explicitly public. This is a real prerequisite, not a promise the current open sync path already provides.
