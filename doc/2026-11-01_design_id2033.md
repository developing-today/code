# Design: abuse-control primitives v1 for ID comms

- **Date:** 2026-11-01
- **Status:** decision-ready design; implementation has not started
- **Issue:** [#2033](https://github.com/developing-today/code/issues/2033), under epic #2056
- **Evidence snapshot:** checkout `design/id-2033` at `a9e976ac245d94682ff7ada8dd5562cc58c9b00f`
- **Inputs:** #2032 investigation (merged as [PR #2243](https://github.com/developing-today/code/pull/2243)); #2030 trust/visibility decision (merged as [PR #2801](https://github.com/developing-today/code/pull/2801))

## Decision to make

Choose a small, implementable set of local policy primitives for ID's mixed comms paths: how a node identifies a counterparty, blocks or mutes it, accounts for resource use, returns a useful refusal, and keeps those controls separate from the signed-object trust model. The issue asks for block/limit/budget objects, enforcement at client/relay/server, composition with accept-all-signed-object behavior, and the operator's quick button.

## Recommendation

Build one **node-local abuse-policy module** with typed subjects and shared accounting, then call it through thin protocol adapters at the earliest point each path has the facts it needs. Keep policy separate from signed graph data and from event validity:

1. Count transport frames and bytes against both a connection and the remote Iroh `EndpointId`; enforce before frame-body allocation/decode where the shared frame codec is used.
2. After signature verification, optionally account content/storage against the distinct event `AuthorKey`. Do not infer an account or author key from an endpoint key.
3. Treat `Block endpoint` as a node-local transport/serving decision, and `Mute author` as a local view decision. Neither changes whether a signed event is valid or what another node stores.
4. Keep persisted operator rules/configuration separate from ephemeral counters. Persist blocks in a node-local control table; put numeric defaults and overrides in a wired `[abuse]` section of `id-server-config.toml`. Rate buckets and live counters are in-memory abuse controls, not billing records; restarting the process resets them, while persisted rules remain.
5. Use one structured refusal contract across adapters. Include a bounded retry duration for temporary rate/budget refusals; permanent blocks have no retry duration. Map HTTP refusals to `429` and `Retry-After`; use the protocol's refusal frame where it has one, otherwise a stable application close code.

This is the smallest useful composition: a common decision and accounting model without pretending that QUIC, HTTP/WebSocket, content-author identity, and direct IP are the same seam or identity.

## Primitive shapes and semantics

These are conceptual interfaces, not a commitment to these Rust names.

### Typed local rules

| Subject kind | v1 meaning | Enforcement |
| --- | --- | --- |
| `EndpointId` | **Block endpoint**: stop new sessions to/from this endpoint, close its current sessions, stop serving it, and remove its local subscriptions. The peer-list quick action creates this rule. | Iroh accept/dial and serve/subscription adapters. |
| `AuthorKey` | **Mute author**: hide that author's objects from the operator's local default views. It does not erase, reject, or stop replicating valid signed events. | Local view/projection only. |
| Account key/ID | Mute that account's attributed content in account-aware views. Do not infer an account from the endpoint that delivered an artifact; endpoint hosting and account identity are separate ([`artifact.rs:147-163`](https://github.com/developing-today/code/blob/a9e976ac245d94682ff7ada8dd5562cc58c9b00f/pkgs/id/src/artifact.rs#L147-L163)). | Account-aware local view only, where the account attribution is verified. |
| Authenticated `identity_client_id` | Mute or rate-limit that WebSocket identity; it is not an Iroh endpoint or an account key. | Collab/WebSocket adapter only. |
| Direct `IpAddr`/CIDR | Deny at the listener for a directly observed address only. Never infer a relayed peer's address. | Listener/host firewall adapter; defer to the later phase. |
| Gossip `TopicId` | Stop local subscribe/pull/serve for that exact gossip topic. | Gossip subscription/serving adapter; defer to the later phase. |
| Metadata tag | A separate typed rule from gossip topic; suppress or avoid pulling matching metadata only where a tag-aware policy path exists. | Tag/view or pull adapter; defer until its semantics are specified and tested. |

Each persisted rule is node-local and carries `{subject_kind, value, created_at, reason, expires_at}`; `expires_at = null` means permanent. Rules are not signed graph objects and are not federated. An endpoint ID, author key, account key/ID, web-client ID, IP, gossip topic, and metadata tag are not aliases. The #2243 review specifically distinguishes endpoint denies from account/author rendering blocks ([review finding](https://github.com/developing-today/code/pull/2243#discussion_r4411443930)). If a peer row exposes multiple identities, “Block endpoint” and “Mute author/account” remain separate, explicit actions. A peer without an established author/account identity can still be blocked by endpoint.

For v1, use a per-node operator control table for live block/mute rules, and a wired `[abuse]` table in `id-server-config.toml` for numeric defaults and explicit budget overrides. The config's current parse/load support is not enough by itself; `id serve` must consume it. Keep counters in memory and label them as runtime enforcement/diagnostic counters, not durable billing or audit totals. On restart, counters reset; persisted operator rules and configured limits do not.

### Shared accounting and limits

One `AbusePolicy` evaluator owns token buckets, rolling process-epoch byte/frame budgets, concurrent-session counts, and per-subject overrides. Adapters supply typed subjects and direction (`inbound`/`outbound`); they do not each invent their own counter map. Share the endpoint bucket across a peer's connections so opening more streams does not multiply its allowance. Use an additional connection bucket for fairness. The HTTP/WebSocket adapter uses the authenticated `identity_client_id` when present, otherwise a per-socket pre-auth bucket and a directly observed client IP only when the listener exposes it; it never calls that subject an Iroh endpoint or trusts an arbitrary forwarded-IP header.

“Pre-authorization” ends only when that protocol's own authentication/authorization succeeds; an allow-list for write operations does not authorize unrelated reads or sessions ([`access.rs:1-17,46-80`](https://github.com/developing-today/code/blob/a9e976ac245d94682ff7ada8dd5562cc58c9b00f/pkgs/id/src/access.rs#L1-L17)). Every ID node applies its own policy on work it initiates and work it accepts/serves: the dialer charges outbound bytes, the receiver charges inbound bytes before parsing, and a relay charges only the traffic it handles. The browser is a configuration/diagnostic client, not a trusted enforcement point. A relay does not get the original peer's IP from this design.

Start with the defaults proposed by #2032 / the already-filed implementation issues; make each configurable and observable:

| Control | Initial default |
| --- | --- |
| Authorized endpoint frame rate | 60 frames/s, burst 180 |
| Pre-authorization frame rate | 10 frames/s, burst 30 |
| Authorized endpoint bytes | 512 KiB/s, burst 4 MiB |
| Concurrent connections per endpoint | 4 |
| App-wide inbound/outbound budgets | 32 MiB/s + 20 GiB/hour inbound; 64 MiB/s + 40 GiB/hour outbound |
| Endpoint byte budget | 100 MiB/hour, with 8 MiB/minute burst |
| Direct-IP byte budget | 250 MiB/hour, only when the direct address is observable; later phase |
| Specific-counterparty override | Typed subject plus max bytes and max messages/frames per window; no override unless configured |

The limits are starting safety defaults from the investigation, not billing promises. A message/frame is counted at the adapter's named layer; do not compare a WebSocket message count with an event count without an explicit conversion. The collab adapter uses the common evaluator and the investigation's 120 messages/s, burst 360 proposal, subject to the existing Axum message ceiling. Rate and budget refusals report a bounded retry duration (1 s floor, 60 s ceiling, as proposed in #2032). A specific override is checked before its general endpoint/IP budget, then both the applicable override and aggregate limits are charged; an override can be stricter but cannot raise the node-wide ceiling.

### Refusal contract

Use one typed result with:

```text
reason: rate_limited | budget_exhausted | blocked_by_operator | unauthorized
retry_after_ms: optional positive duration
```

`retry_after_ms` is present for temporary rate/budget refusals and absent for permanent operator blocks or authorization failures. HTTP adapters map temporary refusal to `429` plus `Retry-After`; existing HTTP 429 sites adopt this mapping. Protocols that can return an ID refusal frame do so before ending the request; otherwise close only the affected request stream with a stable application code. Do not close an entire peer connection for one ordinary rate-limit hit. A permanent endpoint block closes that endpoint's sessions. The refusal reason describes a work/serving decision, not whether a signed object is valid.

The direct-IP and external-list limits are deliberate: #2032 notes that relay paths do not expose the original peer IP and recommends against shipping unreviewed “common” block lists because those lists age quickly and relayed peers evade them ([#2032 investigation, §3–4](https://github.com/developing-today/code/blob/0c10ee8878051cfbe63f5ac0ccf7f6cbc74e7847/doc/2026-10-29T10-55-00Z_investigation_comms_abuse_controls/2026-10-29T10-55-00Z_investigation_comms_abuse_controls.md#L178-L255)).

## Composition with trust and serving policy

The newest recorded trust decision is #2030's merged PR #2801: **validity at ingest → stored evidence → per-view writer-set projection**. It supersedes the preliminary #2030 investigation wherever that first version overclaimed; its final correction specifically says per-author grouping does not solve a multi-key Sybil flood. The current `ingest.rs` still shows why the phrase “accept all signed objects” must be scoped: malformed, frozen, and over-cap events can be refused, while some events are stored but voided. The abuse layer must not add a new author-authority rejection at receipt.

| Action | May stop work/serving? | May change store validity/application? | May change this node's view? |
| --- | --- | --- | --- |
| Endpoint block | Yes: session, subscription, or serving | No | Only as a consequence of no new traffic; not an author judgment |
| Author mute | No network denial | No | Yes, local projection only |
| Rate/budget limit | Yes: refuse a request or defer work | No; it is not an invalid-object verdict | No authority effect |
| IP/topic/tag rule | Yes, at its typed listener/subscription/view seam | No | Only the defined local projection/serving result |
| Signature/canonical/chain verification | Refuses malformed or invalid input | Yes, per existing ingest rules | Derived from store state and writer-set view |

Resource policy is allowed to say “not now,” “no budget,” or “this node will not serve this peer.” It must not say that an otherwise valid signed object is invalid, and a local mute/block must not rewrite the object graph or another node's projection. Existing pull/session resource checks remain independent; in particular, retain the current 64 MiB reconciliation session budget and reuse the already-enforced `PullGate` rather than adding parallel checks.

## Viable options and trade-offs

1. **Keep per-feature limiters and add one-offs.** Lowest initial migration cost, and preserves local semantics such as world chat's participant cap. Rejected as the overall design: it cannot express a shared endpoint budget, cross-connection fairness, consistent retry information, or the counterparty overrides in #2032. Preserve semantic feature caps, but make the common evaluator their shared resource accounting seam.
2. **Put all protection in HTTP/reverse-proxy middleware.** Good for web routes and listener IP controls, and can standardize HTTP 429. Rejected as the primary design because `id serve` registers Iroh/QUIC protocols outside HTTP; it cannot police frame sync, blobs, gossip, or world traffic.
3. **One shared local policy evaluator with protocol adapters (recommended).** Gives one typed rule/counter model and observable refusal semantics while preserving protocol-specific seams. Costs an initial adapter migration and careful distinction between endpoint, author, account, and direct-IP identities. This is the best leverage/locality trade: rate/budget behavior is implemented once; callers only supply facts available at their seam.
4. **Replicate block lists or reject blocked authors during ingest.** Appears to make moderation uniform. Rejected: nodes need local operator choices, external lists age quickly and can be evaded through relays ([#2032 investigation, §4](https://github.com/developing-today/code/blob/0c10ee8878051cfbe63f5ac0ccf7f6cbc74e7847/doc/2026-10-29T10-55-00Z_investigation_comms_abuse_controls/2026-10-29T10-55-00Z_investigation_comms_abuse_controls.md#L245-L255)), and ingest-time authority filtering conflicts with #2030's per-view writer-set model and destroys/rejects evidence rather than suppressing its local effect.

## Invariants and implementation acceptance criteria

- Every rule and counter names its subject kind. Endpoint identity is not silently treated as author/account/web identity; changing an endpoint key cannot erase a content/account counter when that identity is independently known.
- Endpoint buckets are shared across that endpoint's concurrent sessions; per-connection limits do not multiply the endpoint-wide allowance. Node-wide budgets remain effective even if peers rotate keys.
- A frame is charged before body allocation/decode where the shared frame seam applies; the existing 1 MiB hard frame cap is retained. No second event-sync session cap is introduced.
- Existing semantic caps (waiting-per-author, pending friend requests, world chat) keep their semantics and produce a structured refusal where their caller can expose one; their counts are not mislabeled as transport frames.
- A rate/budget refusal has a machine-readable reason and a bounded, positive retry duration. HTTP 429 responses include `Retry-After`. The affected request/stream is shed without unnecessarily closing unrelated peer sessions.
- The one-click peer-row action persists an endpoint block, closes/denies that peer's sessions, and makes the block visible/removable from the operator's block list. “Mute author” remains a distinct action.
- Given the same valid signed events, enabling a local author mute does not change which events the store accepts, stores, or marks voided; it changes only the local projection. Tests also prove another unblocked source can still provide the same valid event.
- Direct-IP rules are tested only for directly observed addresses; a relayed connection never inherits an asserted client IP in v1.
- Budgets and block rules are active in production only after `id serve` loads their config/store. Tests cover config parse, defaults, restart semantics, and live rule updates.
- Counters are visible at least through the operator status surface or logs with subject kind, direction, usage, and refusal reason. Do not claim that an unobservable limit is tunable.

## Questions for Drew

**None.** The design resolves the open implementation choices with scoped defaults: endpoint key for transport admission, author key for local muting/content accounting, node-local rules, frame plus byte accounting, and request-stream refusal without peer-wide disconnect. Relay-attested IPs are deferred rather than silently added because that would introduce a separate privacy decision. Initial numeric limits are the #2032 proposals, configurable and observable; no owner preference is needed to start implementation.
