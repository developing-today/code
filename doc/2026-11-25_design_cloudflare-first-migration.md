# Cloudflare-first migration: PM Stack, queues, and unblocked services to Workers + D1 — design and slice plan

- **Date:** 2026-11-25
- **Status:** design + slicing record for [#14866](https://github.com/developing-today/code/issues/14866). The implementation slices in §8 are filed as child issues of #14866 from this record.
- **Direction (Drewry, 2026-11-24):** move PM Stack, the queues, and anything not completely blocked into Cloudflare directly — Workers + D1 — as an emergency programme, not a when-we-get-to-it migration. Exceptions: the Atlas project, the Outlets project, and anything that needs direct access and cannot be proxied through a Worker.
- **Companion:** [#14865](https://github.com/developing-today/code/issues/14865) (write-amplification sweep) — see §7. This programme is the structural move; #14865 is the write-shape fix. Neither substitutes for the other.

## 2. The one decision this programme has to state plainly: D1 vs. Turso

#14866's text says "Workers + D1". Two landed designs of record place PM data elsewhere, deliberately:

- **#9079** (hosted edition): board-family data lives in the **tenant Turso plane** (#9060 model, #9083); D1 is _rejected there for board data_ — a second SQL plane would be a divergence factory.
- **#14084** (push unification): the push registry and unified sends ledger live in the **fleet-platform Turso** store.
- **#14107** (PM serving migration) builds on both and adds D1 only where it already is: decision events.

This design does **not** silently override those records, and it does not read #14866 as doing so either. The ruling this programme works under:

> **Workers are the compute plane for everything in scope. The SQL plane is per data family, following its owning design: D1 for the queue (this programme, §3), decision events (already), and any new small state with no owning design; Turso remains the record for the board family and the fleet-platform ledgers until a superseding decision is recorded on #9079/#14084 themselves.**

If Drewry intends board data in D1 as well, that is a one-line superseding ruling on #9079 — recorded there, it changes slice CF-4's target schema and nothing else in this plan. Absent that ruling, moving board data to D1 would fork the #9060 model mid-flight and is the one move this programme refuses to make by implication.

Everything else in #14866 is unambiguous and this plan executes it at full scope: the queue's live plane moves to D1, every PM surface gets its hosted home per #14107, and every hand-deployed Worker gets the versions pipeline.

**D1 schema sketches** (the two D1 planes this programme owns; the rest follow their owning designs):

- `fleet-queue` (CF-2): the #6741 schema as `D1QueueStore` speaks it — `tasks` (id, queue, kind, status, worker, lane, priority, dedupe_key, payload, result, created_at, claimed_at, completed_at), `task_events` (append-only claim/complete/checkpoint history), `queue_signals` (per-queue generation + reason). The slice's first step is a parity dump: schema diff of real D1 vs. the store's expectations, filed on the slice issue before any cutover.
- Decision events: unchanged (already D1, in service).
- New small state defaults to D1 with the schema recorded on its slice issue, per #14866's acceptance rule (each slice records what moved, what stayed and why, the D1 schema where D1 is the target, and the deploy/rollback path).

## 4. Deploy path — Cloudflare versions, one standard

The estate's working pattern, generalised (this is CF-1):

1. **Build in GitHub Actions**, with Nix where the Worker already builds that way (the d1-gateway workflow's DeterminateSystems Nix installer + magic-nix-cache shape; the sanctioned `cf` tooling in `pkgs/cf`). Per #14866: the Nix Cloudflare Worker GitHub Action to build/publish where it fits, then a **versions deploy**.
2. **Upload as a new version, never straight to 100%.** `wrangler versions upload` with the version stamped with the full commit SHA (the decision-events pattern: `/health` must report that exact SHA).
3. **Health gate, then promote.** The new version's health endpoint answers and reports the deployed commit == the merge commit → `wrangler versions deploy` promotes it. A failed gate leaves the previous version serving and raises an incident (the pm-console-edge pattern).
4. **Rollback is a versions operation, not a redeploy:** promote the previous version id back (pm-console-edge's `rollback_version` workflow input is the shape every in-scope workflow adopts). Data-plane rollback is separate and per slice: D1 changes ship as forward migrations with a recorded down-path or a point-in-time restore note; route flips (PM surfaces) roll back by route state, per #14107 §5.
5. **`workers.json` stops being a hand-maintained claim:** each adopted Worker's entry gains its last-deployed commit, written by its pipeline.

## 5. Exceptions — named, with reasons

- **Atlas project** — named exception in #14866. Its data plane (Turso/vector tiers, direct database access for search and ingest) is the direct-access class as well; `atlas-search` and its sibling Workers stay on their current deployment under the Atlas programme.
- **Outlets project** — named exception in #14866. No surface for it exists in this repo; there is nothing here to move, and this programme records the exception rather than inventing a target.
- **Direct-access-only components** — anything whose function _is_ local or tailnet access: the secrets broker (UDS + Bitwarden session), the fleet proxy broker, the gh cache daemon, tailscaled itself, and the laptop agent. A Worker cannot hold a UDS socket or a tailnet identity for the machine it runs on; these stay, and the queue broker's _store_ moving (CF-2) does not move them.
- **Beside-product data stores** (Kaneo/Pad/Grist) — not exceptions to the programme, but to its data plane: their _serving_ joins the tunnel tier (CF-8) while their stores follow #6816/#3142, per #14107 §3/§8.

## 6. What does not change

- The writer-of-record lease (#9079 §5): serving tier and write authority stay separate facts in every slice; no fallback or cutover silently moves write authority.
- The #14065 rule: no tier renders invented data to fill a gap; every slice's acceptance includes the fail-visibly check for the surfaces it touches.
- Secrets by name only, from Bitwarden; the account-wide Cloudflare admin token never enters a Worker or a workflow env (§1 of the #14107 record; `doc/living/cloudflare-credential-architecture.md`).
- PM book updates ride in the slices that change serving facts (book-live-update rule), not in this design record.

## 7. Coordination with #14865 (write amplification)

The overlap is real and bounded: #14865 hunts whole-table/whole-object rewrites in the PM Stack, the queues, and the bridge; this programme changes _where_ those writes land. Rules agreed by this record:

- **#14865 owns write shape; #14866 owns placement.** A full-table rewrite found in a component does not get "fixed" here by moving it to D1 — that would migrate the defect. Conversely, #14865 does not block a cutover slice on unrelated findings.
- **Cutover slices inherit a gate:** CF-2 and CF-5 may not cut a component over while a #14865 finding for that component is open and unfixed — the slice checks #14865's record first and either waits for the fix or carries it as the slice's first step, saying which on the slice issue.
- Findings either programme surfaces in the other's territory are filed on the owning issue, not duplicated.

## 8. Slice map and dependency shape

Filed as child issues of #14866. **The graph is deliberately near-flat:** every slice except CF-3, CF-6, CF-7, and CF-12 can start today, in parallel, on separate Workers/services with separate deploy paths. Blocking edges exist only where one slice's output is literally another's input:

- **CF-3** (queue backup/DR retarget) is blocked by **CF-2** — the backup's source changes only when the live plane does.
- **CF-6** (interactive surfaces) is blocked by **CF-4** (front-door route state + edge intake must exist) and **CF-5** (the read surfaces it composes) — mirroring #14107's M6 dependencies.
- **CF-7** (heavy surfaces) is blocked by **CF-5** — the indexed projections are built on the read-wave stores (#14107 M7 on M5).
- **CF-12** (drills + close-out) is blocked by **CF-4, CF-5, CF-6, CF-7, CF-8** — a drill of a tier that does not exist yet proves nothing.
- CF-1 (deploy standard) blocks **nothing**: slices can deploy by hand, as today, until CF-1 lands, and adopt the pipeline when it does. Making the whole programme wait on its own tooling is exactly the straight-line failure #14866 forbids.
- CF-2, CF-4, CF-5, CF-8, CF-9, CF-10, CF-11 are mutually independent: different services, different stores, different deploy units.

## 9. Risks and honest unknowns

- **D1QueueStore is unverified against production-shaped load.** The shadow window in CF-2 is the evidence step; if D1 latency or limits fail the queue's claim rates, CF-2's fallback is to keep Turso as the live plane and record the finding on #14866 — the programme's goal is Cloudflare-first, and a measured exception beats a broken queue.
- **`workers.json` is four days stale by construction** (checked 2026-11-23, hand-kept). CF-1's first step re-verifies every entry live; some "by hand" entries (message-bridge) may already have working workflows.
- **The laptop remains in the loop for writes** until CF-6 and the #14043 applier are live: answers are recorded at the edge and applied when the broker path returns. That is the designed shape (#14107 §5.1), stated here so no slice claims otherwise.
- **Two Cloudflare accounts** exist in the estate; every slice names its account + zone in its deploy record rather than assuming.
