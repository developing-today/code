# Design: Joplin continuous sync — target/plugin bridge against the #5848 baseline

Issue: developing-today/code#9004 (follow-on to #7676; programme #5678)
Date: 2026-11-12 (task 15314)
Status: **design only. The build/no-build decision is explicitly pending**
(Drew's 2026-11-11 ruling, recorded on #9004: design it, decide later).
This record does not choose build/no-build, does not change #5848's v1
scope, and treats #2048 as settled.

## Baselines (not reopened)

- **#5848 (v1 baseline):** one-shot Joplin import via a manifest —
  source-vault identity, a Joplin-ID ↔ ID-note/resource mapping,
  idempotent re-import — plus a designed export path. The importer
  holds **no E2EE keys**. Import is an event in ID's append-only log,
  never a silent overwrite.
- **#2048 (settled):** stable note IDs; concurrent edits produce
  multiple heads; merges are explicit, never last-writer-wins and
  never a silent flattening of heads.
- **#5838 (boundary):** ID is a local-first substrate with tombstones,
  its own E2EE policy, and content-addressed blob sync between ID
  devices. Joplin continuity must compose with that substrate, not
  create a second sync engine inside ID.
- **#5844 (boundary):** attachments/resources are first-class,
  content-addressed, and carry their own read decisions.

## Joplin facts from primary sources (fetched 2026-11-12)

Documented facts (source, date of the fetched revision):

1. **Sync model** — `joplinapp.org/help/dev/spec/sync/` (committed
   2026-02-10): the client uploads local changes, polls/downloads
   remote changes, and propagates deletions. A generic `Synchronizer`
   delegates storage operations to a target-specific `FileApi`
   (`create`/`update`/`delete`/`list`); shared sync settings live in
   the target's `info.json`. The current sync protocol version is 3.
2. **Conflicts** — `joplinapp.org/help/apps/conflict/` (committed
   2026-02-10): when both sides changed an item, Joplin keeps a copy
   in a "Conflicts" notebook and the remote version replaces the
   local one; resolution is a manual merge by the user.
3. **E2EE** — `joplinapp.org/help/apps/sync/e2ee/` (current docs):
   notes, notebooks, tags, and resources can all be end-to-end
   encrypted; a sync target then stores ciphertext.
4. **Plugins** — `joplinapp.org/help/apps/plugins/` (committed
   2026-02-22) and the plugin API reference: plugins run on desktop
   and mobile (iOS: only Joplin-recommended plugins) and program
   against `joplin.data` (CRUD on notes/notebooks/tags/resources),
   `joplin.workspace`, `joplin.interop` (import/export modules),
   commands, settings, views, and content scripts.
5. **Synchronizer source** — `packages/lib/Synchronizer.ts` in
   laurent22/joplin (source commit 2026-11-01): explicit sync lock,
   delta-download context, per-item upload/delete/download, conflict
   handling, E2EE handling, lock-failure and sync-version migration
   handling.

Assumption labelled as such (verification: re-check the plugin API module list at each Joplin release and before any build design; a registration surface appearing there reopens Option 2's shape — see blocker B3): **no primary
source documents a plugin API for registering a new sync-target
type.** The plugin API module list in fact 4 contains no such
surface, and the shipping targets (Joplin Server, WebDAV/Nextcloud,
S3, Dropbox, OneDrive, filesystem) are built into the apps. Every
option below is shaped to need no such API.

## Options

### Option 1 — Baseline: one-shot import + idempotent re-import (no continuous sync)

- **Shape:** #5848 exactly as designed. Re-import is a new manifest
  run; diffs are computed against the recorded Joplin-ID mapping and
  land as new ID events. Export is the designed one-way path.
- **Trust/components:** the importer only; runs where the user runs
  it, with the user's Joplin export/JEX or profile access. No daemon,
  no credentials held by ID, no E2EE keys.
- **State owned:** the import manifest (mapping + per-item source
  hashes) — already the #5848 design.
- **Identity/lifecycle:** Joplin IDs map to ID note IDs at import;
  a changed Joplin note re-imports as a new head/event on the same
  ID note when the mapping says so, a deleted-in-Joplin note is
  reported, not tombstoned silently.
- **Client surfaces:** all (operates on exports/profiles, not on
  client internals).
- **Failure/recovery:** a failed run is resumable and idempotent by
  construction; worst case is a stale import, visibly reported.
- **Source of truth:** ID, after import. Joplin remains an external
  source that is periodically folded in, exactly like today.
- **Cost:** zero protocol maintenance. The cost is staleness and
  manual runs.

### Option 2 — ID-hosted Joplin-compatible sync target

- **Shape:** ID hosts a service that speaks a sync-target protocol
  Joplin already ships — realistically the Joplin Server API or a
  WebDAV-shaped `FileApi` surface (fact 1) — backed by ID storage.
  Joplin clients point at it as their ordinary sync target.
- **Trust/components:** a new always-on network service holding, per
  vault, either plaintext items or E2EE ciphertext. This is the
  largest trust expansion of any option: the service is on the
  attack surface for every synced device, and its availability gates
  every client's sync.
- **State owned:** a full second copy of the vault in sync-target
  layout (items as serialized files + `info.json`), plus the mapping
  between target item IDs and ID note IDs, plus sync locks and delta
  state. Two storage shapes for the same knowledge must be kept
  coherent forever.
- **Identity/lifecycle:** Joplin item IDs become load-bearing inside
  ID permanently. Deletions arrive as target deletes and must be
  translated into ID tombstones (#5838) without losing restore
  semantics.
- **Client surfaces:** all desktop/mobile clients that support the
  chosen target protocol.
- **Failure/recovery:** target downtime blocks sync fleet-wide for
  that vault; a corrupt target state risks propagating deletes —
  backups of the target store and a read-only freeze switch are
  required, not optional.
- **Source of truth:** **ambiguous by construction** — Joplin treats
  the target as its truth while ID treats its log as truth. Every
  conflict case in the conflict section below is sharpened by this option.
- **Feasibility note:** possible without any plugin API (it uses a
  built-in protocol), but it is a re-implementation of a moving
  protocol (sync version 3 today) against an oracle that is Joplin's
  own server.

### Option 3 — Joplin-side plugin bridge

- **Shape:** a Joplin plugin (fact 4) watches `joplin.data` changes
  and exchanges them with ID over a local/IPC or HTTP interface;
  ID-side changes are written back through the same data API.
- **Trust/components:** the plugin runs inside every Joplin client
  that installs it, with that client's full data access (including,
  on an unlocked client, decrypted content). ID exposes a small
  bridge endpoint the plugin authenticates to.
- **State owned:** per-client bridge cursor + the #5848 mapping.
  Cursors are per-device, so N clients means N cursors to reconcile.
- **Identity/lifecycle:** mapping as in Option 1, extended with
  per-item version provenance (which side, which device, which
  bridge epoch) so echoes (a change the bridge itself wrote being
  read back as a new change) can be suppressed.
- **Client surfaces:** desktop full; mobile partial; **iOS excludes
  non-recommended plugins** (fact 4), so an iOS Joplin user gets no
  bridge — a coverage hole that must be stated, not smoothed over.
- **Failure/recovery:** a client that is offline or has the plugin
  disabled silently diverges until it next runs; recovery is a
  manifest re-baseline (Option 1) per client.
- **Source of truth:** ID for bridged items, with the plugin as a
  change courier; Joplin-local changes made while the plugin is
  absent are indistinguishable from new edits on its return.

### Option 4 — Headless Synchronizer bridge (a "shadow Joplin client")

- **Shape:** ID operates one headless Joplin profile (Joplin's own
  `Synchronizer`, fact 5) pointed at the user's existing sync target.
  The bridge process reads/writes that profile's data through
  Joplin's own data layer and translates to/from ID using the #5848
  manifest mapping. Materially distinct from Option 2 (no protocol
  re-implementation — Joplin's code does the syncing) and from
  Option 3 (no per-client plugin; exactly one bridge profile).
- **Trust/components:** the bridge holds the profile's credentials
  and, if E2EE is enabled, would need the keys — see blocker B1.
  Without E2EE it sees plaintext, like any Joplin client.
- **State owned:** one Joplin profile (a full local replica) + the
  manifest mapping + bridge cursors per direction.
- **Identity/lifecycle:** the shadow profile is a normal Joplin
  client, so Joplin-side identity, deletions, and conflict behaviour
  are Joplin's own; the bridge adds only the ID mapping.
- **Client surfaces:** all — real clients sync with the target as
  usual; the shadow is one more client.
- **Failure/recovery:** bridge downtime = sync pauses, clients
  unaffected; recovery replays from the profile's own sync state.
  A bridge bug can write bad data as a legitimate client, so the
  bridge ships with a read-only mode and a kill switch.
- **Source of truth:** the Joplin target remains Joplin's truth; ID
  remains ID's truth; the bridge is a translator with an explicit
  manifest, not a third authority.

## #5848 manifest: what continuous sync additionally needs

The manifest already provides: source-vault identity, the
Joplin-ID ↔ ID-note/resource mapping, per-item source hashes, and
idempotent application. Any continuous option (2–4) additionally
needs, as manifest v2 fields:

- **Per-direction cursors** (last applied Joplin change marker and
  last applied ID event marker), so a restart resumes instead of
  re-baselining.
- **A tombstone feed on both sides**: Joplin deletions (target
  deletes / profile deletions) and ID tombstones (#5838) recorded in
  the manifest before either is applied, so delete/restore races are
  decidable (see the conflict cases below).
- **Field-level provenance** for metadata ID does not originate
  (tags, notebook placement, Joplin-specific flags), so a round trip
  does not silently drop or overwrite them.
- **Version mapping**: Joplin's per-item revision state ↔ ID head
  IDs, so "changed on both sides" is detected from records, not
  guessed from timestamps.
- **An E2EE marker per vault/item class**, because the correct
  behaviour for encrypted items is exclusion, not failure (B1).

Re-import (Option 1) needs none of this — which is precisely the
difference between re-import and continuous sync.

## #2048 conflict semantics: concrete cases

Invariants for every option: stable ID identity; concurrent heads
are preserved and surfaced; merges are explicit; no last-writer-wins;
deletions are tombstones with restore, never silent erasure;
#5848 §7's export rule is unchanged.

| Case                                       | Joplin behaviour (facts 1–2)                                | Required ID behaviour (any option)                                                                                                                                                                             |
| ------------------------------------------ | ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Same note edited on two devices offline    | Conflict-notebook copy; remote replaces local; manual merge | Both edits arrive as **two ID heads** on the same note; the UI offers explicit merge. Joplin's own conflict copy, if it syncs back, maps to a _new_ ID note linked as a conflict artifact — never auto-merged. |
| Delete in Joplin vs edit in ID             | Delete propagates as an item delete                         | Manifest tombstone feed decides order from records: the edit becomes a head on a tombstoned note and the user is offered restore-with-edit or confirm-delete. The delete never silently wins.                  |
| Delete in ID vs edit in Joplin             | (Joplin has no tombstone concept beyond delete)             | ID tombstone is exported as a Joplin delete **only** on the designed export path; a later Joplin-side edit of the same item re-imports as a restore proposal, not a resurrection.                              |
| Tag/notebook (metadata) changes both sides | Item-level replacement                                      | Metadata is field-provenanced (manifest v2): disjoint field changes merge; same-field changes head the note's metadata and surface like content conflicts.                                                     |
| Internal links (note ↔ note)               | Joplin IDs in markdown                                      | Links are rewritten through the manifest mapping in both directions; an unmapped target stays a Joplin-ID link and is reported, never rewritten to a guessed ID.                                               |
| Attachments/resources                      | Binary items, content-hashed by Joplin                      | Map to #5844 content-addressed blobs by hash; identical bytes dedupe; a resource edited on both sides is two blobs + an explicit pick, like note heads.                                                        |
| Client offline for weeks                   | Delta download on return                                    | Bridge/baseline re-baseline: the returning client's state is diffed against the manifest before any application; divergence is reported, not folded in silently.                                               |

**Architectural tension, stated plainly:** Joplin's conflict model
(copy + replace + manual merge in Joplin's UI) and #2048's model
(multi-head + explicit merge in ID's UI) are different answers to
the same event. Options 2 and 3 let Joplin's model fire _first_
(inside Joplin's sync), which can destroy the very concurrency #2048
exists to preserve before ID ever sees it. Options 1 and 4 keep the
translation point where both sides' records still exist. Any build
phase must resolve this tension in its own design, with the scenario
matrix below as its oracle — it is the single largest correctness
risk in this programme, ahead of protocol mechanics.

## Migration, operations, rollback

- **Into any continuous option:** start from a completed #5848
  import; extend the manifest to v2 (cursors zeroed, tombstone feed
  opened); run the bridge/target in **read-only shadow mode** first
  (it observes and reports the changes it _would_ apply) for one
  full sync cycle before writes are enabled.
- **Back to baseline:** disabling the bridge/target returns the
  system to Option 1 with the manifest intact; identities created
  during continuous operation persist in the mapping, so a later
  re-import does not duplicate them.
- **Rollback of a bad write window:** ID's append-only log makes
  bridge-applied events enumerable by provenance; rollback is a
  compensating event set, never log surgery.
- **Backups:** whatever store an option adds (target store in
  Option 2, shadow profile in Option 4) joins the existing backup
  set before writes are enabled; a restore drill is part of the
  test corpus.
- **Observability:** per-direction applied/pending/conflicted
  counters and a divergence report are the minimum; "sync is quiet"
  must mean zero pending, not zero logging.

## Maintenance cost and ownership (assumptions stated)

Assumptions: one vault, ≤ 4 Joplin clients, Joplin ships protocol-
relevant changes at most a few times a year (sync version has
reached 3 over the project's life), ID's knowledge layer is pre-1.0
and still changing its own substrate (#5838).

- Option 1: ~0 ongoing.
- Option 2: a named **protocol steward** owns tracking Joplin Server
  / sync-version changes, running the interop corpus against each
  Joplin release, and target-store operations. Estimate 2–4 days per
  Joplin major release plus on-call for the service. Highest cost.
- Option 3: plugin compatibility per Joplin release + bridge
  upkeep; iOS exclusion is permanent support surface ("why doesn't
  it sync on my phone"). Estimate 1–2 days per release.
- Option 4: shadow-profile upgrades track Joplin releases; the
  surface is Joplin's own client behaviour, so breakage is usually
  visible as ordinary client bugs first. Estimate 1–2 days per
  release.
- **Owner requirement:** no continuous option ships without a named
  protocol steward recorded on the build issue. "The fleet" is not
  an owner; an unnamed obligation is how sync bridges rot.

| #   | Scenario                                 | Expected outcome (any continuous option)                                         |
| --- | ---------------------------------------- | -------------------------------------------------------------------------------- |
| S1  | Note created in Joplin, bridge runs      | One ID note, manifest mapping recorded, no duplicate on re-run                   |
| S2  | Same note edited in ID only              | Export path carries it; Joplin shows the edit; no echo head created on return    |
| S3  | Same note edited both sides offline      | Two ID heads; explicit merge offered; nothing auto-merged, nothing lost          |
| S4  | Delete in Joplin, edit in ID             | Tombstone + head; restore-or-confirm prompt; delete does not silently win        |
| S5  | Resource added in Joplin                 | One #5844 blob by hash; re-run adds nothing                                      |
| S6  | Bridge killed mid-application, restarted | Resumes from manifest cursors; applied set unchanged (idempotent)                |
| S7  | E2EE-enabled vault                       | Encrypted items excluded and reported as excluded; no crash, no plaintext demand |
| S8  | Joplin upgrades sync version             | Corpus fails loudly in CI before any production bridge runs the new version      |
| S9  | Bridge disabled for a month, re-enabled  | Re-baseline diff reported first; no silent fold-in                               |
| S10 | Restore drill from backup                | Manifest + mapping restore; S1–S6 re-run green                                   |

## Hard blockers and ordering

- **B1 — E2EE.** #5848 holds no E2EE keys, by design. No continuous
  option can sync the _content_ of E2EE items without reversing
  that decision. Scope any build to non-E2EE vaults/items, with
  S7 behaviour for the rest, or take the keys question back as its
  own decision. This blocks full-fidelity sync, not the design.
- **B2 — Conflict-model tension** must be resolved inside any
  build phase's own design, against the scenario matrix. Not
  resolvable by choosing a transport.
- **B3 — No plugin sync-target registration** if a
  future Joplin release adds one, Option 2's shape changes (register
  instead of re-implement); re-verify at build-design time.
- **Ordering:** #5848 v1 lands first (it is the baseline and the
  migration source). #5838's tombstone/blob surfaces must be stable
  enough to map onto before manifest v2 is designed. #5844's blob
  identity is assumed, not redesigned. Build/no-build is decided
  after this record, by the decision-maker, weighing: how painful
  re-import staleness actually is in use, whether iOS coverage is
  required (eliminates Option 3), and whether a named protocol
  steward exists (gates Options 2–4).

## Recommendation (conditions, not a build decision)

Keep Option 1 as the shipping baseline. **If** continuous sync is
later approved, the evidence above supports designing the build
around **Option 4** (Joplin's own Synchronizer does the protocol
work; the conflict-translation point stays where both records
exist; coverage includes iOS) — with Option 2 disfavoured unless a
requirement appears that only a hosted target meets, because it is
the only option that re-implements a moving protocol and blurs
source-of-truth. Conditions for any build phase: B1 scoped,
B2 resolved in that phase's design against the scenario matrix above, a named
protocol steward, and shadow-mode-first rollout (see Migration).
