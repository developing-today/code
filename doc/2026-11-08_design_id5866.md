## 1. What "parity" means here

Local-dev parity is **contract parity, not backend identity**. A local
environment has parity when (a) it runs the same #5863 storage
contract, at the same contract/schema version, as the deployed
serverless edition, (b) replaying the canonical fixtures (§3) through
that contract produces exactly the world state the fixtures declare,
and (c) every behavioural difference from the deployed backend is
named in the parity-gap list (§5.3) instead of being discovered.
Bit-identical behaviour of the underlying store (D1 vs libSQL
replication timing, edge replica lag, platform limits) is explicitly
**not** part of the parity promise — those are #5681/#5867 concerns,
and pretending a laptop reproduces them would be a false guarantee.

## 2. Decision: local dev targets the contract, never a backend

1. **All local workflows run against the #5863 contract.** Fixtures,
   the offline workflow, and any future local tooling are written
   against the contract surface (journal append/read, world state,
   indexes) only. No local-only code path may call a backend-specific
   feature, because a local path that only works on one store silently
   forks the edition — exactly what #5863 exists to prevent.
2. **The local store is an implementation detail behind the
   contract.** Which store runs locally is the backend-specific
   question deferred in §6. Swapping it must change no fixture, no
   workflow step, and no application code — only the adapter binding.
3. **One command up, one command reset.** A developer goes from a
   clean checkout to a running local serverless edition with a single
   documented command, and back to a pristine state (empty journal,
   fixtures reloaded) with a single reset command. Local state is
   disposable by design; nothing local is ever the only copy of
   anything.

## 3. Decision: fixtures are contract-level journal replays

1. **Canonical fixture form is a journal, not a dump.** A fixture pack
   is a versioned, in-repo sequence of journal appends expressed in
   contract terms, plus a declared expected world state (the oracle:
   replay the journal, compare world state — a model check, not a
   golden backend file). This rides the same export/replay mechanism
   #5867 defines for backend migration, so fixtures, migration, and
   local seeding are one mechanism, not three.
2. **Deterministic and signed-stream-shaped.** Fixture journals carry
   fixed identities, timestamps, and ordering, and respect the #806
   signed-journal shape, so a replay exercises the same ordering and
   verification paths as production traffic. Replaying the same pack
   twice — or on either future backend — yields byte-identical world
   state; a replay that does not is a contract violation, not a
   fixture quirk.
3. **Packs are small, named, and layered:** an empty-world pack, a
   minimal single-world pack for smoke work, and scenario packs named
   for the behaviour they set up. No pack is a copy of production or
   cloud data.
4. **Rejected alternatives:**
   - _Backend-native snapshots_ (a D1 SQLite file, a sqld dump) as the
     canonical form: they fork the fixture set per backend, cannot be
     replayed across backends, and bypass journal invariants on load.
   - _Hand-written SQL inserts:_ they seed rows the journal would
     never have produced, so local state can diverge from any state
     the deployed system can actually reach.
   - _Seeding from a live cloud database:_ non-deterministic, needs
     network and credentials, and imports data local dev has no
     business holding. All three fail §4's invariants.

## 4. Invariants implementation must hold

- **I1 — Contract version pinning.** The local environment declares
  the contract/schema version it runs; a mismatch with the fixture
  pack's required version fails loudly at startup, never silently
  migrates or approximates.
- **I2 — Replay equivalence.** Replaying a fixture pack through the
  contract reproduces its declared world state exactly, on any local
  backend, every time (the pack's oracle check is part of loading it).
- **I3 — Fully offline after setup.** After a one-time tool/dependency
  fetch, starting, resetting, seeding, and exercising the local
  edition requires no network access and no Cloudflare or Turso
  account, token, or cloud database. This is testable: the workflow
  passes with networking disabled.
- **I4 — No production credentials, ever.** Local configuration uses
  dummy/local-only values; tooling refuses a configuration that
  points a local run at a production backend.
- **I5 — No local-only behaviour.** Behaviour observable through the
  contract locally either matches the contract's specification or is
  listed in the parity-gap list (§5.3). An unlisted divergence is a
  bug in the local adapter, full stop.
- **I6 — Disposable state.** Reset returns the environment to the
  pristine post-setup state in one command; no manual file deletion
  or store surgery is ever part of the workflow.

## 5. Decision: the offline developer workflow shape

1. **Shape:** fetch tools once → one command starts the edition
   locally (Worker runtime + local store behind the contract) → one
   command loads a named fixture pack → work → one command resets.
   The workflow is identical regardless of the §6 store choice; only
   the adapter started in step one differs.
2. **Migrations run locally first.** The same contract migrations the
   deployed edition applies run against the local store on startup;
   a migration that cannot run locally cannot ship, because local is
   where it will be debugged.
3. **Parity-gap list.** The local tooling ships a maintained
   `parity gaps` section (in the implementation's local-dev docs)
   naming each known local-vs-deployed difference — expected entries
   once §6 lands include replication lag (locally zero), platform
   limits (locally absent or raised), and any single-primary
   behaviours. An entry names the difference, why it is safe for
   local work, and what would make it unsafe to ignore.
4. **Rejected alternative — "just develop against the cloud":**
   developing against a real D1/Turso cloud database as the default
   loop fails I3 and I4, makes fixture discipline optional (state
   accretes by hand), and couples every contributor's loop to account
   provisioning. Cloud verification remains a pre-release step, not
   the development loop.

## 6. BLOCKED: the backend-specific half (Miniflare/D1-local vs sqld)

**Not decided by this record.** Choosing the local runtime/store
pairing — Wrangler/Miniflare with local D1 vs a local sqld (vs both,
mirroring a "both" outcome) — before #5681/#5867 choose the deployed
backend(s) would either guess the parent's decision or silently
constrain it; this record does neither.

Decision rule, fixed now so the remainder is mechanical once unblocked:

- If #5867 lands **D1 only** → local is Miniflare with its local D1,
  behind the contract adapter.
- If #5867 lands **Turso only** → local is a local sqld / embedded
  libSQL, behind the contract adapter.
- If #5867 lands **both** → local supports both pairings behind the
  contract, fixture packs must replay equivalently on both (I2 is the
  gate), and the _default_ local pairing is whichever #5867 names as
  the reference backend; if it names none, that sub-choice returns to
  #5866's remainder explicitly.

**Resume condition:** #5867 records the backend choice (and #5681
closes or records its storage decision). At that point §6 is settled
by amendment to this record applying the rule above, and #5866
closes. Until then #5866 stays open for exactly this remainder —
no other part of #5866 remains undecided.

## 7. Parent decisions: consumed, none changed

This record consumes #5681's framing (D1 vs Turso vs both; the journal
guarantees of #806 must survive the store), #5863's contract as the
parity target, and #5867's export/replay mechanism as the fixture
mechanism. **No #5681, #5863, or #5867 decision is changed, narrowed,
or pre-empted here**; §6's decision rule is conditional on their
outcome, not a vote for one. If a future amendment under §6 finds the
rule cannot be applied as written, that conflict is recorded as an
explicit proposed change to the parent decision, never folded in
silently.

## 8. Scope exclusions

No implementation code (local tooling is built against this record
later, on its own tickets), no re-decision of deployed storage, and
no sibling scope: #5863–#5865 and #5867–#5869 keep their own records.
