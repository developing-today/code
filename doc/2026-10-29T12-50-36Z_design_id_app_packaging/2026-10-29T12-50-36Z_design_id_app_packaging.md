# Design: ID app packaging — app manifest, folder layout, TUI/web parity

Issue: #2026 (LIST 6a, parent epic #2056). Source evidence: triage task 3343
verdict on #2026 (CONFIRMED, greenfield), call sites re-verified fresh by
queue task 3389 on 2026-10-29 against `origin/main` 5a34fa70. Design only —
no packaging code is built by this task; buildable follow-ups are filed
from it (§6).

## 0. Verified current state

- **No apps directory, no app manifest.** `pkgs/id/` is a single crate tree
  (`src/`, `web/`, `examples/`, `doc/`). Nothing in the tree declares
  "I am an app"; the closest things to apps today are the world programs in
  `pkgs/id/examples/` (`roc-world`, `roc-chat`, `roc-counter`, `tic-tac-toe`,
  …), which are referenced by *path convention* (e.g. `src/commands/world.rs`
  resolves `examples/roc-world` at lines 413–414), not by any declaration.
- **Two interface stacks, hand-duplicated.** CLI/TUI-style:
  `src/cli.rs` + `src/commands/*` (e.g. `cmd_world`, `src/commands/world.rs:71`).
  Web, in two layers: server-side `src/web/*` (Axum routes in
  `src/web/routes.rs` — `create_router` at :252; templates; websockets) and
  the separate `pkgs/id/web/` frontend package (bun, its own lockfile).
  The same features (world, groups, identity) are reachable from both
  stacks because someone wired them twice — there is no shared app
  definition either stack consumes.
- **Three different things are already called "manifest"** — §1 exists
  because of this.

## 1. The three manifests, disambiguated (normative)

| Name (use exactly these) | Artifact | Owner / location today | What it means |
|---|---|---|---|
| **app manifest** | `app.toml` in an app folder (**new, this design**) | the app author | Packaging & declaration: what the app is, what it needs, how it renders. Static, authored, versioned with the app. |
| **world-apply manifest** | `world.toml` → `crate::world_manifest::WorldManifest` (`src/world_manifest.rs:28`) | the world operator, at apply time | Runtime state to converge a *running world* to: `module_hash` XOR `module_source`, `seed`, `grants`, capability ceiling. Parsed/applied by `src/commands/world.rs:861+` (`parse_manifest_file`, diff/plan/apply). |
| **web-build manifest** | `manifest.json` generated by `pkgs/id/web/scripts/build-manifest.ts` | the web build | A build *output*: logical asset name → hashed filename, read by the Rust server to inject asset URLs. Never authored, never an input. |

Rules that keep them apart:

- New code and docs never say bare "manifest" for any of the three; the
  qualified names above are the terms.
- The app manifest **references** a world-apply manifest (or a module hash)
  for its program; it does not absorb its fields. Grants/ceilings stay
  operator decisions at apply time — an app *requests* capabilities in its
  app manifest (§2), the operator's world-apply manifest *grants* them.
- The web-build manifest stays a build artifact of the direct-for-web path
  (§4.2); the adapter path (§4.1) does not produce one per app.

## 2. The app manifest — `app.toml` schema (v1 proposal)

```toml
[app]
id = "world"                 # stable, kebab-case, unique in apps/
name = "World"               # display name
version = "0.1.0"
description = "Host and join a shared world."

[program]                    # the general (non-web) program, if any
kind = "roc-world"           # platform/program kind
source = "program/"          # source dir inside the app folder, OR:
# module_hash = "blake3:…"   # a prebuilt module (mutually exclusive, same
                             # rule as the world-apply manifest)

[interfaces.cli]
commands = ["world"]         # CLI subcommands this app contributes
                             # (dispatched like src/commands/world.rs)

[interfaces.web]
mode = "adapter"             # "adapter" (§4.1) or "direct" (§4.2)
route = "/world"             # page route when the app is active
socket = "/ws/world"         # live-channel route, if any

[capabilities]
request = ["world.host", "world.join", "blob.read", "blob.write"]
                             # requests only — grants happen via the
                             # world-apply manifest / operator, never here

[resources]
files = ["assets/**", "web/templates/**"]   # packaged + content-hashed as a set
```

Design notes:

- **Everything is relative to the app folder.** No absolute paths, no
  references outside the folder except the platform (`kind`) — an app
  folder is copyable as a unit, which is the point of LIST 6a's
  "code + images/resources as one set".
- **`id` is the identity, not the folder name by accident:** folder name
  must equal `id` in v1 (checked by the pack step) so path-based discovery
  and manifest-based discovery can never disagree.
- **Unknown fields are errors, missing optional sections are fine.** An
  app with no `[program]` (a pure web app) or no `[interfaces.web]` (a
  pure CLI app) is valid; an app with *no* interface section is not.

## 3. Folder layout — `pkgs/id/apps/`

```
pkgs/id/apps/
  world/
    app.toml
    program/            # Roc/Wasm world program sources (today: examples/roc-world)
    assets/             # images/resources, content-hashed at pack time
    web/
      templates/        # adapter mode: server-side templates/fragments
      direct/           # direct mode: the app's own frontend sources (optional)
  tic-tac-toe/
    app.toml
    program/            # today: examples/tic-tac-toe (main.roc + built .wasm)
    assets/
```

- `examples/` stays for host/platform development fixtures; an example
  becomes an *app* by moving (or being copied, during transition) under
  `apps/` and gaining an `app.toml`. The two existing candidates prove the
  shape: `examples/roc-world` already has program sources + a README and
  no manifest; `examples/tic-tac-toe` already ships a prebuilt `.wasm`,
  exercising the `module_hash` variant of `[program]`.
- **Discovery:** the host scans `apps/*/app.toml` at startup (and on an
  explicit reload), validates, and registers the app's CLI commands, web
  routes, and capability *requests*. Discovery failures are per-app: one
  malformed `app.toml` disables that app with a named error, never the
  host — the same degrade-don't-die posture as the rest of `pkgs/id`.

## 4. One app, two render paths — the `world` example sketched both ways

The general app is the world program + its CLI surface. Real anchors:
`cmd_world` (`src/commands/world.rs:71`) and the serve flags that host a
world (`--world`, `--world-module <wasm>`, `src/cli.rs:352–360`).

### 4.1 General app + web adapter (the default; `mode = "adapter"`)

The app ships no web code of its own beyond templates. The host's existing
web stack renders it through the generic world surfaces that already
exist:

- Page: `GET /world` → `world_page_handler` (`src/web/routes.rs:257`,
  handler at :317 — renders the world page when a world is active, 404
  when none is).
- Live channel: `world_routes()` (`src/web/world_ws.rs:49`) — the
  websocket bridge between browser and the running world.
- The app's `[interfaces.web]` entry is what *parameterises* these generic
  surfaces (route, socket, which world/app instance), replacing today's
  hardcoded single-world wiring.

This is the parity path: TUI/CLI and web are two renderings of the same
program state, and the app author writes no web-specific logic. Its limit
is the generic surface's vocabulary — an app that needs a genuinely
web-native widget cannot express it here.

### 4.2 Direct-for-web (`mode = "direct"`)

The app ships its own frontend under `web/direct/` in its folder, built
with the same toolchain as `pkgs/id/web/` (bun). The build emits hashed
assets + a **web-build manifest** (§1) scoped to the app; the Rust server
serves them under the app's route and the app talks to the same program
state over the socket/API surface. The app *may* still expose the CLI
surface (the general program doesn't change) — "direct" specialises the
rendering, not the program.

Cost, stated plainly: a direct app owns frontend code forever (build,
asset hashing, dependency drift against `pkgs/id/web/`), which is why
adapter is the default and direct is for apps whose web experience *is*
the product surface.

### 4.3 The rule that keeps the two paths honest

Both modes consume the **same** `app.toml`, the same `[program]`, and the
same capability requests. Mode is a rendering choice declared in one
place; switching an app from adapter to direct changes only
`[interfaces.web]` and adds `web/direct/` — it never forks the program.
That is the parity guarantee LIST 6 asks for, stated as a testable
property, scoped to the apps it can apply to: *any program-backed app
must run in adapter mode with its direct frontend deleted.* A
frontend-only direct app — one with no `[program]`, which §2 explicitly
accepts — is exempt: the adapter renders a hosted program (the existing
`world_page_handler` returns 404 when no world is active), so with no
program there is nothing for adapter mode to render. Such an app gains
the parity guarantee only if it later gains an adapter-compatible
backing program.

## 5. Pack step (proposal, not built here)

`id app pack <folder>` (name bikesheddable): parse + validate `app.toml`,
verify folder name == `id`, hash `[resources]` and the program module,
and emit a bundle descriptor that names content hashes — so installation
and the world-apply step can pin exact bytes the way the world-apply
manifest already pins `module_hash`. The pack step is deliberately the
*only* new machinery v1 needs; discovery (§3) reads unpacked folders in
dev and bundles in deployment with the same manifest.

## 7. What this design does not decide

- The capability *vocabulary* (the strings in `[capabilities].request`) —
  that is the capability-system design (#2027/#2028); the examples here
  are illustrative, and the schema treats them as opaque strings.
- World-program (Roc/Wasm) authoring itself — the platform in
  `examples/roc-world` is the input, not the subject.
- Distribution of apps between users (apps as ID-graph objects, signing,
  install-from-peer) — a later design; the content-hash pinning in §5 is
  chosen so it does not have to be redone when that design lands.
