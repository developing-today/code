# Design: RateAuthorisation as a signed ID-graph object

- **Status:** decision-ready design; one policy question for Drew in §9.
- **Date:** 2026-11-01
- **Issue:** [#2290](https://github.com/developing-today/code/issues/2290)
- **Related:** [#2062](https://github.com/developing-today/code/issues/2062),
  [#2063](https://github.com/developing-today/code/issues/2063),
  [#2041](https://github.com/developing-today/code/issues/2041),
  [#2251](https://github.com/developing-today/code/issues/2251)
- **Scope:** schema, signer authority, versioning, revocation, and quote
  binding. No implementation is included here.

## Intent

Define one auditable, versioned graph object that a liquidity provider (LP)
can sign to authorize a one-direction currency conversion, plus the rules
under which the gateway may rely on it. The graph event is the durable
authorization statement; the gateway's lookup row and revocation set are
rebuildable projections, not competing sources of authority.

The conversion engine remains #2063's application-layer linked-transfer
operation. It checks the authorization before any TigerBeetle write; the
ledger does not store or interpret the RateAuthorisation (#2063, §§1–4).

## The shape

```text
LP's authorized ID signer
       │ ordinary signed ID-graph event
       ▼
currency.rate_authorisation ──► gateway projection ──► quote pins event ID
       │                               │                         │
       └─ currency.rate_authorisation_revoke ──► revoke set      ▼
                                         live checks at submission
                                         then linked ledger batch
```

There is one signed authorization format. Wallets/apps may present it as a
“rate offer”; that presentation and the gateway's enforcement row are views
of the same authorization, not separately signed `token.offer` and
RateAuthorisation objects. This preserves #2041's split between the
graph-facing offer and gateway-enforced authorization as two projections of
one authorization (#2041 design doc, §6).

## Context and evidence

- **Conversion policy is already mostly set.** #2063 specifies a
  one-direction rational rate, integer amount bounds and total cap,
  authorised callers, mandatory expiry, gateway pre-flight checks, revocation
  at submission, and quotes bound to an authorization. It also says posted
  conversions are not undone by revocation (#2063, §§2, 4.1, 4.4).
- **The graph and ledger have different identifiers.** The later #2041
  investigation reconciles graph currency identity as `(issuer public key,
  definition-object hash)` (or its canonical compact hash) with the
  registry's `currency_id` and TigerBeetle's `ledger` u32; graph objects
  refer to the semantic currency, while the gateway resolves the operational
  ledger at submission (#2041 design doc, §1; #2062 design doc, §§2.1–2.4).
  Accordingly this graph body uses `from_currency` / `to_currency`, not
  ledger numbers.
- **An LP is not necessarily a token issuer.** #2041 §6 allows an issuer or
  another liquidity holder to offer a rate. `issuer_id` below therefore means
  the LP/account that authorizes the liquidity, not the issuer of either
  currency (#2041 design doc, §6).
- **The closest implemented envelope is `chain`, not the attestation PoC.**
  `ChainExt` carries the event kind and causal frontier
  (`pkgs/id/src/chain.rs:93-135`); `chain::sign` signs that header and commits
  to the body (`pkgs/id/src/chain.rs:259-308`); `decode` verifies the signed
  header and canonical encoding (`pkgs/id/src/chain.rs:311-342`); event-store
  ingestion verifies body hash and size (`pkgs/id/src/event_store/ingest.rs:433-443`).
  The reviewed graph-token spec supplies the closer body-format precedent:
  canonical CBOR, exact fields, namespaced kinds and no unknown keys
  (#2251 doc, §§0–1).
- **Do not copy attestation as a production contract.**
  `pkgs/id/src/attestation.rs:1-24` labels itself a proof of concept; it uses
  JSON and its generic signing path does not enforce object-specific signer
  authority (`attestation.rs:71-98, 154-175`). Likewise, the group log's
  revoke operation is a local fold input, not itself the signed graph wire
  format (`pkgs/id/src/groups/log.rs:1-10, 123-145`; signed bridge:
  `pkgs/id/src/event_store/resolve.rs:291-357`). These are useful semantic
  examples, not formats to reuse.

### Existing schema conflict to resolve

The merged #2251 spec currently defines signed `token.offer` events and says
supersession is their revocation mechanism (#2251 doc, §1.5). The Nov 1
#2290 triage record instead proposes a gateway-oriented `currency.rate_authorisation`
schema with a distinct signed revoke event, versioning, and quote pinning.
This design follows the newer #2290 direction for the gateway authorization,
but keeps the graph/registry boundary from #2041/#2062. Before implementation,
the #2251 format must be reconciled so there is only one canonical signed
rate object and one rate-unit convention; the old `token.offer` name may
remain as a UI/API label, not as a second signed wire format.

## Design

### 1. Canonical object and body

The event kind is `currency.rate_authorisation`. Its body is a closed,
canonical CBOR map. Required and optional fields are:

| Field | Type and meaning |
| --- | --- |
| `authorisation_id` | `u128`, stable for the lifetime of this authorization; scoped to `issuer_id`. A duplicate ID under that issuer is invalid. |
| `version` | `u64`, starting at 1 and increasing by exactly 1 for each amendment. |
| `issuer_id` | LP account/ID that controls the liquidity accounts; not the currency issuer and not necessarily the event's device key. |
| `from_currency`, `to_currency` | Graph currency IDs `(issuer, definition hash)`, one ordered pair and one direction only. The reverse is a distinct authorization. |
| `rate_num`, `rate_den` | Positive `u128` rational, gcd-reduced; destination major units per source major unit. No floats. |
| `min_amount`, `max_amount` | `u128`, inclusive per-conversion bounds in source-currency minor units; `0 < min_amount ≤ max_amount`. |
| `total_cap` | `u128`, maximum cumulative source-currency minor units for this authorization. Remaining volume is derived gateway state, not a signed field. |
| `authorised_callers` | `"any"` or a non-empty list of account/ID identities. A single counterparty is a one-element list. |
| `not_before` | Optional Unix epoch seconds (UTC); absent means immediately eligible. |
| `expires_at` | Required Unix epoch seconds (UTC); eligible only while `not_before ≤ execution_time < expires_at`. |
| `fee_bps` | Optional explicit fee policy. Any fee remains a separate, quote-visible ledger leg, never hidden in the rate (#2063, §§1–2, 4.4). |
| `reversal_window_secs` | Optional permission for a compensating reversal at the original rate; it does not reverse or mutate posted transfers (#2063, §4.4). |
| `supersedes_event_id` | Required for versions above 1; exact event ID of the immediately preceding version. Absent for version 1. |

Unknown keys, duplicate map keys, non-canonical CBOR, zero denominator,
non-reduced rates, invalid bounds, and currency self-pairs are rejected.
Optional keys are absent when unused; there is no second encoding for a
default value. The event envelope has no trusted wall-clock timestamp, so
`not_before` and `expires_at` are evaluated against the executor's clock at
execution time (#2251 format spec, §1.5).

For source amount `x` in source minor units, the destination amount is
computed with the two fixed currency scales:

```text
y = floor(x × rate_num × 10^dest_scale /
          (rate_den × 10^source_scale))
```

All arithmetic is integer-only, using checked wide intermediates; overflow
and a zero destination result fail before submission. Rounding is down in
the LP's favour, as #2063 §2 requires. This chooses the scale-aware
convention in #2063 and the Nov 1 #2290 triage record over #2251's earlier
minor-unit-per-minor-unit `token.offer` convention (§1.5); the reconciliation
step above must update #2251 before code is written.

The graph event does **not** carry TigerBeetle ledger IDs. The gateway
resolves each currency ID through the #2062 registry and verifies the LP's
two bound liquidity accounts for the resolved ledgers before accepting a
conversion (#2062 design doc, §§2.3–2.4, 4.2; #2063, §3).

### 2. Signing and issuer authority

1. Encode the body as canonical CBOR and place the kind in `ChainExt.kind`;
   sign with the ordinary `chain::sign` event envelope. Do not add a second
   detached signature or a RateAuthorisation-specific header.
2. On ingest, verify the event/header and body commitment using the existing
   chain and event-store checks cited above. Then decode the exact body schema
   and perform RateAuthorisation-specific validation. A valid event
   signature proves which key signed; it does not by itself prove that key
   may authorize an LP's liquidity (#2062 design doc, §4.2).
3. Resolve the signing key to `issuer_id` using the account/device authority
   records and require the device authorization to be active at the issuer's
   accepted frontier. Do **not** compare the body account ID directly to a
   device verifying key: #2062 §4.1b assigns issuance authority to the
   account key and requires resolving device → account; device revocation
   withdraws that device's authority.
4. Require the LP's registry eligibility and both bound liquidity accounts
   to match the authorization's currencies; reject missing, closing or
   closed accounts before any TigerBeetle write (#2062 design doc, §§3–4;
   #2063, §3).

### 3. Version fold and revocation

- Events are append-only. Version `n+1` must name the version `n` event in
  `supersedes_event_id`; a body update is never an in-place edit.
- The live version is the unique tip of the issuer-authorized lineage at the
  gateway's accepted issuer frontier. A missing predecessor, skipped
  version, or competing successors is ambiguous and fails closed. A revoked
  or superseded version never becomes live again by falling back to an older
  event.
- Revocation uses a second signed kind, `currency.rate_authorisation_revoke`,
  with body `{authorisation_id, reason?}`. Only the LP's authorized account
  may sign it. It revokes the entire stable authorization ID, effective for
  new submissions as soon as the event is present in the gateway's accepted
  issuer frontier. A replacement after revocation gets a new
  `authorisation_id`; there is no version rollback or resurrection.
- The control plane materializes revocations by folding verified revoke
  events and checks the set at submission time—not merely when a quote is
  issued (#2063, §§2, 4.1). A revocation prevents new conversions; it does
  not alter a conversion already posted (#2063, §4.4).
- Revisions and revocations are distinct: a revision changes the current
  terms; an explicit revoke terminates the whole authorization. This is
  more direct to audit than requiring the LP to publish a synthetic
  zero-cap successor, at the cost of a second event kind and fold rule.

### 4. Quote binding and submission

A quote is a short-lived gateway record, not a graph event:

```text
{ quote_id, authorisation_id, version, authorisation_event_id,
  source_amount, destination_amount, fee, issued_at, quote_expires_at }
```

Use a 60-second lifetime, as proposed in #2063 §2 and adopted by the Nov 1
#2290 triage record. Pinning the exact event ID means a later version cannot
silently satisfy the quote. At submission the gateway must revalidate all
live conditions: current unique version, signature and signer authority,
not-before/expiry, revocation, LP/account bindings, caller, amount, and
remaining cap. A quote is not a reservation or authorization to bypass those
checks.

The gateway atomically reserves available total-cap volume for concurrent
submissions; it commits usage only for POSTED conversions and releases a
reservation on definitive failure. An unknown outcome holds the reservation
until the executor reconciles the exact transfer IDs. This combines
#2063's posted-only accounting with #2251's reviewed atomic
check-and-reserve/recovery rules (§5, step 6). All rejections are pre-flight
and produce no TigerBeetle write (#2063, §4.1).

## Decisions

1. **One graph event is canonical.** `currency.rate_authorisation` is both
   the signed authorization and the discoverable graph-side offer; the
   gateway table and any `token.offer` presentation are projections. This
   follows #2041 §6's “two projections of one authorization” rule while
   giving #2063's gateway a complete enforceable object.
2. **Graph currency IDs, not ledger IDs, appear in the signed body.** The
   gateway resolves to ledger IDs from the #2062 registry. This keeps the
   graph object about currency identity and leaves operational allocation to
   the control plane (#2041 design doc, §1; #2062, §§2.1–2.4).
3. **Signer authority resolves to an LP account.** Do not equate a device
   signer key with the LP identity; validate the account/device relation and
   current device authority (#2062 design doc, §4.1b).
4. **Explicit signed revocation terminates the whole authorization ID.**
   Version replacement and revocation are separate operations. A revoked
   authorization cannot revive by falling back to an older version.
5. **Quotes pin an event ID and are rechecked at submission.** This prevents
   stale quotes from bypassing replacement, expiry, caller, cap, account or
   revocation checks (#2063, §2).
6. **No platform graph-revoke authority is assumed.** Unless Drew chooses
   otherwise (§9), platform emergency response is a separate, local,
   logged gateway suspension—not a forged issuer event.

## Alternatives considered

| Option | Benefits | Costs / why it loses |
| --- | --- | --- |
| **A. One signed `currency.rate_authorisation` event plus explicit revoke (recommended).** | Complete, auditable graph authority; one object feeds wallet discovery and the gateway projection; explicit withdrawal does not need fake terms; version and quote pinning are precise. | Requires reconciling #2251's already-reviewed `token.offer` schema and its rate-unit/revocation rules before implementation; adds a revoke fold. |
| **B. Keep #2251 `token.offer` as the only signed event and treat RateAuthorisation as its gateway projection.** | Reuses the reviewed canonical-CBOR schema and its `supersedes` lineage; fewer kinds. | Its current body omits #2063's minimum amount and some gateway policy fields, uses a different rate unit convention, and treats supersession as revocation. The gateway and graph semantics would remain difficult to distinguish without expanding that format. It is viable only if #2290's explicit-revoke direction is withdrawn. |
| **C. Keep separate signed graph `token.offer` and signed gateway RateAuthorisation objects.** | Graph discovery and gateway enforcement can evolve independently. | Two signed copies of price, caps, takers and expiry can disagree. It violates #2041's one-authorization/two-projections boundary and forces verifiers to define which signature wins. |
| **D. Store the canonical signed record only in the control-plane database.** | Simple gateway lookup and direct mapping to ledger IDs. | Not a graph object; wallets cannot discover/verify it from the ID graph, and the graph has no canonical authorization to cite. It loses the graph audit/discovery property requested by #2290 and #2041. |
| **E. Put authorization in TigerBeetle.** | A ledger-local representation may look convenient to the executor. | #2063 says TigerBeetle never sees the object; it lacks the identity and authorization semantics required here. |

## Consequences and invariants

- A valid rate authorization is a verified, canonical signed graph event **and**
  a currently authorized LP/account policy. Signature validity alone is not
  sufficient (#2062 design doc, §§4.1b–4.2).
- One event means one ordered currency pair. Reverse rates, caps, expiry,
  caller policy and revocation are independent.
- The gateway's authorization/revocation materialization can be rebuilt from
  verified graph events; it is never the source of issuer intent.
- No float arithmetic; amount scale and rate units are explicit; round down
  in the LP's favour; overflow or zero output rejects before ledger writes
  (#2063 §2; #2251 format spec, §0 for integer amount/rational discipline).
- A superseded, expired, not-yet-valid, revoked, ambiguous, caller-mismatched,
  out-of-bounds or cap-exhausted authorization cannot execute. Rejection
  causes no ledger write (#2063, §4.1).
- Posted conversions are immutable. Revocation blocks only future execution;
  any permitted reversal is a new compensating conversion under the stated
  reversal policy (#2063, §4.4).
- An implementation must not silently retain two incompatible schemas or
  rate-unit conventions. Reconcile #2251 first, then add golden vectors for
  both equal-scale and mixed-scale currencies.

## Acceptance criteria for implementation

1. Canonical-CBOR encode/decode tests accept exactly the specified fields
   and reject unknown keys, non-canonical encodings, invalid currency pairs,
   zero denominators, unreduced rates, invalid bounds and overflow.
2. Chain tests prove that changing the kind/body invalidates the event, the
   body is committed by the existing event hash, and an arbitrary valid
   signer cannot claim an LP account without active account/device authority.
3. Fold tests cover version 1, a valid successor, missing/skipped predecessor,
   concurrent successor fork, repeated revoke, revocation after a newer
   version, and the invariant that no older version reactivates.
4. Mixed-scale rate vectors produce the specified floor result; exact-boundary,
   zero-output and wide-intermediate overflow cases are tested.
5. Gateway tests reject unregistered/ineligible LPs, unbound or closing
   liquidity accounts, stale/revoked/expired authorizations, unauthorized
   callers, out-of-range amounts, insufficient cap and invalid quotes before
   any TigerBeetle submission.
6. Concurrent cap tests show reservations cannot overspend the total cap,
   only POSTED conversions consume it, and definitive failures release it.
7. Quote tests prove that expiry, replacement, revocation or changed live
   policy invalidates an old quote and that a successful quote identifies the
   exact authorization event/version used.
8. An end-to-end worked case creates a one-direction offer, quotes it, submits
   a linked conversion, and shows that the reverse direction requires a
   separately signed authorization.

## Implementation slices

These are independently reviewable/mergeable steps; each has its own tests
and can land without silently enabling the next service layer.

1. **Protocol reconciliation and graph types.** Update the #2251 token
   format contract to make `currency.rate_authorisation` the only signed
   authorization format and settle the scale-aware rate units; implement the
   closed body/revoke types, canonical encode/decode and version/revocation
   fold in `pkgs/id`. Add golden vectors and fork/revoke tests. No gateway or
   ledger writes.
2. **Gateway authorization projection.** Materialize the fold/revocation
   state; validate account/device signer authority, LP eligibility, currency
   registry resolution and liquidity-account bindings; add pre-flight checks
   for time, caller, amount and cap. Verify every failure stops before the
   TigerBeetle client. No quote endpoint required.
3. **Quote and execution binding.** Issue 60-second quote records pinned to
   event ID/version; revalidate live state at submission; implement atomic
   total-cap reservation, POSTED accounting and recovery of unknown outcomes.
   Add end-to-end linked-transfer tests and stale-quote cases.

Step 1 is a prerequisite for step 2; step 2 is a prerequisite for step 3.
Steps 1 and 2 are useful independently as a protocol/fold and a read-only
gateway policy boundary; step 3 is the only slice that enables quote-backed
execution.

## Open questions for Drew

- **Q1 — Platform emergency revocation.** Should the platform be able to
  revoke another LP's authorization in the graph?
  - **A.** Issuer-only graph revocation; platform may locally suspend gateway
    acceptance with a logged control-plane policy (**recommended**). The graph
    remains a truthful record of who withdrew their offer, while incident
    response still has a platform kill switch.
  - **B.** Add a platform-signed `currency.rate_authorisation_platform_revoke`
    event which every verifier honors. This gives a portable emergency
    action, but creates a second revocation authority and changes the meaning
    of the issuer's graph history.

No other decision in this note blocks implementation: the schema, event
lineage, quote lifetime and fail-closed behavior have recommendations above.

## Non-goals

- Implementing the ID graph types, gateway, quote service or conversion
  executor in this design-only change.
- Defining currency issuance, account-factory behavior, ledger allocation or
  conversion atomicity; those belong to #2041, #2062 and #2063.
- Creating platform-signed issuer revocation unless Drew chooses Q1-B.
- Rate discovery, best-rate routing, AMMs/order books, cross-cluster
  conversion, or mutation/deletion of posted transfers.
