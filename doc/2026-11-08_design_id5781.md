## Decision to make

How does an ID world — an entity/triple state image owned by an append-only journal, presented through the shell contract — live inside Bevy, a tick-driven ECS engine with its own `World`, its own replication ecosystem, and a fast breaking-change cadence? Specifically: which side is authoritative for which data, how journal events become Bevy schedules/ticks, which authority posture ships first, and how the whole thing stays deterministic enough for the replay oracles to catch integration bugs.

## Recommendation

**The journal is the only authority; Bevy is a projection.** A Bevy application hosting or joining a world holds a *materialized projection* of the world's entity/triple state in its ECS, rebuilt and advanced exclusively from journal positions. Bevy never writes world state directly: every mutation a Bevy system wants to make becomes an intent submitted to the world's append gate, and takes local effect only when the journal confirms it at a position. Concretely:

1. **State mapping (§1):** ID entities map 1:1 to Bevy `Entity` values through a bridge-owned mapping table; triples map to components by predicate class. Authority is stated per data class — world state (journal-owned), presentation state (Bevy-owned, never journaled), purely local state (Bevy-owned, never leaves the process).
2. **Event flow (§2):** journal appends are applied at a fixed point in the Bevy schedule (a dedicated `JournalSet` before gameplay systems), at most one journal position batch per tick, with an explicit lag budget: a frame may interpolate or predict presentation state, but may never present unconfirmed world state as confirmed.
3. **First posture (§3):** presenter-client first — a Bevy app that joins a world hosted elsewhere. World-host (embedded server) is phase 2; simultaneity (#790) is explicitly out of the first design's scope.
4. **Determinism (§4):** replaying a recorded journal through the bridge must land on identical ECS state; the soak/replay oracles are the acceptance mechanism, and the bridge is where the deterministic subset of Bevy is fenced off from frame-timing nondeterminism.
5. **Provider face (§5):** Bevy offers its render/audio/input surfaces as a #5686 capability provider through the same declaration and grant model as every other provider class; the engine-specific part is confined to how surfaces are produced, per the #5931 §4 open question.

## Viable options

| Option | Trade-offs | Decision |
| --- | --- | --- |
| **Journal-authoritative projection (this design)** | Bevy state is always rebuildable from the journal; replay oracles apply unchanged; the bridge absorbs Bevy's cadence. Costs a mapping layer and an intent round-trip for mutations. | **Recommend.** It is the only option that keeps the world's authority model — one journal, one append gate — intact inside a second stateful runtime. |
| Bevy-authoritative with journal as event log of engine state | Uses Bevy idiomatically (systems mutate components directly) and journals the results. But then two writers exist — engine systems and remote journal writers — and the journal stops being the linearization point; split-brain and lost-update cases reappear in exactly the form the world model was designed to exclude. | Reject. |
| Replication-first: lightyear / `bevy_replicon` carries the shared world | Mature prediction/interpolation and interest management (§5931 §4.3). But replicon/lightyear replicate *engine state* under a server-authoritative or lockstep model; ID replicates a *journal* under a writer-set model. Adopting engine replication as the world transport conflates two different authority questions and strands non-Bevy clients. | Reject as the world transport. `bevy_replicon`-style interest management may inform presenter-side visibility filtering later (§5), and lightyear remains available *inside* a purely local game layer that never touches world state. |
| Dual-write (systems write both ECS and journal) | Looks simple; diverges silently under crash, ordering, and partial-failure cases, with no procedure to decide which copy wins. | Reject. This is the failure mode the projection rule exists to pre-empt. |

## §1 State mapping

### 1.1 Entities

- Every ID entity that is part of the projected world corresponds to exactly one Bevy `Entity`, allocated by the bridge on first projection. The bridge owns an `IdEntityMap` resource: ID entity id ↔ Bevy `Entity`, plus the journal position at which each mapping was created.
- Bevy entities with no ID counterpart (particles, UI nodes, purely local actors) are permitted and are marked with a `LocalOnly` component; the bridge never journals them and the mapping table never contains them.
- Despawn is projection-driven: an ID entity retracted at journal position *p* is despawned (or tombstoned, where a system still holds references) when the projection applies *p* — never because a local system decided the world entity should stop existing.

### 1.2 Triples → components, by data class

| Data class | Examples | Mapping | Authority |
| --- | --- | --- | --- |
| World state | entity existence, world-visible attributes and relations | One Bevy component per predicate family, registered by the bridge schema; values are the journaled values, verbatim | **Journal.** Bevy systems read; mutation only via intents (§2.2). |
| Presentation state | camera, selection, animation phase, interpolated transforms | Ordinary Bevy components/resources owned by presenter systems | **Bevy app.** Never journaled, never granted, never replicated. May be *derived* from world state but is not world state. |
| Purely local state | asset handles, GPU state, input device state, caches | Bevy resources/components marked `LocalOnly` | **Bevy process.** Dies with the process; a restart rebuilds it from assets and the journal projection. |

The classification is per predicate, recorded in the bridge schema, and total: a predicate with no classification does not project (fail-closed), rather than projecting under a guessed authority. This mirrors the provider model's stance that undeclared surfaces do not exist.

### 1.3 Schema and reflection

The bridge schema (predicate → component type, data class, merge/project rule) is data, not code: it is what a Bevy version bump (§Answers Q2) and a world-schema evolution both act on. Where Bevy reflection is available, components register through it so tooling (including the editor line noted in #5931 §4.1) can inspect projected state; reflection is a debugging surface, never a write path.

## §2 Event flow

### 2.1 Journal → Bevy

- The bridge tails the journal from the app's last applied position. Applying a position is atomic with respect to the schedule: a dedicated system set (`JournalSet`) runs at a fixed point — after input collection, before gameplay systems — and applies either all deltas at the next position (or a bounded batch of positions, in order) or none.
- Gameplay and presentation systems therefore always observe a *consistent journal prefix*, identified by position. Any system can read the current applied position; none can observe a half-applied position.
- Catch-up is budgeted: if the app falls behind (join, stall, slow device), the bridge applies at most a configured number of positions per tick and reports lag; presentation may extrapolate *presentation* state during catch-up but world-state components only ever show applied positions.

### 2.2 Bevy → journal (intents)

- A system that wants to change world state submits an **intent** (the same shape as any shell-contract input event): a proposed append, carrying the applied position it was based on.
- The append gate accepts or rejects; the projection applying the resulting journal position is the *only* moment the change becomes visible as world state — including to the app that proposed it. Optimistic local application of world state is prohibited (it would make the local ECS a second authority under a friendlier name). Presentation-layer prediction (e.g. moving a local avatar's *rendered* position) is allowed under §1's presentation class, must be marked predicted, and must reconcile or visibly snap back on rejection.
- This is the shell contract unchanged: #788's presenter obligations are not relaxed because the presenter happens to contain an engine.

### 2.3 What a frame may skip

A frame may skip *rendering* any amount of presentation work. It may not skip *applying* journal positions in order, and it may not apply a later position before an earlier one. Interpolation and prediction live entirely in the presentation class (§1.2) — that is where their nondeterminism is quarantined (§4).

## §3 Authority postures

| Posture | Meaning | Order |
| --- | --- | --- |
| Presenter-client | Bevy app joins a world hosted elsewhere; projection + intents per §1–§2 | **First.** It exercises the full mapping and event flow with the append gate outside the process, which is the case the authority rules must survive. |
| World host (embedded server) | The Bevy process also runs the world's append gate and journal | Second. Adds lifecycle questions (journal storage, admission of other presenters) but no new mapping rules: the host's own Bevy side still consumes its journal through the same projection — hosting never becomes a back door around §2. |
| Both (#790 simultaneity) | One process presents some worlds while hosting others | Follows from the first two by composition; no separate design until both exist. |

## §4 Determinism

- **Replay property:** a recorded journal, replayed through the bridge from an empty Bevy `World`, must produce ECS world-state components identical (by the bridge schema's canonical comparison) to the live run's at the same journal position. This is the soak/replay oracle for the integration, stated as a testable invariant, not an aspiration.
- The property is scoped deliberately: it covers *world-state* components only. Presentation and local state are exempt — and therefore may never feed back into world state (an intent computed from presentation state must carry its world-state inputs explicitly, so replay re-derives the same intent decision from journal data).
- Frame timing is an input the property excludes by construction: journal application is position-ordered, not time-ordered (§2.3). Systems that read wall-clock or frame delta may only write presentation/local state.
- Where the engine's own parallelism makes system order nondeterministic, the bridge fences world-state writes: systems touching world-state components run in the bridge's ordered set. The performance cost is accepted for the world-state subset; presentation systems stay fully parallel.

## §5 Provider face

As a #5686 capability provider, a Bevy app declares the same manifest shape as every other provider class: render surfaces, audio output, input devices — each offered under the standard grant model (§5900's grant lifecycle applies unchanged). The engine-specific content is confined to *how* a surface is produced (a Bevy render target, an audio sink, a gamepad/keyboard source), never to a Bevy-specific declaration or grant dialect — answering #5931 §4's decider question in the affirmative.

Two boundaries:

- **Scripting is not a provider shortcut.** `bevy_mod_scripting` (Lua/Rhai; Rune on hold per #5931 §4.2) may host *local* behaviours. A script receives the host-curated presenter API — intents and world-state reads — never journal write access; the capability discipline is by API design, exactly the pattern #5931 §9 records for embedded scripting generally.
- **Engine replication stays inside the local layer.** lightyear/`bevy_replicon` may serve a purely local multiplayer game layer a Bevy app runs for its own purposes; it never carries ID world state (§Viable options). Interest-management ideas from `bevy_replicon` are noted as input to presenter-side visibility filtering, to be taken up — if at all — in the discovery/visibility design (#5899), not here.

## Answers to the issue's open questions

### Q1 — Where does the bridge live?

**Decision: a separate bridge crate on the #3447 seams** (working name `id-bevy-bridge`), depending on `bevy_ecs` first and the full engine second. Not inside `id-worlds` (the world crate must not grow an engine dependency or an engine release cadence), and not owned outside the workspace (the mapping is part of the world contract; an external owner would drift from the schema it must track). `bevy_ecs`-first matters: per #5931 §4.1 the ECS is usable standalone, including `no_std` targets, so the state mapping (§1) can be proven headless (§Answers Q4) and on constrained targets without the engine's renderer in the dependency graph. The full-engine plugin (schedules, provider surfaces) is a second crate feature/crate layered on the same mapping.

### Q2 — Bevy version policy: pin, track, or abstract?

**Decision: pin per release, track on a scheduled bump, abstract only at the mapping.** The ecosystem evidence (#5931 §4.1) is that every crate pins to a Bevy version and breaking changes arrive per release — abstraction over Bevy's API wholesale would be a second engine written against the first. So: the bridge pins one Bevy minor line per bridge release; a version bump is a scheduled, tested event (the replay oracle in §4 is the bump's acceptance test — a bump that changes projection outcomes is a mapping bug or a named migration, never a silent diff); and the one place abstraction *is* bought is the bridge schema (§1.3), which is data the bump acts on rather than code it rewrites.

### Q3 — Does the #788 WIT / component-model decision change the bridge's shape?

**Decision: no — the bridge is contract-level only.** The bridge consumes the shell contract (journal reads, intent submission) and the provider manifest/grant surface. Whether #788 lands those as WIT components or another binding changes the bridge's *bindings*, not its mapping, event flow, or authority rules. The bridge must therefore depend on the contract as an interface, never on a binding-specific API — that dependency discipline is the whole content of this answer, and it is checkable in the crate graph.

### Q4 — Proving target: 2D-first, 3D-first, or headless-logic-first?

**Decision: headless-logic-first.** The risks of this design are authority, ordering, and determinism — none of which a renderer exercises. The first proving target is a headless `bevy_ecs` app that projects a recorded world, accepts intents, and passes the §4 replay oracle under soak. 2D follows as the first *presenter* target (smallest surface that exercises the full provider face: one render surface, audio, gamepad/keyboard input). 3D is explicitly not a proving target: it adds asset and rendering risk while proving nothing about the incorporation itself.

## Implementation slicing (for the follow-on issues, not this design)

1. **Bridge crate skeleton + schema:** `id-bevy-bridge` on the #3447 seams, `IdEntityMap`, predicate classification, fail-closed projection of a static journal fixture.
2. **Journal tail + `JournalSet`:** position-ordered application, lag budget, intent submission round-trip against a hosted world.
3. **Replay oracle:** recorded-journal soak test proving §4's property; wired as the Bevy-bump acceptance gate.
4. **Presenter-client reference app (2D):** joins a hosted world, declares the §5 provider manifest, predicted-presentation reconciliation demo.
5. **Host posture:** embedded append gate/journal lifecycle, with the host's own Bevy side consuming the same projection.

Each slice files as its own implementation issue referencing this design; per the standing rule, this design issue stays open until Drew reviews the design or the first implementation issue supersedes it — a merged design PR is not, by itself, closure.

## Non-goals

- Implementing any of the bridge in this design, or choosing a game/rendering feature set.
- Bevy editor integration (noted in #5931 §4.1 as in development and unverified in detail).
- Replacing or wrapping lightyear/`bevy_replicon` for non-ID game networking.
- Fyrox/Godot/macroquad incorporation (#5931 §4.4): the mapping in §1 is Bevy-shaped because Bevy's ECS is the entity-model match; other engines are separate designs if ever wanted.
