# Design: client surfaces parity — scripting/API, agent, and CLI front doors over one query model

- Date: 2026-11-08
- Status: **decision record** — the front-door shape is decided
  (§2–§7). Everything this record needs from the query model itself
  is expressed as a requirement on the parent design's decomposition
  item 1 (the query language/shape), so this record does not guess
  or constrain the query syntax that item owns.
- Issue: [#5820](https://github.com/developing-today/code/issues/5820),
  follow-on of [#5675](https://github.com/developing-today/code/issues/5675)
  (ID query surfaces — its decomposition item 5 is this record),
  programme epic #2056. The tables being queried: #2048.
- Parent decisions consumed, not re-decided: #5675 fixes the
  filtering model and its defaults, the owner-override boundary
  (classification is policy; encryption is a cryptographic boundary
  policy never outranks), surface parity as a principle, the
  read-only-by-design query surface, and the pagination/result
  rules (server-side shaping, stable cursors, truncation honesty,
  cost limits). This record decides **how the three front doors
  expose that one model and how parity between them is proven** —
  it changes none of the parent's decisions. **Parent-decision
  impact: none** — where a front-door convenience would change a
  parent decision (a CLI-only bypass, an agent-only endpoint), this
  record rejects the convenience (§5) rather than forking the
  parent; a genuine conflict is a #5675-level amendment, recorded
  there, never worked around in a front door.

## 1. The one idea everything follows from

There is exactly **one query model and one executor**. A query is a
single canonical query document (the shape decomposition item 1 of
#5675 defines); it is executed by one server-side executor — embedded
for a local target, behind the ID transport endpoint for a remote
target, the same code path either way. The scripting/API surface,
the agent surface, and the human CLI are **adapters that produce
that document and render its one result envelope**. A front door
may differ in how a human or a program _expresses_ a query and how
a result is _presented_; it may never differ in what a query means,
what it may reach, or what its result contains. Parity is therefore
not a documentation promise: it is a conformance property of three
adapters against one executor, and §4 makes it a tested one.

## 2. Decision: the canonical query document is the only interface

1. **One document, one envelope.** Every front door compiles its
   input to the canonical query document (table, filters,
   projection, ordering, cursor, limits, target, identity context)
   and consumes the canonical result envelope (rows, field metadata,
   cursor continuation, withheld/truncation signalling, error
   object). There is no second, door-specific wire shape for either
   direction.
2. **Identity rides the document's context, identically on every
   door.** The querying identity and its clearance are established
   by the transport/session, never asserted by door-supplied fields;
   no door may attach, widen, or strip identity. The owner override
   (parent §3) is an explicit field of the query document — present
   in the schema for all three doors, defaulted off, audited by the
   executor — never a door-local flag the executor cannot see.
3. **The executor is the only filtering point.** Doors never filter,
   redact, sort, or paginate result data client-side. A door that
   needs a narrower answer issues a narrower query. (This is the
   front-door restatement of the parent's "filtering is not
   client-side cosmetics", fixed here so no adapter can quietly
   grow a second, divergent filter.)
4. **Versioning.** The query document and the envelope carry the
   query-model version. Doors declare the model versions they
   conform to (§4); a door that cannot express a document at the
   negotiated version refuses it with the shared version error —
   it never approximates the query in a dialect of its own.

## 3. Decision: the three front doors

### 3.1 Scripting / API surface — the reference door

- A client library plus the wire form of the canonical document
  (JSON over the ID transport for remote targets; the same document
  passed in-process for local targets). Synchronous request/reply;
  a query is a value a script can construct, store, diff, and
  replay verbatim.
- This door is the **reference adapter**: the conformance corpus
  (§4) is authored against it, and the other doors are proven
  equivalent to it. Reference status is about testing, not
  privilege — it reaches exactly what its identity's clearance
  reaches, like every door.

### 3.2 Agent surface — the same document, machine-first rendering

- Agents call the executor through a structured tool/function
  surface whose input schema **is** the canonical query document
  and whose output **is** the canonical result envelope. There are
  no agent-only query endpoints, no agent-only fields, and no
  summarised-or-sampled result variant: an agent receives the same
  rows, the same withheld signalling, and the same cursors a script
  would.
- Errors are the shared error taxonomy (§6), machine-readable and
  unmodified. The agent door never converts a denial, a withheld
  notice, or a truncation into an empty successful result.
- Non-interactive by construction (parent §4): the agent door has
  no prompts, confirmations, or interactive override flow. Anything
  that would require one — above all the owner override — is
  available to an agent only when its session identity already
  carries it as the explicit document field of §2.2; the door
  itself cannot ask a human to widen a query mid-flight.

### 3.3 Human CLI — a thin door, human only at the edge

- The CLI is a **thin client over the scripting/API library**, not
  a separate implementation: its flags and arguments map 1:1 onto
  fields of the canonical query document, and it sends the document
  the library builds. A query that cannot be expressed as CLI flags
  can be given as a query-document file, executed unchanged — the
  CLI never has a query the other doors cannot run.
- Human rendering (tables, colour, paging to a terminal) happens
  **after** the canonical envelope arrives and touches presentation
  only. `--json` output is the canonical envelope itself, so a
  human can pipe the CLI into the same tooling a script uses and
  get the same bytes a script would (modulo key ordering the
  envelope spec fixes).
- The CLI gets no local magic: running against a local server goes
  through the same executor, identity, and filtering as any door.
  The owner override is spelled the same explicit way as on the
  other doors (a deliberate flag that sets the §2.2 document field
  and is echoed in the audit line the CLI prints), never implied by
  "you are on the machine".

## 4. Decision: parity is a tested property (the conformance corpus)

1. **One corpus, every door, both targets.** A shared conformance
   corpus of query/result cases — authored once, versioned with the
   query model — is executed in CI through **all three doors**
   against **both** a local and a remote fixture server. A door
   ships only while its corpus run is green; adding a door or a
   query-model version means adding its corpus run, not writing a
   parity claim.
2. **What equivalence means.** For each corpus case, the three
   doors' canonical envelopes must be equal under the envelope's
   own equality rules: same rows and fields, same order, same
   cursor continuations, same withheld/truncation signalling, same
   error code for failure cases. The CLI's human rendering is
   exempt from byte equality and from nothing else — its `--json`
   form is in the corpus like any other door's output.
3. **The corpus covers the parity-sensitive cases by construction:**
   filtered remote queries at several clearance levels (including
   withheld-row and withheld-field signalling), owner override on
   and off (and refused where the parent's encryption boundary
   applies), cursor continuation **across doors** (§7, P3),
   truncation and server cost-limit refusals, read-only enforcement
   (a mutating attempt fails identically everywhere), and the full
   error taxonomy of §6.
4. **Divergence is a defect in the door, never a feature.** A case
   where a door legitimately cannot match (a rendering-only CLI
   table width, say) is recorded as a named, reviewed exemption in
   the corpus itself — visible, counted, and limited to
   presentation. Semantic exemptions do not exist: a door that
   cannot produce the canonical outcome for a case does not ship
   that case.
5. **Oracle.** The corpus's expected envelopes are the oracle
   (golden corpus in the testing doctrine's sense): they are
   derived from the query model's specification, not captured from
   whichever door was built first, so the corpus can catch the
   reference door being wrong too.

## 5. Rejected alternatives

- **A dialect per door** (SQL for the CLI, JSON for agents, a DSL
  for scripts): three languages drift into three semantics; parity
  becomes translation faithfulness, which is unprovable in the
  corpus sense of §4 because there is no single document to
  compare. Rejected — expression may vary, the compiled document
  may not.
- **CLI as an independent implementation** talking to the server
  directly: doubles the executor's client surface and guarantees
  slow divergence (the historical failure this ticket exists to
  pre-empt). The CLI is a renderer over the reference library.
- **Agent convenience endpoints** (pre-filtered summaries, sampled
  results, an agent-only "search everything" verb): they hand
  agents a different — usually broader or dishonestly narrower —
  view than their identity's clearance defines, and they break
  withheld-result honesty. Agents get the model, not a shortcut.
- **Parity by documentation and code review** ("the doors are
  specified to behave the same"): unverifiable, and the first
  divergence ships silently. Parity exists only as the §4 corpus.
- **Client-side result shaping in the doors** (fetch wide, filter /
  sort / paginate locally): defeats server-side filtering, cursor
  stability, and cost limits at once — three parent decisions
  broken by one convenience.

## 6. Decision: one error taxonomy, no door translations

- Executor errors carry a stable code from one taxonomy (denied by
  clearance, withheld signalling is _not_ an error, invalid query,
  version mismatch, cost limit, target unreachable, read-only
  violation). Every door surfaces the code unchanged: the API
  returns it, the agent tool returns it, and the CLI maps it
  deterministically to an exit status **in addition to** printing
  the code — the mapping is a published table in the corpus, so
  all three mappings are tested, not asserted.
- No door invents errors the executor did not produce, and none
  swallows one: a failed query is never an empty result on any
  door (the error-path restatement of truncation honesty).

## 7. Invariants implementation must hold

- **P1 — One model.** Every door compiles to the same canonical
  query document and consumes the same result envelope; there is
  no door-specific query semantics anywhere in the system.
- **P2 — No door widens access.** Identity and clearance are
  established outside the doors and are identical across them;
  the owner override is one explicit, audited document field,
  spelled on every door, bounded exactly as the parent fixes
  (own server, unencrypted data only).
- **P3 — Cursors are door-independent.** A cursor minted through
  one door continues through any other door against the same
  target; pagination state lives in the envelope, never in a
  door's session.
- **P4 — Honesty survives every door.** Withheld, truncated, and
  cost-limited outcomes are signalled identically on all doors;
  no door renders a partial answer as complete or a denial as
  emptiness.
- **P5 — Read-only everywhere.** No front door can mutate through
  the query surface. A mutating surface, if the parent's separate
  design ever admits one, arrives on all doors in the same release
  with the same permissions and audit — or on none.
- **P6 — Conformance gates shipping.** A door (or a query-model
  version) whose §4 corpus run is not green does not ship; parity
  exemptions are presentation-only, named, and counted in the
  corpus.
- **P7 — The CLI is replaceable.** Deleting the CLI loses only
  human rendering: every query it could run is runnable verbatim
  through the scripting/API door from the document the CLI built.
- **P8 — Errors are the executor's.** One taxonomy, surfaced
  unchanged by every door; door-specific error inventions are
  defects under §6.

## 8. What this record does not do

It does not define the query language/shape itself (#5675
decomposition item 1 — this record states the adapter requirements
it must satisfy: a compilable canonical document, an envelope with
cursor and honesty signalling, a version field), the classification
model (item 2), filtered execution and audit internals (item 3),
the override mechanics beyond the door-visible field (item 4), or
result-shaping rules beyond door behaviour (item 6). Implementation
issues, when filed, cite the invariant (§7) or section (§2–§6) they
realise; the conformance corpus (§4) is filed as the first
implementation issue once item 1 fixes the document shape, because
the corpus cannot be authored against a shape that does not yet
exist — that ordering is deliberate, and this record is its
tracking home until then.
