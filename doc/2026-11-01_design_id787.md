## 1. Decision to be made

Where should kitty negotiation, stream assembly, richer key semantics and browser
parity live, while keeping the existing durable `Input` event unchanged?

**Recommendation:** negotiate only on a supported, explicitly opted-in raw
terminal session; frame complete input tokens before durable submission; carry
the original key bytes through existing `input.data_hex`; decode them through an
additive Roc rich-key API; give the browser an equivalent, separately selected
encoder. Start with **disambiguation only**, not key-release/all-key reporting.
Preserve the legacy encoder, parser meanings and default session behavior.

The opt-in is an initial rollout safeguard for old compiled guests, not a claim
that terminal capability proves guest compatibility. No new durable event,
guest import, structured session key frame or automatic guest discovery is needed.

## The shape

```text
F13.4 in-band detection ──► raw connection's keyboard mode/lifecycle
                                  │ negotiated keys
SSH bytes ─► bounded token assembler / control-reply filter
                                  │ complete UTF-8 key token
browser richer encoder ────────────┤
                                  ▼
                    existing input { data_hex }
                    existing authorization + bounds
                    durable Input(Vec<u8>) / replay
                                  ▼
                    Roc rich decoder → application
                    Key.parse compatibility projection
```

This is a **proposed** architecture. Current raw SSH forwards chunks directly,
and the browser currently uses only its legacy encoder (evidence below).

## 3. Viable options and trade-offs

| Option | Benefit | Cost / reason not selected |
| --- | --- | --- |
| A. Keep legacy input, add an Escape timeout only | Least change; old compiled guests work | Cannot remove Escape/Alt ambiguity; cannot meet #787's richer-key parity criterion. |
| B. Enable kitty, add cases only to `Key.parse` | Small apparent patch; no wire schema change | Split CSI and UTF-8 remain broken before parsing; modifier information has no place in the existing union; old binaries still cannot decode it (evidence §2). |
| **C. Adapter framing + additive rich decoding + equivalent browser encoding** | Meets the issue on existing byte Input; shared testable semantics; explicit fallback | Requires bounded per-connection state and coordinated rollout; selected. |
| D. Structured key ClientFrame / new durable key event | Convenient typed host interface; potentially broad native-client reuse | New protocol compatibility surface and/or journal/ABI migration. Unnecessary for opaque byte payloads, and a new durable event conflicts with #787. Defer typed session-frame design, not this issue's bytes. |

Within C, full press/repeat/release, alternate physical keys and associated text
are viable future profiles, but increase browser keyup/focus-loss and consumer
requirements. Disambiguation alone meets this issue's stated need; enabling more
flags before their semantics exist buys no acceptance coverage. These are proposed
scope choices, not statements that the existing code implements a kitty profile.

## 4. Recommended behavior and interfaces

### 4.1 Minimal profile and richer event

Define a named `kitty-disambiguate-v1` profile. Proposed negotiation is push
disambiguation flag 1 (`ESC [ > 1 u`), with one matching pop (`ESC [ < 1 u`) on
exit. F13.4 owns the support query (`CSI ? u`) and reply classification. Do not
interpret the issue's shorthand `CSI > u` as unconditional enablement.
The implementation's first slice must check these proposed wire values and key
tables against the upstream kitty specification and captured terminal fixtures;
the issue and current source do not themselves specify the numeric table.

Request **no** event-type, all-keys, alternate-key or associated-text flags.
Keyboard auto-repeat remains another actionable press, as today's keydown-only
browser path does (`web/src/world.ts:257-261`). Do not add keyup listeners.

Add `Key.parse_events : Str -> List(KeyEvent)` alongside `Key.parse`. Proposed
event shape: `{key: NamedKey | UnicodeScalar, modifiers: modifier-set,
kind: Press}` plus an explicit Unknown representation retaining source text.
Support existing named keys, CSI-u Unicode/control identities, and the profile's
modified CSI letter/tilde forms. Parse parameters with checked numeric bounds;
unsupported flags, extra fields, event kinds or key numbers yield Unknown, never
a guessed actionable key. Physical scan codes and text-composition events are
not claimed by this logical-key API.

`Key.parse` keeps all existing legacy expectations unchanged, including the
modified-arrow Unknown expectation. For newly recognized kitty sequences it may
project unmodified named/printable keys and Ctrl+letter to existing tags; keys
with unrepresentable modifiers remain Unknown. Never erase Alt/Shift/Ctrl merely
to make an old application act. `parse_events` is the authoritative rich API;
the parity oracle compares it, not lossy projections.

Normalize a printable scalar to its resulting Unicode value with Shift consumed
into that value (e.g. uppercase `A`), preserving Alt/Ctrl; special-key Shift
remains a modifier. This is a proposed logical-text policy to make browser `key`
and terminal input comparable without requesting physical/alternate-key data.
Legacy text cannot prove physical Shift state; do not invent it.

### 4.2 Framing belongs before journaling

Introduce a bounded assembler on each **active raw connection**, before
`raw_frame`. Retain incomplete UTF-8, CSI and SS3 across SSH callbacks; emit one
complete key token per `input.data_hex`, independent of transport partitions.
Do not parse keys into a new host event or rewrite accepted token bytes. Plain
text emits complete Unicode scalars. This intentionally changes active-mode
event grouping, not the durable event type; applications that count updates
rather than keys must explicitly opt in. Inactive legacy sessions keep their
current forwarding behavior, including its known split-input limitation.

Proposed safety defaults: at most 256 bytes per pending token, bounded by the
existing input maximum as well; 5-second incomplete-token deadline; detection
budget owned by F13.4 rather than a second independent timer. On invalid UTF-8,
overlong tokens, incomplete active tokens at EOF/deadline, or input queue loss:
diagnose and close the active session, restoring protocol state if possible.
Do not turn a truncated escape tail into ordinary application text. Tune limits
only with fragmentation/latency fixtures; no unbounded buffer or replacement
character that silently changes a command. This bounds memory to O(connections).

The current `try_send` path can drop a whole chunk (`src/world_ssh.rs:534-548`).
An active assembler must receive a fatal overflow signal or the connection must
close there; continuing after a missing prefix is not safe resynchronization.
Do not put partial decoding state in a shared guest model: multiplayer callers
would otherwise need participant-keyed, snapshot/replay-aware pending buffers.

### 4.3 Detection, ownership and restoration

Proposed state machine:

```text
Legacy (default)
  explicit rich opt-in + raw session → Detecting (F13.4)
  supported → push profile → verify enabled flag → Active
  unsupported / timeout → Legacy (no push left outstanding)
Active → normal exit / refused join / error → pop owned push → Closed
```

Use F13.4's connection-local control-reply demultiplexer. Consume only recognized
replies to outstanding probes, with bounded state and one owner; preserve keys
coalesced with replies in order. Drain pre-activation legacy keystrokes as legacy
before switching modes; never retroactively decode them as kitty. After a push,
verify with the profile query before admitting active keys; failure pops the
owned push and falls back. Query responses are capability evidence, not authority.
Unsolicited or malformed controls follow bounded unknown-token handling, not an
unrestricted reply filter that swallows arbitrary keys.

Track whether a push was sent successfully, including failure before verification,
and pop only that owned stack entry. Coordinate teardown with the existing
alternate-screen restoration and repeat refused-join errors after restoration
(`src/world_ssh.rs:739-768`). Normal return, admission failure, write/read error,
EOF and cancellation all need a teardown path. A dead transport cannot guarantee
delivery of reset bytes; document best-effort cleanup rather than claiming it.
Never push/pop for `cmd:`, explorer or framed exec channels.

The terminal-facing owner is `SshIo` today, not `SshFrameIo`. SSH-over-iroh uses
the same raw presentation adapter; it must not add another negotiation layer.
`id world join` is currently line-oriented (`src/commands/world.rs:1754-1809`);
making it a local raw terminal presenter is outside #787. F13.4 should expose a
transport-neutral detection result so future raw presenters reuse this profile.

### 4.4 Browser parity and compatibility rollout

Keep `terminalBytesForKey` and its tests as the default legacy path. Add a
separate rich encoder selected by an explicit **per-connection** keyboard option,
not by silently replacing that function. Add the equivalent opt-in to raw SSH
server configuration; both defaults remain legacy. These selectors are new
implementation work, not fields that exist in today's shell contract. They are
adapter-local configuration and require no new ClientFrame.

The operator opts in only for a world compiled with the extended Key module (or
an equivalent decoder). Since no guest input-profile advertisement exists in the
cited contract, do not auto-enable globally merely because a terminal supports
kitty. A future automatic rollout needs a separate guest-compatibility mechanism.
Browser refresh/new SSH connection returns to the configured default; changing
world/program compatibility requires reconnecting in the appropriate mode.

Rich browser encoding handles the same named keys and Unicode scalars as the
terminal profile, with CSI-u for ambiguous controls and explicit modifiers.
Parity means **equal decoded events**, not necessarily identical byte strings:
plain UTF-8 and a permitted CSI-u scalar may describe the same logical key.
Keep Meta/OS shortcuts and Dead/Process/Unidentified excluded. Preserve AltGr
printable-as-text behavior; do not reinterpret Ctrl+Alt text as a command.
Multi-scalar committed text remains UTF-8 text, not a fabricated physical key.
IME expansion, Meta capture and additional function keys are not first-slice
requirements. Paste and the manual text form stay on their existing paths (§2).

## 5. Invariants and implementation acceptance

1. **Issue parity:** shared fixtures feed real terminal bytes and browser events
   into the **actual Roc `parse_events` decoder** and compare full logical events.
   A TypeScript encoder comparing against itself is insufficient.
2. **Escape versus Alt:** active-mode Escape, Alt+x, Alt+Escape and an Escape
   followed by x are distinct; active decoding does not use an Escape timeout to
   choose between them. Legacy fallback retains its ambiguity and is labeled so.
3. **Richer controls:** distinguish Tab/Ctrl+i and Enter/Ctrl+m; test Ctrl/Alt/Shift
   combinations of the existing named keys, Unicode/emoji, shifted text and AltGr.
   Unknown protocol forms never become unmodified application actions.
4. **Chunking:** every split point of UTF-8, CSI-u, modified CSI/SS3 and reply+key
   streams, plus multiple coalesced keys, produces the same ordered active tokens
   as unsplit input within the assembly deadline. Interleaved connections cannot
   mix pending state. Overflow/malformed/timeout/EOF paths are bounded and tested.
5. **No control-plane journal entries:** probes/replies/push/pop produce zero
   durable Input events, no program update and no input-use consumption. A real
   accepted key still crosses existing scope/size checks; presentation state is
   never journaled. Verify exact key bytes survive persistence and replay.
6. **No schema migration:** `Input(Vec<u8>)`, input/paste ClientFrame shapes,
   journal version and guest ABI remain unchanged. Replaying old bytes with the
   same old module remains unchanged; recompiling a module with new key semantics
   is an explicit program change, not promised historical semantic equivalence.
7. **Lifecycle:** one push/pop pair on supported opted-in raw sessions; no push
   on unsupported/timed-out detection or excluded modes. Restore on accepted
   and refused sessions, failures and cancellation; test fragmented/late replies.
8. **Compatibility:** all existing Key expectations and browser legacy modifier
   tests pass. Bundled screen/chat/territory examples still act once per press;
   old compiled guests stay on legacy by default. No new release-driven actions.

## 7. Questions, risks and non-goals

**Questions genuinely needing Drew: none.** The issue already supplies the
product choice (kitty parity without a durable-event change). Minimal feature
flags, explicit initial opt-in and additive APIs are reversible engineering
defaults. F13.4's as-yet-unmade API is an integration dependency, not a reason to
leave this design unfinished: the required input is a connection-local supported
profile plus a bounded control-reply classifier. If it differs, adapt E, not the
journal or guest ABI. Numeric wire validation is an implementation prerequisite,
not a question for Drew.

Principal risks are split-input corruption, stale capability replies, dropped
queue chunks, old compiled guest compatibility and silent test skips. Sections
4–6 give each a containment rule and observable check. Initial opt-in sacrifices
automatic adoption deliberately; do not mark it as automatic capability rollout.

Non-goals: implementing F13.4 rendering/detection here, graphics/sixel, native
shells, command toggles, focus frames, guest-profile discovery, physical-key/IME
APIs, release/all-key profiles, journal migration or changing other issues.
