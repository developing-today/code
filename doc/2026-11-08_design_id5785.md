# Design: output safety beyond plain text — markup contexts, safe-plain as a user choice, ingest without evaluation, and the ANSI/OSC disposition

- Date: 2026-11-08
- Status: **design — decision record. This document is the deliverable of #5785; the issue closes when this record lands, per its acceptance criteria.**
- Issue: [#5785](https://github.com/developing-today/code/issues/5785).
- Predecessor: [#3455](https://github.com/developing-today/code/issues/3455) (closed) settled the plain-text contract — one shared Unicode 16 Cf set, escaped at render — in `doc/2026-11-01_design_id3455.md`. This record covers the four things #3455 explicitly left open.
- Compatibility: [#5679](https://github.com/developing-today/code/issues/5679) and its children #5849–#5855 own the semantic markup **vocabulary** and per-target styling. This record supplies the encoding/safety **invariants** those designs consume; it does not re-decide their vocabulary (see §5).
- Scope: `pkgs/id` surfaces that emit markup or terminal control carrying data values. Base commit for every file:line citation below: `99f657e08a` (main, 2026-11-08). No runtime behaviour changes in this record; any concrete gap found against these rules gets its own filed issue.

## Decision summary

1. **Markup contexts (§1):** a data value may enter markup only in a text, quoted-attribute, or sanitized-URL context, each with its named encoding rule below. A data value must **never** enter a script context.
2. **Safe-plain (§2):** safe-plain is a **user-selected rendering mode**, per-client, opt-in — it is not a data classification and is never stored on the data. It composes with #3455: safe-plain output is plain-contract output (Cf/Cc escaped at render) with markup dropped entirely.
3. **Ingest (§3):** one rule — **stored or forwarded data is never evaluated downstream**: no template evaluation, no markup rendering outside §1, no terminal emission outside #3455.
4. **ANSI/OSC (§4):** terminal escape **sequences** are in scope for the output-safety contract but are **not** part of the Cf character contract. They are handled at the sequence level by terminal adapters, as the code already does; the Cf set is not extended.

## 1. Which surfaces may emit markup carrying data values, and the per-context rules

Only the `pkgs/id` web surfaces emit markup today (inventory, §6). The rules:

- **Text context** (element content): the value is encoded with the crate's one HTML text escaper, `html_escape` — `&`, `<`, `>`, `"`, `'` are replaced (`pkgs/id/src/web/templates.rs:1166-1172`). Call sites already follow this uniformly, e.g. every interpolated field in the explore views is passed through it (`pkgs/id/src/web/explore.rs:221-374`), and the routes module carries an inline twin for its own templates (`pkgs/id/src/web/routes.rs:780`). New markup emitters must use this escaper for every data value in text context; raw interpolation of a data value into markup is a defect against this record.
- **Attribute context**: data values may appear only inside **quoted** attributes, encoded with the same `html_escape` set (which includes both quote characters, `templates.rs:1170-1171`). Unquoted attributes carrying data values are prohibited — the escaper's guarantees do not extend to them.
- **URL context** (`href`/`src` values): text/attribute escaping is **not sufficient** for URLs — a `javascript:` value survives entity escaping intact. URL values must pass the link sanitizer, `sanitize_link_url`, which neutralizes unsafe schemes including tab-obfuscated ones (`pkgs/id/src/web/markdown.rs:3984-4016`, applied on every link emit path, e.g. `markdown.rs:2992`, `markdown.rs:5046-5047`, `markdown.rs:5271`, `markdown.rs:5616`). This is the one URL rule; no surface may emit a data-carried URL that has not passed it.
- **Script context**: **prohibited, without exception.** No data value is ever interpolated into a `<script>` body, an event-handler attribute, or a `javascript:` URL (the URL case is additionally closed by the sanitizer rule above). There is no encoding in this codebase that makes a script-context interpolation safe, so the contract is exclusion, not escaping.
- **Blob serving is not a markup context**: stored blobs are served only under a passive-type allowlist with `nosniff` and a sandboxing CSP; active types (`text/html`, CSS, JavaScript, JSON, XML) are downgraded to `application/octet-stream` and forced to attachment download (`pkgs/id/src/web/routes.rs:920-961`, `routes.rs:1021-1039`). A stored value therefore never becomes markup in this origin by being served.

## 2. Safe-plain: a user-selected rendering mode

**Decision: safe-plain is a rendering mode the user selects, not a property of the data.**

- **Mode, not classification.** Nothing about a value makes it "safe-plain data"; confidentiality classification is a separate model (#5675) and is explicitly out of scope here. Safe-plain describes how a client renders, never what a value is. It is therefore never written to storage, never travels with the data, and one client's choice cannot affect another client's rendering of the same value.
- **Semantics**: in safe-plain mode a surface renders every data value as text only — no markup is emitted for the value, links are shown as their text plus the literal URL string (already sanitized per §1 if rendered at all), and embedded raw HTML in source content is displayed as source, never rendered.
- **Default and scope**: the default is the surface's current rendering (rich/markdown as today); safe-plain is **opt-in, per-client**. Scope is the client (the user's own viewer/editor), not per-world and not per-field: a per-world or per-field flag would have to be stored with shared data, contradicting the not-a-classification rule, and would let a data author dictate (or strip) another reader's protection. The existing editor `ContentMode::Plain` is a per-file _editing_ mode for plain-text files (`pkgs/id/src/web/content_mode.rs:10-18`) and is **not** this toggle; the two must not be conflated — safe-plain governs rendering of values on any surface, ContentMode governs how a file is edited.
- **Composition with #3455**: safe-plain output is a strict subset of the #3455 plain contract. Values rendered in safe-plain mode pass through the same render-time escaping #3455 settled (Cc, Cf, and U+2028/U+2029 escaped by the plain renderers, `pkgs/id/src/commands/text.rs:43-81,104-133`); safe-plain adds "no markup" on top, it does not replace or weaken the character contract. Today's markdown pipeline already treats raw HTML blocks as literal source rather than rendering them (`pkgs/id/src/web/markdown.rs:324-333` — the HTML-block tracker exists so raw HTML interiors stay literal content), which is the behaviour safe-plain generalizes to all values.

## 3. The ingest rule: stored or forwarded data is never evaluated downstream

**One rule, binding on every ingest path (uploads, sync, federation, bridge/forwarding): stored or forwarded data is data. It is never evaluated downstream** — concretely:

- no template evaluation of stored values;
- no markup rendering of stored values outside the §1 contexts (and §1's blob rule is part of this: a served blob is a download or a passive render, never active content);
- no terminal emission of stored values outside the #3455 plain contract (values reach a terminal only through renderers that escape per #3455, or through the sequence-filtering adapters of §4).

Current code already implements this rule at the audited points, and this record makes it the stated contract those points are audited against: uploaded image bytes are verified against their declared type rather than trusted (`pkgs/id/src/web/routes.rs:87-94`, `routes.rs:2090-2097`), upload types are allowlisted (`routes.rs:2032-2047`), and blob serving downgrades active types (`routes.rs:920-961`). A new ingest path that forwards a value into any evaluation context not listed in §1/§4 is a defect against this record, to be filed as its own issue.

## 4. ANSI/OSC disposition: in the output contract, out of the Cf contract

**Decision: escape sequences are a sequence-level concern, handled by terminal adapters; the Cf character set is not extended to cover them.**

Evidence and reasoning:

- A Cf character is a single scalar; an ANSI/OSC sequence is a multi-byte protocol unit introduced by ESC (a Cc control). Folding sequences into the character contract would blur the exact boundary #3455 drew, and the code already handles the two levels in two places: the plain renderers escape characters (`text.rs:81`), while terminal paths demultiplex sequences — the SSH line buffer runs a full escape-state machine that consumes CSI, OSC (terminated by BEL or ST), and string sequences byte-by-byte so they never reach the line (`pkgs/id/src/world_ssh.rs:1367-1440`).
- The world presentation layer makes the split structural: its text projection rejects any line containing a control character (`pkgs/id/crates/id-core/src/world_presentation.rs:86-116`), guests can never supply escapes (`world_presentation.rs:5-13`), and `render_ansi` emits only adapter-generated sequences from validated numeric style fields over control-free glyphs (`world_presentation.rs:638-673`, `world_presentation.rs:751`). The only escape constants on the SSH path are adapter-generated (`pkgs/id/src/world_ssh.rs:80-82`), and world data is passed through `terminal_text`, which drops control and format characters, before framing (`world_ssh.rs:986-1003`, `world_ssh.rs:1919-1924`).
- **Recorded residual** (accepted, not silently passed over): `terminal_text` strips the ESC byte but leaves an OSC payload as ordinary visible text — its own test pins `a\x1b]52;c;AAAA\x07b` rendering as the inert text `a]52;c;AAAAb` (`world_ssh.rs:3149-3154`). That is safe under this contract (the payload cannot act on the terminal once ESC and the remaining controls are gone) though cosmetically noisy. Any future tightening (dropping OSC payloads wholesale in `terminal_text`) is a behaviour change to file separately; it is not required by the safety contract.
- Terminal _probing_ (capability detection that emits queries and demultiplexes replies) is likewise an adapter-level, sequence-level mechanism and stays out of the character contract; it is tracked by its own work (#786 Phase 2, task 8067), not by this record.

## 5. Compatibility with #5679 and #5849–#5855

#5679 (OPEN) designs the semantic markup vocabulary and style-override mapping for programs-as-websites; its children #5849–#5855 cover the vocabulary per target. This record and that family are complementary and non-overlapping:

- **This record owns**: which contexts a data value may enter, and the encoding/sanitization rule per context (§1); safe-plain's semantics (§2); the ingest no-evaluation rule (§3); the ANSI/OSC level split (§4).
- **#5679's family owns**: which elements/attributes exist, what they mean, and how style overrides map per target.
- The vocabulary designs **consume** §1 as an invariant: any element or attribute the vocabulary introduces that carries a data value inherits the §1 rule for its context (text, quoted-attribute, sanitized-URL; never script). Nothing in this record adds, removes, or renames any vocabulary element, and nothing in the vocabulary family may relax a §1 rule — a vocabulary need that appears to require raw data interpolation is escalated back to this contract, not resolved locally.

## 7. What this record does not do

- It changes no runtime code and introduces no sanitizer; §1 restates the rules the existing escaper/sanitizer already implement, as the contract future emitters are reviewed against.
- It does not re-decide #5679's vocabulary or styling (§5), and does not touch the confidentiality classification model (#5675) beyond distinguishing it from output encoding (§2).
- Implementation gaps discovered later against §1–§4 are filed as concrete issues citing this record — they are not reopenings of #5785.
