## Decision to make

Choose the v1 contract for a forum-like experience on ID: its object graph and identity, theme and rendering boundary, moderation semantics, and how embedded games and succession forks fit—without making a central account database, a server the authority over every copy, or an unsafe code-execution surface.

## Recommendation

Build **public, registration-free boards as signed object graphs**, with immutable/hash-linked posts and explicit superseding versions; separate host availability, board moderation, and personal filtering; make themes data-only tokens/layout/assets; and represent embedded games as package-pinned graph references with signed async turns and forkable save points. Start from direct board references and replicate the same objects between willing hosts. Defer closed/encrypted boards, live-session hosting, executable themes, and ownerless-board recovery/quorum.

This is the smallest design that satisfies the nostalgia-as-a-feature request while retaining the graph as the authority. It uses the existing signed-event substrate rather than inventing a parallel identity or content-addressing system. Its sharp limit is explicit: the design does not promise deletion from every host, real-time game hosting, or player-signed evidence from today's host-owned world journal.

## Options and trade-offs

| Option | Benefits | Costs / failure modes | Verdict |
|---|---|---|---|
| **A. Conventional hosted forum:** central accounts, mutable database rows, server-defined theme templates, server-owned moderation/deletion. | Familiar phpBB model; easiest conventional admin and synchronous UX. | Registration reappears; one host becomes canonical; moderation can erase or rewrite the only history; arbitrary templates are unsafe and do not port to non-web clients. | Reject for v1: nostalgia can inform the experience, not replace the graph underneath. |
| **B. Signed graph with view-layer moderation (recommended):** public board root and child objects, key-based identity, immutable history, data-only themes, async games, and opt-in replication. | Portable board identity; author-attributed history; works offline; forks and theme lineage are native; one object set can have different honest views. | Requires clients to compute projections; no universal takedown; key loss is real; public objects are not confidential; real-time games need additional infrastructure. | Choose. Keep v1 public and bounded; make every non-goal explicit. |
| **C. Hosted federation with a canonical board operator:** signed posts replicated outward, but one operator owns the board database and has final say. | Easier abuse response and consistent presentation than B; more familiar hosted operations. | Federation is only a mirror, not portability; operator authority conflicts with the signed-root model; unclear what another host's copy means after moderation or succession. | Reject as the core model. A host can choose what it serves, but that must not be mislabeled as global board authority. |

## V1 model decisions

### 1. Identity and board/object graph

- **Author identity is the verifying key that signed the event.** No account, password, email, username reservation, or board registration. The author may publish a profile claim; a reader's petname remains local. Two keys may use the same display name, and clients show a key-derived disambiguator.
- **Board identity is a stable board ID plus its signed root lineage.** Derive the board ID from `(creator signing key, random nonce)`; the root event hash is the shareable address. The creator's key signs the initial Board object; subsequent root versions cite the prior version. A board link resolves by object reference, not by the host that first served it.
- V1 object vocabulary: `Board`, `Rules`, optional `Forum`, `Thread`, `Post`, `Attachment`, optional self-issued `Membership`, `RoleAttestation`, `ModerationAction`, `Theme`, `GamePost`, `GameTurn`, `SavePoint`, `Handoff`, and `Fork`. Each is a typed, signed, hash-linked event. The schema must use existing chain signing/verification and preserve the signed author; a second, board-specific account/signature system is out of scope.
- Posts and game turns are append-only. Editing a post creates a signed superseding version; author deletion is a tombstone request, not byte erasure. Thread/post order is a view rule, with explicit parent/reply refs. Each thread pins the rules version under which it opened; rule changes apply to new threads and do not rewrite existing threads' rules. Attachments are content-addressed blobs referenced from posts, not inline media bytes.
- Membership is optional and self-issued (“I follow/contribute to this board”), not approval by an operator. Role attestations are board-scoped and signed by the current authority; a role on one board has no authority on another.

### 2. Themes and rendering

- A Theme is a signed, versioned object with `parent_theme`, a finite token set, a small layout enum, and content-addressed asset refs. Font refs are content hashes, not remote URLs, so rendering does not fetch mutable external resources. Applying a theme is a board reference; changing it creates a child theme, preserving attribution and fork lineage.
- **No custom HTML, JavaScript, templates, or arbitrary CSS in v1.** A finite data schema can be rendered by web and terminal clients; executable styling would create a code and portability boundary. The richer CSS escape hatch floated in the #2052 sketch is not adopted.
- The same board content remains readable without a theme or on clients that do not implement a layout option. Unknown presentation fields are ignored or produce a safe fallback; they do not affect signed content or game state. This follows the existing portable presentation boundary: guests emit validated data, never HTML/CSS/terminal escapes (`pkgs/id/src/world_presentation.rs:1-6, 14-29`).

### 3. Moderation and the three views

Moderation separates three different powers; they are not interchangeable filters in one ordered authority chain:

1. **Host availability:** a host decides what it stores or serves under its published resource and safety policy. A refusal is local to that host; it does not invalidate the signed object or compel other hosts to remove it.
2. **Board projection:** signed `ModerationAction` events—hide, label, pin, lock, or view-ban—apply to the board's default presentation. Actions cite the target and the moderator's role proof/frontier. Undo is another action. The log is append-only; hiding never means erasing.
3. **Personal overlay:** each reader may additionally hide writers or objects. The personal choice can make the reader's view narrower, but cannot make a host serve bytes it withheld or overrule a board action in other people's views.

For public boards, board-level actions and their attribution are visible in the normal moderation history; do not silently hide moderation decisions. The raw/unfiltered view is an audit path, subject to host availability and law. Moderation is a rendering decision, not a way to rewrite signed history. Rate/volume controls remain host resource policy, not an implicit judgement that a valid author lacks authority.

This is aligned with the latest trust/visibility decision: ingest checks validity, storage is evidence, and a named view decides what counts. The #2238 writer-set design is a separate reviewed spec for per-view author counting; boards should reuse the distinction, not copy its metric-specific wire format as a board ACL.

### 4. Embedded games and succession

- `GamePost` is a board post that references an immutable package/version hash, package-defined configuration and roles, a play mode, and a genesis state or save point. The package is referenced, never inlined. A later package version cannot change an existing game's rules. Keep game-role vocabularies package-defined (the DM/campaign case needs asymmetric roles); ID only authenticates the key that signed an object.
- V1 mode is **async turns**. Each `GameTurn` is signed by the acting player's author key and references the game instance, turn index, move payload, and prior game frontier. The game state is deterministic replay/fold over that lineage. Competing turns at a frontier remain visible forks; a board/view can select a displayed line but cannot delete alternatives.
- **Succession is a first-class async lineage:** a signed `SavePoint` names package version, frontier and state hash; a signed `Handoff` names the recipient and terms; the recipient's acceptance begins their leg. A `Fork` starts an alternate instance from a cited save point. The accepted handoff chain is the social “main line”; protocol identity remains the graph. Save blobs are referenced by hash.
- The three #2053 examples map without new modes: tic-tac-toe is async-turns; D&D-style play is async-turns with package-defined DM/player roles and freeform posts beside structured state; Dwarf Fortress is succession with a single-writer leg and a handoff at each save point.
- The world journal is an execution trace, not player-authored proof. The authoritative game history is the signed board-level turn lineage. If a future game mode wants match attestation over host-journal inputs, #2814 must first provide player-signed input capture. Mutual-concession/witness attestation remains optional follow-on work; this board design does not promise ranked results.
- **Defer live-session games** (real-time eat-the-dots/agar class): hosting, rendezvous, tick latency, session discovery, and persistent-world responsibility are unresolved systems work. V1 can display a link/reference to a live session later without making live play a launch requirement.
- Package signature is provenance, not safety. Running an embedded game must use the existing sandbox and its module/fuel/memory/message bounds; guest code has no ambient filesystem/network imports (`pkgs/id/src/sandbox.rs:1-39, 160-176, 246-258`). Any world effect must still pass the host's allowed-and-granted capability check (`pkgs/id/src/world_caps.rs:480-508`).

### 5. Federation and visibility

- V1 is for public boards. Board identity is independent of its serving host; willing hosts replicate the same signed object set. A board may publish an opt-in signed listing; a directory is an index over listings, not a new authority.
- Start with a direct board reference and one host. Add listing/discovery and multi-host replication as independently testable slices; current peer discovery tracks peers/endpoints (`pkgs/id/src/discovery.rs:1-20, 38-53`), not board/content holders.
- **Closed/encrypted boards are not v1.** They need a separate confidentiality/key-management design, including what membership, moderation, and replication reveal. Public visibility is not a UI toggle that makes already-replicated objects private.
- If the owner key is lost without a predeclared successor, the board remains readable/replicable but cannot silently reassign its authority. Anyone can create a successor fork citing the old root. No moderator-quorum recovery is specified in v1.

## Invariants for implementation

1. **No registration gate:** valid signing keys can author without an account; keys—not display names or transport endpoints—identify authors.
2. **One signature envelope:** all board/game objects verify through the existing signed-event path; the author and content hash are reproducible from stored bytes.
3. **Stored/served/counted/rendered are distinct:** host availability, board projection, and personal overlay are separately named. A moderator never deletes another host's bytes.
4. **Append-only provenance:** edit, delete request, moderation, role change, succession, and fork are new signed objects with explicit references; no silent rewrite of history or theme lineage.
5. **Pinned inputs:** every view/game line names the exact board/rules/theme version, relevant frontier and resolution context; no wall-clock winner or host arrival order silently chooses the canonical branch.
6. **No executable theme surface:** board-controlled content cannot inject HTML, JavaScript, CSS, terminal escapes, or ambient capabilities into a renderer.
7. **Package pinning and bounded execution:** embedded games name immutable bytes and execute only inside operator-granted capability/resource ceilings.
8. **Player evidence is player-signed:** never infer a player's signature from a host-authored `WorldEvent`; a turn that cannot verify as the acting player is not in the authoritative game lineage.
9. **Forks are preserved:** concurrent versions, turns, save continuations and board-successor roots remain attributable; a view may choose a presentation but cannot erase other valid branches.
10. **Safe degraded rendering:** a missing attachment/package/theme, unsupported layout, or stale replica degrades to a readable reference plus status—not an unsafe interpreter or an invisible alternate history.

## Acceptance criteria for implementation

- A board can be created and opened from its signed reference on a second client without account registration; the same public key authors on multiple boards, and duplicate display names remain disambiguated. The author key is derived from the verifying key in the signed header (`pkgs/id/src/event_store/resolve.rs:84-87`).
- Board root, rules, thread, post, attachment ref, edit/tombstone request, theme, role, and moderation action round-trip through signed encoding/decoding; invalid signatures, wrong authors, bad refs, and malformed variants are rejected without partial projection.
- Two hosts holding the same signed object set compute the same pinned board projection; a later event/fork does not silently change a saved view with unchanged provenance.
- Board moderation hides/labels/pins/locks in the board view, while the audit history still attributes the action; a separate reader can apply a personal hide without changing the board view. Host refusal is visibly a host limitation, not a global deletion.
- A theme applies by reference, can be forked with parent attribution, and renders as tokens/layout/assets in web and terminal clients; unsupported/missing theme data has a safe default. No board theme can execute code.
- A post can reference an attachment by content hash; retrieved bytes and length are checked against the reference (`pkgs/id/src/documents.rs:121-145`) and remain separate from the signed post body.
- A tic-tac-toe `GamePost` pins a package hash. Valid player-signed async turns replay deterministically; a wrong signer/frontier is rejected; a competing turn is exposed as a fork. A save-point handoff/acceptance and a third-party fork both replay from the cited frontier without changing the source line.
- The board/game UI labels attestation as absent or as an optional separate state; it does not label host journal events as signed player moves or claim tournament-grade finality until the relevant signed-capture/attestation work is complete.
- Public boards replicate without a primary-server assumption; stale/partial replicas identify their staleness. Closed-board access is not implied by this acceptance set.

## Phased implementation plan

Each slice is independently reviewable and mergeable behind the relevant capability/feature boundary. Existing gated candidates are linked; this design task does not modify or commission another issue.

1. **Signed board object vocabulary and codec** — Board/Rules/Forum/Thread/Post/Attachment/Membership/RoleAttestation/ModerationAction/Fork; canonical body encoding, reference validation, supersession, signature/fork fixtures. This matches candidate [#2812](https://github.com/developing-today/code/issues/2812); keep it an object-layer slice, no UI or enforcement.
2. **Read-only board projection and themes** — local board lookup, stable refs, rules/theme resolution, safe web/terminal rendering, stale/fork indicators; define board and personal projections with provenance. This matches candidate [#2813](https://github.com/developing-today/code/issues/2813), which remains gated on this synthesis.
3. **Board authoring and moderation** — create/revise threads and posts, attachment refs, roles, append-only moderation actions, raw/audit path, personal overlay. Add state-machine/property tests for independent views and role revocation; keep host refusal behavior explicit.
4. **Async game posts and succession** — package-pinned GamePost, player-signed GameTurn, deterministic replay, SavePoint/Handoff/acceptance/Fork; prove on tic-tac-toe. Use #2266's open PoC only as a test lead after its review is dispositioned, not as merged production code. Do not make this slice depend on #2814 unless it chooses to attest the host journal instead of board-level signed turns.
5. **Replication and board discovery** — direct refs first, then opt-in listings and multi-host replication with partial/stale status and authorization tests. Host discovery must not be confused with current peer discovery. Keep public-only; encrypted boards and live sessions remain separate future designs.

## Questions for Drew

These do not block recording the design; the recommendations above are the implementation defaults until ruled otherwise.

1. **Theme power:** (a) allow custom HTML/CSS in v1, (b) data-only tokens/layout/assets, or (c) allow a later opt-in code surface. **Recommend (b)**; it preserves web/terminal parity and avoids letting board content execute in renderers.
2. **Moderation transparency:** (a) public signed board action log, (b) private/sealed board actions, or (c) public metadata with narrowly sealed reasons/targets. **Recommend (a) for board actions**, while hosts retain a separately stated ability not to serve restricted content; add a sealed mechanism only if a real reporting/privacy requirement is in v1.
3. **Closed boards:** (a) include encrypted membership/replication in v1, or (b) public-only v1 with a later key-management design. **Recommend (b)**; encryption changes membership, moderation, discovery, and replication together.
4. **Lost board-owner key:** (a) moderator quorum can recover authority, or (b) no recovery—read-only old board plus a signed successor fork. **Recommend (b)**; it avoids silently changing who owns the old signed root.
5. **Real-time embedded games:** (a) require live-session hosting/discovery in v1, or (b) ship async turns/succession first. **Recommend (b)**; live host, rendezvous, latency, and discovery are separate unresolved operational problems.
6. **User-visible identity and key rotation:** (a) treat each signing key as its own board identity, (b) define a multi-device account that maps several keys to one person, or (c) make a signed successor-key chain part of boards v1. **Recommend (a)** for v1, with local petnames and optional signed profile claims; defer account aggregation/recovery so boards do not invent a second identity system. The reviewed writer-set design explicitly leaves key-versus-account identity to the broader ID core design.

No implementation code or tests were changed for this design. The issue remains open for review and Drew's rulings.
