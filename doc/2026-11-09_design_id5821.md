# ID queries: result shaping & cursor pagination — decision record

- Date: 2026-11-09
- Status: decision record for [#5821](https://github.com/developing-today/code/issues/5821)
- Parent design: [#5675](https://github.com/developing-today/code/issues/5675) (ID query v1), decomposition item 6
- Programme: epic [#2056](https://github.com/developing-today/code/issues/2056)

This record settles only what #5821 names: result formats, truncation
honesty, server cost limits, and cursor pagination semantics for local
and remote ID queries. It does not re-decide the parent's filtering
model, owner-override boundary, or surface parity. Where a choice here
touches a parent decision, the parent wins and the touch is named.

## 1. One result envelope, every surface

**Decision.** Every query, local or remote, returns the same envelope:

```json
{
  "rows": [ { "...": "projected fields only" } ],
  "next_cursor": "opaque string or null",
  "complete": false,
  "truncated": ["page_size"],
  "withheld": { "rows": 3, "fields": 1 },
  "cost": { "scanned": 1200, "returned": 100, "ms": 42 }
}
```

- `rows` carries projected fields only. Projection, ordering, and
  limits are pushed to the executing server (parent §6); a client
  never receives a full dump to shape locally.
- The scripting/API and agent surfaces consume this envelope as JSON.
  The human CLI renders the same envelope as a table; the table is a
  rendering, not a second format, and the CLI must surface
  `complete`/`truncated`/`withheld` as visible markers, never drop
  them for tidiness.
- A SQLite-shaped result is a *derived export* a client may build
  from envelopes (the query-Redis-get-SQLite composability pattern),
  not a wire format. The server never speaks SQLite in v1.

**Rejected.** Per-surface result schemas (drift between doors is the
parity failure the parent forbids); CSV as a wire format (loses the
envelope, and with it truncation honesty).

## 2. Cursor pagination: keyset, opaque, context-bound

**Decision.**

- Pagination is keyset (cursor) pagination over the query's declared
  ordering extended with the row's stable ID as final tiebreaker:
  `(sort_key..., row_id)`. Offset pagination is rejected: it drifts
  under concurrent writes, which the parent explicitly forbids.
- A cursor is an opaque, versioned token encoding: the last returned
  `(sort_key..., row_id)`, the query-shape hash, and the filtering
  context (requester identity + clearance + override state) it was
  minted under. A cursor presented with a different query shape or a
  different filtering context is rejected with a machine-readable
  `cursor_context_mismatch` error — never silently restarted, never
  honoured across a clearance change (a cursor must not become a
  capability to read past a revoked grant).
- Cursors expire. Default lifetime 15 minutes, server-configurable;
  an expired cursor returns `cursor_expired` and the client restarts
  the query. Expiry bounds how long a server must keep any pagination
  state and bounds the staleness window of a long read.
- Ordering must be total before pagination is offered: if the query
  declares no ordering, the server imposes `row_id` ascending and
  says so in the envelope's first page. Non-deterministic orderings
  are not paginatable.
- Local and remote semantics are identical; a local query may not
  offer a "just give me everything" bypass. The only local difference
  is cost (§4): the caps exist on both, with different defaults.

## 3. Truncation honesty

**Decision.** A result that is not the whole answer looks different
from one that is — in the envelope, mechanically:

- `complete: true` appears only when the server returned every row
  the query matched *after filtering*, subject to §3's withheld
  accounting. Anything else is `complete: false` with at least one
  `truncated` reason.
- `truncated` is a closed enum: `page_size` (more pages exist;
  follow `next_cursor`), `server_cap` (a §4 limit cut the result;
  narrowing the query is the remedy, cursor continuation is *not*
  offered past a cap cut), `cost_limit` (scan/time budget exhausted),
  `filtered` (sensitivity filtering withheld rows or fields).
- Withheld-result signaling follows the parent design's per-level
  honesty rules (decomposition item 3 owns the levels); this record
  fixes only the mechanics: when the parent's rule for a level is
  "counts", the counts ride in `withheld.rows`/`withheld.fields`;
  when the rule is "nothing", the fields are absent *and* `filtered`
  is absent from `truncated` — absence must be indistinguishable from
  a query that matched nothing withheld, or the envelope itself
  becomes an existence leak.
- A page cut is never presented as a cap cut or vice versa: the
  remedy differs (continue vs. narrow), so the reason must too.

**Rejected.** Silent truncation (the parent's named failure mode);
a bare `has_more` boolean (cannot distinguish page/cap/cost/filtered,
so clients guess wrong); returning withheld counts for all levels
(re-decides the parent's per-level honesty choice).

## 4. Server cost limits

**Decision.** Guardrails are server-side, enforced identically in
shape on local and remote execution, with stricter remote defaults:

| Limit            | Remote default | Local default | On breach |
| ---------------- | -------------- | ------------- | --------- |
| Page size        | 100, max 1000  | 100, max 1000 | clamp + `page_size` truncation |
| Scan cap         | 100k rows examined | 1M rows examined | `cost_limit`, partial envelope or error |
| Wall-clock       | 10 s per page  | 60 s per page | `cost_limit` |
| Result bytes     | 4 MiB per page | 16 MiB per page | page cut at row boundary |

- Limits are per page, not per query: a well-behaved client can walk
  a large result in bounded pages; a single page can never DoS the
  serving server (the parent's cost-limit requirement).
- The `cost` block reports rows scanned and milliseconds spent on
  every page, so expensive query shapes are visible to the requester
  and to the serving server's audit log (parent §2 audit) alike.
- Raising local limits is an operator configuration choice; raising
  them is never a query parameter — a requester cannot ask a remote
  server to spend more on them. The owner override (parent §3) does
  not raise cost limits: it changes filtering on the owner's own
  unencrypted data, and policy never outranks cryptography or turns a
  cost guardrail into a per-query negotiation.

## 5. Invariants implementation must hold

1. Same query + same filtering context ⇒ same envelope shape, local
   and remote; only values and cost figures differ.
2. No silent partial answers: `complete: false` always carries a
   reason; `complete: true` is never emitted past a cap or filter cut.
3. A cursor never widens access: context mismatch or expiry is an
   error, never a fallback to an unfiltered or restarted read.
4. Pagination order is total and stable for the life of a cursor.
5. Every page is cost-bounded; no query parameter raises a server cap.
6. Withheld signaling follows the parent's per-level rules exactly;
   the envelope adds no leak channel of its own.

## Open questions (not decided here)

- Exact classification levels and their withheld-signaling rules —
  owned by decomposition item 3 of #5675, deliberately untouched.
- Whether a future v2 offers snapshot cursors (a pinned read view for
  long analytics walks). v1 accepts cursor expiry + restart instead;
  snapshot isolation is a real cost on the serving server and needs
  its own record if wanted.

No implementation is included in this record. Implementation tickets
may be cut against §§1–4 directly; each must name which invariant(s)
its tests oracles cover.
