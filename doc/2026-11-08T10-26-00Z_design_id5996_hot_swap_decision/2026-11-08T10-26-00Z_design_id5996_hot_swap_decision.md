# Design: hot-swap alternatives — decision record for the v1 mechanism

- **Date:** 2026-11-08
- **Status:** decision recorded; no implementation is included here.
- **Issue:** [#5996](https://github.com/developing-today/code/issues/5996), part of the worlds design program [#5955](https://github.com/developing-today/code/issues/5955); parent topic [#5964](https://github.com/developing-today/code/issues/5964) (dynamic user functions — server-compiled DLLs, hot-swap into running worlds).
- **Inputs:** [#5964](https://github.com/developing-today/code/issues/5964) (the requirement this decision serves: server compiles user code itself, world picks it up when compiled, mismatch default is "keep running what you'd already published"); [#5966](https://github.com/developing-today/code/issues/5966) (per-function gas/timeout research — cited as an evaluation input, per #5996 scope); [#5962](https://github.com/developing-today/code/issues/5962) (server invariants / per-tick world budget); [#5967](https://github.com/developing-today/code/issues/5967) (per-user function mapping — the consumer: switches are rebinds that take effect only at tick boundaries, state survives a switch only by explicit handover); the prior-art research under #5955 (Roc offers no runtime module hot-swap; dynamic component linking is immature in the WASI 0.3 era).
- **Evidence baseline:** `origin/main` `0865aad9a9d6d8f1d1a179364ce1693ebc36a059`, host files re-read fresh for this record (citations below).

## Decision to make

#5964 needs per-tick switching of user functions inside a running world. #5996 scoped three mechanisms to deliver it and asked for the v1 pick, evaluated on five axes: swap latency at a tick boundary; isolation strength; metering compatibility; determinism for replay; implementation cost against the current host (`pkgs/id/src/world_compile.rs`, `pkgs/id/src/world_session/`).

## Recommendation

**V1 is mechanism 2 — restart with a warm compile cache — realized in the host's own terms as instance-per-function restart:** a user function is a separately compiled Wasm module; a swap discards the function's old Wasmtime instance and instantiates the new module fresh at a tick boundary, handing state over through the snapshot/restore seam that already exists for whole worlds. There is no literal OS-process restart in v1 because the host's isolation unit is not a process — it is a Wasmtime instance (`pkgs/id/src/sandbox.rs`); the native-worker tier is the only process-shaped target, and per-function native processes are a reopen case (§5), not the v1 default.

The other two mechanisms are rejected for v1, for different reasons: mechanism 1 (component-model dynamic instantiation) is the best long-term shape but bets v1 on immature dynamic-linking tooling the host does not have; mechanism 3 (interpreted behavior layer) is the cheapest swap but abandons #5964's core requirement — user code is real Roc, compiled by the server — and builds a second language and metering stack to maintain forever (§4).

## 1. The current host, as verified for this record

Everything the v1 mechanism needs already exists in whole-world form; v1 is a narrowing of existing seams to per-function scope, not a new subsystem.

- **Server-side compile.** `world_compile.rs` compiles Roc source server-side under limits (≤8 files, 128 KiB/file, 256 KiB total, 120 s ceiling), default target `wasm32`, optional native `x64musl`; imports are checked against the granted set (`check_imports`). The trust chain of #5964 — the server trusts the code because it compiled it — is this pipeline's existing posture.
- **Artifact identity.** A compile is pinned by BLAKE3 digests of the source files, the platform tree, and the compiler binary (`digest_sources` / `digest_tree` / `digest_file` in `world_compile.rs`). Installed modules are identified by `module_hash` (BLAKE3 of the module bytes, `world_session/mod.rs`) and may carry an Ed25519 `ModuleSignature` over the domain-separated digest, checked against configured module trust keys (`world_session/types.rs`, `with_module_trust_keys`).
- **Execution and metering.** `sandbox.rs` runs modules on Wasmtime with fuel metering per guest call (`consume_fuel`, per-call fuel statistics), memory limits, and trap/fuel-exhaustion handling. Per-function fuel budgets — the metering model #5967 and #5966 assume — are this mechanism at per-function scope.
- **Atomic install with fallback.** `WorldService::install_wasm` compiles, instantiates, and only then activates a new program: "A failed compile or write leaves the running program unchanged." That is exactly #5964's stated mismatch/failure default — keep running what you'd already published — already implemented for whole worlds.
- **State handoff.** A freshly instantiated guest rebuilds its model from a snapshot (`plaza_snapshot` / `plaza_restore`, `sandbox.rs`: "Replace the model with one rebuilt from `snapshot`… intended for a freshly instantiated guest"). Restart-with-state-handoff is therefore a proven host pattern, not a new invention.
- **The one real gap:** the compile cache today lives inside each job directory (`XDG_CACHE_HOME` set to the job dir in `world_compile.rs`), so nothing is warm across compiles. A persistent, content-addressed cache is v1 work (§3), keyed by the identity scheme that already exists.

## 2. Evaluation on the five axes

| Axis | 1. Wasm components, dynamic instantiation | 2. Restart + warm compile cache (v1 pick, as instance restart) | 3. Interpreted behavior layer |
| --- | --- | --- | --- |
| Swap latency at tick boundary | Best in theory: link a pre-compiled component, no restart. But only once dynamic linking exists (below). | Compile is off the swap path (done at publish time, cache-warm); the swap itself is one instantiation + snapshot restore at the boundary — milliseconds-to-tens-of-ms class on Wasmtime, and it happens between ticks, never mid-tick. | Best in practice today: a data update, effective next tick, ~zero cost. |
| Isolation strength | Strong: components import only declared WIT interfaces; mismatch is a link error. | Strong: a fresh instance per function; a trap, hang, or poisoned guest kills that function's instance only, and the pre-swap version stays installed until the new instance is proven (§3). Same boundary the host already trusts for whole worlds. | Weakest of the three at the function level: all functions share one interpreter inside one guest; an interpreter bug or a pathological script is a shared-fate event, and "isolation" is whatever the interpreter author remembered to check. |
| Metering compatibility | Good eventually: fuel metering applies per instance; per-function attribution needs the component runtime to expose the same accounting `sandbox.rs` has today. | Native fit: the existing Wasmtime fuel model meters each instance's calls; per-function budgets (#5966, #5962) are a direct reuse. | Worst: fuel does not see inside an interpreter. Metering must be reinvented as interpreter step-counting, then kept in agreement with the host fuel model — two metering stacks, diverging forever. |
| Determinism for replay | Good: components are deterministic given the same inputs, assuming deterministic instantiation. | Good: the replay artefact is (module hash, snapshot, tick inputs) — module identity is already content-addressed (§1), and snapshot/restore is the existing replay seam. | Best: interpreted data is trivially replayable — if the interpreter is deterministic, which becomes one more thing to prove and keep true. |
| Implementation cost against the current host | Highest, and schedule-risky: the host runs core Wasm modules, not components; there is no WIT interface for user functions, no component runtime in `sandbox.rs`, and the research under #5996 notes dynamic hot-link of arbitrary components remains immature (statically linked before shipping is the norm). V1 would wait on other ecosystems. | Lowest of the compiled options: compile (§1), identity, metering, atomic install, and snapshot handoff all exist in whole-world form. New work is per-function scope (a function module is smaller than a world module, compiled against a function platform/interface), the persistent warm cache, and binding swap bookkeeping in the session layer. | Deceptively high: the swap is cheap, but v1 would have to design, implement, meter, and document a behavior language, its tooling, and its debugging story — and every future language feature request lands on us. It also cannot express what Roc expresses, so it caps the feature it was built to enable. |

## 3. The v1 mechanism, specified

1. **Function artifact.** A user function compiles through the `world_compile.rs` pipeline as its own module — Roc source in, `wasm32` module out — against the world's declared function interface (the interface contract itself is #5964's design deliverable; this record fixes only the swap mechanism). The artifact is identified by its BLAKE3 module hash and the compile provenance triple (source, platform, compiler digests).
2. **Warm cache.** Compiles are cached persistently, keyed by that provenance triple plus the target. A source edit that changes nothing about the key is a cache hit and never recompiles; the cache lives outside any single job directory (the §1 gap). Cache entries are content-addressed, so a poisoned or partial entry fails its digest check and is recompiled, never trusted.
3. **Publish, then swap.** Compiling a new version never disturbs the running one. Following the `install_wasm` pattern: instantiate the new module, run its init, and only on success mark it the function's active version. Any failure — compile error, instantiation trap, interface mismatch — leaves the previously published version running, per #5964's stated default.
4. **Tick-boundary swap only.** A version becomes active at a tick boundary, never mid-tick; invocations already in flight finish on the old instance (the mapping model of #5967). The old instance is discarded after the boundary; there is no in-place mutation of a live instance, ever — that is what makes the swap auditable and the replay artefact small.
5. **State handoff.** For a version upgrade of the *same* function, state hands over through the snapshot seam: snapshot the old instance's state blob, restore it into the fresh instance; a failed restore rejects the swap and the old version continues with its state intact. For a switch to a *different* function, the #5967 rule governs: fresh init unless the user explicitly hands a state blob over — schemas are never assumed shared.
6. **Metering.** Each function instance runs under its own fuel budget (existing `sandbox.rs` metering), inside the world's per-tick budget (#5962). A function that exhausts fuel or traps loses its turn per the #5967 failure table; its instance is poisoned and the next tick re-instantiates from the last good version + state.

## 4. Rejected alternatives

- **Mechanism 1 — Wasm target + component-model dynamic instantiation.** Rejected for v1 on cost and schedule risk, not on merit: it is the only alternative whose isolation story (declared WIT imports, link-time mismatch errors) is strictly better than instance restart, and if dynamic component linking matures it likely becomes the v2 answer. Today the host has no component runtime, no WIT function interface, and the ecosystem tooling statically links components before shipping — dynamic hot-load of arbitrary components is the immature part, and it is precisely the part v1 would depend on.
- **Mechanism 3 — data-driven behavior layer.** Rejected because it answers a different requirement: #5964 requires user code to be real code the server compiles (the DLL recollection, the trust chain, the Roc platform), and an interpreted layer delivers none of that — while adding a language, a second metering model, and an expressiveness ceiling. Its one decisive win, near-zero swap latency, is not the binding constraint: v1 swaps at tick boundaries, where instance-restart latency already fits.

## 5. What would reopen this decision

- **Component-model maturity:** Wasmtime component support in the host's sandbox *and* ecosystem tooling for dynamic link/instantiation of arbitrary components (post-WASI-0.3) — re-evaluate mechanism 1 as the primary, keeping this record's publish/swap/state rules unchanged on top of it.
- **Measured swap latency:** if production measurement shows instantiation + restore at tick boundaries missing the tick budget at real function counts (the failure would appear as world-budget exhaustion in the #5967 mapping), first optimize the restore path, then re-evaluate mechanism 3 for the latency-critical subset — with data, not by default.
- **Native-tier functions:** if user functions must run on the native (`x64musl`) tier, the restart in mechanism 2 becomes a literal process restart; the cache, identity, and fallback rules carry over, but isolation and metering must be re-argued for processes (no Wasmtime fuel) before shipping.
- **Non-programmer authoring:** if worlds need behavior authorable by non-programmers inside the client, that is a new requirement — an interpreted layer may be the right answer *for that surface*, layered over (not replacing) compiled functions.
- **Interface churn:** if the function interface changes shape frequently enough that recompilation of every function dominates, revisit — the cache key already versions the platform, so this trigger means measured cache-hit collapse, not a feeling.

## 6. Consequences and follow-ups

- #5964's design doc can now fix the DLL interface contract against a known mechanism: per-function core-Wasm modules, content-addressed identity, tick-boundary activation, snapshot state handoff.
- Implementation work implied (to be filed from #5964, not here): per-function compilation against a function platform; the persistent content-addressed compile cache; per-function instances and swap bookkeeping in the session layer.
- No code changes accompany this record, per #5996 scope.
