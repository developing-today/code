# Design: session header + segment checkpoint event kind

- Date: 2026-11-01
- Status: **design recommendation** — no implementation is included in this record.
- Issue: [#2240](https://github.com/developing-today/code/issues/2240), under #2034 / #2056.
- Scope: Define the signed session start/header and segment checkpoint wire records, their verifier, key and segment policy, retention/fork behavior, and the `peer_signature` policy needed to build the gated PoC without another design round.

## The shape

```text
authenticated session setup
   ├─ fresh session MAC key (delivered privately to authorized participants)
   └─ signed `session.start` ChainExt event
          │  header event ID is the session ID; commits to key + policy
          ▼
     MAC-authenticated ephemeral frames ── every 256 frames or 2 s ──┐
          │                                                          │
          └─ live state                                              ▼
                                              signed `session.checkpoint` event
                                              {previous checkpoint, ordered root,
                                               state transition, optional co-signature}
                                                         │
                                  optional content-addressed body/blob for replay
                                                         │
                           existing event graph, fork proofs, `after`, sync, pruning
```

Frames remain off the durable event graph. The graph stores a signed start event and compact signed checkpoints; a checkpoint may commit to a separately fetched segment body when a class needs replay evidence. This preserves a clear distinction between **a signer committed to this segment root** and **a verifier had the segment bytes and independently replayed them**.

## Decision

Use the existing signed event graph for a typed `session.start` record and the requested `session.checkpoint` records. Add typed fields to `ChainExt`; do not create a parallel artifact chain for checkpoint metadata. `session.start` is a companion kind: the signed header must exist before frames are accepted, and it is also the clean key-rotation point. A session ID is the `session.start` event ID, avoiding a self-referential header hash. Keep large replay logs or snapshots in the existing content-addressed event-body/blob path, not in the metadata fields and not as separately signed `artifact.rs` records.

Use a fresh, random 32-byte MAC key per session. Deliver it to authorized participants over an authenticated, confidential session-setup channel; the public signed header carries only a domain-separated BLAKE3 commitment to the key. A rotation closes the current session and starts a new one with a new `session.start` event, session ID, and key. It never silently changes the key inside an active session.

The default checkpoint boundary is **256 frames or 2 seconds, whichever occurs first**, plus best-effort flushes on commit, blur, graceful disconnect, and key rotation. Pin the effective limits and flush policy in the signed start record and make world-level ceilings configurable through `WorldLimits` without overloading its existing snapshot `checkpoint_every` setting.

Use checkpoints as causal graph events that name the start event and immediate prior checkpoint. Compaction must keep active session heads, the causal ancestors needed to resolve their `after` references, relevant fork proofs, and dependencies named by persisted waiting rows. A missing dependency remains waiting or incomplete; it is never treated as verified. Apply fork-dependent validity at the session/audit consumer, not by changing generic event-store fork semantics.

Keep `peer_signature` optional in the wire shape and required by policy only for **observed competitive metadata** (latency, connection path, and similar observer facts), where the signer must be an authorized peer, relay, or witness other than the player. Match inputs/results, durable chat, and money retain their own per-player/per-message/per-transaction signatures; a checkpoint co-signature does not replace them.

## Context and evidence

### Issue scope

Issue #2240 asks for `SessionHeader` and `SegmentCheckpoint` records, canonical-CBOR encoding and golden vectors, a concrete verifier, and explicit decisions on event-vs-artifact storage, MAC-key handling and rotation, segment defaults and world configurability, fork/waiting/compaction behavior, and classes requiring `peer_signature` ([issue body](https://github.com/developing-today/code/issues/2240)). Its Nov. 1 triage comment assigns those choices to this design and gates the PoC until the design has had its review round (#2056); it does not settle their technical answers ([issue comment](https://github.com/developing-today/code/issues/2240#issuecomment-6555134773)).

### Current tree facts

- `ChainExt` is serialized inside the signed event header and currently contains `kind`, `group`, `after`, and typed tag/document/removal fields (`pkgs/id/src/chain.rs:93-118`). Its wire form rejects unknown fields and omits absent optional fields (`chain.rs:120-136`); `validate()` enforces which typed payload belongs to each kind (`chain.rs:172-255`). The implementation should therefore add typed `session_start` and `session_checkpoint` fields with strict kind/payload exclusivity; it should not add an unvalidated catch-all map. `after` is capped at `MAX_AFTER` (`chain.rs:33,104-107`).
- `chain::sign` validates the extension and author sequence/backlink before signing (`chain.rs:271-309`). `decode` accepts canonical CBOR, verifies the signed header, and derives the event ID as BLAKE3 over the signed bytes (`chain.rs:311-342`). The new records should reuse this path, not invent a second canonicalization or event-signature scheme.
- An event header commits to an optional body’s BLAKE3 hash and size, while the body is stored separately (`chain.rs:271-276`; `pkgs/id/src/event_store/ingest.rs:433-444`). Sync batches can carry headers without bodies (`event_store/ingest.rs:327-333`), and documents already use separate content-addressed bytes (`pkgs/id/src/documents.rs:3-17`). Therefore a small checkpoint must be independently verifiable from its typed header fields; body availability controls replay verification, not whether the event header can be verified.
- The artifact alternative is real: `pkgs/id/src/artifact.rs:1-20,50-108` has a separate per-author chain and separate storage/transport shape; it signs JSON bytes and verifies them strictly (`artifact.rs:221-309`). This differs from the event graph’s canonical-CBOR/BLAKE3 event identity and would introduce a second path for `after`, sync, forks, and retention.
- `WorldLimits` already contains bounded world settings, including `retained_events` and `checkpoint_every` (`pkgs/id/src/world/mod.rs:57-102`). The existing `checkpoint_every` trims the world journal behind a program snapshot; it is not a live-stream signing interval (`world/mod.rs:74-76`). World `Input` events are host-sequenced rather than participant-signed (`world/mod.rs:315-354`), so this design must not claim a session checkpoint fixes input authorship.
- Fork proofs and their headers have dedicated event-store tables (`pkgs/id/src/event_store/mod.rs:12-22`), and ingest treats proof headers as present dependencies while voiding the forked author’s chain from the fork point (`event_store/ingest.rs:43-67`). The current tree has both the in-memory waiting pool at `pkgs/id/src/waiting.rs:37-55` and persisted waiting rows at `pkgs/id/src/event_store/waiting_rows.rs:26-47,177-202`; the default waiting age is seven days (`waiting.rs:48-55,113-117`). The issue’s `waiting.rs` citation is valid in this checkout; the Nov. 1 triage comment saying that file is absent is stale.
- An event-store pruning primitive already exists: `prune_behind_cut` accepts `cut` and `protected` roots (`event_store/mod.rs:527-544`), walks causal parents of roots (`:591-638`), then removes unprotected events and repairs author chains (`:649-716`). The newer writer-set design records that this primitive has no production caller yet (`doc/2026-10-30T13-15-00Z_design_id_writer_set_view_projection/2026-10-30T13-15-00Z_design_id_writer_set_view_projection.md:1221-1235`). The gap is a retention policy/caller, not the absence of pruning code.
- The match/audit family’s latest Nov. 1 synthesis comment keeps player-signed input capture as a prerequisite, puts fork-dependent validity at the attestation layer, and distinguishes full replay from sampled audit (#2039). This is consistent with the current host-sequenced world input path above. The adjacent design PR #3807 is still open, so this record treats that comment as the latest recorded family direction, not as a merged implementation.

### Source precedence

The October #2034 investigation remains the source of the two-tier model and its concrete 256-event / 2-second proposal (#2034, especially its §5 and §8; repeated in the PoC scope at §8). Its statement that the event store has no pruning/compaction is superseded by the code at `event_store/mod.rs:527-716`: pruning exists, but the newer writer-set record says it has no production caller. ## 1. Record shape and encoding

`SessionHeader` is the typed payload of a `ChainExt` event with `kind = "session.start"`. `SegmentCheckpoint` is the typed payload of an event with `kind = "session.checkpoint"`. Both are signed with `chain::sign`; cross-author references to the session start and immediate prior checkpoint are in `ChainExt.after`, while same-author ancestry is provided by the author chain’s backlink. The session-start event’s BLAKE3 ID is the session ID.

### `SessionHeaderV1`

| Field | Wire type | Rule |
| --- | --- | --- |
| `version` | `u16` | Exactly `1` for this format. |
| `class` | closed enum | `presence`, `document_live`, `match_input`, `match_observed_metadata`, `chat_live`, or a later explicitly versioned class. Unknown classes fail closed. |
| `participants` | sorted unique list of existing author IDs | The event author is the session owner. The list scopes the MAC stream; it is not proof that each participant consented to the session. |
| `initial_state` | existing BLAKE3 hash type | Hash of the state from which the first segment starts. |
| `mac_suite` | enum | `HMAC-SHA-256/v1`; no algorithm negotiation by unsigned live frames. |
| `session_nonce` | 32 random bytes | Domain-separates the commitment from the event-derived session ID; key freshness comes from generating a new random key for each session. |
| `mac_key_commitment` | 32-byte BLAKE3 hash | `BLAKE3("id.session.mac-key.v1" || session_nonce || key)`; the 32-byte random key itself is never in the signed graph. |
| `max_frames` | `u32` | Effective event-count boundary; must be within the world’s configured session limit. Default `256`. |
| `max_interval_ms` | `u32` | Effective elapsed-time boundary; must be within the world’s configured session limit. Default `2000`. It is a scheduling limit, not proof of each frame’s wall-clock time. |
| `flush_on` | set of closed enum values | Includes `commit`, `blur`, and graceful `disconnect`; a rotation closes the current session. |
| `authorized_observers` | sorted unique list of author IDs | Identifies relays/witnesses allowed to countersign observer facts. Empty for classes that do not use observed metadata. |
| `required_countersigner` | optional role/policy | Absent for ordinary ephemeral classes; observer role for `match_observed_metadata`. The allowed signer IDs are fixed by the header’s participants/observer policy. |
| `previous_session_checkpoint` | optional event ID | Set when a key rotation or explicit restart creates a new session; names the prior session’s final accepted checkpoint when available. Include it in `after` if it is a cross-author dependency. |

Do not put `started_at`/`ended_at` in the evidence contract: signer-supplied wall time is not a trusted ordering or delivery receipt. A local display may attach advisory time outside the signed proof.

### `SegmentCheckpointV1`

| Field | Wire type | Rule |
| --- | --- | --- |
| `version` | `u16` | Exactly `1`. |
| `session_start` | event ID | Must resolve to a valid `session.start` event. |
| `segment_seq` | `u64` | Starts at `0` and increments by exactly one. |
| `previous_checkpoint` | event ID | The immediate prior checkpoint; absent only for segment `0`. |
| `first_frame_seq`, `last_frame_seq` | `u64` | Strictly consecutive with the preceding segment; the first segment starts at `0`. |
| `frame_count` | `u32` | Must equal `last_frame_seq - first_frame_seq + 1` and not exceed `max_frames`. |
| `frames_root` | BLAKE3 hash | Ordered, domain-separated rolling commitment over each canonical frame digest and MAC, seeded by the session-start ID and prior root. |
| `state_before`, `state_after` | BLAKE3 hashes | `state_before` equals the header’s initial state or previous checkpoint’s `state_after`; the checkpoint attests to the transition to `state_after`. |
| `close_reason` | enum | `count`, `interval`, `commit`, `blur`, `disconnect`, or `rotation`. Time/blur/disconnect reasons may be best-effort; they do not imply an exact timestamp. |
| `peer_signature` | optional `{signer_id, role, signature: [u8; 64]}` | Signature over the canonical checkpoint core hash, excluding this field; required only by the class policy below. |

For exact root calculation, let `canonical_frame` be the canonical-CBOR payload bytes (excluding the session ID, sequence, and MAC fields). Compute `frame_mac = HMAC-SHA-256(key, "id.session.frame.v1" || session_id[32] || frame_seq_be_u64 || canonical_frame)` and `frame_digest = BLAKE3("id.session.frame.v1" || session_id[32] || frame_seq_be_u64 || canonical_frame || frame_mac[32])`. For segment `0`, seed `root_0 = BLAKE3("id.session.segment.v1" || session_id[32] || segment_seq_be_u64 || session_start_id[32])`; later segments use `previous_checkpoint_id[32]` in place of `session_start_id`. Fold frames in sequence: `root_(i+1) = BLAKE3("id.session.segment.step.v1" || root_i[32] || frame_digest[32])`. The final root is `frames_root`. All integers are unsigned big-endian fixed-width; all BLAKE3 results are 32 bytes.

The optional event body may carry the ordered segment bytes for audit/replay classes. Its hash and size are already committed by the signed event header. Body absence or later expiry does not erase the checkpoint commitment, but it does mean the verifier cannot recompute the segment root or replay it. Do not label a root-only check as a replay verdict.

### Canonical encoding and vectors

Use the existing ChainExt canonical-CBOR path. The `Wire` form must name the new typed fields, retain `deny_unknown_fields`, and omit absent optional fields so old event encodings remain unchanged (`chain.rs:120-136,321-342`). `validate()` must require exactly the payload matching the kind (`chain.rs:172-255`). Golden vectors in the implementation spec must freeze:

1. Canonical CBOR for one `session.start` and one `session.checkpoint` event, with fixed Ed25519 test keys.
2. Their signed event bytes and BLAKE3 IDs, plus the header’s key commitment.
3. A two-frame HMAC-SHA-256 transcript and its ordered rolling root.
4. A `peer_signature` over the checkpoint core hash and the enclosing author-signed event.
5. Rejections for noncanonical CBOR, unknown fields/classes, wrong kind/payload pairing, bad MAC, broken sequence/predecessor/state linkage, oversized segments, and a missing/unauthorized required countersigner.
6. A compatibility vector proving a pre-existing non-session ChainExt still encodes byte-for-byte as before.

## 2. Decisions and trade-offs

### A. Graph event or parallel artifact

| Option | Benefits | Costs / risks |
| --- | --- | --- |
| **Ordinary graph event — chosen** | Reuses the canonical signed header, BLAKE3 event ID, author sequence/backlink, `after`, event sync, fork proofs, and existing event-body hash. One verifier path. | Each checkpoint consumes a durable graph event; class retention still needs explicit roots and blob policy. Adds typed ChainExt fields and kind validation. |
| `artifact.rs`-shape signed artifact | Separate artifact storage can suit large, independently retained logs. | Introduces a second chain, JSON/SHA-256 signing format, push/pull path, and separate ordering/fork/retention semantics. A graph reference would still be needed for causal `after` resolution. |

Checkpoint **metadata** belongs in the graph. Large frame logs/snapshots may use the existing optional event body and content-addressed retrieval (`chain.rs:271-276`; `event_store/ingest.rs:327-333`; `documents.rs:3-17`); this is not a parallel artifact chain.

### B. MAC key and rotation

| Option | Benefits | Costs / risks |
| --- | --- | --- |
| Put the raw key in the public header | Simple to distribute and reconstruct. | Anyone who reads the signed graph can forge MACs; this is not a secret-key scheme. **Reject.** |
| Derive from a long-term key | Avoids transporting a fresh random key. | Couples session confidentiality and rotation to a long-lived secret and requires every authorized participant to share the same keying material and derivation context. It also makes key lifecycle harder to audit. |
| **Fresh per-session key + public commitment — chosen** | Independent session compromise/rotation; the signed header binds the expected key without revealing it. | Requires authenticated confidential setup to deliver the key; the event graph alone cannot deliver it. |

The owner generates a uniformly random 32-byte key and 32-byte `session_nonce`, delivers the key only over authenticated confidential setup to header participants, and signs `BLAKE3("id.session.mac-key.v1" || session_nonce || key)` in `SessionHeader`. Each frame carries the HMAC specified above. Authorized participants verify that their delivered key matches the signed commitment. All holders of a shared MAC key can forge MACs, so a MAC proves group-key possession/integrity, not individual authorship. Input authorship remains a separate per-author signature requirement for match evidence.

On rotation, close the current segment if possible and sign a **new `session.start`** with a fresh session ID/key/commitment and `previous_session_checkpoint` pointing at the last accepted checkpoint. If a disconnect is abrupt, the prior checkpoints remain valid and the uncheckpointed tail is reported incomplete; the protocol does not invent a final checkpoint.

### C. Segment policy and world configuration

| Option | Benefits | Costs / risks |
| --- | --- | --- |
| Count only | Predictable event bound. | A quiet session can leave a long uncheckpointed tail. |
| Time only | Bounds quiet-session loss. | A burst can create an oversized segment. |
| **Whichever first, plus lifecycle flushes — chosen** | Bounds both event volume and tail age; commit/blur/disconnect close sooner when observed. | Timer/blur/disconnect delivery is best-effort; only the periodic interval and count rule are guaranteed by the producer. |

Use the investigation’s concrete PoC defaults: **256 events or 2 seconds, whichever comes first**, plus best-effort commit/blur/disconnect flush (`#2034` §5 and §8; the #2240-linked PoC was specified with these values). Add distinct session fields to `WorldLimits`; do not reinterpret `checkpoint_every`, which currently controls pruning behind a world snapshot (`world/mod.rs:74-76`). Store the effective values in the signed start event. A class may require a stricter limit; a session may not loosen its world’s configured ceiling. The frame sequence and roots establish order; wall-clock fields are not used to prove frame timing.

### D. Fork proofs, waiting, and compaction

Each checkpoint includes `session_start` and `previous_checkpoint` as explicit payload references. Cross-author references must also be in `ChainExt.after`; same-author ancestry is carried by the existing chain backlink. The two session references fit under ChainExt’s `MAX_AFTER` cap, though the builder must preserve the rest of the causal frontier and fail rather than silently drop it. On out-of-order arrival, normal dependency handling holds the checkpoint in the waiting pool until its start and predecessor are available. The pool is bounded and its default age is seven days (`waiting.rs:37-55,101-117`; persisted rows: `event_store/waiting_rows.rs:26-47,177-202`). The store forgets events dropped by age/caps and sync sends them again (`event_store/ingest.rs:63-67`); expiry never promotes an event, and without a re-offer the session remains incomplete.

The compaction caller must add these hashes to the existing `protected` roots passed to `prune_behind_cut`:

- The latest accepted checkpoint for every active session, which protects its causal ancestry including the start and prior checkpoints (`event_store/mod.rs:527-544,591-638`).
- Durable class roots (for example, a retained match/audit or durable-chat record) for their full policy retention period.
- Existing referenced hashes needed to resolve persisted waiting rows; pruning must not remove a present dependency while an unexpired waiting row names it.
- Fork-proof IDs/headers needed to explain a conflicting author sequence (`event_store/mod.rs:12-22`; fork-dependency behavior: `event_store/ingest.rs:43-67`).

The store’s prune method retains protected roots and their causal parents; it can remove an unprotected event and repair an author chain (`event_store/mod.rs:609-638,649-716`). The implementation must prove root construction with tests before any production caller uses it. A checkpoint whose start, predecessor, or causal parent is later voided by a fork becomes invalid/incomplete at the session/audit consumer; do not rewrite generic store semantics. This follows the latest recorded #2039 synthesis direction that fork-dependent validity belongs at the attestation layer. If a required dependency is missing, forked, expired from waiting, or pruned without its root, fail closed and do not claim a complete session.

### E. `peer_signature` policy by class

`peer_signature` signs `BLAKE3("id.session.checkpoint.peer.v1" || canonical-CBOR(CheckpointCoreV1))`, where `CheckpointCoreV1` contains every checkpoint field except `peer_signature`; the normal event author’s ChainExt signature then covers the complete payload including the countersignature. It is not the shared MAC. A required signature is validated against the authorized signer IDs and role recorded by the session policy.

| Class | `peer_signature` on checkpoint | Durable evidence rule |
| --- | --- | --- |
| Presence / cursor / typing | Not required | Ephemeral state; a checkpoint records a recoverable state transition, not a disputed fact. |
| Ordinary live document editing | Not required | Live steps/cursors are not durable claims; the saved revision remains its own signed `document.put` event (current ChainExt document path: `chain.rs:108-117`; existing collab/save split is described by #2034). |
| Match input / replay transcript | Not a substitute for player signatures | Each player’s input must be player-signed before it can support authorship or replay claims. Current world inputs are host-sequenced (`world/mod.rs:315-354`); #2039 names player-signed input capture as a prerequisite. A checkpoint alone is not a valid match log. |
| Match result / agreement | Not required on a session checkpoint | Use the #2037 two-player agreement/claims and witness decision; the checkpoint is evidence, not the outcome. |
| **Observed competitive metadata** (latency, connection path, IP continuity) | **Required** from an authorized peer, relay, or witness if the metadata is used as competitive evidence | The #2038 audit investigation says self-reported metadata is not evidence-grade and requires external countersigning (#2038; see also #2039’s Nov. 1 synthesis). Without an observer signature, omit the metadata and report L3 as `INCONCLUSIVE`; never infer it from a player’s MAC. |
| Durable/disputable chat | Not required on a checkpoint | Keep per-message author signatures when a message itself may be disputed; a checkpoint co-signature does not establish which participant authored each frame. Checkpoint-only retention is for explicitly live/low-retention chat. |
| Currency / identity / membership | Not applicable; never authoritative through a live checkpoint | Keep per-transaction or per-membership-operation signatures and the existing ledger/graph rules; checkpoint roots cannot replace those records. |

The `peer_signature` field is optional in the general checkpoint schema, but `match_observed_metadata` is invalid **as evidence-grade metadata** without the required non-player countersignature. Other classes do not gain stronger status merely by including an optional peer signature.

## 3. Verifier walk

1. **Decode event:** call the existing `chain::decode`; reject noncanonical CBOR, invalid event signature, wrong domain, unknown fields, malformed typed payload, or invalid author sequence/backlink (`chain.rs:271-342`). Compute the event ID from the signed bytes as the current path does.
2. **Validate kind/payload:** `session.start` has exactly `session_start`; `session.checkpoint` has exactly `session_checkpoint`; all other kinds have neither. Apply `ChainExt::validate` and closed enum/version checks.
3. **Validate start:** bind the session ID to the start event ID; check sorted unique participants/observers, initial-state hash, key suite/commitment shape, flush policy, and effective session limits against the world configuration. Authorized key holders also verify the delivered key against the commitment. The raw key is never expected in graph bytes.
4. **Resolve dependencies:** require the start event and immediate predecessor in `after`/the author chain before processing. If absent, leave the event waiting. If a dependency expires, do not accept the child as verified.
5. **Validate checkpoint chain:** check session owner, header ID, consecutive segment number, immediate predecessor, frame sequence/count bounds using checked arithmetic, state continuity, close reason, and root domain. Reject gaps, replays under another session ID, inconsistent state hashes, and segments exceeding the signed policy.
6. **Validate available frames:** if the segment body is present, verify each frame MAC, strict frame sequence, and the ordered rolling root; replay only under the class’s deterministic consumer. If bytes are absent, report “signed root committed; frames not independently replayed,” not “replay verified.”
7. **Validate countersignature by class:** recompute the checkpoint core hash excluding `peer_signature`, then verify the signature and authorized role. Missing or invalid observer signature makes observed metadata ineligible and its audit result inconclusive; it does not erase an otherwise valid event.
8. **Apply fork validity:** consult the event store’s fork proof/void status for the start, checkpoint, and causal parents. The session/audit consumer marks dependent evidence invalid or incomplete; it does not repair or reinterpret the event graph.

## 4. Invariants and implementation acceptance

An implementation is ready when tests demonstrate all of the following:

1. New session event fields use canonical CBOR and the existing signed-event verifier; old non-session event bytes remain unchanged.
2. Raw MAC key bytes never appear in the signed header, event body, or checkpoint archive. The key commitment, session ID, class, and policy are signature-bound.
3. Every live frame is MAC-authenticated and monotonically sequenced; the checkpoint root commits to the ordered frames, not an unordered set.
4. Every checkpoint has an immediate predecessor and contiguous segment/frame numbers; the verifier distinguishes an absent tail from a broken history.
5. The effective 256-frame / 2-second policy is configurable through world limits, recorded in the header, and enforced by count-or-time; commit/blur/graceful-disconnect are additional best-effort boundaries.
6. A MAC proves shared-key possession only. It does not prove which participant authored a frame, that an unseen recipient received it, or that the header’s participant list is consent by those participants; admission/consent belongs to the session handshake or a class-specific signed agreement.
7. Class policy prevents a checkpoint from replacing per-player match-input signatures, #2037 result records, per-message durable-chat signatures, or per-transaction currency signatures. Observed competitive metadata requires an external countersigner.
8. Out-of-order start/checkpoint dependencies wait; waiting expiry never promotes them. Prune tests prove that active/durable session roots and waiting-row dependencies survive `prune_behind_cut`, with fork proofs retained.
9. Forks that invalidate a session start/checkpoint or its required ancestry cause the consumer’s result to become invalid/incomplete without changing generic event-store fork behavior.
10. Golden vectors cover start/checkpoint canonical bytes, event IDs/signatures, MACs, roots, peer signatures, malformed encodings, and old-event compatibility.
11. This issue delivers design only. The #2241 PoC remains gated until this record has a review round under #2056; no permanent feature or PoC is implemented by this PR.

## Questions for Drew

**None.** The five choices scoped by #2240 are resolved above; their remaining implementation details do not require a policy ruling from Drew. The session module has a technical prerequisite: identify or provide an authenticated confidential transport adapter for delivering the fresh session key. If none exists, the production session feature stays disabled until that adapter is built; do not send the key through the public event graph.

## Non-goals

- No production session code, retention caller, UI, or PoC is built in this design PR.
- No per-frame Ed25519 signatures; no claim that a MAC proves authorship, receipt, fairness, or trusted wall time.
- No replacement of match attestation, player-signed input capture, observer metadata, durable chat, currency, identity, or membership protocols.
- No change to the generic event-store fork rule; consumer validity follows the latest recorded #2039 direction.
