# Design: F12.13 journal replication (read replicas over a signed stream)

- Date: 2026-11-01
- Status: **decision-ready design; implementation gated** on the F12.6
  audit-log framing contract (#1063, slice 1 / task 4885).
- Issue: [#806](https://github.com/developing-today/code/issues/806)
  (Phase 12 stack PR #801).
- Branch: `design/id-806`.

## The shape

```text
single writer                                  read-only replica
WorldActor ──durable append──► journal.jsonl ──signed stream──► verify + persist
    │                              │                              │
    └─ publish after fsync         └─ compact / version bump       ├─ journal + module
                                                                  └─ restore WorldService
                                                                         │
                                                               spectator sessions offline
```

Replicate the authoritative world journal, not the current `Records` projection.
The replica stores the verified journal and required active module, restores through
the existing world restore path, and serves spectator-only sessions from that
restored state. It never becomes a second writer.

## 1. Decision to make

Choose the transport, integrity contract, and replica lifecycle for read replicas
that follow a single writer's journal, reproduce its program records, refuse
tampered data, and continue serving spectators when the writer is unavailable.
The stream must preserve the F11.12 journal compatibility rules and align its
outer framing with F12.6, as required by #806.

## 2. Context and evidence

- #806 explicitly requires signed-stream journal replication, no write conflicts,
  spectator service during writer outage, F11.12 format compatibility, and
  refusal of tampering. Its acceptance also requires writer-record parity.
- The on-disk journal is ordered JSONL: `JournalEntry` is a tagged serialized
  enum, begins with `Created`, and records events, authority changes, installs,
  and checkpoints ([`world/mod.rs:468-643`](../pkgs/id/src/world/mod.rs#L468-L643)).
  Capability bearer secrets are not journaled; only digests are
  ([`world/mod.rs:468-472`](../pkgs/id/src/world/mod.rs#L468-L472)).
- F11.12 is now landed: versions 1 and 2 are supported, `ExecutionProfile`
  requires v2, and the writer bumps the header atomically before appending an
  incompatible entry ([`world/mod.rs:646-683`](../pkgs/id/src/world/mod.rs#L646-L683),
  [`world_store.rs:143-154`](../pkgs/id/src/world_store.rs#L143-L154),
  [`world_store.rs:177-197`](../pkgs/id/src/world_store.rs#L177-L197)). Restore
  refuses an unsupported header before applying entries
  ([`world/core.rs:148-168`](../pkgs/id/src/world/core.rs#L148-L168)). PR
  [#1353](https://github.com/developing-today/code/pull/1353) is the latest
  recorded F11.12 decision: bump-on-first-new-variant-write.
- Journal append is fsynced before the actor acknowledges a mutation;
  compaction atomically replaces the file with a header, state entries, and a
  checkpoint ([`world/actor.rs:375-392`](../pkgs/id/src/world/actor.rs#L375-L392),
  [`world_store.rs:200-252`](../pkgs/id/src/world_store.rs#L200-L252)). A stream
  therefore must publish only durable entries and treat compaction as a reset
  boundary, not as ordinary append-only tailing.
- Restore rebuilds world state and replays program inputs; a checkpoint carries
  the program snapshot, module hash, seed, and retained events
  ([`world/core.rs:333-363`](../pkgs/id/src/world/core.rs#L333-L363),
  [`world/core.rs:364-422`](../pkgs/id/src/world/core.rs#L364-L422)). The module
  bytes are content-addressed and hash-checked on restore
  ([`world_store.rs:595-639`](../pkgs/id/src/world_store.rs#L595-L639)).
- Existing `world_records` replication is explicitly a cache of the current
  key/value projection, not the journal; it coalesces changes and omits history
  ([`world_records.rs:1-18`](../pkgs/id/src/world_records.rs#L1-L18),
  [`world_records.rs:154-199`](../pkgs/id/src/world_records.rs#L154-L199)). Its
  `id world mirror` command prints that projection and does not open a
  `WorldService` ([`cli.rs:1536-1561`](../pkgs/id/src/cli.rs#L1536-L1561),
  [`commands/world.rs:156-192`](../pkgs/id/src/commands/world.rs#L156-L192)).
- The existing world session protocol serves snapshots, views, events, and
  revocation-aware sessions over `WORLD_ALPN = /id-world/1`
  ([`world_net.rs:30-32`](../pkgs/id/src/world_net.rs#L30-L32),
  [`world_session/mod.rs:1846-2020`](../pkgs/id/src/world_session/mod.rs#L1846-L2020)).
  `open_world` already restores a journal into a `WorldService`
  ([`world_store.rs:366-437`](../pkgs/id/src/world_store.rs#L366-L437)).
- The repository has signing precedents: `directory_log` hashes the serialized
  signed body and uses Ed25519 `verify_strict`
  ([`directory_log.rs:40-53`](../pkgs/id/src/directory_log.rs#L40-L53),
  [`directory_log.rs:87-102`](../pkgs/id/src/directory_log.rs#L87-L102));
  artifacts add an ordered hash chain and reject gaps or conflicting sequence
  numbers ([`artifact.rs:288-309`](../pkgs/id/src/artifact.rs#L288-L309),
  [`artifact.rs:425-478`](../pkgs/id/src/artifact.rs#L425-L478)). The serving
  node already derives a Dalek signing key from its Iroh identity
  ([`store.rs:91-119`](../pkgs/id/src/store.rs#L91-L119),
  [`commands/serve.rs:1062-1068`](../pkgs/id/src/commands/serve.rs#L1062-L1068)).
- The newest #806 triage comment says #227/F11.12 is complete, but the F12.6
  structured audit-log sink is still outstanding; #1063 routes its first slice
  to task 4885 and places OTLP export in a later slice
  ([latest #806 triage](https://github.com/developing-today/code/issues/806#issuecomment-6558378663),
  [latest #1063 triage](https://github.com/developing-today/code/issues/1063#issuecomment-6552368736)).
  The current #1063 slice describes audit-record fields and a sink, not a
  finalized reusable wire encoding. That gap is an implementation gate, not a
  reason to conflate the audit record with a `JournalEntry`.

## 3. Viable options

| Option | Advantages | Costs / why not chosen |
| --- | --- | --- |
| Extend the `world_records` iroh-docs document to carry journal data | Reuses an existing sync substrate and read tickets. | A CRDT key/value document is the wrong authority for an ordered journal: it represents the latest projection, coalesces intermediate changes, and cannot directly restore/serve a world. It would blur the cache/source-of-truth boundary documented in `world_records.rs:1-18`. |
| Send the journal through the existing interactive `WORLD_ALPN` session | Reuses session framing and the existing node endpoint. | Couples replication lifecycle/versioning to participant frames; no replication cursor, durable change feed, checkpoint-reset contract, or replica read-only mode exists there. An interactive session is not the source journal API. |
| Add a dedicated signed replication stream with snapshot/reset plus ordered tail | Keeps the authoritative JSONL journal, replication integrity, and participant sessions separate; supports reconnect, compaction, and offline serving. | Requires a cursor/change feed, signature and framing contract, durable replica store, and read-only world mode. It is gated on F12.6's framing decision. |
| Re-send a complete signed journal snapshot on every sync | Smallest initial protocol and easy to validate atomically. | Repeats all journal and module bytes on every reconnect; poor fit for a continuously followed world. Still needs an explicit snapshot boundary and rollback/format validation. Retain full snapshots as initial sync and compaction recovery, not the steady-state path. |

## 4. Recommendation

Choose the dedicated replication stream. Add a separate replication ALPN and
replication session API; do not change `/id-world/1` participant frames or treat
the iroh-docs records mirror as journal replication.

### Wire and trust contract

1. The source is the existing single writer. It emits a snapshot at first sync,
   then ordered durable journal-entry batches. A frame is published only after
   `WorldJournal::append` succeeds; compaction or a journal-header version bump
   emits a complete signed reset snapshot before later tail entries. The
   actor/store owns the feed so snapshot-plus-subscribe has no race and never
   reads a journal inode while compaction replaces it.
2. Define the cursor as `(entry ordinal, rolling digest)` over the exact
   `JournalEntry` bytes, seeded with the replication domain, world ID, source
   node ID, and current header version. It can be recomputed from the current
   JSONL file after restart. Compaction or a header bump changes the chain
   base; a replica whose cursor is not in the current chain receives a full
   signed reset snapshot. The client sends a fresh random session nonce, and
   every signature binds that nonce so captured frames cannot be replayed into
   another sync session.
3. Carry the `world_id`, source node ID, journal header version, transfer kind,
   stream cursor, previous-frame digest, entry range, and payload digest in the
   signed envelope. Bind signatures to a replication-specific domain tag and
   the exact serialized envelope bytes; use Ed25519 `verify_strict`. Trust only
   the explicitly selected/pinned source node ID, and require the signer to
   match it. Do not accept a key supplied only by the stream.
4. The payload carries the exact serialized `JournalEntry` bytes (including
   JSONL entry boundaries), never a lossy projection. Frames are size-bounded;
   larger module payloads are chunked and reassembled against a declared hash.
   The stream carries the active module bytes needed by restore and checks them
   against the journal's BLAKE3 module hash. A signed terminal frame commits
   the completed snapshot/batch digest and cursor; incomplete transfers do not
   replace the current replica state.
5. The receiver checks the signature, trusted signer, domain, world ID, cursor
   continuity, previous digest, entry decoding, header version, and module
   hashes before making a batch visible. It refuses gaps, conflicting repeats,
   malformed/tampered frames, and unsupported journal versions. A complete
   reset is staged beside the active replica and atomically installed; a tail
   is durably appended only after its complete signed batch verifies.
6. Apply the F12.6 framing contract to the outer envelope once #1063's slice 1
   defines it. Keep audit facts about replication separate from the journal
   payload. The dependency is specifically the shared framing contract; do not
   make F12.13 wait for OTLP export if that later F12.6 slice is not needed to
   define the envelope. If #1063 does not define reusable wire framing, record
   that explicitly and have F12.13 own its versioned envelope rather than
   silently inventing an incompatible interpretation.

### Replica lifecycle

- **Presence-preserving restore (Codex finding, 2026-11-01).** The existing
  restore path synthesizes presence-off events for every participant still
  present at restore time and feeds them to the program on replay
  (`WorldCore::restore`, `pkgs/id/src/world/core.rs` restore replay loop).
  That is correct for a writer restart (its sessions really ended) but wrong
  for a replica: a snapshot taken while participants remain connected to the
  writer would mark them offline in the replica's program state (e.g. the
  territory program's online status) even though the journal is intact,
  breaking writer-record parity at the snapshot cursor. Replica restore must
  therefore use a presence-preserving mode: presence at the snapshot cursor
  is restored as session state without feeding synthesized presence events
  into the program, and no synthetic event is ever journaled or counted
  against the verified cursor. Phase 3/4 owns this mode; Phase 4 acceptance
  includes a snapshot taken with participants connected, proving the
  replica's `Records` equal the writer's at the same cursor.
- The replica reuses the restore/program reconstruction path in
  `world_store::open_world`, but implementation must add a read-only open path:
  validating an already-verified replica must not use the writer's mutating
  `FileJournal::open` recovery/header-bump behavior. The replica exposes only
  spectator/read-only access and does not accept world mutations, admin
  operations, local schedule/tick firing, or program capability side effects.
  Viewer presence must not be appended to the replicated journal or fed back
  into authoritative program state.
- Serve the existing participant protocol from the local `WorldService` after
  sync, so spectators do not need the writer online. Expose the last verified
  cursor/time as staleness metadata. Keep the current records-only `mirror`
  command and its semantics unchanged; the new operation is a journal replica.
- A revoked capability cannot be learned by a replica while disconnected. The
  replica therefore needs an explicit offline-admission policy (§8). Regardless
  of that policy, it never grants more than spectator scope and applies every
  revocation present in its last verified journal.

## 5. Invariants

1. There is one writer; replicas cannot commit a journal entry or originate
   authoritative world mutations.
2. The replicated payload preserves journal order, entry bytes, `Created`
   header/version, and checkpoint semantics. No stream may reorder, omit, or
   synthesize entries.
3. Acknowledged source writes are streamable only after durable append. A
   source crash or interrupted transfer leaves the last complete replica
   usable; no partial line or unverified batch is exposed.
4. Every accepted frame is bound to the selected source identity, world,
   session nonce, domain, cursor and preceding digest. Tampering, truncation
   presented as a completed batch, replay at an incompatible cursor, a gap,
   or a fork is refused.
5. The F11.12 rule is preserved: a version-1 reader refuses a v2 journal at
   the header boundary; a replica refuses a version newer than it supports
   before applying any entry. Header bumps/reset snapshots precede entries
   that require the newer format.
6. A replica can reproduce the writer's program `Records` at the same verified
   journal cursor, including after restart and checkpoint compaction. Records
   remain a derived projection, not the replicated source of truth.
7. A read replica can serve spectator sessions while disconnected from the
   writer; it reports its verified cursor and never claims to be fresher than
   that cursor.

## 6. Acceptance criteria for implementation

- Initial full sync restores the same world sequence, active module hash, and
  program `Records` as the writer at the signed snapshot cursor — including
  a snapshot taken while participants are still connected to the writer
  (no synthesized presence-off effects in the replica's program state), and
  including a friend-delegated spectator capability authorized from the
  replicated directory facts.
- Tail sync preserves every `JournalEntry` in order and reaches the same
  `Records`; reconnect catches up without duplication or loss.
- A compaction and a v1→v2 header bump produce a reset the replica can install
  without losing state; v1/v2 compatibility and refusal of a future version
  are tested at the header, before entry application.
- Mutating a signed frame, payload, previous digest, sequence/cursor, or module
  bytes; using an untrusted signer; truncating before the signed terminal
  frame; replaying captured frames under a new session nonce; replaying a
  gap/fork; and exceeding frame/transfer bounds are all
  refused, with the last complete replica left intact.
- Writer restart, replica restart, disconnect during a frame, and reconnect
  after compaction leave the replica usable and eventually converged.
- After the writer is stopped, a replica started from its durable copy serves
  spectator sessions and the same records as its last verified cursor. It
  refuses participant writes, admin operations, local authoritative events,
  schedules/ticks, and capability side effects.
- Tests prove no bearer capability secret is copied from the journal, and that
  a revocation already present in the replicated journal is enforced by the
  replica.
- The implementation's outer frame encoding is covered by F12.6's settled
  contract or by an explicitly documented F12.13-owned versioned envelope if
  F12.6 supplies no reusable wire format.

## 7. Phased implementation plan

The phases are independently mergeable. All are gated on #1063 slice 1/task
4885 settling the shared framing seam; OTLP export is not a prerequisite unless
that work makes it one.

1. **Wire contract and crypto primitives.** Define the replication envelope,
   domain separation, cursor/hash-chain rules, bounded payload behavior, and
   test vectors. Map to F12.6 framing, or explicitly document the dedicated
   envelope if F12.6 does not define one. No network serving or replica CLI.
2. **Writer snapshot/feed and stream server.** Add a race-free actor/store
   snapshot-plus-subscribe API; publish only after fsync; send full snapshots
   on first sync, compaction, and header bump; register the dedicated ALPN.
   Cover append/compact/concurrent-connect and torn-append cases.
3. **Durable receiver and verifier.** Implement pinned-source verification,
   cursor validation, staged snapshot install, append-only tail persistence,
   module transfer/hash checks, restart and reconnect. Add tamper, truncation,
   gap, fork, unsupported-version, and size-limit negatives.
4. **Read-only world service and spectator path.** Reuse journal/program restore
   while adding a non-mutating replica open path, add a hard read-only
   actor/session mode, prevent local events and side effects, and serve
   spectators using the existing world session protocol. Verify offline
   startup and Records parity.
5. **Operator interface and resilience.** Add CLI/configuration to follow a
   pinned source into a durable replica directory and run/serve that replica;
   report source ID, world, cursor, and staleness. Exercise writer outage,
   restart, cursor reset after compaction, and the chosen offline-admission
   policy. Keep the existing records-only `id world mirror` behavior intact.

## 8. Open decisions

### Needs Drew: admission of new spectators after a writer outage

The issue requires a replica to serve spectators while the writer is offline,
but a disconnected replica cannot learn about a revocation made after its last
verified journal cursor. This changes the security/availability promise, not
just implementation detail.

- **A — Continue indefinitely from the last verified journal.** Best outage
  availability; a recently revoked spectator may retain access until the
  replica reconnects. The stale cursor must be shown to operators.
- **B — Require a writer-signed admission lease.** Bound revocation staleness;
  after lease expiry, refuse new spectator sessions (existing sessions may
  either finish or be closed at expiry, to be specified). Offline serving is
  guaranteed only within the lease. **Recommendation:** B, with the lease
  duration configurable per replica and a conservative default chosen in
  implementation, because journaled revocation is an access-control boundary.
- **C — Never admit new sessions while disconnected.** Strongest freshness,
  but does not meet the natural reading of “replicas serve spectators … while
  the writer is offline.” Not recommended.

No other decision needs Drew before implementation. The remaining gate is a
cross-issue contract for F12.6: its latest slice-1 triage names audit fields
and a sink but does not yet publish the shared wire encoding. The implementers
of #1063 and #806 should settle that seam before phase 1; recommendation is a
shared, explicitly versioned outer envelope with the journal as a distinct
payload, and no dependency on OTLP unless required by that contract.

## Non-goals

- Multi-writer replication, conflict resolution, or failover that promotes a
  replica to writer.
- Replicating the records projection as the authority, or changing the
  existing records-only mirror.
- Replicating unrelated world stores (petnames, outbox). The directory is
  partially in scope, against the original assumption: spectator
  authorization demonstrably depends on it — `WorldCore::effective_scopes`
  (`pkgs/id/src/world/core.rs`) intersects account ceilings from the
  directory and zeroes scopes for a cross-account delegation whose accounts
  are not friends, while the journal carries only account subjects. A
  journal-only replica with an empty directory would reject a valid
  friend-delegated spectator capability while fully synchronized. The
  replication scope therefore includes the directory facts
  `effective_scopes` consults — account ceilings and the friendship graph
  for accounts appearing in capability chains — carried in the signed
  snapshot (bound into the snapshot digest) and kept current by the signed
  stream; other directory uses stay out of scope. Phase 4 acceptance
  includes the friendship-delegation spectator case (cf. the existing test
  in `world/tests.rs`) served by a replica with no writer contact.
- OTLP export itself; it remains F12.6 work.
