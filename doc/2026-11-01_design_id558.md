# Design: `id world dev` authoring loop

- Date: 2026-11-01
- Status: **design** — no implementation is included in this change.
- Issue: [#558](https://github.com/developing-today/code/issues/558), F12.15.
- Evidence baseline: checkout `a9e976ac245d94682ff7ada8dd5562cc58c9b00f`.
- Sequencing: F11.16 / #544 is complete. F12.9 implementation #1066 remains
  open; the Phase 12 plan orders F12.7 → F12.8 → F12.9 → F12.15. The newest
  triage notes on #558 and #1066 supersede the older #558 intake comment that
  still described #544 as open.

## Decision to make

Choose the scope and safety boundary of `id world dev`: where the compiler and
world run, how a source edit becomes a candidate, what makes a candidate safe
to activate, and how fixture replay and deterministic fuzzing fit the edit loop.
The design must meet the issue's four outcomes: watch/rebuild/hot-swap through
F12.9 migration in a scratch world, fixture replay on each change, deterministic
fuzzing against declared invariants, and edit-to-running under three seconds
for an example ([#558](https://github.com/developing-today/code/issues/558);
Phase 12 plan, `.opencode/plans/phase-12-platform-flexibility.md:60`).

## Context and constraints

### The existing seams

- There is no `Dev` variant today. `WorldCommand` is the `id world` command
  enum (`pkgs/id/src/cli.rs:1456-1458`). Existing `Compile` takes a host node,
  Roc entry file, optional extra files, seed, and admin token
  (`pkgs/id/src/cli.rs:1642-1669`). Its handler reads bounded source and sends
  it to the connected host (`pkgs/id/src/commands/world.rs:219-268`); this is
  not a local authoring loop.
- The compiler engine already validates source names and bounds inputs to 8
  files, 128 KiB per file and 256 KiB total (`pkgs/id/src/world_compile.rs:22-36,
  151-194`). It runs the configured compiler with a 120-second per-compile
  ceiling (`pkgs/id/src/world_compile.rs:28-33, 205-210`). The dev loop should
  reuse this bounded compile path, but must not make the running world depend
  on a remote host or weaken its limits.
- `Replay` and `Verify` are offline sandbox commands. They take a module,
  fixture and explicit seed (`pkgs/id/src/cli.rs:1936-1980`); the handlers
  decode bounded fixtures, check the module, then replay or verify it
  (`pkgs/id/src/commands/world.rs:1351-1373, 1410-1430`). Verify already
  replays twice and reports the first divergence
  (`pkgs/id/src/world_fixture.rs:407-438`).
- Existing fixture files are deliberately module-bound: the header stores the
  recorded module hash (`pkgs/id/src/world_fixture.rs:42-56`), and
  `check_module` refuses bytes whose hash differs (`pkgs/id/src/world_fixture.rs:341-356`).
  Replay starts at the last install, refuses inputs before that install, and
  feeds recorded inputs/system events through the sandbox
  (`pkgs/id/src/world_fixture.rs:359-404, 801-859`). Therefore ordinary
  `id world replay` cannot serve as the every-edit regression runner: a source
  edit changes the module hash.
- Installation is an actor-serialized journal operation, and a new program
  currently starts with a clean slate (`pkgs/id/src/world/actor.rs:1278-1338`).
  Separately, snapshots are only accepted after a probe instance restores and
  reproduces both the snapshot and records (`pkgs/id/src/sandbox.rs:884-907`).
  The dev path must use F12.9's upgrade/migration contract rather than
  approximate it with a dev-only state copy or ordinary install.
- The library can create an in-memory `WorldCore` and spawn a `WorldHandle`
  actor with a guest program (`pkgs/id/src/world/core.rs:44-55`,
  `pkgs/id/src/world/handle.rs:25-44`); there is no corresponding `dev` CLI
  variant. Use this existing local actor seam for the disposable scratch world.
- F12.9's issue defines the required gate: migrate on a probe, commit only when
  migrated state round-trips, and leave the old program running on failure;
  it remains open as #1066. The Phase 12 plan explicitly sequences F12.15 after
  F12.9 (`.opencode/plans/phase-12-platform-flexibility.md:45, 60, 75`).
  The latest #1066 triage further records that F12.7 (#1064) and F12.8 (#1065)
  precede it. #544 is now closed and its `Verify` command exists, despite the
  older #558 intake note saying it was open (latest #558 and #544 issue
  comments; source also confirms `Verify` at `pkgs/id/src/cli.rs:1955-1980`).

### Options

| Concern | Viable options | Trade-off |
| --- | --- | --- |
| Execution boundary | (A) Watch and compile against a connected hosted world; (B) run an isolated local scratch world. | A reuses the current remote compile route, but a save can mutate a shared world and needs network/admin credentials. B adds a local runner seam, but is safe by default, works offline, and gives the command a genuinely disposable target. |
| File watching | (A) Poll source contents; (B) use filesystem events, debounce them, then rescan the declared inputs. | Polling is simple and avoids event-loss edge cases, but spends work while idle and adds polling latency to the three-second budget. Events are responsive, but may be duplicated/coalesced or miss a change; a debounce plus full bounded rescan handles those cases. |
| Candidate activation | (A) install/restart on every successful compile; (B) F12.9 probe/migrate, committing only after its validation. | A is simpler but discards scratch state and bypasses the exact migration being developed. B is gated on #1066, but matches the issue and exercises the production upgrade semantics. |
| Fixture compatibility | (A) keep strict module-hash matching only; (B) add cross-version behavior to normal replay; (C) retain strict normal replay and add an explicit `dev` regression mode. | A makes old fixtures useless after edits. B weakens a useful safety check for every caller. C allows old recorded inputs/expected records to test a candidate while leaving `replay`/`verify`'s existing contract intact. |
| Fuzz placement | (A) run an unbounded fuzz campaign on every save; (B) run a bounded deterministic campaign as an explicit/optional check, with a small opt-in smoke budget. | A makes the latency target unpredictable. B makes failures reproducible and keeps the default edit loop responsive; longer campaigns remain user-invoked. |

## Recommendation

Implement `id world dev DIR` as a **local, offline, long-running authoring
session**. It watches the app's declared Roc source and platform inputs, compiles
to a candidate with the existing bounded compiler engine, and keeps one
isolated, disposable scratch world alive. Use the existing in-memory core and
world actor, plus the F12.9 upgrade operation (and its journal adapter if the
upgrade API requires one), not a second dev-only world state machine. Do not
connect to or install into a hosted world.

On each edit, debounce filesystem events, rescan the bounded declared inputs,
and compile once. Treat that snapshot as the candidate version; if files change
again during compilation or validation, discard the stale candidate and build
the newest snapshot. A compile error reports diagnostics and leaves the current
scratch program running. Before activation, replay configured regression
fixtures against the candidate from their recorded input sequence and expected
records. Use replay's expected-record comparison for this gate; `verify` checks
that two fresh runs agree, not that the candidate agrees with the fixture's
recorded expected state (`pkgs/id/src/world_fixture.rs:407-421, 427-442`). Then
ask F12.9 to migrate the live scratch state on its probe instance.
Promote only if fixture checks and migration both pass; on either failure,
report the reason and keep the prior program/world running. The initial compile
creates the scratch program; later edits use migration, never a clean install.

Keep `id world replay` and `verify` strict. Add an explicit cross-version
fixture mode used only by `dev`: a fixture's old module hash remains provenance,
but is not a candidate hash gate; its recorded inputs and expected records are
the regression contract. Do not remove or rewrite the hash check for ordinary
replay. The recorded hash is a content-consistency check, not an authenticity
signature (`pkgs/id/src/world_fixture.rs:341-356`). A fixture with incomplete
history, no expected records, an unsupported event, or an input before the last
install cannot gate a dev candidate; fail with a specific diagnostic and
require a suitable complete fixture instead.
The fixture runner must not claim to cover unrecorded host events (the existing
fixture contract documents this caveat in `pkgs/id/src/world_fixture.rs:416-421`).

Keep fuzzing separate from the every-edit critical path. Provide a deterministic
seeded harness over bounded generated guest inputs and a small, versioned
invariant declaration format. V1 invariants should be deliberately narrow and
machine-checkable: guest calls do not trap, records remain valid JSON, declared
record keys remain present, and declared numeric bounds/order relations hold.
The command prints the seed and first failing input sequence so the failure is
reproducible; the checked-in acceptance test includes a known seed that exposes
a deliberately faulty example/invariant pair. A small explicit fuzz smoke run
may be requested in `dev`; the full run is a separate command/flag and never
delays ordinary save-to-running. Do not use nondeterministic host entropy in
the generated input sequence.

### Why this option

This composes the existing bounded compiler, offline replay, deterministic
verification and probe-validated snapshot ideas without making a developer's
save a remote deployment. It also makes the most important gap explicit:
module-bound production fixtures need a narrowly scoped dev regression mode,
not a silent relaxation of all replay checks. The three-second goal is
measurable on a small Roc example after warm-up, while fuzz runs remain
reproducible without turning that latency goal into an unbounded promise.

## Invariants

1. **No remote side effects:** `id world dev` makes no network connection and
   cannot install into a named hosted world. Its in-memory scratch world is
   isolated from user worlds and discarded when the session exits.
2. **One source snapshot per candidate:** compiler, fixture and migration
   diagnostics identify the same source/module hash. A candidate invalidated
   by a subsequent edit is never promoted.
3. **Last-good preservation:** source/compiler/fixture/migration failure leaves
   the currently running scratch version and its state intact.
4. **F12.9 is authoritative:** hot-swap uses its probe/migrate/commit/rollback
   path. No alternate direct state replacement is permitted.
5. **No broad replay relaxation:** normal `replay`/`verify` still reject a
   module-hash mismatch. Only `dev` opts into cross-version regression replay,
   and it reports that the fixture was recorded under a different module.
6. **Deterministic fuzz:** the same candidate, declared invariants, seed and
   case budget produce the same input sequence and first failure.
7. **Bounded work:** compile inputs, fixture sizes, generated input sizes,
   fuzz cases and run time have explicit limits; errors do not create an
   infinite rebuild loop.
8. **Latency definition:** edit-to-running is measured from the debounced
   filesystem change to the CLI's successful “candidate active” result,
   including compile, fixture replay and migration. It excludes optional fuzz
   runs and initial process startup; report the cold-start number separately.

## Acceptance criteria for implementation

- `id world dev DIR` runs without network access, uses a disposable in-memory
  scratch world, and watches all declared source/platform inputs.
- Saving a valid change compiles one candidate and hot-swaps through F12.9
  migration. Saving invalid source, failing a fixture, or failing migration
  reports the failure and leaves the last-good version running.
- A migration test changes snapshot format/state, preserves the migrated
  records, and proves a deliberately failing candidate leaves the previous
  program and state active (F12.9's issue #1066 exit).
- A complete fixture recorded under an earlier module hash replays against a
  candidate on each change and compares the declared expected records. A
  deliberately mismatching candidate is reported and not promoted. Ordinary
  `replay` and `verify` still reject module mismatches.
- The fixture path reports unsupported/partial/missing-expectation cases
  clearly and does not imply host-event coverage beyond the recorded stream.
- The deterministic fuzz command accepts an explicit seed and bounded case
  budget, checks the declared invariants, prints a reproducible first failure,
  and passes a fixed-seed regression test that catches the seeded faulty
  example/invariant pair.
- On a documented small Roc example, after warm-up, the p95 of 20 save-to-active
  edits is under 3 seconds on a recorded toolchain/machine. Include compile,
  fixture and migration time in that number; report cold startup separately.
- CLI parse/help and integration tests cover start/stop, debounce/coalescing,
  stale candidate discard, last-good preservation, fixture failure, migration
  rollback and deterministic fuzz replay.

## Phased implementation plan

Every phase is a separately reviewable, mergeable slice. The order below keeps
the CLI usable at each merge and avoids landing a fake migration path.

1. **Local scratch runner and one-shot `dev` (foundational).** Add the command
   shape, local compiler configuration/source discovery, temporary isolated
   world lifecycle and one-shot compile/launch. Reuse existing compiler bounds;
   test cleanup and prove no remote client is constructed. This is useful
   before watch support and establishes the local-world seam.
2. **Watch, rebuild and transactional hot-swap.** Add event watch + debounce +
   bounded rescan, source snapshot identity, stale-candidate discard, and
   last-good diagnostics. Integrate only after F12.9 (#1066) and its upstream
   ABI/SDK prerequisites land. Hot-swap the scratch world through the F12.9
   probe/migration path; test successful migration and rollback.
3. **Fixture replay as a promotion gate.** Add `--fixture` inputs and the
   dev-only cross-module-hash regression mode. Keep ordinary replay strict.
   Run fixtures against the candidate before promotion; report and retain the
   last-good scratch world on failure. Test old-hash pass/fail cases and
   unsupported fixture diagnostics.
4. **Deterministic fuzz and declared invariants.** Add the bounded invariant
   file format, seeded input generator, counterexample reporting and
   fixed-seed seeded-bug test. Keep it opt-in or a small bounded smoke run so
   it does not enter the normal edit-to-running latency path.
5. **End-to-end latency and authoring docs.** Add the repeatable small-Roc
   benchmark, verify p95 under three seconds with fixtures and migration
   included, document setup/troubleshooting and run the relevant package/CLI
   checks. If the target misses, optimize the measured stage and retain the
   same correctness gates rather than dropping fixture or migration work.

### Dependency gate

F12.15 implementation must not start its hot-swap phase until F12.9 #1066 is
implemented. The newest F12.9 triage records F12.7 #1064 and F12.8 #1065 as
upstream prerequisites, consistent with the Phase 12 sequence at
`.opencode/plans/phase-12-platform-flexibility.md:75`. The F11.16 replay
prerequisite #544 is already satisfied. These sequencing facts do not block
this design record; they determine when phase 2 can merge.
