# Design: ID core v1 — app model and minimum capabilities

- Date: 2026-11-01
- Status: **design** — implementation is planned in four separately mergeable steps below; this record changes no implementation.
- Issue: #2028, “ID core build v1 — app model + capability system, enough to start app examples” (parent epic #2056).
- Decision basis: the latest #2028 synthesis comment (2026-11-01) combining the app-packaging investigation #2026 and capability-taxonomy investigation #2027. Where the earlier taxonomy's ordering differs, this newer synthesis controls.

## 1. Decision to make

What is the smallest ID core—an app model plus a capability/presentation set—that enables the sticky-notes (#2031), chat (#2051), and boards (#2054) examples without making them wait on hardware, location, media, speech, or other v1.1 work?

**Decision:** land app-folder packaging and host discovery first; then add exactly one structured interface capability, `form.*`, together with a bounded `Form` presentation; then make `text/1` a first-class projection for every presentation; finally bind the app's declared web routes to the existing web host. Extend the existing `world_caps` and `WorldSurface` seams. Do not create a second capability protocol or an app-supplied HTML/DOM surface.

The recommendation intentionally follows the order recorded in the latest #2028 synthesis: packaging (#2324 / task 5769), `form.*` (#2340 / task 5770), `text/1` (#2339 / task 5771), then the web adapter (#2325 / task 5772). The taxonomy investigation had proposed `Text` as the first surface variant, but the newer synthesis puts the structured input needed by the first apps first; `text/1` remains required before the web binding is complete.

## 2. Context and evidence

### The request and settled scope

The #2028 issue body asks for a “ruthlessly” small app model and capability set that lets the sticky-notes, chat, and boards work start. Its latest synthesis comment records three options, recommends packaging → `form.*` + `text/1` → web adapter, and explicitly defers the rest of #2027's taxonomy. It says the first real app after the four core steps should be sticky-notes, after its own design step; the pack step remains deferred until the discovery shape survives the PoC. This is the controlling scope, not a request to implement every filed capability.

### What exists in `pkgs/id` now

- **There is a reusable program and host seam, not an app registry.** The `WorldProgram` contract covers initialization, update, view/layout, records, wants, and snapshot/restore (`pkgs/id/src/world/mod.rs:871-925`). The existing `PeerDiscovery` is peer/server gossip, not packaged-app discovery (`pkgs/id/src/discovery.rs:1-20,324-365`).
- **The world-apply manifest is an operator/runtime artifact.** It contains such things as module hash/source, grants, ceilings, profile, and schedule (`pkgs/id/src/world_manifest.rs:1-55`); world diff/apply parses and applies it (`pkgs/id/src/commands/world.rs:477-535,1025-1085`). It must not be overloaded into the proposed app manifest.
- **Capability requests already have a bounded protocol and enforcement path.** `world_caps` defines wants/results and subscriptions/events (`pkgs/id/src/world_caps.rs:1-24,52-89,215-307`); `CapLedger` checks grants and ceilings (`pkgs/id/src/world_caps.rs:467-592`). The actor handles providers and recomputes wants (`pkgs/id/src/world/actor.rs:442-496,618-660`), while compile-time imports are gated against effective grants (`pkgs/id/src/world_compile.rs:111-149,197-225`). The new interface capability belongs in this path.
- **Presentation is typed only for `Screen`.** `WorldSurface` has one variant and the existing plain UTF-8 path is separate (`pkgs/id/src/world_presentation.rs:23-43,256-271`). The session validates and transmits view data and optional surface (`pkgs/id/src/world_session/mod.rs:2038-2082`). SSH renders screens to ANSI (`pkgs/id/src/world_ssh.rs:904-925`); the browser handles a screen or falls back to text and builds text-only DOM nodes (`pkgs/id/web/src/world.ts:175-178`, `pkgs/id/web/src/world-surface.ts:343-449`). The newest presentation design likewise records that text is currently untyped and `Screen` is the sole `WorldSurface` variant (`doc/2026-10-31T17-47-20Z_design_world_presentation_and_fuel/2026-10-31T17-47-20Z_design_world_presentation_and_fuel.md:70-95`).
- **The existing example path is usable as the proof point.** `roc-screen` imports the shared screen/platform types and emits a screen document (`pkgs/id/examples/roc-screen/main.roc:1-23`); its build script builds the host adapter and validates the resulting Wasm (`pkgs/id/examples/roc-screen/build.sh:32-44`). Existing app candidates are examples, not registered packages; #2026 identifies `roc-world` and `tic-tac-toe` as the first packaging candidates (see its §3).

### Decisions already established by prior records

The #2026 packaging record proposes `pkgs/id/apps/<id>/app.toml`, folder-name/ID equality, folder-relative content, strict unknown-field rejection, and at least one interface section. It distinguishes an app manifest from the world-apply manifest and says the app requests capabilities while the operator grants them (#2026, §1–3). Its proposed schema is at `doc/2026-10-29T12-50-36Z_design_id_app_packaging/2026-10-29T12-50-36Z_design_id_app_packaging.md:47-91`; discovery behavior is at `:116-120`.

The #2027 taxonomy says to extend `world_caps` and `WorldSurface`, not create parallel systems, and excludes guest-supplied DOM/HTML. It proposes bounded `Form` data and a line-oriented text presentation whose projections are available for each surface (#2027, §7–8; `doc/2026-10-29T14-05-00Z_investigation_capability_taxonomy/2026-10-29T14-05-00Z_investigation_capability_taxonomy.md:211-237`). Those are proposals, not shipped behavior; the current-code evidence above and the newer #2028 synthesis confirm that.

## 3. Options and trade-offs

| Option | What it includes | Benefits | Costs / why not chosen |
| --- | --- | --- | --- |
| **A. Full taxonomy now** | App packaging plus all #2027 follow-ups (device info, text, forms, location, media, MQTT, speech, style) and pack/build work. | Broadest device and presentation coverage; fewer deferred capability decisions. | Makes the first examples wait on hardware, MQTT, sensors, media and speech they do not need. It expands the first build beyond the issue's smallest-core constraint. |
| **B. Packaging only** | `app.toml`, `apps/`, discovery and web binding; no new structured interface. | Quickly tests packaging and host registration. | Sticky-notes/chat still lack structured input. They would encode forms in terminal grids or invent app-specific workarounds, multiplying future migration cost. |
| **C. Phased minimum — recommended** | Packaging/discovery; one `form.*` capability and typed `Form`; `text/1` for all surfaces; then app-declared web adapter routes. | Establishes a real app folder, grants, structured input and a transport-neutral readable mode, enough for the named examples; each slice can land and be tested separately. | Defers specialized device and media behavior; makes example authors wait for the ordered core slices rather than starting permanent apps on an unreviewed packaging PoC. |

## 4. Recommended design

### 4.1 App model and discovery

Adopt the #2026 app-manifest vocabulary and layout, constrained to what the four v1 steps consume:

```text
pkgs/id/apps/<app-id>/
  app.toml
  program/                 # source or prebuilt module, when applicable
  assets/                  # retained for later packaging; not packed in v1
  web/                     # adapter-owned templates, if needed later
```

`app.toml` is the **app manifest**, distinct from both the operator-authored **world-apply manifest** and the generated **web-build manifest**. Use the proposed `[app]`, `[program]`, `[interfaces.cli]`, `[interfaces.web]`, and `[capabilities].request` sections from #2026. Keep the proposed `id`, `name`, `version`, and description fields; program source and `module_hash` are mutually exclusive; CLI/web declarations describe offered interfaces; capability declarations are requests only. Do not implement the `direct` web mode or resource hashing/packaging in this v1 core.

The host scans `apps/*/app.toml` at startup and on an explicit reload, validates each app, then registers its declared interfaces and requested capabilities. Each app is self-contained: paths are relative to its folder, its folder name must equal its manifest ID, unknown fields fail validation, and a manifest with no interface section is invalid. A malformed app is disabled with a named diagnostic without taking down host startup. These constraints are the #2026 proposal and match #2028's latest PoC acceptance (first `tic-tac-toe` package; malformed-manifest rejection).

App metadata cannot elevate authority. The app manifest may request capabilities; only operator-side world configuration grants them. Keep both the current capability ceiling and grant checks in force, including at compile time. In particular, a requested capability must never silently become a grant.

### 4.2 One capability extension: `form.*`

Add the smallest structured-input vocabulary required by the first apps: `form.*` with one typed `Form` presentation variant. A `Form` carries bounded, validated field descriptions, validation hints, and named actions; a user submission returns as a `form.result` event through the existing wants/subscription mechanism, since a user may answer well after the initial request. Keep one active surface at a time so presentation replay remains deterministic, and preserve the current `Screen` behavior.

The guest supplies data, never executable or trusted markup: no HTML, CSS, script, DOM nodes, or guest-selected asset URLs. Validate form shape, field counts, string/argument bounds, and submitted values at the host before rendering or delivering a result. Enforce `form.*` through the existing catalog, request/subscription-event path, `CapLedger`, and operator grant path; do not create a second registry or transport. Form definitions must fit the existing wants-size bound and submitted values the existing argument-size bound; use the existing constants rather than adding a form-specific larger limit. The implementation issue should name the exact constants and add boundary tests.

### 4.3 Make `text/1` a first-class projection

Formalize line-oriented UTF-8 text as `text/1`, not an accidental fallback. Add a `Text(TextSurface)` `WorldSurface` variant whose payload is an ordered sequence of UTF-8 lines. It is append/readable output without cursor addressing or redraw. Every active surface has a deterministic text projection: `Text` is its own projection, `Screen` is readable lines, and `Form` is fields plus numbered/named actions. This makes a pipe, transcript, SSH text client, or browser without a rich renderer useful without weakening the typed surface contract. Text is a main presentation mode, not a fallback or capability grant.

Keep the legacy untyped text path readable for existing programs, and keep old `Screen` frames valid; new `text/1` producers use the typed variant. Do not add multi-surface composition, a layout/focus engine, or cursor animation to this step.

### 4.4 Bind apps to the existing web host

For this phase, support the adapter path only. The host reads `[interfaces.web]` from the app manifest and binds the declared page route and optional socket route to that app's host implementation. In particular, the initial `world` package uses `/world` and `/ws/world` as in #2026. Test with two apps so route selection is manifest-driven rather than a single hard-coded world route. The adapter renders validated `Screen`, `Form`, and text data; guest content remains inert data, not page markup.

The direct-web path and its generated build manifest are not part of this core. They can be reconsidered after adapter-backed examples establish that per-app frontends are necessary.

## 5. Invariants

1. **One capability system:** extend `world_caps` wants/results/subscriptions and `WorldSurface`; do not add a parallel app permission protocol or bypass `CapLedger`/compile-time grant checks.
2. **Request is not grant:** `app.toml` records requests. Effective grants remain operator-owned by the world-apply flow.
3. **Stable app identity:** `pkgs/id/apps/<id>/app.toml` has `app.id == <id>`; app-owned paths cannot escape the app folder.
4. **Fail closed, isolate failures:** malformed or unknown manifest data disables only that app, with a diagnostic; it does not silently reinterpret fields or stop the host.
5. **Bounded typed data:** every new surface and form submission is validated and bounded before it crosses the host/program seam. Guests never supply HTML/CSS/DOM.
6. **Compatibility:** existing text-only programs and `Screen` payloads remain usable while `text/1` and `Form` are introduced; adding a surface must not change the meaning of existing tags or grants.
7. **Future sensor safety:** location/media/speech and other sensor capabilities are outside v1 and must never be wildcard-grantable if later added. Consent remains explicit and revocable per use, as specified by the taxonomy record.
8. **PoC is evidence, not the permanent feature:** review the packaging/discovery shape from the `tic-tac-toe` proof before building the first permanent app on it; do not let an unreviewed PoC silently become the permanent interface.

## 6. Acceptance criteria for implementation

The v1 core is ready for app examples when all of the following hold:

- A valid app folder can be discovered, validated, and represented without changing the world-apply manifest format; unknown fields, mismatched folder/ID, missing interfaces, invalid paths, and malformed TOML are rejected with app-scoped errors.
- One invalid app does not prevent another valid app or the host from starting. Reload/discovery behavior is deterministic and has a targeted test.
- The packaged `tic-tac-toe` proof exercises the supported app-manifest program form and demonstrates that discovery is not tied to its folder's legacy example path.
- A program can request `form.*`; no grant is implied by packaging; a granted form round-trips validated user input through the existing capability protocol; an ungranted request is refused through the existing refusal behavior.
- Form bounds and malformed payloads are rejected, guests cannot inject markup, and existing `Screen` validation/rendering remains unchanged.
- A `text/1` consumer can read every supported surface as deterministic line-oriented output; old plain text and `Screen` clients still behave as before.
- Two apps can coexist with routes declared in their manifests; `/world` and `/ws/world` resolve to the intended app, and the adapter renders only validated surface data.
- The sticky-notes, chat, and boards authors have the app folder/discovery contract, structured form input, readable text contract, and web adapter binding needed to proceed without needing sensors, MQTT, speech, or a direct-web runtime.

## 7. Phased implementation plan

Each phase is a small PR/issue-sized change that can be merged and verified on its own. The order is deliberate: each step extends the interface established by the prior step, so the steps are **independently mergeable**, not independent parallel work.

| Phase | Scope / issue packet | Mergeable result and done check |
| --- | --- | --- |
| **1. App packaging PoC** | #2324; latest synthesis task 5769. Package `tic-tac-toe` under `pkgs/id/apps/` with `app.toml`; implement host discovery and malformed-manifest rejection. Keep the pack step deferred. | Discovery registers a valid fixture; invalid manifests produce named per-app failures without stopping host startup; folder ID and relative-path checks are tested. Review the PoC shape before a permanent app depends on it. |
| **2. Structured form capability** | #2340; task 5770. Add `form.*` and the `Form` `WorldSurface` variant using bounded DTOs and the existing wants/grants protocol. | A granted form round-trips a user action; ungranted requests follow existing refusal behavior; bounds, validation, replay, and no-HTML/CSS invariants have tests; `Screen` compatibility is retained. |
| **3. `text/1` contract** | #2339; task 5771. Formalize the line-oriented text representation/projection for every surface. | Golden/contract tests show deterministic text for Text, Screen, and Form; a text-only consumer needs no cursor support; legacy text behavior remains covered. |
| **4. Web adapter binding** | #2325; task 5772. Bind `[interfaces.web]` routes from `app.toml` to the existing host adapter, including `/world` and `/ws/world`. | A two-app routing test proves manifest-driven isolation; Screen/Form/text render through trusted host code only. The v1 core is then ready for the sticky-notes design/PoC (#2031), which should be triaged next. |

Do not fold the pack step into phase 1: #2026 explicitly makes content hashing/packaging later, and #2028's latest synthesis defers it until discovery survives the proof. Do not pull in #2338–#2345 (device info, text, forms, location, media, MQTT, speech, style) wholesale: #2339 and #2340 are the only capability follow-ups in this v1 sequence; the remaining work stays v1.1 or later.

## 8. Risks, deferred decisions, and Drew

- **Compatibility risk:** `WorldSurface` is consumed by session serialization, SSH, and browser code. Append surface types compatibly and test old payloads at each adapter; do not assume a Rust enum change is wire-compatible without checking the encoding path.
- **Manifest drift:** schema v1 should be strict and versioned. Unknown fields are errors, not ignored; add fields only through a reviewed schema change.
- **PoC overreach:** phase 1 proves packaging/discovery; defer permanent app architecture and packing until its shape is reviewed.
- **Deferred scope:** the eight #2027 taxonomy items remain individually filed; do not broaden v1. The ESP32/MQTT choice (#2343: Home Assistant bridge vs ID speaking MQTT directly vs direct web) should be made when the first hardware app is scheduled, not for this web/TUI/text core.

**Questions that genuinely need Drew for this design: none.** The #2028 synthesis says no question blocks v1. The MQTT choice is a deferred v1.1 decision with the options and recommended timing above, not a prerequisite to these four steps.
