## 1. Decision in one paragraph

Exactly one layer auto-scales: the **stateless currency-service front-end**, which
scales out and in automatically on demand signals (§2). The store layer **never
auto-scales across stages**: a stage transition (A→B, B→C) is a reviewed,
evidence-gated migration, *triggered for review* — never executed — by sustained
envelope pressure measured the way #5829 prescribes (§4.2). Hot accounts are
mitigated inside the current stage (§3) long before they are a reason to move
stages. Everything whose change alters money semantics — the backend stage, the
system of record, the invariant suite, authorisation requirements — is on the
never-auto-scale list (§5).

## 2. The front-end: stateless, automatically scaled

### 2.1 Shape

- A front-end instance holds **no request-relevant state**: no sessions, no cached
  balances used for decisions, no in-memory idempotency record, no account affinity.
  Any instance can serve any request; correctness state lives entirely behind the
  #5823 port (Stage A: journal + Redis projection per #5824).
- The request path per instance: authenticate/authorise (including the #2290
  RateAuthorisation check before posting, per #5828), call the port, return the
  port's per-item typed results unchanged. Conversion (#2063) runs through the same
  path; a converted transfer's legs post or fail as #5828 declares.
- Instance replacement is invisible: killing any instance mid-load loses no
  committed transfer (the commit point is the store's, #5824 §2.1) and no
  in-flight request outcome — a client retry with the same idempotency key returns
  the original outcome from the store, whichever instance serves the retry.

### 2.2 Autoscaling rule

- **Scale-out signal** (any, sustained over a 5-minute window): in-flight request
  concurrency per instance above its configured ceiling; request queue depth
  (accepted-but-unstarted requests) above zero and rising; or posting p99 latency
  above the current stage's #5829 envelope ceiling while store-side latency is
  inside its envelope share (i.e. the bottleneck is demonstrably the front-end,
  not the store — scaling the front-end against a store bottleneck is prohibited,
  it only deepens store contention).
- **Scale-in signal**: all scale-out signals below half their thresholds for a
  30-minute window, with a per-action cooldown at least as long; scale-in removes
  one instance at a time and never below the configured minimum (≥ 2, so a single
  instance failure is never an outage).
- **Bounds**: a configured maximum instance count caps cost; hitting the cap is an
  alerting event, not silent degradation — sustained cap saturation is a
  stage-pressure signal under §4.2.
- Scaling changes **capacity only**. It must be impossible for a scaling event to
  change any transfer's outcome (§6, invariant A1).

## 3. Hot-account mitigations (inside the current stage)

A single popular currency/account is the expected hot spot (parent, load model).
Mitigations apply in this order; each is a performance device only — correctness
never rests on any of them (the #5824 rule for Stage A devices, generalised).

1. **Per-account striping.** Posting contention is striped per account behind the
   port, so one hot account serialises only against itself, never against
   unrelated accounts. Striping never reorders a single account's postings.
2. **Batched postings.** The port's batched-transfer shape (#5823 §3) is the burst
   absorber: clients and internal producers batch where their semantics allow,
   and the front-end coalesces concurrent single postings to the same account
   into one port call when they arrive inside a short (≤ 10 ms) window, returning
   each caller its own per-item result.
3. **Queue-based burst smoothing.** A bounded queue in front of the port absorbs
   bursts up to the stage's #5829 burst floor (Stage A: 6,000 tps / 60 s). The
   queue is finite by design: at capacity, new postings are refused with an
   explicit retryable error — never buffered without bound, never silently
   dropped after acceptance.
4. **Cached balance reads for approximate consumers only.** Dashboards and other
   explicitly approximate consumers may read cached balances with the stage's
   declared staleness bound (#5829 envelopes: ≤ 1 s cached). Posting decisions
   and caller-facing balance answers after an acknowledged write follow #5824
   §2.3 (read-your-committed-writes) at every scale, on every instance.
5. **Per-account fairness.** Sustained load from one account must not starve
   others: the smoothing queue schedules across accounts (weighted round-robin
   by account), so a hot account consumes its share of port capacity, not all
   of it.

## 4. Scaling triggers

### 4.1 Automatic (front-end only)

The §2.2 rule, and nothing else, is automatic. Its metrics — per-instance
concurrency, queue depth, posting p99 split front-end vs store — are among the
measurements #5829 §5.5 already requires campaigns to publish in trigger-ready
form, and production telemetry must report the same metrics under the same
names, so a trigger threshold means the same thing in a campaign and in
production.

### 4.2 Stage-transition triggers (review, never execution)

A stage transition review **opens** when either holds:

- **Sustained envelope pressure**: production load at or above **70% of the
  current stage's #5829 sustained floor** (Stage A: 2,000 tps → review at
  1,400 tps) on 14 of any 21 consecutive days, measured as daily sustained
  (not burst) throughput; or
- **Envelope breach under campaign**: a #5829 stage-gate campaign shows the
  current stage failing any envelope line (posting p99, read p99, recovery
  ceiling) at or below its sustained floor.

Opening a review is all the trigger does. The transition itself requires the
#5829 §6 stage gate (full campaign against the *target* stage, envelope record
published) plus the target stage's own migration design (#5826 for B, #5827
for C) — a decision recorded on the parent, executed as a migration, never as
an autoscaling action. This answers the parent's open question 2 with a
number, as it asked: Stage A stops being sufficient at sustained 1,400 tps
(70% of its envelope floor) — that is where the review starts, not where the
service falls over.

Within a stage, store capacity actions (Redis memory/CPU sizing, Turso
per-database provisioning in Stage B) are operator actions taken against the
same published metrics; they are not autoscaling and not stage transitions,
and they never change which store is the system of record.

## 5. What never auto-scales

- The **backend stage** (A→B→C) — §4.2: review-triggered, gate-executed.
- The **system of record** and the commit point (#5824 §2.1) at any stage.
- The **invariant test suite** and its pass rule (#5823 §4): no load condition
  waives, samples, or defers an invariant.
- **Idempotency and journal retention**: never shortened under load.
- **RateAuthorisation requirements** (#2290/#5828): load never skips or
  post-dates an authorisation check.
- **Reconciliation** (#5824 §4): it may scale its workers, but its coverage
  (every account, every currency) and its journal-wins rule never degrade
  under load.
- **Region topology**: v-next promises **single-region, strongly consistent**
  operation (parent open question 5). There is no automatic cross-region
  failover and no multi-region active operation in this design; both are
  deferred to a future parent-level decision, and no trigger in §4 implies
  them.
- **Schema and directory changes** (Stage B's currency→DB directory, #5826):
  operator-run migrations with invariant checks, never scaling side-effects.

## 6. Invariants implementation must hold

Inherited from the parent (principle 3) and #5823/#5824, plus the
autoscaling-specific set; each must be covered by the #5823 invariant suite
or the #5829 programme as named:

- **A1 — Scale-invariance of outcomes.** For any transfer sequence, the set of
  outcomes (posted/failed per item, final balances) is identical whether the
  front-end runs 1 instance or its maximum, and across scale-out/scale-in
  events mid-sequence. (Suite: run the #5823 case catalogue against a
  front-end whose instance count changes during the run.)
- **A2 — No instance-local correctness state.** Terminating every front-end
  instance and replacing them with fresh ones at any point loses no committed
  transfer and no idempotency outcome. (#5829 crash-injection leg, front-end
  fault point.)
- **A3 — Per-account order.** Mitigations (§3) never reorder one account's
  postings relative to each other; cross-account order is unspecified, as in
  the parent.
- **A4 — Bounded smoothing.** The burst queue's bound is a hard bound: beyond
  it, refusal is explicit and retryable; accepted work is never dropped.
- **A5 — Read honesty at scale.** Cached reads are served only to consumers
  declared approximate, always within the stage's staleness bound, and are
  never an input to a posting decision — on any instance, at any load.
- **A6 — Triggers change capacity, not semantics.** No §4 trigger alters the
  port, the outcome vocabulary (#5823 §3.6 stage-declared semantics), or any
  §5 item; a trigger's only effects are instance count (§4.1) or an opened
  review (§4.2).

## 7. Alternatives rejected

- **Automatic stage transitions on a metric threshold.** Rejected: a stage
  transition is a data migration between stores with different declared
  semantics (#5823 §3.6), not a capacity dial. Automating it would put the
  highest-risk operation in the system on the least-reviewed trigger.
- **Stateful / sticky front-end instances** (account affinity, local balance
  caches for decisions). Rejected: it reintroduces a single-writer bottleneck
  per account, makes instance loss a correctness event, and forks the
  read-consistency story per instance — against parent principle 2 and
  #5824 §2.3.
- **Scaling the store by adding hot-layer writers** (e.g. multiple Redis
  primaries for one projection in Stage A). Rejected: Stage A's authority
  rests on one journal and one idempotent apply path (#5824 §2–§3); writer
  multiplication buys throughput by spending the recovery story. Store
  pressure is a §4.2 signal, not a cue to fork the store.
- **Unbounded queue smoothing** ("never refuse a posting"). Rejected: an
  unbounded queue converts overload into unbounded latency and memory, and
  hides the stage-pressure signal §4.2 depends on. Explicit refusal at a
  published bound is the honest behaviour.
- **Per-account front-end sharding** (route account X always to instance N).
  Rejected: sticky routing by another name — state by stealth, with hot
  accounts pinned to fixed capacity instead of the pool's.
