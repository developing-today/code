# Design: per-user function mapping — bot battles, strategy hot-switching, human+AI-partner composition

- **Sibling states, verified fresh 2026-11-08:** #5955 OPEN/parked; #5964 OPEN/queued (design not yet landed); #5968 OPEN/parked (small_fix in flight); #5966 OPEN/parked; #5962 OPEN/parked; #5988 CLOSED/done. Where this design spends a concept a sibling owns (rebind mechanics, intent blending, the cutoff mechanism, budget invariants), it names the seam and does not redefine that part.
- **Method:** the mapping is specified as a deterministic function of its tick inputs, because the F8 adjudication substrate (§7) requires matches to be replayable by an auditor.

## Decision to make

A world maps over a set of user functions — one function per user, all matching one interface. Decide (1) the function interface and who owns the state between ticks, (2) the per-tick mapping algorithm and its complete failure table, (3) the switching/trigger model — cadence, immediate vs next-load, conditional selection, and which layer owns what, (4) how a human in control with an AI partner composes into the same mapping, and (5) fairness: how budgets keep one user function from starving the others.

## Recommendation

Give every user exactly one **binding** per world (§1): a bound function, its persisted state blob, and a controller that may be the function alone, a human alone, or a human+partner composite. Run the mapping once per tick in a **fixed deterministic order**, invoking each binding under its own **fuel budget** and collecting exactly one intent (or one failure outcome) per binding (§2, §3). Switches are **rebinds that take effect only at tick boundaries**, requested at any time, validated for interface conformance **at request time**, and selected either by the user-owned metered selector function or by an opted-in world trigger (§4). Treat the human+partner composite as one binding with one budget and a fixed authority order — human override, then partner proposal, then world default (§5). Make fairness a **fuel** property, never a wall-clock one: per-function fuel caps bound every invocation, and the world per-tick budget is enforced with a deterministic rotating start so budget exhaustion cannot permanently starve the tail of the order (§6).

## 1. The per-user function interface

- **Entry shape.** Two entry points: *init*, run once at bind time with the bind config, returning the initial state; and *step*, run once per tick with the view and the state, returning an intent and the next state. There is no per-tick setup or teardown beyond *step*; a function that needs phases encodes them in its state. *step* is the single per-tick entry point — no separate intent and cleanup calls — so one invocation is one metered unit with one outcome. That is what makes the failure table in §3 complete: every invocation ends in exactly one row of it.
- **The view.** The world offers a read-only **view** per tick: the world-defined snapshot the function may observe (its own entity, visible neighbours, public world state — the world author decides the projection). The view is data, not a handle: it carries no capabilities, and reading it is not metered (it is already materialised; metering starts at *step*). The view vocabulary is the world-defined one; the intent vocabulary belongs to #5968.
- **State persistence and ownership.** State is an opaque blob owned by the **binding** — in effect by the user, through their function. The world stores it between ticks, hands it back verbatim, and never interprets it. It is size-capped by the world (a bind-time constant); a *step* that returns an oversized state fails as a crash (§3) and the pre-tick state is kept. State survives a switch only when the user asks for a handover: a switch (§4) starts the new function from *init* unless the user supplies a state blob the new function accepts at bind time — a function never inherits a predecessor state silently, because the two cannot be assumed to share a schema.
- **Interface identity.** The interface is a named, versioned contract of the world (entry names, view and intent schemas). Conformance is a property of a function artifact, checked once at bind/switch time (§4) — never re-checked per tick.

## 2. The per-tick mapping algorithm

For tick *t*, the mapping runs:

1. **Freeze the binding set.** Apply every switch whose effective tick is *t* (§4). The active bindings for the tick, their functions, and their pre-tick states are now fixed; nothing that arrives during the tick changes them.
2. **Fix the order.** Order bindings deterministically: the rotating schedule of §6 over a stable binding order (registration order, tie-broken by binding id). The order is a function of *t* and the binding set only, so an auditor replays the same order.
3. **Invoke.** For each binding in order: if the remaining world per-tick fuel (§6) cannot cover the minimum invocation cost of the binding, the binding takes the world-budget-exhausted row of §3 without being invoked. Otherwise invoke *step* with the tick view and the stored state, under the per-function fuel budget of the binding, metered per F10 (§6).
4. **Collect exactly one outcome per binding** — an intent, or one failure row (§3). A binding never produces two intents and never produces none silently: the outcome is recorded in the tick log either way.
5. **Commit.** For each successful invocation, replace the stored state of the binding with the returned state (atomic per binding: a failure never half-commits). Hand all collected intents to the tick resolution of #5968 in mapping order.
6. **Log.** The tick log records the frozen binding set and order, the outcome row and fuel consumption of each binding, and any switch applied at step 1. This log is the F8 replay artefact (§7).

## 3. Failure table

Every invocation — and every binding skipped without invocation — ends in exactly one row. *Default intent* is the world-declared default for the entity of the binding; where the world declares none, it is the no-op intent of #5968. State means the pre-tick state unless the row says otherwise.

| Case | Detection | Intent used | State after | Recorded / follow-up |
| --- | --- | --- | --- | --- |
| Success | *step* returns | the returned intent | the returned state | fuel debited (F10) |
| Fuel exhaustion (gas) | the per-function fuel budget is spent mid-*step* (mechanism: #5966) | default intent | pre-tick state (no commit) | strike +1; outcome row: fuel-exhausted |
| Timeout | the wall-clock backstop fires (cooperative / single-host only, per C4) | default intent | pre-tick state | strike +1; outcome row: timeout; cross-host adjudication never cites this row — fuel is the portable bound (§6) |
| Crash | trap, panic, or undecodable return | default intent | pre-tick state | strike +1; outcome row: crash, with the trap class |
| Malformed intent | the returned intent fails #5968 validation | default intent | pre-tick state | treated as crash; outcome row: malformed-intent |
| Oversized state | the returned state exceeds the world cap | default intent | pre-tick state | treated as crash; outcome row: oversized-state |
| Contract violation | the function attempts an effect outside the *step* contract | default intent | pre-tick state | treated as crash and flagged; outcome row: contract-violation; repeated flags are an abuse-budget matter (the F8 per-counterparty budget precedent) |
| World budget exhausted | the world per-tick fuel is spent before the turn of this binding (§6) | default intent | pre-tick state (not invoked) | no strike — the user is not at fault; outcome row: world-budget-exhausted |
| Binding suspended | the strike limit was reached earlier (below) | default intent | pre-tick state (not invoked) | outcome row: suspended, until the user switches or repairs the function |
| Unbound mid-tick | cannot happen: the set froze at step 1 (§2) | — | — | a switch or unbind requested during tick *t* is a request about tick *t+1* (§4) |

**Strikes.** A strike is a per-binding counter of consecutive failure rows in the fuel-exhausted / timeout / crash family (including its treated-as-crash rows). A success resets it to zero. At the world-configured limit (default **3**) the binding is **suspended**: it stops being invoked and takes the suspended row until the user switches function or explicitly resumes it. Suspension is protective, not punitive: it stops a broken function from consuming scheduling slots every tick, and it is visible to the user with the last failure row attached.

## 4. Switching and triggers

- **A switch is a rebind.** Switching the function of a binding replaces the bound artifact (and, per §1, normally its state). The rebind mechanics — how a new artifact is loaded, linked, and made live — belong to #5964; this design fixes only when a switch takes effect and who may request one.
- **Cadence.** A user may request a switch at any time and as often as they like — every tick, every second, every minute; the request rate is not the bound. The effect rate is: a switch takes effect only at a **tick boundary**. Requests are stamped with the tick at which they were received and become effective at the freeze step (§2 step 1) of the next tick, in request order; several requests in one tick collapse to the last one. No switch ever lands mid-tick, because a mid-tick change would make the tick outcome depend on arrival timing and break replay (§7).
- **Immediate vs next-load triggers.** The world author may provide a **trigger function** that requests switches. Two modes, both boundary-effective: *next-load* (the default) makes the switch effective at the next tick boundary; *immediate* makes it effective at the next tick boundary too, but additionally pre-empts any already-queued user switch for that binding and notifies the user out-of-band at request time. Immediate is about pre-emption and notification, not about breaking the boundary rule — there is no mode in which a function changes during a tick.
- **Conditional strategy selection.** The pattern from the issue — *if green bots are visible, load the green-bot strategy; if green and blue, load the generic one* — is supported in two places, and the design assigns them disjoint jobs:
  - A **selector function** owned by the user: a small, separately metered function bound alongside the main one, evaluated at the freeze step with the incoming view, returning the id of the function to bind for this tick. Selection logic that inspects the world lives here. The selector runs under a small fixed fuel budget (a world constant); if it fails (any §3 row), the binding keeps its current function — a broken selector never unbinds the user.
  - A **world trigger** (above) may *propose* switches for bindings whose users have opted in to world-proposed strategies. A proposal the user has not opted into is advisory only: it is surfaced to the user, never applied.
  - **Ownership split:** the world owns *when* switches may take effect and may *propose*; the user owns *whether* a switch happens (their own request, their selector, or their opt-in) and *which* function is theirs. Neither layer may silently do the job of the other.
- **Conformance validation timing.** A switch is validated **at request time**, against the interface contract of §1: artifact identity, entry points, view/intent schema versions, state cap. A non-conforming target is rejected at request time, the requester learns immediately, and the current binding is untouched — conformance is never discovered at tick time, so the freeze step never has to improvise. This is the seam with #5964: hot-swap loads the artifact; this design requires the conformance verdict to exist before the rebind is queued.

## 5. Human + AI-partner composition

- **One binding, one budget.** A binding whose controller is a human with an AI partner is a **composite controller** on the same single binding: the mapping (§2) sees one binding, invokes one controller, collects one intent, and debits one budget. Composition is inside the controller, invisible to the scheduler; the mixed case is first-class precisely because the mapping never has to know.
- **Authority order.** Within a tick, the composite resolves to exactly one intent: (1) a human intent submitted inside the tick input window wins; (2) otherwise the partner proposal stands; (3) otherwise the world default. The partner is a *step* function in the §1 sense (it receives the view, it is fuel-metered from the budget of the binding); the human input arrives through the input path of #5968, and the blending mechanics — how a human intent modifies a partner proposal rather than replacing it, where a world enables that — belong to #5968. This design fixes only the authority order and the single-intent outcome.
- **Timing.** The partner computes its proposal during the invocation window of the binding. A human intent that arrives after the window closes is not lost: it is input to the *next* tick, where it wins by the same authority order. A human who goes silent simply has a partner-driven binding; a partner that fails takes the §3 row for the binding, and the human may still submit inside the window.
- **State.** The composite shares the one state blob of the binding. The partner reads and writes it through *step*; the human affects it only through intents. There is no second, human-owned state channel — one binding, one state, one audit trail (§7).

## 6. Fairness: fuel budgets (C4, F10)

- **Fuel, not wall-clock (C4).** The working interpretation recorded on #5967 (shown to Drew 2026-11-04, not objected to) is adopted as a rule of this design: cross-host fairness is specified in **fuel-style budgets**, because fuel consumption is deterministic and identical on every host, while wall-clock is not. A wall-clock deadline survives only as a cooperative, single-host backstop (the timeout row of §3); it is never the fairness mechanism and never appears in adjudication (§7).
- **Two budgets.** Each binding has a **per-function fuel budget** per tick, set by the world (it may vary by binding class, never by user identity beyond what the world rules publish). The world has a **per-tick fuel budget** (the invariants around it belong to #5962). The per-function budget is the primary bound: an invocation is cut off the moment it is spent (§3), whatever the world budget says.
- **Why a slow function cannot starve others.** Starvation by wall-clock is impossible by construction: a function consumes at most its own fuel budget, and fuel is debited as it runs, so a *slow* function and a *fast* function with the same consumption cost the tick the same. No function can consume fuel budgeted to another binding.
- **The one real starvation risk, and its guard.** If the sum of per-function budgets exceeds the world per-tick budget, late-order bindings can be cut by the world budget (§3, world-budget-exhausted) — and a fixed order would cut the *same* bindings every tick. The guard is the rotating schedule of §2 step 2: the start position of the order rotates deterministically with the tick number (a function of *t* and the binding set, so replay reproduces it), which spreads world-budget cuts evenly across bindings over time. Worlds that can afford it should instead size the two budgets so the world budget never binds; the rotation is the guarantee for worlds that cannot.
- **Metering (F10).** Deterministic wasmtime fuel already meters every GuestCall kind for world code; the open remainder this design owns is per-*user*-function metering inside a world. It is discharged as follows: each invocation debits the fuel account of its binding; the tick log (§2 step 6) records per-binding consumption and outcome; accounts are therefore auditable per user, per tick, from the log alone.

## 7. Adjudication and replay (F8)

The arena adjudication substrate recorded on #5967 (F8, design of 2026-10-28: match attestation + audit, program epic #2056) is the only prior design for adjudicating user-vs-user program contests, and this design is built to fit it: results are valid by mutual concession, or a witness re-runs the game logic over the messages of both players, and the full log is replayable by an auditor for validity and cheating. Every choice above serves that fit — boundary-only switches, a deterministic invocation order, fuel as the only portable bound, exactly one outcome per binding per tick. Given the frozen binding set, the views, and the budgets, the mapping has no hidden inputs, so the tick log of §2 step 6 is sufficient for a witness or auditor to reproduce every intent and every failure row exactly.
