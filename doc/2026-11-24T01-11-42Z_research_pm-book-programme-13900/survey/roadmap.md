## 2. How items roll up

- **Epic rollup** (`aggregator/src/epics.ts`): `uniqueEpicItemsByRef` takes every pool item classified Epic; `buildEpicRollups` groups children by `epicRef` and counts done/total — a child is done per `isEpicChildDone` (state/status). Rollups feed `/projects` (now the pool section of `/program`) and the `/roadmap` drill-down (header comment, `epics.ts`).
- **Complexity weighting** (`aggregator/src/weights.ts`, #1108): progress is weight, not counts — `effort/xs=1, s=4, m=12, l=40` (l is a floor, flagged open-ended); unsized items contribute no weight and are counted visibly as unsized, never zero-weighted. Summaries also split open weight by `mode/*` (physical/hybrid = hands weight, online, unmoded).
- **Epic closure gate** (`epics.ts` `evaluateEpicClosureGate` + `scripts/epic-closure-gate.ts`, monitored report-only by `fleet-monitor/epic_close_check.py`): an epic may not close while its complete subtree has open children / unmet conditions; blockers are enumerated by condition. This is the same invariant the Kaneo safety nets enforce from the other side (`invariant-sweeper.py` invariant (a), `closure-watchdog.py`).
- **Reparenting**: `aggregator/src/epic-reparent.ts` + `scripts/epic-reparent.ts` move sub-issue parents; conformance is checked by `scripts/check-epic-conformance.ts`.
- **Roadmap roll-up** (`/roadmap`, `/api/roadmap.json`): rows from three sources merge — (1) Grist `Roadmap` table (`sources/live.ts` `gristRoadmap()`), (2) repo files `planning/roadmaps/*.md` in developing-today/code + `ROADMAP.md` in dezren39/darwin-nix (`sources/repo-roadmap.ts`, #1738), (3) Project-pool/program data. Merge rule (#1738): a title in both repo-file and Grist collapses to the **repo-file row**; the Grist duplicate is noted in provenance and its links unioned in. Rows carry Title/Status/Horizon/Area/Intent-or-Notes/Links; horizons are validated (`roadmap-horizon.ts`: buckets Now/Next/Later/Ideas/Ongoing for repo files; aggregator `Horizon` type `today|tomorrow|next-3-days|longer|incoming` in `model.ts` for tier items — two different horizon vocabularies, see D11). View filtering is shared between the page and its twin (`filterRoadmapForView`, #8723). Annotations attach via `roadmap-annotations.ts` (see §4).
- **Program roll-up** (`/program`): per project — status distributions over Status/Area/Horizon/Kind (`projects.ts` `distribution(...)`), epic rollups, tracked-issue state, orchestration freshness; stale/conflicting Project Status vs derived state is surfaced, not hidden (`projects.ts`: canonical-status comparison #1198/#1199-family; `/conflicts` lists every live source disagreement).
- **Console roll-up** (`console/src/plan.ts`): a separate, simpler ladder for the phone app — `PHASES = doing|now|next|later|built` derived from labels (`phaseOf`), `KINDS = note|bug|change`, `CAPABILITIES` list with phases; `parseRoadmap` parses the plan doc's markdown table into `RoadmapRow`s. This is a *second* roadmap implementation, not a view of the aggregator's — see D12.

## 3. How prioritisation is computed / recorded

Priority is recorded in **four places that do not automatically agree** (the `/conflicts` page exists partly because of this):

1. **Fleet queue priority (execution order)** — numeric bands `10/20/30/40/50/70/90` (`design-reprioritization-2026-11-12.md` band map; queue tasks carry `priority`, claimed in priority-then-age order — `console/src/work.ts` `board()`: `ORDER BY (priority IS NULL), priority ASC, created_at ASC`). Programs map to bands in the 2026-11-12 scheme (P1–P3 band 20, P4–P6 band 30, P7–P9 band 40; the doc's "Queue re-banding — APPLIED (2026-11-12, queue lane)" section records the re-banding as done). Owner prompts from the console take the top band, 10 (`promptPacket` in `console/src/work.ts`: "Owner prompt from the console: top band (10)").
2. **Console task priority scale** — `PRIORITY_SCALE = [10,20,30,40,50,70,90]` (`console/src/ops.ts`); `Ops.setTaskPriority` writes it on queue tasks.
3. **Issue rank labels (console ranked-issues view)** — `RANKS = [expedite, priority/critical, now, priority/high, next]` with `RANK_PRIORITY` mapping to numbers (`console/src/ops.ts`); `Ops.priorities()` searches open issues carrying any rank label and sorts by rank then issue number; `Ops.setRank()` adds the new label *first*, then removes the others, so a failure never leaves an issue rankless. Intake routes assign ranks by kind (`console/src/plan.ts` `ROUTES`: per-kind labels + rank).
4. **Project fields (portfolio intent)** — Horizon + Status + Area on Project #4, and effort weights (§2) for progress. The Project's **single writer is the orchestrator** (`pm-stack/README.md`: "Agents and the dashboard do not edit Project fields directly; the aggregator reads the pool through the fleet feed") — a dashboard status change is a `status-request` action consumed by the orchestration pass, which performs the write itself (`aggregator/src/actions.ts` header).
5. **Quota-side prioritisation** (adjacent, recorded here because `/quota` is the PM surface for it): pool/route guidance, forecast and reweight proposals in `aggregator/src/quota-{guidance,forecast,reweight}*.ts` and `scripts/quota-reweight-proposals.ts` / `quota-weekly-review.ts` — proposals, recorded as records/PRs, not silent reprioritisation. Detail beyond this pointer: UNVERIFIED in this survey.

Design-doc frame: `design-register-2026-11-11.md` (the register of PM designs), `design-tracking-manifest-2026-11-11.md`, `lineage-manifest-2026-11-12.md` (which design/issue lineage each piece descends from — including, at line 329, the open question "#1518 Define code/config embeddings…"), `decisions-ledger-system.md` (2026-11-11: the ledger that decision sets mirror), `needs-user-actions-design-2026-10-26.md` (the needs-user/attention design; its 2026-10-27 update renames and redefines escalation semantics — the live vocabulary in code is the `needs-drew.ts` census + attention tiers, see D13).

## 4. How the answer-back flows work (roadmap/prioritisation angle)

Full catalogue in `website-pages.md` §F; the flows that change roadmap/priority state:

- **Decision sets** (`/decisions/<setId>`, console `#needs/questions`): an answer/defer/request-info records a resolution in the decisions store; the ledger catcher applies it to the Muse-side decisions ledger; a `status-request`-class consequence (e.g. an epic/project status change) is *not* written by the dashboard — it becomes an action (below).
- **Dashboard actions** (`POST /api/actions`): `triage` answers (answer/snooze/escalate/de-escalate/delegate/dismiss) and `status-request` are consumed by the orchestration pass — the Project's single writer — which applies them and reports back via `POST /api/actions/result`; the item's next published tier entry carries the ack. Priority-relevant: escalate/de-escalate are tier overrides with the reason recorded; snooze suppresses until a named time and renders visibly as "snoozed by you".
- **Console direct writes** (the exception path): rank changes (`setRank`), issue comments, queue actions (`queueAct`: claim/block/park-family verbs via `POST /console/api/queue/<task>/<action>`), and hands-done label removal are performed by the console itself through `gh`/the queue broker, audit-logged before execution (`console/src/{ops,work,server}.ts`). See D4.
- **Roadmap annotations** (`POST /api/roadmap/annotations`, `/alias`): Drew-side notes/aliases attach to roadmap rows without editing Grist or the repo files — the annotation store (`roadmap-annotations.ts`) is the aggregator's own, reconciled at render (`roadmap-reconcile.ts`).
- **Intake** (console `#more/intake`, `plan.ts`): a note/bug/change becomes a GitHub issue with the route's labels + rank *and* a queue packet (`triage.enqueue` or, once an issue exists, `prompt.enqueue`) — i.e. new work enters both the portfolio record and the execution queue in one action, with the rank from the route table, not chosen ad hoc.
