### T2a. Projector tables — `pm-stack/projector/schema.sql`, owner/writer: projector

- `pmp_items` — projector — GitHub issues and PRs keyed by repo-qualified ref `owner/repo#N`; the join key everywhere.
- `pmp_item_deletions` — projector — durable deletion markers keyed by ref; makes item deletion absorbing against stale replays (#6782).
- `pmp_comments` — projector — comments across all repos, including PR reviews and review/line comments Kaneo never syncs; primary key `(id, kind)`; `deleted` is the tombstone flag.
- `pmp_links` — projector (human/agent-written via the link registry) — the link registry: subject↔GitHub ref relations (`tracks` | `implements` | `relates`); subjects are `kaneo:<projectSlug>/<taskId>`, `grist:<docId>/<tableId>/<rowId>`, or `gh:<ref>`. The map calls it: "**No. The only non-rebuildable cross-service relationship in the projector schema:** human/agent-written subject↔GitHub links" (`pm-stack/SHARED-SCHEMA-MAP.md`).
- `pmp_deliveries` — projector — webhook deliveries; the GitHub delivery GUID is the unique key, so a redelivered webhook is applied at most once; `outcome` is `applied` | `duplicate` | `ignored` | `error`.
- `pmp_delivery_errors` — projector — the first failed attempt per delivery, kept separately so a successful retry does not erase the original failure evidence.
- `pmp_sync_state` — projector — reconciliation cursors, one per `(repo, stream)`; streams are `issues` | `prs` | `issue_comments` | `review_comments` | `reviews`.
- `pmp_push_events` — projector — push events recorded for audit and later exec-strip aggregation; read-only here, the projector does not write back to GitHub.
- `pmp_hot_events` — projector — append-only normalized change ledger over the webhook stream (#5204); `seq` is the monotonic cursor consumers paginate on; `event_id` is stable per (delivery, sub-event).
- `pmp_consumer_checkpoints` — projector — per-consumer sweep checkpoints over `pmp_hot_events.seq`; a checkpoint only ever moves forward.
- `pmp_v_links_items` (view) — projector — every link joined to the linked item's live state and title.
- `pmp_v_subject_activity` (view) — projector — one unified activity stream per subject: every comment on every linked item, newest first.

## T3. Projector conflict rule

Sources: `pm-stack/projector/schema.sql` (header contract), `pm-stack/projector/src/store.ts` (`upsertItemStatements`, `commentUpsertStatement`, `upsertLink`, `deleteItem`, `markCommentDeleted`), `pm-stack/projector/README.md`, `pkgs/pm-projector/package.nix` (build only — no conflict logic).

**The plain statement the chapter should carry:** there is no human dispute-resolution rule for links/edges in the projector code — no disputed flag, no arbitration, no multi-writer vote. What exists instead is a set of coded overwrite guards that decide every conflict mechanically, by source timestamp and by primary key. The projector's own header states its posture: "The projector is glue: GitHub stays the source of truth for code work, Kaneo/Grist stay the source of truth for their own layers, and this database only holds links and projections. It is disposable … It never writes back." (`pm-stack/projector/schema.sql`).

The coded rules, one per object:

- **Items — monotonic, stale never wins.** "Upsert an item. Monotonic: a stale source (older updated_at) never overwrites." (`pm-stack/projector/src/store.ts`, `upsertItemStatements`). The guard key is `source_updated_at`.
- **Items — deletion is absorbing, with one escape.** "Deletion is absorbing (#6782): an item whose ref carries a deletion marker is not recreated by an event at or before the deletion's source timestamp (stale webhook replays, in-flight reconcile responses). An event strictly newer than the marker wins and clears it — GitHub is the source of truth, and such an event means the item demonstrably exists at a later source time than its deletion." (`pm-stack/projector/src/store.ts`). The marker lives in `pmp_item_deletions`; the marker itself is monotonic — "a later delete event refreshes it, an older one never moves it backwards" (`deleteItem`).
- **Comments — monotonic guard + tombstone absorption.** The comment upsert's conflict clause is `ON CONFLICT(id, kind) DO UPDATE … WHERE pmp_comments.deleted = 0 AND (excluded.source_updated_at >= pmp_comments.source_updated_at OR …)` — a deleted (tombstoned) comment accepts no update at all, and a live comment accepts only an update whose payload-reported last-update time (`updated_at`; `submitted_at` for reviews) is at or after the stored one (`pm-stack/projector/src/store.ts`, `commentUpsertStatement`). Tombstones are retained even when their item is deleted, because they are "the absorbing guard that rejects stale comment replays" (`deleteItem`). One named exception exists: the #3087 one-time migration correction for pre-fix review rows whose fabricated `source_updated_at` would otherwise freeze them forever (same function).
- **Links/edges — last writer wins, silently, on the full key.** `upsertLink` is `INSERT INTO pmp_links … ON CONFLICT(subject, ref, relation) DO UPDATE SET note = excluded.note, created_by = excluded.created_by, created_at = excluded.created_at` (`pm-stack/projector/src/store.ts`). So two writers writing the same `(subject, ref, relation)` do not conflict visibly: the later write replaces `note`, `created_by`, and `created_at`, and no history is kept. A different `relation` value is a different row (the primary key is `(subject, ref, relation)` in `pm-stack/projector/schema.sql`), so `tracks` and `relates` for the same subject↔ref coexist rather than dispute. Removal is a plain `DELETE FROM pmp_links WHERE subject = ? AND ref = ? AND relation = ?` (`deleteLink`). There is no code path that marks a link disputed, contested, or pending review.
- **Deliveries — first delivery id wins; duplicates are recorded, not reapplied.** Deliveries dedupe on the delivery id, which intake requires; `pmp_push_events` inserts use `ON CONFLICT(delivery_id) DO NOTHING`, and the README's e2e duplicate-delivery test proves a redelivered push GUID yields one row (`pm-stack/projector/README.md`; `pm-stack/projector/schema.sql`). A failed first attempt is preserved in `pmp_delivery_errors` even when a retry later succeeds (`pm-stack/projector/schema.sql`).
- **Projection contract (the general rule behind all of the above).** "A projection writes only what the event proves. An absent field proves nothing — it neither defaults a value nor erases a stored one — and the only timestamps a row carries are ones its own payload reported." (`pm-stack/projector/schema.sql`, "PROJECTION CONTRACT (#4302, audited in #4303)").
- **Checkpoints — forward only.** "A checkpoint only ever moves forward and never past the high-water cursor the server issued for that sweep, so a failed sweep resumes from its old checkpoint and replays safely." (`pm-stack/projector/schema.sql`, `pmp_consumer_checkpoints`).

File evidence for "no dispute rule": the grep for `conflict|disput|overwrite|supersed|duplicate` over `pm-stack/projector/src/`, `pm-stack/projector/README.md`, and `pkgs/pm-projector/` returns only the dedupe/monotonic uses above (delivery duplicate receipts in `src/server.ts` and `src/operation-forwarder.ts`, the `ON CONFLICT` clauses in `src/store.ts`) — no dispute vocabulary or state exists. Raw grep: `sideline-material/survey-topup/projector-conflict-grep.txt`.

**Reconciled truth, in one sentence:** `pm-console` is the one PM-stack app that NixOS does **not** declare — it runs as the hand-installed user unit `pm-console.service` copied from `pm-stack/systemd/pm-console.service` by `pm-stack/console/install.sh`, executing `bun run src/server.ts` straight out of the primary checkout, and it is kept current by its own redeploy timer, not by `nixos-rebuild switch`.

Evidence, point by point:

- **The NixOS module declares no console.** `nixos/services/pm-stack/default.nix` declares these `systemd.user.services`: `pm-projector`, `pm-aggregator`, `pm-dispatch`, `pm-git-sync`, `pm-projector-reconcile`, `quota-gatherer`, `pm-digest-daily`, `pm-digest-weekly`, `quota-weekly-review`, `fleet-feed-collector`, `pm-tunnel`, `pm-tunnel-watchdog`, `pm-kaneo`, plus `pm-projector-proxy`, with timers for `pm-git-sync`, `pm-projector-reconcile`, `quota-gatherer`, `pm-digest-daily`, `pm-digest-weekly`, `quota-weekly-review`, `fleet-feed-collector`, `pm-kaneo`, `pm-tunnel-watchdog`, and sockets for `pm-projector`, `pm-aggregator`, `pm-dispatch`. A grep for `pm-console` over `nixos/` and `home/` returns nothing.
- **The module's own header explains the split it intended — and the console is not in it.** "Code source (2026-11-10, code#8171 …): the projector, aggregator, dispatch, and git-sync are Nix packages built from this repo (`pkgs/pm-projector`, `pkgs/pm-aggregator`, `pkgs/pm-dispatch`, `pkgs/pm-git-sync`) and the units below run their store wrappers. … The checkout-run model this replaces (units `bun run`ning straight out of ~/git/code …) is retired" (`nixos/services/pm-stack/default.nix`, header). There is no `pkgs/pm-console` — `pkgs/` contains `pm-aggregator`, `pm-dispatch`, `pm-git-sync`, `pm-projector` only.
- **The `pm-stack/systemd/` copies are the console's live declaration (plus legacy copies for NixOS-owned apps).** `pm-stack/systemd/` holds: `pm-aggregator.service`, `pm-console.service`, `pm-console-expose.service` + `.timer`, `pm-console-redeploy.service` + `.timer`, `pm-console-android-release.service` + `.timer`, `pm-dispatch.service`, `pm-host-health.service` + `.timer`, `pm-invariant-sweeper.service` + `.timer`, `pm-kaneo-sync-guard.service` + `.timer`, `pm-quota-watchdog.service` + `.timer`, `pm-tunnel.service`. Of these, only the `pm-console*` family is installed from this directory by a live script (below); the `pm-aggregator`/`pm-dispatch`/`pm-tunnel` copies are the pre-NixOS files the module header says are "kept beside this history in git".
- **How the console actually runs.** Unit name: `pm-console.service` (user unit). Its file, `pm-stack/systemd/pm-console.service`, declares: `WorkingDirectory=%h/git/code/pm-stack/console`, `ExecStart=/run/current-system/sw/bin/bun run src/server.ts`, `EnvironmentFile=%h/.local/state/pm-console/.env`, `CPUWeight=900`, `Restart=on-failure`, `WantedBy=default.target`. Build route: none — there is no build step; Bun runs the TypeScript source in the checkout directly.
- **How it is installed and kept current.** `pm-stack/console/install.sh` refuses to run from anywhere but the primary checkout ("run from the primary checkout at $EXPECTED (the unit runs that checkout)"), copies `pm-stack/systemd/pm-console.service` to `~/.config/systemd/user/pm-console.service`, also installs the `pm-console-expose`, `pm-console-redeploy`, and `pm-console-android-release` service+timer pairs, creates `~/.local/state/pm-console/.env` if absent (`PM_CONSOLE_PORT=4872`, empty `PM_CONSOLE_OWNER_EMAILS`), then runs `systemctl --user daemon-reload`, `systemctl --user enable pm-console.service`, `systemctl --user restart pm-console.service`, `systemctl --user enable --now` on the three timers, and health-gates on `http://127.0.0.1:4872/console/health`. `pm-stack/console/redeploy.sh`, run every minute by `pm-console-redeploy.timer`, compares the checkout's console tree (kept at main by `pm-git-sync`) with the last-deployed tree hash; on a difference it self-checks the new code on no listener, and only on a pass runs `install.sh` to restart the service — failed code never enters service.
- **What the README says (consistent, but easy to misread).** The README's table lists Console as "this repo (Bun app, user unit `pm-console`)" on `127.0.0.1:4872`, "public behind sign-in as `pm.security.cab` (console at `/console`, dashboard at `/` through the console's gate)", defined in `console/` (`pm-stack/README.md`). The same README's sentence "one `nixos-rebuild switch` deploys the whole stack: the `pm-apps` services …, the PM user units (`pm-aggregator`, `pm-projector`, `pm-dispatch`, `pm-tunnel`) and the Kaneo stack's lifecycle are declared in `../nixos/services/pm-stack`" pointedly does **not** list `pm-console` among the switch-deployed units — the chapter should not upgrade that sentence into "the switch deploys the console".

## T5. Port 4871

Sources: `pm-stack/PORTS.md` (pm-stack table), `pm-stack/aggregator/src/config.ts:281`, `pm-stack/aggregator/src/freshness-ipc.ts`, `pm-stack/aggregator/src/server.ts` (freshness IPC listener, ~line 5509), `nixos/services/pm-stack/default.nix` (aggregator + projector environments).

**It is not a registry-only name — a real component listens on it, inside the aggregator process.** The registry row reads: "4871 | pm-aggregator freshness IPC (`/publish`) | loopback | `pm-stack/aggregator/src/config.ts:148` (`PM_AGG_FRESHNESS_PORT` default 4871); `nixos/services/pm-stack/default.nix:163`" — status **live** (`pm-stack/PORTS.md`; line numbers in the registry are as of its 2026-11-05 audit — in current code the default is set at `pm-stack/aggregator/src/config.ts:281`, `freshnessPort: parseAggregatorPort(env.PM_AGG_FRESHNESS_PORT, "PM_AGG_FRESHNESS_PORT", "4871")`, and the NixOS module sets `"PM_AGG_FRESHNESS_PORT=4871"` in the `pm-aggregator` unit's Environment).

Two-line description for the chapter: Port 4871 is the pm-aggregator's second, loopback-only listener — a separate `Bun.serve` on `127.0.0.1:4871` inside the aggregator process, commented in code: "Cross-process publishers get a separate loopback-only listener; never add this port to PM_AGG_HOSTS or expose it through the Cloudflare tunnel" (`pm-stack/aggregator/src/server.ts`). Its only route is `POST /publish`, "The only write seam for cross-process freshness publishers", which accepts a bounded (16 KiB) JSON freshness notice into the aggregator's `FreshnessStore` and replies 202 — no source payload is accepted or returned (`pm-stack/aggregator/src/freshness-ipc.ts`). The known publisher is the projector: the NixOS `pm-projector` unit carries `Environment = [ "PM_AGG_FRESHNESS_URL=http://127.0.0.1:4871/publish" ]` (`nixos/services/pm-stack/default.nix`). Browser-facing freshness delivery is a different seam on the main 4870 listener (`GET /freshness/stream` SSE and `GET /api/freshness-events.json`, `pm-stack/aggregator/src/server.ts`).
