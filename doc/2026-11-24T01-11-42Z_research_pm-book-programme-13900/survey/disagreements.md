# Disagreements — docs/designs vs code (PM-SURVEY, 2026-11-23)

Bookwright rule applied: where a research/design doc and the code disagree, **the code wins**; the survey says so. Ground truth: laptop clone `~/git/code` at `4d937b3`. Writers cite these numbers (D1, D2, …). **Count: 14.**

## Website / pages surface

**D1. Kaneo image: fork vs upstream.** `pm-stack/aggregator/src/program.ts` (the aggregator's own program page text) says the execution board runs "our fork (developing-today-forks/kaneo) so multi-repo linking is on our schedule", and `pm-stack/README.md`'s Phase-1 framing repeats the fork programme. The deployment code, `pm-stack/compose.yml`, pins the **upstream** image `ghcr.io/usekaneo/kaneo:2.47.0@sha256:3df62194…`. Code wins: the deployed board is upstream v2.47.0; the fork exists as a repo (fleet references were repointed to it, code#5454) but is not what compose runs.

**D2. Grist version pin.** `pm-stack/README.md`'s Phase-2 table says Grist is `gristlabs/grist-oss:v1.7.21`, "pinned by digest". `pm-stack/grist/compose.yml` line 28 names **no tag at all** — `gristlabs/grist-oss@sha256:d761de16…`. Code wins: only the digest is pinned in the deploy file; whether that digest is v1.7.21 is UNVERIFIED. (Pad's pin, by contrast, carries tag + digest as its README-style comment promises: `pad/compose.yml`.)

**D3. "The aggregator reads no Pad data."** `pm-stack/README.md` states this absolutely, and `PORTS.md` simultaneously records the aggregator's `/api/health` reporting "pad: state up, ok true" and concludes "the aggregator consumes Pad on 7777 successfully"; `aggregator/src/config.ts` keeps a Pad base URL and `server.ts` accepts `pad` as a stack-token target. Reconciliation the book should use: the aggregator reads no Pad _planning data_ (no source adapter consumes Pad content), but it does probe Pad for health/topology. The README sentence as written is broader than the code.

**D4. Who writes GitHub labels for needs-Drew items.** `aggregator/src/needs-drew.ts` header (#1226): "The aggregator never writes labels back; the orchestrator remains the only label writer." The console — part of the same PM stack — does write them: `console/src/work.ts` `handsDone()` POSTs a comment and DELETEs the `user/escalated` label via `gh`, and `Ops.setRank()` adds/removes rank labels. Code wins: the _aggregator service_ never writes labels; the _stack_ does, through the console, and the orchestrator is not the only label writer. (The related standing rule in `pm-stack/README.md` — "The orchestrator is the Project's single writer. Agents and the dashboard do not edit Project fields directly" — is about Project _fields_; the console writes _labels_, which is exactly the seam the book must not blur.)

**D5. Notify relay: documented routes vs routed routes, and deployed vs not.** `pm-stack/notify-relay/README.md`'s route table lists `POST /mirror/event` and `GET /answer/:ledgerId` / `POST /api/needs-drew/:ledgerId/answer` in the same table as the live routes (flagged only by a "Lands in" column as steps 2–3). The code is explicit that they are **not routed**: `notify-relay/src/index.ts` header — "POST /mirror/event arrives with step 2 and the answer routes with step 3; they are not routed yet", everything else 404s. And `pm-stack/platform/workers.json` records `pm-notify` as **"not deployed"** with a null address, while the relay README's acceptance paragraph reads as a deploy procedure awaiting execution. Code/registry win: today the edge answer-intake and the dead-man's switch **do not exist in production**; phone answers go to the laptop aggregator (§4a of `push.md`). Any doc that describes edge answering as available is ahead of the code.

**D6. Worker count: eighteen vs twenty.** `pm-stack/platform/README.md`: "This repository holds eighteen Cloudflare Workers… [`workers.json`] lists all eighteen." `workers.json` in fact lists **20** workers (counted directly: pm-console-edge, message-bridge, decision-events, pm-notify, mcpx, queue-transport-alert, github-ci, voice-line, muse-agent-handoff, desktop-commander, fleet-hosted, atlas-search, cold-store-rehydrator, developing-today-backup, pkarr, id-hosted-worker, id-worker-poc, id-d1-journal-poc, lab-ops-hub, cf-container-hello). Its own test (`workers.test.ts`) holds the JSON to the repo's wrangler files, so the JSON is the live list; the README's "eighteen / fourteen answered / two Actions-deployed" figures are stale as of the file's own `checked: 2026-11-23`.

**D7. Decision sets page: manifest says no API twin; the server implements a decisions API.** `aggregator/src/pages.ts` gives the `decisions` entry no `api:` field (one of only three pages without one). `aggregator/src/server.ts` nevertheless implements `/api/decisions/<setId>/submit|defer|request-info|events`, `/api/decision-sets` (+`/submit`), and the console reads the underlying sets. The manifest is a _page_ registry, so this is a manifest-completeness gap rather than a false claim — but a book chapter generated from `pages.ts` alone would miss the entire decisions write API. Code wins.

**D8. `/decisions/<setId>` is missing from the reachability map.** `pages.ts` `SUBROUTE_PARENTS` lists item, discuss, program-project, service-detail, alerts-preferences, and projects-merge — but not the decision-set detail page, even though `/decisions`'s own blurb says "Each row opens the set's own page" and the push notification's whole purpose is opening it. Consequence in code: `manifestRouteFor("/decisions/…")` returns null, so decision-page renders are outside the #1147 render registry that `/api/health` reports. Code (the map) wins for health accounting; the page indisputably exists.

**D9. The single-question answer store is named two ways.** `aggregator/src/decisions.ts` header says decision sets mirror the ledger and are distinct from "the question store in needs-drew.ts", while `aggregator/src/notifications.ts` and `sw-source.ts` route single-question answers through `/api/needs-drew/<ledgerId>/answer` into the same resolution machinery, and the console's `Work` reads _sets_ from "the decisions file" for the same questions (`console/src/work.ts`: "the questions store could not be read"). Which file a single-question (non-set) answer ultimately writes is not unambiguously documented in the code surveyed — UNVERIFIED; the book should describe the endpoint and the ledger application, not invent a store.

## Roadmap / hierarchy surface

**D10. "Aggregators" as a hierarchy level does not exist in code.** Programme framing (and this survey's brief) lists "major initiatives, projects, epics, aggregators" as hierarchy types. In code, Kind on Project #4 is exactly `Task | Epic` (`aggregator/src/model.ts`), programs are a document scheme (`design-reprioritization-2026-11-12.md`), and "aggregator" names a _service_, not a node type. The book must not present a four-level typed hierarchy; the real ladder is program (doc/Area) → project (registry + Project #4) → epic (Kind=Epic + sub-issue parent) → task/item. See `roadmap.md` §1.

**D11. Two horizon vocabularies.** Repo-file/Grist roadmap rows use buckets `Now | Next | Later | Ideas | Ongoing` (`aggregator/src/sources/repo-roadmap.ts` `HORIZON_BUCKETS`, validated by `roadmap-horizon.ts`), while aggregator tier items use `Horizon = today | tomorrow | next-3-days | longer | incoming` (`aggregator/src/model.ts`), and Project #4 has its own free-standing `Horizon` single-select whose values are whatever the Project defines (read verbatim in `projects.ts`). No doc surveyed names all three or their mapping. Code wins per surface; a single "horizon" definition in the book would be wrong.

**D12. Two roadmap implementations.** The console's roadmap (`console/src/plan.ts`: phases `doing|now|next|later|built` derived from labels, capabilities parsed from a plan doc) is an independent implementation with its own vocabulary, not a client of the aggregator's `/api/roadmap.json` (Grist + repo files + pool). Docs that speak of "the roadmap" in the singular (e.g. the Phase-2 framing in `pm-stack/README.md`, where Grist is "the" tables/roadmap layer) understate this: in code there are two roadmap surfaces with different sources, plus the repo-file source that now _wins over Grist_ on title collisions (#1738 merge rule in `sources/repo-roadmap.ts`) — the opposite precedence from a reader who took Grist as the roadmap source of record.

**D13. Needs-user design vocabulary vs live census vocabulary.** `pm-stack/needs-user-actions-design-2026-10-26.md` (with its 2026-10-27 naming/escalation update) designs the needs-user surface around its own terms; the shipped code splits waiting items by `user/review` + `user/escalated` labels and `hands:v1` markers into hands / review / agent-decides (`aggregator/src/needs-drew.ts` `needsDrewWait`), and the console renames the buckets again for the phone (Questions / Only you can do / Reviews / Escalated, `console/public/app.js` `viewNeeds`). The design also filed acceptance "#1007 appears in the queue" which the code's own header records as impossible by design (#1007 is closed; the census is open-only) — "recorded on #1226 rather than claimed as met". Code wins; the book should use the census vocabulary and treat the 2026-10-26 doc as history.
