Closes #7016

## Problem

Nothing reconciles the open-issue set against fleet-queue coverage. Issues enter the queue only when a creator-class lane files them (file + enqueue in the same pass); anything filed another way — a work lane filing a blocker mid-task, an audit lane, by hand, or predating the queue (epics) — silently never gets a queue item, so no lane ever dispositions it. The 2026-11-07 reconciliation found 23 such issues across the four repos; that day's import was a one-off.

## What this adds

**Broker — read-only `POST /coverage`.** Given the open-issue set the caller just enumerated, it answers per issue whether a **live** task (`queued`/`claimed`/`parked`/`blocked`) holds its repo-health dedupe key in the named queue. Per Drew's doctrine (2026-11-07): a `done` task is **not** coverage (done means triage or a landed slice, not a resolved issue), and neither is a task in a `*-shadow` queue. It never writes tasks or events.

**`scripts/fleet/queue-reconcile/`** — the scheduled job:
- enumerates open issues with `gh api --paginate` (PRs filtered out; a partial page would read as coverage that does not exist),
- asks the broker for the diff,
- with `--import`, enqueues a triage packet per uncovered issue **through the sanctioned CLI path**, dedupe-keyed `repo-health:v1:triage:<repo>:issue:<n>` so re-runs are idempotent by construction,
- **observe-only by default**, matching the sweeper revalidator's two-step rollout,
- a fetch or broker failure exits **3** and names the repo in an ERRORS section — it never reports as "0 uncovered".

**systemd units** (hourly at :41, `Persistent`) + a row in `doc/fleet-schedule-registry.md` per the same-pass rule.

**`AGENTS.md`**: the file-and-enqueue rule for issues filed outside a creator run.
