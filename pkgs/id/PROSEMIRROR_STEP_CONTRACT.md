# Collaborative ProseMirror step compatibility contract (initial)

This document pins the TypeScript compatibility target for the next stage of
the Rust-native collaboration validator. The server's first validation slice
landed in #15270: it checks recognized step shapes, schema names, bounds, and
batch transactionality, but does not yet prove that transforms apply to the
document tree. This document and corpus do **not** implement that missing
application behavior or claim [issue #1618](https://github.com/developing-today/code/issues/1618)
is fixed.

## Oracle and corpus

The oracle is the TypeScript ProseMirror implementation used by the editor:
`pkgs/id/web/src/editor.ts` defines `richSchema`, `rawSchema`, and
`getSchema`; `pkgs/id/web/package.json` pins `prosemirror-model` and
`prosemirror-transform`. The checked-in corpus at
`pkgs/id/web/src/test-fixtures/prosemirror-step-corpus.json` is generated by
`bun run src/test-fixtures/generate-prosemirror-step-fixtures.ts` from those
schemas and `Transform`, then checked by `src/prosemirror-step-corpus.test.ts`.
For each accepted case, the oracle is the exact resulting document JSON after
applying steps in order. For each rejected case, the oracle is rejection at
the first invalid step; no later step is applied and no partial document is
committed.

## Initial supported contract

- Modes `rich`, `markdown`, and `plain` use `richSchema`; `raw` uses
  `rawSchema` (`editor.ts:getSchema`). `media` and `binary` are not editable
  modes (`collab.ts:CONTENT_MODES`) and are out of scope for step application.
- The initial supported step type is `replace` (`ReplaceStep`), whose JSON
  requires integer `from` and `to` positions and a `slice` JSON object
  deserializable by ProseMirror's `Slice.fromJSON` against the mode schema.
  ProseMirror registers the other core types (`replaceAround`, `addMark`, and
  `removeMark`) too, but they are explicitly **not yet in this Rust contract**:
  Rust must reject them until their exact fields, semantics, and fixtures are
  added. Every accepted step must deserialize via `Step.fromJSON(schema,
  value)` and apply successfully to the current document. Do not implement
  shape-only acceptance.
- The base document must deserialize with the mode's schema. Apply each batch
  sequentially to the result of the preceding step. Any parse error, schema
  mismatch, failed transform, invalid position, or unsupported `stepType`
  rejects the entire batch. The server must not persist, advance version,
  acknowledge, or broadcast a prefix of a rejected batch.
- Fail closed on unknown step types, unknown slice nodes/marks, malformed
  non-object entries, and invalid/out-of-range positions. The rejection
  vectors and their TypeScript outcomes are in the fixture corpus.
- Resource bounds must match the wire envelope: at most 1,000 steps per
  message and at most `MAX_STEPS_MESSAGE_BYTES` (currently 1 MiB minus 4 KiB)
  of encoded step payload, from `collab-step-budget.ts`. The Rust parser must
  additionally bound nesting/individual JSON size before allocating; an exact
  nesting/depth limit remains to be selected and should be pinned by a Rust
  test before rollout.

## Rust implementation sequence and blockers

1. Implement bounded JSON decoding plus fail-closed step-type/field parsing;
   blocker: select and test explicit JSON nesting and per-step allocation caps.
2. Implement schema-aware slice, node, and mark decoding for the `rich` and
   `raw` modes; blocker: reproduce editor schema details from `editor.ts`, not
   a shape-only approximation.
3. Implement ordered transform semantics for the four registered core step
   `replace` semantics and compare final document JSON against this corpus;
   blocker: add fixtures and contract fields before enabling `replaceAround`,
   `addMark`, or `removeMark`.
4. Integrate validation transactionally at the server acceptance boundary,
   then test rejection leaves version, storage, broadcast, and acknowledgement
   unchanged. This task intentionally does not implement that server change.
