## Required dispositions (a)–(d)

### (a) Signed-object JSON — DECISION: receipt gates take the refusal

`pkgs/id/crates/id-sync/src/artifact.rs:1333` (`receive_pushed`) decodes
peer-pushed bytes as a `SignedArtifact`; `:1286` decodes a pull
`PullRequest` and `:1406` a fetched `Page`. In the main crate,
`pkgs/id/src/boards.rs:883` decodes a `BoardObject` from
`artifact.body` (a `serde_json::Value`) after `artifact.verify()`, and
`pkgs/id/crates/id-events/src/attestation.rs:111,146` and
`pkgs/id/src/currency.rs:136,232` decode signed events' body bytes.
`pkgs/id/src/web/identity.rs:527` decodes a token payload whose
signature is verified over the exact bytes before the parse.

Decision, with reasons: **receipt gates for signed objects take the
refusal too — they are not deliberately out.** A signature covers the
exact bytes, but a lenient struct decode collapses a duplicated key
before any consumer sees the body, so two readers of the same signed
bytes can still disagree about what was signed: the verifying reader
acts on the last value, a re-serializing or `Value`-reading consumer
may act on the document as written. The board-object canonical
re-encode check (`to_value(&object) == artifact.body` under
`boards.rs:883`) mitigates one typed consumer; it does not cover
every present and future consumer of a signed body, and the receipt
is the one point where untrusted bytes enter — refusing there
protects all of them at once. This is consistent with the receipt
contract direction of issue #3231 rather than an exception to it.
Conversion pattern for the follow-up (lossless form): validate
uniqueness by running `parse_json_without_duplicate_keys` over the
raw bytes and discarding its `Value`, then run the existing typed
decode (`from_slice` / `from_str`) over the original bytes.
Decoding the helper's `Value` with `from_value` is NOT the general
pattern: with serde_json's default features a `Value` cannot
represent integers above `u64::MAX` losslessly, and signed bodies
in this tree carry `u128` fields (e.g. `RateAuthorisation`), which
the current typed decoders support. Signature verification is over
the raw bytes and is unchanged either way. All (a) sites are marked
**gate — follow-up** in the table and are listed in the conversion
follow-up issue filed from #6521.

### (b) Self-produced files — per site, not by assumption

Every site whose input is a file or state the same crate writes is
marked not-a-gate with the (b) reason in the table (22 sites: serve
info, publications registry, group/directory/local-claims/petname/
outbox append logs, tag registry + MetaDoc, world cache, directory
replay, world journal scans, artifact store replay, world_dev
snapshot state). The reasoning is the same shape but was verified per
site: the writer is this code and cannot emit a duplicate key, so
refusal would be defence against hand edits only. Where a store's
contents arrive from peers (artifact store, group log, replica
journal), the disposition names the receipt path that gates them —
the file replay is not the entry point.

### (c) Non-JSON decoders — boundary: stated exception, out of scope

Postcard decodes exist in production at
`pkgs/id/src/match_audit.rs:519`, `pkgs/id/src/chat_presence.rs:482`,
and `pkgs/id/src/commands/peers.rs:363`; MessagePack (`rmp_serde`)
decodes at `pkgs/id/src/seitan/accept.rs:125` and
`pkgs/id/src/web/collab.rs:565` (collab frames are MessagePack
arrays). Both formats can carry duplicate map keys in principle.
**Boundary: they are outside this contract, as a stated exception in
the contract statement in `json_unique.rs`.** Reasons: no filed
instance exists of a duplicate map key reaching a check through
either format; both decode into typed structs/arrays at a single
layer (there is no two-reader `Value` stage for the disagreement to
live in, which is the failure this contract exists to prevent); and
the one signed MessagePack path (seitan accept) already refuses
trailing bytes and requires exactly one value. The exception is
recorded, not silent: a filed instance of a duplicate map key
through either format reopens this boundary and it becomes a
follow-up of its own. The helper is not extended to binary formats.
