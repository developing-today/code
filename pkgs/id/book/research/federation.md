## Three different things called a relay

An **Iroh relay** forwards encrypted packets between endpoints and allows a direct path when reachable. The endpoint public key authenticates the connection. Application policy decides whether a peer may connect, fetch a namespace, relay a group event or modify a world. An **ID member relay** validates a chained message before forwarding. The current gate checks the signed origin, message ID, group authority and hop history, then appends the relay’s own hop. An **offline application backstop** can retain authorized data according to an explicit retention profile. A transport hop alone commits to neither application retention nor delivery. [Iroh endpoint/relay reference](https://docs.rs/iroh/latest/iroh/) · [ID relay gate](https://github.com/developing-today/code/blob/4cfceaa8afc08cf2cea88b9d733a2ace14c8ad5a/pkgs/id/crates/id-sync/src/relay_gate.rs) · [ID relay/proxy decision](https://github.com/developing-today/code/blob/4cfceaa8afc08cf2cea88b9d733a2ace14c8ad5a/doc/2026-11-08T11-08-53Z_design_id5813_relay_proxy_protocol/2026-11-08T11-08-53Z_design_id5813_relay_proxy_protocol.md)

The current chained path uses `/id-chained-relay/1` and strictly decodes its JSON transport frame before `RelayGate::decide`. On a forward it preserves signed origin bytes. Its documented reply distinguishes duplicate and refused. Pinned iroh-gossip 0.101.0 cannot run ID’s membership check before eagerly forwarding a broadcast, so it is unsuitable for distributing private chained messages. Upstream described topic authorization and an incompatible gossip ALPN as proposed work for 1.0. A future upgrade needs an independent gate review. [Relay ingest](https://github.com/developing-today/code/blob/4cfceaa8afc08cf2cea88b9d733a2ace14c8ad5a/pkgs/id/crates/id-sync/src/relay_ingest.rs) · [Gate and version finding](https://github.com/developing-today/code/blob/4cfceaa8afc08cf2cea88b9d733a2ace14c8ad5a/pkgs/id/crates/id-sync/src/relay_gate.rs) · [Upstream release notes](https://www.iroh.computer/blog/iroh-gossip-road-to-1-0)

Durable facts retain their original signed events. Signed session checkpoints commit to ordered ephemeral segments. The defaults in code are 256 frames or 2,000 ms; explicit commit is another design trigger. The sender’s checkpoint can attest to its ordered segment and state. Live frames are MAC-authenticated; a checkpoint does not establish another participant’s observation, exact timing or a match outcome. Late joiners recover durable facts and checkpoints. The live contract intentionally permits loss of the uncheckpointed tail. [Session checkpoint implementation](https://github.com/developing-today/code/blob/4cfceaa8afc08cf2cea88b9d733a2ace14c8ad5a/pkgs/id/crates/id-store/src/session_checkpoint.rs) · [#2036 design §§3–5](https://github.com/developing-today/code/blob/4cfceaa8afc08cf2cea88b9d733a2ace14c8ad5a/doc/2026-11-01_design_id2036.md)

## Hosted parity and replay evidence

The hosted export implementation keeps verbatim signed header bytes. An object’s BLAKE3 operation ID and an export entry’s SHA-256 manifest digest identify different things. Blob references in an applied `document.put` cite BLAKE3; the R2 data plane addresses content by SHA-256. Export resolves those citations by content. The Worker store holds headers and references to document blobs, so a successful header round-trip alone cannot prove that every historical application payload is available on that host. Its test fixture is shared with the native suite and already covers missing references. [Worker export algorithm](https://github.com/developing-today/code/blob/4cfceaa8afc08cf2cea88b9d733a2ace14c8ad5a/pkgs/id/hosted-worker/src/export.ts) · [Worker fixture and named tests](https://github.com/developing-today/code/blob/4cfceaa8afc08cf2cea88b9d733a2ace14c8ad5a/pkgs/id/hosted-worker/test/export.test.ts) · [Signed operation identity](https://github.com/developing-today/code/blob/4cfceaa8afc08cf2cea88b9d733a2ace14c8ad5a/pkgs/id/crates/id-store/src/chain.rs)

**Proposed route-pair oracle.** Fix two participant keys, their membership frontier, signed events, a referenced media blob, a missing parent and a fork. Exercise direct peer, encrypted packet relay and hosted import/export over the same supported fixtures. Compare against a hand-declared set of admitted event IDs, visible application values and policy verdicts as well as cross-comparing routes. Also compare exact signature-bearing bytes and referenced-blob closure. Keep route telemetry, endpoint addresses, custody signer and local receipt times out of the equality key. Repeat with missing content, catch-up after a partition, relay retry after acknowledgement loss, and a persisted store reopened midway. A missing reference must produce the specified error everywhere that promises an export. Use local test doubles or owned fixtures. The existing [#10698](https://github.com/developing-today/code/issues/10698) journal suite remains responsible for world state, not this object-level oracle.

The attestation reducer defines signed complete/partial witness decisions and objections. The audit layer defines a versioned Postcard log and names a pinned tic-tac-toe program/ruleset. A clean, complete replay under the named runtime can establish a technical result. Intellectual honesty in the UI requires a separate verdict for actual validity or independent observation. The tests already distinguish edited input, claimed versus signed move, replay divergence, unsupported rules, and insufficient observational evidence. No claim in this report says those tests ran on this SHA. ## OCapN integration decision proposed for review

Keep the [existing #9143/B13 evidence boundary](https://github.com/developing-today/code/blob/4cfceaa8afc08cf2cea88b9d733a2ace14c8ad5a/doc/2026-11-13T03-40-00Z_design_id-atlas-summit/part-b/B13-research-ocapn.md). Adopt capability references, netlayer separation, pipelining and certified handoff as semantics to evaluate. The upstream group still describes pre-standardization; its list includes Dart, JavaScript and Guile/Racket. A contemporary Rust-facing candidate exists: **Glowcap 0.1.1** exposes a Rust Host/Session API over C ABI archives with optional Iroh transport. Its existence supports a comparative interoperability experiment. It does not establish independent security review, pure-Rust implementation, long-term suitability, or compatibility with a specific ID pin. Preserve native signed grants and the ingest gate. An explicit attenuating wrapper or recipient binding needs ID-specific proof.
