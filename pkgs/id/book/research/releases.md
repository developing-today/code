# Platform releases and installation

_Research snapshot of November 23, 2026. Code and issue observations refer to the cited revisions and collection times._

The [ID design history and decisions carried forward](research-archive.md) identifies the newer tested-commit, per-app tag decision. The [From an app directory to a reproducible guest release](research-developer.md) supplies installation, update and rollback cases.

Drew selected **Linux → Android → Web → macOS → Windows**, adopted mobile-native as high priority, and chose independent, granular platform releases. This is a sequencing and support policy. Each release still needs a working installer and passing evidence for the capabilities it advertises. The release work already has a home in #12819, with shell conformance in #12821. The proposed naming scheme below is an implementation choice. ## Release identity and compatibility

The static workflow inventory has ID checks, benchmarks, E2E, hosted-worker routing checks and an id-mail Worker publish/promote pair. The mail Worker path belongs to its named service; the PM Android workflow and MCPX release workflow belong to their own components. An ID-native release pipeline and an established per-platform ID tag grammar were not identified in the pinned tree. The release PR title/body search found no open #12819 implementation. Verify live refs and release records on the authorized laptop before adopting a grammar. Published assets must be identified by component-qualified tag and exact digest rather than selecting the newest release of this monorepo. [CI policy](https://github.com/developing-today/code/blob/4cfceaa8afc08cf2cea88b9d733a2ace14c8ad5a/.github/ci-policy.md) · [ID checks](https://github.com/developing-today/code/blob/4cfceaa8afc08cf2cea88b9d733a2ace14c8ad5a/.github/workflows/id-check.yml) · [ID mail publish](https://github.com/developing-today/code/blob/4cfceaa8afc08cf2cea88b9d733a2ace14c8ad5a/.github/workflows/id-mail-worker-publish.yml) · [Monorepo installer precedent](https://github.com/developing-today/code/blob/4cfceaa8afc08cf2cea88b9d733a2ace14c8ad5a/.github/workflows/mcpx-release.yml)

**Proposed grammar** `id-<product>-<platform>-v<version>`, with CPU/ABI variants named and hashed in the platform release manifest. For example, `id-shell-linux-v0.1.0` would identify a Linux desktop-shell release; `id-shell-android-v0.1.0` would identify its native Android counterpart. These are illustrative unissued names. Treat a hosted service, a browser bundle, a CLI binary, a Nix package and a desktop installable as explicit products when they need independent compatibility or rollout. Preserve any pre-existing tags. If an architecture can ship independently within a platform and the channel needs separate epochs, include that architecture in its component tag or use separate manifests with distinct versions. The decision belongs in the existing release slice.

The manifest should record product, platform/architecture, version and build number, source commit, artifact/checksum/signature, accepted shell protocol revisions, supported surfaces and providers, ABI/schema ranges, minimum OS/browser, previous release/update requirements, evidence URLs and unsupported features. Lookup filter must match the component and platform exactly; verify digest/signature before installation. Retain the previously verified installer and user data migration plan. Installing an older executable is safe only if it can read the persistent data it will encounter. Prevent an update from silently expanding an app's capability grants.

## Release-handoff sequence

1. Recheck [#12819](https://github.com/developing-today/code/issues/12819) and its parent [#6297](https://github.com/developing-today/code/issues/6297), fresh claims and the status of #10928/#12817. Validate current tags via read-only GitHub REST matching-refs and releases plus existing repo release scripts. Record which actors can publish each product and whether material signing access exists by name only. Honor a live owner or a separate release decision.
2. In its own worktree, make the smallest change that produces a reproducible, installable artifact for one target and records a truthful capability statement. Preserve the existing flake/library/CLI APIs. Automate a clean install and upgrade fixture on that target. Do not recreate #13147's target gating, #13111's TUI work or [#12605](https://github.com/developing-today/code/pull/12605)'s build caching work.
3. Push the branch, dispatch the focused artifact and oracle on a Fleet GitHub-hosted runner, save handle/run ID/URL, collect immutable output hashes. Use repeat-session affinity for a follow-up; pick a macOS/Windows runner only for a check requiring that target. For Android, separate ordinary Linux-hosted Gradle/NDK/emulator checks from physical-device Keystore, background behavior and input evidence; document the exact route. Report an unavailable emulator/NDK/device as missing evidence.
4. Keep automatic CI nightly on main, as the repository policy specifies. A targeted Fleet dispatch is independent verification. After merge, select the actual main SHA for release evidence and run the relevant install/conformance gates for that SHA; establish a signed manifest only from those artifacts. A successful Cargo compile, emulator-only result or another target's passing test cannot unblock a platform-specific release. [Repo CI policy](https://github.com/developing-today/code/blob/4cfceaa8afc08cf2cea88b9d733a2ace14c8ad5a/.github/ci-policy.md) · [Shared release gate](https://github.com/developing-today/code/blob/4cfceaa8afc08cf2cea88b9d733a2ace14c8ad5a/.github/scripts/release-gate.sh)
5. Record the target-specific status, capability statement, release URI and digest in the book and owning issue. Update client selection, documentation and rollback instructions together. A working Linux release does not wait for app-store or Windows evidence and does not mark those platforms released. The program’s Pages book remains a documentation site under the shared repository deployment.
