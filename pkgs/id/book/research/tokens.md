# Tokens, trading and metered execution

_Research snapshot of November 23, 2026. Code and issue observations refer to the cited revisions and collection times._

The [Currency, market offers and execution budgets](research-economy.md) adds an exact supply-audit counterexample and ties offline settlement and execution budgets to separate invariants. The [Three design records for repository review](research-contracts.md) gives the compatible correction choices.

An ID token represents a grant or capability offered by a particular server or world. Its issuer determines the in-world entitlement. The public term is **units**. The existing identifiers containing `currency` remain wire and library compatibility contracts. Drew selected double-entry accounting with **Units**, **Pending** and **Revoked** as account classes. The account classes of a token programme share one ledger. This chapter proposes how to extend those decisions to a game inventory, an offer and a budget a world may spend on its user's behalf. ## Proposed capability and asset model

Use the v1 semantic identity as ERTP's brand; the public representation is copyable. Issuance requires the existing authorized issuer/generation. A transfer requires the sender's signed authorization, the intended operation, and verification by the chosen binding. Sharing an image, currency definition, amount description, signed receipt or Atlas search result must confer no way to debit its holder. Give the UI separate handles for viewing an account, receiving payment, spending within a limit, and issuing supply. Resolve a lost reply by a persisted request ID before signing a replacement. [ERTP issuer/mint model](https://docs.agoric.com/guides/ertp/issuers-and-mints) · [ERTP purses and payments](https://docs.agoric.com/guides/ertp/purses-and-payments)

For identical inventory items, use ordinary finite units with integer quantity. For a unique item, the conservative interoperable building block is a programme with cap one and scale zero, verified issuer, and a signed metadata link to content-addressed art. Cap one alone does not define whether an item burned today can be reissued tomorrow. A unique collectible needs both one live owner and a lifetime issuance/reissuance policy, including the supply-account exception. Keep the item class gated until those rules are specified. Replicated art and names remain readable under their own media permissions. An offline game may accept graph-provisional ownership under its published rules. Mark any item whose use consumes a remotely supplied scarce resource as requiring the appropriate anchored receipt.

## Proposed market and escrow contract

An advertisement contains the issuer-qualified asset identifiers, public terms, binding, expiry and offer digest. Query and match can run on any peer, locally, or in an Atlas derivative; an index entry is a discovery hint. An acceptance names the exact terms/version, both sides' authorized accounts, maximum give, minimum want, acceptance of fees, and exit conditions. A peer may attach a signed offer during a partition. The interface shows whether it is advertised, accepted awaiting escrow, reserved, settled, canceled/refunded, expired, or disputed.

1. Begin with firm, whole-fill offers. An accepted seat specifies one set of give/want quantities and explicit fees. Partial fills require an opt-in lot size, integral price calculation and minimum cumulative output per fill. Sequential matching and book ordering are local policies. The safety predicate must hold for each independently accepted seat regardless of match ordering.
2. Reserve the `give` assets under their bound authority. A matcher produces a candidate reallocation but cannot move assets. In one settlement domain, validate all inputs, floor/scale/fee terms, expiry and expected revisions before submitting the linked postings. Each seat receives at least its entire accepted `want` bundle or recovers its full escrowed `give`. Fees for failed offers require separate authorization if supported. An equivalent retry returns the terminal outcome; a conflicting reuse fails. [Offer safety](https://docs.agoric.com/guides/zoe/offer-safety) · [Atomic reallocations](https://docs.agoric.com/reference/zoe-api/zoe-contract-facet) · [TigerBeetle linked events](https://docs.tigerbeetle.com/coding/linked-events/)
3. For crash recovery span the graph, intent store and ledger with persisted intent, deterministic leg IDs, reconciliation and an idempotent publication outbox. A single storage transaction cannot cover all those stores. Across servers maintain the ruled bilateral signed entries and explicit reconciliation. Never describe two independent acknowledgements as an atomic swap. A common escrow holding both assets can offer a stronger guarantee only after both deposits and its authority, exit rights and recovery assumptions are established. When escrow is unavailable, the UI retains its last signed status and displays pending until reconciliation. [Recorded boundary and PoC results](https://github.com/developing-today/code/blob/4cfceaa8afc08cf2cea88b9d733a2ace14c8ad5a/doc/2026-11-14T06-22-00Z_poc_currency_gateway_boundary_results/2026-11-14T06-22-00Z_poc_currency_gateway_boundary_results.md) · [Durable Object storage scope](https://developers.cloudflare.com/durable-objects/best-practices/access-durable-objects-storage/)
4. Where the trade is a currency conversion, reuse the signed directional rate authorization and exact-version quote, explicit fee, checked integer arithmetic and linked-leg conversion executor. At admission check the latest unrevoked authorization, quota and authenticity. The stage-adapter design makes authorization at durable admission binding: recovery completes an admitted conversion even if that authorization later expires or is revoked. A fresh intent must pass the current checks. For Pending Units, retain Drew's specific countersigned chain of options and time/exit policy. A generic offer must never let a pending unit fund ordinary use or bypass the original grant's provenance. Keep ambiguous option-escrow timing outside the generic settlement path pending current #2296 evidence. [Conversion design](https://github.com/developing-today/code/blob/4cfceaa8afc08cf2cea88b9d733a2ace14c8ad5a/doc/2026-11-01_design_id2063.md) · [Grant ruling](https://github.com/developing-today/code/issues/2296#issuecomment-6721993178)

### Backend transitions and identity

The staged design has distinct guarantees. Redis plus its durable store admits and recovers in sequence. A destination credit is spendable after the durable posted mark. A transfer spanning independent Turso databases can pass through a recoverable saga with held funds and compensations. A TigerBeetle linked chain settles atomically within its supported domain. Surface the weakest active guarantee to both counterparties and test migration with pending and posted records under the same canonical receipts. The performance figures in the verification programme are targets until timed on an identified deployment. [Staged contract](https://github.com/developing-today/code/blob/4cfceaa8afc08cf2cea88b9d733a2ace14c8ad5a/doc/2026-11-05_design_id5828.md) · [Verification programme](https://github.com/developing-today/code/blob/4cfceaa8afc08cf2cea88b9d733a2ace14c8ad5a/doc/2026-11-08_design_id5829.md)

An identity detail matters before a backend migration. Today the hash covers the entire canonical definition body, including its serialized binding and numeric ledger on an anchored definition; a changed body changes the semantic ID. Preserve that historical definition when a backend changes. A proposed, signed operational routing record can map its immutable binding to a fenced replacement instance, with both backends' last verified watermarks and the old instance closed for writes. If the logical binding itself changes, use an explicit predecessor/successor relation and authorized migration, with both identities visible. Add a vector that moves a deployment and still verifies old signed events before promising portable IDs across backend changes. ## Proposed fuel budget

A fuel quote names the app digest, executor identity, payer, allowed effect classes, maximum guest units, maximum host units, conversion ratio to any grant units, schedule version and expiry. Optional local execution uses operator-funded capacity or a local grant. A remote executor may require a finite grant before admission. A local meter unit is never implicitly transferable or redeemable at every server.

- **Reserve.** Verify the payer's signed budget, audience/executor, method set, version and revocation generation. Reserve against that budget before admitting any effect that incurs a charge. Splitting a parent into child funds debits the parent's available amount. Child limits, expiry, operation set and audience can only narrow. A child grant must fail an attempted reserve if its parent is revoked under the selected validation policy. A non-expiring offline delegation cannot promise immediate remote revocation.
- **Execute.** Retain the pure guest boundary and existing fairness scheduler. Price host effects where the host consumes an approved command, with prevalidated bounds such as input bytes, maximum output bytes, per-batch items and request count. Apply a separate memory cap, storage quota, cancellation deadline and job concurrency limit. Pin guest bytes, runtime/configuration, ABI, arithmetic/rounding and host cost schedule for reproducibility. Record external inputs once and replay their receipts. A native app backend that cannot enforce equivalent instruction metering advertises the usable capability subset or runs the metered guest on a permitted host.
- **Settle.** The receipt commits invocation ID, grant, caller, app, schedule version, reserved maxima, debits by resource, released remainder, execution outcome, and effect receipt hashes. Enforce checked arithmetic and total debit no greater than authorized reserve. On success bill measured guest units and priced host effects per schedule. Current upstream Wasmtime documentation says accounting on trap may be inexact, and a blocked host call is outside Wasm execution control. Distinguish a quoted per-slice trap charge for operator-sponsored quota from exact per-instruction billing. Require release-specific conformance before exposing any transferable debit for a failed guest. Refuse an ambiguous external effect retry unless its adapter supports persisted idempotency/status resolution. [Wasmtime fuel and host calls](https://docs.wasmtime.dev/api/wasmtime/struct.Config.html#method.consume_fuel) · [Determinism constraints](https://docs.wasmtime.dev/examples-deterministic-wasm-execution.html)
- **Recover.** Reopen a durable intent after a restart and reconcile by invocation and effect IDs. Charges need an immutable idempotency record beyond a live Wasmtime store. Expiry, cancellation or revocation blocks new spend at its serialization point. A charge already committed stays part of the receipt; release unspent reservations once. Restoration of an export rebuilds a view. It cannot create a second writer or regenerate held spending authority. In a partition only an exclusive authority with a specified fencing/anti-equivocation scheme can promise independently spendable preallocation. The graph default remains verifiable provisional claims. [Escrow-rights precedent and assumptions](https://arxiv.org/abs/1503.09052)
- **Bound abuse.** Reject invalid, oversized, expired and unauthorized commands before decoding/dispatching expensive work. Rate-limit untrusted ingress by byte cost and burst at the node and account/grant level; reserve bounded storage and queue space. Preserve the existing queue rule for eligible fuel-bounded guest calls and weighted sponsor budgets. Opening extra worlds must not multiply one payer's entitlement. A restricted, exhausted, or offline service still permits local graph drafts and reading previously authorized data. [ID guest admission](https://github.com/developing-today/code/blob/4cfceaa8afc08cf2cea88b9d733a2ace14c8ad5a/pkgs/id/crates/id-worlds/src/guest_burn.rs) · [Burst/rate definitions](https://datatracker.ietf.org/doc/html/rfc3290#appendix-A.4)

## Conformance oracles and implementation order

Use signed fixture inputs, a deterministic logical clock, fixed schedule and independent reference balances. Run the same operation sequence through the public caller-facing path, graph-native and anchored backends where the guarantee applies, and hosted relay with an injected lost reply. These are proposed verification cases. No test suite was run for this research pass.
