# Whose authority survives disconnection, recovery and retry?

*Research snapshot of November 23, 2026. Code and issue observations refer to the cited revisions and collection times.*

An agent can present a valid owner signature after the owner has removed its role on another device. A recovered identity can control its next keyset entry while lacking the keys to read an old backup. A hosted worker can acknowledge receipt while the recipient still lacks the object. Each UI needs to say exactly which of these facts it has established. Each host needs to enforce the same answer for the same evidence.

This chapter proposes integration contracts and conformance cases. The code observations refer to [main at 7310a957](https://github.com/developing-today/code/tree/7310a95730791e66da98f7b0e13865930058a516/pkgs/id). Runtime coverage across hosts and fresh CI results are unverified here.

## Inventory before adding a credential

| Existing boundary | What the source establishes | Design consequence |
|---|---|---|
| Local names, ID links and invitations | A private petname names a peer for one local user. A bare ticket names no inviter. The link form can bind an inviter key. The v2 decoder now enforces the source depth cap for externally supplied signed bytes, including events naming a parent. [Petnames][pet] · [Invitation forms][inv] · [Current invite decoder][event] · [#13250](https://github.com/developing-today/code/issues/13250) | Show how the counterparty key was learned. Reusing a friendly name, presenting a hash, or following a locator confers no new permission. Use the decoder’s existing fixture when testing import surfaces. |
| Graph space authority | A root grant signs for its space. A child needs delegation and attenuated typed path, permissions and validity. A stale authority frontier blocks delegated writes while reads can be marked stale. Same grant nonce plus same envelope is idempotent. Two-key control transfer requires matching signed statements. [Grant verifier][grant] · [Cross-signing ceremony][cross] | Preserve typed addresses, explicit delegation and the configured staleness bound. Distinguish a link between keys from transfer of control. |
| Agent/world authority | Agent delegation v1 has depth one, with owner-only renewal and role-defined lifetime bounded to 15 minutes–4 hours, default one hour. Role binding and signed delegation are verified by the host. A transport token alone grants no world role. [Agent delegation][agent] | A valid general graph delegation is insufficient to create a second generation of agent delegates. Design adapters for distinct authority domains. |
| Append moderation and trust | Admission receives policy at approval time. B02 implements local signed revocation and disable. B28 distinguishes suspect and prior admissions by local admission time, preserves bytes, and requires defined evidence to clear indeterminacy. [Graph admission][admit] · [B02][b02] · [B28][b28] | A queue item is a proposal. Approving it is a new decision. Independent replicas can first learn of a withdrawal at different times. |
| Custody and recovery | Guardian approvals name a request bound to an identity, prior head and successor. A successful recovery rotation revokes prior keys. The verifier has a checkpoint finality rule and ordinary continuation wins over a competing recovery from the same head. Recovery codes are a separate recorded design. [Recovery flow][flow] · [Guardian rules][rec] · [Code decision][codes] | UI can distinguish restoring a backup, rotating to a successor, and regranting a device or agent. Only advertise recovery methods actually enrolled for that identity. |
| MCP, query privacy and receipts | Host PolicySession gates tool/world/object/program scope, per-session budgets and audit. B17 defines signed query/relay authority. B18 maps scopes to disclosure policy. B19 distinguishes admission, bounded retention and challenge-verified presence. [MCP policy][mcp] · [B17][b17] · [B18][b18] · [B19][b19] | A host audit entry records a host’s claim. A B19 receipt asserts exactly its own kind. Neither establishes that a remote user viewed a message or that an external side effect completed. |

## Design lessons across generations

| Precedent | Import into ID | Limit of the analogy |
|---|---|---|
| Hardy’s KeyKOS confused-deputy example (1988) demonstrates a service inadvertently using its own privileges to fulfill a client request. E’s sealer and unsealer carry matched, distinct powers. [Hardy’s paper](https://www.cis.upenn.edu/~sga001/classes/cis331f19/resources/hardy88confused.pdf) · [E unsealer](https://papers.agoric.com/papers/robust-composition/full-text/) | Pass the specific effect capability into a provider invocation. Preserve the separation between the authority that creates a signed effect receipt and the narrower authority to inspect that receipt. | An in-process object reference or a private type alone cannot cross the wire as an authenticated grant. Preserve ID’s signed, scoped transport checks and verifier boundary. |
| SPKI/SDSI (1999) separates local naming from authorization certificates and reduces delegation chains by intersection. [Experimental RFC 2693](https://www.rfc-editor.org/rfc/rfc2693.html) | Put acting key, originating space, requested operation and remaining scope into the verifier’s decision trace. The private UI maps that result to the local user’s labels. | String prefixes lose the typed segment boundaries the ID verifier checks. Keep the existing chain format and test exact segment containment. |
| Tahoe-LAFS distinguishes write, read and verify capabilities. Directory links can convey narrower authority into a subtree. [Tahoe-LAFS capabilities](https://tahoe-lafs.readthedocs.io/en/latest/specifications/uri.html) · [Directory nodes](https://tahoe-lafs.readthedocs.io/en/latest/specifications/dirnodes.html) | Distinguish locating immutable bytes, reading plaintext, decoding media, and authorizing a future stream. Model what a recipient can keep after receiving bytes. | A Tahoe capability can embed a secret. An ID content hash is an identifier. Exposing a hash may disclose membership in a private collection even where no plaintext is returned. |
| Macaroons (2014) add contextual caveats to delegated bearer credentials. [Authors’ paper](https://research.google/pubs/macaroons-cookies-with-contextual-caveats-for-decentralized-authorization-in-the-cloud/) | Limit a delegated operation by audience, resource, duration and permitted action. Keep the predicate vocabulary finite and canonical, with unknown restrictions refused. | The paper’s chained MACs and bearer semantics have different verification assumptions from ID’s signed proof-of-key model. General third-party caveat calls would introduce availability and disclosure dependencies. |
| CONIKS (2015) studies verifiable key bindings, private lookup and consistency checking across views. [Authors’ USENIX paper](https://www.usenix.org/conference/usenixsecurity15/technical-sessions/presentation/melara) | For a recovered identity, persist the last independently observed head and detect incompatible continuations when devices reconnect. Request authorized independent evidence when a signer is suspect. | A single witness cannot establish that every peer saw the same history. Publishing raw user directory lookups or a global graph of who checked whom would expose relationships. Route design work under [#9148](https://github.com/developing-today/code/issues/9148). |
| Spritely Goblins implements distributed object references and asynchronous messaging via OCapN. The ID archive has a dedicated B13 comparison. [Goblins OCapN](https://files.spritely.institute/docs/guile-goblins/0.18.0/OCapN.html) · [ID B13][b13] | Bind promised results to a session and authority ceiling. A rejected predecessor cancels dependent calls. Treat a handoff as an explicit recipient-bound grant. Let unreachable session-local references expire without modifying durable graph ownership. | Persistent sturdy references, live session references and graph ownership have different lifetimes. Wire compatibility requires pinned independent implementations, a codec and netlayer, and interop evidence. |
| Messaging Layer Security advances group epochs when members change. [RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.html) | Scope future confidentiality to an explicit membership epoch for private group traffic. Compare the encrypted-message design against the existing relay’s durable/ephemeral split in [#2036](https://github.com/developing-today/code/issues/2036). | Changing keys cannot erase messages already disclosed. MLS group membership does not determine grant scope for an ID graph write. Adding MLS is a separate interoperability and key-management decision. |
| MCP HTTP authorization binds resources to token audiences. Its security guidance forbids passing an incoming token through to downstream services. [Authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization) · [Security guidance](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices) | Authenticate at the HTTP boundary, then require signed ID role proof and the host ceiling for each effect. A downstream service gets independently scoped credentials when integration requires them. Treat tool descriptions and annotations as display metadata. | A successful HTTP session, tool listing or consent at connection time cannot authorize arbitrary subsequent programs. Local MCP transports still need the same host authority check. |

## Four decisions hidden inside a single “retry”

Consider an agent that submitted a moderated graph write just before its owner withdrew a grant. The response got lost and a peer brings the write back online a day later. Proposed host behavior follows the phase of the operation.

| Operation | Evidence and outcome |
|---|---|
| Verify historical bytes | Verify original signatures and bound evidence. Retain the original admission decision and its frontier. Apply B02/B28 quarantine or flagging when incident evidence arrives. Replay of pure state carries no external side effect. |
| Admit a new write or approve a pending write | Recompute current grant, role, scope, expiry and applicable revocations. Reject a stale delegated write under the existing profile. An offline editor can retain a local draft and resubmit after reconciliation. Label the draft locally until admitted. |
| Resume an already committed effect | Match a stable operation ID to an authorized principal, resource, action and input digest. An identical completed request gets the prior outcome only to the extent the current caller may see it. A conflicting digest is refused. Distinguish idempotent replay at this boundary from the nonce semantics of signed graph grants. |
| Resume an external effect whose outcome is unknown | Persist an intent before dispatch. Reconcile by the target’s receipt or idempotency mechanism, if available. If the provider cannot resolve uncertainty, keep the result unknown and show the owner. Do not reissue an irreversible operation merely because the connection broke. |

**Proposed local decision record.** The producing host records the operation category, policy/revocation frontier seen, grant or role reference, decision time or interval, disposition and a link to any private receipt. The client sees its authorized explanation and a correlation handle. A foreign caller with no access to the resource receives the deployment’s uniform unavailable response. Counts, response shape and presence of a private path can disclose an object even when its contents are protected. B18 scopes and retention should also govern graph expansion, hidden-neighbor counts and search diagnostics. Any timing equivalence needs measurements. [B18 disclosure policy][b18] · [Existing B19 receipts][b19]

**Offline policy.** Previously authorized local use of bytes already possessed, tentative editing, and acquiring a new authority grant are different actions. Show the age and provenance of the local policy state where the existing rules admit a stale read. Require the appropriate fresh authority before distributing sensitive output or committing a delegated write. For currency or external resources needing exclusive settlement, apply the owning asset protocol’s reservation and finality rules. This classification requires no global always-online verifier. Bounded offline delegation leaves a real exposure interval after remote revocation. Communicate that interval in product terms. [Graph delegation][grant] · [Agent lifetime][agent]

## Identity lifecycle and permissions a person can understand

1. **Enrollment.** Show the local identity name, active device, custody method, reachable recovery method and what a successor can do. Device authentication, key possession, hosted login and successful graph authorization are distinct checks. Confirm an actual enrollment record before displaying a recovery badge. Respect the simplicity-first custody design in [#5684](https://github.com/developing-today/code/issues/5684).
2. **Recovery.** Name the identity and successor. Show whether the process will decrypt previously backed-up material, rotate the signing key, or do both. Use the existing guardian threshold and verifier’s delay, cancellation and checkpoint rules. Keep the one-time recovery-code variant separate and retain its settled parameters. Treat a request beside the chain as pending evidence. The owner can see supersession, cancellation and completion locally. [Guardian rules][rec] · [Recovery codes][codes]
3. **Re-entry.** Reconcile the old device’s highest verified head. A stale device must not reintroduce removed grants through import or cached permission choices. Previously encrypted content and third-party credentials may require independent recovery. Restoring signing authority alone has no effect on their encryption. New remote grants require current evidence for the new device.
4. **Permission review.** Before granting, summarize who asks, what resource and action are covered, which device or operator supplies the effect, how long the grant lasts and whether it can be delegated. Show recording microphone input separately from transmitting it. Preserve the user-versus-world-operator split. During update, compare old and new effective scopes. An unverified usage declaration remains unknown. [#5960](https://github.com/developing-today/code/issues/5960) · [#5999](https://github.com/developing-today/code/issues/5999) · [#6017](https://github.com/developing-today/code/issues/6017)
5. **Withdrawal.** Confirm which local authority was removed, name affected grants by owner-visible labels, and distinguish local enforcement from observations at remote peers. Show the difference between “future access withdrawn,” “peer acknowledged” and “previous plaintext copied.” Offer only recovery actions supported by this device and custody model. Local petnames and contact topology remain private unless there is explicit authority for disclosure. [Local names][pet] · [B02][b02]

## Verification and working order

The rows below are proposed joint scenarios. The named oracles can be implemented with deterministic clocks, fixture keys and synthetic contents. No live service or real credentials are necessary to specify their expected outcomes.

| Scenario | Independent oracle | Existing route |
|---|---|---|
| Same child scope beneath two visually similar typed segments | The verifier admits only the exact authorized segment. Renaming a private petname changes the label and leaves the decision bytes and effective scope unchanged. | [#9132](https://github.com/developing-today/code/issues/9132), [grant verifier][grant] |
| Remove a role between submission and moderator approval | The pending item remains identifiable, and approval under the new policy refuses it. Repeated denial causes no external effect. A preexisting signed admitted record remains available subject to B02/B28 release rules. | [#10237](https://github.com/developing-today/code/issues/10237), [admission][admit]. Preserve its closure hold. |
| Restore a stale device during guardian recovery | The requesting key cannot act as successor while evidence is pending. A competing ordinary continuation and a qualifying cancellation yield exactly the guardian verifier’s outcomes. Future signing and access to old encrypted content have separate results. | [#2382](https://github.com/developing-today/code/issues/2382), [guardian tests][rt] |
| Re-enter via an MCP tool after delegated role expiry or local budget exhaustion | No downstream provider invocation. Audit identifies refusal. When the local quota is exhausted the host emits the defined park event. A fresh HTTP token that lacks the applicable ID role fails to restore authority. | [#6300](https://github.com/developing-today/code/issues/6300), [#7917](https://github.com/developing-today/code/issues/7917), [policy][mcp]. The designated #7917 slice is bounded program interaction and spike reporting. |
| Deliver A → B → C handoff after its session is lost | Intended recipient and ceiling survive only as specified for its reference class. A failed precursor yields zero dependent effects. Repeated delivery has at most one application effect if that contract is supported. | [#9143](https://github.com/developing-today/code/issues/9143), [B13][b13]. |
| Compare operator claims from two partitions | Preserve both signed claims and time of local admission. Conflicting results survive investigation. The UI labels each B19 receipt kind separately and never relabels a host audit entry as verified user action. | [#9148](https://github.com/developing-today/code/issues/9148), [#2039](https://github.com/developing-today/code/issues/2039), [B19][b19]. |
| Ask for a private result through local and hosted graph search | Under identical policy and evidence, response data, count fields, visible neighbor links and disposition disclose only permitted facts on both routes. Test a user newly denied after a prior successful result. | [#9144](https://github.com/developing-today/code/issues/9144), [#6062](https://github.com/developing-today/code/issues/6062), [#10698](https://github.com/developing-today/code/issues/10698). |

Start with an inventory of normal entry points and the grant/role verifier each invokes. Then trace a single read, a moderated write and an agent effect across one local and one hosted profile. Use those traces to locate which checks run at grant creation, intake, approval, dispatch, retry and receipt retrieval. Only after a confirmed unsatisfied invariant and fresh ownership review should a new finding be filed. Keep the existing issue map and B-series identifiers. New credential formats, a compulsory witness service and a second recovery system are unnecessary for these comparisons. The remaining design decisions are which effects require fresh cross-peer evidence, which may produce offline drafts, and what a reauthorized caller can learn from an operation receipt. Decide these per existing capability and resource class, with the verifier, UI and conformance vector changed together.
