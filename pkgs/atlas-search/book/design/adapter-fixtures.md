## Proposed publication and deletion protocol

1. Reserve a unique source delivery under a per-source/host lock with a fencing token. Store source scope, object ID, revision/cursor, event type, observation time, and reason code. Separate source discovery progress, staged progress, publication and reconciliation coverage. An already-completed delivery has no new effects. Newer deletes/reclassifications fence out stale updates. On sources without ordered revisions, fetch the current version again.
2. Compare cheap revision metadata, then SHA-256 of the source bytes, then versioned parsed chunks. The stable embed key covers allowed content bytes, model ID and digest, pooling/normalization and parser/chunker contract as applicable. Store pipeline fingerprints independently so a model-only change need not reparse. A moved byte span can create a new occurrence of an existing embed. Source-native boundaries take precedence over overlap. A small edit charges exactly the changed distinct embed inputs, including any changed boundary neighbours. Measure that count instead of promising one embed for every possible edit. [#6028](https://github.com/developing-today/code/issues/6028) · [#12625](https://github.com/developing-today/code/pull/12625)
3. Land candidate bytes only within a policy-approved restricted staging area, preserving object/occurrence authority. Unknown/mixed boundary is restricted. The gate records ordered write/classify/dedup/provenance/publish verdicts. A missing verdict fails, a changed stage input invalidates all affected later verdicts, empty publish cannot advance the public watermark. Produce counts and typed refusal/publish attestations at batch sensitivity, chain to prior attestation, exclude candidate text. De-duplicate within each authorized security domain; sharing a content digest cannot authorize another occurrence, CAS locator or private history. [#11995](https://github.com/developing-today/code/pull/11995) · [#6045](https://github.com/developing-today/code/issues/6045)
4. Keep durable tombstones keyed by source/scope/object/version. In one metadata transaction, advance applicable policy/revocation epoch, retire the occurrence from the serving manifest, enqueue idempotent deletes for each FTS/vector/sparse/cache/recommender/snapshot/replica target and preserve a minimal forensic attestation. All query, read, recommend and cached paths acquire a valid serving generation with the correct epoch. On failure to validate a revocation floor, deny the affected scope, including offline replicas; configure explicit lease expiry if offline availability is desired. Built but unpublished snapshots are unreachable. An authorized live duplicate retains its own references. A physical object is reclaimed only when all permitted reference/retention requirements allow it. The purge ledger records acknowledgements by target/generation, unresolved offline replicas, CAS collection, old index/cache invalidation and backup retention/restore gating. Restore replays tombstones before serving. Distinguish immediate logical removal, asynchronous verified deletion, and retained backups with documented expiry. Across independent systems this supplies one visible logical operation. SQLite WAL does not guarantee crash-atomic transactions across attached files. FTS deletion may retain recoverable terms, and the underlying engine/version decides how physical erasure can be substantiated. [SQLite ATTACH](https://sqlite.org/lang_attach.html) · [FTS5 secure deletion](https://www.sqlite.org/fts5.html#securedelete)
5. Record freshness as latest verified source offset, last complete reconciliation time, last accepted batch, latest serving manifest, and replica/cache progress. A continuing backup or webhook receipt alone does not demonstrate corpus freshness. Limit rates by measured budget and load, halt on plan exhaustion, and treat incomplete or failed collection as unknown. Keep source IDs, locators, content digests and per-source small counts local or restricted as appropriate.

## Muse adapter and per-source fixtures

The issue asks for main and side conversations, memory and artifacts. An allowlisted repository REST title search for “Muse” and “Atlas” returned #9097 alone. The published automatic-ingest chapter says it has no recorded Muse export/API mechanism. This evidence establishes the requested data families. It does not establish any export format, local database, API scopes, exhaustive deletion markers, or automation rights. Do not assign those properties to Muse. [#9097](https://github.com/developing-today/code/issues/9097) · [Atlas automatic ingest](https://developing-today.github.io/code/atlas/design/automatic-ingest.html)

**Atlas-side fixture contract.** Now fixed as `atlas-muse-import/v1`, with a 17-step synthetic fixture and a reference replay, in [the #13607 design record](https://github.com/developing-today/code/tree/main/doc/2026-11-26T08-18-36Z_design_atlas_muse_import_contract_13607); where the table below and that record differ, the record governs. The input to the adapter is a manifest plus a local payload directory. A future authorized export mapper emits this shape after verifying the producer schema. A fixture writer can already produce it. An export file, provider API or account session does not need to exist to exercise this contract. A source locator for read tools is issued independently of the stable source object key.

**Fixture acceptance.** Offer a synthetic two-part snapshot with a main thread, side branch, a memory record and an artifact linked twice. Replaying either part produces the same occurrences and adds zero vectors. Updating one message revision changes the intended span and leaves both attachment references intact. Deliver a later delete before replaying the original update; that reference stays retired by revision. A newer explicit restore requires source authority and a later accepted revision. A delta omitting a sibling preserves that sibling; a scope-complete, authorized export with a missing item can propose a tombstone only once completeness is verified. An account visibility change revokes impacted reads immediately. Corrupt member digests and incomplete manifests produce no partial visible publish. The oracle derives expected revision and occurrence sets by replaying a small independent source fixture. Search, read, related and cached reads run under two ceilings; the narrower caller never receives the restricted side branch or an existence oracle. Provider-specific validation will require a user-authorized export/API sample whose format and completeness can be documented, and local mapping before any live ingestion.
