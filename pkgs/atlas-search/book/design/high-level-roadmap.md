# High-level roadmap

> **The whole-project view, Atlas slice — a dated snapshot.** This chapter carries Atlas's share of the merged priority list built by the Code Book programme (tracker [#13905](https://github.com/developing-today/code/issues/13905)): the items Atlas owns, in full, and one-line pointers to the items Atlas only touches. The census behind it was taken on **2026-11-23/24**; statuses are as of that census unless a later read is named. The merged list itself lives in the [Code Book](https://developing-today.github.io/code/code/). Where this chapter and a living tracker disagree, the tracker is right and this chapter is stale.

This chapter does not replace [Roadmap and issue map](roadmap-and-issue-map.md). That chapter is the Atlas programme's own workstream order and issue register, counted from the Atlas census. This chapter is the cross-project ranking — where Atlas's items sit in the whole project's order, why they sit there, and what their timing record says. The two chapters cross-reference; neither duplicates the other.

The merged list is ordered across the whole project: execution substrate first (fleet), then the physical substrate (lab), then the data substrate (backups, ingest, storage placement), then search intelligence (Atlas and ID together), then the ID platform build-out, then the gateway, PM and fork surfaces, then the record itself. Atlas owns items 7–14 — the whole data substrate and the whole search-intelligence tier. Item numbers below are the merged list's numbers, kept so a reader can move between books and the Code Book without renumbering.

Types used below: a _capability set_ is a capability set to reach; a _problem_ is a problem to solve; a _milestone_ is a milestone; a _shift goal_ is a goal that marks a shift. Status words are the census's: done, in flight, designed, not started — each with its evidence.

## Item 7 — Backups and storage automated, minimal duplication, one coherent complete backup set

- **Type:** problem. A seed item from Drew's list on #13905.
- **Description:** Replace per-system backup timers and overlapping copies with one automated mesh: every store backed up, deduplicated by content, restorable as one coherent set.
- **Status (census 2026-11-23):** partially done, mesh not started. What exists is the laptop's daily `atlas-backup` timer — a database snapshot plus an extracts archive with verify proof, into the shared R2 bucket `supabase-backups` under `atlas/` by date — one system's backup, automated. The cross-system mesh in #9093 is designed only. The estate it must cover is large: 50 Turso databases, live-verified 2026-11-23 in the PM census. Atlas is primary because it holds the largest store and the only working backup today.
- **Most related:** [#9093 — backup mesh: all-Turso 14-day restic-zstd to R2, the R2/laptop/Drive mesh, D1 and laptop databases into Turso](https://github.com/developing-today/code/issues/9093) (open) · [#9094 — OpenCode DB backup economics](https://github.com/developing-today/code/issues/9094) · [#3125 — provenance programme, whose backup and plain-extracts rule carries Drew's 2026-10-31 ruling: keep all data, clean only byte-identical duplicates, keep backups](https://github.com/developing-today/code/issues/3125) · [#9098 — embed-storage economics](https://github.com/developing-today/code/issues/9098) · [#9133 — storage benchmark harness](https://github.com/developing-today/code/issues/9133).
- **Timing:** the daily backup timer is live today; no start date is in the record. The #9093 mesh has no timing in the record. Drew's keep-everything rule is dated 2026-10-31. No planned date, no recorded miss, and no reprioritisation are in the record for this item.
- **Ordering rationale:** safety precedes scale. Ingest automation (item 8) and storage migration (item 11) both mutate the corpus; they should not run ahead of a coherent restore story.

## Item 8 — Atlas ingestion fully automated

- **Type:** capability set. A seed item from Drew's list on #13905.
- **Description:** Continuous ingestion — event hooks where the source supports them, scheduled sweeps otherwise, delta-only where possible — replacing today's manual, script-driven imports, with a recount procedure so corpus counts never freeze silently again.
- **Status (census 2026-11-23):** designed, acceptance unmet — the single biggest ingest gap in the Atlas census. Today all corpus ingestion is manual and script-driven; the only Atlas schedule on the laptop is the daily backup timer; canonical counts are frozen at the 2026-10-31 publish (18,325 sessions, 122,124 messages, 107,639 chunks). A staging tier exists in code (`atlas_stage` v1) whose aggregator, embedder and session-close hook are explicitly not built.
- **Most related:** [#9097 — continuous ingestion programme](https://github.com/developing-today/code/issues/9097) (open; workstream E of the v1 build-out under [#8983](https://github.com/developing-today/code/issues/8983)) · [#7969 — recurring ingestion sweep runner and guardrail monitor](https://github.com/developing-today/code/issues/7969) (open, not built) · [#6018 — long-term ingestion programme](https://github.com/developing-today/code/issues/6018) · [#6028 — delta-only ingestion and offset embeds](https://github.com/developing-today/code/issues/6028) · [#5670 — migrate ingest scripts into code and the fleet binary](https://github.com/developing-today/code/issues/5670).
- **Timing:** the continuous-ingestion design is dated by #9097's source list (Drew, 2026-11-12). The miss of record: canonical counts froze at the 2026-10-31 publish because ingestion stayed manual — the freeze is the stated reason the recount procedure is an acceptance item. No projected automation date is in the record.
- **Ordering rationale:** everything in the search-intelligence tier is only as fresh as this pipeline. It outranks coverage expansion (item 9) because automating the pipe precedes widening what flows through it.

- **Most related:** [#3125 — provenance registry programme](https://github.com/developing-today/code/issues/3125) (open, priority/high) · cold-tier follow-ons [#8227 — shard writer](https://github.com/developing-today/code/issues/8227) (already tasked, parked — it needs a dedicated shift) through [#8231](https://github.com/developing-today/code/issues/8231) · [#9100 — virtual filesystem over the CAS](https://github.com/developing-today/code/issues/9100).

- **Ordering rationale:** provenance is the trust layer under deduplication, deletion propagation and the ID-graph publication (item 12); finishing it before the recommender (item 13) keeps the behavioural tables rebuildable.

## Item 12 — Atlas and ID integration: search runs across the core system

- **Type:** shift goal. A seed item from Drew's list on #13905. Atlas is the primary book for this item; the ID book carries it as a cross-link, because the graph side and its projectors are treated in the ID book's detail.
- **Description:** End the split where ID has no live query path into Atlas and each server answers with basic per-server BM25-style queries: Atlas objects and provenance become ID-graph objects, ID content is vectorised into Atlas, and one retrieval core serves the CLI, REST, MCP and ID.
- **Status (census 2026-11-23):** designed, implementation not started. Verified 2026-11-23: ID has no live query path into Atlas; the shared ground in code is only the content-hash v1 test vectors. Drew's "Atlas baked into ID" framing is recorded as a direction to explore, not a decision of record — the recorded decisions are #6062 (format) and #9109 Part C.
- **Most related:** [#6062 — ID-graph publication format design](https://github.com/developing-today/code/issues/6062) (open, design only) and the projectors [#11182 — versions, files, relations](https://github.com/developing-today/code/issues/11182), [#11183 — attestations and ingest runs](https://github.com/developing-today/code/issues/11183), [#11184 — projector operations](https://github.com/developing-today/code/issues/11184), [#11185 — view presets](https://github.com/developing-today/code/issues/11185), [#11186 — conformance audit](https://github.com/developing-today/code/issues/11186) (all open; #11182–#11185 enqueued in the ID-100 list at priority 70) · [#9109 — #9106 Part C: storage economics, ID search, recommendations](https://github.com/developing-today/code/issues/9109) · [#9106 — second ID programme epic](https://github.com/developing-today/code/issues/9106) · [#5755 — fleet atlas-search fan-out over the shard core](https://github.com/developing-today/code/issues/5755).
- **Timing:** the #6062 design was open at census; the projectors #11182–#11185 were enqueued on 2026-11-23 (ID-100, priority 70). No projected dates are in the record.
- **Ordering rationale:** the highest-leverage shift in the census: it converts two half-systems into one core. It ranks first in its tier because rerank and recommender quality (item 13) and the ID-graph apps (item 15 in the ID book) both presume a unified corpus and ranking path.

## Item 13 — Rerank and recommender systems in Atlas

- **Type:** capability set. A seed item from Drew's list on #13905.
- **Description:** A learned reranking stage in the serving path (golden-set-gated) and a recommender built from real retrieval behaviour — session co-occurrence neighbours, feedback signals, recommendation objects with per-class retention, and a "next 10" surface.
- **Status (census 2026-11-23):** designed; serving does not exist. Verified: production fusion is reciprocal-rank fusion over full-text search (BM25) plus vector only; no learned or cross-encoder reranker exists in the serving path; feedback is captured (`atlas-feedback/v1`) with no ranking consumer found; recommendation generation does not exist — only the snapshot-paging state machine was in flight, and it has since landed: PR #12873 merged and #10158 closed as completed on 2026-11-23 (re-verified before this chapter merged). Recommendation generation itself still does not exist. The golden set — 311-query v3 plus 54 held-out — is the gate every candidate must pass.
- **Most related:** [#9140 — recommendation objects, search history, retention classes](https://github.com/developing-today/code/issues/9140) (open, design) · [#10158 — recommendation snapshot paging](https://github.com/developing-today/code/issues/10158) (closed, completed 2026-11-23; PR [#12873](https://github.com/developing-today/code/pull/12873) merged; hard dependency #9083 — at census it was open, in review, with the PR unmerged) · [#8627 — standing cross-agent eval sets](https://github.com/developing-today/code/issues/8627) (the quality oracle) · [#5733 — Jaccard third-signal gate](https://github.com/developing-today/code/issues/5733) (eval results on record) · [#5773 — query-understanding front-end](https://github.com/developing-today/code/issues/5773) · [#5774 — query-time parameter surface](https://github.com/developing-today/code/issues/5774) · [#9092 — search v1 build-out](https://github.com/developing-today/code/issues/9092).
- **Timing:** golden-set gate results are on record from the 2026-11-08 design onward; #10158's PR #12873 was open at census and merged on 2026-11-23. No ship date is in the record — the gate doctrine is explicit that a reranker that hurts on Atlas's own queries does not ship, whenever it is ready.
- **Ordering rationale:** deliberately after items 8–10: a reranker trained or evaluated on a frozen, provenance-poor corpus would bake in today's gaps. The eval gate (#8627) existing is what makes this safe to build next.

## Item 14 — Atlas as a multi-client search service: the product decision and its build

- **Type:** milestone.
- **Description:** Answer the open product question — Atlas as a multi-client service (OpenChamber and fork sessions, ID, and agents as first-class consumers) versus Drew's personal CLI — and build the service shape the answer implies, with per-agent identity instead of today's shared hosted identity.
- **Status (census 2026-11-23):** in flight, decision open. A service shape already exists de facto (the fleet search service, the Worker, and the mcpx `atlas` server, all live), but the thread-2 commitment is unanswered on the issue, and all hosted MCP callers still share one identity (`hosted-per-user`, personal ceiling).
- **Most related:** [#12900 — search improvements; thread 2 is this decision](https://github.com/developing-today/code/issues/12900) (open, in review; thread 1 parallel branches landed via PR #13039; thread 3, the Rust binary, substantially landed) · [#5350 — epic: Atlas as Rust binary and multi-client service](https://github.com/developing-today/code/issues/5350) (open; children #5351–#5356 all closed) · [#8625 — MCP surface and per-agent identity](https://github.com/developing-today/code/issues/8625) (open, blocked on cross-client acceptance) · [#6805 — Worker cache eviction and invalidation](https://github.com/developing-today/code/issues/6805).
- **Timing:** #12900's exploration was opened by Drew on 2026-11-04, moved into this repo on 2026-11-22, and its thread 1 landed on 2026-11-23 (PR #13039). The thread-2 decision has no date in the record.
- **Ordering rationale:** the decision gates real investment in identity, caching and ceilings; it sits after item 12 because ID-as-consumer is the strongest evidence for the multi-client answer.
