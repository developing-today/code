# Implementation programme and evidence gates

**November 23, 2026.** This plan orders the next Atlas experiments by what their results can establish. It extends the existing design chapters. Each experiment has an input, a comparison and a stopping condition. A merged component is evidence about the repository. A production claim also needs a receipt identifying the running version, store role and publication generation. The living work ledger is [the programme tracker](https://github.com/developing-today/code/issues/13241). This chapter's delivery is [#13541](https://github.com/developing-today/code/issues/13541).

## 1. Follow one source revision to its reader

Start with an approved first-party source with an existing writer, such as repository comments. In a disposable store, capture one synthetic revision, deliver it twice, edit one part, then remove it. Record the highest contiguous source revision durably staged, the revision admitted by classification, the published generation and the revision seen by Fleet on cold and warm queries. Preserve gaps explicitly. A cursor can advance after durable staging even while the serving generation lags. The first transition that fails identifies the owning component.

Use the existing sweep state machine, watermark detector, ordered promotion gate and occurrence writer. Register stable source identity independently of content identity. Identical text from two sources has two occurrences, potentially with different entitlements. Key vector reuse by model revision, preprocessing and the actual byte window seen by the encoder. An unchanged central chunk can acquire new context after an adjacent edit. Reuse only an unchanged encoder input. On an incomplete crawl, preserve the previous generation and reconcile the missing page before inferring deletion. Measure the live canonical database in a consistent read transaction. Identify its writer and published consumer independently. Record aggregate physical row counts and the observation interval for each store role. Shards, content stores and staging units have different schemas. A recount of a file whose provenance is unresolved remains useful as a file observation. It cannot establish freshness for an entire source. The October 31 canonical figures, a later rebuilt export and a publish-source snapshot each answer a different question. Extend the source inventory one connector at a time. For queue/PM and ID record an ordered native event or revision. For GitHub reconcile object identities, pagination, permissions and deletes. For Muse establish which owner-authorized conversation, memory and artifact exports exist. For OpenCode admit only the agreed visible part types. For notes, reports, repo docs and local stores, record producer, scope, revision, deletion authority and replay procedure. The first memory connector already registers five corpus types and demonstrates one promotion path. External repositories await the relevant licensing and zone dispositions; Gmail remains paused. ## 2. Prove eligibility before experimenting with ranking

Force an unauthorized synthetic item to be the closest vector and the strongest literal match. Give a second caller the same ceiling but a different source grant. Derive the expected admissible IDs from a small independent fixture, then inspect both branch candidate sets, the fused list, hydrated neighbors, explanations and cache hits. Change only the forbidden item and its interaction history. The lower-ceiling caller should see identical results. A failure here takes precedence over a latency improvement.

Compare exact search over eligible rows against the installed index's actual predicate placement. A global nearest-neighbor lookup followed by a filter can exhaust the pool with forbidden rows and omit the best eligible neighbor. Partition static authorization boundaries before search. For a dynamic restriction unsupported by the index, retain filtered exact retrieval as the oracle and fallback. Repeat on the real local and service backends. Check the actual route used when the CLI can delegate to standalone. ## 4. Exercise consumers and recommendations on the same revision

For hosted access, start with an opaque occurrence reference. Resolve it against current authority through the service's job-scoped read path. Test a removed grant after a result, cursor and cache entry have already been issued. Repeat with REST, MCP, standalone CLI and Fleet, recording the actual backend and identity class. Cache admission, result expiry, D1 invalidation, purge and replica staleness require separate observations. A merged D1 component proves nothing about a live Worker result's lifetime. [The Atlas MCP server](../reference/mcp.md) · [Design: MCP and programmatic access, next steps](access-evolution.md) · [Worker result-cache policy](https://github.com/developing-today/code/issues/6805) · [D1 invalidation](https://github.com/developing-today/code/pull/13378)

Prove the two ID directions independently. Publish an Atlas occurrence with lineage to the ID graph and replay it. Separately ingest a native ID revision into Atlas, retrieve it, resolve the current ID object, then tombstone it. Preserve origin and pipeline identity to prevent cycles. A changed model revision produces a distinct derived index row. Changing only a hidden graph edge must leave a lower-ceiling query unchanged. The Atlas→ID publication design and the ID→Atlas async vector contract have different implementation owners. [Publication format](https://github.com/developing-today/code/pull/7998) · [ID search](https://github.com/developing-today/code/issues/9138) · [Async vector contract](https://github.com/developing-today/code/issues/10171) · [Design: search integration for fleet and ID](fleet-and-id-integration.md)

For the recommender, compare a time-decayed eligible profile, session co-occurrence, recency and visible graph neighbors with a recency-only baseline on later eligible events. Report candidate coverage, nDCG, repeated items, diversity and p95. Freeze the admitted order before signing the page snapshot. Test retries and revocation against the existing snapshot state and durable accumulator. Production candidate generation, signer and deployment each need their own proof. ## 5. Record the release decision

For each arm, retain the code SHA, source and index generations, scope policy revision, parser/chunker/model revisions, qrels fingerprint, class denominators, latency and resource budget, run URL, outcome and rollback target. Separate observed data from proposed thresholds. Publish aggregate results and synthetic examples only. A failed authorization invariant blocks release. An inconclusive quality comparison stays in shadow. An accepted change switches readers to a generation whose preconditions still hold. A rollback must continue to enforce newer deletions and grant revocations.

Keep three decisions with Drew. The wrong-tier copies in #8479 require a purge or reviewed reclassification decision. The multi-client scope in #12900 determines which identities to provision. OpenCode reasoning records in #9097 require an explicit inclusion decision. None of these decisions is necessary to run the synthetic experiments above. Capture per-source freshness and use the measured bottleneck to choose the next work item.
