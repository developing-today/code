# Consumers: fleet, agents, memory and ID

Source: written from `pkgs/fleet/crates/fleet-search/src/` (`cli.rs`, `client.rs`, `pyjson.rs`, `render.rs`), `pkgs/atlas-search/docs/memory-integration-design-8567.md`, `home/common/mcpx-settings.nix`, and the consumer inventory in the Atlas programme research, in https://github.com/developing-today/code/blob/main/. Provenance only — this chapter is complete without following it.

Atlas exists to be asked questions by other systems. This chapter names every class of consumer, the surface each one actually uses, and the sensitivity ceiling each one gets — because in Atlas the ceiling is part of the consumer's identity, not a per-query preference. A **ceiling** is the highest rung of the sensitivity ladder (canonically `public`, then `internal`, then `private`, then `sensitive`; in code spelled `shareable`, then `personal`, then `local-only`, then `secret-bearing`) a search may touch; it is enforced inside the branch queries, before any ranking, and then clamped server-side to the calling client's cap, so `effective = min(requested, cap)` and no consumer can widen its own access by asking. The full model is in [Sensitivity tiers and client ceilings](sensitivity.md); the serving machinery behind every surface here is in [The service and the Worker](service-and-worker.md).

One caveat applies to every consumer equally: the corpus they search is the frozen 2026-10-31 publish (18,325 sessions, 107,639 chunks) until automatic ingest lands. Agents routinely assume the corpus is current. It is not, and that gap — not latency, not ranking — is the largest consumer-facing problem Atlas has.

## Fleet: `fleet search`

The primary agent-facing consumer is the fleet itself. Every fleet agent and seat — Muse lanes, OpenCode sessions, other seats — looks up prior work through `fleet search`: past decisions, session evidence, "have we seen this before", across all the corpora Atlas holds. The user's order of 2026-11-22 made `fleet search` the documented route for all agents and sessions.

`fleet search` is not a second implementation. It is the `atlas-search` client surface **ported flag-for-flag** into the fleet binary: the same hybrid full-text plus vector search (default mode hybrid; `--mode fts` or `--mode vector`), the same filters (`--kind`, `--topic`, `--project`, `--client`, `--since`/`--until` session dates, `--max-sensitivity`), the same shaping flags (`--group-by-session`, `--expand` for neighbouring chunks, `--with-message`, `--hydrate`, `--pool` per-branch candidates, `--k` final results), and a `get-chunk` verb that returns one chunk with its provenance. The fleet workspace deliberately carries no second embedder and no second backend; the search domain consumes the Atlas crates as they are.

Because the two binaries must print identical bytes for identical searches, the port is guarded. The fleet copies of the two output writers — `pyjson.rs`, the Python-shaped JSON writer, and `render.rs`, the envelope renderer — must stay byte-identical to the `atlas-search` originals outside their pinned parity headers. A repository script, `check-fleet-search-parity.sh`, compares exactly those two files, with its own contract test suite beside it. One honesty note: the guard workflow is dispatch-triggered only, so the check exists and is cheap, but nothing runs it automatically on every change to either copy — drift is detectable on demand, not yet gated on push.

Routing depends on where the caller sits. A sandbox seat defaults to **via-service**: the job protocol against the laptop service at `http://127.0.0.1:18760`, reached through the laptop SSH forward, with a loud fallback to standalone if the service route fails. A laptop seat defaults to **standalone**, which is a delegation rather than a reimplementation: the fleet verb runs the deployed `atlas-search` artifact with the caller's arguments in `atlas-search`'s own shape and inherits its output byte-for-byte. Explicit flags beat environment, which beats fleet configuration, which beats the host default. Two details follow from the protocol's shape: `get-chunk` is job-scoped in the protocol, so it always runs through the standalone artifact (with a loud note when via-service is in effect); and `init` and `fetch-model` are not fleet verbs at all — they stay on `atlas-search`, and asking fleet for them is a usage error. Ceilings on this surface are enforced by the service from the client identity read out of `~/.config/atlas-search/client.json`: the sandbox-scripts identity is capped at `personal`, the user's own CLI identity at `secret-bearing`.

## Agents: the MCP server in mcpx

The second live consumer class is agents speaking the Model Context Protocol (MCP), the standard tool protocol agents use to call external services. The Atlas MCP server is the Worker's `POST /mcp` endpoint: a stateless Streamable HTTP MCP server exposing **exactly one tool, `search`**, running through the same single execution path as the Worker's REST search — same pinned context, same ceiling, same Durable Object cache, so an agent's MCP query and a REST query for the same text share one cache entry. Cache purge and inspect are deliberately not MCP tools: purge is a write, and inspect is an operator audit surface.

On the laptop, this server is wired into **mcpx** — the fleet's MCP aggregation daemon — as a remote server named `atlas`, configured in the mcpx settings as a URL plus bearer authentication expanded from the daemon's environment at runtime (the token value never lands in the configuration file or the Nix store). That wiring is what puts Atlas search in front of OpenClaw, OpenCode sessions, OpenChamber, and Muse lanes as one namespace among their other tools.

Here the book must state the source behaviour over the design's ambition. The memory-integration contract for this endpoint says the MCP layer stamps the calling agent's identity and enforces that agent's own ceiling and corpus scoping. **That is not what the shipped endpoint does.** The Worker checks one shared gate token and extracts no caller identity from it; every MCP caller shares the one hosted identity — disclosure context `hosted-per-user`, ceiling `personal`. Per-agent identity stamping, per-agent ceilings and corpus scoping, and a query audit log are later slices of issue #8625, deliberately not improvised in the current code, and #8625 stays open on the cross-client acceptance verification (each named consumer querying the unified index with its own identity). What an agent gets today is real and useful — the full hybrid search at the `personal` ceiling, cached — but it is a shared door, not a per-agent one. The endpoint's own reference is [The Atlas MCP server](../reference/mcp.md).

## Memory: the OpenClaw and agent-memory integration (design)

The third consumer is agent memory itself, and this one is a **design, not shipped behaviour**. The decision of record is `pkgs/atlas-search/docs/memory-integration-design-8567.md` (issue #8567, decided by the user 2026-11-10 under parent #1300): fleet and agent memory integrates **into** Atlas — everything queryable across all agents and corpora — rather than living in local-only silos or in a separate new store.

The design indexes one unified index over **five corpora**, each keeping its existing owner and source of truth: agent memory (OpenClaw's memory store), Muse memory files, the Zettelkasten/Emanote notes, repo docs, and research reports. Every indexed unit carries its corpus, agent, source reference, update time, sensitivity, and zone. The index lives inside Atlas as named corpora in the existing store, ingested through the same staging and registry path as every other source — no new vector store, and the index is always disposable while the corpora never are. Memory content gets no side door around the staging, classification, and promotion discipline described in [Ingest today: staging, classification, promotion](ingest.md).

The access-pattern decision is **MCP first**, for four recorded reasons: one protocol all agents already speak; one policy-enforcement point instead of one per tool; identity travels with the protocol; and Atlas stays a service rather than becoming a library forked into every consumer. Native library access is reserved for Atlas-internal processes; per-tool native access was the rejected alternative, revisit-able only on a measured latency case with its own design record. The query surface itself is the same core `run_search` over the union, with ceiling and corpus filters applied inside the branch queries — before ranking, never after — and every hit naming its corpus and source reference.

What exists today is the MCP endpoint above and the decision. The connectors that would feed the five corpora into the unified index are not built: the corpus registry and memory connector are issue #8622, the remaining corpus connectors are #8626, and both are open. Until they land, memory recall still runs against per-agent silos — OpenClaw against its own local store, each agent against its own files — and the unified memory index this design describes does not exist to be queried.

## ID: the designed consumer with no live query path

The fourth consumer, ID — the fleet's identity and object-graph system — is likewise **designed, with no live query path today**. The designed relationship runs in both directions. Atlas corpus objects, with their provenance and lineage, publish **into** the ID graph in a defined publication format (issue #6062, with a projector set filed as #11182–#11186, all unstarted). In the other direction, ID content is automatically vectorized — Snowflake plus the second embedder from #9092 — feeding a built-in ID search over the object graph, with recommendation surfaces on top (issue #9109, Part C of the ID/Atlas federation programme). Neither direction is built: the publication format is undesigned-to-unbuilt, no projector runs, ID objects are not in the Atlas corpus as a searchable class, and there is no ID-side query surface to call. The full design, its substrate questions, and its issue map are in [Design: search integration for fleet and ID](../design/fleet-and-id-integration.md); nothing in this chapter's other sections should be read as ID search working.

## Evaluation: the consumer that measures the rest

The final consumer is Atlas's own quality loop. Evaluation consumes the same core as every other surface — the same `run_search`, the same corpus, the same embedding space — and scores what comes back against judged golden sets, so that a ranking change proposed for fleet or agents is measured before it is believed. It also consumes Atlas's exhaust: every executed search can mint a query trace, and users and agents can attach feedback to a (query, chunk) result identity; both feed statistics and weekly reports. Evaluation gets no special ceiling and no special corpus — that is the point — and its instruments, gates, and recorded disagreements are the whole of [Evaluation: golden sets and gates](evaluation.md).

## The ceilings, in one table

| Consumer | Surface | Ceiling cap |
|---|---|---|
| The user's own CLI (`drew-cli`) | `fleet search` / `atlas-search`, standalone or via-service | `secret-bearing` |
| OpenChamber sessions | via-service | `personal` |
| Fork / OpenCode agents | via-service | `personal` |
| Sandbox scripts and Muse lanes (`sandbox-scripts`) | via-service | `personal` |
| Hosted MCP callers (all agents, shared identity) | Worker `POST /mcp` via mcpx `atlas` | `personal` (context `hosted-per-user`) |
| The Worker itself (`cf-worker`) | Worker to laptop service | `personal` |
| Evaluation | local harness against the corpus and saved rankings | no client cap — it runs locally under the user's own access, not through the service |

Two properties of this table matter more than any row. First, the caps are enforced where the consumer cannot reach them: in the service's clamp, inside the branch queries, and — for the Worker — in a compile-time pin verified again before caching. Second, the table is short because the client set was kept short on purpose: Aster is explicitly not a client of this service, and there is no public or anonymous search surface at all. A new consumer joins Atlas by being named, tokened, and capped — never by finding an open door.
