Reconciliation of the 37 repairs

The 15:25 UTC operator receipt names 37 distinct tasks. Between 18:05:13 and 18:05:26 UTC, read-only requests to the active queue broker recovered exactly one persisted repaired event for each task, with 37 distinct event IDs. Every task’s payload.dedupe.checked_at matched the timestamp in the published ledger. For 29 tasks the event had the same second as the payload stamp. For eight the event had the following second. This verifies persistence for this set. Proving atomicity under a failed write requires a fault-injection fixture. Operator ledger · Repair writer

The observed queue states were 18 done, 15 blocked, three claimed and one parked. Fifteen records carried nonempty stored dependency data. Each read observed a single task and may race with subsequent transitions. The event and task detail are separate reads. The public operator ledger records the immediate queued state after repair.

The broker’s authenticated local read route accepts a per-task /events-list request filtered by kind=repaired, followed by a rich /list read restricted to the same task ID. Use the configured client credential without printing it. The CLI’s show and timeline implementations at the inspected source enumerate particular event kinds and omit repaired.
