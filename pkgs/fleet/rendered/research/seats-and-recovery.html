Seat identity, credential readiness and channel recovery

A seat can be reachable through the bridge, unable to reach the queue, and intentionally lack credential access. An operator deciding whether to assign work needs those three facts separately. This design makes the broker responsible for authorization and gives the operator a probe and a recovery owner for each dependency.

Enrolment and work ownership

The front-door design describes one intake path across kinds. Its four probes cover bridge, queue, GitHub and shell. The intake order is pushed work, queue, shortlist or refill, then priority. A claimed task can carry platform, lane, pool or model requirements. First-claim registration makes a new lane available without reserving its name in advance. Generic installation paths and bootstrap token provisioning have separate acceptance evidence. Testing one entry point cannot establish what a new installation of each supported kind receives.

Registry proposal. Use an authenticated installation ID as the seat record. Store its verified principal, kind, capability results and timestamps, repo and operation grants, policy revision and last-seen at the broker. Keep the human-facing name mutable. Bind independently verified machine IDs where available. The machine registry already owns node capacity and watchdog-observed health. A machine can run several seats. A shared service credential proves possession of that service credential alone. Preserve unverified historical identities as reported until each installation presents a verifiable enrolment receipt. Keep reported and independently verified source revisions separate.

A new kind proves the same four operations through its supported entry point. Add a metadata-only credential capability challenge where the work requires it. A seat designed for credential-free work can enrol without that grant. Enforce the required capability in the broker for direct claims, intake claims, dispatch and reads. A retry for an existing installation must return its original binding. A different installation using the same display name must receive a different ID. Exercise simultaneous registration, revocation during a lease and reinstall after a stale alias. First-claim lane registration still works. Throttle excessive new aliases per authenticated principal and recover stale ownership only after checking outstanding leases and pending transfers. An operating target for the number of busy lanes belongs in capacity planning.

Shortlist experiment. The local shortlist’s eight entries and low-water mark of three are a baseline. Record task revision and queue watermark when a candidate is handed out. Distinguish an already-dispositioned task at handout, an eligible task lost to another lane before claim, and a successful claim. Compare claims per 100 handouts, refill reads and writes, time to first successful claim, and replacement/restart behavior for host-local and seat-shared variants. Replay one time-ordered stream under both policies. Measure per rung and queue size before changing defaults. Intake tracker

Task handoff proposal. Carry immutable work identity, checkpoint digest, outstanding verification, lease epoch, sender and intended recipient. Use a broker-clock 15-minute deadline. Commit one transfer and its receipt under the original grant. Same recipient and request ID can recover the receipt after a lost response. Wrong recipient, stale epoch, altered checkpoint or late first redemption leaves the old grant unchanged. The bridge can notify the recipient while the queue retains authority over redemption. Keep worker-assigned batches. For conversation threading add an explicit parent message, retry-stable send ID, and per-recipient delivery and acknowledgment cursors. Test a replayed acknowledgment and a missing message before claiming ordered delivery. Checkpoint design · Lifecycle receipts · Delivery capability

Credential distribution and refresh

Readiness has four dimensions: process reachability, refresh activity, initial inventory readiness, and the authority and freshness of a requested entry. At the inspected November 23 handler revision, public health omits detailed refresh errors. An authorized item read during initial loading can include a diagnostic. An accepted refresh request returns HTTP 202, including when its worker skips overlapping work. Observe the sweep and the requested item before declaring a rotation complete. Handler and tests · Incident and owner

Bind every distributed credential file to immutable provider item and project IDs, owning service, intended principal, audience and required seat capability. Distinguish daemon credentials from client credentials at lookup. Ambiguous aliases fail before any file is created. Install atomically under the intended owner and private mode. Audit the protected local recovery copy by version, permission and a scoped restore canary. Return a verdict without logging values or reusable fingerprints. The transport chain may recover from a connection failure using a route with equivalent authority. A denial or expired grant terminates the lookup across transports.

A list-plus-one-get-per-entry design makes 222 provider calls at 221 items and 2,211 at 2,210 items, before retries. Size cold readiness gates from measured list time, fetch batches, installation, allowed retries and probe delay. A user-facing rollout timeout should preserve the previous usable generation. It must not repeatedly kill a cold refresh before the inventory becomes usable. Preflight an isolated listener, serialize heal and deployment per service, and journal activation intent before changing the registry pointer. Verify the running executable, generation directory, listener and authenticated client. On interrupted activation, reconcile the pointer with the durable journal and restore the previous working closure when the candidate fails. Use the registry deployment path for the real cutover.

For the deliberately deferred secrets-broker cutover, first read the active generation and build revision at the registry. Retain the known-working generation throughout an isolated cold rehearsal. Set the deployment window from that rehearsal and its measured retry allowance. Require an authorized synthetic read and complete inventory before promotion. Observe at least a second successful refresh across a heal tick after the flip, with a recorded operator and rollback target. Until those receipts exist, the proposed cutover remains open. Health-gate tracker

Qualify recovery on a disposable instance with independent control. Pause listing and then a second fetch across two heal ticks. Require a stable process, eventual completed refresh and readable synthetic entry. Restore a broken executable candidate with its executable bit set and a missing interpreter. Require the resolver to select the next candidate that actually passes its version probe, then recycle the full restored prelude. Bring up all five legs from cold and rerun the drill against the healthy stack. The second run should cause zero restarts. A warm health check leaves cold recovery open.
