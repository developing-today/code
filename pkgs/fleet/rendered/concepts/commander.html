The Commander door: Desktop Commander over MCP

The Commander door is the fleet’s public path to the Desktop Commander MCP server running on the laptop. Desktop Commander gives an AI client terminal and filesystem access to the machine it runs on; the vendor sells that reach as a metered hosted relay. The fleet instead runs its own unmetered path, end to end on its own Cloudflare account and its own hardware: a Cloudflare Worker holds the public door, a second, service-token-only door guards the bridge into the laptop, a Cloudflare Tunnel carries the traffic, and a small gateway on the laptop turns the HTTP stream back into the packaged server’s stdio.

Tracking issue: developing-today/code#13404. The Worker source is pkgs/desktop-commander/worker/; the packaged server is pkgs/desktop-commander; the laptop unit is defined in home/common/default.nix.

Source: https://github.com/developing-today/code/blob/main/pkgs/desktop-commander/worker/src/index.ts

The chain, hop by hop

AI client
  -> POST https://commander.security.cab/mcp          (the public door)
     the desktop-commander Worker: OAuth 2.1 / machine-bearer gate
  -> POST https://commander-link.security.cab/mcp     (the bridge door)
     Cloudflare Access app: service-token-only policy
  -> sandbox-link Cloudflare Tunnel
  -> http://127.0.0.1:8931/mcp on the laptop
     supergateway (desktop-commander-bridge user unit), streamable HTTP
  -> the packaged Desktop Commander (stdio), version 0.2.52
  1. The client speaks streamable-HTTP MCP to https://commander.security.cab/mcp. Hosted clients (Claude, ChatGPT) connect from their own servers; header-capable clients (Claude Code, Cursor, mcpx, and the fleet’s own fleet commander) connect directly with a bearer token.
  2. The public-door Worker (desktop-commander, pkgs/desktop-commander/worker/src/index.ts) checks the bearer, then proxies the request transparently: method, path, query, headers and body pass through, and the response — including the Mcp-Session-Id header and any SSE stream — passes back untouched. Before proxying it deletes the caller’s own credentials (authorization, cf-access-jwt-assertion, cf-access-client-id, cf-access-client-secret) and substitutes its own bridge-door service token. workers_dev is off: the custom domain is the only public door.
  3. The bridge door at commander-link.security.cab is a Cloudflare Access application with a service-token-only policy (the atlas-search pattern). Only the Worker holds that token; nothing else can present it, so the bridge door accepts the Worker’s egress and nothing else.
  4. The tunnel is the existing sandbox-link Cloudflare Tunnel: it terminates the bridge door on the laptop at http://localhost:8931.
  5. supergateway (the desktop-commander-bridge systemd user unit in home/common/default.nix, wrapping pkgs/supergateway) serves the packaged Desktop Commander in streamable-HTTP mode on 127.0.0.1:8931, path /mcp, stateful sessions, with /healthz for gateway health.
  6. The packaged Desktop Commander (pkgs/desktop-commander, @wonderwhy-er/desktop-commander version 0.2.52, built from the npm registry tarball) runs as a stdio MCP server under the gateway. It is the same package the vendor device agent runs; only the transport and the door in front of it are the fleet’s.

The fleet binary’s own client for this door — fleet commander health and fleet commander exec, tier T1 of the laptop route forms — is covered in fleet laptop route forms. This chapter is about the door itself, not that client.

The OAuth 2.1 front door

The Worker runs its own OAuth 2.1 authorization server (src/oauth.ts), because hosted clients cannot pass a Cloudflare Access login at /mcp — they arrive from their vendors’ servers, not from a browser the owner is signed into. It landed in PR #13488, superseding the original #13404 design in which the whole hostname sat behind Access and machine clients used a public-door service token; that public-door token is retired at this door (the token still exists; nothing accepts it here any more). The bridge door did not change.

  • Discovery (public): GET /.well-known/oauth-protected-resource (also under /mcp) and GET /.well-known/oauth-authorization-server. Issuer https://commander.security.cab, resource https://commander.security.cab/mcp, scope commander.
  • Registration (public): POST /register (RFC 7591). Public clients only (token_endpoint_auth_method: "none"); redirect URIs must be https or loopback http. Clients are stored in the OAUTH_KV namespace under client:<id>.
  • Authorize: GET /authorize renders the approval page (behind Access, above); approving is a form POST back to /authorize that issues a single-use authorization code, valid 10 minutes and bound to the client’s PKCE S256 challenge.
  • Token: POST /token exchanges the code (PKCE verified; a code is consumed on any attempt, successful or not) for an opaque access token valid 1 hour and a rotating refresh token valid 30 days.
  • State: codes, access tokens and refresh tokens are stored in OAUTH_KV under the SHA-256 of the presented value (code:<hash>, at:<hash>, rt:<hash>), never in the clear. Revoke a client by deleting its at: / rt: entries and its client: record from the namespace.

The machine bearer

The owner’s own tooling skips the OAuth flow with a single static bearer token, compared in constant time. Its canonical value lives in fleet secrets under the name desktop-commander.machine-bearer; the Worker receives it as the per-version secret MACHINE_BEARER, staged by the publish workflow from the GitHub environment secret of the same name. fleet commander resolves it by that fleet-secret name at call time and never stores it.

Laptop configuration (home/common/default.nix)

  • desktop-commander-bridge.service (systemd user unit): supergateway wrapping the packaged Desktop Commander — --outputTransport streamableHttp --streamableHttpPath /mcp --port 8931 --host 127.0.0.1 --stateful --healthEndpoint /healthz, restart on failure. Its start script exports the real user PATH first, because the wrapped server exists to run the user’s commands.
  • desktop-commander-remote.service (systemd user unit): the vendor device agent (desktop-commander remote). It stays running until the self-hosted endpoint is stood down as a separate recorded step; the two paths coexist deliberately.

Operations

  • Health: GET https://commander.security.cab/healthz answers {"ok":true,"service":"desktop-commander"} with no token — it proves the Worker answers, nothing about the hops behind it. End-to-end health is an MCP initialize + tools/list against /mcp with a valid bearer (fleet commander health does exactly this through the whole chain), and the laptop-local check is the gateway’s http://127.0.0.1:8931/healthz.
  • Deploys are Cloudflare version deployments from GitHub Actions, modeled on the id-mail publisher/promoter pair:
    1. Publish (desktop-commander-worker-publish.yml, manual dispatch on main, confirm_upload): runs the Worker’s tests (pkgs/desktop-commander/worker/test/ — proxy, OAuth and promote suites), a credential-free dry run, then uploads a new version with its secrets file. Uploading changes no traffic. The run emits a provenance artifact naming the exact version, tag and baseline.
    2. Promote (desktop-commander-worker-promote.yml, manual dispatch with the publish run id and attempt, confirm_promotion): verifies the run was a successful manual publish on main, checks the live deployment still matches the manifest baseline, then creates a deployment with exactly that version at 100%. Tests (desktop-commander-worker-tests.yml) also run on pushes and PRs touching the Worker directory.
  • Token rotation: rotate the bridge-door service token or the machine bearer in fleet secrets / the desktop-commander-production environment, then publish and promote a new Worker version — version secrets are per-version, so a rotation only takes effect on a version uploaded with the new values. Rotating the machine bearer also means every machine client picks the new value up by name on its next call; nothing caches it.
  • Revoking a hosted client: delete its at:<hash> / rt:<hash> entries (and its client: record) from the OAUTH_KV namespace. There is no admin UI; the namespace is the record.
  • The vendor agent stand-down is a separate recorded step on #13404, deliberately not part of any deploy: desktop-commander-remote keeps running alongside the self-hosted door until it is taken.
