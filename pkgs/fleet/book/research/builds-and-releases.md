# Remote verification, fork convergence and releases

A dispatch receipt should identify the source tree under test, command, workflow revision, image digest, runner class and assertion. A green image build, a green export and a passing workload answer different questions. Keep each result when a later step fails. ## Which environment can prove the result?

The fleet-build investigation traced failures to differences between the image's configured editor user and the root account used by the workflow. Recent upstream changes addressed Nix feature configuration, build users and the home directory used during pure evaluation. A subsequent root smoke check encountered a checkout owned by the earlier user. The correction made the smoke checkout root-owned before the root check. The branch run at `2db5a5d8` passed all eight jobs. Main's subsequent publication workflow on merge commit `95d6c5da` succeeded in run `45228189518`. A runner pulling the published digest and a consumer command succeeding still need their own receipts. The container investigation remains subject to the recorded item-specific hold. ## Convergence across the forks

In the November 23 historical sample, twelve reporting issues itemized 118 failed target attempts over 102 distinct forks and eleven distinct source SHAs. The classifications were 100 failures from missing workflow scope, 15 rule refusals on two forks and three conflicts on one fork. A thirteenth failed workflow could not post its usual report. These denominators describe recorded failures; a fleet-wide failure rate also needs successful attempts in the same window. Issue closure time measures triage. The ancestry test measures convergence. [Incident trail](https://github.com/developing-today/code/issues/12484) · [Ruleset case](https://github.com/developing-today/code/issues/12490) · [Reporter correction](https://github.com/dezren39/fleet/pull/94)

Give each observation the target repository ID, upstream SHA, attempt and timestamp. A missing workflow permission or rule exemption belongs with its owner; retry after a grant change. A transient network failure gets bounded backoff within the rate budget. A merge conflict requires target-specific review that preserves the fork's commits. Prove recovery by testing whether the triggering upstream commit is an ancestor of target HEAD. A newer push may cover an earlier failed attempt. Give incomplete traversal and reporting failure distinct outcomes. Keep the public-only fork boundary during every check.

The missing-installation case in umbrella #87 has a decision history in code #6645. Retaining central push and mirror monitoring avoids new grants and accepts recovery latency when the primary path fails. A pilot installation on selected forks could quantify recovery time and privilege cost. Broader installation needs an explicit owner decision on scopes, affected forks, rotation and removal. Retain current coverage until a measured recovery objective justifies a pilot. Verify installs by application identity and target repository. ## Membership and release acceptance

At umbrella revision `45ad3e42`, the policy and submodule declarations contained 22 unique matching path/repository pairs. The management tiers comprise one FULL member, four FULL-lite members and seventeen umbrella/autocommit members. The member table records the individual purpose and policy. Devcontainer initialization, warm builds, requested permissions and membership have separate consumers. Never infer access or initialization from a gitlink. Compare the policy, declared path/URL and actual mode-160000 tree entry at one commit. Before adding a member, record its purpose, owner, consumers, tier and removal path. When removing it, unwind consumers and indexing policy before removing the gitlink. Keep private member contents outside the public umbrella. [Membership policy and per-member ledger](https://github.com/dezren39/fleet/blob/45ad3e42/FLEET.md) · [Submodule declarations](https://github.com/dezren39/fleet/blob/45ad3e42/.gitmodules)

A proposed release manifest identifies the intended Fleet source tree, immutable static asset and SHA-256, bootstrap pin, required capabilities and book revision. Require one observation per deployed broker and operator seat, including service identity, generation, observable source revision, probe time and transition receipt. A channel may deliberately lag with a named owner, reason and next probe. Render unknown when a component cannot be reached. The book receipt should include the built chapter set, CLI surface diff, warning count and the Pages deployment revision. Generate pin text from this manifest where possible; make expired or unsupported pins visible in the currentness check. A runtime feature probe remains useful for mixed-version seats. [Publish script](https://github.com/developing-today/code/blob/1f9bc15391ca/scripts/muse/publish-fleet.sh) · [Registry deployment](https://github.com/developing-today/code/blob/1f9bc15391ca/pkgs/deploy/deploy.py) · [Release follow-up](https://github.com/developing-today/code/issues/13307)

Stage promotion as publish and verify, change the bootstrap pin, canary a registered generation, exercise cross-seat probes, then verify the book build at the corresponding revision. A rollback selects the preceding registered generation and appends its outcome. Acceptance fixtures include a wrong asset digest, a missing generation directory, a seat without the required verb, a stale documentation build and a pass with a previously declared exception. Report the observed difference for each component so that a single successful canary cannot certify the fleet.
