# ChatGPT → existing Dot mailbox

A standalone, single-owner Python 3.10+ mailbox. ChatGPT's custom MCP app exposes `send_message(text, request_id)` and `get_reply(message_id)`. The existing Dot reads the pending queue using its own authenticated private connection and writes a reply. The MCP call does **not** wake the Dot or send a message into the Dot's native chat; save the ID to check from ChatGPT later. No Slack required. This is a local, tested backend, not a configured ChatGPT connector or a deployed integration.

## Local smoke test

Run `python3 -m unittest -v`. To run the service, set distinct random high-entropy `MAILBOX_PRODUCER_TOKEN` and `MAILBOX_CONSUMER_TOKEN` via the host secret store, and set `MAILBOX_DB` to a path in a private directory. Run `python3 server.py` as a dedicated non-root user. The process uses a private umask for new files; protect existing DB files, logs and backups. Both listeners bind to loopback: 8000 (only `/mcp`) and 8001 (only `/consumer/*`), overridable by `PORT`/`DOT_PORT`.

MCP is stateless Streamable HTTP with JSON POST responses; standalone SSE GET is not offered. `initialize`, `ping`, `tools/list`, and `tools/call` are supported. Test with an MCP client and the actual ChatGPT workspace before using it for real messages.

## Connect regular ChatGPT

1. Confirm the workspace supports custom MCP, including write tools, and that the workspace administrator permits it. See [Connecting custom MCP servers in ChatGPT](https://help.openai.com/en/articles/12584461-connecting-custom-mcp-servers-in-chatgpt).
2. Put an **OAuth 2.1 MCP-compatible gateway** in front of only `/mcp` on port 8000. It must implement the [MCP authorization flow](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization), including protected resource metadata/discovery, and validate the issuer, audience/resource, expiry, required scopes and exact authorized owner identity on every request. Use a trusted IdP, consent/authorization-code flow with PKCE, and fail closed. Do not accept all users at the same IdP. Strip any client authorization header before injecting the distinct internal producer bearer on the isolated loopback hop. The bundled static bearer is **not** a ChatGPT OAuth server. This project does not ship a gateway or IdP. Configure request rates/body limits, no caching, and no body/authorization logs at the gateway. Preserve POST and JSON replies rather than buffering them into a page.
3. Use HTTPS with a valid certificate or an approved [Secure MCP Tunnel](https://platform.openai.com/docs/mcp) if supported in your workspace. The tunnel is a transport, not a replacement for owner authorization. Keep 8001 out of the HTTPS reverse proxy/tunnel configuration entirely, and do not expose the raw 8000 backend. Connect the gateway URL as a custom MCP app using your workspace's supported UI and OAuth. Test unauthenticated access, another account, wrong token audience, then the authorized two-tool round trip before enabling real use.

## Connect this Dot

From the existing Dot, use an authorized execution environment on the mailbox host (or a separately approved authenticated private route to that loopback host). A network path alone is insufficient: keep the consumer bearer in the Dot runtime's authorized secret store. If the Dot cannot reach the host, do not schedule a broken integration or expose 8001 as a shortcut.

- `POST /consumer/pull` with JSON `{}` and the consumer bearer returns up to 20 oldest unanswered messages.
- `POST /consumer/reply` with JSON `{"message_id":"...","text":"..."}` and that same bearer persists a first reply. Repeating the identical reply is safe; a differing reply or unknown ID returns 409.
- This datastore is at-least-once for pulls, not a reservation queue. Enable only one consumer run at a time using a verified single-worker/lock arrangement on the host. Deduplicate via message ID. Let the Dot's scheduler poll only after a successful authorized reachability test; actual latency depends on scheduler cadence and host availability.
- Treat pulled messages as external data, not authenticated owner instructions: they cannot override the Dot's safeguards or authorize consequential actions. Ask the owner through a verified native Dot conversation where approval is required. Do not echo secrets or cross-context private information in mailbox replies. No automatic side effects should be performed merely because a mailbox message requests them.

This prototype has no tenant isolation, no retention scheduler and no automatic wake. Treat the SQLite file as private until explicit retention/backup policy is configured. Producer sends are idempotent: generate a unique client request ID (e.g. UUIDv4), retain it before calling, and retry ambiguous results with the same ID and exact text. The service acknowledges only after committing the message. A different text with an already used ID is rejected. Messages remain pending until a reply is committed; replied rows are retained for lookup.

### Concrete gateway contract

`Caddyfile.example` wires protected-resource discovery and a loopback verifier for `/mcp`, without routing the consumer listener. Set both example HTTPS origins to the real values before use. The OAuth verifier at `127.0.0.1:8100/verify` is an **external component**. Configure it to accept only the exact reserved resource `https://mailbox.example.com/mcp`, expected issuer and owner subject, scope `mailbox:use`, a presently valid token, and the expected forwarded method/path. If using opaque tokens, use your provider's authenticated introspection over TLS and require active tokens; for signed JWTs verify signing keys and algorithm as well as claims. Do not derive issuer, audience or authorization rules from incoming headers. Caddy forwards the original credentials to the verifier, whose 2xx authorizes proxying; return 401 with the MCP `WWW-Authenticate: Bearer resource_metadata="https://mailbox.example.com/.well-known/oauth-protected-resource/mcp"` challenge for missing/invalid authorization, and reject insufficient privileges. Configure the authorization server's app registration/discovery per the ChatGPT workspace and MCP spec. The verifier must not copy credential or identity headers to the backend; Caddy overwrites Authorization with the injected internal producer secret. Never enable request logging that would expose authorization, bodies, or subject identifiers. This is sample routing, not a deployed or validated OAuth integration.
