# Public libraries and model operations

**Evidence.** The published reference reports 14 documented Go symbols and identifies one real consumer of `pkg/client`: its test exercises the daemon operation `task_get`. The chapter reports no production caller within the repository at its census. The plugin's production path is separate. Its Bun-first `plugin/core/daemon.ts` discovers the endpoint and reuses the connection, and `plugin/core/ops.gen.ts` generates method bindings from the operation table. The parity table, for example, maps `chat_completions` to `ops.chatCompletions()`. This is evidence of the published design and test, not proof of today's deployed clients. [Public Go client](https://developing-today.github.io/code/public-client.html) · [Coverage](https://developing-today.github.io/code/coverage.html) · [HTTP API](https://developing-today.github.io/code/http-api.html) · [Parity](https://developing-today.github.io/code/parity.html)

**First release boundary.** Keep the existing Go module's pre-1.0 promise. A caller constructs `client.New` with a transport, calls `Call`, `CallRaw`, or `Invoke[T]`, handles argument errors, unknown operations and HTTP failures, and can inspect `Operations`/`Operation`. The compiled client and the running daemon can come from different commits. “Generated from the same table” ensures consistency at build time; a newer client can still ask an older daemon for an absent operation. Contract fixtures should cover current/current, older/current and current/older. Distinguish local argument validation, unavailable server operations, and remote refusal in each result. The documented lookup methods return `api.Op` from an internal package. Compile a *separate module* that lists, filters and passes operation records to another function. If that caller needs the type name, expose a public alias or descriptor while preserving existing methods. [Go client](https://developing-today.github.io/code/public-client.html) · [Go module compatibility](https://go.dev/doc/modules/version-numbers)

## Model resolution, prompt, proxy, repair, hooks and administration

**Existing behavior.** The book already documents `internal/model.Provider.Generate`, named `model.providers`, ordered `model.profiles`, explicit credential variable names, `model.budget`, `model.timeout`, and per-attempt timeout. The configured provider defaults to `none`. The configuration chapter adds an important qualification: explicit model/provider requests and the legacy scripting provider's environment or installed-CLI discovery can select generation when the request permits it. The old `repair.provider` and `repair.model` settings mentioned in a fleet file are reported as unregistered. The behavioral oracle for “no model” must count every attempted outbound call and CLI spawn. Reading `model.provider` alone cannot prove it. [Configuration](https://developing-today.github.io/code/configuration.html) · [Consumer](https://developing-today.github.io/code/consumer.html)

**One resolution path.** For every model-consuming operation, resolve the ordered candidates from the existing provider/profile configuration and explicit request. Intersect with caller sensitivity ceiling, eligible plan endpoints, total deadline and remaining quota. Require explicit eligibility for the selected route, including plugins, compatible remote endpoints and legacy CLI providers. Resolve credential references only after eligibility and keep values in process. Expose configured profile ID, selected provider/model, configuration revision, selection reason and measured or unknown usage. A 402 terminates model work for that request. A subsequent candidate is eligible after an unstarted or known-safe failure only within the same authorization, quota and deadline. Once a streamed response is partially delivered, retain partial status and stop. Mark usage unresolved if a provider never delivered the final usage frame. [OpenAI streaming reference](https://developers.openai.com/api/reference/resources/chat)

* **A 402 currently advances a model profile.** The HTTP adapter formats any non-2xx as a plain error containing the upstream body. The profile router appends every unsuccessful attempt and advances. Its per-profile token budget caps each attempt's requested tokens separately; it is not a meter of plan eligibility or the profile's cumulative spending. The existing positive-control test makes a 503 advance to the second fake provider. The raw chat proxy separately forwards upstream HTTP status and body and has one upstream for its request. * **Feedback has two working consumers.** The dashboard reads interactions and posts score/notes. Its stats tabs request the daemon's stats route. The semantic ranker uses separate execution and retrieval multipliers on the combined keyword/vector score. There is a concrete join defect for ratings: the call path stores `server:tool`, proxy-injected tool names use `namespace__function`, and rank lookup uses `namespace.function`. The store uses substring matching over serialized tool names. Even with the same spelling, similarly named tools can borrow one another’s scores. A proposed correction is to store source-native, exact tool identities separately from display names, settle aliases when the call/catalog mapping is still available, and match exact identity. Read old rows using their known source format only when their lookup is unambiguous. Keep unresolved historical records visible without using them to weight a tool. Test a custom namespace, one tool whose name prefixes another, and an unrelated caller-supplied proxy function. One trace's feedback must affect only its identified tool. The synchronous tool handler records serialized arguments and successful results for non-dry-run calls. The proxy stores the user query and up to 1 MiB of the upstream reply. The source branches contain no recording-consent check. A bounded copy still contains content. Keep trace ID, stable tool identity, scores and duration for local ranking and stats. Offer optional content capture only with explicit scope, short retention, and the authorized reader’s access; a secret-bearing scope suppresses content before the store, logs and dashboard receive it.
