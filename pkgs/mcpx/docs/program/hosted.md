# Hosted servers, protocol revisions and release channels

The official MCP site names 2026-07-28 as current. For this revision, Streamable HTTP uses a POST per request, does not define protocol sessions or GET/Last-Event-ID redelivery, and uses response-stream closure to signal cancellation. Previous handshake-based versions have a different contract. The following branches belong in lifecycle code and the book. The [active laptop service](runtime.md) reported version 0.1.0. Its store output differs from the CLI output; the source commits associated with both binaries are unknown. The existing era-probe chapter already specifies per-server mode, cache and lane handling. Issue #1414 already restricts persisted state to legacy streamable HTTP and proposes reusing the takeover restore path. The restart versus explicit-end split landed in [PR #10755](https://github.com/developing-today/code/pull/10755). Verify both branches on the current release and add failure coverage for interrupted calls. For interrupted mutation record uncertainty; cancellation cannot undo a committed side effect. | Current-revision fixture sees no GET-resume, legacy session header or DELETE and no duplicate mutating invocation. | Legacy session-capable Streamable HTTP (2025-11-25 example) | Scope previous session affinity to instance/server, canonical endpoint, credential principal, protocol revision and compatible generation. Try a harmless request first. Session 404 requires fresh initialization, optional replay is GET + cursor for the exact previous stream; clear invalid affinity on endpoint/principal change. On retirement request DELETE where supported, accepting 405 as unsupported. | Fixture logs original and fresh initialization, valid cursor confined to its stream, correct cleanup, zero duplicate write POSTs during session loss. |
| Legacy separate HTTP+SSE transport | Reconnect and negotiate new connection under the declared compatibility policy. | Fresh connection advertised; client sees explicit loss of pending response, resubscribes only authorized subscriptions. |
| No mutual protocol version | Reject candidate at compatibility check, leave previous admitted route active where its authority is still valid. | Existing consumer continues using pinned generation, refused candidate visible in status. |

**Deployments.** For a hosted upstream store the declared URL, registry origin/publisher/name/version, expected release identity or digest, supported protocol range and compatibility requirement for stored data. Distinguish registry evidence, operator-supplied deployment evidence, and self-reported server information in inspection output. An immutable manifest can still point at mutable code behind a stable URL. An observed version is not certified by an unsigned serverInfo response. Use a dedicated version URL or provider deployment evidence joined to a signed release record for strong pinning. Credential selection must bind to the approved resource at each endpoint; deny an unapproved origin introduced by redirect or discovery.

Canary using a test principal with a minimal ceiling. Verify protocol discovery, expected tool/schema fingerprint, a curated read-only smoke call when expressly permitted, and denial of a prohibited tool before route promotion. Reverse the local routing generation if the old target remains independently addressable and compatible. Changing the declared version label for the same mutable URL cannot roll back the server. A provider rollback creates a new deployment and needs its deployment owner/credentials and compatibility evidence. A Worker rollback does not roll back bound data; a binding deletion or Durable Object class change may make it impossible. Refuse a downgrade requiring data recovery until the operator supplies a compatible release or a separately approved recovery. [Cloudflare rollbacks](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/) · [MCP Registry FAQ](https://modelcontextprotocol.io/registry/faq)

**Cold shutdown intent, #1414 Phase 3.** The explicit restart/end split already landed in [PR #10755](https://github.com/developing-today/code/pull/10755). The open tracker calls for a [current-main done check](https://github.com/developing-today/code/issues/1414#issuecomment-7071764863). The following extends the verification contract. An explicitly planned frontend restart retains eligible legacy session records until the successor checks generation and principal; permanent removal/stop performs a bounded DELETE and clears the affinity. Distinguish host termination with unknown intent in status and choose the documented operator policy; never guess removal from SIGTERM alone. Cap retained record lifetime by upstream expiry when known and a configurable local retention budget. Keep `savedAt` distinct from last successful reuse. Verify takeover refreshes the same persisted structure without writing headers or access tokens. Include reboot, expired record, stale config, changed principal and denied reconnect in the matrix. Display counts of fresh, resumed, forgotten, rejected and cleanup-deferred sessions; classify 401/403 as authorization findings and require the authorized resolver before retry. A test fixture acknowledges an invocation then drops its response; assert the invocation was never blindly replayed. Check newest #1414 comments for recorded answers before implementing any policy.

**OAuth.** Treat a client calling MCPX /mcp and MCPX calling each upstream as independent grant relationships. Use resource metadata discovery, scope and audience validation for the negotiated authorization profile. Reauthentication and refresh are scoped to the resource and principal; do not forward incoming bearer tokens to upstream services. Expose status through credential-reference name, reason and required action, never token value or OAuth callback data. Build the issue's conformance matrix with a dated profile, inbound/outbound role, scenario, expected wire/event outcome and evidence. Cannot infer any conformance count from the issue number alone. [MCP authorization, 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)

**Release-channel gate.** Derive promised OS, architecture, package format, channel and exact install invocation from the book. For every advertised tuple require a publish owner, immutable release locator/digest, compatibility metadata and supported smoke venue. In clean dispatched environments, resolve the published channel, verify artifact identity, install to an isolated prefix, report version and run a harmless isolated discovery exchange. Test the previous release locator as downgrade target. Track publish failure separately from entitlement or runner failure. Until owner and actual assets are verified, mark unsupported channels explicitly in the chapter. No CNAME, login or billing changes are prerequisites for these dry probes.

**Implementation order.** First pin the issue definitions, current source, release artifacts, owner and live listener inventory. Record both protocol-era fixtures and in-flight duplicate-execution oracle. Then add compatibility-aware read-only discovery, generation diff/status, supervisor attach protocol and crash fixtures, and finally canary rollout per server. Run lifecycle tests through Fleet on a venue supporting Unix sockets and child process lifetimes. Run an isolated systemd venue for cgroup/socket activation and controlled tailnet for multi-instance hostname/deadline behavior. Record run/ref/oracle per fixture; a venue failure is classified independently.
